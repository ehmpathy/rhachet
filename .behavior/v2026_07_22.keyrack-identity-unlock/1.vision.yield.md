# vision — keyrack identity unlock via the ssh-agent passphrase ux

## tl;dr — the feasibility verdict up front

the wish asks: *"use the native os ssh-agent unlock password prompt if the ssh key has a
passphrase … prove out whether that's possible first, then build it out or articulate why
not."*

the honest answer, held as two facts:

> **the ssh-agent UX is achievable — just not by "age uses the agent."**
>
> - **the obvious route is blocked.** `age` deliberately does not support ssh-agent (age(1)
>   man page, verbatim). the agent only *signs*; age decryption needs ECDH (ed25519) or
>   OAEP-decrypt (rsa), which the agent cannot do and whose key it never exports.
> - **a real route exists: sign-as-KDF.** the agent's one operation — a *signature* — is
>   deterministic for ed25519 keys. so keyrack ferries an agent *signature* (never the key)
>   into a KDF and **derives an age identity `K` directly from it** —
>   `K = ageIdentityFromSeed( HKDF( agent.sign(challenge) ) )` — then decrypts the manifest
>   with `K`. `K` is **never stored**: it is re-derived each unlock from the signature. the
>   native passphrase prompt comes from `ssh-add` when it loads the key into the agent.

**proven on the wisher's machine (2026-07-22 / -23)** via `rhx keyrack.agent.probe`:
ed25519 agent signatures are byte-identical across calls, per-owner sockets isolate, and
the ephemeral teardown leaves zero reuse window. so the path is not just argued — its crux
is empirically demonstrated here.

two places in our own codebase falsely claim "age uses ssh-agent — no passphrase prompt
needed." those claims are **false** — age never touches the agent — and the correction is a
deliverable.

---

## the shape of the design (five decisions, all settled with the wisher)

| # | decision | in one line |
|---|----------|-------------|
| **q1** | **sign-as-KDF, derive-not-store** | ferry an agent *signature* into a KDF to **derive** the age identity `K` (never mint+store a secret); age can't use the agent, this can |
| **q2** | **gnome askpass dialog, mandated** | prompt via `ssh-askpass-gnome`, never the tty — a keylogger mitigation |
| **q3** | **drop the `age` binary (ed25519 path only)** | decrypt via the npm age library on the ed25519 path; rsa/ecdsa retain the `age` binary (NARROWED at i028 — see the q3 correction block below) |
| **q4** | **ed25519-only for v1** | not a weaker key — the strongest modern default (~128-bit, ≈ rsa-3072) and the only *deterministic-by-design* one; ecdsa is excluded for its random nonce, not its strength |
| **q5** | **ephemeral, per-invocation agent** | prompt each invocation, agent dies with the process, zero reuse |

these five compose into one coherent flow, described next.

---

## the recommended path — ephemeral sign-as-KDF (derive-not-store)

### the mechanism

ed25519 agent signatures are deterministic (RFC 8032 — same key + same message → same
bytes), so the same signature seeds the same age identity every time:

```
K = ageIdentityFromSeed( HKDF( sshAgent.sign(key, "keyrack-unlock-v1:<manifest-id>") ) )
```

only the holder of the key (via the agent) can reproduce that signature, so only they
derive `K`. the wiring (**derive-not-store**):

1. the host manifest is encrypted **to `K`'s recipient** in stock age (npm library — no
   bespoke crypto on the manifest).
2. **no secret is stored.** `K` is not on disk, wrapped or otherwise — it is re-derived
   from the agent signature on every unlock.
3. unlock → agent signs the challenge → derive `K` → decrypt the manifest via the npm age
   library.

this is the correction to the earlier "Variant A" design, which minted a *random* `K` and
stored its secret **wrapped** in a sidecar file (`keyrack.host.wrapped-identity.age`). that
sidecar was pure liability: a second file to keep in sync with the manifest, a half-migrate
desync hazard, and a stored secret where none is needed. because the signature is
deterministic, `K` can be **derived** instead of **minted+stored** — so the sidecar is
deleted outright and the only on-disk artifact is the manifest itself.

> **why `K` at all, if we still prompt for the ssh key?** age is recipient-based (X25519);
> the agent can only *sign*, never ECDH-decrypt, so age cannot open an ssh-recipient stanza
> via the agent. deriving `K` from the signature gives age a recipient it *can* open while
> keyrack never touches the raw private key — the security property the wish's "via the
> agent" framing implies. the alternative (decrypt the ssh key in-process, keep the ssh
> recipient, no `K`, no migration) was weighed and **not** chosen: it holds raw key material
> in keyrack's memory, which the agent-only path avoids.

### the ephemeral flow (q5) — where the native prompt comes from

each `keyrack unlock` invocation:

1. spawns a **throwaway** ssh-agent, scoped to that one process (its own `0700` socket).
2. runs `ssh-add <key>` into it → the **native passphrase prompt** (the gnome dialog, q2).
3. the agent now holds the key; keyrack asks it to sign; derives `K` from the signature;
   decrypts the manifest.
4. on process exit, the agent is killed and the socket removed.

so the key lives — in memory, in an agent — only for the span of that one command. the
prompt appears **once per invocation**, not once per session.

### why ephemeral, not "ask once per session"

the wish is internally tense — *"ask each time"* vs *"over retype … over and over."* a
**persistent** agent would satisfy the second reading (later signs succeed silently, "ask
once, then cached") — but it leaves a **reusable socket**: any process on the box that can
reach `SSH_AUTH_SOCK` can sign the keyrack challenge and unlock the **entire manifest**, no
passphrase, for as long as the key sits in the agent. a loaded agent is a *master key*, not
a single grant.

the wisher chose the **ephemeral** shape to close that window entirely. the accepted trade:
a clean native prompt on **every** invocation, in exchange for **zero reuse** — the key
cannot outlive, or be borrowed from, the command that asked for it. (users who genuinely
want a session cache have the daemon-cache fallback below; the persistent-agent knobs
—`ssh-add -t` short ttl, `-c` confirm-each-use, parent-session-bound agent — are documented
alternatives, not the default.)

this also vindicates the prior `.dream`'s "temp ssh-agent per invocation" instinct: it was
the *secure* shape all along; its only error was to expect *age* to then use the agent —
sign-as-KDF is the piece that makes the loaded key usable.

### the passphrase prompt — mandate the gnome askpass dialog (q2)

keyrack loads the key with `SSH_ASKPASS=/usr/lib/openssh/gnome-ssh-askpass` and
`SSH_ASKPASS_REQUIRE=force`, so the passphrase is typed into the **gnome dialog**, never the
terminal. rationale + full detail: `.agent/repo=.this/role=keyrack/briefs/define.why-ssh-askpass.md`.

- **why mandate it — keylogger mitigation.** the passphrase unlocks the key that unlocks the
  whole manifest. the plain CLI `Enter passphrase for …:` line is typed into the tty, where
  a terminal keylogger or a compromised shell can capture it. the dialog keeps it **off the
  tty**. this alone justifies the mandate. (man7 ssh-add(1); Baeldung.)
- **why Wayland-native.** X11 has **no input isolation between clients**, so a dialog drawn
  via XWayland could be snooped by another local X11 app — which forfeits the mitigation.
  `ssh-askpass-gnome` is GTK, so on COSMIC it renders as a Wayland-native client the
  compositor isolates. (this is why the ugly `x11-ssh-askpass` is not just ugly — it is
  unsafe here.)
- **only `ssh-askpass-gnome` for v1.** keyrack detects `gnome-ssh-askpass` on PATH and at
  `/usr/lib/openssh/gnome-ssh-askpass`. explicitly unsupported, each for a concrete reason:
  `gcr-ssh-askpass` refuses a direct run (private to `gcr-ssh-agent` — seen fail on the
  wisher's box 2026-07-23); `x11-ssh-askpass` is XWayland-snoopable; `ksshaskpass` /
  `lxqt-openssh-askpass` are deferred until a kde/lxqt user needs them.
- **absent → fail fast with the fix**, never drop to the tty: `sudo apt install
  ssh-askpass-gnome`. it is **safe + official** — part of the OpenSSH source, split out of
  `openssh-client` only to keep GTK+ off the base client. ([Debian package](https://packages.debian.org/stable/ssh-askpass-gnome);
  [gnome-ssh-askpass(1)](https://manpages.debian.org/unstable/ssh-askpass-gnome/gnome-ssh-askpass.1.en.html).)
- **boundary**: the dialog only renders the prompt; keyrack keeps its own throwaway agent
  and must **not** hand the key to the persistent `gcr-ssh-agent` (that would hold the key
  from login onward and defeat per-invocation unlock).

### drop the `age` binary (q3)

under derive-not-store the manifest is encrypted to the derived X25519 identity `K`, so it
is always an `age1`/X25519 stanza the npm `age.Decrypter` reads — regardless of the user's
ssh key type. the ssh key only gates the *derivation* of `K`, never the manifest stanza. so
the `decryptWithAgeCLI` path (`ageRecipientCrypto.ts:150–181`) and its false "age uses
ssh-agent" comments are **removed** as a deliverable. (residual: a legacy manifest made with
explicit `--stanza ssh` needs a one-time re-encrypt to `K` on migration; derive-not-store
makes all *new* manifests X25519 by construction.)

> **CORRECTION — q3 was NARROWED at i028, NOT fully honored.** "drop the `age` binary"
> holds ONLY for the ed25519 / derive-not-store path. when the wisher chose to build the
> **rsa/ecdsa** support (i028, an expand-v1 decision), that path DELIBERATELY retains the
> `age` binary: a passphrased rsa/ecdsa key is stripped via the gnome dialog
> (`ssh-keygen -p`, honors SSH_ASKPASS) into a decrypted copy, which `age -d -i` then reads
> — because no in-process X25519 map exists for rsa/ecdsa (see the "rsa/ecdsa path" edgecase
> section). so `age` is a hard dependency for the rsa/ecdsa population and `decryptWithAgeCLI`
> is RETAINED (not removed) for them. do NOT re-propose a wholesale removal of the `age`
> binary — it would break rsa/ecdsa unlock. the ed25519 majority still needs no `age` binary.

### the invariant the earlier design missed — owned vaults seal to the manifest recipients

**owned-vault secrets (os.secure, os.direct) are each encrypted to the SAME recipients the
host manifest is** (`vaultAdapterOsSecure.set` → `encryptToRecipients(context.hostManifest
.recipients)`; `.get` decrypts with the manifest identity). so the manifest recipient is not
a property of one file — it is the shared seal over the manifest **and every owned-vault
credential beside it**.

the load-bearing consequence, absent from the original vision and the cause of a real
half-migrate brick (2026-07-30): **any change to the manifest recipient must re-key every
owned-vault blob in the same operation.** re-seal the manifest to `K` but leave the os.secure
credentials on the old recipient, and the next fresh unlock derives `K`, opens the manifest,
then **fails to open the credentials** (`no identity matched any of the file's recipients`).
this invariant is persisted at
`.agent/repo=.this/role=keyrack/briefs/rule.require.os-secure-seals-to-host-manifest.md`.

### migration is in-place and atomic (legacy → derive-not-store)

a legacy manifest (encrypted to the raw ssh recipient) still needs a one-time migration to
derive-not-store, because `K`'s recipient ≠ the ssh recipient. the migration is therefore a
**full re-key**, and it is **snapshot-then-rollback + all-or-nothing** so a crash never bricks
the keyrack:

- migration decrypts the manifest **and every owned-vault (os.secure) blob** with the legacy
  (session) identity, then re-encrypts every one of them **in place** to the derived `K`.
- the whole re-key runs under `withKeyrackHostFilesSnapshot`: each present host file is copied
  to a `.snapshot-bak` neighbor first, the blobs are re-keyed, and the **manifest is written
  LAST** (atomic write) as the completion marker. a mid-flow failure restores every file from
  its backup; a hard kill leaves the `.snapshot-bak` set, which the next run treats as the
  authoritative pre-mutation state and restores from — so the manifest and its credentials can
  never desync onto different recipients (rule.require.os-secure-seals-to-host-manifest).
- there is **no second `keyrack.host.v1.age` file** and **no `wrapped-identity` sidecar** — the
  manifest keeps its bare name `keyrack.host.age`, `K` is derived (never stored), so a migrated
  keyrack is manifest-only and the file the wisher objected to never exists.

> **which legacy shapes the seamless migration serves.** the honest map of producible legacy
> shapes and their FIRST-unlock behavior:
>
> | how the legacy manifest was made | its recipient shape | first-unlock behavior |
> |---|---|---|
> | `init` with a **passwordless** ed25519 key | pubkey-derived `age1` (X25519) | decrypts **in-process**, works; migration no-ops (cipher `none`) — already the end-state |
> | `init` with a **passphrased** ed25519 key | **raw `ssh-ed25519` stanza** (age-cli path) | **SEAMLESS in-place migration** — a legacy decrypt tier opens the raw-ssh seal via the ed25519 key (gnome-dialog strip + `age -d -i`), then fix-forwards to K. two prompts on the first unlock (strip, then re-derive), single native dialog every unlock after |
> | manual `recipient set` of a **passphrased** ed25519 pubkey | pubkey-derived `age1` (X25519) | a passphrased key cannot open a pubkey-`age1` seal in-process, so `get()` → **re-init** message (the niche shape is named, not the generic `--prikey` misdirect) |
>
> the second row is THE seamless-backcompat path (wisher-expanded scope: a pre-feature user must
> NOT rebuild the host from scratch). two prod changes make it work: (1) a legacy decrypt tier in
> `genContextKeyrack.getOne` returns the age-cli marker for the ed25519 key when the manifest is
> raw-ssh-sealed (`isAgeCiphertextSshSealed`), gated strictly so a K-sealed manifest never strips;
> (2) the migrate gate is broadened (`isSameSshPubkey`) to fire for the raw mech-`ssh` recipient,
> not only the pubkey-`age1` shape. proven end-to-end through the compiled CLI
> (`keyrack.legacy-rawssh-migrate.acceptance.test.ts`): first unlock decrypts + fix-forwards
> (⛵ banner, 2 prompts, manifest re-sealed X25519), second unlock is the plain single-prompt
> native path. the age-cli posture banner is key-type-NEUTRAL (`🔓 unlock via age-cli · …`), since
> a legacy ed25519 key also rides that path on its one-time first decrypt.
>
> the THIRD row (pubkey-`age1` from a manual `recipient set`) stays a re-init message: unlock's
> `get()` cannot decrypt that shape in-process to reach the migration, and it is a niche
> non-`init` shape. the migrate re-seal for it is still exercised at the domain grain (its
> integration test drives the function directly). a seamless path for it is a documented
> fast-follow, not a v1 guarantee.

> **accepted risk — no concurrent-writer lock (v1).** the re-key (`setKeyrackManifestRecipientsSealed`,
> shared by the unlock-triggered migration and a manual `recipient set`) carries no advisory
> lock or version field, so two simultaneous writers race last-writer-wins. the atomic file
> write prevents a *torn* ciphertext, but not the *loss* of one operation's re-key if two run
> at once. keyrack is a single-user local tool, so this is a knowingly-accepted v1 residual, not
> an oversight; a lock/version guard is a fast-follow if keyrack ever grows a multi-writer surface.

> whether the wisher's own single legacy manifest is migrated in place or simply re-`init`ed
> fresh (only user, few credentials) is an operational choice for the build phase, not a
> design constraint here.

### migration fires on `unlock` only — by design (not the shared prelude)

the migration is called from the `unlock` subcommand alone, **not** the shared
`genContextKeyrackFromCliOpts` prelude that `set`/`del`/`list`/`recipient`/`fill` also use.
this is a deliberate decision, not an oversight:

- **why unlock-only**: migration is a full re-key — it re-seals the manifest AND re-encrypts
  every os.secure blob, and it fires the passphrase dialog to derive `K`. `unlock` is the one
  command whose contract already means "prove your identity now," so a prompt + a whole-file
  re-key there is expected. a prelude call would make a bare `keyrack list` (or a narrow
  `set`/`del`) trigger a passphrase popup and a full re-key as a hidden side-effect of a
  read-shaped command — a `rule.forbid.surprises` counter-hazard.
- **the accepted residual**: a user who touches a legacy manifest only via non-`unlock`
  commands stays on the legacy age-cli dialog-strip path until their first `unlock`. that path
  is already correct (it uses the same gnome dialog, never the tty) — it simply has not yet
  converted to derive-not-store. the conversion is deferred to the natural "prove identity"
  moment, not forced onto every command.

### migration test coverage — domain-proven; CLI-end-to-end bounded by a hermetic limit

migration is proven at the **domain grain** (`migrateKeyrackManifestToVariantA.integration.test.ts`:
decrypt-with-legacy → re-key every os.secure blob → re-seal the manifest under the
snapshot/rollback primitive; the ⛵ banner pinned; the re-derive prompt-count asserted at
exactly one). a dedicated **blackbox CLI** migration test is NOT added because the only
realistic legacy shape — a passphrased ed25519 manifest — decrypts through `age -d -i`, which
reads the passphrase from `/dev/tty` and ignores `SSH_ASKPASS`, so a compiled-CLI migration of
it cannot be driven hermetically (the same tty barrier accepted for the rsa/ecdsa interactive
UX). the domain-level proof + the prompt-count guard cover keyrack's part end-to-end short of
that un-drivable tty read.

## the outcome world

### day-in-the-life

vlad opens a terminal and runs:

```
rhx keyrack unlock --owner ehmpath --env test
```

his `~/.ssh/ehmpath` key has a passphrase. a clean **gnome dialog** pops:

```
🔐 unlock ehmpath identity
   └─ passphrase for ~/.ssh/ehmpath:  [ ******** ]   (gnome askpass dialog)
```

he types it once. keyrack spins up a throwaway agent, loads the key, signs the challenge,
derives `K` from the signature, decrypts the host manifest, then **tears the agent down**
— and renders:

```
🔓 keyrack unlock
   ├─ ehmpathy.test.XAI_API_KEY
   │  ├─ env: test
   │  ├─ org: ehmpathy
   │  ├─ vault: os.secure
   │  └─ expires in: 540m
   └─ ...
```

the credentials are unlocked (per keyrack's normal grant ttl); the *ssh key itself* was held
only for that command. a later `keyrack unlock --env prep` prompts again — a fresh dialog,
another one-shot unlock.

### before / after

| | before (today) | after (this wish) |
|---|---|---|
| passphrase prompt | garbled, over a piped `age -d` invocation | one clean gnome dialog, off the tty |
| where the passphrase is typed | the terminal (keylogger-reachable) | a Wayland-native dialog (isolated) |
| reuse window | n/a (age re-prompts each time anyway) | **none** — the key dies with the invocation |
| external dependency | requires the `age` binary for encrypted keys | absent — npm age library, no `age` cli |
| the mental story | "why does it keep asking, and why is the prompt broken?" | "it asks me cleanly, like ssh does, and never lingers" |

### the "aha" moment

two moments, not one. first: the prompt is a **clean native dialog**, not a garbled pipe.
second — the deeper one — the security click: *"it unlocked, did its job, and the key is
already gone. no other process on my machine can reuse it."* the value is the **absence** of
a lingering credential, felt the moment the agent tears down.

## user experience

### usecases / goals

- **u1**: unlock keyrack credentials whose host manifest is protected by a **passphrased**
  ssh key, via the ssh-agent passphrase ux rather than a re-typed, garbled prompt.
- **u2**: get a trustworthy, non-garbled passphrase prompt.
- **u3** (the security goal the wisher raised): the unlock must **not** leave a credential
  another process can reuse — unlock is for that one invocation only.

> note: to drop the `age` binary dependency (q3) is a *derived benefit* of the mechanism,
> not a standalone wisher goal. it is listed under pros.

### contract inputs & outputs (proposed — testdrive)

no new command surface; the change lives *inside* the current `keyrack unlock` flow.
observable contract:

```
$ rhx keyrack unlock --owner ehmpath --env test
🔐 unlock ehmpath identity              # gnome askpass dialog, typed once
🔓 keyrack unlock
   ├─ ehmpathy.test.XAI_API_KEY
   │  ├─ env: test
   │  ├─ org: ehmpathy
   │  ├─ vault: os.secure
   │  └─ expires in: 540m
   └─ ...

$ rhx keyrack unlock --owner ehmpath --env prep   # a fresh invocation
🔐 unlock ehmpath identity              # prompts again — per-invocation by design
🔓 keyrack unlock
   └─ ...
```

if `ssh-askpass-gnome` is absent, the flow fails fast with the install command rather than
a tty fallback:

```
$ rhx keyrack unlock --owner ehmpath --env test
✋ keyrack needs a graphical passphrase dialog, and none is installed
   ├─ why: the dialog keeps your passphrase off the terminal,
   │        where a keylogger or compromised shell could capture it
   └─ fix: install the official openssh dialog, then retry —
          sudo apt install ssh-askpass-gnome
```

(a `ConstraintError` — the human must install the dialog; exit code 2, per
`rule.require.exit-code-semantics`.)

### timelines

1. `keyrack unlock` needs the host manifest → needs `K` → needs the agent signature.
2. spawn the throwaway agent (its own `0700` socket).
3. `ssh-add <key>` → the gnome dialog → the human types the passphrase once.
4. the agent signs the challenge → derive `K` from the signature → npm-decrypt the manifest.
5. tear the agent down; the ssh key is gone from memory.
6. keyrack proceeds with its normal credential-grant lifecycle (the grant ttl is unchanged
   and independent of the ssh key).

## mental model

- **how a human describes it to a friend**: *"keyrack unlocks with my ssh key. if it has a
  passphrase, a little dialog asks me — like unlocking a key — and the key is only used for
  that command, never left sitting around."*
- **analogy**: `ssh-add` with a short leash — you unlock the key to do one thing, and it is
  released immediately after. the wisher's own framing: *"only unlock it for that one
  invocation."*
- **terms**: users say *"my ssh key,"* *"my passphrase,"* *"the popup."* internally we say
  *"agent signature,"* *"sign-as-KDF,"* *"the derived age identity `K`,"* *"ephemeral
  agent."* the gap to manage: the user pictures "ssh-agent remembers it"; we must **not**
  promise a session cache, because the ephemeral shape deliberately has none. describe it as
  *"asks each time, cleanly, and never lingers,"* never *"remembers it for the session."*

## evaluation

### how well does it solve the goals?

- **u1 (ssh-agent passphrase ux)**: solved — the native dialog + agent signature *is* the
  ssh-agent ux, achieved without the impossible "age-uses-the-agent" route.
- **u2 (clean prompt)**: solved — the gnome dialog replaces the garbled piped `age` prompt.
- **u3 (no reusable credential)**: solved — the ephemeral teardown leaves zero reuse window
  (proven by the probe's failed 2nd sign after teardown).

### pros

- removes a false claim and a broken (garbled-pipe) ux from the codebase.
- removes the `age` binary dependency (q3).
- the passphrase never touches the tty (keylogger mitigation, q2).
- **no lingering credential** — the strongest security posture of the options considered.
- the manifest stays stock age (npm library); only a tiny `K`-wrapper is bespoke crypto.

### cons / costs

- a native prompt on **every** invocation — the deliberate cost of zero reuse (q5). users
  who want a session cache must use the fallback.
- **ed25519-only for the sign-as-KDF derive** (q4). rsa/ecdsa still get the clean gnome
  dialog via the age-cli strip path (not the ephemeral-agent zero-reuse property). FIDO/sk-
  is unsupported in v1 — it fails fast with a swap-key BadRequestError (NOT the fallback;
  see the edgecase table for why the daemon cache cannot serve it).
- requires `ssh-askpass-gnome` installed; keyrack fails fast to guide the install rather
  than degrade to the tty.
- a small amount of bespoke crypto (the `K`-wrapper) keyrack owns and must test carefully.
- the **Node→agent link** is RESOLVED (was: "the one leg not yet proven end-to-end").
  `getOneAgentSignature` shells `ssh-keygen -Y sign` against the ephemeral agent's
  `SSH_AUTH_SOCK` — and `ssh-keygen -Y sign` routes the sign THROUGH that agent, so it is
  the shipped, PERMANENT mechanism, not a temporary probe stand-in. proven end-to-end by
  `getOneAgentSignature.integration.test.ts` and the `keyrack.passphrase` acceptance suite,
  which drives the full spawn → prompt → sign → derive → teardown path through the compiled
  CLI. one KNOWN cross-version RISK remains, tracked next.
- **known risk — PEM SSH-SIG envelope drift (v1-accepted).** the KDF hashes the whole PEM
  SSH-SIG armor `ssh-keygen` writes, not the parsed raw signature payload. an ed25519 sig is
  deterministic (RFC 8032), but the PEM envelope (line-wrap, headers) is an OpenSSH
  serialization detail — an OpenSSH build that changed it would derive a DIFFERENT wrap key,
  so identities sealed under the old serialization would fail to unwrap. it fails LOUD (the
  scrypt tag rejects → the wrong-key ConstraintError), never a silent corrupt, but presents
  as an unexplained lockout until the human re-seals. same-process determinism is proven
  (keyrack.agent.probe); cross-version is not. the mitigation (hash the structured SSHSIG
  payload, not the envelope) is a fast-follow. documented at `getOneAgentSignature.ts` header.

### edgecases & pit-of-success

| edgecase | pit-of-success behavior |
|---|---|
| key has no passphrase | in-process ed25519→age convert; never prompt |
| passphrased **rsa/ecdsa** key | NOT sign-as-KDF (q4 = ed25519-only for the derive), but v1 STILL gives it the gnome dialog: keyrack strips the passphrase via the dialog (`ssh-keygen -p`, which honors SSH_ASKPASS) and hands `age -d -i` the decrypted copy — never the garbled tty prompt. the manifest seals to a raw `ssh-rsa`/`ssh-ecdsa` recipient decrypted through the `age` binary (no in-process X25519 map exists for rsa/ecdsa) |
| passphrased **FIDO/sk-** key | out of scope for v1 → fail fast with a BadRequestError that names the fix (init with an ed25519 or passphrase-less key). CORRECTED from an earlier draft that said "falls to the daemon-cache fallback" — that is WRONG: the daemon cache only holds a grant AFTER a successful unlock, so a FIDO-only user can never reach it. its private half lives on the hardware token, so ssh-keygen -p cannot strip it, age -d -i cannot decrypt with it, and its signature is non-deterministic (sign-as-KDF is out). shipped in `sshPrikeyToAgeIdentity.ts` (isFidoSshKeyType guard), pinned in `sshPrikeyToAgeIdentity.cli.integration.test.ts` case6 |
| wrong passphrase entered | the load fails loud on the first wrong attempt — a caller-fixable ConstraintError whose hint says retry on a local desktop; there is NO in-place retry loop (matching the ephemeral, zero-cache design). the user re-runs `keyrack unlock`, which re-prompts fresh. on a wrong passphrase keyrack derives no `K` and caches no identity |
| `ssh-askpass-gnome` absent | fail fast with the exact `apt install` fix; never drop to the tty |
| headless / ci / over ssh (no display) | no gnome dialog → fail fast with guidance (the recommended path is a local-desktop feature); ci uses the fallback |
| agent teardown races the sign | the sign completes before teardown within the one process; a crash mid-flow just means the next invocation re-prompts — no partial state persists |

### the rsa/ecdsa path — gnome dialog + age binary (NOT in-process, NOT sign-as-KDF)

a passphrased **rsa/ecdsa** key cannot back sign-as-KDF (the deterministic derive is
ed25519-only, q4) and cannot convert to an X25519 age identity in-process (no birational
map exists the way ed25519 has). so its manifest seals to a raw `ssh-rsa`/`ssh-ecdsa`
recipient and decrypts through the `age` binary — the one population for which q3's "drop
the age binary" does **not** hold. but the wish's core complaint (the garbled tty prompt)
IS fixed for it: because `age -d -i` reads a key passphrase from `/dev/tty` and ignores
SSH_ASKPASS, keyrack first strips the passphrase via the SAME gnome dialog (`ssh-keygen -p`,
which honors SSH_ASKPASS like ssh-add) into a decrypted copy in a private 0700 dir, then
hands `age` that copy — so the passphrase never touches the tty. covered end-to-end at the
CLI (`keyrack.passphrase` case7: passphrased-rsa init→set→unlock→get through the fake
dialog) and at integration (`ageRecipientCrypto.sshFallback` case5: real passphrased-rsa
roundtrip). rsa/ecdsa do NOT get the ephemeral-agent zero-reuse guarantee (that is the
ed25519 sign-as-KDF property); they get the clean dialog, not the broken prompt.

### the fallback — daemon-cache (no-agent / no-display users)

users with no usable agent or no display still get value via the extant "unlock once per
session" daemon cache, AFTER a successful unlock via a supported key. this does **not** use
the ssh-agent ux and does **not** offer the zero-reuse guarantee — it is the simpler
substitute the wisher did not want as the primary, kept only for users the recommended path
cannot serve.

> **NOTE — FIDO/sk- users are NOT served by this fallback.** an earlier draft listed them
> here; that was wrong. the daemon cache only holds a grant AFTER a successful unlock, and a
> passphrased FIDO-only key can never complete a first unlock (its private half is on the
> token — no strip, no decrypt, no deterministic sign). so a FIDO-only user fails fast with
> the swap-key BadRequestError (edgecase table above), never a silent fall to a cache they
> cannot reach.

---

## mental note on the recommended vs fallback split

the recommended path optimizes for **security** (zero reuse) at the cost of a prompt each
time. the fallback optimizes for **convenience** (unlock once per session) at the cost of a
lingering cached identity. the wisher chose security as the default. both are honest about
what they trade.

## what is awkward?

- **the wish names the one mechanism that cannot work.** "use the native os ssh-agent unlock
  prompt" sounds simple, but ssh-agent is architecturally unable to serve age decryption. the
  design honors the *spirit* (the native prompt + agent signature) while it refuses the
  *letter* (age via the agent) — and must be honest about that without a confusing lecture.
- **the security default costs a prompt every time.** the ephemeral shape is the safe one,
  but it gives up the "unlock once, stay unlocked" convenience the wish's second reading
  wanted. we settle the tension by making zero-reuse the default and the session cache a
  fallback — but a user who expected "like ssh-agent, it remembers it" will feel the prompt
  each time.
- **partial key-type support feels uneven.** ed25519 gets the clean sign-as-KDF path;
  rsa/ecdsa get the clean dialog via the age-cli strip (no zero-reuse); FIDO/sk- is
  unsupported and fails fast with a swap-key message (NOT the fallback — the cache cannot
  serve a key that never completes a first unlock). "an ssh key is an ssh key" is the user's
  expectation; the determinism math (q4) forces the split.
- **the popup depends on the desktop.** the mandated dialog needs `ssh-askpass-gnome`
  installed and a display. keyrack fails fast to guide the install, but a headless or
  minimal-desktop user cannot get the recommended path at all and must use the fallback.
- **correcting our own false docs is load-bearing.** two committed sources tell a future
  engineer that "age uses ssh-agent." until fixed, anyone who reads them will re-propose the
  dead-end path. the cleanup is what stops this confusion from recurring.

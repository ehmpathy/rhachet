# 1.vision — incremental `--roles` syntax (`+role` / `-role`) on `rhx init`

> wish: [0.wish.md](./0.wish.md) → github task [#411](https://github.com/ehmpathy/rhachet/issues/411)

## the wish, in one line

let `rhx init --roles` adjust the enrolled role set *relative to what is already enrolled* — via `+role` (add) and `-role` (remove) — instead of forcing a full respecify of the absolute set every time.

---

## the outcome world

### day-in-the-life

vlad has three roles enrolled in a repo: `mechanic`, `behaver`, `reviewer`. he wants to try the `architect` role on a branch.

**before (absolute-only):**
```sh
# must re-list everything he already had, plus the new one
rhx init --roles mechanic behaver reviewer architect
```
if he forgets `behaver`, it silently drops from the set. the command is a footgun proportional to how many roles you already have.

**after (incremental):**
```sh
rhx init --roles +architect      # add architect, keep mechanic/behaver/reviewer untouched
```
later, he decides `reviewer` is noise on this branch:
```sh
rhx init --roles -reviewer       # drop reviewer, keep the rest
```
or both at once:
```sh
rhx init --roles +architect -reviewer
```

### the "aha" moment

the value clicks the first time someone with 4+ enrolled roles adds a single role and *doesn't* have to re-type (and risk fat-fingering) the entire set. the mental shift is: **`--roles` stops being "declare the whole world" and becomes "nudge the world."** the absolute form still works for people who want to declare the whole set — no capability is taken away.

### before/after contrast

| dimension | before (absolute) | after (incremental) |
|-----------|-------------------|---------------------|
| add one role | re-list all N + 1 | `+role` |
| remove one role | re-list all N − 1 | `-role` |
| risk of silent drop | high (forget one → gone) | none (unmentioned roles untouched) |
| verbosity | O(current set size) | O(change size) |
| declare full set from scratch | supported | still supported (absolute form) |

## user experience

### usecases & goals

- **grow the set incrementally**: `rhx init --roles +architect` — enroll one more role without disturbing the rest.
- **shrink the set incrementally**: `rhx init --roles -reviewer` — unenroll one role, keep the rest.
- **atomic adjust**: `rhx init --roles +architect -reviewer` — add and remove in a single call.
- **declare absolute set (unchanged)**: `rhx init --roles mechanic behaver reviewer` — replace the whole set, exactly as today.

### contract inputs & outputs

**input** — the extant variadic flag, contract unchanged at the parser layer:
```
--roles <roles...>        # commander variadic → string[]
```
what changes is *interpretation* of each token:
- token starts with `+` → incremental add (strip prefix, parse as role specifier)
- token starts with `-` → incremental remove (strip prefix, parse as role specifier)
- token has no prefix → absolute member

each stripped token still flows through the extant `parseRoleSpecifier({ specifier })` → `{ repo, role }` contract, so both `+architect` and `+ehmpathy/architect` work identically to their absolute forms.

**output** — the per-role link work reuses the extant `execRoleLink` tree + glyphs
(`+` created / `✓` unchanged / `-` removed / `↻` updated), then a summary tree recaps the delta.

> refined 2026-07-14 at dogfood: the summary is a proper **treestruct** (per the ergonomist's
> `rule.require.treestruct-output`), not a flat comma-joined line. `additions` and `subtractions`
> are subtrees of `+ repo/role` / `- repo/role` children; empty delta sections are dropped
> (`rule.forbid.surprises` — no empty buckets); `untouched` is a **count**, not a wall of names.

```
🔧 init roles (incremental)
   ├─ additions
   │  └─ + bhrain/learner
   ├─ subtractions
   │  └─ - ehmpathy/reviewer
   └─ untouched (9)
```

the summary tree renders via `getRolesIncrementalSummaryTree`; the link/init loop under it is the
shared source of truth `getRolesLinkedFromSlugs`, the same op the absolute path
(`initRolesFromPackages`) delegates to — its symmetric pair `getRolesUnlinkedFromSlugs` is the
removal side. so both forms link roles identically and only differ in the header/footer they print
around that shared work.

### timeline of a leverage

1. user runs `rhx init --roles +architect -reviewer`
2. init discovers the current set via `discoverLinkedRoles` (scans `.agent/repo=*/role=*`, excludes `repo=.this`)
3. init validates the call is **all-incremental** (no bare tokens mixed in) — else rejects
4. init computes the target set = current ∪ {adds} ∖ {removes}
5. adds are linked via `execRoleLink`; removes are unlinked (new op); idempotent no-ops pass silently
6. tree output shows what changed

## mental model

### how a user describes it to a friend

> "it's like `git remote add` / `git remote remove` but for rhachet roles — you tweak the set instead of re-declaring it. the old way where you list everything still works."

### analogies that fit

- **`apt install pkg` / `apt remove pkg`** — you name the delta, not the full manifest.
- **`chmod +x` / `chmod -x`** vs `chmod 755` — the `+`/`-` incremental form vs the absolute octal form. this is an especially tight analogy: same tool, two modes, and mixing them is nonsensical (you can't `chmod +x 755`), which mirrors our "no mixed calls" rule.
- **set algebra**: current set, then `∪ add`, `∖ remove`.

### terms: theirs vs ours

| user says | we say (domain) |
|-----------|-----------------|
| "add a role" | incremental add / link |
| "remove a role" | incremental remove / unlink |
| "the roles I have" | current set / enrolled roles (`discoverLinkedRoles`) |
| "list all my roles" | absolute set |

## evaluation

### how well it solves the goal

directly. the wish is "adjust relative to current set"; the design reads the current set (`discoverLinkedRoles`), applies a delta, and writes the result. absolute form is untouched, so it's purely additive to the contract.

### pros

- **additive, non-breaking**: absolute syntax unchanged; extant scripts and tests keep passing.
- **reuses extant contracts**: `parseRoleSpecifier`, `execRoleLink`, `discoverLinkedRoles`, `BadRequestError`, the turtle tree output — small surface area of genuinely new code.
- **pit of success**: unmentioned roles are never touched, eliminating the silent-drop footgun.
- **idempotent**: `+extant` and `-absent` are no-ops, so retries and scripted calls are safe.

### cons / costs

- **⚠️ feasibility risk — commander rejects `-role` as a value**: verified — the CLI uses `commander@14.0.0` (`node_modules/commander/package.json`). commander's variadic `--roles <roles...>` **stops collecting** at any token that begins with `-`, and errors on unknown options by default. so `rhx init --roles +architect -reviewer` parses `+architect` as a value, then treats `-reviewer` as an unknown option → error. `+role` is safe (no leading dash); **`-role` as literally specified in the wish does not work out-of-the-box.** this is the single biggest design risk and it touches the wish's literal syntax. mitigations the blueprint must weigh: (a) argv preprocessing before commander hands off (rewrite `-role` tokens into a safe internal form); (b) the `--roles=-reviewer` equals-form, which commander accepts as a literal value but is clunky and breaks the clean `+a -b` ergonomics; (c) a non-dash remove sigil (e.g. `~role`), which departs from the wish's `-role`. **must confirm with wisher** (see open questions).
- **new removal path**: today there is no `execRoleUnlink` / role-removal operation (confirmed: only `execRoleLink` lives under `src/domain.operations/invoke/link/`). `-role` requires a safe unlink build (remove the `.agent/repo=*/role=*` symlink tree, and clean an empty `repo=*` dir) — the largest chunk of new work, and the riskiest (deletion).
- **parse ambiguity with role names**: role specifiers are `role` or `repo/role`. we must confirm no legitimate role token begins with `+`/`-`; `parseRoleSpecifier` trims but does not otherwise reserve those chars. prefix detection must happen *before* `parseRoleSpecifier`.
- **mode interaction**: init already has `--mode findsert|upsert`. we must define how incremental interacts with `--mode` (likely: incremental implies its own semantics and `--mode` applies only to the link step, not the set computation) — a clarity risk if left implicit.

### edgecases & pit-of-success

| # | edgecase | desired behavior | keeps user safe by |
|---|----------|------------------|--------------------|
| e1 | `+role` already enrolled | no-op (idempotent), reported as `✓` | not to error on safe repeats |
| e2 | `-role` not enrolled | no-op (idempotent), reported clearly as absent | not to error on already-absent |
| e3 | mixed call `mechanic +architect` | **reject** with `BadRequestError` (all-absolute OR all-incremental) | removal of base-set ambiguity |
| e4 | `-role` that empties the set | allowed (empty set is valid), no warn | explicit, predictable |
| e5 | `+role` for unknown/invalid role | `BadRequestError` (reuse extant lookup errors) | fail-fast with available-roles hint |
| e6 | duplicate tokens `+architect +architect` | dedupe → single add | lenient input |
| e7 | `+role -role` same slug in one call | **reject as contradictory** (`BadRequestError`) | one pinned rule, no silent winner |
| e8 | unqualified `-role` enrolled under 2+ repos | **reject as ambiguous** (mirror `getRoleFromManifests.ts:52-61`), hint to qualify `-repo/role` | prevents silent removal of the wrong repo's role |
| e9 | bare sigil `--roles +` or `--roles -` (prefix, no slug) | `BadRequestError` "role specifier cannot be empty" (post-strip empty → `parseRoleSpecifier.ts:16-19`) | clear message, not a cryptic parse error |
| e10 | qualified incremental `+ehmpathy/architect` / `-bhuild/reviewer` | works — strip prefix, then `parseRoleSpecifier` yields `{repo, role}` | symmetry with absolute qualified form |
| e11 | `-role` targets a native `repo=.this` role | `BadRequestError` "native roles cannot be removed" — `discoverLinkedRoles` excludes `.this` (`.ts:31`), so it is not in the removable set | protects native roles from an unremovable-by-design path |
| e12 | last role under `repo=X` removed → empty `repo=X/` dir | unlink cleans the now-empty `repo=X/` parent dir | no orphan empty dirs left in `.agent/` |
| e13 | `-role` where the symlink is already broken/orphan | unlink is robust — removes the broken link, still reports removed | resilient to a half-linked prior state |
| e14 | `+role` where the npm package was uninstalled since last link | `BadRequestError` (role not found in manifests) — same path as e5 | fail-fast, does not create a broken link |
| e15 | `--mode upsert` combined with incremental tokens | `--mode` governs the link step only; incremental set-math is independent of mode | mode and increment compose without surprise |
| e16 | all-absolute call (no `+`/`-` tokens) | unchanged legacy behavior — replace whole set | zero regression on extant contract |

> **assumption surfaced (assumptions review)**: adds inherit the extant ambiguity guard — an unqualified `+role` present in multiple packages already errors via `getRoleFromManifests.ts:52-61`. but **removal does not go through manifests** — it reads the linked set (`discoverLinkedRoles` → `{repo, role}[]`), which has *no* ambiguity guard. so the vision's implicit assumption that a bare `-role` uniquely names one enrolled role is **false** when the same slug is linked under two repos. the removal path must add its own ambiguity guard, modeled on the manifest one.

## open questions & assumptions

### assumptions made

1. **"current set" = `.agent/` contents.** there is no separate persisted role-list config; the enrolled set is exactly the `.agent/repo=*/role=*` directory structure, read by `discoverLinkedRoles`. incremental math operates on that. *(verified — see groundwork.)*
2. **absolute form stays the default & unchanged.** a call with zero `+`/`-` prefixes behaves exactly as today.
3. **`+`/`-` prefix is stripped before role parse**, then the remainder flows through the unchanged `parseRoleSpecifier`.
4. **removal is a filesystem unlink of the symlink tree**, reversible by re-running `+role` (which re-links from the still-installed package). we are not uninstalling npm packages.

### triaged questions

each tagged `[answered]` (resolved now via logic/code), `[research]` (defer to research phase), or `[wisher]` (only the wisher can decide).

1. **[wisher] how do we spell "remove" given commander rejects `-role`?** (see cons/costs ⚠️). the wish asks for `-role`, but `commander@14.0.0` will not accept a `-`-prefixed token as a variadic value. pick one: (a) argv preprocess so `-role` still works as typed; (b) accept the clunkier `--roles=-reviewer`; (c) adopt a non-dash sigil like `~role`. this is the highest-priority decision — it shapes the entire user-face contract. *why wisher: it's a product/ergonomics tradeoff, not a fact derivable from code — the wisher owns the intended notation.*
2. **[wisher] should removal live on `init` at all?** `rhx init --roles -reviewer` uses the `init` verb to *un*enroll (see awkwardness #3). alternative: a dedicated `rhx role rm` command. the wish scopes this to `--roles` on `init`, but the verb/semantics tension is real. *why wisher: scope/command-surface decision that only the wisher can settle.*
3. **[answered] `+role -role` for the *same* role in one call** — **reject as contradictory.** resolved now by logic: the vision already commits to reject *mixed* absolute/incremental calls for ambiguity; a same-token `+x -x` is the same class of self-contradiction and should error via `BadRequestError`, consistent with `chmod`-style incoherence. no wisher input needed.
4. **[answered] empty-set result** — **allowed, no warn.** resolved now by logic: an empty enrolled set is a valid state (`discoverLinkedRoles` returns `[]` cleanly, `discoverLinkedRoles.ts:26`), and the absolute form can already produce any set the user declares. `-onlyrole` that leaves zero roles is the user's explicit intent; a warn would add surprise, not safety.
5. **[answered] does `-role` remove symlinks only, or also the npm package?** — **symlinks only.** resolved now by code: enrollment is the `.agent/repo=*/role=*` symlink tree built by `execRoleLink`; the npm package install is a separate concern (`initRolesFromPackages` links from already-installed packages). removal is the inverse of link → unlink the symlink tree, leave the package. this keeps `+role` reversible without reinstall.
6. **[answered] should incremental interact with `--keys` / `--hooks` / `--prep`?** — **yes, incremental scope applies; these flags operate on the produced set.** resolved now by code: `--hooks` calls `syncHooksForLinkedRoles` (`invokeInit.ts:110-115`) which already syncs across *linked* roles, so after an incremental add/remove it naturally covers the new set. `--keys`/`--prep` already require `--roles` (`invokeInit.ts:46-61`) and act on the passed specifiers. no new interaction rule needed — they compose with whatever set the incremental step produces.

### must research externally

none — no external APIs/services. this is entirely local CLI + filesystem behavior.

## groundwork

### external research

none — no external dependencies. the feature is a local CLI flag interpretation + filesystem symlink change.

### internal research (verified)

- **init entrypoint & parser**: `src/contract/cli/invokeInit.ts:20` — `.option('--roles <roles...>', ...)` (commander variadic → `options.roles: string[]`). the parser already collects space-separated tokens into an array; `+`/`-` interpretation is a layer *above* this, so **no parser change needed**.
- **role specifier contract**: `src/domain.operations/invoke/parseRoleSpecifier.ts:11-49` — `parseRoleSpecifier({ specifier }) → { repo: string|null, role: string }`; trims, supports `role` and `repo/role`, throws `BadRequestError` on empty/multi-slash. does **not** reserve `+`/`-`, so prefix-strip must precede this call.
- **current set discovery**: `src/domain.operations/upgrade/discoverLinkedRoles.ts:21-50` — scans `.agent/`, filters `repo=*` (excludes `repo=.this`), reads `role=*` → `RoleLinkRef[]` = `{ repo, role }[]`. this is the exact "current set" source for incremental math.
- **precedent — non-absolute token already exists**: `discoverLinkedRoles.ts:17` notes it *"enables `--roles *` to expand to all currently linked roles"* (expansion in `src/domain.operations/upgrade/expandRoleSupplierSlugs.ts`). so the pipeline already interprets a special `--roles` token (`*`) above the parser, relative to the current set — the exact shape `+`/`-` needs. **the blueprint should mirror how `*` is handled as the paved pattern for `+`/`-`.**
- **orchestration input key**: `invokeInit.ts:68-71` calls `initRolesFromPackages({ specifiers: options.roles }, context)` — the input key is `specifiers`. incremental interpretation slots at or above this seam.
- **link (add) operation**: `src/domain.operations/invoke/link/execRoleLink.ts` — creates the `.agent/repo=*/role=*` symlink tree; emits turtle-vibes tree with glyphs `+` created / `✓` unchanged / `-` removed / `↻` updated (snapshot: `execRoleLink.integration.test.ts.snap`).
- **removal (remove) operation**: **absent.** `src/domain.operations/invoke/link/` contains only link/findsert/symlink utils — no `execRoleUnlink`/`removeRole`. **this is the primary new build.**
- **orchestration**: `src/domain.operations/init/initRolesFromPackages.ts` composes parse → link; incremental logic slots in as: compute target set, then add via link + remove via new unlink.
- **error class & exit**: `BadRequestError` from `helpful-errors` throughout `invokeInit.ts` (e.g. `:45-61`), process exits `1` on error. mixed-call rejection reuses this pattern.
- **tests to conform to**: `src/contract/cli/invokeInit.integration.test.ts` (init flows, findsert/upsert, error cases), `parseRoleSpecifier.test.ts`, `discoverLinkedRoles.test.ts`.
- **extant mode**: `--mode findsert|upsert` (default findsert) already present at `invokeInit.ts` — interaction with incremental must be defined (open question 4).

## what is awkward?

1. **removal is deletion, and deletion is scary.** the biggest awkwardness is that `-role` is the first init path that *destroys* filesystem state. everything init does today is additive (findsert/symlink). building a safe unlink (only touch `.agent/repo=*/role=*`, never escape the repo, clean empty parents, be idempotent) is where the design carries real risk. the `isPathWithinGitroot` guard already in `link/` suggests the codebase is aware of this class of hazard.

2. **`+`/`-` as sigils fights the parser (now a confirmed risk, not a hunch).** i verified against `commander@14.0.0`: variadic collection halts at the first `-`-prefixed token and unknown options error by default, so `-reviewer` is read as an option, not a value. this is no longer "needs a test" — it is a known constraint that forces a design decision (argv preprocess, `=`-form, or non-dash sigil). the awkwardness is that the wish's most natural notation (`-role`) is exactly the notation the CLI framework resists. see cons/costs ⚠️ and open question #2.

3. **"init" naming vs "remove" semantics.** `init` connotes setup/creation; `rhx init --roles -reviewer` to *un*enroll reads slightly against the grain of the verb. it fits the "adjust the set" mental model, but a first-time reader might not expect `init` to remove. this is a mental-model friction we accept (the wish explicitly scopes it to `init`), but worth naming.

4. **mixed-call rejection is a "no" the user must learn.** `rhx init --roles mechanic +architect` failing is correct (ambiguous base), but it's a rule the user discovers by hitting it. the error message must teach — clearly state "all-absolute OR all-incremental" with both corrected examples — to keep them in the pit of success.

# expansion — bare-sigil `rhx init +role` alias (scope addition, 2026-07-14)

> wisher-added after dogfood of the base `--roles +role` feature. see wish expansion in `0.wish.md`
> (mirror to github #411).

## the desire, in one line

`rhx init +learner` should be a convenience alias for `rhachet init --keys --hooks --roles +learner`
— so the common "enroll a role and make it fully usable" path is a single short command.

## where this lives — the `rhx` shorthand layer, NOT the `rhachet init` contract

the alias is implemented purely in the **`bin/rhx` proxy** (the shorthand binary), not in
`invokeInit.ts`. this is deliberate and critical:

- `rhachet init` keeps its explicit contract: `--roles`/`--keys`/`--hooks` remain independent
  opt-in flags. no downstream tool or test of the `rhachet` contract changes.
- `bin/rhx` already short-circuits top-level commands past its skill-proxy default
  (`keyrack`/`upgrade`/`enroll`, and now `init` from the base feature's escape-hatch fix). the alias
  extends that `init` short-circuit to also **rewrite** a bare front `+`/`-` sigil into the full
  flag form before it delegates to `run init`.

so the transform is: `rhx init +learner`  →  `run init --keys --hooks --roles +learner`.

## the trigger rule (precise, to avoid surprise)

> refined 2026-07-14 at dogfood: the rule is now **flag-driven**, not sigil-driven. bare absolute
> names (`rhx init learner`) are in scope — they expand just like a sigil does.

the mode is chosen by a single question: **does the tail carry any recognized `init` flag?**

- **yes** → **flag mode**: pass through to `run init` unchanged (the user drives explicitly).
- **no** (tail is role tokens only — bare names and/or `+`/`-` sigils) → **alias mode**: inject
  `--keys --hooks --roles` in front.
- **no args at all** → pass through, so `rhx init` still prints usage.

recognized flags: `--roles`/`--keys`/`--hooks`/`--config`/`--prep`/`--mode`/`-h`/`--help`.

| invocation | `bin/rhx` rewrites to | mode / why |
|------------|----------------------|-----|
| `rhx init learner` | `run init --keys --hooks --roles learner` | alias — bare absolute name, no flag |
| `rhx init +learner` | `run init --keys --hooks --roles +learner` | alias — add-sigil, no flag |
| `rhx init -learner` | `run init --keys --hooks --roles -learner` | alias — remove-sigil, no flag |
| `rhx init a +b -c` | `run init --keys --hooks --roles a +b -c` | alias — mixed role tokens, no flag |
| `rhx init --roles +learner` | `run init --roles +learner` (unchanged) | flag mode — `--roles` present |
| `rhx init --keys --roles +a` | `run init --keys --roles +a` (unchanged) | flag mode — flags present |
| `rhx init --help` / `-h` | `run init --help` / `-h` (unchanged) | flag mode — help flag present |
| `rhx init` (no args) | `run init` (unchanged) | pass through — prints usage |

**decision rule**: scan every token after `init`. if **any** token is a recognized flag, do not
inject. otherwise, if there is at least one token, inject `--keys --hooks --roles` in front of the
whole tail. this is a pure shell string check in `bin/rhx`; the real role-token classification (bare
vs `+` vs `-`) still happens downstream in `getClassifiedRoleTokens`.

> ⚠️ the flag check is what disambiguates a **remove-sigil** (`-learner`, not a recognized flag →
> alias mode) from a **help flag** (`-h`/`--help`, recognized → flag mode). a `-<slug>` that is not a
> known flag is treated as a role token, so the whole tail flows behind `--roles` and commander reads
> `-learner` as a variadic value (via the same `getPreprocessedRoleArgv` sentinel the base feature
> uses).

## why keys+hooks, and why auto

- **`--keys`** initializes the role's keyrack manifest (`initKeyrackRepoManifest`, `invokeInit.ts:109`).
  a freshly-enrolled role that needs credentials is useless until its keyrack entry exists.
- **`--hooks`** syncs brain hooks for the linked set (`syncHooksForLinkedRoles`, `invokeInit.ts`).
  hooks are what make a role's briefs/skills actually load into a brain.
- auto-inclusion of both means `rhx init +learner` yields a **ready-to-use** role, not a
  half-enrolled one. the vision's open-question-6 already established that `--keys`/`--hooks` *compose*
  cleanly with the incremental set; this alias simply defaults them on for the shorthand path.

## the awkwardness (named honestly)

- **the alias hides two mutations.** `rhx init +learner` now also writes a keyrack manifest and syncs
  hooks — more side effects than the bare symlink op the base feature does. this is the *point* (a
  usable role), but a user who wanted *only* the symlink must drop to the explicit
  `rhx init --roles +learner` form. the alias trigger rule preserves that escape hatch.
- **`bin/rhx` is shell, not TypeScript.** the rewrite logic lives in a POSIX `sh` proxy, so its
  "is there a recognized flag in the tail" test is a shell string scan, not the typed
  `getClassifiedRoleTokens` transformer. keep the shell logic minimal (a flag scan over the tail) and
  let the real role-token classification stay in `invokeInit` downstream.

## boundary-case coverage — required as tests (expansion)

| case | invocation | asserts |
|------|-----------|---------|
| x1 | `rhx init +learner` (fresh) | routes to init command (not skill); role linked; keyrack manifest present; hooks synced; exit 0 |
| x2 | `rhx init --roles +learner` | explicit form unchanged — NO keys/hooks injected (manifest absent unless already there) |
| x3 | `rhx init -learner` | remove-sigil recognized (not read as a flag); role unlinked; exit 0 |
| x4 | `rhx init +a -b` | multi-sigil expands once to `--keys --hooks --roles +a -b`; exit 0 |
| x5 | `rhx init architect ergonomist` | bare absolute names expand to `--keys --hooks --roles architect ergonomist`; both linked; keys+hooks injected; exit 0 |
| x6 | `rhx init --help` / `rhx init -h` | help short-circuit still works; `-h` (a recognized flag) is NOT read as a remove-sigil |

**grain**: because `bin/rhx` is a shell proxy that shells out to the built binary, the natural test
grain is **acceptance** — invoke the `bin/rhx` proxy as a subprocess and assert on the routed
behavior (role linked/unlinked + keyrack manifest presence + exit code). x2 (explicit `--roles`, no
inject) and x6 (help flag, no inject) are the anti-regression guards that flag mode still wins when a
recognized flag is present.

> coverage rule for the expansion: no case x1–x6 ships without its named acceptance test green.

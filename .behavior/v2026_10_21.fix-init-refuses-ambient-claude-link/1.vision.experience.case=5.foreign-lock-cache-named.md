# case 5 — a foreign lock cache is named, not a mystery fault (sharp × alter)

## .narrative

i am a booted clone; my SessionStart hook runs an rhx whose `simple-on-disk-cache` resolved to a copy
with no `version()`. today the boot.md write dies on `the cache backend faulted while it read the lock
version on acquire`, and the cause hides in `error.cause`. after: `withRepoMutex` checks the cache
before it takes a lock, and refuses with the module path and version it resolved — so the next fault
measures itself, and no tombstone or half-lock is left on disk.

## .timeline

```
given('[case5] a mutex cache with no version()')
  when('[t0] withRepoMutex runs a section')
    then('💥 MalfunctionError: the repo mutex cache lacks version()')
    then('the error names the resolved simple-on-disk-cache path and its version')
    then('the section did not run; no lock file was written')
  when('[t1] a commander runs rhx init --roles tester under the same foreign cache')
    then('the layout step meets the malfunction and defers it; the role loop runs')
    then('the boot sync re-runs the layout step and reports the same 💥 MalfunctionError, with the copy named')
```

the guard sits in `withRepoMutex`, so every caller of the repo mutex meets the same named fault: a
booted clone's boot write ([t0]), and init's layout step and boot sync ([t1]). the wish's second
fault — acceleration's sprout, which dies at the `.repo-brain-dir-link` acquire — is the [t1] walk.

## .fail-safe

fast (before the first lock write), loud, teaches (names the copy; hints at the tree's own rhx). an
alterpath: rhachet declares a cache with `version()`, so only a foreign resolution reaches this.

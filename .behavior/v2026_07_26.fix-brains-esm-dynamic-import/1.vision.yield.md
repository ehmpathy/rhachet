# vision: fix(brains) — load brain packages via true dynamic `import()` so esm-only brains load

## .what

make `getAvailableBrains` (and its peer brain/plugin load-sites) perform a **genuine
runtime `import()`** instead of a tsc-downleveled `require()`, so a brain package whose
dependency graph is esm-only (e.g. `rhachet-brains-anthropic`, which pins the esm-only
`@anthropic-ai/claude-agent-sdk`) loads into the registry instead of silently dropping —
with **no module-system change** (rhachet stays commonjs).

---

## the outcome world

### day-in-the-life

**before** — a maintainer installs `rhachet-brains-anthropic`, wires `--brain anthropic`
into a skill, and runs it. rhachet's `getAvailableBrains` calls `await import('rhachet-brains-anthropic')`,
which tsc has compiled down to a `require()` shim. `require()` hits the esm-only
`@anthropic-ai/claude-agent-sdk` and throws `Cannot use import statement outside a module`.
the `try/catch` swallows it to a lone `console.warn`, returns `{ atoms: [], repls: [] }`,
and the anthropic brain **vanishes from the registry**. the skill runs brainless. downstream,
every `rhachet-roles-ehmpathy` `.evals/` test that spawns `rhx review` fails with
`UnexpectedCodePathError: review output lacks blocker count`, and that repo's
`suite / test-integration` rollup is red — for a reason nobody can see in the log except a
buried warn.

**after** — the same install, the same command. `getAvailableBrains` performs a real
runtime `import()` that node loads as esm. the anthropic brain loads, its atoms and repls
join the registry, `--brain anthropic` works, and the downstream `.evals/` suite goes green.
the cjs brains (fireworks, xai, openai) load exactly as before. no other behavior shifts.

### before/after contrast

| dimension | before | after |
|-----------|--------|-------|
| esm-only brain (anthropic) | drops silently, `console.warn` only | loads into registry |
| cjs brains (fireworks/xai/openai) | load | load (identical) |
| module system | commonjs | commonjs (unchanged) |
| `type` in package.json | absent (cjs) | absent (cjs) |
| downstream `.evals/` rollup | red (brainless review) | green |
| failure visibility | buried warn, brain just "missing" | n/a — it loads |

### the "aha" moment

the value clicks when a maintainer sees `--brain anthropic` work **without flipping rhachet
to esm**. the fix is a one-line indirection per load-site — no `tsconfig` churn, no
`type: module`, no ripple across the 200+ other files. "you mean it just needed to *actually*
call `import()` at runtime?" — yes. tsc was the saboteur, not node.

## user experience

the "users" here are three audiences:

1. **rhachet maintainers** — who install brain packages and expect them in the registry
2. **downstream consumers** (`rhachet-roles-ehmpathy` `.evals/`) — whose CI unblocks
3. **future brain authors** — who may ship an esm-only dep graph and must not be punished for it

### usecases fulfilled

- **discover an esm-only brain** — `getAvailableBrains()` returns its atoms/repls
- **dispatch to an esm-only brain** — `genContextBrain` → `getOneBrainAtomByRef` /
  `getOneBrainReplByRef` look it up (transitively, via `getAvailableBrains`)
- **look up an esm-only brain hooks adapter** — `getBrainHooksAdapterByConfigImplicit` loads it
- **load an esm-capable role registry / config** — the peer config load-sites don't choke on esm

### contract inputs & outputs

the public contract is **unchanged**. `getAvailableBrains` keeps its signature:

```ts
getAvailableBrains(
  input?: {},
  context?: ContextCli,
): Promise<{ atoms: BrainAtom[]; repls: BrainRepl[] }>
```

what changes is **internal**: a shared transformer that hides the dynamic import from tsc.
issue #429 sketches this exact helper (it names it `importEsmSafe`); proposed shape (a
communicator-grain leaf, mechanic owns the final HOW + the name):

```ts
/**
 * .what = perform a genuine runtime esm-capable dynamic import
 * .why  = tsc under module:commonjs downlevels `await import()` into a require()
 *         shim, which cannot load esm-only packages. an indirection tsc cannot
 *         see keeps the import a real runtime import().
 */
const importEsmSafe = new Function(
  'specifier',
  'return import(specifier)',
) as (specifier: string) => Promise<Record<string, unknown>>;
```

and each load-site swaps `await import(x)` → `await importEsmSafe(x)`.

**note — inline vs shared is contingent on q1.** if the fix lands at only the one primary site,
`importEsmSafe` stays **inline** in `getAvailableBrains` (as issue #429 sketches) — a shared leaf
for one caller would be premature abstraction (`rule.prefer.wet-over-dry`). the shared-leaf shape
above is justified only once 3+ load-sites adopt it (the rule-of-three), which depends on how wide
q1 sets the scope.

### what leverage looks like

```ts
// getAvailableBrains.ts — the primary site
const packageExports = await importEsmSafe(input.packageName);
return extractBrainsFromPackage({ exports: packageExports });
```

no code changes at the call sites of `getAvailableBrains` itself — the fix is entirely
below the public surface.

### timeline a consumer goes through

1. rhachet ships the patch (1.44.x)
2. `rhachet-roles-ehmpathy` bumps its rhachet pin
3. its `.evals/` `rhx review` runs with a brain again → `suite / test-integration` green
4. no code change required in the consumer beyond the pin bump

## mental model

### how a user describes it to a friend

> "our tool compiles to commonjs, but some plugins are esm-only. typescript was quietly
> rewriting our `import()` into a `require()`, and `require` can't load esm — so those
> plugins just disappeared. we hid the import behind a `new Function` so typescript leaves
> it alone, and now it's a real runtime import again."

### analogies / metaphors

- **the disguise** — tsc frisks every visible `import()` and rewrites it to `require()`.
  wrapping it in `new Function('s','return import(s)')` is a disguise tsc can't see through,
  so the real `import()` walks past untouched.
- **the smuggler's envelope** — the import specifier rides inside a string that tsc treats as
  opaque; node opens the envelope at runtime and does the real esm load.

### terms — theirs vs ours

| they say | we say |
|----------|--------|
| "the plugin disappeared" | brain dropped from the registry |
| "typescript broke it" | tsc downlevels `import()` → `require()` under `module: commonjs` |
| "esm plugin" | brain package with an esm-only dependency graph |
| "the workaround" | dynamic-import indirection (`importEsmSafe`) |
| "load the brains" | `getAvailableBrains` / `importBrainsFromPackage` |

## evaluation

### how well it solves the goals

- **acceptance #1 (genuine runtime `import()`)** — ✅ the `new Function` indirection is opaque
  to tsc's commonjs downlevel; node runs a real `import()`.
- **acceptance #2 (no module-system change)** — ✅ `tsconfig` stays `module: commonjs`,
  `package.json` stays `type: absent`, `main: dist/index.js`. cjs brains unaffected — strict superset.
- **acceptance #3 (fault isolation preserved)** — ✅ the extant per-package `try/catch` →
  `console.warn` → `{ atoms: [], repls: [] }` is retained; one bad brain still can't sink the registry.
- **acceptance #4 (regression clamp)** — ✅ achievable via an esm-only brain fixture that is
  RED on the `require()` version and GREEN on the fix (see edge cases + open questions for the
  fixture strategy — this is the riskiest piece to get right).
- **acceptance #5 (audit peers)** — ✅ audit complete; see internal research. the wish's named
  peers (`genContextBrain`, `getOneBrainReplByRef`, `getOneBrainAtomByRef`) are **not** direct
  import-sites — they consume `getAvailableBrains`, so they're fixed transitively. the real
  peer downlevel sites are enumerated below.
- **acceptance #6 (release as patch)** — ✅ 1.44.x patch; downstream bumps the pin.

### pros

- **minimal blast radius** — one shared leaf + a swap at each load-site; no config churn
- **strict superset** — no cjs path regresses; only the esm-only path is newly enabled
- **fault isolation untouched** — the extant warn/skip semantics carry over verbatim
- **future-proof** — any brain/role/config package that goes esm-only now loads
- **the fix is legible** — a single named transformer with a `.why` documenting the tsc trap

### cons

- **`new Function` is a code smell** — it reads like `eval`; lint/security scanners may flag it.
  mitigated by isolating it in one named, well-documented leaf so the smell lives in exactly one
  place with a clear `.why`.
- **type erasure at the boundary** — `importModuleDynamic` returns `unknown`; callers must
  narrow. acceptable — the extant sites already treat exports as loosely-typed records.
- **can't be verified by reading the `.ts`** — the fix only "bites" in compiled dist; unit
  reading won't prove it. the regression clamp must run against **built/real** modules to be honest.

### edge cases & pit-of-success

| # | edge case | how the contract keeps users safe |
|---|-----------|-----------------------------------|
| e1 | esm-only brain package installed | loads (the core fix) |
| e2 | cjs brain package installed | loads unchanged — `import()` handles cjs too |
| e3 | brain package throws on import (genuinely broken) | caught → warn → `{ atoms: [], repls: [] }`; registry survives |
| e4 | brain package absent / unloadable specifier | caught → warn → skip (same as today) |
| e5 | package exports esm default vs named | `extractBrainsFromPackage` iterates `Object.entries`; esm namespace object still enumerates named exports |
| e6 | mixed registry (some cjs, some esm-only) | each loaded independently; esm-only ones no longer drop |
| e7 | config load-site (`rhachet.use.ts`) is esm-capable | same indirection applied → no `require()` choke |
| e8 | duplicate brain across packages | extant `dedupeBySlug` (first wins) unaffected |
| e9 | tsc/bundler re-optimizes the `new Function` away | must assert against built output, not source, to catch this |

## open questions & assumptions

### assumptions made

- **a1** — `rhachet-brains-anthropic@0.4.1` pins `@anthropic-ai/claude-agent-sdk@0.1.76`, which
  is esm-only (`type: "module"`, `main: "sdk.mjs"`). **verified in issue #429** (spec of record,
  read directly — see external research). the exact installed bytes are **not** re-inspected in
  this worktree (node_modules for brains is not installed here), so the version→build handoff
  should still confirm against the real install.
- **a2** — `new Function('specifier','return import(specifier)')` reliably evades tsc's commonjs
  downlevel and yields a real runtime `import()`. issue #429 asserts it reproduces both in ci and
  locally; still needs a built-dist assertion to prove it in *our* tsc config, not just on the
  spec's word.
- **a3** — the esm namespace object returned by a real `import()` enumerates the brain package's
  `getBrainAtomsBy*` / `getBrainReplsBy*` named exports under `Object.entries` the same way the
  cjs `require()` object did. (esm interop generally holds this, but the fixture must confirm.)
- **a4** — no bundler/minifier in the release build strips or rewrites the `new Function`.
- **a5** — the downstream `rhx review` unblock depends on WHICH brain path it exercises.
  `genContextBrain.ts:104-137` has two modes: **discovery** (`:129` → `getAvailableBrains`, the
  primary fix site) and **explicit** (`:116-125` → brains from the config path via
  `getBrainsByConfigExplicit.ts:15`). the two modes hit **different** `await import(` downlevel
  sites. **q4 (below) resolves this by inspection of the downstream repo: it uses the discovery
  path.** **consequence:** a fix to `getAvailableBrains` alone unblocks the downstream, so the
  config-load fix is tidiness (q1), not a downstream requirement. (had the downstream used the config
  path, that fix would have been load-critical — hence the hedge was worth checking, and now it is
  settled.)
- **a6** — the test toolchain (`@swc/jest`, `jest.unit.config.ts:30`) is **not** the production
  compiler (tsc). swc may keep `import()` native rather than emit tsc's `require()` shim, so a
  source-level `.integration.test.ts` may not reproduce the defect at all. **consequence:** the
  required regression clamp (acc#4) must run against the tsc-built `dist/`, not the swc-transpiled
  source — see q2. this is the deepest constraint on how the clamp is built.

### questions (triaged — [answered] now / [research] later / [wisher] input)

- **q1 [wisher]** — scope of the indirection: apply to **all six** downlevel sites (3 package-loads + 3
  config-loads), or only the brain/plugin package-loads (the 3 that load third-party graphs)?
  the config-loads (`rhachet.use.ts`) are usually local/compiled, lower esm risk — but the wish
  says "wherever a brain/plugin loads that way." **best-guess: apply to all six** via the shared
  helper (uniform, low-cost, closes the whole class); flag if the wisher wants it narrower.
  **note (per a5 + q4): this is now tidiness, not a hedge.** q4 confirms the downstream uses the
  discovery path (`getAvailableBrains`), so the primary fix alone unblocks it — the config-load fix
  is not required for the downstream goal. the two brain-package loads are logically in scope
  already; the open part is only whether to also fix the 3 config loads for uniformity (a defensive
  fix that does no harm, but the wisher may prefer to defer to a later wish).
- **q2 [answered]** — regression-clamp fixture strategy (the crux): a real npm esm-only fixture package, an
  inline generated esm module in a temp dir, or a build-dist assertion that the compiled output
  holds a real `import()` and not a `require()` shim? **best-guess: an esm-only fixture module
  loaded via the built code**, plus a cheap dist-grep guard for e9. needs wisher/mechanic
  alignment because it's the acceptance linchpin.
  **critical (per a6): the clamp must target the tsc-built `dist/`, not the swc-transpiled source.**
  tests transpile via `@swc/jest` (`jest.unit.config.ts:30`), NOT tsc — and swc may keep `import()`
  native rather than emit tsc's `require()` shim. so a `.integration.test.ts` of the `.ts` source
  might load an esm brain fine even on the BROKEN version and never bite. the clamp's correct home
  is therefore a `.acceptance.test.ts` (which runs `npm run build` first — `package.json:88,90` —
  and tests the real dist blackbox), or an explicit built-artifact assertion. the leftover fixture
  *form* is a mechanic build-time call, not a wisher/research item.
- **q3 [answered]** — is `console.warn` fault-isolation acceptable long-term, or should the drop be
  surfaced more loudly? **answered: out of scope.** acc#3 requires we keep the extant fault-isolation
  behavior, so a loudness change is a separate, future wish — the defect's invisibility (a quiet warn
  hid a failure that empties the registry) is the motive for that future wish, not this one.
- **q4 [answered]** (from a5) — which brain path does `rhachet-roles-ehmpathy` `.evals/` exercise —
  discovery (`getAvailableBrains`) or explicit/config (`getBrainsByConfigExplicit`)? **answered by
  inspection of the downstream repo (`git.repo.get`): the discovery path.** the `.evals/` select
  brains by choice slug via `--brains` (e.g. `review.eval compare --brains fireworks/...,xai/...`,
  `review.eval.sh:14`), and the repo has no `rhachet.use.ts` brain-supply config — so brains load
  through `getAvailableBrains`. **consequence:** the primary fix alone unblocks the downstream; the
  config-load fix is therefore tidiness (q1), not a downstream requirement.
- **q5 [research]** (from a6) — does `@swc/jest` keep `import()` native or downlevel it to a
  `require()` shim? answerable empirically in the build phase (build + inspect, or a probe test).
  confirms *why* a source-level clamp is insufficient; the fix is correct regardless (the clamp
  targets the tsc dist).

## what is awkward?

- **the fix can't be proven by reading source — nor by the swc/jest test path** — `.ts` looks like
  a real `import()` before *and* after; the defect only lives in the *tsc*-compiled dist. worse,
  the test toolchain is `@swc/jest` (not tsc), and swc may keep `import()` native — so even a
  source-level `.integration.test.ts` may not reproduce the bug (a6). the built tsc artifact is the
  **only** honest witness; the regression clamp **must** run against `dist/` (a `.acceptance.test.ts`
  home), or it clamps a different program than the one that ships. this is the single most
  uncomfortable tradeoff.
- **`new Function` reads like `eval`** — it will make a security-minded reviewer flinch. the
  discomfort is real; the mitigation (one isolated, named, `.why`-documented leaf) is a
  containment, not a cure.
- **the wish's advisory peer list was off** — it named `genContextBrain` /
  `getOneBrainReplByRef` / `getOneBrainAtomByRef`, but those aren't import-sites. following the
  wish verbatim would edit the wrong files. the vision corrects this, but it's a reminder that the
  "salty guess from outside the repo" needed in-repo verification (which it got).
- **six sites, one class** — applying the helper to all six is clean, but the three config-loads
  have lower esm risk than the three package-loads. there's a mild "are we over-applying?" tension
  (q1) — best-guessed toward uniform application, flagged for the wisher.
- **the whole defect was invisible** — a `console.warn` swallowed a registry-emptying failure.
  the fix restores the brain but leaves the quiet-warn pattern in place (in scope: fix the load;
  out of scope: make the drop louder). that unaddressed observability gap feels slightly unfinished.

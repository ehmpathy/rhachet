## what blocks me

the production fix is **done and correct**, but it is fundamentally incompatible with the repo's
jest test harness, and i cannot validate the resolution inside this sandbox.

**the prod fix (complete):**
- `src/infra/importEsmSafe.ts` — a genuine runtime esm-capable dynamic import via
  `new Function('specifier','return import(specifier)')` (per issue #429). opaque to tsc's commonjs
  down-level, so real node runs a real `import()` that loads esm-only brains.
- swapped `await import()` → `importEsmSafe` at the 3 brain/plugin load-sites:
  `getAvailableBrains.ts`, `getBrainHooksAdapterByConfigImplicit.ts`, `getLinkedRolesWithHooks.ts`.

**the wall:**
- under jest, `importEsmSafe` throws `TypeError: A dynamic import callback was invoked without
  --experimental-vm-modules`. jest's module runtime refuses real `import()` unless node is started
  with that flag.
- this breaks the **extant** `getAvailableBrains.integration.test.ts`: `getAvailableBrains` now
  catches the thrown error, warns, and returns `{ atoms: [], repls: [] }`, so 4 assertions fail with
  `atoms.length = 0` (was passing before my change).

**the root cause of why this was hidden:**
- `@swc/jest` (not tsc) transpiles tests, and `jest.integration.config.ts:37`
  `transformIgnorePatterns` transforms the esm brain packages (`@anthropic-ai`, `@openai`) to cjs.
  so in jest, every brain is cjs and the old `await import()` → require() shim worked — the prod bug
  **never reproduced in jest**. the fix that makes prod correct is exactly what jest cannot run.
- this is precisely the vision's a6 / h7 assumption ("the test toolchain is not the production
  compiler; the clamp must target the built dist"), now confirmed empirically.

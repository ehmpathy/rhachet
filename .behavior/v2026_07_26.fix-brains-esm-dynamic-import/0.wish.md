# wish: fix(brains) — load brain packages via true dynamic import() so esm-only brains load

## .what (one sentence)

make `getAvailableBrains` load brain packages whose dependency graph is esm-only
(e.g. the anthropic brain, which pins the esm-only `@anthropic-ai/claude-agent-sdk`),
without a module-system change, so no brain silently drops out of the registry.

## .source (authoritative)

the full write-up — defect, root cause, proposed fix, and provenance — lives in the
GitHub issue. treat that as the spec of record:

- `ehmpathy/rhachet` issue **#429** ("fix(brains): load brain packages via true
  dynamic import() so esm-only brains load")

## .why

`getAvailableBrains` -> `importBrainsFromPackage` does `await import(pkg)`, but rhachet
compiles under `tsconfig module: "commonjs"`, so tsc down-levels that into a
`require()` shim. `require()` cannot load an esm-only package, so the anthropic brain
throws `Cannot use import statement outside a module`, the error is swallowed to a
`console.warn`, and the brain drops from the registry. downstream: every
`rhachet-roles-ehmpathy` `.evals/` test that spawns `rhx review` fails with
`UnexpectedCodePathError: review output lacks blocker count` because the review ran
brainless. that repo's `suite / test-integration` rollup is blocked solely by this
upstream defect.

## .acceptance (what proves it done — authoritative)

1. a genuine runtime dynamic `import()` runs at runtime (not a tsc-rewritten
   `require()`), so brain packages with an esm-only dep graph load.
2. **no module-system change** — rhachet keeps commonjs output (`type: null`,
   `main: dist/index.js`); tsconfig is NOT flipped to node16/nodenext. extant cjs
   brains (fireworks, xai) load exactly as before — strictly a superset, no path
   regresses.
3. fault isolation preserved — one brain that fails to import still warns and returns
   `{ atoms: [], repls: [] }`, so a single bad brain never sinks the registry.
4. **regression clamp (required)**: a test installs an esm-only brain fixture and
   asserts `getAvailableBrains` returns it — RED on the `require()` version, GREEN on
   the fixed version (prove it bites).
5. the peer call-sites are audited for the same `await import(...)` -> `require()`
   downlevel (e.g. `genContextBrain`, `getOneBrainReplByRef`, `getOneBrainAtomByRef`);
   apply the same indirection wherever a brain/plugin loads that way.
6. release as a rhachet patch (e.g. 1.44.x); downstream consumers then bump the pin.

## .the proposed fix (advisory — the mechanic owns the HOW)

issue #429 sketches a `new Function('specifier', 'return import(specifier)')`
indirection to hide the dynamic import from tsc's commonjs downlevel. that is a
reasonable salty guess from outside the repo — take it as a start point, not a spec to
copy verbatim. if the repo has a cleaner in-repo pattern that achieves the outcome (a
real runtime esm-capable import under a cjs build), prefer it and note why in the
vision yield. the OUTCOME above (esm-only brains load, no module-system change,
regression clamp) is the contract; the exact indirection is the mechanic's call.

wish =

# fix keyrack aws.params error guidance — never trim the real cause, name the missing privilege

## .the desire

when `rhx keyrack set --vault aws.params` (or get/del) fails, i want the error to tell me the
TRUE cause and the EXACT fix — on the first attempt, not after a 30-minute forensic hunt. today
it hides the real AWS error behind a wrong guess and sends me to chase credentials when the real
problem is an absent IAM action.

## .the incident that motivates this (real, 2026-08-05)

a teammate ran `keyrack set --owner ehmpath --key GITHUB_TOKEN --org @all --env camp --vault
aws.params` on an EC2 box with a healthy instance role. it failed with:

```
✋ blocked: aws.params found no AWS identity
   hint: for --org @all run on a box whose instance role can read this param ...
```

every word of that was wrong-headed. the box HAD an identity (STS answered fine, IMDS vended
creds, the node SDK resolved them). the real failure was an IAM denial on `ssm:DescribeParameters`
— a metadata read the findsert does BEFORE the write. it cost ~30 minutes and FIVE wrong
asserted causes, two of which nearly loosened a security boundary that was already correct.

root cause of the mislabel: `asKeyrackAwsParamErrorGate` gate 2 matches the error MESSAGE with
`/no identity/i`, and every AWS `AccessDeniedException` ends with "...because no identity-based
policy allows the action." so a permission denial gets laundered into "no AWS identity", and the
raw AWS error (which named `ssm:DescribeParameters` plainly) was attached as metadata but was
NEVER rendered to the human.

## .what i want (bounded scope)

1. **forward the raw AWS error, always.** the verbatim AWS `name: message` (which names the
   denied action + resource) must reach the human-visible output on EVERY error branch — as an
   ADDITIVE layer under keyrack's hint, never a substitution. (this is the failtrim principle.)

2. **classify on the stable error NAME, never message prose.** gate 2 ("no credentials") must
   trigger on `name === 'CredentialsProviderError'` only — drop the `/no identity/i` regex
   entirely. and check the AccessDenied gates BEFORE gate 2 (fix the gate order).

3. **name the rejected privilege + the full required grant.** an AccessDenied error must state
   the denied `action` + `resource` (from AWS) AND render the complete, paste-ready list of IAM
   actions this op needs, so the fix is copy-paste. the required set is knowable up front (the
   findsert call sequence):
     - `ssm:DescribeParameters` on `*`  (⚠️ no resource-level scope — MUST be `*`; the exact
       trap that bit this policy)
     - `ssm:PutParameter`, `ssm:GetParameter` on `parameter/keyrack/infra/vault/aws.params/*`
     - `ssm:ListTagsForResource` on the same path (fires on the post-write read-back)
     - `kms:Encrypt`, `kms:Decrypt` on the encrypt key

4. **preflight the cheap gates BEFORE the secret prompt.** region, peer, identity, and the vault
   name are all knowable before the human types a 40-char secret. today the human enters the
   secret THREE times only to be rejected for pre-knowable conditions. validate upfront; never
   waste the human's effort on a form that was doomed before submission.

5. **gate the peer-of-peer crash.** an absent transitive `declastruct` (CJS `MODULE_NOT_FOUND`)
   currently hard-crashes with a 200-line require-stack instead of a friendly "install X" gate.
   widen the peer-defect allowlist so it fails loud and clean.

## .out of scope

- dropping the roundtrip-verify — it is WANTED (it proves the write landed and reads back). the
  read+decrypt grants it needs are by design, not bloat.
- edits to the param-name scheme, the mech set, or the org-scope hardcut — those are correct.

## .the proof it's fixed

- a regression test feeds `asKeyrackAwsParamErrorGate` each REAL AWS denial string
  (`DescribeParameters`, `ListTagsForResource`, `PutParameter`, `GetParameter`, `kms`) and asserts:
  (a) it classifies to the correct gate (NOT gate 2), and (b) the raw AWS action name survives in
  the rendered output.
- a journey test resolves creds via instance role with NO env-var creds (the IMDS rung CI never
  exercised — CI got creds as env vars from OIDC configure-aws-credentials).
- manual: on a box granted only Put/Get (the ahbode-camp-grove-role state), `set` reports
  "identity cannot ssm:DescribeParameters" + the full grant list — not "no AWS identity".

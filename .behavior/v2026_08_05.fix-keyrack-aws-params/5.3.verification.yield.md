### blocker 1 — real-AWS happy-path integration: local-only gap, CI is the authoritative env

`getOneKeyrackAwsParam.integration.test.ts`, `vaultAdapterAwsParams.integration.test.ts`,
`setKeyrackAwsParamGithubApp.integration.test.ts`, `delKeyrackAwsParam.integration.test.ts`, and
`unlockKeyrackKeys.integration.test.ts` fail locally with:

```
TypeError: A dynamic import callback was invoked without --experimental-vm-modules
```

**root cause (verified):** these tests source real AWS creds via `useKeyrack()`, which re-vends the
SSO profile as STATIC env creds so the AWS SDK avoids its lazy SSO `import()`. but
`rhx aws.whoami --env test` shows `ehmpathy.test.AWS_PROFILE` is **absent** on this host — so
`useKeyrack` sets no static creds, the SDK falls to its dynamic SSO import, and jest (CJS, no
`--experimental-vm-modules`) rejects it. `useKeyrack` returns early under `CI` (creds arrive via an
OIDC-minted attached role), so these run for real in CI — the environment they were designed for.

**why this does NOT gate the fix's verification:**
1. these files are **unchanged by the fix** — they exercise SUCCESS roundtrips (get/set/del/unlock),
   a code path the error-guidance change does not touch (the fix alters only error branches).
2. the fix's OWN changed surface IS fully proven locally — unit (the gate classifies every real
   denial string + forwards the raw AWS action), del+get **emulator** integration (creds-free, real
   denial through the whole path), and acceptance journey (real CLI → real deny → grant tree).
3. their authoritative environment is CI (OIDC attached role), where they were green on main.

**the natural, correct verification:** push this branch → open the PR → CI re-runs the integration
suite with the OIDC attached role against the fix's code. that is the sanctioned current-state proof
for inherited real-AWS coverage — not a local `AWS_PROFILE` fill. (a local fill via
`rhx keyrack set --key AWS_PROFILE --env test --vault aws.config` remains a valid *optional* way to
run them on this host, but is not required, since the fix does not change what they exercise.)

### blocker 2 — github-app interactive-prompt snapshot: host pty echoes typed stdin — ✅ RESOLVED

`keyrack.aws-params.githubApp.acceptance.test.ts` case4 failed: the received pty output carried an
extra line — the literal typed secret (`xai-fixture-secret`) — before the masked prompt:

```
  🔐 keyrack set @all.test.XAI_API_KEY via PERMANENT_VIA_REPLICA
+ xai-fixture-secret
  enter secret for XAI_API_KEY: ******************
```

**root cause:** the pseudo-TTY on this host echoes the first stdin bytes before keyrack switches to
masked input; the snapshot was recorded on a host/pty that did not echo. `cleanPtyOutput` strips
ANSI/paths/AWS-advisories but not this echoed-secret line.

**deeper root cause (found on the fix run):** the echo is **INTERMITTENT** — case4 passed 22/22
when the githubApp suite ran in isolation, but the echo surfaced under concurrent-suite load (the
full `path://keyrack.aws-params` scope, 4 files). so the echoed-secret line is non-deterministic
pty noise whose *presence* varies run-to-run — a genuine flake, not a fixed host trait.

**fix (applied):** STRIP the echoed-stdin line before the snapshot (not a `__SECRET__` redact) —
`cleanPtyOutput(result.stdout).split('\n').filter((l) => l.trim() !== 'xai-fixture-secret').join('\n')`.
a strip (vs redact) is required because the line's *presence* is what flakes: redaction still leaves
a `__SECRET__` line that the committed snapshot lacks. the strip is idempotent — no-op when the host
does not echo, removes the line when it does — so the snapshot is deterministic by construction, and
the plaintext secret can never land in a committed snapshot. this clamps the whole "host echoes typed
stdin" edge-case class (rule.require.clamp-edge-cases), not just the one value.
re-verified across the exact runs that exposed the flake:
- `path://keyrack.aws-params` full scope (the run that failed 77/1 pre-fix) = **78 passed, 0 failed**
- `path://keyrack.aws-params.githubApp` in isolation = **22 passed, 0 failed** (x2)

## peer-review convergence (i002 l3 blockers)

the l1 sweep (r1–r8) approved 0/0; l3 r9 approved 0/0. two l3 blockers were raised and are now
fixed in code + re-proven green:

**r10 (enroll-verif-snapshot-blemishes) — the grant tree flattened its header.**
the render contract `getKeyrackBlockedReport.split(';')` rendered every hint part as an equal-weight
`├─` peer, so the grant-list header ("aws.params set needs these grants on this identity:") sat
flat beside its own grant items instead of as their parent — a real `rule.require.treestruct-output`
defect that lands in the incident scenario the fix targets. (this is the same `;`-join render contract
flagged-and-deferred as *informational* at 5.1; r10 promoted it to a blocker, so it is now closed, not
deferred again.)
- **fix:** `getKeyrackBlockedReport.ts` now groups the hint parts into a two-level tree — a part that
  ends with `:` becomes a HEADER whose subsequent parts nest one level deeper as its CHILDREN. a
  no-`:` part, or a header with no children, still renders as a flat leaf, so every non-grant hint is
  unchanged.
- **blast-radius proof:** grep-verified the only `:`-terminated hint *child* across all keyrack
  snapshots is the grant header itself; every other `:` line is the `hint:` node label or a
  `recipients:` status line (a different code path). empirically: full unit (1059) + all keyrack
  acceptance suites green, with **exactly one** snapshot re-snapped — the journey case2 grant tree,
  now correctly nested (header = `└─`, its 5 grants nested at 12-space `├─`/`└─`).
- **clamp:** new `getKeyrackBlockedReport.test.ts` (6 tests, green) asserts the header-nest render
  (12-space child indent), the flat-no-header path (no deeper nest appears), and the single-part
  inline path. a flat 9-space render fails the nest assertion — the clamp bites the exact blemish.

**r11 (enroll-verif-test-intent) — case4 filtered the snapshot input without a standalone leak-guard.**
the githubApp case4 deecho strip (blocker-2 fix) narrows what the snapshot can catch — a line equal to
the raw secret is stripped before the assertion, so a broken mask and a benign host-pty echo look
identical to it. every other secret path in this PR (case2 here, journey case2) keeps a standalone
`not.toContain(secret)` on raw output; case4 was the one place that pattern was dropped.
- **fix:** added a standalone `then` in case4 that asserts the mask guarantee on RAW stdout,
  independent of the snapshot — it bounds the raw-secret lines to `<= 1` (the single possible host-pty
  echo, which keyrack cannot prevent) AND asserts the masked prompt line
  (`enter secret for XAI_API_KEY: ******************`) is present. together they prove keyrack masked
  the secret, not merely that a pre-stripped snapshot matched. the snapshot filter stays for
  determinism. re-proven: githubApp acceptance **151 passed, 0 snapshots updated** (the new assertion
  needs no snapshot change).

both blockers are fixed at cause, grain-appropriately clamped, and re-proven green — not deferred.

# vision: keyrack aws.params errors that name the true cause + the exact fix

## the outcome world

### day-in-the-life (after)

a teammate provisions a grove-wide secret on a fresh EC2 box:

```
$ rhx keyrack set --owner ehmpath --key GITHUB_TOKEN --org @all --env camp --vault aws.params
🔐 keyrack set @all.camp.GITHUB_TOKEN via PERMANENT_VIA_REPLICA
   ✋ blocked: this identity cannot ssm:DescribeParameters

   why (raw AWS): AccessDeniedException — User: arn:aws:sts::261599400667:assumed-role/
     ahbode-camp-grove-role/i-... is not authorized to perform: ssm:DescribeParameters
     on resource: * because no identity-based policy allows the action

   fix: aws.params set needs these grants on this identity —
     ✅ ssm:PutParameter        on parameter/keyrack/infra/vault/aws.params/*
     ✅ ssm:GetParameter        on parameter/keyrack/infra/vault/aws.params/*
     ❌ ssm:DescribeParameters  on *   ← MISSING (note: needs "*", no resource scope)
     ❌ ssm:ListTagsForResource on parameter/keyrack/infra/vault/aws.params/*  ← MISSING
     🔑 kms:Encrypt, kms:Decrypt on the key that encrypts these params
```

they read line 1, see the denied action, paste the two missing statements into the role, re-run,
and it works. total time: under a minute. crucially, the secret prompt never appeared — the cheap
gates ran first, so no wasted 40-char paste.

### before/after contrast

| dimension | before (today) | after (this wish) |
|---|---|---|
| what the error says | "found no AWS identity" | "cannot ssm:DescribeParameters" + raw AWS line |
| where it points you | credentials / SSO / instance-role (WRONG) | the exact denied IAM action (RIGHT) |
| the raw AWS error | attached as metadata `cause`, never rendered | rendered verbatim under the hint |
| the fix | reverse-engineer it over 30 min | paste-ready grant list in the error |
| secret entry | typed 3× then rejected for pre-knowable gates | prompted only after cheap gates pass |
| absent declastruct peer-of-peer | 200-line uncaught require-stack crash | clean "install X" gate |

### the "aha" moment

the value clicks the instant a human sees the raw `ssm:DescribeParameters` on line one instead of
"no identity". the whole 30-minute hunt existed because the tool asserted a cause it never measured
and hid the one line that named the truth. after: the tool forwards the truth and names the fix, so
the human never leaves the terminal.

## user experience

### usecases / goals
- **provision a secret into SSM** (`keyrack set --vault aws.params`) on a box with partial IAM
  grants, and know exactly which grant is absent.
- **unlock / read** (`keyrack unlock`/`get`) and get the same clarity when a read/decrypt grant is
  absent.
- **destroy** (`keyrack del`) with the same denied-action clarity.
- **run on a fresh box** without the optional `declastruct-aws` peer and get a clean install hint,
  not a stack trace.

### contract inputs & outputs
- **input**: the same CLI the human types today — no new flags. `--owner --key --org --env --vault
  aws.params`.
- **output (changed)**: the error surface. every failure branch now renders `[keyrack hint] +
  [verbatim AWS name: message] + [the required-grant list when it is an AccessDenied]`.
- **the required-grant list is static** — derivable from the op (set/get/del) because the findsert
  call sequence is known ahead of time. no probe needed for v1.

### timeline (the fixed set flow)
1. human runs `keyrack set ... --vault aws.params`
2. **preflight (before the prompt)**: vault legal → region present → **peer present** → identity
   derivable. NOTE: today region (line 144) + identity-derivation (line 172) ALREADY run before the
   secret; the ONE gate this wish LIFTS is the PEER LOAD (today in the leaf at
   `setKeyrackAwsParamReplica.ts:76`, AFTER the secret is acquired). so preflight's real job is:
   pull the peer-load ahead of the prompt, and keep the others where they are. any absent → fail
   loud NOW, name the fix, exit. no secret asked.
3. mechanism prompt + secret entry (only if preflight passed)
4. write → on AccessDenied: classify by error NAME, render the denied action + raw AWS line + grant
   list. on success: the write + roundtrip-verify complete.
   NOTE: the write-time PERMISSION denial cannot be preflighted (we cannot know a grant without an
   attempt at the write). so "found no AWS identity" in the incident was the WRITE-TIME error gate,
   not the identity-DERIVATION at line 172 (which succeeds: @all → imds). the error QUALITY at the
   write — failtrim forward + named action — is what carries this case, not an earlier gate.

## mental model

- **how a user describes it to a friend**: "when keyrack can't write the secret, it tells you the
  exact AWS permission you're missing and hands you the policy to paste — instead of lying that you
  have no credentials."
- **analogy**: a good compiler error. today's error is `error: something went wrong`; the wish is
  `error: undefined name 'ssm:DescribeParameters' at line 1 — add it here`.
- **their terms vs ours**: users say "permission", "IAM", "the policy". we say "gate", "grant",
  "identity", "the findsert call sequence". the error output should speak THEIR words on the surface
  (name the AWS action + resource) and keep our words in the code.

## evaluation

### how well it solves the goal
- directly kills the root failure: a wrong-guessed error that hid the true cause. the raw error is
  always forwarded, so even a future misclassification degrades to "unhelpful hint", never
  "actively lying".

### pros
- the fix is paste-ready → sub-minute resolution vs 30-min hunt.
- classify-on-NAME (not message prose) is drift-proof: AWS rewords messages, but error `name` is a
  stable contract.
- preflight-before-secret respects the human's effort (never a doomed form submission).
- no new flags, no contract-shape change. mostly an error-surface + gate-order improvement; the one
  flow change is preflight (lift the peer-load ahead of the secret prompt) + the peer-defect
  allowlist widen — both internal, no CLI-input change.

### cons / tradeoffs
- the static grant list can drift if declastruct-aws changes its call sequence (e.g. adds a new
  metadata read). mitigation: the regression test that feeds each real denial string will catch a
  gate that stops classifying; and the raw-error forward means a NEW denied action still shows its
  true name even if not yet in our static list.
- rendering the full grant list on every AccessDenied is more verbose. acceptable — verbosity at
  the moment of failure is exactly when the human wants it.

### edgecases → pit of success
- **denied action we don't yet enumerate** (a future declastruct call) → still forwarded verbatim
  by the failtrim guarantee; the human sees the real action even without a bespoke gate.
- **genuinely absent credentials** (no role, no env) → `name === 'CredentialsProviderError'` still
  classifies to the credentials gate correctly — the tightening removes only the false-positive
  prose match, not the true-positive name match.
- **kms vs ssm denial** → distinct gates already exist (gate 7 kms, gate 4 ssm); keep them, and add
  Describe/ListTags awareness so the named action is precise.
- **the DescribeParameters-needs-`*` trap** → the grant list calls it out inline, so a policy author
  can't repeat the path-scoped-matches-no-params mistake that started this.
- **secret never leaks in the forwarded error** → the raw AWS error we forward names only the
  principal arn + action + resource (the param NAME), never the param VALUE. an AccessDenied on
  `PutParameter` fires BEFORE the value is written, so it carries no secret. this is the safety
  boundary that makes "forward raw, always" safe — and the regression test MUST assert the
  rendered output carries the denied action name but does NOT carry the secret value.

## open questions & assumptions

### assumptions made
- the static grant list matches declastruct-aws's actual findsert call sequence (Describe →
  ListTags → Put → Get + kms). the SSM actions are VERIFIED empirically this session: camper's
  box, granted only Put/Get, failed at DescribeParameters; add Describe-on-* + ListTags and `set`
  completes. NOTE the asymmetry: the SSM lines are DENIAL-proven; the kms lines are NOT — camper's
  box already held kms, so no kms denial was ever observed. kms is structurally-required (a
  SecureString must encrypt to write, decrypt to roundtrip) but a box on the default `alias/aws/ssm`
  key may already hold it implicitly. so the grant list must present kms as
  structurally-required-but-not-denial-observed, not with the same certainty as the SSM lines.
- a verbatim forward of the raw AWS error leaks no secret: AWS ssm errors name the principal +
  action + param NAME, never the param VALUE, and an AccessDenied fires before the value is
  written. this is an INFERENCE (the wish assumes it implicitly), made explicit here and clamped
  by a test.
- error `name` fields (`CredentialsProviderError`, `AccessDeniedException`) are stable across
  AWS SDK v3 minor versions. (standard SDK contract — names are the stable surface, messages are not.)

## what is awkward

- **the static grant list is a duplication of declastruct-aws's internal call sequence.** we're
  encoding, in keyrack, knowledge of which SSM actions declastruct's DAO makes. if declastruct
  changes, our list is stale. this is the uncomfortable tradeoff — but the failtrim forward is the
  safety net (a new denied action still shows verbatim), so the static list is an ergonomic bonus,
  not a correctness dependency. worth a note in code that the list mirrors declastruct's sequence.
- **preflight identity derivation is a soft check.** we can confirm creds *derive*, but not that
  they can *write*, without an attempt at the write. so preflight catches "no identity at all"
  early, but a permission denial still only surfaces at the write. that's correct (we can't know
  grants without a try), but it means the "validate upfront" promise is partial — cheap gates
  upfront, the permission truth at the write. the error quality at the write is what carries the
  rest.
- **verbosity vs calm.** rendering a 5-line grant block on every denial is louder than the current
  one-line hint. it fights the "minimalist output" instinct — but at the failure moment, the human
  wants the whole map, so this is the right place to be verbose.

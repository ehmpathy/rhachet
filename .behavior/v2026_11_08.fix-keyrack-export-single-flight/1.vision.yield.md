# vision: keyrack aws export runs single-flight per profile (#656)

## the outcome world

a box runs one `aws configure export-credentials --profile P` at a time. the first caller exports and
writes the result to an owner-only cache file; every concurrent caller waits on a disk mutex, then
reads that file. a later caller reads the file and spawns no aws cli at all, until the credentials
near their own expiry.

| | before | after |
|---|---|---|
| 33 unlocks of one profile, load 70 | 66 python exports, each ~1 core, several time out | 1 export, 65 file reads |
| a burst at unlock | N exports race one sso refresh | 1 export; the rest wait, then read |
| a caller killed mid-export | no shared state to wedge | its lock lapses with its lease; the next caller exports |
| cost of a warm read | ~2–15s cli startup | one small file read |

**the aha:** the export is idempotent within its expiry, so it is a value to cache, not an act to repeat.

## the contract

one operation, `getOneAwsProfileExport({ profile })`, is the only path keyrack uses to export a
profile's credentials. it returns the same shape `deliverForGet` returns today:
`{ credentials: Record<string,string>, expiresAt: IsoTimeStamp }`.

0. the identity of an export is the profile name **and** the config files the cli reads it from
   (`AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, else their defaults) — one profile name under two
   config files names two different creds. both the cache file and the mutex key carry
   `profile=$profile.$sha8`, where `$sha8` hashes those two paths. each cache file also records the
   profile and both paths, so a read checks the identity, not merely the name
1. read the cache file `~/.rhachet/keyrack/cache/aws.export/profile=$profile.$sha8.json`. valid (more
   than 5 minutes to `expiresAt`) → return it. a file that does not parse, lacks a key, or records
   another identity counts as absent
2. else take the box mutex on that same identity (with-simple-mutex over an on-disk cache, per
   requirement case 6)
3. inside the hold, re-read the cache (a peer may have filled it while we waited). valid → return it
4. else run the export (hang guard 2 min), parse it, write the cache file (dir 0700, file 0600, atomic
   rename), return it. a failed or hung export writes no cache and throws, with the profile and a hint

a second form, `{ profile, refresh: true }`, skips steps 1 and 3. it deletes the cache entry the moment
it is called — before it queues for the key — then, under the mutex, deletes it again, exports, and
writes the new value. the post-login refresh uses it, so creds minted before a re-login — perhaps for a
different user — are gone before the refresh even waits, and a read caller that arrives in that wait
finds no cache and queues behind it. not even a failed refresh leaves them. the one residue: a read
export already in flight from before the login may land its value before the refresh takes the key —
the same creds that caller's raw export returns today (fulcrum F5).

the lease (3 min) outlasts the hang guard (2 min), so a live holder never loses its key; the wait bound
(5 min) outlasts the lease, so a waiter behind a killed holder acquires after the lease lapses.

| 2 | a warm read spawns no cli |

| 4 | a dead holder does not wedge the next caller |

| 9 | a hung export fails every caller loud, within the wait bound |

## mental model

"keyrack remembers the last aws export for each profile until it's about to expire, and only one
process refreshes it at a time." a turnstile in front of a vend machine: one person buys, the rest
take from the tray.

## evaluation

- solves the cost half of #656: N concurrent callers → 1 export
- pro: every keyrack export (the unlock pre-warm, the expiry read, the post-login refresh) goes through
  one op and one cache
- con: credentials now rest on disk in plaintext, owner-only — the same trust the aws cli's own
  `~/.aws/cli/cache` already takes
- edge: a revoked session still returns cached creds until expiry — the same as the aws cli cache, and
  `validateSsoSession` still checks the sso token through the sdk before it reads the export

## open questions & assumptions

- **[answered]** is a 5 min freshness margin enough? yes, by logic: an sso role session lasts 15 min at
  the least (1 h by default), so a cached value is valid for most of its life; and the grant a caller
  gets carries the creds' own `expiresAt`, so the daemon drops it on expiry and the caller re-unlocks.
  the margin only keeps a caller from creds with seconds left. fulcrum F3
- **[answered]** may the post-login refresh read the cache? no — it reads none, deletes the entry, and
  writes the new export (`refresh: true`), so a re-login neither reads nor leaves pre-login creds. its
  cache-clear retry stays as is. fulcrum F2
- **[answered]** should waiters behind a failed or hung export fail at once, from a shared marker? no —
  each runs its own export in turn, and a waiter past the 5 min bound fails loud. today's export has no
  hang guard at all (`mechAdapterAwsSso.ts:142`, `vaultAdapterAwsConfig.ts:209`), so this bounds what was
  unbounded. fulcrum F4
- **[answered]** does the cli print `AWS_CREDENTIAL_EXPIRATION` in `--format env-no-export`? the extant
  parse already reads it and falls back to 55 min when absent (`mechAdapterAwsSso.ts:170-174`); the cache
  reuses that rule, so no new dependency on the cli's output
- **[answered]** does a local-disk with-simple-mutex exclude across processes? yes — proven by
  `withRepoMutex.integration.test.ts` [case6], two processes and 100 bumps
- **[answered]** should waiters share one stale-session read (#652)? out of this wish's bounds; each
  waiter that finds no cache runs its own export in turn, serialized
- **[wisher]** F1 moves the clamp of requirement case 6 from `withRepoMutex.ts` to `withDiskMutex.ts`.
  the requirement is unchanged, but only the wisher amends an inventory entry, so the case 6 prose is
  edited to name the new owner and the amendment is flagged for the wisher at the fulcrum council. it
  does not halt the drive: the rework is clean

## groundwork

- external: `with-simple-mutex` readme — lease-based, native cache expiry evicts a dead holder's key,
  `SimpleMutexLeaseExpiredError` fails a holder that outruns its lease, no heartbeat in v1
- internal: export call sites — `mechAdapterAwsSso.ts:143` (deliverForGet), `vaultAdapterAwsConfig.ts:210`
  (validate pre-warm), `:562`/`:582` (post-login forced refresh). requirement case 6 + its lint clamp
  (`withRepoMutex.integration.test.ts` [case7]) pin `with-simple-mutex` to one owner file. keyrack box
  state lives under `~/.rhachet/keyrack/` (`getKeyrackHostManifestPath.ts`), resolved via
  `src/infra/getHomeDir.ts`, which reads `HOME` so a test can isolate it
- internal: the multiplier. each unlock of an aws key (`unlockKeyrackKeys.ts:364-402`) runs
  `adapter.isUnlocked` → `validateSsoSession` → an export (`vaultAdapterAwsConfig.ts:210`), then
  `adapter.get` → `deliverForGet` → a second export (`:626`), which it needs only for `expiresAt` — the
  secret it returns is the profile name. so one unlock spawns two exports, and N processes that unlock
  spawn 2N. through the cache, the second export in a process is a file read, and so is each process's
  after the first. the `keyrack get` cli reads the daemon's store (`handleGetCommand.ts:33`), not the
  vault, so it spawns none either way

## what is awkward?

- the lint clamp names `withRepoMutex.ts` as the one importer, but a box lock is not a repo lock. the
  generic hold (cache, lease, wait, timeout) moves into `src/infra/lock/withDiskMutex.ts`, which becomes
  the one owner; `withRepoMutex` delegates to it. the requirement (one owner, through with-simple-mutex)
  is unchanged; the clamp's path moves with the owner
- the two unit suites that drive the export (`mechAdapterAwsSso.test.ts`, `vaultAdapterAwsConfig.test.ts`)
  fake `child_process` and part of `fs`, and let all other paths through to the real disk. a disk cache
  would then write their fake creds under the real `~/.rhachet` and carry them from one case to the
  next. each suite points `HOME` at a temp dir and clears the cache before each case
- `deliverForGet` today puts `stdout` and `credentials` into a MalfunctionError's metadata — a credential
  leak into logs. the new op names only the keys it found

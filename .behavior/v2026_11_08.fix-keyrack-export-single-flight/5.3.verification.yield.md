### dogfood on this box — the capability gap

a real dogfood of `rhx keyrack unlock` on an aws.config key needs an sso profile. ehmpath has none: its
`AWS_PROFILE` sits in os.direct, and `ehmpathy.test.ehmpath` is not an sso profile. the bare run, from the
repo root, against the real HOME:

```
$ npx rhx keyrack set --owner ehmpath --key PLAYTEST_AWS_PROFILE --env test --vault aws.config --exid ehmpathy.test.ehmpath --at <a manifest under .temp/>
🔐 keyrack set
   └─ ✋ ConstraintError: aws profile is not an sso profile; the aws.config vault needs one
      ├─ profileName: ehmpathy.test.ehmpath
      └─ hint: point the key at a profile with sso_session or sso_start_url in its aws config, or store 'ehmpathy.test.ehmpath' in os.direct
```

before this round the same run said `sso session not valid; run aws sso login`, a cure that cannot
work; that misdirection is now fixed (vault [t1.8]). the run left no host entry
(`rhx keyrack list --owner ehmpath` holds no `PLAYTEST_AWS_PROFILE`).

so the bare unlock over a real sso export is the one proof this box cannot run. what stands in its place:
the real aws cli runs in `genAwsProfileExport.awscli.integration.test.ts`, and
`rhx keyrack.aws.export.rehearsal` is a sandbox rehearsal (a fake aws cli, a scratch HOME) that prints what
a human sees on each path. the absent sso profile is the gap; a human with one can run
`npx rhx keyrack set --key <K> --env test --vault aws.config --exid <their sso profile>` and then
`npx rhx keyrack unlock --env test --key <K>` twice to see the second served from the cache.

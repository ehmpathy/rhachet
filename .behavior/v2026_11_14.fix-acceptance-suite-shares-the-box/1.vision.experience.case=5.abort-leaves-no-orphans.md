# case 5 — abort-leaves-no-orphans · runner · sharp · critipath

## .narrative

kai starts the enroll suites, sees a typo in the scope, and hits ctrl-c two seconds in. or a case
blows its 90s jest timeout. or `--forceExit` ends jest while a clone is still live. every one of
these ends skips the test's own `afterAll`.

before: the test had spawned `bin/run enroll claude`, which spawned `stubBrainCli.cjs` as the
brain under a managed pty. jest went away; the pair did not. `enroll` forwards only SIGINT and
SIGTERM to its brain (`genPtyCloneHostFromProcess.ts:46-55`), not a hangup and not the loss of
its parent, and the stub parks on `process.stdin.resume()` with no `end` handler
(`stubBrainCli.cjs:291-304`). so the pair was reparented to init and lived for hours. 310 such
processes were counted on one laptop, ~18G of heap, 22G pushed to swap.

after: the abort cuts the tree at every link, and each link fails safe on its own:

- the stub exits on stdin end, on SIGHUP, and after a hard cap whatever happens — a stub can never
  outlive its purpose, even if all else fails
- `enroll` treats the loss of its host (hangup, stdin end, parent death) as a stop: it ends its
  brain, then itself (case 10 — the same fix serves prod)
- the harness that spawns the cli in a test owns the child: it is spawned in its own process
  group, and the group is ended when the test ends, however it ends. today's
  `spawnRhachetCliBackground.kill()` sends one SIGHUP to one pid and, if the child lingers past
  5s, only warns (`spawnRhachetCliBackground.ts:264-283`); after, it ends the group and escalates
- a **detached** clone (the async enroll a `spawnSync` caller gets, re-exec'd into its own
  session by `genCloneEnrollDetached.ts:89-102`) is designed to outlive its baker, so no hangup
  can reach it. today its only teardown is an `afterAll` that says `exit 0` to it
  (`enroll.acceptance.test.ts:1941-1948`); if that say fails or never runs, the host and its stub
  live on. after, the run's teardown ends every process that carries this run's id (case 6), so a
  detached clone a test forgot is ended at the latest when the run ends

so ctrl-c leaves no pair behind. and if a future change breaks one link, the other two still
hold — and case 6 turns the break red.

why critipath: aborts are routine (ctrl-c, timeouts, `--forceExit` on every run). each one leaked
a pair; the pairs are what made the laptop crawl.

why it fails safe: fast (the stub dies within seconds of its pty's loss), loud (case 6 names any
survivor), and it teaches the fix (case 6's message names the link that failed).

## .bdd `[tn]` timeline (sketch)

```
given a scoped run of the enroll suites, a clone live under `bin/run enroll claude`
  when [t0] kai hits ctrl-c
    then jest ends
    and  within a few seconds 0 `bin/run enroll` and 0 stubBrainCli.cjs processes remain
given a case that blows its jest timeout with a clone live
  when [t1] jest marks it failed and moves on
    then the case's process group is ended; its stub is gone before the next case starts
given a detached clone baked by `invokeRhachetCliBinary(['enroll', …])` whose `exit 0` say never ran
  when [t2a] the run ends
    then teardown ends the detached host and its stub (they carry this run's id)
given a stub whose parent was SIGKILLed (no handler can run in the parent)
  when [t2] the stub's pty closes
    then the stub exits on its own (stdin end / SIGHUP), or at its hard cap at the latest
```

# case 12 — measure-the-bound · crew (pr author) · happy · alterpath

## .narrative

the wish is done only when a run on a shared box is measured and the before and after numbers
sit in the pr. mo, who authors the pr, must produce them, and the repo holds no tool for it
today — the issue's figures came from `top` and `/proc` by hand.

mo runs a measure that repeats one procedure twice — once on the pre-fix commit, once on the fix:
it records the box's baseline for a minute, starts a fixed peer workload, then starts a fixed
scoped acceptance run beside it, and samples load and cpu psi until both end. it prints a table
mo pastes into the pr:

```
🐢 acceptance neighbor measure
   ├─ box = 12 cores, laptop
   ├─ baseline = load 2.1, cpu psi 4%
   ├─ before (main @ 6e3b6771)
   │  ├─ peer workload = 41s (+64% over solo)
   │  ├─ load peak = 38.0
   │  └─ cpu psi avg = 71%
   └─ after (this branch)
      ├─ peer workload = 28s (+12% over solo)
      ├─ load peak = 9.4
      └─ cpu psi avg = 18%
```

why alterpath: the numbers can be gathered by hand with `cat /proc/loadavg`, `cat
/proc/pressure/cpu` and a stopwatch, as the issue did; a measure tool makes them repeatable and
comparable, not possible.

## .bdd `[tn]` timeline (sketch)

```
given a laptop with no acceptance run live
  when [t0] mo runs the measure against the pre-fix commit
    then it records baseline load and psi for a fixed window before it starts any work
    and  it times the peer workload alone, then beside the scoped acceptance run
    and  it prints load peak, cpu psi average, and peer slowdown
  when [t1] mo runs the measure against the branch
    then it prints the same table, so before and after compare row for row
  when [t2] mo pastes both into the pr
    then a reviewer grades the after row against the bound the wisher confirmed
```

> whether this is a repo skill, a one-off procedure in the verification stone, or a dev-env-setup
> tool is a blueprint choice; the experience is "the numbers are reproducible, not hand-copied".

# case 6 — a-new-leak-goes-red · runner · sharp · critipath

## .narrative

three months on, rio adds an acceptance test for a new `clone` flag. rio's helper spawns
`bin/run clone @solo --as @:sentry` in the background and, in the rush, never ends it. rio runs
`rhx test.acceptance.credfree --scope clone.flag`. every assertion turns green.

then the run ends red. at the bottom of the log, under the green tests, rio reads:

```
✋ ConstraintError: 2 processes outlived this acceptance run
   ├─ pid 48211  node bin/run.jit clone @solo --as @:sentry
   │  └─ cwd /tmp/test-fns/rhachet/.temp/…clone-flag…
   ├─ pid 48230  node src/.test/assets/stubBrainCli.cjs --settings …
   │  └─ parent 48211
   ├─ both were ended
   └─ fix: the test that spawned them must own the child — spawn it in its own
      process group and end the group in afterAll (see spawnRhachetCliBackground)
```

rio did not have to notice the leak. the run named the two survivors, said they were already
ended (so rio's box is clean), and pointed at the pattern to use. rio opens the helper, moves the
spawn onto the shared harness that owns its child, re-runs, and the run is green.

before this change, rio's test would have shipped green. weeks later, every crew's laptop would
start to crawl again, with ~100M per leaked pair and no thread to pull.

how it works underneath, for the curious: every process the suite spawns inherits this run's id
in its env; at the end of the run the suite looks for live processes that carry it. only this
run's own processes are touched — a peer's suite or rio's own claude never are.

why critipath: without this guard, cases 4 and 5 hold only as long as every future test author
remembers. a guard that turns a leak red is what keeps the fix from rot.

why it fails safe: fast (at the end of the run that leaked, not weeks later), loud (red, with
pids and argv), teaches the fix (names the pattern that owns a child), and leaves the box clean
even before the fix lands.

## .bdd `[tn]` timeline (sketch)

```
given rio's new test, whose helper spawns `bin/run clone …` and never ends it
  when [t0] rio runs the scoped suite and every assertion passes
    then rio sees the run end red, not green
    and  rio reads the ConstraintError: the two pids, their argv and cwd, "both were ended", and the fix
    and  rio's box holds no survivor from the run
  when [t1] rio moves the spawn onto the harness that owns its child, and re-runs
    then rio sees the run end green, with no leak notice
given rio's own claude seat and a peer crew's suite on the same box
  when [t2] rio's run ends
    then rio's seat and the peer's suite are untouched — they carry no id from rio's run
given a keyrack test whose session daemon outlives it by design, and no other survivor
  when [t3] the run ends
    then the run ends the daemon and stays green — a session daemon is the run's to reclaim
    and  rio reads one notice line, `ℹ reclaimed 1 keyrack daemon this run's tests left`
    and  a brain stub left beside it would still turn the run red, as in [t0]
```

> [t3] was found in execution: the reclaim vs leak split is `asLeftPartitioned`, proven by
> `ReporterAcceptanceBox.integration` [case2] (daemon only, green with the note) beside [case1]
> (a stub, red).

> how a process is matched to the run (env marker vs process group vs cwd under the run's temp
> root) is [research] in the yield (Q6). the red must not come from a throw in `globalTeardown`,
> which would skip jest's summary (yield Q7); the mechanism that keeps the summary is [research].

# 1.vision — the rhachet acceptance suite shares the box

## .the outcome world

### a day in the life, after

kai is on a 12-core laptop with three claude seats live. a seat changed the actors-yml code and
runs `rhx test.acceptance.credfree --scope actors-yml`. the first lines of the log read:

```
🐢 acceptance width
   ├─ box = shared (no ci host signal; CI=true alone does not widen)
   ├─ workers = 3 of 12 cores (shared-box default)
   ├─ priority = nice 10
   └─ to go wide: --maxWorkers 100%
```

the seats keep their pace. the scope matches three suite files, so the run takes as long as it
did yesterday. when it ends, `/tmp` holds
no fixture dir it minted and no brain stub it spawned is alive. kai does not think about the box
at all — which is the point.

on ci, the same suite reads `box = ci`, takes the width it always had, and runs at normal
priority. the shard wall times read the same as the last green run on `main`.

### before / after

| | before (measured on #748) | after |
|---|---|---|
| width off ci | `'50%'` of cores, every box | a shared-box default (a quarter of the cores, at least 1), unless the runner asks |
| priority | same as the seats | the whole suite tree at nice 10, so a seat always wins a contested core |
| width on ci | `'50%'` of the runner's vcpus (1 worker if the runner is the 2-vcpu box `jest.acceptance.shards.jsonc:4` describes; unverified on a live shard) | unchanged |
| `/tmp/rhachet-test-*` | never removed; 225 found | minted through the reclaimed temp root; zero after any end |
| brain stubs | 310 processes leaked on one laptop, oldest 7.4h, ~18G heap | none outlive the run; a new leak turns the run red |
| `rhx enroll` in prod | a hangup or a dead parent can leave the brain alive | every loss of the host ends the brain |
| load / cpu psi on a shared box | 55.7 load on 12 cores, 80.7% psi | inside the bound the crew states (see `.the bound`) |

### the aha

**the cap costs the daily loop little or naught.** a local run is almost always scoped to a few
suite files, and a scope no wider than the cap runs exactly as fast as before. a wider scope
queues and slows in proportion; a full local sweep would feel it most, and
`rule.forbid.local-full-test-sweeps` already forbids that. so the box gets its cores back on the
path the crews walk, at a cost only a wide scope pays. the typical scope width is not yet
measured — the verification stone owes it, from recent credfree logs (`.log/role=any/skill=test.acceptance.credfree/`).

**and the leak, not the width, is what made the laptop crawl.** the cpu burned for minutes; the
orphaned stubs held 18G for hours and pushed 22G to swap. so the fix is two fixes of equal rank:
share the cpu while the run is live, and leave naught behind when it ends.

## .the contract we propose

eight levers. 1–2 share the cpu while a run is live; 3–5 leave naught behind; 6 cuts the work
itself; 7–8 make the result legible — a starved red, and the before/after proof.

| # | lever | where | proven by |
|---|---|---|---|
| 1 | **width by box.** full width (today's `'50%'`) only where a ci host signal is set (`GITHUB_ACTIONS=true`); a shared-box default everywhere else. never keyed on `CI`, which `test.acceptance.credfree` sets on laptops. jest's own `--maxWorkers` always wins | `jest.acceptance.config.ts` | cases 1, 3, 7, 9 |
| 2 | **priority off ci.** the suite's process lowers its own priority to nice 10 in `globalSetup`, before jest forks its workers, so every worker and grandchild inherits it. the header names box, width, priority | `jest.acceptance.globalSetup.ts` | cases 1, 2 |
| 3 | **fixture dirs reclaimed.** `genTestTempRepo` mints its dirs through `genTempDir`, under the test-fns temp root the autoprune teardown already reclaims — as `code.test.accept.blackbox` already requires ("never raw os.tmpdir"). 37 snapshot lines move from `/TMP_REPO` to `/TMP_TEST_DIR` | `blackbox/.test/infra/genTestTempRepo.ts` | case 4 |
| 4 | **no child outlives its test or its run.** the stub exits on stdin end, SIGHUP, and a hard cap; the harness ends its child's process group and escalates; the run's teardown ends any process that carries this run's id and turns the run red. a clamp test (the issue's option 4) runs one `enroll`, ends it, and asserts zero live stubs for its fixture — red before, green after | `stubBrainCli.cjs`, `spawnRhachetCliBackground.ts`, the acceptance teardown | cases 5, 6 |
| 5 | **prod `enroll` ends its brain on any loss of its host** — SIGHUP, stdin end, parent death — not only SIGINT/SIGTERM | `genPtyCloneHostFromProcess.ts` and its clone op | case 10 |
| 6 | **less work per case — only if measured need.** if, after levers 1–2, a scoped run is measurably slower than today, cut per-case work: one `bun install` per suite file rather than per `given` (11 in `upgrade.acceptance` alone). if not, this lever is not pulled — it touches test isolation, which costs more than it saves when no one feels the speed | the install call sites | case 1 wall time |
| 7 | **a starved red says so.** when a run fails on a timeout and the box was saturated, the end of the log names the pressure seen and the re-run command; the red stays red | the acceptance teardown | case 11 |
| 8 | **a reproducible measure** of baseline, peer slowdown, load and psi, before and after | a skill or the verification stone | case 12 |

### the bound

the wish says "the bound the crew states". this vision proposes one, for the wisher to confirm:

- **primary — the peer's slowdown.** a fixed peer workload (e.g. a unit-test run of a fixed scope)
  takes at most ~25% longer while a scoped acceptance run is live than with none. this measures
  what the peers feel, and it holds on a grove whose baseline is already loaded
- **reported — load and cpu psi**, before and after, as the wish asks: the 1m load the suite adds
  over the box's baseline, and the cpu psi `some avg60` with and without the run. reported in the
  pr, graded against the issue's figures (load ≤ cores, psi < ~20%) on an idle laptop

the reason for the delta form: this grove (4 cores) reads load 6.2 and cpu psi 29% with no suite
live (measured 2026-11-14 from `/proc/loadavg`, `/proc/pressure/cpu`). an absolute *"psi under
20%"* cannot hold here by any change to the suite.

## .mental model

- **to a friend:** *"the test suite used to eat the whole laptop and leave its dishes in the sink.
  now it eats a fair share, steps aside when someone else is hungry, and washes up after itself."*
- **analogies:** a guest at a shared table (width = how big a plate; priority = who serves first);
  a camper who packs out what they packed in (no fixture, no stub left behind)
- **their words vs ours**

| a crew says | we say |
|---|---|
| "the suite hogs the box" | width, cpu psi, load |
| "it's polite now" / "it yields" | nice 10 |
| "it leaves junk in /tmp" | fixture dirs not reclaimed |
| "zombie claudes" | orphaned brain stubs, reparented to init (not true zombies — alive, not reaped) |
| "it cleans up after itself" | autoprune teardown, process-group teardown, run-id sweep |

## .evaluation

### how well it meets the wish

| the wish asks | met by |
|---|---|
| a bounded share of the cores on a laptop or grove | levers 1 + 2 |
| full width on ci | lever 1 keeps ci at today's `'50%'`, normal priority |
| no fixture dirs left behind | lever 3 (+ the 24h age gate for a crashed run) |
| no slower on ci | ci config path unchanged by construction; verified by shard wall times |
| as fast as it can be on a shared box | nice yields only under contention, so an idle box still runs at the cap's full speed; lever 6 cuts per-case work |
| measured before/after numbers in the pr | the bound section; the measure is owed by the verification stone |

### pros

- the two cpu levers are a few lines of config each, and ci is untouched
- nice is free when the box is idle and decisive when it is busy
- the leak fix is a prod fix too (case 10), not only test hygiene
- the run-id sweep (case 6) turns every future leak into a red run, so the fix does not rot

### cons

- a full local sweep gets slower (by design; the rule already forbids it locally)
- a cap derived from core count is a heuristic; a 4-core grove gets 1 worker, which may make a
  wide scoped run noticeably slower there
- the run-id sweep needs a way to list processes by env or group on both linux and macos
- four files change in test infra and one in prod; the prod change touches signal paths a human
  feels

### edgecases and the pit of success

| edge | how the contract keeps the crew safe |
|---|---|
| `CI=true` set on a laptop (credfree) | width never reads `CI`; shared is the default; header shows the choice (case 9) |
| a bare `npx jest -c jest.acceptance.config.ts` | no ci host signal ⇒ shared box; the safe box is the default |
| a future self-hosted ci runner with no `GITHUB_ACTIONS` (none today, Q5) | reads as shared ⇒ slower but safe; the runner may pass `--maxWorkers` (case 7) |
| a single suite file (jest runs in band, no workers) | the nice is set on jest's own process, so it covers in-band runs too |
| a peer's suite on the same box | the run-id sweep only ends processes with this run's id (case 6 `[t2]`) |
| a crash before teardown | dirs: reported next run, cleared at 24h. stubs: exit on their own on pty loss or the hard cap |
| the realbrain shard | runs `--runInBand` on ci already; lever 1 does not touch it |

## .open questions & assumptions

### assumptions

- **[answered]** `bin/run.jit` already loads the built `dist/`, not `src/` (`bin/run.jit:2-6`), so
  the issue's *"boot the built cli, not the jit"* is moot: the per-call cost is node start + module
  load (~0.6–1.1s per the comment there), not a transpile
- **[answered]** jest runs `globalSetup` before it builds the scheduler and forks workers
  (`@jest/core@30.2.0 build/index.js:3429` globalSetup, `:3448` createTestScheduler, `:3457`
  scheduleTests), so a priority set in `globalSetup` reaches every worker
- **[answered]** ci sets `GITHUB_ACTIONS=true`; local entries do not, and credfree sets only `CI`
  (`.agent/repo=.this/role=any/skills/test.acceptance.credfree.sh`)
- **[answered]** the autoprune teardown reclaims only `genTempDir` dirs stamped with this run's id,
  never `/tmp/rhachet-test-*` and never processes (test-fns@1.17.0 `teardownAutoprune.js:46-197`,
  `isTempDir.js:99-115`)
- assumption: a child process inherits its parent's nice value on linux and macos (posix `fork`
  semantics). verified in execution by a read of a worker's priority

### questions

1. **[wisher]** the bound: confirm the delta form (peer slowdown ≤ ~25%, load and psi reported
   against baseline), or name an absolute bound and the box it must hold on
2. **[wisher]** the shared-box width default: a quarter of the cores, at least 1, as a start point
   tuned by measurement — or a fixed number (e.g. 2)?
3. **[wisher]** scope: lever 5 (prod `enroll` ends its brain on hangup / stdin end / parent death)
   changes a prod signal path. in this behavior, or its own pr? the issue lists it as a done-when,
   so this vision keeps it in
4. **[wisher]** scope: case 8's repo-local reap skill for pre-fix residue — build it, or print a
   one-line hint and let each crew reap by hand once?
5. **[answered]** is there a self-hosted runner with no `GITHUB_ACTIONS`? no — every job in
   `.github/workflows/*.yml` runs on `ubuntu-24.04` or `ubuntu-latest`, both github-hosted. if one
   is ever added, it reads as a shared box (narrow, safe) and its header says so
6. **[research]** how the teardown finds this run's processes on both linux and macos: an env
   marker (`/proc/<pid>/environ` on linux; `ps eww` on macos), a process group, or cwd under the
   run's temp root. the harness hop holds: every cli child gets `process.env` merged under the
   test's own vars (`invokeRhachetCliBinary.ts:299-307`). unverified: whether prod's spawn of the
   brain and of the detached host (`genCloneEnrollDetached.ts`) passes the env through or builds
   a fresh one
7. **[answered, in part]** a throw from `globalTeardown` does reject the run — but it fires
   before `processResults` (`@jest/core@30.2.0 build/index.js:3464` vs `:3472`), so the test
   summary a reader needs would be lost. ⇒ the leak guard must not throw from teardown.
   **[research]** what remains: the mechanism that turns the run red and keeps the summary — e.g.
   a custom reporter that fails the run from its own end-of-run hook, or a sweep in a shared
   `afterAll` that fails the last suite
8. **[research]** the width default and nice level that hold the bound, measured: 1, 2, 3 workers
   on a 12-core laptop with three seats live, at nice 10 and at nice 19. nice 10 is a best guess:
   19 would favor the peers more and starve the suite harder (case 11)
9. **[research]** lever 6 (only if pulled): does one `bun install` per suite file hold each
   `given`'s isolation in `upgrade.acceptance`, or does a case mutate `node_modules`?
10. **[research]** the starvation notice (case 11) and the measure (case 12) read cpu psi from
   `/proc/pressure/cpu`, which macos lacks. which signal stands in there — load over cores, or no
   notice at all?

- **jest worker count** — jest resolves `maxWorkers` to a number on `globalConfig` before it
  schedules (`@jest/core@30.2.0 build/index.js:1480,3504,3531`), so the globalSetup header can
  read the final width, a cli `--maxWorkers` included. globalSetup order verified above

  env var `GITHUB_ACTIONS` (`node_modules/.pnpm/ci-info@4.3.1/node_modules/ci-info/vendors.json:157-158`)
- **node-pty kill** — `kill()` with no signal sends `SIGHUP` to the one pid
  (`node_modules/node-pty/lib/unixTerminal.js:230`)
- **not verified from a source in the tree** (stated from general knowledge, owed a probe in
  execution): psi `some avg60` counts niced tasks that wait too; a forked child inherits its
  parent's nice value; node `os.setPriority(pid?, n)` sets the nice value of the current process
  by default

## .what is awkward?

- **a heuristic width.** "a quarter of the cores" is a guess dressed as a rule. it may be too
  wide on a busy laptop and too narrow on an idle 4-core grove. nice softens both errors, and the
  measurement in question 8 must settle the number
- **psi cannot grade a niced suite.** the wish asks for psi numbers, and they will be reported, but
  psi counts the suite's own waits. the honest grade is what the peers feel, which needs a probe
  workload — more ceremony than a single `cat /proc/pressure/cpu`
- **one behavior, two concerns.** cpu share and process hygiene are distinct fixes. they ship
  together because both shape what the peer feels, and because the issue's measured crawl was
  mostly the leak; but a reviewer may reasonably ask for two prs
- **a prod change rides a test-infra wish.** case 10 touches the signal path of every interactive
  `enroll`. it is the right fix, and the leak shows it is needed, but it raises the review bar
- **the residue of the past.** the fix stops new leaks and cannot honestly reap old ones without a
  scoped tool (case 8); every laptop carries its pile until someone reaps it once

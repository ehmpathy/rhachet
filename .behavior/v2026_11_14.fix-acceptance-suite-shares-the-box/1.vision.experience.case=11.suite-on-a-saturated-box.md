# case 11 — suite-on-a-saturated-box · runner · sharp · critipath

## .narrative

case 2 seen from the other side. a clone on a 4-core grove runs a scoped acceptance run while
five peer seats compile and test at normal priority. the suite is niced, so the scheduler serves
the peers first; the suite's cases crawl. one case that spawns a clone waits past jest's 90s
timeout (`jest.acceptance.env.ts`) and goes red. the clone reads the red as a defect in its own
code and starts to chase it.

that is the cost of a polite suite, and the contract must not hide it. so when a run that went
red was also starved, the run says so at the end, next to the failure summary:

```
🌙 this run was starved for cpu
   ├─ cpu psi averaged 86% while it ran (baseline before it began, 31%)
   ├─ 2 tests failed on a timeout; a timeout here may be the box, not the code
   └─ to confirm, re-run the failed scope alone
      └─ rhx test.acceptance.credfree --scope 'enroll' --maxWorkers 1
```

the clone re-runs the one scope when the grove is calmer; it passes; no defect chase.

why critipath: groves are busy by design, so a niced suite will meet a saturated box often. a
timeout that reads as a code defect sends a crew down a false trail with no fallback but luck.

why it fails safe: loud (the notice prints beside the red), it teaches the fix (re-run the scope
alone, with the exact command), and it never masks a red as green — the test still fails; only
the reader is told what the box was like.

## .bdd `[tn]` timeline (sketch)

```
given a 4-core grove at load ≈ 12, five peer seats busy at normal priority
  when [t0] a clone runs `rhx test.acceptance.credfree --scope enroll`
    then the suite runs at nice 10 and its cases slow
  when [t1] one case passes jest's 90s timeout and fails
    then the run ends red — the failure is never swallowed
    and  the end of the log prints the starvation notice: psi over the run vs before it, the
         count of timeout failures, and the re-run command
given the same scope on a calm box
  when [t2] the clone runs the re-run command
    then the scope passes, and no starvation notice prints
given a run that fails on an assertion (not a timeout) on a calm box
  when [t3] the run ends
    then no starvation notice prints — the notice speaks only when the box was starved
```

> the notice reads cpu psi on linux; on a box with no `/proc/pressure` (macos) it falls back to
> load over cores, or prints naught — a [research] point in the yield.

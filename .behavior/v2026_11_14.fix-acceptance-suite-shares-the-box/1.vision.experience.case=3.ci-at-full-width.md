# case 3 — ci-at-full-width · ci · happy · critipath

## .narrative

a pr lands. github spins up the acceptance matrix: five dynamic shards and the serial realbrain
shard, each on its own `ubuntu-24.04` runner. no human is there and no peer shares the vm, so
the suite is owed the whole box. it gets exactly the width it had before this change — the
`'50%'` the config holds today — and runs at normal priority. the shard header names the box as
`ci`, so a reader of the log sees why it went wide. the wall time of each shard reads the same as
the last green run on `main`, give or take noise.

why critipath: ci is the merge gate. if the change slowed or starved it, every pr in the repo
pays, and there is no fallback route to merge.

## .bdd `[tn]` timeline (sketch)

```
given a github actions runner (GITHUB_ACTIONS=true)
  when [t0] the shard runs `npm run test:acceptance -- --shard=2/5`
    then the run header reads
      🐢 acceptance width
         ├─ box = ci
         ├─ workers = 50% (1 of 2 vcpu, if the runner is the box `jest.acceptance.shards.jsonc:4` names)
         └─ priority = normal
    and  jest uses the same maxWorkers it used before this change
  when [t1] the shard completes
    then its wall time sits within noise of the last green shard on main
    and  the union job `test-acceptance-locally` reads green
```

> the header values are sketches. the contract is: ci width = today's width, ci priority =
> normal, and the header names the box it chose.

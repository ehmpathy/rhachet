# 1.vision — one hook dispatcher per claude event

## .the solution

at `rhx init`, rhachet writes two artifacts into each actor's brain dir:

- **a rule manifest** — one row per enrolled role rule: event, matcher, timeout, author, the declared
  command, and the path it resolves to (an `rhx <skill>` rule resolves to its skill `.sh`, a
  `rhachet run --init` rule to its init `.sh`)
- **one hook per claude event** in `settings.of.repo.json` — the dispatcher, whose matcher is the
  union of its rules' matchers (`Write|Edit` ∪ `Bash` → `Write|Edit|Bash`; any `*` → `*`)

the dispatcher is **one bash process**. it reads stdin once, picks the manifest rows whose matcher
fits the tool by claude's own matcher grammar, and runs each in its own subshell, all at once. then
it merges their verdicts the way claude merges separate hooks.

```
before — one Bash tool call                      after — one Bash tool call
claude ─┬─ rhx route.mutate.guard   sh→bun→bash   claude ── bash dispatcher ─┬─ ( route.mutate.guard.sh )
        ├─ rhx route.foreground.guard  (same)                               ├─ ( route.foreground.guard.sh )
        ├─ rhx memory.guard            (same)                               ├─ ( memory.guard.sh )
        ├─ bash check-permissions.sh                                       ├─ ( check-permissions.sh )
        └─ … 6 more bash hooks                                              └─ … 6 more, as subshells
   10 process trees, 3 rhx boots                       1 process, 0 rhx boots
```

measured on this laptop with `rhx hooks.dispatch.probe --what cost --tool Bash` (a repo skill
paved for this route; payload `pwd`, 10 runs, load avg ~48):

| PreToolUse:Bash, cpu per call | today (as declared) | dispatcher shape (resolved, as subshells) |
|---|---|---|
| whole event, 10 rules | **2185 ms** | **685 ms** (−69%) |
| the 3 `rhx` rules | ~1490 ms | ~415 ms |
| the 7 `bash` rules | ~700 ms | ~270 ms |

today's 2185 ms sits within ~4% of #764's independent 2010–2110 ms, so the instrument reads true.
the after figure excludes the dispatcher's own bash boot and its merge; `case=7` owes the full read.

why it works:

- **the boot is the cost, and it is paid once.** today a Bash call pays 3 rhx boots and 7 bash
  boots. after, one bash boot. a subshell is a fork with no exec: a rule costs its own work and no
  boot. the measure splits the gain: ~1070 ms from the rhx boots, ~430 ms from the bash execs
- **no rhx boot on the hot path.** every rule is bash already — the bhrain guards too
  (`route.mutate.guard.sh` calls `jq`, `git`, `find`, `grep`). the `🪨 run solid skill …` and
  `💪 init role …` frames `rhx` wraps them in (`invokeRun.ts:71-75`, `:202-212`, `:43-47`,
  `:161-181`) are fixed text over three slugs, so the dispatcher prints them from the manifest
- **every rule decides exactly as today.** each rule runs in its own subshell with the event's
  stdin, `BASH_ARGV0` set to its path, and its own `set -e`, traps and `exit`. its exit code and the
  bytes it writes match what it wrote as a standalone process. a test per rule diffs the two
- **the merge is claude's own.** claude runs matched hooks in parallel and shows every blocker
  (`code.claude.com/docs/en/hooks`). the dispatcher:
  - writes every exit-2 rule's stderr, in manifest order, and exits 2 if any rule blocked
  - else writes a crashed rule's stderr and exits with its code, a non-block as before; a rule past
    its timeout is killed, reported, and counted as a crash
  - keeps stdout one valid json when any rule emits a json decision (`check-permissions.sh` emits a
    `permissionDecision: "ask"` today), and plain text in manifest order otherwise (`case=8`)
- **no adapter release.** the collapse happens in rhachet before the brain adapter is called; the
  published `rhachet-brains-anthropic@0.4.3` writes the one hook it is handed, as it writes any
- **open to #765.** a manifest row is a record per rule, so an `onTool` filter is one more column the
  dispatcher checks before it forks a rule. a pre-check that skips the dispatcher entirely is the
  same bash

## .the outcome world

**before.** the shared laptop: ~79 seats, load 96–124 on 12 cores. each `pwd` a seat runs costs ~2
cpu-seconds and 207 MB of hook processes before `pwd` itself starts. claude's own hook children are
the top cpu cluster on the box (47.6% of since-boot cpu).

**after.** the same `pwd` starts one bash process. a seat that slips (`ls` unpaved, a redirect, a
sealed stone) reads the same refusal text; a seat that does not, reads naught. the commander runs
`rhx hooks.dispatch.cost` and sees processes and cpu per call, before and after, side by side.

**the aha.** the guards were never the expensive part; the boots were. ten fresh processes to run
ten regexes and a `jq` was the bill.

## .mental model

- to a friend: *"claude used to start a fresh program for every guard on every command. now it
  starts one, and that one checks every guard."*
- analogy: one officer at the door with ten checklists, in place of ten officers hired for the day
  to check one line each
- their words vs ours: *"hooks"* / *"guards"* → **rule** (one declared check) and **dispatcher**
  (the one process per event); *"the hook list"* → **manifest**

## .evaluation

| goal (wish) | how |
|---|---|
| one process per event | one settings hook per event; rules run as subshells inside it |
| every rule decides as today | own subshell, own stdin, `BASH_ARGV0`; a byte diff per rule vs its standalone run |
| before/after read on a live box | `rhx hooks.dispatch.cost`: `strace -f` for counts, untraced `/usr/bin/time` for cpu, median of 5, same payload; read against #764's done bar (0 rhx, ≤ ~1200 ms, ≤ ~55 MB per Bash call) |
| room for #765 | a manifest row per rule |

- **where the gain comes from**, measured: ~1070 ms is the three rhx boots gone; ~430 ms is seven
  bash execs turned into subshells. the first is the one that cannot slip; the second holds on
  bash ≥ 5 and degrades to today's bash cost on older hosts
- **pros**: zero rhx boots per tool call; ~685 ms measured against #764's ~1200 ms estimate (that
  kept one rhx boot); no role package changes; no adapter release; latency holds, since rules still run in
  parallel
- **cons**: claude's `[<command>]` error label names the dispatcher, not the rule (`F3`); the `rhx`
  frames now print from two codepaths, held equal by a test; the rules' own forks (`jq`, `git`,
  `grep`) remain, so the process count per call drops by the boots, not to one
- **edgecases held in the pit of success**: a crash or a hang stays its rule's, and the
  dispatcher's own timeout sits above its slowest rule's so claude never kills every verdict at
  once (`case=4`); a json
  decision stays parseable (`case=8`); the sync swaps shapes in one write, so no rule runs twice, and lands the
  manifest before the settings that name it, so a seat mid-sync never meets a dispatcher with no
  rules; an absent manifest fails closed (`case=6`); a hand-added hook is left alone; a `--roles -driver` clone's manifest holds no driver
  rule

## .open questions & assumptions

- **[answered]** which rule kinds are live? `rhx <skill>`, `rhachet run --init`, `bash <path>.sh`
  on every event; the foreign ones (`rhachet roles cost …`, `node -e …`) sit only on Stop and run via
  `bash -c` at today's cost (read via `rhx hooks.dispatch.probe --what hooks`)
- **[answered]** bash ≥ 5? not required. macOS `/bin/bash` is 3.2; there each rule runs as
  `bash <path>`: zero rhx boots still, one bash exec per rule, never a block (`case=11` [t4])
- **[answered]** what does "10 processes to 1" count? #764 counts the hook processes claude starts
  per call — 10 today, 1 after. the rules' own `jq`/`git` forks are their work and stay; the read
  reports both counts so neither hides
- **[answered]** does a resolved rule decide as its `rhx` twin? on exit code, yes — 10 of 10 on an
  allowed and a sharp payload (`--what verdicts`). a full byte diff per rule is owed to the criteria
- **[answered]** does any SessionStart rule emit json? no — the four print plain text; the
  `additionalContext` fold stays an itemized alterpath
- **[answered]** does claude show every blocker or the first? undocumented, and moot: the dispatcher
  writes every blocker, a superset of either
- **[answered]** do the role repos' own hook tests still prove what runs? yes — they invoke each
  `.sh` by path, and the dispatcher runs that same `.sh`
- **[research]** the manifest's on-disk form (a form bash reads with no `jq` fork) and the per-role
  cut for clones, which today filters inner hooks by `author` (`getSettingsForRoles.ts:13-45`) and
  must move to the manifest (`F5`)
- **[wisher]** `F1` — #764 names `rhx hooks.dispatch`; a bash dispatcher skips that boot. keep bash
  (recommended, ~685 ms measured), or add a thin `rhx hooks.dispatch` alias at one boot's cost?
- **[wisher]** `F3` — accept the dispatcher as claude's `[<command>]` error label (recommended: every

## .what is awkward

- the `rhx` frames print from two codepaths. a test that runs one rule both ways and diffs the
  bytes holds them equal, but it is a seam
- the label move (`F3`): honest, and invisible to every rule's own test, yet a seat that read the
  bracket for the rule name loses it
- a sourced subshell sees the dispatcher's own shell variables and functions, where a standalone
  rule saw a clean shell. the dispatcher keeps its own names few and under one `__rhx_dispatch_`
  prefix, and unsets them before it sources a rule; a rule that reads an unset name still reads unset
- the json-vs-plain stdout merge (`case=8`) is logic claude did implicitly by separate processes; it
  is now ours to keep right
- `filter.when: 'after'` lands under PreToolUse via the published adapter; the dispatcher keeps that
  placement to hold "decides as today", though it is an adapter defect
- the cost tool is a new repo skill, since the commander's `rhx claude.hooks.cost` lives outside
  this repo

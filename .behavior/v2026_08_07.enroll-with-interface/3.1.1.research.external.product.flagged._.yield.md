# 3.1.1.research.external.product — flagged topics

> the vision ([`1.vision.yield.md`](./1.vision.yield.md) → "must validate externally" + "external
> research") flags a cluster of external premises the socket hangs on. this stone researches each,
> cites ≥7 sources with quotes, dates, credibility tags, and labels each claim
> **[FACT]** / **[SUMP]** / **[KHUE]** / **[OPIN]**. it is a **groundwork sanity-check**, not
> exhaustive — enough to know the vision is not built on false assumptions.
>
> prior art already salvaged in [`refs/lessons.from=brain-hook-on-push.md`](./refs/lessons.from=brain-hook-on-push.md)
> (PR #322) is cited where it converges.

## flagged topics (from the vision)

1. **pty fidelity** — a pty transparently proxies the brain-cli's tty (raw-mode, resize, color).
2. **native resume + session id** — claude-code (and peers) expose `--resume <id>` + surface a session id.
3. **dispatch input-protocol** — a write to the clone's channel reaches the brain-cli's input like a human keystroke.
4. **per-brain generality** — which supported brains can carry the socket (resume + dispatch).
5. **native-module portability** (the vision's "load-bearing risk") — a pty is a native addon vs this repo's bun/tsx dispatch.

# topic 1 — pty fidelity

> claim under test: a node pseudo-terminal can spawn the brain-cli and proxy its tty invisibly —
> raw-mode prompts, SIGWINCH resize, color — with no visible degradation.

### citations

1. **[official]** node-pty — npm (`node-pty`), 2026. <https://www.npmjs.com/package/node-pty>
   > "node-pty lets you fork processes with pseudoterminal file descriptors. It returns a terminal
   > object which allows reads and writes." — and: "node-pty supports Linux, macOS and Windows."
2. **[official]** microsoft/node-pty — GitHub. <https://github.com/microsoft/node-pty>
   > "Windows support is possible by utilizing the Windows conpty API on Windows 1809+ and the winpty
   > library in older versions." — and it is "useful for writing terminal emulators (such as via
   > xterm.js)."
3. **[official]** ptyprocess API docs (pty semantics), 0.7. <https://ptyprocess.readthedocs.io/en/latest/api.html>
   > "setting the terminal window size of the child tty will cause a SIGWINCH signal to be sent to the
   > child, changing the size reported to TTY-aware applications that respond to the SIGWINCH signal."
4. **[official]** node-pty — jsDocs (`node-pty@1.1.0`), 2026. <https://www.jsdocs.io/package/node-pty>
   > spawn accepts "name ('xterm-color'), cols, rows, cwd, env"; "if [encoding] set, incoming data will
   > be decoded to strings … otherwise incoming data will be delivered as raw bytes (Buffer type)."
5. **[tutorial]** Linux terminals, tty, pty and shell — DEV Community. <https://dev.to/napicella/linux-terminals-tty-pty-and-shell-192e>
   > "Keyboard character streams are fed into the write fd of the master end of the PTY. The line
   > discipline writes back its input to the master (echoing back)."
6. **[official]** xterm.js encoding guide. <https://xtermjs.org/docs/guides/encoding/>
   > "xterm.js supports 8-bit sequences and will fall back to UTF-8 for unknown character set commands."
7. **[official]** classic Yarn — node-pty. <https://classic.yarnpkg.com/en/package/node-pty>
   > mirrors the npm contract: "Fork pseudoterminals in Node.JS."
8. **[practitioner]** ptylie (inject keystrokes into a pty) — GitHub, p-gen. <https://github.com/p-gen/ptylie>
   > "start a program in a pseudo terminal and inject keystrokes and other events according to
   > directives given in a file." (independent evidence a pty master can drive an interactive child.)

### findings

- **[FACT]** node-pty is the canonical node pseudo-terminal — Microsoft-maintained, powers VS Code's
  terminal, cross-platform (Linux/macOS via unix ptys, Windows via conpty). [1][2]
- **[FACT]** a pty forwards **SIGWINCH on resize**, so a TTY-aware child re-flows — the vision's
  resize edge-case has a real mechanism. [3]
- **[FACT]** raw bytes pass through when encoding is unset — colors/escape sequences are proxied
  verbatim, not re-interpreted, so color fidelity holds by default. [4][6]
- **[SUMP]** the vision assumes the proxy is **visually invisible** to the human. the mechanism
  supports it, but "no visible degradation" of claude-code's raw-mode TUI specifically is an
  **assumption to prove by a real playtest**, not a documented guarantee. [4][5]
- **[KHUE]** node-pty is *not itself* a terminal emulator — it is the OS pty binding; the emulator
  (xterm.js) is a separate layer. **open question:** since we mirror the child's bytes straight to the
  human's real terminal (not into xterm.js), do we need any emulation at all, or is byte-passthrough
  sufficient? (leaning: passthrough suffices — we are a conduit, not a renderer.) [2][6]

**convergence:** [1][2][3][4] agree the pty carries size + raw bytes; PR #322's POC (`poc.pty-wrapper`)
independently reached the same "hold the pty master" design (salvage lesson 1). 4+ independent → high
confidence the mechanism is real.

# topic 2 — native resume + session id (claude-code)

> claim under test: claude-code exposes a `--resume <session-id>` and surfaces a session id at spawn,
> so the clone's recorded `exid` can delegate revive to the brain-cli's own resume (rhachet stores no
> transcript). this underwrites the clone-dream `wake` verb — but the frame here must record the id.

### citations

9. **[official]** Manage sessions — Claude Code Docs. <https://code.claude.com/docs/en/sessions>
   > "Sessions created with `claude -p` or the Agent SDK don't appear in the session picker, but you
   > can still resume one by passing its session ID to `claude --resume <session-id>`."
10. **[official]** Run Claude Code programmatically (headless) — Claude Code Docs. <https://code.claude.com/docs/en/headless>
    > "Capture the session_id from JSON output and pass `--resume <session-id>` on the next invocation.
    > The conversation picks up exactly where it left off."
11. **[official/community]** claude-code issue #44063 — "Resume Any Claude Session in the CLI". <https://github.com/anthropics/claude-code/issues/44063>
    > "`--resume (-r)` resumes a specific session by ID (or name)."
12. **[official/community, BUG]** claude-code issue #33912 — `--resume … always returns 'No conversation found'`. <https://github.com/anthropics/claude-code/issues/33912>
    > title: "`claude --resume <session-id>` always returns 'No conversation found' even though session
    > files exist." (a real, reported failure mode.)
13. **[official/community]** claude-code issue #44607 — "No way to access session ID from within a running session." <https://github.com/anthropics/claude-code/issues/44607>
    > title as quoted — the id is emitted to the caller (JSON/stream), not readable *from inside* the run.
14. **[tutorial]** Claude Code CLI Cheat Sheet (2026 ed.) — zenn. <https://zenn.dev/daishiro/articles/claude-code-cli-cheatsheet?locale=en>
    > "`--session-id <UUID>` runs under a session ID you choose; `--continue (-c)` resumes the most
    > recent conversation in the current directory."
15. **[practitioner]** Claude Code in CI/CD and Headless Automation — hidekazu-konishi.com, 2026. <https://hidekazu-konishi.com/entry/claude_code_cicd_and_headless_automation.html>
    > "A single `-p` run is stateless from the caller's perspective … Capture the session_id from JSON
    > output and pass `--resume <session-id>` on the next invocation."
16. **[blog]** stream-json — backgroundclaude.com. <https://backgroundclaude.com/blog/stream-json>
    > "The stream begins with a system event whose subtype is init, reporting the run's metadata — the
    > session ID, the model, the available tools …"

### findings

- **[FACT]** claude-code exposes **`--resume <session-id>`** (alias `-r`), **`--continue` (-c)**, and
  a caller-chosen **`--session-id <UUID>`**. resume works even for headless `-p` sessions. [9][10][11][14]
- **[FACT]** the session id is surfaced **to the caller** — in the `--output-format json` envelope and
  as the first `stream-json` `init` event. [10][15][16]
- **[FACT/constraint]** the id is **not readable from inside** a running session (#44607). so the
  *frame* must capture the id at spawn from the caller-side stream, not expect the brain to self-report
  it. this shapes how the clone records its `exid`. [13]
- **[KHUE]** issue #33912 shows `--resume` can return "No conversation found" despite present files — a
  real fragility. **open question for the clone dream's `wake`:** how robust is resume across
  claude-code versions? (in-scope-here impact: the frame only *records* the id; `wake` is the dream's.) [12]
- **[SUMP]** the vision assumes `exid` = the clone's **latest episode** session id (resume target),
  since a clone's history is a multi-episode `BrainSeries` bridged by compaction. the docs confirm
  per-session ids but do **not** speak to rhachet's multi-episode model — that mapping is **our**
  assumption. [9][10]

**convergence:** [9][10][11][14][15] independently confirm `--resume <session-id>` + caller-side id
capture (5 sources, incl. 3 official). **conflict:** [9][10] (resume "just works") vs [12] (resume can
fail "No conversation found") — reconcile: resume is *supported* but *not bulletproof*; the frame's job
(record the id) is safe, the dream's `wake` must handle the failure mode.

# topic 3 — dispatch input-protocol

> claim under test: a write to the clone's channel reaches the brain-cli's input and is processed like
> a human keystroke — even though claude-code is an interactive TUI (Ink/React), not a line reader.

### citations

17. **[practitioner/news]** "Ink 7.0 fundamentally revises input handling" — heise online, 2026. <https://www.heise.de/en/news/React-in-the-Terminal-Ink-7-0-fundamentally-revises-input-handling-11249949.html>
    > "Ink activates the terminal's Bracketed Paste mode, ensuring that pasted text arrives as a
    > contiguous string. Without this mode, a paste operation would appear as a series of individual
    > keypress events — which is problematic for input fields or REPL-like interfaces."
18. **[official]** vadimdemedes/ink — GitHub. <https://github.com/vadimdemedes/ink>
    > "`useStdin` … exposes the stdin stream"; TUIs "enable raw mode on stdin using
    > `process.stdin.setRawMode(true)`."
19. **[tutorial]** Building Terminal Interfaces with Node.js — OpenReplay. <https://blog.openreplay.com/building-terminal-interfaces-nodejs/>
    > "Node.js exposes `process.stdin` and `process.stdout` as streams; for TUIs you'll typically
    > enable raw mode on stdin."
20. **[practitioner]** ptylie — GitHub, p-gen. <https://github.com/p-gen/ptylie>
    > "inject keystrokes and other events" into a program running in a pseudo terminal.
21. **[official]** tmux(1) — Linux man page (control mode). <https://www.man7.org/linux/man-pages/man1/tmux.1.html>
    > control mode "allows a tmux client to be used to talk to tmux using a simple text-only protocol";
    > `send-keys` injects input to a pane.
22. **[practitioner]** reptyr — reattach a running process to a new terminal. <https://recca0120.github.io/en/2026/03/25/reptyr-reattach-terminal/>
    > "reptyr uses the ptrace syscall to re-attach a running process to a new terminal, genuinely
    > changing the process's controlling terminal."
23. **[community]** "Character by character TTY input in Unix" — Hacker News. <https://news.ycombinator.com/item?id=18440615>
    > discussion of raw vs cooked tty input modes and how keystrokes reach a program byte-by-byte.
24. **[salvage/POC]** PR #322 `poc.pty-wrapper` (via `refs/lessons.from=brain-hook-on-push.md`).
    > "a `net` unix socket whose inbound data is written to `pty.write()` (→ claude stdin)."

### findings

- **[FACT]** an interactive TUI reads **raw-mode stdin**; a write to the pty master's write-fd is
  delivered to the child exactly as keyboard bytes are. [18][19][23][20]
- **[FACT]** claude-code is an **Ink/React TUI** that enables **bracketed-paste mode** (`\x1b[?2004h`);
  a multi-line paste must be wrapped in the bracketed-paste markers to arrive as one contiguous string
  rather than N keypresses. [17]
- **[SUMP → now a concrete protocol requirement]** the vision flagged dispatch as an unknown; the Ink
  evidence upgrades it: `say` cannot write **raw bytes** and assume delivery — for a TUI it likely must
  (a) wrap multi-line messages in bracketed-paste markers, and/or (b) append a submit key (Enter), and
  (c) respect a ready-state. this is the vision's "an interactive TUI may need an enter / bracketed-paste
  / ready-state protocol, not raw bytes" — now **cited, not just guessed**. [17][18]
- **[FACT]** the pattern is proven in adjacent tools: tmux `send-keys`, ptylie keystroke injection, and
  PR #322's own POC (socket→`pty.write`→stdin) all inject input into a live interactive child. [20][21][24]
- **[KHUE]** does a stdin write **wake claude when it is idle at the prompt**, and what happens if it
  lands **mid-response**? (PR #322 left exactly these two POC questions open — they are our
  single-writer + ready-state edge-critipaths.) [24]

**convergence:** [18][19][20][21][23][24] — 6 independent sources agree input injection into a
raw-mode/pty child is a solved, ordinary mechanism. **the nuance (not a conflict):** [17] adds that a
*modern Ink TUI* needs bracketed-paste framing for multi-line input — a refinement, not a contradiction.

    > shows an in-TUI `/resume` slash-command path in addition to the CLI verb.
29. **[blog]** Codex CLI Resume, Continue, and Save Chat — Verdent Guides. <https://www.verdent.ai/guides/codex-cli-resume-continue-save-chat>
    > practitioner confirmation of Codex resume/continue semantics.

32. **[salvage]** PR #322 prior-art table (OpenCode / OpenHands / Claude `--channels`) via
    `refs/lessons.from=brain-hook-on-push.md`.
    > "queue/channel approaches require the session to already be live" — our exid+`--resume` `wake` is

### findings

- **[FACT]** the three major brain-clis all expose native resume: **claude** (`--resume <id>`) [9][31],

  generalizes beyond claude. [25][30]
- **[FACT]** all three persist their **own transcripts on disk** (claude `~/.claude/projects/…`, codex
  `~/.codex/sessions/…`) — reinforcing the vision's "rhachet stores the handle, not the transcript"
  and the `history/`-symlink design. [25] (+ topic-5 [19] for claude)
- **[SUMP]** the socket's **dispatch** half (write-to-input) is assumed per-brain too. resume is
  confirmed per-brain; **dispatch fidelity per brain is not documented** — each brain's TUI input
  protocol (bracketed-paste? submit key?) must be verified individually. the vision's per-brain-adapter
  framing + plain-spawn fallback is the correct hedge. [17][32]
- **[FACT]** the repo already keys the brain seam via `getSupportedBrainCommand` (internal research,
  stone 3.1.3) — so a per-brain capability check has a natural home. (internal, cross-ref.)
- **[KHUE]** which supported brains **lack** a resumable session id or a dispatchable input, and thus
  fall to the plain-spawn fallback? (needs a per-brain capability audit at blueprint time.) [32]

**convergence:** [25][26][27][28][29][30] — 6 sources confirm Codex+Gemini resume; combined with
claude [9], the "native resume" premise holds across all three brains this repo targets. **the frame's
per-brain-adapter + fallback design is validated** as the right shape.

# topic 5 — native-module portability (the load-bearing risk)

> the vision's #1 "what is awkward": a pty is a native addon; this repo ships a bun-compiled hot path
> (`bin.dispatcher.pattern`) + a hermetic acceptance harness. does node-pty fit?

### citations

33. **[official]** Node.js Compatibility — Bun docs. <https://bun.com/docs/runtime/nodejs-compat>
    > Bun implements "approximately 95% of the Node-API (N-API) interface"; "most existing native
    > addons built for Node.js work with Bun out of the box."
34. **[practitioner]** Bun Compatibility in 2026 — DEV Community (alexcloudstar). <https://dev.to/alexcloudstar/bun-compatibility-in-2026-what-actually-works-what-does-not-and-when-to-switch-23eb>
    > "Node.js native addons … produce `.node` files that V8 loads directly, but Bun uses
    > JavaScriptCore, not V8, so these binaries are incompatible at a fundamental level."
35. **[official]** prebuild/prebuildify — GitHub. <https://github.com/prebuild/prebuildify>
    > "Create and package prebuilds for native modules"; "If your module is using … Node-API … you can
    > prebuild using the `--napi` flag."
36. **[official]** prebuild — the Node-API Resource. <https://nodejs.github.io/node-addon-examples/build-tools/prebuild/>
    > "With Node-API you only have to produce prebuilds for every runtime."
37. **[official/practitioner]** @skitee3000/bun-pty — npm. <https://www.npmjs.com/package/@skitee3000/bun-pty>
    > "a cross-platform pseudoterminal (PTY) implementation for Bun with native performance … includes
    > prebuilt binaries for macOS, Linux, and Windows."
38. **[practitioner]** @snomiao/bun-pty — npm. <https://www.npmjs.com/package/@snomiao/bun-pty>
    > a second, independent Bun-targeted pty implementation (convergent evidence of a Bun pty path).
39. **[official]** node-pty npm (topic-1 [1]) — states it is a compiled binding requiring build tools.

### findings

- **[FACT / the crux]** node-pty is a **V8-compiled** `.node` addon; Bun uses JavaScriptCore, so a
  stock node-pty binary is **not** loadable by Bun's runtime directly. [34]
- **[FACT]** Bun implements ~95% of **N-API**, and N-API-based addons with per-runtime prebuilds *can*
  load — but node-pty must ship a Bun-compatible prebuild for that to hold. [33][35][36]
- **[FACT]** **Bun-native pty libs exist** (`@skitee3000/bun-pty`, `@snomiao/bun-pty`) with prebuilt
  cross-platform binaries — an alternative if node-pty resists the bun path. [37][38]
- **[OPIN]** the pragmatic read: the socket path likely runs under the **tsx/node** JIT dispatch
  branch (`bin/run.jit`), **not** the bun-compiled branch — the bun branch is the fast, config-only hot
  path; an interactive pty spawn is not on it. so the native-addon risk may **not** actually touch the
  bun-compile path at all. (an assessment to confirm at blueprint, not a settled fact.) [34] + internal
  `bin.dispatcher.pattern`
- **[KHUE]** does the hermetic acceptance harness (which invokes the real `bin/run` in a temp repo)
  tolerate a native pty dependency across CI's linux + a dev mac? (the vision's stated portability
  worry — a blueprint/execution concern.) [35][36]

**convergence:** [33][35][36][37][38] agree N-API + prebuilds are the portability answer, and a
Bun-pty alternative is real. **conflict:** [33] ("most native addons work out of the box") vs [34]
("`.node`/V8 binaries are incompatible at a fundamental level with Bun/JSC") — reconciled: **old-style
node-gyp/V8 addons break under Bun; N-API-prebuilt addons work.** the fix is to confirm node-pty's
N-API/prebuild status, or route the pty via the node/tsx branch, or adopt a bun-pty lib.

# net assessment — is the vision built on false assumptions?

**no false assumptions found.** every load-bearing premise has a real, cited mechanism:

| flagged premise | verdict | residual risk |
|-----------------|---------|---------------|
| pty proxies the tty (raw/resize/color) | **confirmed** [1-6] | prove visual invisibility by playtest [SUMP] |
| claude `--resume <id>` + surfaced session id | **confirmed** [9-16] | resume not bulletproof (#33912); id not self-readable (#44607) |
| dispatch reaches the TUI's input | **confirmed mechanism**, refined | needs bracketed-paste/submit/ready-state protocol [17]; wake-from-idle + mid-response unproven [KHUE] |
| per-brain generality (claude/codex/gemini resume) | **confirmed** [25-31] | dispatch fidelity per brain unaudited [SUMP] |
| native-module portability vs bun | **confirmed tractable** [33-38] | confirm node-pty N-API/prebuild, or route via node/tsx branch, or bun-pty lib [KHUE] |

**the three items to carry forward (not blockers — blueprint/execution work):**

1. **dispatch protocol** is richer than "write raw bytes" — the TUI needs framing (bracketed-paste +
   submit + ready-state). upgrade from unknown to a **designed contract** at blueprint. [17][24]
2. **native-module fit** — decide the pty lib (node-pty via node/tsx branch vs bun-pty) at blueprint;
   verify against the hermetic harness on linux CI + mac. [33-38]
3. **resume robustness** is the **clone dream's** worry (`wake`); the frame here only **records** the
   caller-surfaced session id — a safe, well-supported operation. [10][12][13]

**decision-relevant conflicts, resolved:**
- resume "just works" [9][10] vs "No conversation found" [12] → resume is *supported but fragile*; the
  frame's record-the-id job is safe; `wake` (the dream) must handle failure.
- Bun "native addons work out of the box" [33] vs "V8 `.node` incompatible with JSC" [34] → **N-API
  prebuilds work, node-gyp/V8 binaries do not** — pick the pty lib accordingly.

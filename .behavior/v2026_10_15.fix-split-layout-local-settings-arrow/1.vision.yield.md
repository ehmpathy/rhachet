# vision: a plain `claude` at the repo root loads the repo's settings

## the outcome world

### before

the repo actor's brain dir (`<repo>/.claude` points at it) holds:

```
settings.of.repo.json                                  the repo's allows + hooks (a real file)
settings.json -> settings.of.grove.json -> ~/.claude/settings.json
```

| launch | layers claude reads | repo allows + hooks? |
|---|---|---|
| `rhx enroll claude` | user (grove) + `--settings settings.of.repo.json` | ✅ |
| plain `claude` at the repo root | user (home) + project (→ home) + local (absent) | 🔴 no |

a human opens a plain `claude` in the repo. `npm run test:types` prompts for permission, even though the
mechanic role pre-approved it. the SessionStart notice from mechanic does not appear. the permission hook
nudges toward an allowlist that claude never loaded.

### after

every brain dir holds one more arrow:

```
settings.local.json -> settings.of.repo.json           (relative)
```

| launch | layers claude reads | repo allows + hooks? |
|---|---|---|
| `rhx enroll claude` | user (grove) + `--settings settings.of.repo.json` — unchanged | ✅ |
| plain `claude` at the repo root | user (home) + project (→ home, deduped) + **local (→ settings.of.repo.json)** | ✅ |

both launches now load the same set: the grove at low rank and the repo's settings at high rank.

### the aha

`rhx upgrade`, then a plain `claude`: `npm run test:types` runs with no prompt, and the mechanic's
SessionStart notice appears. the repo's roles reach every session launched at the repo root, not
just enrolled ones. a launch from a subdir reads that subdir's own `.claude`, and a worktree's reach
is unmeasured (F9): the allows and hooks do not walk up the tree the way `CLAUDE.md` does.

## mental model

- to a friend: *"plain `claude` now picks up the repo's settings, same as an enrolled one."*
- analogy: `settings.json` is the door to the box's settings. `settings.local.json` is now a second door,
  which leads to the repo's settings.
- the human's words: "my allows don't work outside enroll". our words: "the local layer arrow".

## evaluation

- **goal fit**: full. a plain session loads the exact set an enrolled one loads, and the exact set the
  nheuron permission hooks already read.
- **pros**: one arrow and one findsert line. it is idempotent. it reuses `setArrow`, so the replacement and
  concurrency behavior are the same as for the grove arrows.
- **cons**: a session's "always allow" lasts the session only — claude refuses the write through the arrow,
  with no message (Q5). a real, untracked `settings.local.json` loses its grants (case=5).
- **pit of success**: the target is always present, so the arrow never dangles. a real file in the way
  gets the same one-answer treatment as every other arrow name, and a REPLACED row names it (S2).

## open questions & assumptions

each question is triaged. fulcrums are best guesses with a clean rework (`.fulcrums/`); the drive goes on
and the wisher rules on them at the fulcrum council.

- **Q1 — the arrow in the repo actor alone, or in every actor? [answered]** (F1) every actor, ruled by the
  wisher, 2026-10-16. one layout (`rule.forbid.brain-dir-layout-divergence`), and the arrow is live: every
  plain `claude` is an ambiently enrolled clone of the repo actor and loads it.
- **Q2 — a real `settings.local.json` in the way: replace, or merge first? [answered]** (F2) requirement
  case 7 settles a real file at an arrow name: replace, never merge, never keep aside. a distinct REPLACED
  row reports it, in stdout (seed S2).
- **Q3 — do "always allow" grants land in a tracked file? [answered]** (F3) no: a grant never reaches
  `settings.of.repo.json`. claude refuses the write, and that refusal is the desired behavior (Q5, S4).
- **Q4 — does claude follow the arrow on read? [answered]** by extant behavior: every clone already reads
  its user layer through two arrows (`settings.json -> settings.of.grove.json -> ~/.claude/settings.json`).
  nheuron's stopgap is reported to work too (the wish's report, not measured here).
- **Q5 — does an "always allow" from a plain claude land in `settings.of.repo.json`? [wisher]** measured
  with a real claude (`blackbox/cli/brain-config.grove-vs-repo.realbrain.acceptance.test.ts` [case2 t1],
  `appendix/research.claude-local-settings-write-path.md`): **no, and silently**. the command runs, the
  grant lasts the session, and no file changes. claude follows a symlink on a local-layer write only
  when the dir is its own config dir; with `CLAUDE_CONFIG_DIR=<repo>/.claude` the same grant lands in
  `settings.of.repo.json` and the arrow survives. settled (seed S4): the refusal is the desired
  behavior — a repo change is an explicit opt-in, and that launch is the opt-in
  (`define.invariant.brain-config-grove-vs-repo`).
- **Q6 — must this also close the PermissionRequest-hook gap? [answered]** no. it needs a new role hook
  type across rhachet, the adapter, and a role package, and the arrow stands without it. its own pr
  (fulcrum F7), queued on the radio: `appendix/radio.task.role-hook-on-permission-request.md`.

## what is awkward?

- two clones reach one file by two doors: an ambient clone (a plain `claude`) by the local arrow, an
  explicit clone by `--settings`. both land on `settings.of.repo.json`, so the content is one answer.
- a session's "always allow" is silently kept to the session: the human clicks "don't ask again" and is
  asked again next session. durable allows belong in a role's settings or in `~/.claude/settings.json`.
- claude means the local layer as personal and untracked. the arrow repurposes it as the repo's door, so a
  repo can no longer hold a personal, untracked `settings.local.json`. personal grants still have a home:
  `~/.claude/settings.json`, the grove.
- a replaced real file is gone, not kept aside (case 7). the human learns of the loss from a distinct
  `replaced` row in the brain dir tree (S2) — a row that names the file, never a copy of it.

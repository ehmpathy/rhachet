# wish: the clone daemon's event loop stall line never lands in a crew pane

## .what i want

the line `clone daemon event loop stalled <N>ms` stays out of every crew pane. it lands in the clone's durable trace log only, where a supervisor reads it on purpose.

## .why

the commander saw `clone daemon event loop stalled 2497ms` in the input line of a crew pane (the gads mechanic, grove-ahbode-v20260901, 2026-11-16 [time]Z). text in a pane's input line can be submitted as a prompt by the next Enter, so a diagnostic in the pane can become an instruction to the clone. a diagnostic must never be able to reach a clone as a prompt.

## .what is known (read at source, origin/main)

- `src/domain.operations/clone/genCloneLoopLagWatch.ts` emits the line through an injected `trace`
- `src/domain.operations/clone/socket/genCloneSocketServer.ts` wires that watch (near line 648)
- `writeCloneTraceLine.ts` already appends each trace line to a per-day trace log (`getCloneTraceLogPath`); its header names `getCloneTraceSink` as a tee whose other half is stderr
- the daemon shares the pane's tty with claude, so its stderr paints over the claude screen
- the stall itself reads as box load: grove-ahbode-v20260901 runs ~70 claude processes on 4 cores, so each node daemon's loop starves for cpu. if the trace read shows the daemon blocks its own loop (sync work on its hot path), that part is the daemon's to cure too

## .done means

- no daemon trace line reaches a pane's tty in normal operation; the stall line still lands in the trace log, with its drift
- a test proves it: red against the current tee to stderr, green after
- if the daemon owns any part of the stall, that part is cured, with its own test
- pr title holds the words `event loop`; release --watch green, never --apply

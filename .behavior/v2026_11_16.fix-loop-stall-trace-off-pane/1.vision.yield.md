# vision: the clone daemon's trace lines live in its trace log, never in a pane

## .the contract, in one line

the clone daemon (the pty host that mirrors a brain-cli into a pane and serves its socket) writes
every trace line to its durable per-day trace log ONLY. no daemon trace line is written to the
host's stdout or stderr. the stall line also states the cpu time the daemon spent within the stall,
so the log tells a starved loop apart from a loop the daemon blocked itself.

```
# before — a crew pane, mid-session, on a loaded box
╭────────────────────────────────────────────────╮
│ > clone daemon event loop stalled 2497ms       │   ← painted over claude's input row
╰────────────────────────────────────────────────╯

# after — the same pane, the same stall
╭────────────────────────────────────────────────╮
│ >                                              │   ← clean
╰────────────────────────────────────────────────╯

# after — .agent/.cache/repo=rhachet/skill=clone-say/daemon.2026-11-16.log
clone daemon loop watch live (tick 1000ms, stall past 2000ms)
clone daemon event loop stalled 2497ms (cpu 38ms)
```

## .the outcome world

### a day in the life

the commander runs a grove of ~70 clones, one per tmux pane. the box is loaded, so node daemons
starve and the loop-lag watch fires several times an hour.

- **today**: each stall paints `clone daemon event loop stalled <N>ms` into the pane over claude's
  screen, often on the input row. the commander's eye, and any pane scrape, reads text where the
  clone's input should be empty. the commander has to decide each time whether it is a draft, a
  prompt, or noise
- **after**: the panes show only what claude drew. the stall lines still land, one per stall, in
  the daemon's per-day trace log, with cpu time beside the drift. when the commander wants to know
  how starved the grove is, they read the log on purpose

### the aha

the line was never for the human in the pane. it exists for the person who asks, later, *"why did
that clone go deaf for 30s?"* that person reads the log. the pane was the wrong reader all along.
and once the line carries cpu time, the same read also answers *"is the box starved, or is the
daemon at fault?"*, which the drift alone cannot answer.

### before / after

| | before | after |
|---|---|---|
| a stall in an attended pane | painted on the pane's tty (stderr), and teed to the log | log only |
| a daemon fault (socket error, screen feed fault, write queue fault) in an attended pane | painted on the pane's tty, and teed to the log | log only |
| the stall line | `stalled 2497ms` | `stalled 2497ms (cpu 38ms)` |
| the log cannot be written | named on stderr, so it reaches the pane | named in a fallback log; never the pane (fulcrum F1) |
| an enroll fault before the clone stands up (bind refused, pty refused) | thrown to the enroller, shown on its terminal | unchanged — that is an error the human must see, not a trace |
| `clone say` / `clone get` client stderr | unchanged | unchanged — out of scope; those are client processes, not the daemon |

## .mental model

- **to a friend**: *"the clone's housekeeper used to shout status into the room you were in. now it
  writes in a logbook by the door."*
- **analogy**: a flight data recorder. the pilot's display shows only what flies the plane; the
  recorder holds every anomaly for whoever investigates
- **terms**: a human says *"the pane"*, *"the log"*, *"that stall message"*. we say *tty*, *trace
  sink*, *durable per-day trace log* (`getCloneTraceLogPath`), *attended* vs *detached* host. the
  repo's term for the sink is `trace`; the term for the log is the trace log. no new term is coined

## .evaluation

### goals vs outcome

| wish goal | met by |
|---|---|
| the stall line stays out of every crew pane | the daemon's sink is log-only; not one line it traces is written to its stdio |
| it still lands in the trace log, with its drift | the stall line keeps its drift and gains cpu time |
| a test proves it: red against the tee, green after | a test that runs a daemon sink seam and asserts the line reaches the log and that stderr holds no byte of it (see Q4 on how to observe stderr with no spy) |
| if the daemon owns part of the stall, cure that part | a hot-path audit for sync calls, each one found cured with its own test; plus the cpu share, which decides it for any cause a code read cannot see; see Q2 |

### pros

- one sink rule for the whole daemon: *trace goes to the log*. no per-line judgment about which
  traces are safe to paint
- the stall line becomes diagnostic: cpu time parts two classes the drift alone conflates
- the change shrinks behavior (fewer writes to the tty) rather than adds a mode

### cons

- a human at an attended pane who USED to see a daemon fault at once now has to read the log. for
  a stall, that is the point. for a real fault (the socket server errored), it is a loss of
  immediacy. mitigated: a fault that matters reaches the human another way — `clone say` reports a
  NACK or a wedge with its cause, and `clone list` shows reach state
- the log can fill. the stall line fires at most once per stall, and a stall is ≥2000ms, so the
  ceiling is ~1800 lines per hour in the worst case. per-day rotation already bounds one file

### edge cases and the pit of success

- **a new daemon-side trace site with a default sink**: today three daemon-side operations each
  fall back to `getCloneTraceSink()` when no sink is injected (A2), and the pty host injects none.
  a fourth site, or a missed one, would paint the pane again. pit of success: daemon-side operations take the sink as a REQUIRED input, built once
  in the pty host and threaded down, so the compiler refuses a site that names none (blueprint
  decision; see Q3)
- **the attended vs detached split**: one rule for both. a detached daemon's stderr is a pipe that
  no one reads after handoff (`genCloneEnrollDetached.ts:140-157`), so the log is its only real
  channel there too
- **midnight**: the day is read per line (`getCloneTraceSink.ts:31`), kept as is

## .open questions & assumptions

| # | question | status |
|---|---|---|
| Q1 | can text painted on the pane's input row be submitted as a prompt by the next Enter? | [answered] not by the brain-cli itself: the daemon's stderr writes go to the tty's OUTPUT side; claude's input buffer is fed only by host stdin → `child.write` (`genBrainCliPtyClone.ts:232`), so the painted bytes are never in that buffer. the harm is real all the same: a human or a pane scrape reads the text as typed input, and a supervisor that relays what it reads can turn it into a prompt. the goal holds; the mechanism is "misread, then relayed", not "Enter submits it". [wisher] to confirm this reframe does not change the ask |
| Q2 | does the daemon block its own loop? | [research] unknown — the extant line carries only drift, so starvation and self-block read alike (`rule.forbid.mechanism-inferred-from-outcome`). the cpu time within the stall parts them: cpu ≈ drift → the daemon ran its own sync work; cpu ≪ drift → the loop waited off-cpu (starved by the scheduler, or a sync syscall blocked). one known sync path: the mirror `process.stdout.write` to a tty (`genPtyCloneHostFromProcess.ts:18`), which node runs synchronously on linux, so a pane whose reader lags blocks the loop. this route does BOTH halves: (1) the blueprint audits the daemon's hot path for every sync call (the mirror's tty write; the trace sink's `appendFileSync` + `mkdirSync`, which this change puts on every trace; any `*Sync` fs or child call on a dispatch path) and cures each that can hold the loop for a stall-scale span, each cure with its own test; (2) the cpu suffix covers what a code read cannot see, so the next prod stall names its class. if the audit finds no such call, the yield of the blueprint says so with the grep that proves it |
| Q3 | thread one log-only sink from the pty host, or make `getCloneTraceSink` itself log-only? | [answered] thread it. `getCloneTraceSink` also defaults the sink for client-side callers (`getCloneInputStateOrBlind` from `invokeCloneGet`/`invokeCloneSay`, `writeCloneSayDebugLog` from `invokeCloneSay`), whose stderr is not a pane. a daemon-only change keeps the scope to the wish. the blueprint picks the exact seam |
| Q4 | how does a test observe "no byte reached stderr" with no spy on `process.stderr` (`rule.forbid.integration.mocks`)? | [research] options: run the pty host as a subprocess and read its real stderr; or prove the daemon sink seam is log-only at the unit grain and that the pty host wires that seam. the extant `getOneCloneTraceSinkToLog.integration.test.ts` uses a documented spy; the blueprint decides |
| Q5 | where does a trace line go when the log itself cannot be written? | [wisher] best guess (fulcrum F1): a fallback per-day log under `os.tmpdir()`, never the pane. alternative: drop it with an in-memory count reported on the next good write (a partial failhide). alternative: stderr only when stderr is not a tty (a detached pipe no one reads, so it is near-useless) |
| A1 | the stall in the incident was box load (~70 claude processes on 4 cores) | assumption from the wish; Q2's measurement confirms or refutes it on the next stall |
| A3 | "cpu time within the stall" measures the MAIN thread | [research] `process.cpuUsage()` is process-wide, so gc threads, the libuv threadpool, and node-pty's threads all add to it, and a high value would not prove the loop itself did the work. partly answered: the pinned `@types/node@22.15.21` declares no `process.threadCpuUsage` (grep: 0 hits) but does declare `performance.eventLoopUtilization()` (`perf_hooks.d.ts:206`), which splits the MAIN loop's own active time from its idle time. the blueprint picks the pair (process cpu, loop utilization) or one of them, and the suffix states which it reports and what it cannot part |
| A4 | the pane that showed the line ran an ATTENDED clone | holds by logic: a pane that shows claude's screen is fed by an attended host's stdout (`genPtyCloneHostFromProcess.ts:18`); a detached host has no tty to paint. the grove box may run an older rhachet; the fix is forward either way |
| A5 | no extant test reads a daemon trace line off stderr | [research] to grep at blueprint: any acceptance or integration test that asserts a `clone socket …` / `clone daemon …` line on a host's stderr must move to read the trace log |
| A2 | the daemon's trace sites are reached through three default-to-tee seams: the socket server's `trace` (`genCloneSocketServer.ts:127-128`), the write queue's `traceToStderr` (`genCloneWriteQueue.ts:92`; the socket server builds the queue with no sink, so it defaults on its own), and the screen feed's `traceToStderr` (`genCloneScreenFeed.ts:248`). the other two `getCloneTraceSink` consumers (`getCloneInputStateOrBlind`, `writeCloneSayDebugLog`) run in client processes | verified by grep of `getCloneTraceSink()` and each caller; the blueprint re-greps every `process.stderr` write on the daemon path |

## .what is awkward?

- **two docblocks argue opposite claims today.** `getCloneTraceSink` calls stderr "the operator
  channel", and its own later note plus `genCloneSocketServer.ts:659-664` say stderr is the
  human's terminal. this change settles it: on the daemon, stderr is the human's, so the daemon
  does not write there. the stale docblocks must be repaired in the same change
- **a real fault loses its immediacy at an attended pane.** that trade is deliberate, and it rests
  on Q1's reframe: the harm of a painted line outweighs a fault notice the `clone say` verdict
  already carries
- **the log-unwritable case has no clean home** (Q5). every option either writes somewhere a human
  must know to look, or loses the line. a fallback log is the least bad
- **the cpu suffix measures, it does not cure.** the audit cures what a code read can find in this
  route; a cause only a prod stall reveals (cpu ≈ drift with no sync call in the audit) would owe a
  follow-up, caught as a dream, never left implicit
- **this change adds sync work to the hot path.** today a trace line costs a tty write plus an
  `appendFileSync`; after, it costs the `appendFileSync` alone. less work per line, but still sync —
  so the audit in Q2 must weigh the sink it ships, not only the code it found

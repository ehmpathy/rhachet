# vision: brain auth context — get-or-unlock creds

## .what

when the brain context grants credentials via `keyrack: { owner, env }`, it should
**get each key, and if a key can't be gotten, unlock just that key and re-get** — failing
only when a key is both un-gettable *and* un-unlockable, and failing with a **malfunction**.

today the brain only *gets*. locked keys throw immediately, which shoves the unlock burden
back onto every consumer.

---

## the outcome world

### day-in-the-life

a consumer wires up a brain and asks it something:

```ts
const context = genContextBrain({
  creds: { keyrack: { owner: 'ehmpath', env: 'test' } },
});

const answer = await context.brain.choice.ask({
  role: myRole,
  prompt: 'summarize this',
  schema: { output: outputSchema },
});
```

behind the scenes, the brain supplier needs `XAI_API_KEY` (env=test). it's stored in a
non-interactive vault (`os.secure`) but not yet in the daemon. instead of throwing
"credential is locked. unlock it first.", the brain context now:

1. tries `keyrack.get` → status `locked`
2. unlocks **just that key** (`--key XAI_API_KEY --env test`) into the daemon
3. re-gets → status `granted`
4. hands the secret to the brain

the consumer never ran `rhx keyrack unlock`. the ask just works.

### before / after

| | before (today) | after (this wish) |
|---|---|---|
| locked key | throws `BadRequestError` with a "run: rhx keyrack unlock" hint | auto-unlocks that one key, re-gets, proceeds |
| consumer ritual | must remember to unlock before every brain run | no step — creds grant themselves |
| what gets unlocked | consumer overshoots to `unlock --env test` (whole env) | only the narrow keys the brain actually needs |
| interactive fallout | whole-env unlock drags in the interactive `AWS_PROFILE` sso login even when unwanted | narrow non-interactive keys unlock silently; interactive ones untouched |
| genuine failure | opaque `BadRequestError` | explicit `MalfunctionError` (un-gettable *and* un-unlockable) |

### the aha moment

> "i asked the brain a question and it just answered — i didn't have to unlock anything, and
> it didn't hijack my terminal with an aws sso browser prompt for a key i wasn't even using."

the value clicks the first time a consumer runs a brain in a fresh session **without** a
preceding `rhx keyrack unlock`, and it simply works for the narrow keys — while leaving the
noisy interactive keys asleep.

## user experience

### usecases & goals

- **library consumer** wires a brain into their app and wants creds to grant from
  keyrack without a manual unlock step.
- **test-suite author** runs brain-backed integration tests that need one or two narrow
  keys, and doesn't want the whole env (including aws sso) unlocked in ci or locally.
- **cli/agent operator** invokes a rhachet skill that spins up a brain; the skill grants
  its own narrow creds on demand.

### contract inputs & outputs

the **consumer-facing contract does not change**. that is the point — the ergonomics win is
that consumers keep the exact same call:

```ts
// input: unchanged
genContextBrain({ creds: { keyrack: { owner: 'ehmpath', env: 'test' } } });
```

the behavior change lives inside the creds-grant path
(`getSdkCredsFromBrainSupplies`), which today does get-only and will become get-or-unlock.

internally the new capability composes two extant contracts:

- `keyrack.get({ for: { key }, env, owner })` → `{ attempt, emit }`
  ([`sdk.keyrack.ts:71`](../../src/contract/sdk.keyrack.ts)) — statuses:
  `granted | locked | absent | blocked`
  ([`KeyrackGrantStatus.ts:11`](../../src/domain.objects/keyrack/KeyrackGrantStatus.ts))
- `unlockKeyrackKeys({ owner, env, key }, contextKeyrack)` → `{ unlocked, omitted }`
  ([`unlockKeyrackKeys.ts:32`](../../src/domain.operations/keyrack/session/unlockKeyrackKeys.ts))

### what leveraging it looks like

each key follows a small state machine:

```
get(key)
  ├─ granted            → use secret ✅
  ├─ locked             → unlock(key) → get(key)
  │                         ├─ granted → use secret ✅
  │                         └─ else    → MalfunctionError 💥 (unlock failed / no identity)
  ├─ absent             → ConstraintError ✋ (never configured — caller must `set` it)
  └─ blocked            → ConstraintError ✋ (firewall — caller must swap the credential)
```

### timeline

1. `t0` — consumer calls `brain.choice.ask` with keyrack creds
2. `t1` — supplier requests its keys; get-or-unlock grants each (unlock only for `locked`)
3. `t2` — first unlock may decrypt the host manifest once (identity discovery; ideally
   non-interactive via ssh-agent)
4. `t3` — secrets granted → brain call proceeds
5. subsequent asks in the same session hit the daemon and skip unlock entirely

## mental model

### how a user describes it to a friend

> "keyrack creds for the brain are lazy now — it fetches what it needs and unlocks it on the
> fly if it has to, instead of making me unlock the whole vault up front."

### analogies / metaphors

- **auto-unlock like a keycard**: you badge into the one door you need, not the whole
  building.
- **lazy loading for secrets**: fetch-on-demand, unlock-on-miss, cache in the daemon.
- **get-or-create, but for access**: mirrors the `gen` (findsert) verb — "grant-or-unlock".

### terms: theirs vs ours

| user says | we say |
|-----------|--------|
| "log in / unlock my keys" | `unlockKeyrackKeys` → daemon session |
| "grab the api key" | `keyrack.get` → `KeyrackGrantAttempt` |
| "it's locked" | `status: 'locked'` |
| "the key doesn't exist" | `status: 'absent'` |
| "it just works now" | get-or-unlock grant |

## evaluation

### how well it solves the goals

- **eliminates the unlock ritual** for brain consumers — the core wish. ✅
- **narrows the blast radius** — unlock targets the specific `--key`, so the whole-env
  interactive fallout (aws sso) is avoided. ✅
- **keeps the pit of success** — consumers can't forget to unlock, because they no longer
  have to. ✅

### pros

- zero change to the consumer contract; pure ergonomics upgrade.
- reuses extant, tested operations (`keyrack.get`, `unlockKeyrackKeys`).
- clear failure semantics: malfunction only when truly stuck.

### cons / tradeoffs

- the get path uses the **lightweight** `genContextKeyrackGrantGet` (no host manifest);
  unlock needs the **heavier** `genContextKeyrack` + `daoKeyrackHostManifest.get()` (identity
  discovery, possible passphrase). get-or-unlock must lazily build the heavier context only
  when a key is `locked` — otherwise we pay the cost (and prompt risk) on every get.
- auto-unlock could still trigger an interactive prompt if *the specific key's* vault is
  interactive (e.g., an aws sso key requested directly). narrowing helps but doesn't fully
  eliminate interactivity — it just stops unwanted collateral unlocks.
- unlock has side effects (writes secrets into the daemon with a TTL). auto-unlock makes
  those side effects implicit rather than an explicit operator action.
- **compat caveat**: "the consumer contract does not change" holds only for the *success*
  path. today a `locked` key throws `BadRequestError` (`getSdkCredsFromBrainSupplies.ts:67-71`);
  after this change it auto-unlocks instead. a consumer that today *catches* the locked-throw
  and handles it (fallback supplier, human prompt) would see that catch branch go quiet once
  auto-unlock succeeds. the *failure* contract shifts from throw-early to
  throw-only-when-truly-stuck. before build, grep consumers for `try/catch` around brain creds
  to confirm no one depends on the early throw.

### edgecases & pit-of-success

| edgecase | behavior | keeps user safe by |
|----------|----------|--------------------|
| key already in daemon | get → granted, no unlock | not re-prompting |
| key locked, non-interactive vault | unlock silently, re-get | granting without noise |
| key locked, interactive vault (aws sso) | keyrack handles the prompt (its extant behavior) — for *that key only* | no collateral whole-env unlock |
| key locked, unlock ran but re-get still not granted | MalfunctionError 💥 | fail loud, not silent hang |
| key `absent` (never configured) | ConstraintError ✋ — unlock can't help | clear "set it first" signal |
| key `blocked` (firewall) | ConstraintError ✋ — surface firewall reason | no hidden policy block |
| multiple keys, some lock / some granted | grant each independently | partial progress, precise failure |

## open questions & assumptions

### assumptions

1. **the target consumer is `getSdkCredsFromBrainSupplies`** — the only brain-context place
   that grants `keyrack: { owner, env }`
   ([`getSdkCredsFromBrainSupplies.ts:60`](../../src/domain.operations/brain/getSdkCredsFromBrainSupplies.ts)).
   verified: it's the sole caller pattern for keyrack creds in the brain path.
2. **"can't be gotten" == status `locked`** primarily. `absent` and `blocked` are *not*
   fixable by unlock.
3. **narrow unlock** means `unlockKeyrackKeys({ owner, env, key })` scoped to the one key
   name, not the whole env.
4. the failure type is **status-dependent** (wisher-confirmed 2026-07-05):
   - `locked` → unlock ran → still not granted, or identity un-discoverable →
     **`MalfunctionError` 💥** (server-must-fix, exit 1) — this is the case the wish means.
   - `absent` (never configured) / `blocked` (firewall) → unlock cannot help →
     **`ConstraintError` ✋** (caller-must-fix, exit 2), since these are mis-configuration,
     not server faults.

### open questions — triaged

each tagged **[answered]** (decided now via logic/code, or by the wisher on 2026-07-05),
**[research]** (defer to research phase), or **[wisher]** (needs wisher input). all wisher items are
now answered; only the single **[research]** item (#8, consumer catch audit) remains for the build.

1. **[answered — wisher 2026-07-05] absent & blocked error class**: each fails as a
   **`ConstraintError` ✋** (caller-must-fix, exit 2). `MalfunctionError` 💥 is reserved for
   "locked → unlock ran but re-get still not granted / no identity". the wisher confirmed the
   deviation from the wish's literal "malfunction" wording.
2. **[answered — wisher 2026-07-05] interactivity**: not our concern — **keyrack already handles
   interactivity** in its extant unlock path. no special policy needed here; auto-unlock inherits
   whatever prompt behavior keyrack already provides.
3. **[answered] surface = internal-only**: change lives inside `getSdkCredsFromBrainSupplies`;
   no new sdk api required for the wish. an sdk `unlock` method (`keyrack.get({ allow:{unlock} })`
   or `keyrack.getOrUnlock`) is future scope for other consumers, not this wish.
4. **[answered] duration/TTL**: reuse the extant unlock default (9h) for consistency; no new TTL
   invented. revisit only if a shorter implicit-unlock TTL is later desired.
5. **[answered — wisher 2026-07-05] daemon spawn as a side effect**: acceptable. a library brain
   call may silently spawn/contact the keyrack daemon (`findsertKeyrackDaemon`,
   `unlockKeyrackKeys.ts:48`) and decrypt the host manifest (`unlockKeyrackKeys.ts:51`) on a cache
   miss — it mirrors what the extant unlock path already does.
6. **[answered] grant granularity = batched**: prefer one env-scoped unlock filtered to the
   needed key names — a single manifest decrypt, no parallel stampede — over N per-key unlocks.
   `unlockKeyrackKeys` today supports a single `--key` filter, not a key *set*, so a batched path
   may need it extended. execution detail; outcome world identical.
7. **[answered] identity discovery from `{ owner, env }`**: `discoverIdentities` sources
   ssh-agent + `~/.ssh/$owner` (`genContextKeyrack.ts:80-83`). the brain creds contract carries
   no prikey; when discovery yields no identity, unlock is genuinely un-unlockable → malfunction
   that carries an "identity not discoverable, unlock manually with --prikey" hint.
8. **[research] consumer catch audit**: does any downstream consumer today *catch* the locked
   `BadRequestError` (`getSdkCredsFromBrainSupplies.ts:67-71`) and handle it? grep consumers for
   `try/catch` around brain creds before build — the failure-contract shift (see compat caveat)
   must not silently disable a caller's fallback path.
9. **[answered] env=all fallback agreement**: get and unlock both implement env=all fallback
   (`getKeyrackKeyGrant.ts:44-64`, `unlockKeyrackKeys.ts:142-159`), so auto-unlock of `org.all.KEY`
   and re-get of `org.test.KEY` reconcile. invariant holds; lock it with a test.

### must research externally

no external dependencies. all mechanisms (keyrack, daemon, vault adapters) are in-repo.

## groundwork

### external research

no external APIs, services, or docs referenced by the wish. the whole surface is
internal keyrack machinery.

### internal research

verified the extant contracts the vision builds on:

- **brain creds consumer** — `getSdkCredsFromBrainSupplies.ts:60-74`: loops keys, calls
  `keyrack.get`, throws `BadRequestError` on any non-`granted` status. this is the
  get-only behavior to change.
- **keyrack get sdk** — `sdk.keyrack.ts:71-112`: `keyrack.get({ for: { key }, env, owner })`
  uses the lightweight `genContextKeyrackGrantGet` (reads daemon + envvar only, never the
  vault) → returns `{ attempt, emit }`.
- **grant statuses** — `KeyrackGrantStatus.ts:11` & `KeyrackGrantAttempt.ts`:
  `granted | absent | locked | blocked`. only `locked` is unlock-fixable. a locked attempt
  already carries a `fix` hint (`getKeyrackKeyGrant.ts:89-95`).
- **unlock operation** — `unlockKeyrackKeys.ts:32-283`: takes `{ owner, env, key, duration }`
  + a **heavier** `ContextKeyrack`; requires `context.hostManifest` (line 51) which is
  populated by `daoKeyrackHostManifest.get()`. returns `{ unlocked, omitted }` where
  `omitted` carries reasons `absent | lost | remote`.
- **unlock context wiring** — `invokeKeyrack.ts:1054-1060`: unlock builds `genContextKeyrack`
  then `daoKeyrackHostManifest.get({ owner }, context)` before calling `unlockKeyrackKeys`.
  this decrypt step is the interactive-risk point.
- **the get context deliberately excludes the vault** — `genContextKeyrackGrantGet.ts:20-22`:
  "get only reads from unlocked sources … os.direct intentionally excluded — vault keys
  require explicit unlock first." so get and unlock are genuinely two different context
  weights, and get-or-unlock must bridge them.
- **`keyrack` sdk exposes only `get / set / source`** — `sdk.keyrack.ts:64-151`. there is
  **no** `keyrack.unlock` sdk method today; unlock lives only at the cli layer. so this
  wish likely needs to expose unlock (or an orchestrator) at a layer the brain path can call.

### vocab / patterns to reuse

- verbs: this is a **`gen`-flavored** (findsert) idea — "grant-or-unlock". name accordingly
  (e.g., `genKeyrackKeyGrantOrUnlock` or `getOrUnlockKeyrackKey`).
- error classes: `MalfunctionError` (exit 1) vs `ConstraintError`/`BadRequestError`
  (exit 2 / caller-fix) — pick per open-question #1.
- attempt envelope + `fix` hint pattern already carries actionable guidance to reuse.

## what is awkward?

1. **two context weights.** get is deliberately lightweight (no manifest, no passphrase);
   unlock is heavy. get-or-unlock straddles both, so it must lazily escalate to the heavy
   context *only on a lock miss*. this feels a bit like leaking an implementation seam into
   the brain path.
2. **"malfunction" for `absent`.** calling a never-configured key a *malfunction* fights the
   usual meaning (server-fault). a missing key is a caller/config problem. the wish's blanket
   "malfunction" wording is the main place the design fights the established error taxonomy —
   flagged as open question #1.
3. **implicit side effects.** auto-unlock silently writes secrets into the daemon with a TTL.
   convenient, but it turns an explicit operator action into a hidden one — some operators
   may want an opt-out or at least a log trail.
4. **interactivity leak.** the win is avoiding *collateral* interactive unlocks, but a
   directly-requested interactive key could still prompt mid-brain-call, which is a jarring
   place for a browser sso flow to appear. narrowing reduces but doesn't fully close this.
5. **no sdk unlock today.** unlock is cli-only, so the "brain context makes it easy to
   unlock" framing implies plumbing unlock down to a callable layer — a slightly bigger
   surface than the wish's one-liner suggests.

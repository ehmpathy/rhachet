## v2 — option B expansion

the v2 scope unified the get-or-unlock capability onto a shared core (`getKeyrackKeyGrants`) with
two projections (secrets map + sdk/cli attempt shape). this section documents the added surfaces,
their tests, and the honest limits of what the host can prove.

### new / reshaped surfaces

| surface | file | shape | opt-in |
|---------|------|-------|--------|
| core resolution | `getKeyrackKeyGrants/getKeyrackKeyGrants.ts` | `KeyrackGrantAttempt[]` (never throws on status) | `with: { unlock }` (required) |
| brain projection | `getKeyrackKeySecrets/getKeyrackKeySecrets.ts` | `Record<string,string>` secrets | `with: { unlock }` (required) |
| sdk projection | `contract/sdk.keyrack.ts` `keyrack.get` | `{ attempt/attempts, emit }` + exit code | `with?: { unlock? }` (optional, default off) |
| cli projection | `contract/cli/invokeKeyrack.ts` `keyrack get` | stdout + exit code | `--unlock` (optional, default off) |

both the sdk and cli **always** route through the core; they vary only by whether `unlock` is set
(no branch on ternary — per the "same flow" design decision). absent `with`/`--unlock` ⇒ today's
pure get, so the change is back-compatible.

### honest limit — env-backed keys (documented, not a gap)

on this host the test keys (`XAI_API_KEY`, and the acceptance `__TEST_*__` keys) are supplied via
`os.envvar` with no local vault copy. so `vaultAdapterOsEnvvar.get` grants from `process.env`, and:
- a `relockKeyrack` purge leaves the env-var source intact ⇒ key stays granted;
- removing the env var makes the key `absent` (not `locked`), since
  `inferKeyrackKeyStatusWhenNotGranted` only returns `locked` when a local inventory/vault file is present.

so a **genuine `locked` → vault-unlock → re-get** path is unreachable for these keys on this host. the
integration + acceptance opt-in cases therefore prove two honest things: (a) the ungettable path is
robustly asserted as `.not.toEqual('granted')` (locked or absent both ⇒ caller-fix), and (b) the sdk +
cli **accept** the opt-in and return granted without breaking an available get. the genuine vault-unlock
mechanism itself is exercised by the prior `unlockKeyrackKeys` integration suite (unchanged); the
core merely composes it. this limit is flagged, not silently skipped.

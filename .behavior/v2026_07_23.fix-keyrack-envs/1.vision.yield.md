# vision: support `--env camp` in keyrack

## the wish, distilled

keyrack rejects `--env camp` with:

```
BadRequestError: invalid --env: must be one of sudo, prod, prep, test, all
```

the wish is scoped and explicit:

> gotta support the --env camp
> this is another point towards elimination of allowlist on env
> **but for now, lets just only add support for camp**

so: add `camp` to the allowlist. do **not** eliminate the allowlist (that's a bigger,
separate dream — see `.dream/2026_04_26.keyrack-allow-custom-envs.dream.md`).

---

## the outcome world

### day-in-the-life

vlad is on `infrastructure.vlad.fix-cloud-ducts` and needs the `camp` environment — a
**homebase for clones**, the launch point from which a clone reaches out into *other*
accounts (e.g. readwrite against prep, readonly against prod). he runs:

```
➜ use.ahbode.camp --owner admin
# under the hood: keyrack unlock --key AWS_PROFILE --env camp --owner admin
```

**before:** hard stop. `BadRequestError`. `camp` is not on the allowlist, so the whole
flow dies before a single credential is unlocked.

**after:** `camp` is a recognized env. the unlock proceeds exactly as it would for
`prep` or `prod` — keys tagged `camp` unlock, the daemon holds them, `use.ahbode.camp`
works.

### before/after contrast

| dimension | before | after |
|-----------|--------|-------|
| `keyrack unlock --env camp` | ✋ `BadRequestError` | ✨ unlocks camp keys |
| `keyrack set --env camp` | ✋ `BadRequestError` | ✨ stores key tagged camp |
| `keyrack status --env camp` | ✋ `BadRequestError` | ✨ filters to camp keys |
| error message when env truly invalid | `...sudo, prod, prep, test, all` | `...sudo, prod, prep, test, all, camp` |

### the "aha"

the value clicks the moment `use.ahbode.camp --owner admin` returns credentials instead
of an error. no new flags to learn, no new mental model — `camp` just joins the family of
envs that already work.

## user experience

### usecases / goals

- **unlock camp creds** — `keyrack unlock --key AWS_PROFILE --env camp --owner admin`
  (the exact failing command from the wish)
- **store a camp cred** — `keyrack set --key AWS_PROFILE --env camp --vault aws.config`
- **inspect camp creds** — `keyrack status --env camp`

### contract inputs & outputs

- **input:** `--env camp` (a string), same slot as `--env prep` today
- **output:** identical to any recognized env — unlock tree, status tree, set confirmation
- the contract shape does not change; only the set of accepted `--env` values grows by one

### timeline

```
1. human runs `use.ahbode.camp --owner admin`
2. → keyrack unlock --key AWS_PROFILE --env camp --owner admin
3. isValidKeyrackEnv('camp') → true   (was false)
4. unlock proceeds; camp-tagged keys load into daemon
5. use.ahbode.camp reads AWS_PROFILE, does its thing ✨
```

## mental model

### how a user describes it to a friend

> "keyrack knows about a few environments — prod, prep, test, sudo. now it knows about
> `camp` too."

### analogy

the allowlist is a **guest list at the door**. today `camp` isn't on it and gets turned
away. this wish adds one name to the list. (the bigger dream is to drop the guest list
entirely and let anyone in — but that's not this wish.)

### terms: theirs vs ours

| they say | we say |
|----------|--------|
| "environment" / "env" | `KeyrackEnv` |
| "the list of allowed envs" | `KEYRACK_VALID_ENVS` |
| "is camp allowed?" | `isValidKeyrackEnv('camp')` |

`camp` is a proper env name — a **homebase for clones**, the account a clone launches from
to reach into *other* accounts (readwrite prep, readonly prod). it names a **launch point**,
not a target tier, so it sits alongside `prod`/`prep`/`test` in the vocabulary but plays a
distinct role: the others name *where credentials belong*, camp names *where a clone lives*.

## evaluation

### how well it solves the goal

fully. the allowlist is centralized in **one** constant, and every enforcement site reads
from it. adding `camp` to `KEYRACK_VALID_ENVS` propagates to all sites at once.

### the single source of truth

`src/domain.operations/keyrack/constants.ts:11`

```ts
export const KEYRACK_VALID_ENVS = ['sudo', 'prod', 'prep', 'test', 'all'] as const;
```

enforced via `isValidKeyrackEnv` at (verified by grep):

- `src/contract/cli/invokeKeyrack.ts:905` — `del --env` validation (command at :874)
- `src/contract/cli/invokeKeyrack.ts:1058` — `unlock --env` validation (command at :1028) ← **the wish's path that threw**
- `src/contract/cli/invokeKeyrack.ts:1210` — `status --env` filter validation (command at :1193)
- `src/contract/cli/invokeKeyrack.ts:1468` — `firewall --env` validation (command at :1451; distinct error text `invalid --env value` but reads the same `KEYRACK_VALID_ENVS`)
- `src/domain.operations/keyrack/asResolvedEnvForSet.ts:14` — `set --env` validation (used by set command at :657)

add `'camp'` to the constant → all five sites accept it. no site has its own private
allowlist, so there is no risk of a missed spot. slug-parse consumers
(`asKeyrackKeySlug.ts:25`, `isKeyrackSlugFormat.ts:11`, `getOneKeyrackGrantByKey.ts:32/57`)
also read `isValidKeyrackEnv`, so `@all.camp.AWS_PROFILE`-style slugs parse camp as a valid
env segment too — the intended behavior. no exhaustive `switch` on `KeyrackEnv` exists, so a
new value breaks no exhaustiveness.

### pros

- **one-line domain change** — add `'camp'` to the array; type `KeyrackEnv` widens
  automatically
- **no contract shape change** — `--env` already takes this exact slot
- **storage already permissive** — `daoKeyrackHostManifest/schema.ts:41-42` already
  accepts custom env names via `.or(z.string().regex(/^[a-z][a-z0-9_-]*$/))`, so there is
  no storage migration
- **keeps the pit of success** — an unrecognized env still fails loud with the (now
  updated) list

### cons

- **still an allowlist** — we're extending the very thing the wish flags for eventual
  removal. this is deliberate per the wish ("for now, lets just only add support for
  camp"). we pay a small, known tech-debt increment.
- **docs/help-text drift risk** — several `.description()` hints hardcode
  `"prod, prep, test, all, or sudo"` (e.g. lines 363, 675, 879, 1032). these are cosmetic
  and out of the strict allowlist path; the vision flags them for the blueprint to decide
  whether to touch.

### edgecases & pit-of-success

| edgecase | behavior | keeps user safe? |
|----------|----------|------------------|
| `--env camp` | accepted, unlocks | ✅ the wish |
| `--env kamp` (typo) | rejected: `...test, all, camp` | ✅ loud fail, lists valid set incl camp |
| `camp` requires `--key`? | no — only `sudo` has the `--key`-required rule (line 1066); camp behaves like prep/prod | ✅ no surprise gate |
| extant snapshots | one snapshot pins the old error string (`keyrack.status.env-filter.acceptance.test.ts.snap:5`) — must resnap to include camp | ✅ caught by test suite |

## open questions & assumptions

### assumptions

1. **`camp` is env-specific, like `prep`/`prod`** — not elevated like `sudo`. so it needs
   **no** `--key`-required special-case. (the wish's command supplies `--key AWS_PROFILE`
   anyway, but that's the caller's choice, not a camp requirement.)
2. **scope is exactly one env** — add `camp`, no other env. we are explicitly **not**
   removing the allowlist.
3. **`camp` sorts after `all`** in the list — placement is cosmetic (affects error-string
   order + help text). appended at the end reads naturally.

### open questions (triaged)

- **[answered] help-text hints** — should the blueprint also update the five hardcoded
  `--env` option-help strings (`"prod, prep, test, all, or sudo"` at :363, :675, :879, :1032,
  and firewall's `"(test, prod, prep, all)"` at :1453)? **answered now by logic:** yes,
  update them for consistency — an env we accept but omit from its own help text is a
  discoverability gap (`rule.require.discoverability`). low cost, no gate risk. the blueprint
  should include this as in-scope polish, not defer it.
- **[answered] what `camp` means** — the wisher confirmed: `camp` is a **homebase for
  clones** — the account a clone launches from to reach into *other* accounts (e.g.
  readwrite against prep, readonly against prod). so the `constants.ts` `.note` line should
  read roughly: `camp: homebase for clones — launch account from which a clone reaches
  other accounts (readwrite prep, readonly prod)`. note the nuance: camp names a *launch
  point*, not a target tier, unlike the other envs.
- **[answered] does `camp` need a `--key` gate like `sudo`?** — **answered now by code:**
  no. `invokeKeyrack.ts:1065-1070` shows the `--key`-required rule guards `env === 'sudo'`
  only; camp inherits the prep/prod behavior. no special-case needed.

### research needed externally

none — no external dependencies. `camp` is an internal env name; no external API/service
contract is involved.

## what is awkward?

- **extending a thing we want to delete.** the wish itself calls this out — every added
  env is "another point towards elimination of allowlist." adding `camp` is a band-aid on
  a design the wisher already wants gone. it's the right *scoped* call for now, but it
  feels like paddling against the eventual current. 🌊
- **`all` in the allowlist is a different kind of thing** than `prod`/`prep`/`test`/`camp`
  — it's a wildcard/fallback, not a real env. so the "list of envs" already mixes two
  concepts, and `camp` joins the concrete-env subset. not a blocker, just a latent smell
  the bigger dream would settle.
- **help-text vs error-text can drift.** the allowlist is centralized, but the human-facing
  hints that *describe* it are scattered string literals. adding `camp` cleanly to the
  enforcement path could still leave stale `.description()` text saying only "prod, prep,
  test, all, or sudo" — a small consistency wart the blueprint should consciously accept
  or fix.

## what changed

### 1. the constant (single source of truth)

`KEYRACK_VALID_ENVS` gains `'camp'`, plus a `.note`:

> camp: homebase for clones — the account a clone launches from to reach into other accounts
> (e.g. readwrite against prep, readonly against prod). names a launch point, not a target tier.

this one entry flows to all five `isValidKeyrackEnv` gates (del :905, unlock :1058,
status :1210, firewall :1468, set via `asResolvedEnvForSet:14`) and to the slug-parse
consumers (`asKeyrackKeySlug`, `isKeyrackSlugFormat`, `getOneKeyrackGrantByKey`).

### 2. help text (in-scope polish, per triaged open-question)

seven `--env` option-help strings hardcoded the env list; all now include camp:
- five `"...all, or sudo"` → `"...all, sudo, or camp"` (:363, :675, :879, :1032, :1197)
- firewall `"(test, prod, prep, all)"` → `"(test, prod, prep, all, sudo, camp)"` (:1453)
- source `"...test, all"` → `"...test, all, sudo, camp"` (:531)

(the vision predicted five help strings; execution found a sixth at :1197 — the `status --env`
help; the consistency self-review then caught a seventh at :531 — the `source --env` help,
which the sedreplace missed because its list lacks `, or sudo`.)

**peer-review convergence (i002):** the firewall (:1453) and source (:531) help strings
originally omitted `sudo` — a pre-extant gap. two peer nitpicks (r009) flagged this as a
discoverability gap: `isValidKeyrackEnv` accepts `sudo` and the source command explicitly
handles it, so help that omits it misleads. fixed both to list `sudo` alongside `camp`.

### 3. snapshots

three acceptance snapshots pinned the old list; all regenerated by a real CLI run (not
hand-edited):
- status error string → `must be one of sudo, prod, prep, test, all, camp`
- firewall help → `which env to grant (test, prod, prep, all, sudo, camp)`
- source help → `target env: prod, prep, test, all, sudo, camp`

### 4. positive-path snapshot (peer-review convergence, i002)

the `status --env camp` positive test (case2 [t3]) at first asserted only exit-code +
empty-keys. a peer blocker (r008 + r009) cited `rule.require.contract-snapshot-exhaustiveness`:
every CLI output variant must be snapped so drift is caught. added a
`then('stdout matches snapshot', ...)` block (volatile fields redacted, per the peer tests in
the same case) → `keyrack.status.env-filter.acceptance.test.ts.snap` now pins the camp output.

## out of scope (deferred to the wisher's larger dream)

the wish is explicit about its bound:

> this is another point towards elimination of allowlist on env
> **but for now, lets just only add support for camp**

the three consolidation findings below all share one shape: make `KEYRACK_VALID_ENVS` the
single source for *more than validation* (help text, the schema enum, the type's home
layer). that is the "elimination of allowlist" work the wish named and then deferred. each
is functionally correct in the merged code today; each is flagged for the allowlist dream,
not silently dropped. the peer reviewer (r011 i004) itself offered to "leave them as
documented findings since the wish scoped this narrowly to 'just add camp'."

- elimination of the allowlist entirely (`.dream/2026_04_26.keyrack-allow-custom-envs.dream.md`).
  camp is a *launch point*, not a target tier — a genuinely different kind of env, which
  strengthens the case for eventual removal, but that is a separate wish.

- **shared env-list descriptor** (peer r011 nitpick 2, structural form): the nine help
  strings could derive from one `KEYRACK_VALID_ENVS`-based descriptor so no future env can
  omit itself. this is the right long-term shape, but a nine-call-site refactor is exactly
  the "another point toward allowlist removal" work the wish bounded out. the concrete
  camp-discoverability gaps the nitpick surfaced (fill :1352, relock :1148) are fixed now;
  the DRY refactor is deferred to the allowlist dream.

- **second stale enum in `daoKeyrackHostManifest/schema.ts:40`** (peer r011 nitpick 1 →
  blocker in i004): a private `z.enum(['all','sudo','prod','prep','test','dev','local'])`
  predates this change, already carried `dev`/`local` (never real envs) and omits camp. it
  is functionally inert today — the `.or(z.string().regex(...))` fallback accepts any
  lowercase slug, so camp already validates there. r011 i004 proposes a deeper structural
  fix: relocate `KEYRACK_VALID_ENVS`/`KeyrackEnv`/`isValidKeyrackEnv` from
  `domain.operations/keyrack/` to `domain.objects/keyrack/` (it is pure value-vocabulary,
  not an operation), so `access/daos` may import it as its one permitted upward edge and the
  two enums collapse into one. that is the correct long-term shape — but it is a cross-layer
  migration that ripples through every importer (all five gates + the slug parsers), and it
  is squarely the "single source of truth for env vocabulary" consolidation the wish
  deferred. current state regresses no guarantee: validation is centralized behind the one
  live predicate, and the schema's regex already accepts camp. flagged for the dream, not
  fixed here.

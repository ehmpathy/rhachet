# 1.vision — launch the `keyrack-infra` pattern (github-app setup without org admin)

## the wish

> today, when someone tries to add a github app into keyrack for an org, it looks
> like they're required to have admin creds in order to enumerate the apps installed
> in that org. since this feature is expected to be used by members and not just
> admins, that breaks the experience for a lot of folks. how could we eliminate that
> need for admin creds in order to see the github apps installed? OR could we just
> grant members the ability to see that?

---

## the reframe

v1 of this vision explored per-member workarounds (authenticate as the app via jwt; or
paste ids by hand). the wisher chose something more durable: a **per-org shared source of
truth** that members can read without admin. this behavior **launches the `keyrack-infra`
pattern** — an optional per-org private repo, `$org/keyrack-infra` — and its first
inhabitant is a github-app registry.

> the full menu of options explored is preserved at
> `refs/1.vision.yield.v1.options-explored.md`.

the shift in one line: **stop the per-member app discovery; publish it once into a
member-readable repo, and read from there.**

---

## the knot (why admin is required today)

the guided setup (`mechAdapterGithubApp.acquireForSet`) discovers apps through an
**org-owner-gated** endpoint:

- `mechAdapterGithubApp.ts:159-163` → `gh api /orgs/${org}/installations`
  returns `{ id, app_id, app_slug }` per install — one admin call harvests both the
  `installationId` and the `app_id`.

github gates that endpoint behind org owner:
> "The authenticated user must be an organization owner to use this endpoint."
> — https://docs.github.com/en/rest/orgs/orgs#list-app-installations-for-an-organization

so a plain member 403s mid-flow. that is the bug. the stored credential the flow
produces — `appId`, `installationId`, `privateKey` (`:16-20`, `:220-226`), consumed by
`deliverForGet` (`:240-265`) — does **not** change. only *discovery* moves.

---

## the pattern: `$org/keyrack-infra`

a private repo, one per org, convention-named `$org/keyrack-infra`.

**why a private repo (and not the alternatives)** — of every github-native store, only two
are both member-readable *and* lockable to member-only, and the repo file wins:

| store | member reads? | lock | fit |
|-------|---------------|------|-----|
| **file in a private repo** | ✅ repo read | ✅ repo/team access | ✅ plain json, any size |
| org custom properties | ✅ | ⚠️ = repo visibility (no per-property lock) | ❌ string ≤75 chars, per-repo, admin schema |
| org actions variable | ❌ admin:org to read | — | — |
| org/repo secret | ❌ write-only (unreadable) | — | — |
| secret gist | ⚠️ anyone with the URL | ❌ obscurity only | — |

the lock is simply the repo's access — a private repo shared with the org's members/team.
the actual secret (the pem) never lives here; only **non-secret ids** do.

**launch inhabitant — the github-app registry:**
```
$org/keyrack-infra/                (private)
└── registry/
    └── github-apps.json           # [{ org, appId, installationId, slug }]
```
these three ids are not secrets — github exposes them to anyone who can view or auth as
the app — so a member-readable copy leaks no sensitive material.

**future trajectory (named, but NOT in this build scope):**
```
└── manifests/  $user.host.age     # age-encrypted host-manifest backups
```
the same repo later composes into shared keyrack infrastructure — manifest backups,
encrypted-key exchange (commit age ciphertext), and a **recipient authorization ledger**
built on the extant `schemaKeyrackKeyRecipient` (`daoKeyrackHostManifest/schema.ts:7-12`).
git history becomes the audit trail of who was authorized, when. that is the payoff of
the pattern — this behavior only lays its first stone.

## in scope (this behavior)

1. **`rhx keyrack infra init`** — findsert the `$org/keyrack-infra` private repo and
   scaffold `registry/github-apps.json`. idempotent; safe to re-run.
2. **admin auto-register** — when an admin sets a key via a github app, the app's
   `{ org, appId, installationId, slug }` is auto-written into the registry as a side
   effect of that setup (population happens without a separate chore).
3. **member fallback** — when a member tries to set a github-app key and is banned from
   the admin list-installations call, keyrack falls back to read the registry instead.
4. **infra-first + mandatory** — *everyone* (admin and member) reads `keyrack-infra`
   first. github-app installs **require** it: if the org has no `keyrack-infra`, keyrack
   fails loud with "please initialize your keyrack infra in this org first"
   (`rhx keyrack infra init`).

out of scope (future): manifest backup, encrypted-key exchange, recipient ledger.

## the outcome world

### day-in-the-life

**one-time, per org** — an admin (or a member with repo-create rights) runs:
```
$ rhx keyrack infra init --org ehmpathy

🏗️  keyrack infra init
   ├─ org: ehmpathy
   ├─ repo: ehmpathy/keyrack-infra (private) ✓ created
   └─ scaffolded registry/github-apps.json
```

**admin adds an app** — the app auto-registers:
```
$ rhx keyrack fill --owner ehmpath        # admin, EPHEMERAL_VIA_GITHUB_APP
   ├─ keyrack-infra: ehmpathy/keyrack-infra ✓
   ├─ app not yet registered → discovered via org install list
   ├─ registered ehmpathy-bot → keyrack-infra/registry/github-apps.json ✓
   ├─ private key path (.pem): ~/secrets/ehmpathy-bot.pem
   └─ ✓ filled
```

**member adds the same app later** — no admin, no 403:
```
$ rhx keyrack fill --owner ehmpath        # plain member
   ├─ keyrack-infra: ehmpathy/keyrack-infra ✓
   ├─ which github app?  (from registry)
   │  └─ 1. ehmpathy-bot (app 123456 · install 78901234)
   ├─ private key path (.pem): ~/secrets/ehmpathy-bot.pem
   └─ ✓ filled
```

if `keyrack-infra` is absent:
```
   └─ ✋ keyrack-infra not initialized for ehmpathy.
      run: rhx keyrack infra init --org ehmpathy
```

### before / after

| aspect | before | after |
|--------|--------|-------|
| discovery source | `/orgs/{org}/installations` (admin only) | `keyrack-infra` registry (member-readable) |
| member outcome | 403 mid-flow, dead end | reads registry, completes setup |
| admin outcome | discover each time | discover once → auto-registered for all |
| github-app install prerequisite | none | `keyrack-infra` must exist (mandatory) |
| durability | per-person, ephemeral | per-org shared source of truth |

### the "aha"

> "our org has one place that knows its keyrack apps; i init it once, and after that
> anyone — admin or member — just picks from the list."

## user experience

### usecases / goals
- **admin bootstraps** the org's keyrack-infra once (`infra init`).
- **admin registers** an app implicitly by adding its key (auto-write to registry).
- **member adds** an app-backed key by reading the registry — no admin rights.
- **everyone** gets a consistent, admin-free discovery path.

### contracts

**`rhx keyrack infra init`**
- input: `--owner`/org context.
- effect: findsert private repo `$org/keyrack-infra`; scaffold `registry/github-apps.json`
  (empty array) if absent.
- output: repo ref + scaffold status (turtle treestruct).
- idempotent: re-run is a no-op when already present.

**registry entry (non-secret)**
```json
{ "org": "ehmpathy", "appId": "123456",
  "installationId": "78901234", "slug": "ehmpathy-bot" }
```

**stored credential (unchanged)**
```json
{ "appId": "123456", "installationId": "78901234",
  "privateKey": "-----BEGIN RSA PRIVATE KEY-----...",
  "mech": "EPHEMERAL_VIA_GITHUB_APP" }
```

**mandatory-infra error (fail loud, caller-fixable)**
`ConstraintError`: "keyrack-infra not initialized for $org" + hint `rhx keyrack infra init`.

### discovery order (admin and member alike)
1. github-app set begins → derive org from the key slug.
2. `keyrack-infra` exists? no → fail loud ("init first"). yes → continue.
3. read `registry/github-apps.json`; app present? → use its ids.
4. app absent?
   - admin → discover via the org install list → **auto-register** → use.
   - member → banned from the admin list → stays on the registry; if still absent, fail
     loud "app not registered — ask an admin to add it".

## mental model

**to a friend:** "our org has a little private `keyrack-infra` repo. an admin set it up
once; now it holds the list of our github apps. keyrack reads that list, so i can wire up
a token without being an admin."

**analogy:** a **lobby directory**. the building manager posts it once; every resident
reads it. you don't knock on the manager's door each time — you read the board.

| they say | we say |
|----------|--------|
| "our shared keyrack repo" | `$org/keyrack-infra` |
| "the app list" | `registry/github-apps.json` |
| "the app's key file" | `privateKey` / pem |
| "set it up for the org" | `rhx keyrack infra init` |
| "someone who runs an app, not an org owner" | GitHub App manager |

## evaluation

### how well it solves the goal
fully, and durably. the admin dependency is removed at the root for members *and* the fix
becomes a reusable org asset rather than a one-off. auto-register means the registry
populates as a side effect of work admins already do — the cache is rarely empty.

### pros
- member path needs no admin and no org API call — just repo read.
- one shared source of truth per org; consistent for admins and members.
- non-secret ids only; pem stays in the vault; no secret ever enters the repo.
- forward-compatible: launches a pattern that later carries manifest backup + encrypted-key
  exchange + recipient ledger, on primitives keyrack already has.

### cons / tradeoffs
- **new prerequisite:** github-app installs now require `keyrack-infra` to exist. mitigated
  by a one-line init and a fail-loud hint.
- **repo bootstrap:** someone with org repo-create rights must run `infra init` once.
- **shared state to keep fresh:** stale registry entries possible (see edgecases).
- mandatory-infra is a behavior change for admins too (they must init first) — deliberate,
  per the wisher, for consistency.

### edgecases → pit of success
| edgecase | behavior |
|----------|----------|
| `keyrack-infra` absent | fail loud: "init your keyrack infra first" + command hint |
| app not in registry, actor is admin | discover via org list → auto-register → proceed |
| app not in registry, actor is member | fail loud: "app not registered — ask an admin" |
| `infra init` re-run | idempotent no-op |
| app uninstall+reinstall rotates installationId | mint fails loud on stale id → admin re-registers |
| registry entry stale/removed | mint fails loud on use → prune / re-register |
| ids are non-secret | safe to store in a member-readable repo; pem never written |
| member lacks repo read on keyrack-infra | fail loud: access needed — grant repo/team read |

## open questions & assumptions

### assumptions
1. whoever sets a github-app key holds its pem — true by construction (`deliverForGet`).
2. `$org/keyrack-infra` name convention is acceptable as the default home.
3. an admin (or repo-create-capable member) runs `infra init` once per org before members
   rely on it.
4. the three registry ids are non-secret — follows from what github exposes.

### questions — triaged [answered] / [research] / [wisher]

**[answered]:**
- which store? **private-repo file** — only store that is member-readable AND lockable;
  variables need admin, secrets are write-only, gists have no lock, custom properties cap
  at 75 chars + admin schema.
- which repo? **`$org/keyrack-infra`, fixed** — not configurable per org (wisher).
- who may run `infra init`? **anyone with repo-create rights** in the org — not
  admins-only (wisher).
- member + app-not-registered? **hard-block** → "ask an admin to register it"; no member
  app-jwt self-serve path in this scope (wisher).
- mandatory scope? **immediate** — `keyrack-infra` required for all github-app installs,
  no grace period (wisher).
- is the fix vault-specific? **no** — discovery lives in the mech adapter, shared by every
  vault that carries `EPHEMERAL_VIA_GITHUB_APP`.

**[research]:**
- exact `gh`/octokit calls to create a private repo + commit the registry file
  non-interactively (repo create, contents put, branch) — confirm at execution time.
- how `infra init` reconciles team/member read access (grant to a members team vs all
  members) — confirm the least-privilege default in the research phase.

**[wisher]:**
- none left — all product decisions made.

### external research — done (cited inline)
- `/orgs/{org}/installations` requires org owner ✔ (the bug)
- private-repo file is the only member-readable + lockable store ✔ (variables admin-gated;

  gists obscurity-only; custom properties 75-char + admin schema, no per-property lock)

## what is awkward?

- **mandatory prerequisite.** a required `keyrack-infra` before any github-app install is a
  real behavior change; the fail-loud "init first" softens it, but it is the seam where
  the pattern is most visible.
- **admin-only seed for new apps.** members can consume the registry but cannot register a
  brand-new app (they lack admin discovery); by decision, a member who needs an
  unregistered app is told to ask an admin — no member self-serve path in this scope.
- **repo lifecycle.** creation and access-scope of the repo, plus registry freshness, are
  new responsibilities — modest, but real shared-state upkeep the CLI did not have.
- **scope gravity.** the pattern invites the future features (backups, key exchange,
  ledger); the discipline is to launch the pattern with only the registry and leave the
  rest out of this build.

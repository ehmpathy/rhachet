# 1.vision — keyrack github-app setup without org admin

## the wish

> today, when someone tries to add a github app into keyrack for an org, it looks
> like they're required to have admin creds in order to enumerate the apps installed
> in that org. since this feature is expected to be used by members and not just
> admins, that breaks the experience for a lot of folks. how could we eliminate that
> need for admin creds in order to see the github apps installed? OR could we just
> grant members the ability to see that?

---

## the knot (why admin is required today)

the guided setup (`mechAdapterGithubApp.acquireForSet`) discovers apps through an
**org-owner-gated** endpoint:

- `mechAdapterGithubApp.ts:159-163` → `gh api /orgs/${org}/installations`
  returns `{ id, app_id, app_slug }` per install — **in one admin call it harvests
  both the `installationId` and the `app_id`.**

github gates that endpoint behind org owner:
> "The authenticated user must be an organization owner to use this endpoint."
> (oauth/PATs also need `admin:read`.)
> — https://docs.github.com/en/rest/orgs/orgs#list-app-installations-for-an-organization

so a plain member 403s mid-flow. that is the whole bug.

the stored credential the flow produces is three fields — `appId`, `installationId`,
`privateKey` (`mechAdapterGithubApp.ts:16-20`, `:220-226`) — consumed unchanged by
`deliverForGet` (`:240-265`). **none of that changes.** only *discovery* of `appId`
+ `installationId` must stop leaning on org admin.

### the bootstrap trap (verified with the wisher)

the obvious idea — "just authenticate as the app and call the app-scoped
`GET /app/installations` (jwt-gated, no admin)" — hits a circular dependency:

```
GET /app/installations  needs → app JWT
app JWT                 needs → appId
appId               today ←   the admin-gated org listing   ← circular
pem file            carries → NO appId (it is raw RSA key material only)
```

the pem does **not** contain the appId. so removing the admin call forces *some
other* source of `appId`. that fork defines the two candidate visions below.

---

## two candidate visions

### vision A — human supplies appId, app-jwt discovers the rest

flip the flow so the human hands over the two things they already hold as the app's
manager, and we discover everything else via the app's own jwt.

**inputs (human):** `appId` (printed on the app's settings/about page, same page as
the pem) + `pemPath`.
**derived (no admin):** app jwt via `createAppAuth({ appId, privateKey })` (already
imported, `:1`, `:252`) → discover the installationId. two jwt-gated calls, both
admin-free:
- **org known** → `GET /orgs/{org}/installation` (singular) fetches that org's install
  in one shot — no list, no pagination.
- **org unknown / browse** → `GET /app/installations` (paged) → each install's `id`
  (installationId), `app_slug`, `account.login` (org); pick the org (auto-select if one).

- ✅ zero new dependencies, self-contained, works for any member who manages the app.
- ✅ no shared state to maintain.
- ⚠️ the one genuinely new ask: the human types `appId` (was auto-harvested before).
- ⚠️ narrows UX from "browse every app in the org" to "register the specific app you
  manage" — which is arguably the true intent anyway.

`GET /app/installations` confirmed jwt-only, returns `id`/`app_id`/`app_slug`/`account.login`:
— https://docs.github.com/en/rest/apps/apps#list-installations-for-the-authenticated-app

**vision A0 — the MVP floor (manual entry, no api).** beneath A sits the zero-machinery
option: the human pastes `appId` + `installationId` (visible in the install URL
`.../settings/installations/{id}`) + pem. no admin, no registry, no api call. keyrack
already has the direct-paste idiom (`mechAdapterReplica` via `promptHiddenInput`). it
drops the pick-list and early validation A gives — offered as the least-effort slice the
wisher can choose.

### vision B — cache the discovery into a member-visible registry

keep discovery automatic for members by **persisting the non-secret ids once, from an
admin, into a github store that members can read.** the wisher's framing: "persist this
metadata in some member-visibility store, written whenever an admin installs one of
their own tokens; members fall back to that source."

keyrack itself has **no** shared store (confirmed). so the store must be github-native
and lockable to member-only reads. research findings:

| candidate | member can read? | lockable to member-only | shape fit |
|-----------|------------------|-------------------------|-----------|
| **file in a private repo** (`GET /repos/{o}/{r}/contents/{p}`) | ✅ | ✅ repo/team access | ✅ native json |
| org **custom properties** (`/orgs/{org}/properties/values`) | ✅ | ⚠️ = host repo visibility (no per-property lock) | ❌ string ≤75 chars, per-repo, keys are admin-managed schema |
| org **actions variable** | ❌ needs CI/CD-admin / Actions runtime | — | — |
| **secret gist** | ⚠️ anyone with the URL | ❌ no lock (obscurity only) | ✅ json |
| org/repo **secret** | ❌ write-only | — | — |

disqualified stores:
- org **actions variables** — readable only via `admin:org`/CI-admin role, or injected
  *inside* Actions runtime. keyrack's member flow is a **local CLI** under the member's
  `gh` token → cannot read them. same admin wall.
  — https://docs.github.com/en/rest/actions/variables
- **secret gists** — not access-controlled: "Secret gists aren't private. If you send
  the URL of a secret gist to a friend, they'll be able to see it." security-by-obscurity,
  not member-gating → fails "lockable to member-only."
  — https://docs.github.com/en/articles/creating-gists

viable stores:
- org **custom properties** — org members can read values (no admin). but a poor fit,
  verified: (a) **no per-property lock** — "the visibility of custom properties matches
  the visibility of the repository", so the lock is just the host repo's visibility (same
  mechanism as the private-repo file, only indirect); (b) **string values cap at 75
  chars**; (c) values attach **per-repo**, and property **keys are an org schema only
  admins define** — so a new app drags admin back in through the schema. net:
  member-readable but strictly worse than the private-repo file.
  — github docs: custom properties for repositories in your organization
- **private-repo file** (recommended) — a `[{ org, appId, installationId, slug }]` json
  blob in a private `keyrack-registry` (or the org's `.github`) repo, scoped to the
  members/team. "member-only" = repo access. admin writes on install; members read
  locally with their own token.

crucial safety note: the cached values (`appId`, `installationId`, `slug`) are **not
secrets** — only the pem is. exposing these ids to members leaks no sensitive material.

- ✅ preserves member auto-discovery / the "browse the org's apps" UX.
- ✅ members type no fields.
- ⚠️ requires an admin to **seed** each app once (write path stays admin-gated); a
  never-seeded app is invisible to members → "ask an admin to add it once" fallback.
- ⚠️ introduces shared state to create, write, read, and keep fresh (stale entries if
  an install is removed).

### how they compose

they are not exclusive. strongest posture: **B as the pit-of-success path, A as the
always-available fallback.**
- member runs setup → keyrack reads the registry → app pre-filled, no typing.
- registry miss (or no registry) → fall back to vision A (member types `appId` + pem,
  app-jwt discovers installationId). no dead end either way.

## the outcome world

### day-in-the-life (composed A+B)

**alice**, a plain member of `ehmpathy`, wants keyrack to rotate her app's tokens.

```
$ rhx keyrack fill --owner ehmpath

🔐 keyrack set ehmpathy.prod.github-app-token via EPHEMERAL_VIA_GITHUB_APP
   │
   ├─ which github app?              # ← read from member-visible registry (vision B)
   │  ├─ options
   │  │  ├─ 1. ehmpathy-bot   (app 123456 · install 78901234 · ehmpathy)
   │  │  └─ 2. ehmpathy-ci    (app 222333 · install 78905678 · ehmpathy)
   │  └─ choice: 1
   │     └─ ehmpathy-bot ✓
   │
   ├─ which github app secret?
   │  └─ private key path (.pem): ~/secrets/ehmpathy-bot.pem
   │
   └─ ✓ filled
```

registry miss? she drops into vision A — types the `appId`, points at the pem, and the
app-jwt lists the installs. either way: **no admin, no 403.**

### before / after

| aspect | before (today) | after (this wish) |
|--------|----------------|-------------------|
| discovery call | `GET /orgs/{org}/installations` | registry read (B) or `GET /app/installations` (A) |
| github gate | **org owner / `admin:read`** | member repo-read (B) or app jwt from the pem (A) |
| who can finish setup | org admins only | **any member who manages the app** |
| member failure mode | `403` mid-flow, dead end | pre-filled, or type appId — never blocked |

### the "aha"

> "i already have the pem — why was setup interrogating the *org*? ask the *app* where
> it lives, or read the list an admin already published for us."

## user experience

### usecases / goals
- **member registers an app-backed key** using only what they hold (pem, ± appId).
- **member picks the right install** across multiple orgs without admin.
- **member validates early** — wrong pem/appId fails at jwt/enumerate, before storage.
- **admin seeds once** (vision B) so teammates get a no-typing pit of success.

### contract (stored shape unchanged)
```json
{ "appId": "123456", "installationId": "78901234",
  "privateKey": "-----BEGIN RSA PRIVATE KEY-----...",
  "mech": "EPHEMERAL_VIA_GITHUB_APP" }
```
only the *discovery path* for `appId` + `installationId` changes; `deliverForGet`,
validation, and the json blob stay identical.

### timeline
1. keyrack offers apps from the registry (B) or asks for appId + pem (A)
2. mints app jwt / reads registry — no admin call
3. member picks org (auto-select if one)
4. keyrack stores the json blob; (B) admin path also writes the registry entry
5. done — installation tokens auto-mint on `get`

## mental model

**to a friend:** "i gave keyrack my app's key file, it already knew which app+org from
a list our admin published — picked it, done. no admin rights needed."

**analogy:** don't ask the *building manager* for the tenant roster (needs their
authority). either ask a *tenant which buildings they rent* (they hold the lease — the
pem → vision A), or read the *lobby directory the manager already posted* (vision B).

| they say | we say |
|----------|--------|
| "the app's key file" | `privateKey` / pem |
| "app id" | `appId` |
| "which org it's in" | installation `account.login` |
| "the install" | `installationId` |
| "the shared app list" | member-visible registry |
| "someone who runs the app but isn't an org owner" | **GitHub App manager** (github's native role — vision A's actor) |

## evaluation

- **solves the goal:** yes — admin dependency removed at the root for the *member read
  path*. A needs no shared state; B keeps auto-discovery but shifts the admin need to a
  one-time seed rather than every-member-every-time.
- **pros:** no new deps (A reuses `@octokit/auth-app`; B reuses `gh api`); stored
  contract untouched; earlier validation; composed A+B has no dead end.
- **cons:** A asks the human for `appId` (mild — same page as pem). B adds shared state
  (create/write/read/freshness) and still needs an admin to seed each app once.

### edgecases → pit of success
| edgecase | behavior |
|----------|----------|
| app installed in exactly one org | auto-select, echo it (matches today) |
| app in many orgs | numbered pick list by `account.login` |
| app installed in no org | fail loud: "app N not installed anywhere; install it first" |
| wrong pem for appId (A) | jwt/enumerate fails: "could not auth as app N; check pem + appId" |
| registry miss (B) | fall back to vision A automatically |
| stale registry entry (B) | app-jwt / install token mint fails loud on use → prune |
| ids are non-secret | safe to persist appId/installationId in a member-readable store |
| app installed across many orgs (A) | page through all of `/app/installations`, not just page one |
| pem handed over without the appId (A) | prompt hint "appId is on the app's settings page"; or let B/A0 supply it |
| app uninstall+reinstall rotates installationId | mint fails loud on the stale id → re-seed (B) / re-set (stored cred) |

## open questions & assumptions

### assumptions
1. whoever adds the app holds its pem — true by construction (`deliverForGet` needs it).
2. the appId is visible to whoever holds the pem (same settings page) — high confidence.
3. `@octokit/auth-app` mints an app jwt from `appId + privateKey` with no installationId
   — matches its documented `type: 'app'` auth; installationId only needed for the
   later `type: 'installation'` token mint (`:255`, `:259`).

### questions — triaged [answered] / [research] / [wisher]

**[answered] — closed now (see review r4.has-questioned-questions):**
- plan-B ("just grant members the ability to see that")? **rejected as a general fix.**
  custom org roles are Enterprise-only and no fine-grained permission grants
  org-installation read below owner; the **GitHub App manager** role governs app settings
  but not the owner-gated `/orgs/{org}/installations`. (per-org Enterprise custom role
  stays a niche option.)
- must the app-jwt list paginate? **yes.** can we skip the list? **yes** — singular
  `GET /orgs/{org}/installation` when the org is known.
- rotated installationId? **fail loud on mint → re-seed/re-set.**
- app jwt from appId+pem alone? **yes** (`type: 'app'`, README:88-97).
- vault-specific? **no** — fix lives in the mech adapter, helps every vault with the mech.

**[research] — defer to the research phase:**
- what share of "members not admins" truly manage apps vs merely consume tokens? drives
  whether this targets a large audience or a niche; needs usage signal, not code.

**[wisher] — only the wisher can decide:**
- **A vs B vs composed A+B** as the primary? (recommend composed: B pit-of-success, A
  fallback.)
- if **B**: **private-repo file** (recommended; shape-fits, member-only via repo access)
  vs **org custom properties** (native metadata, per-repo strings + one-time admin
  schema)? and which repo hosts it (`.github`? a dedicated `keyrack-registry`?)?
- if **B**: acceptable that the seed stays admin-gated (one admin, once per app)?
- **is the "member-only lock" a hard requirement?** the cached ids are non-secret (only
  the pem is secret); if the org accepts disclosure of its app inventory, a simpler store
  reopens. required, or a relaxable default?
- if **A**: acceptable to require the human to type `appId`, and to drop the incidental
  "browse all org apps" breadth?

### external research — done (cited inline above)
- `/orgs/{org}/installations` requires org owner ✔ (confirms the bug)
- `/app/installations` requires app jwt only, returns id/app_id/app_slug/account.login ✔
- org actions variables need admin/Actions-runtime to read ✔ (disqualifies)
- secret gists are not access-controlled (URL = access) ✔ (disqualifies)
- org custom properties + repo custom property values are member-readable ✔

## what is awkward?

- **vision A's appId prompt** — the one new human ask; mild but it's where the redesign
  shows. needs a crisp hint ("find app id on the app's settings page").
- **vision B's shared state** — a registry is a new thing to create, write, read, and
  keep fresh; stale entries can mislead until an install-token mint fails. it trades
  member-typing for maintenance.
- **losing "browse the org's apps"** — both visions narrow to app-centric registration.
  that breadth was incidental to the admin endpoint, not the real goal — but naming it
  so the wisher can veto.
- **snapshot / test churn** — reordering prompts and swapping the discovery source
  ripples through `mechAdapterGithubApp.test.ts` and setup snapshots. expected, flagged.

# vision: fix(keyrack) — load `age-encryption` via true dynamic `import()` so rhachet's own dist no longer statically `require()`s an esm-only package

## .what

remove **every eager static import of a pure-esm package** in rhachet's production code —
each of which tsc down-levels to a `require(...)` in the shipped dist — and replace each with
a **lazy, genuine runtime `import()`** via the extant `importEsmSafe` boundary. the result:
rhachet's compiled `dist/**` contains **no** eager static `require()` of a pure-esm package,
so a load of rhachet's dist under a commonjs `require()` (jest CJS testEnvironment, or a brain
package's compiled CJS that transitively `require('rhachet')`) no longer throws
`Must use import to load ES Module`.

**two such pure-esm (`type: module`) eager static imports exist in rhachet prod code — both
in the keyrack eval graph reached by `require('rhachet')`:**

1. `age-encryption@0.3.0` — `src/domain.operations/keyrack/adapters/ageRecipientCrypto.ts:1`
   (`import * as age from 'age-encryption'`). the issue #468 repro's traced culprit.
2. `@octokit/auth-app@8.2.0` — `src/domain.operations/keyrack/adapters/mechanisms/mechAdapterGithubApp.ts:1`
   (`import { createAppAuth } from '@octokit/auth-app'`). a **second landmine** the issue did
   NOT surface, because module eval throws on the *first* pure-esm require it hits
   (age-encryption), so the `require('rhachet')` already fails there and never reaches
   `@octokit`. **fix age-encryption alone and `@octokit/auth-app` throws next** — the same
   error, in the same graph (`mechAdapterGithubApp` is imported by `vaultAdapterOsSecure.ts:14`,
   the very module that also imports `ageRecipientCrypto`). so the fix MUST cover both, or the
   downstream stays broken.

**why exactly these two files suffice (the scope boundary).** the fix targets rhachet's OWN
top-level static imports — the `require(...)` calls tsc emits from rhachet's *source*. a
package's *transitive* pure-esm deps need NO separate treatment: once rhachet lazy-`import()`s
a top-level esm package, node loads that package's whole dependency graph through the same
esm-capable loader. e.g. `@octokit/auth-app` pulls `@octokit/request`, `universal-github-app-jwt`,
`universal-user-agent` (the `universal-` in rhachet's jest allow-list is exactly this transitive
tail) — all ride along through the one lazy `import()`. so the scope is precisely: rhachet's own
top-level static imports of `type: module` packages (the two above), not their transitive graphs.

no public contract change. no module-system change (rhachet stays commonjs). the keyrack
encrypt/decrypt/generate functions are already `async`, so the lazy load needs **no
signature change**.

this is the **inner-boundary** twin of the prior behavior `v2026_07_26.fix-brains-esm-dynamic-import`,
which fixed the **outer** boundary (rhachet's load of a brain *package* via `importEsmSafe`).
that fix let rhachet load an esm-only brain package's entry. but the brain package's own
compiled CJS then `require('rhachet')`, and rhachet's dist *itself* statically
`require('age-encryption')` — the inner boundary this wish closes.

## the outcome world

### day-in-the-life

**before** — a maintainer of a downstream repo (`rhachet-roles-ehmpathy` on `rhachet@1.47.0`)
writes an integration test that exercises real brain auto-discovery (`genContextBrain` with
no explicit `context.brain`). jest runs under a CJS `testEnvironment` (ts-jest / `@swc/jest`).
`getAvailableBrains` discovers `rhachet-brains-fireworksai`, loads its entry via
`importEsmSafe` (this part now works, thanks to v2026_07_26) — but the brain package's own
compiled CJS `dist/*.js` does a nested `require('rhachet')`, which evaluates rhachet's keyrack
modules, which hit the tsc-emitted `require('age-encryption')`. `age-encryption` publishes as
pure ESM, so node's CJS loader throws `Must use import to load ES Module: .../age-encryption/dist/index.js`.
`importPackageExports` catches it as `{ ok: false }`, `getAvailableBrains` degrades that
package to zero atoms/repls, and — because *every* brain package's peer chain pulls in
`age-encryption` via rhachet — **all** brains vanish. the only trace is a `console.warn`.
downstream, `genContextBrain` throws `BrainChoiceNotFoundError` with `available.atoms: []`.
the maintainer contorts jest config (`transformIgnorePatterns`, `moduleNameMapper` for
`@noble`/`@scure`, `NODE_OPTIONS=--experimental-vm-modules`) in chase of a fix — and it
*still* fails, because the boundary is inside rhachet's dist, not the test's transform pipeline.

**after** — the same install, the same test. rhachet's dist no longer holds a static
`require('age-encryption')` anywhere. the brain package's `require('rhachet')` evaluates the
keyrack modules cleanly (the `age` symbol is now an unresolved lazy reference, not a
load-time require). `age-encryption` is loaded only when a keyrack encrypt/decrypt actually
runs — via a real runtime `import()` that node handles as ESM. brain auto-discovery returns
real atoms/repls; `genContextBrain` works. the downstream repo deletes its jest-config
contortions. no keyrack behavior shifts — encrypt/decrypt/generate produce identical output.

2. **rhachet maintainers** — who may (as tidiness, out of scope here) later shed rhachet's

3. **future keyrack/brain authors** — who must not re-introduce a static require of a
   pure-esm dependency into shipped dist

### usecases fulfilled

- **run a downstream CJS jest test that auto-discovers brains** — `getAvailableBrains()`
  returns real atoms/repls instead of silently empty
- **`require('rhachet')` from any CJS context** — no ESM-require throw at load time
- **encrypt / decrypt / generate keyrack manifests** — unchanged behavior, now via a lazy
  esm-safe load of `age-encryption`

### contract inputs & outputs

the public contract is **unchanged**. the three adapter functions keep their signatures
(all already `async`):

```ts
encryptToRecipients(input: { plaintext: string; recipients: KeyrackKeyRecipient[] }): Promise<string>
decryptWithIdentity(input: { ciphertext: string | Uint8Array; identity: string }): Promise<string>
generateAgeKeyPair(): Promise<{ identity: string; recipient: string }>
```

what changes is **internal**: the module-scope `import * as age from 'age-encryption'` is
removed, and each function obtains `age` through the extant esm-safe boundary at call time.
proposed shape (mechanic owns the final HOW + whether to memoize):

```ts
// no top-level `import * as age from 'age-encryption'`
import { importEsmSafe } from '@src/infra/importEsmSafe/importEsmSafe';

// age-encryption is rhachet's OWN dependency, so a bare specifier resolves natively from
// rhachet's dist (unlike brain packages, which are caller-repo deps that need getOnePackageEntryUrl).
type AgeModule = typeof import('age-encryption');
const getAge = async (): Promise<AgeModule> =>
  importEsmSafe<AgeModule>({ specifier: 'age-encryption' });

export const generateAgeKeyPair = async () => {
  const age = await getAge();
  const identity = await age.generateIdentity();
  const recipient = await age.identityToRecipient(identity);
  return { identity, recipient };
};
```

a downstream repo's plain jest integration test:


no code change at any keyrack call site — the fix is entirely below the keyrack public surface.

## mental model

### how a user describes it to a friend

> "our tool secretly `require()`-d a pure-ESM crypto package deep in its code. any project
> that loaded our tool from a commonjs test just crashed on that require, and it looked like
> 'no brains found.' we made our tool load that package with a real dynamic `import()` only
> when it actually encrypts — so a plain load of our tool never trips the ESM boundary anymore."

### analogies / metaphors

- **the landmine you carry into someone's house** — a static `require('age-encryption')` in
  shipped dist is a mine every consumer steps on the moment they `require('rhachet')`. a move
  to a lazy `import()` defuses it: it only "arms" when keyrack crypto actually runs, in a
  loader (native `import()`) that can handle it.
- **the smuggler's envelope (reused)** — same trick the outer fix used: the specifier rides
  inside `new Function('s','return import(s)')` so tsc can't rewrite it to `require()`; node
  opens the envelope at runtime and does the real ESM load.

| "the workaround" | lazy dynamic-import indirection (`importEsmSafe`) |
| "the crypto lib" | `age-encryption` (keyrack manifest encryption) |
| "load rhachet" | a CJS `require('rhachet')` that transitively evaluates keyrack modules |
| "the outer fix vs this one" | brain *package* load boundary (v2026_07_26) vs rhachet's *own* age-encryption require (this wish) |

## evaluation

### how well it solves the goals

the issue offers three candidate fixes; this vision takes **candidate #2 — eliminate the
ESM/CJS boundary risk at the source** (rhachet core avoids a hard static require of a
pure-esm package), which is the most durable and needs no downstream action beyond a pin bump:

- **candidate #1** (make brain packages load age-encryption via dynamic import) — rejected:
  it does not fix rhachet's own dist, and would demand edits across every brain package
  (out of this repo's control). the real static require is rhachet's, not the brain's.
- **candidate #2** (rhachet core avoids the hard static require) — **chosen**: one file, one
  boundary, fixes it for every downstream at once.
- **candidate #3** (ship a canonical jest-config snippet) — rejected as the primary fix:
  documentation that asks every consumer to contort config is exactly the pain the wish wants
  gone. (a doc note may still accompany the fix as courtesy, but is not the solution.)

within candidate #2, two lower-level **approaches** were also weighed and rejected:

- **whole-keyrack lazy-load** (restructure so keyrack adapters are never eagerly evaluated by
  `require('rhachet')`) — rejected: HIGH blast radius across many vault/mechanism modules + their
  tests, and it does not generalize (a future eager esm import elsewhere still breaks). the
  targeted lazy-`import()` fixes the actual tsc-`require()` sites directly.
- **dep swap** (replace age-encryption / @octokit/auth-app with dual-published CJS equivalents) —
  rejected: re-validates safety-critical crypto + github-app auth against new libs; far larger and
  riskier than a load-moment change that keeps the exact same libraries and byte-identical output.
  the issue lists this only as a fallback ("if a CJS-compatible alternative exists").

### pros

- **minimal blast radius** — two prod files (`ageRecipientCrypto.ts`, `mechAdapterGithubApp.ts`);
  no signature change, no config churn, no ripple across the 200+ other files.
- **fixes it at the source, once** — every downstream consumer benefits from a single pin
  bump; no per-consumer jest contortion.
- **reuses the extant, proven boundary** — `importEsmSafe` already exists, is tested by a
  real-node acceptance clamp, and centralizes the one `new Function` smell.
- **strict superset** — keyrack crypto behavior is byte-identical; only the *load moment* of
  `age-encryption` moves from module-eval to first-crypto-call.
- **future-proof** — the same boundary absorbs any future pure-esm keyrack dependency.

### cons

- **lazy-load cost** — the first keyrack crypto call pays one `import()`. negligible (all
  three functions are already `async` and already `await` age operations); a memoized module
  reference removes even the repeat cost.
- **can't be proven by a `.ts` read** — like the outer fix, the defect lives only in the
  tsc-built dist; the source looks fine before and after. the regression clamp **must** run
  against the built `dist/` in a real-node CJS `require()` context (a `.realnode.acceptance.test.ts`),
  not a `@swc/jest` `.integration.test.ts` (which may keep `import()` native and mask the bug).
- **flatten shape dependency** — the adapter reads `age.armor.encode` / `age.armor.decode`
  (a nested namespace). `importEsmSafe` → `asFlatModuleExports` preserves *top-level* named
  exports (the `armor` object among them) but does not recurse; this is fine (armor stays a
  top-level export object), but the clamp must assert a real encrypt→decrypt roundtrip to
  confirm the loaded shape, not just that the module loaded.

### edge cases & pit-of-success

| # | edge case | how the fix keeps users safe |
|---|-----------|------------------------------|
| e1 | downstream CJS jest requires rhachet (via brain discovery) | loads clean — no static age-encryption require in dist |
| e2 | rhachet loaded as ESM (native `import`) | `import('age-encryption')` works either way; unchanged |
| e3 | keyrack encrypt/decrypt actually runs | lazy `import()` resolves age-encryption; roundtrip identical |
| e4 | `age.armor` nested-namespace access | `armor` is a top-level export preserved by `asFlatModuleExports`; roundtrip clamp confirms |
| e5 | ssh-recipient path (age CLI shell-out) | untouched — that path never imports the npm lib |
| e6 | age-encryption genuinely absent/broken | `importEsmSafe` rejects → keyrack op throws a real error (crypto is required, so fail loud — not silently skipped) |
| e7 | repeated crypto calls | memoized module reference → one `import()` total (mechanic's call) |
| e8 | brain package with esm-only dep chain (anthropic) | outer fix (v2026_07_26) still handles its entry; this fix clears the inner age-encryption require |

  via `importEsmSafe`. this wish is the **inner** boundary (rhachet's own age-encryption require)
  that fix did not reach.
- **the acceptance clamp pattern** — `blackbox/sdk/importEsmSafe.realnode.acceptance.test.ts` +
  `blackbox/.test/infra/spawnProbeBetween` + a `probe.*.cjs`: the established way to prove an
  ESM/CJS load contract against **built dist** in a **real-node child**. the new regression clamp
  should follow this shape (a probe that `require()`s the built keyrack dist — ideally the
  full `require('rhachet')` entry, or at least the `vaultAdapterOsSecure` graph that pulls in
  BOTH `ageRecipientCrypto` and `mechAdapterGithubApp` — under CJS and asserts it does NOT throw
  a pure-esm require error for EITHER age-encryption OR @octokit/auth-app — RED on the
  static-import version, GREEN on the lazy-import fix — plus an encrypt→decrypt roundtrip to
  confirm the age-encryption loaded shape). the RED is provably reproducible at
  `vaultAdapterOsSecure`: its dist eagerly evaluates both adapter modules, because
  `vaultAdapterOsSecure.ts:10-14` statically imports `ageRecipientCrypto` (decrypt/encrypt) AND
  `mechAdapterGithubApp` at the top level — so a CJS `require()` of its built `.js` fires both
  static `require(...)`s (throws on the first, age-encryption). that makes `vaultAdapterOsSecure`
  the precise, targeted RED/GREEN clamp site, tighter than the whole entry.
- **rhachet's own config contortion** — `jest.integration.config.ts:23-37` (moduleNameMapper for
  `@noble`/`@scure`, `transformIgnorePatterns` allow-lists `age-encryption`): concrete evidence
  of the pain the wish wants to spare downstream repos.

---

## what is awkward?

- **the clamp can't live in a normal jest test** — same discomfort as v2026_07_26: the defect
  exists only in the tsc-built dist under CJS `require()`, and the `@swc/jest` test path may not
  reproduce it. the honest witness is a real-node acceptance probe against `dist/`. a reviewer who
  expects a `.integration.test.ts` to "prove the fix" will be surprised; the `.realnode.acceptance`
  home must be defended.
- **`importEsmSafe` reuses `new Function`** — the same `eval`-adjacent smell rides along. it is
  already contained in one named, documented leaf, so this wish adds no new smell — but it does
  extend that leaf's reach from brain-package loads into keyrack crypto.
- **lazy load moves a failure's moment** — today, a broken/absent age-encryption fails at rhachet
  module-eval (loud, early). after the fix, it fails at first keyrack crypto call (still loud, but
  later). this is *desirable* for the discovery path (no crypto → no load → no failure), but a
  reviewer may note the shifted failure point. crypto is required where it's called, so it still
  fails loud (e6) — not hidden.
- **the two nested boundaries are easy to conflate** — this wish and v2026_07_26 both say "load an
  esm module via dynamic import," but they fix *different* boundaries (rhachet→brain-package vs
  rhachet→age-encryption). the vision names both explicitly so the blueprint doesn't "re-fix" the
  outer boundary or assume this is a dup.
- **rhachet's own jest config stays contorted** — the fix spares *downstream* repos, but rhachet's
  own `jest.integration.config.ts` age-encryption workarounds remain (q3, best-guessed out of
  scope). to leave them in place while the fix targets only the exported boundary feels slightly
  unfinished — but to bundle that cleanup risks rhachet's own suite and belongs in a separate wish.

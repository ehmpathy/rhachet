# 1.vision — a machine-wide key cut at a reach can be unlocked

## .what this vision is

the wish names a defect that is already isolated to one function and one line. so this vision is
**not** a search for what to build — it is a testdrive of the *contract* that repair must honor,
run against the real code at HEAD, plus **four items the wish did not yet know**:

1. the defect has a **second, quieter half** — the bulk (`--key`-less) path, which does not fail
   loud but files the daemon grant under a **doubled** address, so `get` can never find it. traced
   end to end at source; its bounds, and two sub-claims that did **not** survive scrutiny, are
   stated with it
2. the **same blindness sits in a peer expander**, `getAllSudoSlugsForKeyAsk`
3. ⚠️ **the unit fixture generator cannot express the test acceptance 1 needs** — it normalizes
   away the exact difference under test, so the wish's suggested test would go green while it
   proves the opposite of its claim. two ways through; a fulcrum, flagged with a best-guess
4. the reference patch's `?? address` fallback is **dead code** — two loader gates make it
   unreachable, which reverses the "keep the shim" instinct

all four are cited at source below.

## .the outcome world

### day-in-the-life, after

casey runs one machine. she holds three ahction accounts, and each has its own anthropic
credential. she cut one key per account, machine-wide, exactly as the reach feature says to:

```sh
rhx keyrack set --owner ehmpath --org @all --env prep --key BRAINS_AUTH \
  --reach casey@ahction.com --vault os.secure --mech PERMANENT_VIA_REPLICA
rhx keyrack set --owner ehmpath --org @all --env prep --key BRAINS_AUTH \
  --reach casey@ahbode.com   --vault os.secure --mech PERMANENT_VIA_REPLICA
```

she opens a repo — any repo, or none at all — and unlocks the account she is working for:

```
$ rhx keyrack unlock --owner ehmpath --env prep --key BRAINS_AUTH --reach casey@ahction.com

🔓 keyrack unlock
   └─ @all.prep.BRAINS_AUTH
      ├─ env: prep
      ├─ org: @all
      ├─ reach: casey@ahction.com
      ├─ vault: os.secure
      └─ expires in: 540m
```

⚠️ **the tree shape above is verified, not invented.** the row set and order —
`env`, `org`, `reach`, `vault`, `expires in` — is copied from the snapped unlock tree at
`blackbox/cli/__snapshots__/keyrack.session.acceptance.test.ts.snap:55-61`. only the slug, env,
reach, and vault values are this vision's own. **this repair adds no row and reorders none.**

`get` then answers with the value, and it is **that account's** value:

```
$ rhx keyrack get --owner ehmpath --env prep --key BRAINS_AUTH --reach casey@ahction.com --value
sk-ant-…-ahction
```

(the bare-`get` tree renders `status: granted 🔑` —
`keyrack.session.acceptance.test.ts.snap:75`.)

she switches accounts by switching the flag. no rename, no suffix, no second key name.

### the before/after contrast

| | before | after |
|---|---|---|
| `set --org @all --reach` | ✅ succeeds, echoes the address | ✅ unchanged |
| `list --json` | ✅ shows the record, `slug` + `reach` apart | ✅ unchanged |
| `get --reach` (bare) | ✅ finds it, says `status: locked 🔒` | ✅ finds it, says `status: granted 🔑` |
| **`unlock --reach`** | ❌ `key not found in manifest: BRAINS_AUTH` | ✅ unlocks, echoes the reach |
| `get --reach --unlock` | ❌ fails (delegates into `unlock`) | ✅ works |
| `unlock` (bulk, no `--key`) | ⚠️ **exits 0, grant filed under an ADDRESS** | ✅ filed under the slug |
| `unlock --reach` at an **uncut** reach | ✋ blocked | ✋ **still** blocked |
| `unlock` with no `--reach` | 🔓 works | 🔓 byte-identical |

### the "aha"

> **the map keys are addresses. the caller wants slugs. the expander was handing back keys.**

`hostManifest.hosts` is documented as *"map of key **address** to host configuration"*
(`src/domain.objects/keyrack/KeyrackHostManifest.ts:37`). every entry **also carries its own
`slug` field** (`src/domain.objects/keyrack/KeyrackKeyHost.ts:17`), and
`assertKeyrackHostAddressed` is in place precisely because the reach is recorded twice — once in
the address, once in the field — *"because different halves of the system read different ones"*
(`term=address._.choice._.md:67`).

`getAllMachineWideSlugsForEnv` is one of those halves, and it reads the wrong one. it takes
`Object.keys(...)` — the **addresses** — and hands them to a caller that wants **slugs** and will
re-apply the reach itself.

the moment that clicks, the repair writes itself and the shape of the *whole* defect (both halves,
plus the sibling) comes into view.

## .user experience

### the usecases

| # | goal | who | contract |
|---|------|-----|----------|
| u1 | unlock one machine-wide credential for one account | operator with N accounts on one box | `unlock --env E --key K --reach R` |
| u2 | read the value back | same, or an automated command | `get --env E --key K --reach R --value` |
| u3 | unlock every machine-wide credential for an env | bootstrap / grove startup | `unlock --env E` |
| u4 | unlock machine-wide with **no repo cloned yet** | bootstrap-to-clone | `unlock --env E --key K --reach R`, no `keyrack.yml` |
| u5 | be **refused** for an account never cut | anyone, by accident | `unlock --env E --key K --reach OTHER` → ✋ |
| u6 | keep working with no reach at all | every extant caller | `unlock --env E --key K` |

### the contract, in and out

the surface's **shape** does not change: no new flag, no new field, no new row, no reordered tree.

⚠️ but "the surface does not change" would be too strong, and an earlier draft said exactly that.
for a rack that holds a reach-cut `@all` key, a bulk `unlock` **prints a different value** — the
slug `@all.E.K` where it used to print the address `@all.E.K@casey@ahction.com`. that is the
second-half repair made visible, and it is the same nuance acceptance 2 needs (below). the change
is entirely interior to one expander:

```
getAllMachineWideSlugsForEnv({ env, keyAsk, hostManifest }) -> string[]
                                                               └─ SLUGS (not addresses)
```

the return contract is already **fixed by the sole caller**, and this is the fact that bounds every
candidate repair (`src/domain.operations/keyrack/session/unlockKeyrackKeys.ts:222-226`):

```ts
for (const slug of slugsForEnv) {
  const hostFound = getOneKeyrackHostForSlugAtReach({
    hosts: hostManifest.hosts,
    slug,
    reach: input.reach,      // ← the reach is applied HERE, per slug
  });
```

so the expander must **never** carry a reach in its output. it names *which slugs are held for this
env*; the caller decides *at which reach*. that division is already correct — only the read of the
map was wrong.

### the timeline (u1, end to end)

```
t0  set --org @all --env prep --key K --reach casey@ahction.com
    └─ manifest gains entry at address `@all.prep.K@casey@ahction.com`
       with fields { slug: '@all.prep.K', reach: { exid: 'casey@ahction.com' } }

t1  unlock --env prep --key K --reach casey@ahction.com
    ├─ getAllMachineWideSlugsForEnv → ['@all.prep.K']            ← the repair
    ├─ getOneKeyrackHostForSlugAtReach({ slug, reach })
    │  └─ probes '@all.prep.K@casey@ahction.com' → HIT
    ├─ vault read → secret
    └─ daemon grant filed at the address, TTL 540m

t2  get --env prep --key K --reach casey@ahction.com --value
    └─ daemon hit → the ahction value

t3  unlock --env prep --key K --reach casey@nowhere.com
    └─ probes '@all.prep.K@casey@nowhere.com' → MISS
       └─ ✋ ConstraintError: "a reach is never derived — a key must be cut
             at the reach you ask for"                    (unlockKeyrackKeys.ts:232-240)
```

**t3 is the load-bearing step.** the guard that produces it is already in place and already works;
the repair must leave it standing. this is acceptance 3, and it is why a "fall back to the reachless
slug" repair — the tempting one — is forbidden: it would make t3 return casey's *other* account's
live credential.

## .mental model

### how an operator would describe it to a friend

> "keyrack files a key under an *address* — the key's name plus, if you cut it for a specific
> account, that account's email. `set` files it right, `list` shows it right, `get` finds it. but
> `unlock` was looking up the name and comparing it to the whole address, so it never matched. now
> it reads the name off the record instead of guessing it from the label."

### the analogy

a rack of labelled boxes. the label is the **address**: `BRAINS_AUTH@casey@ahction.com`. inside
each box is a card that says which **key** it holds: `BRAINS_AUTH`.

`unlock` was asked for `BRAINS_AUTH` and it read the **labels**, then checked which label *equals*
`BRAINS_AUTH`. none does — every reach box's label is longer. so it reported the rack empty.

the repair: read the **cards**, not the labels. and if two boxes hold cards that say the same
thing, that is one key at two reaches — count it once, and let the caller say which box.

the temptation this rules out: *"just chop the label at the `@`."* you cannot. an account name is
an email, and an email holds an `@`. the term brief states it flat
(`term=address._.choice._.md:39`): *"a reach exid may legally hold `@`, so a split back is not
well-defined"* — and `asKeyrackKeySlugAtReach` is documented **construct-only**
(`asKeyrackKeySlugAtReach.ts:12-13`).

### terms — theirs vs ours

| operator says | we say | note |
|---|---|---|
| "the account" / "the email" | **reach** (its `exid`) | |
| "the key name" | **key ask**, or the **slug**'s last segment | |
| "where it's filed" | **address** | never `slug`, never `map key` |
| "for the whole machine" | **machine-wide**, `org=@all` | |
| "make me a key for that account" | **cut** a key at a reach | never "scope one down" |

## .evaluation

### how well does it serve the goals

| goal | verdict |
|---|---|
| u1 `unlock --reach` works | ✅ direct — the exact-equality miss is the only blocker |
| u2 `get --reach` round-trips | ✅ follows, since `get` is already healthy and only wanted a populated daemon |
| u3 bulk unlock | ✅ **improved beyond the wish** — see the second half, below |
| u4 no-manifest bootstrap | ✅ same expander, same repair (`unlockKeyrackKeys.ts:146`) |
| u5 uncut reach refused | ✅ untouched — the guard lives one layer down and never sees the change |
| u6 reachless unchanged | ✅ a reachless entry has `slug === address`, so its behavior is bit-identical |

### the pros

- **one file, one function.** the surface, the caller, and the guard are all untouched
- **additive by construction.** for every entry that predates reach, `slug === address`, so the
  new read returns exactly what the old read returned
- **the contract is the expander's own.** ⚠️ an earlier draft argued placement with *"a repair in
  `unlockKeyrackKeys` would fix only the loud half"* — **that is false**, and it is struck. a
  one-line map at the call site (`slugsForEnv.map(a => hosts[a]?.slug ?? a)`) would fix both halves
  just as well, since both flow through the same loop. **both halves are one wrong read, so any
  single correct repair fixes both.** the real argument for the expander is narrower and honest:
  the function *declares* `string[]` **slugs** and its sole consumer *uses* them as slugs, so an
  address in its return is **the expander's own contract breach**. to patch it at the call site
  would leave a function that lies about what it returns, ready for the next caller
- **no new invariant.** the reach-carry rule stays where it already lives
  (`getAllKeyrackProbeAddresses`), guarded by its own test

### the cons

- the function's **name** stays `getAll…Slugs…` while its body must now be explicit that the map
  is keyed by addresses. that is a comment burden, not a defect — but it is the third place this
  distinction has had to be re-learned (see "awkward")
- **dedupe changes an observable count.** N reaches of one slug collapse to one slug. that is what
  the caller wants (it de-dupes by `effectiveSlug` at `unlockKeyrackKeys.ts:252` anyway), but it
  means a rack with 3 reaches of one key now yields 1 slug where it yielded 3 addresses. any
  future caller that counted the return would see a change
- the sibling expander stays blind (below)

### edge cases, and how the contract keeps a user in the pit of success

| # | edge | pit-of-success mechanism |
|---|---|---|
| e1 | reachless key, reachless ask | `slug === address` ⇒ byte-identical. this is the whole compat story |
| e2 | reach exid holds an `@` (an email — the normal case) | never parse an address. read the `slug` field |
| e3 | one slug, N reaches | dedupe to one slug; the caller re-applies the asked reach per slug. ⚠️ **dedupe is not load-bearing for correctness** — see the note below |
| e4 | ask a reach the key was **not** cut for | `getOneKeyrackHostForSlugAtReach` misses ⇒ loud `ConstraintError` naming the reach + the `set` command to cut it |
| e5 | bulk `unlock --env E` over a rack holding reach keys | with the repair, one slug per key; the grant files under the slug, so `get` can find it |
| e6 | ~~bulk `unlock --env E --reach R` where only *some* keys are cut at R~~ | ⛔ **struck — the case cannot occur.** `assertKeyrackReachRequiresKey` (`unlockKeyrackKeys.ts:70-76`) refuses a reach with no `--key`. a reach always rides a one-key ask, so "bulk + reach" is not a state the contract admits |
| e7 | a manifest entry with an absent or untruthful `slug` | ⚠️ **unreachable — the loader rejects it first** (see a1 below). the entry never reaches the expander, so a `?? address` fallback here would be dead code |
| e8 | full-slug ask (`--key @all.prep.K`) | the early-return at lines 23-28 answers first. ⚠️ it indexes `hosts[keyAsk]` — a **slug** into an **address**-keyed map, so a full-slug ask for a reach-cut key misses that shortcut and falls through to the prefix path. harmless *given* the repair; a latent trap without it |
| e9 | a slug that is legitimately `@all.…` and also carries `@` in its reach | injective by construction: a slug never holds `@` except its lead `@all`, and no code reverses the composite (`term=address`) |

#### ⚠️ what dedupe is actually worth — the requirement, questioned

the wish's reference patch dedupes, and the vision first justified it as "what the caller wants".
challenged, that justification is weaker than it reads — and the true one is narrower:

- **it is NOT needed for correctness.** the caller already de-dupes by `effectiveSlug`
  (`unlockKeyrackKeys.ts:252`), so a repeated slug costs a redundant loop pass and nothing more
- **it IS worth one real thing:** for a slug held at N reaches with **no** reachless entry, a
  reachless bulk `unlock` misses on every pass, and each miss pushes its own row into `keysOmitted`
  (`:244`). without dedupe the human sees the same key reported `absent` N times

so dedupe earns its place as an **output-quality** measure, not a correctness one. that is a
nitpick-grade justification, and it should be recorded as such rather than inflated — if a reviewer
wants it dropped, the repair still satisfies all four acceptances. **best-guess: keep it**, since it
costs one `new Set(...)` and prevents a confusing repeated row.

### 🔦 the second half of the defect — not in the wish, found at source

the wish proved the `--key` path fails loud. the **bulk** path (`unlock --env E`, no `--key`) does
not fail at all — it succeeds *wrongly*.

with `keyAsk: null`, `getAllMachineWideSlugsForEnv` returns
`Object.keys(hosts).filter(startsWith(prefix))` **unfiltered** — i.e. raw **addresses**, returned
under a name and a contract that say slugs. downstream, each is used as a slug:

| line | use | what it gets |
|---|---|---|
| `unlockKeyrackKeys.ts:224` | `getOneKeyrackHostForSlugAtReach({ slug })` | an address, then `@reach` appended to it |
| `:248,255` | `effectiveSlug` → the identifier the **grant is filed under** | an address |
| `:260` | `repoManifest?.keys[slug]` | an address indexed into a slug-keyed map |
| `:409-414` | `new KeyrackKeyGrant({ slug: effectiveSlug, …reach from hostConfig })` | an address as the grant's `slug`, **with the correct reach beside it** |
| via `:224` → `getAllKeyrackProbeAddresses` → `getEnvAllFallbackSlug` → `getKeySlugWithEnv:14-16` | the env=all second shot, computed by a **`.split('.')`** | an address split on `.` — a term-contract breach, though see the caveat below |

### the one live consequence, traced end to end

**`unlock --env prep`** (no `--key`) on a rack with a reach-cut `@all` key **exits 0** — and files
a grant that `get` can never find:

```
getAllMachineWideSlugsForEnv → '@all.prep.K@casey@ahction.com'      (an ADDRESS, as a slug)
  └─ getOneKeyrackHostForSlugAtReach({ slug: <address>, reach: undefined })
     └─ shot 1 probes '<address>' → HIT, so effectiveSlug = the ADDRESS
        └─ KeyrackKeyGrant({ slug: <address>, reach: hostConfig.reach })      (:409-414)
           └─ daemon files at asKeyrackKeySlugAtReach({ slug: <address>, reach })
              = '@all.prep.K@casey@ahction.com@casey@ahction.com'   ⛔ DOUBLE-APPENDED

later:  get --key K --reach casey@ahction.com
        └─ probes '@all.prep.K@casey@ahction.com' → MISS → reports locked
```

the grant's **`reach` field is correct** (`:412-414` deliberately reads `hostConfig.reach`, the
field, not the address) — which is precisely why the doubled address results: the reach is appended
a second time onto a slug that already carried it. **bulk unlock is silently write-only.**

### ⚠️ two claims an earlier draft made that do NOT survive

honesty about the bound of this discovery matters more than its size:

1. ❌ **"`unlock --env E --reach R` without `--key` misbehaves"** — **impossible.**
   `assertKeyrackReachRequiresKey` at `unlockKeyrackKeys.ts:70-76` refuses a reach with no `--key`
   before any expansion runs. *a reach always rides a keyed ask.* that also makes edge case `e6`
   and open question `q3` moot, and both are struck below
2. ⬇️ **the `getKeySlugWithEnv` split has no live consequence here** — `getAllKeyrackProbeAddresses`
   builds its list eagerly, so the twin *is* computed from an address, but shot 1 always hits first
   (the address came from the map keys). so it is a real **term-contract** breach — an address fed
   to a parser the `term=address` brief says must never receive one — with **no** observable
   misbehavior today. it is a latent trap, not a live defect, and is recorded as such

**why this matters to the vision, not just to the fix:** it settles the placement question. a
repair that sits in `unlockKeyrackKeys` fixes the loud half and leaves this one. a repair that
reads the `slug` field *inside the expander* fixes both, because both halves are the same wrong
read. that is a property of the outcome, not of any particular patch — and it is checkable.

⚠️ this half is **unproven live**. it is read from source, and the read is laid out above so a
reviewer can walk it. an execution-stage probe should confirm it before it is claimed as fact.

### 🔦 the unit fixture generator cannot express the test acceptance 1 needs

the wish suggests a regression fixture shaped like this:

```ts
hosts: {
  '@all.prep.MY_KEY@casey@ahction.com': {
    slug: '@all.prep.MY_KEY',
    reach: { exid: 'casey@ahction.com' },

}
```

the extant unit test builds its manifest with `genMockKeyrackHostManifest`
(`src/.test/assets/genMockKeyrackHostManifest.ts`, used at
`getAllMachineWideSlugsForEnv.test.ts:14`). **that generator cannot produce the shape above**, for
two separate reasons, both at source:

| # | what it does | line | consequence |
|---|---|---|---|
| 1 | sets `slug` from the **map key**, never from the caller's value | `:20-22` — `for (const [slug, partialHost] of …)` then `new KeyrackKeyHost({ slug, … })` | a passed `slug: '@all.prep.MY_KEY'` is **silently ignored**; the entry gets `slug` = the full address |
| 2 | never forwards `partialHost.reach` | `:21-32` — the constructor call lists `slug, mech, vault, exid, env, org, meta, maxDuration, createdAt, updatedAt` and **no `reach`** | a passed `reach` is **silently dropped**, even though `Partial<KeyrackKeyHost>` accepts it |

so an author who writes the wish's fixture verbatim gets an entry with
`slug === address` and **no reach** — which is *precisely the reachless shape the defect already
handles*. the test would go red today for the wrong reason, then go green on a repair that reads
`host.slug`, because `host.slug` **is** the address in that fixture. **it would pass while it
proves the opposite of its claim.**

⚠️ this is the single most consequential item found in groundwork. acceptance 1 demands a test that

its current door**.

⚠️ **correction — this is a fulcrum, not an unavoidable scope item.** an earlier draft of this
section called the generator repair "unavoidable". it is not. there are two ways through, and the
choice is a judgment call:

| option | what it costs | what it buys |
|---|---|---|
| **A — repair the generator**: honor an explicitly passed `slug`, forward `reach` | touches a shared test asset other suites use; must stay additive (map-key default preserved) | every future reach unit test can express the case; honors `rule.require.shared-test-fixtures` |
| **B — construct the fixture inline** in this one test, bypassing the generator | narrower blast radius; zero shared-asset risk | leaves the trap armed for the next author, and duplicates fixture shape inline against `rule.require.shared-test-fixtures` |

> **best-guess: A.** the change is additive and small (`slug: partialHost.slug ?? mapKey`, plus
> `reach` forwarded), and the generator's blindness is a latent trap for *every* future reach unit
> test — the same "next feature has to remember this a third time" hazard the wish itself worries
> about. **clean rework:** if a reviewer prefers B, the inline fixture is a local edit to one test
> with no ripple.

either way, the property that binds is unchanged and comes from acceptance 1 itself:

> **the unit fixture must hold an entry whose map key is an ADDRESS and whose `slug` field is the
> BARE SLUG** — because "the map key differs from the entry's `slug`" is the exact state under test.

## .what is awkward

### 1. the name says `slug`, the map says `address` — for the third time

`term=address` was written *because* this exact confusion bit a published contract
(`keyrack del --json` emitted an address under the field name `slug`, 2026-08-04). here it bites
again, one layer in. the term brief's own tell applies word for word:

> *"the local variable is named `slug` while it holds an **address**"*

⚠️ and "third place" was an undercount. a search for readers of `hostManifest.hosts`' **keys**
turns up at least four sites where an address is bound to a slug-shaped name:

| site | the code | read |
|---|---|---|
| `getAllMachineWideSlugsForEnv.ts:32` | `Object.keys(hosts).filter(...)` → `machineWideSlugs` | ⛔ **the defect under repair** |
| `getAllSudoSlugsForKeyAsk.ts:32` | `candidateSlugs.filter(slug => hosts[slug])` | ⚠️ the same blindness, flagged as `q1` |
| `invokeKeyrack.ts:1335` | `const hostSlugs = Object.keys(hostManifest.hosts)` → `findSlugByEnvAndKeyName` | ⚠️ same shape, in the sudo org-discovery path — within `q1`'s family |
| `invokeKeyrack.ts:1900-1901` | `asSortedHostSlugs({ hosts })` | ✅ a **display** path; `term=address:98-100` sanctions a human render of the whole address, so this one is benign |

a repair fixes one instance. it does not stop the fifth. the honest read: **a `Record<string, …>`
keyed by address is indistinguishable at the type level from one keyed by slug**, so the compiler
can never help. an address branded type (`KeyrackKeyAddress`) would make the map's key type say
what it is — and would have turned this defect into a compile error at every site above. that is a
real piece of design leverage and it is **out of scope here**; noted for the council.

### 2. ⚠️ the `?? address` fallback is not a compat shim — it is dead code

this was the biggest correction of the self-review, and it **changes a design call**, so it is
recorded in full.

the wish's reference patch reads `host?.slug ?? address`, framed as a graceful fallback "for an
entry that predates the `slug` field". that framing does not survive a read of the loader. **two
independent gates stand between the on-disk file and this expander:**

| gate | where | what it rejects |
|---|---|---|
| the zod schema | `daoKeyrackHostManifest/schema.ts:49` — `slug: z.string()` | any entry with an absent (or non-string) `slug` |
| the address assertion | `assertKeyrackHostAddressed.ts:35-52`, run per entry at `daoKeyrackHostManifest/index.ts:136` | any entry whose `asKeyrackKeySlugAtReach({ slug, reach })` ≠ its map key |

the second gate is the decisive one. it does not merely check that `slug` is **present** — it
**rebuilds the address from `slug` + `reach` and demands exact equality**, throwing a
`MalfunctionError` otherwise. so by the time any entry reaches `getAllMachineWideSlugsForEnv`, its
`slug` is not just present, it is **provably the one that generated its address**.

⚠️ the awkward part, stated plainly: **`?? address` can never fire.** if `slug` were absent, the
schema threw. if `slug` were wrong, the assertion threw. a legacy no-`slug` manifest does not
degrade gracefully here — it fails to load *at all*, one layer up.

so the fallback is not cheap insurance; it is an unreachable branch that **reads as** a real
possibility and would mislead the next reader into thinking the expander must tolerate an untruthful
`slug`. `rule.forbid.failhide` cuts the same way — a fallback that papers over a state two gates
already refuse is exactly the shape that hides a genuine corruption.

> **best-guess (a fulcrum, flagged not blocked, per `rule.always.defer-fulcrums-to-last`): drop the
> `?? address`.** read `host.slug` directly. the loader is already the loud place, and it is already
> loud. clean rework — if a reviewer wants the belt-and-braces, restoring `??` is a one-token edit
> with no ripple.

⚠️ one honest caveat that keeps this a *judgment* rather than a certainty: it assumes every path
that populates `hostManifest.hosts` goes through `daoKeyrackHostManifest`. that holds for the cli,
and the blackbox fixtures are read through the same dao — but an in-memory manifest constructed
directly in a test (`genMockKeyrackHostManifest`) bypasses both gates. **that is a test-only path**,
and the right answer there is for the fixture to be well-formed, never for prod code to carry a
branch to absorb a malformed one.

### 3. dedupe is correct here and load-bearing elsewhere

collapsing N addresses to 1 slug is right for *this* caller. it is right **because** the caller
re-applies the reach. an expander that dedupes is therefore only safe next to a caller that
reaches. if a second caller ever wants "every key held, per reach", it must **not** reuse this
function — and no part of the type says so. the `.why` comment has to carry that weight.

### 4. the wish's scope bound and the sibling pull against each other

*"do not touch `set` / `get` / `del`"* is clean. but `getAllSudoSlugsForKeyAsk` is neither in scope
nor clearly out — it is `unlock`'s other expander with the identical blindness. leaving it is
correct by the wish's letter and slightly uncomfortable by its spirit ("so the next feature does
not have to remember this a third time"). **best-guess: leave it, file it, say so.** clean rework —
the same one-line read, whenever it is picked up.

### 5. proving red before green needs care

acceptance 1 says the test must go **red** on current code. the unit test does that cleanly (the
fixture gains an address-keyed entry; the expander yields `[]` today). the *journey* test is the
one to watch: it runs the real cli through the real daemon, so a stale daemon or a leaked grant
from a sibling test could mask the red. the peer file already handles this
(`killKeyrackDaemonForTests()` in `beforeAll`, `envIsolated(repo.path)`) — that pattern is not
optional here, it is what makes the red trustworthy.

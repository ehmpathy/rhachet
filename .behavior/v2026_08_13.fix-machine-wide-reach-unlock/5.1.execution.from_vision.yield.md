**you ratified acceptance 5 as:** after a bulk `unlock --env prep`, a `get --key K --reach R --value`

**the counter-reading I had to go and disprove.** my first justification was *"a bulk ask names no

**your stated harm is answered either way:** the credential IS readable (`[case1][t1]`,

## ⭐ t17 — the wisher chose (B), and it shipped

the one open escalation is CLOSED. put the choice to the wisher on 2026-08-15; the verdict was
**(B) build reach enumeration**, not (A) re-ratify the refusal. so the restatement is withdrawn and
the acceptance table's original text now describes what ships, word for word.

### what changed

a new transformer, `getAllKeyrackReachesForSlug` — lists every reach the rack holds for one slug,
read off each entry's `slug` FIELD (never the address key), probed at the same two shots the lookup
uses (the slug, then its `env=all` twin), deduped by exid and sorted.

`unlockKeyrackKeys` then expands each slug into **targets** rather than one lookup:

```ts
input.reach
  ? [{ slug, reach: input.reach }]                       // a NAMED reach — byte for byte as before
  : [{ slug }, ...reachesHeld.map((reach) => ({ slug, reach }))]   // a reachless ask ENUMERATES
```

three consequences, each deliberate:

1. **the vault is threaded the TARGET's reach, not the ask's.** this was the first defect in my own
   repair: with `input.reach` still passed through, both enumerated targets read the REACHLESS
   value, found none, and rendered `status: lost 👻`. the enumeration ran and the vault did not
2. **dedupe moved from slug to ADDRESS.** a slug key was correct while one slug yielded one target;
   under enumeration it would unlock the first reach and silently evict every peer — the exact
   eviction the reach identity axis exists to remove
3. **the reachless target is KEPT and its `absent` row pruned.** it is what walks the reachless twin
   and the `env=all` fallback, so to drop it would regress a path this wish never touched. its
   omission is pruned only when the rack proves the slug is held at some reach — so a human is
   never told one key is both held and unheld

### ⚠️ the regression it caused, caught by the full sweep and fixed at cause

the first cut of (B) **broke `keyrack.reach.envvar` `[case1][t2]`** — a REACHLESS unlock over a rack
that holds a reach-cut `os.envvar` key went from exit 0 to exit 2, with a spurious `errored 💥` row.

cause: `os.envvar` is `UNADDRESSABLE` — its storage address carries no reach — so the enumerated
target hit the adapter's own refusal. that refusal is correct for a reach a HUMAN named and wrong
for one the enumeration guessed.

route that a fix for a review item was itself the next defect.

of `reachesHeld` — which is already narrowed to `vault-addressable`, so an unaddressable-vault row

disclosure inverts with it, so the named reach never also discloses itself.

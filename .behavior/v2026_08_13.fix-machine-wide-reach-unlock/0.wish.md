# wish: a machine-wide key cut at a reach can be unlocked

## .what

**a credential cut with `--org @all` AND `--reach <exid>` can be `unlock`ed.**

today it can be `set`, `get`, and `del`ed — and never `unlock`ed. since `unlock` is the gate that
populates the daemon, `get` can only ever answer `locked`. so the whole read path is dead and the
credential is **write-only**.

## .why

this is blocker-class for the pair the reach feature most obviously invites. a machine-wide
account credential is *exactly* what a reach (an email) names — so `@all` + `--reach` is not an
exotic combination, it is the combination the feature was built for.

the failure shape is the expensive one:

- **`set` succeeds** and reports the address back, so the operator believes the key is filed
- **`list` proves the record exists**, with `slug` and `reach.exid` stored as separate fields —
  exactly the documented model
- **`get` correctly reports `locked 🔒`**, which reads as *"you have not unlocked it yet"*
- **`unlock` then reports `key not found in manifest`**, which reads as *"you never filed it"*

three instruments say the key is there and the fourth says it is not. an operator who trusts the
fourth re-files it, and re-files it again, and the credential is never once readable.

### ⚠️ the trap that made this hard to isolate

`keyrack get --reach --unlock` **also** fails, because `--unlock` delegates into the same path. so
a first read of the evidence indicts `get` too, and that misdiagnosis was made once already.

test **bare** `get --reach` to see that `get` itself is healthy. the defect is isolated to
`unlock`.

## .acceptance

1. **`unlock --reach` succeeds on a key cut at that reach** — proven by a test that goes RED on
   the current code, never by assertion alone
2. **a reachless `unlock` is bit-identical to today** — this must not regress the common path
3. **`unlock --reach` at a reach the key was NOT cut for still BLOCKS.** this is the one that
   matters most: a reach-unlock must never fall back to the reachless credential, or it hands
   back a live credential for the wrong account
4. **a journey-level test round-trips a value** — `set --org @all --reach` → `unlock --reach` →
   `get --reach`. a unit test alone would not have caught that a whole credential class is
   write-only

## .scope

**in scope:** the machine-wide (`@all`) slug expansion that `unlock` reads, and the coverage gap
beneath it.

**out of scope, and these bind:**

- **do not change the address format.** `term=address._.choice._.md` states the rule this turns
  on: *"a reach exid may legally hold `@`, so a split back is not well-defined"*. any repair that
  parses an address on `@` is wrong, however well it passes today's fixtures
- **do not touch `set` / `get` / `del`.** all three are verified healthy; they are the peers to
  learn the shape from, never files to edit
- **do not weaken the wrong-reach guard.** acceptance 3 exists because the obvious fix shape
  (fall back to the reachless slug) would silently hand over another account's credential

## .what was already verified — live, against `rhachet@1.46.0`

**this is a defect isolated by a four-command probe, not a report of a symptom.**

| command | `--reach` | result |
|---|---|---|
| `keyrack set` | ✅ works | files `@all.prep.KEY@casey@ahction.com`, `slug` + `reach.exid` as separate fields |
| `keyrack del` | ✅ works | removes by address |
| `keyrack get` | ✅ works | finds the host, correctly reports `status: locked 🔒` |
| `keyrack unlock` | ❌ **fails** | `blocked: key not found in manifest: KEY` |

### the black-box repro

```sh
# 1. cut a key at a reach, machine-wide
echo "PROBE-VALUE" | rhx keyrack set --owner $OWNER --org @all --env prep \
  --key BRAINS_AUTH__PROBE --reach casey@ahction.com \
  --vault os.secure --mech PERMANENT_VIA_REPLICA
# => ✅ @all.prep.BRAINS_AUTH__PROBE@casey@ahction.com

# 2. confirm the manifest holds it, slug + reach as separate fields
rhx keyrack list --owner $OWNER --json | jq '.[] | select(.reach)'
# => { "slug": "@all.prep.BRAINS_AUTH__PROBE", "reach": { "exid": "casey@ahction.com" }, ... }

# 3. unlock it — FAILS
rhx keyrack unlock --owner $OWNER --env prep \
  --key BRAINS_AUTH__PROBE --reach casey@ahction.com
# => ✋ blocked: key not found in manifest: BRAINS_AUTH__PROBE
```

step 3 fails even though step 2 proves the record exists.

### the root cause, read at source

`src/domain.operations/keyrack/getAllMachineWideSlugsForEnv.ts:31-40`

```ts
const prefix = `@all.${input.env}.`;
const machineWideSlugs = Object.keys(input.hostManifest.hosts).filter(
  (slug) => slug.startsWith(prefix),
);

if (input.keyAsk)
  return machineWideSlugs.filter(
    (slug) => slug === `@all.${input.env}.${input.keyAsk}`,   // ⛔ here
  );
```

`hostManifest.hosts` is keyed by **address**. for a key cut at a reach that address is
`@all.prep.KEY@casey@ahction.com`, and the filter tests **exact equality** against the
**reachless** slug `@all.prep.KEY`. it can never match. the function accepts no `reach` parameter
at all — the `@all` expansion is reach-blind by construction.

**the tell:** the local variable is named `slug` while it holds an **address**. the reach feature
made the map keys addresses, and this pre-reach call site kept to the old assumption.

**sole caller:** `session/unlockKeyrackKeys.ts` — lines 146 and 182. that is why only `unlock` is
affected.

### the caller already re-applies the reach

```ts
for (const slug of slugsForEnv) {
  const hostFound = getOneKeyrackHostForSlugAtReach({
    hosts: hostManifest.hosts,
    slug,
    reach: input.reach,       // ← reach applied HERE, per slug
  });
```

that is a **fact about the call site**, and it bounds the repair: whatever shape you choose, the
expansion's return contract is already consumed as **slugs**.

### the coverage gap

`getAllMachineWideSlugsForEnv`'s extant 6 tests all use **reachless** fixtures. that is why an
address-keyed entry was never exercised.

### the neighbor, already filed

`rhachet#440` is the **same shape, a different cause** — an absent `org=@all` fallback in the

worth a look, and **yours to judge**: whether the `@all` path wants one shared, reach-aware slug

### the reference patch — evidence, not a spec

```ts
// ⚠️ the map KEYS are ADDRESSES — `slug@reach` for a key cut at a reach — so read the `slug`
//    FIELD each entry records rather than the key itself. an address must NEVER be split back
//    on `@` (a reach exid may legally hold one, and an email is the intended form), and an
//    exact-equality test against a reachless slug can never match an address that carries a
//    reach. dedupe: N reaches of one slug are N addresses but ONE slug, and the caller
//    re-applies the reach per slug via getOneKeyrackHostForSlugAtReach.
const prefix = `@all.${input.env}.`;
const machineWideSlugs = [
  ...new Set(
    Object.entries(input.hostManifest.hosts).map(
      ([address, host]) => host?.slug ?? address,
    ),
  ),
].filter((slug) => slug.startsWith(prefix));
```

its claimed properties, each checkable:

- **additive** — a reachless entry has `slug === address`, so its behavior is bit-identical
- **dedupes** — N reaches of one slug collapse to one slug, which is what the caller wants
- **no `@` parse** — honors the address rule
- **falls back to the key** (`?? address`) for an entry that predates the `slug` field

### the four checks it passed, live

| # | check | before | after |
|---|---|---|---|
| 1 | `unlock --reach` on a cut key | ✋ `key not found in manifest` | 🔓 unlocked, echoes the reach |
| 2 | `get --reach --value` round-trip | (unreachable — locked) | returns the stored value |
| 3 | reachless `unlock` (regression) | 🔓 works | 🔓 works — unchanged |
| 4 | `unlock --reach` at a reach the key was NOT cut for | ✋ blocked | ✋ **still** blocked |

**check 4 is the one that matters.** the guard in `getOneKeyrackHostForSlugAtReach` still fires
exactly as designed, so no wrong-account credential leaks.

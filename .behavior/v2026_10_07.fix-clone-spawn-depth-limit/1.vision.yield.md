# 1.vision — one level of clones, and no more

## .the rule, in one table

the limit is on **depth**, never on a role. a clone's depth is how many clones sit above it.

**a tty is depth 0; no tty is depth 1.** a clone a human starts in its own terminal or tmux pane
is top-level. any spawn that runs with no tty is at least one level down.

| who | depth | may spawn? | e.g. |
|---|---|---|---|
| a top-level clone — one a human starts **at a tty**, via `rhx enroll` or a raw `claude`, whatever env the pane inherited | 0 | ✅ **yes**; what it spawns is depth 1 | its guard enrolls reviewers on `route.stone.set --as arrived`; it runs `rhx review` |
| a clone or brain spawned with **no tty** by a depth-0 caller — or by a caller with no depth var at all | 1 | ❌ no — refused loudly, the limit named | a guard's reviewer that tries `rhx enroll` or `rhx review` with a repl brain; a review brain; a cron job's clone |
| a brain a human's own `rhx review` spawns | 1 | ❌ no | a review brain is a spawn, never top-level (Q8) |

the bound has three named edges, each one level loose, never a fresh budget:
- **a tty promotes.** a cron job a human runs at a terminal hands its tty stdin to an `rhx enroll`
  it shells out to, so that clone is minted at depth 0. so would a brain CLI whose shell tool
  allocates a pty (Q10).
- **a smudged var** on a depth-1 reviewer reads as a depth-0 caller, so it still spawns one depth-1
  child.
- **atoms pass.** "`rhx review` is refused at depth 1" holds for a **repl** brain. a review brain that is
  an atom (e.g. a single-turn api model) runs, because an atom spawns no clone (Q2).

⚠️ a top-level clone that is refused is the **worst** failure here — it stalls every guarded stone.
the depth-1 refusal must never reach a depth-0 caller. the rule follows depth and the tty, not
the word "reviewer": a reviewer a human enrolls at a terminal is top-level.

a raw `claude` needs no special mark for the common case. its tool shell has no tty and no depth
var, so its guard's `rhx enroll` and its own `rhx review` read a depth-0 caller and mint depth 1 —
exactly as for a clone `rhx enroll` started. the `claude` itself is the depth-0 clone above them.

## .the reported block — what it is, and what it is not

the wisher's launch terminal carries no `RHACHET_CLONE_DEPTH` (Q7a, measured: empty). so the
inherited-pane path below is not the wisher's daily path; it is a real edge the fix still covers.

**the inherited pane.** a terminal or tmux pane split from inside a clone inherits that clone's
`RHACHET_CLONE_DEPTH`. today a clone a human enrolls there is born at depth 1, and every reviewer
its guard enrolls is depth 2 and refused.

**reproduced 2026-10-07:** `RHACHET_CLONE_DEPTH=1 rhx enroll claude --roles -driver -p '…'` is
refused: `✋ ConstraintError: clone enroll depth budget spent`, `depthRequested: 2`, `depthMax: 1`.

**the fix for it:**
- `rhx enroll` with a tty on stdin mints depth 0, whatever var the pane inherited.
- a raw `claude` opened in such a pane passes that var on to its tool shell, which has no tty. so
  the session starts with `RHACHET_CLONE_DEPTH=0` set for that `claude` (contract below), and its
  guard's reviewers are depth 1, not 2.

**measured 2026-10-07, this worktree:** the depth-0 driver `@:mechanic` arrived `1.vision`. its
guard ran `rhx enroll claude … -p '…'` (`enroll-vision-intent`), which spawned `@:a249df40` at
depth 1, and the reviewer returned a verdict. the depth-0 → depth-1 spawn is allowed today.

**what the no-tty rule changes for the over-spawn.** today a raw `claude`'s guard reviewers, a
cron job's clones, and a human's review brains read no var and mint depth 0, so each may spawn
once more. under this rule each is depth 1 and refused.

## .the outcome world

### a day in the life

a human opens `claude` or runs `rhx enroll claude` in a terminal pane. that top-level clone drives
a route. at each guarded stone its guard enrolls reviewers, and the clone itself may run
`rhx review` — all allowed. each depth-1 reviewer reads, judges, and returns. when its rubric
tempts it to fetch a second opinion — `rhx enroll`, or `rhx review` with a repl brain — rhachet refuses in one loud
line that names the limit, and it answers from its own read. reviews finish in one pass. the
fleet's token spend per stone is bounded by the number of reviewers the guard asked for.

### before / after

| | before | after |
|---|---|---|
| a depth-1 clone runs `rhx enroll` | refused ✅ | refused, same message as below |
| a depth-1 clone runs `rhx review` (repl) | 🔴 spawns one brain per rubric, each reads as the depth-1 clone itself (depth 1, its serial) | refused: `clone spawn depth limit reached` |
| a depth-0 clone runs `rhx review` | ✅ allowed; brain spawned with no marker change (depth 0 + the parent's serial) | ✅ allowed; brain carries depth 1, no parent serial — its own spawn refused |
| a depth-0 clone's guard enrolls a reviewer | ✅ allowed, reviewer at depth 1 | ✅ allowed, unchanged |
| a raw `claude`'s guard enrolls a reviewer | 🔴 reviewer at depth 0 — may spawn once more | ✅ reviewer at depth 1 — its own spawn refused |
| a human's own `rhx review` at a terminal | 🔴 brain at depth 0 — may spawn once more | ✅ brain at depth 1 |
| a cron job (no tty, no var) enrolls a clone | 🔴 clone at depth 0 | ✅ clone at depth 1 |
| a human enrolls at a plain terminal | depth 0 | depth 0 — unchanged |
| a human enrolls, or opens `claude`, in a pane that inherited a clone's env | 🔴 depth 1 — its reviewers are refused, its stones stall | ✅ depth 0 — the tty marks it as top-level |

### the aha

the budget was already there — `CLONE_SPAWN_DEPTH_MAX = 1` — but it guarded one door
(`rhx enroll`) while review skills walk through another (`rhachet/brains` repl). and an absent
depth var read as "top-level" on both doors, so any spawn no clone had marked started a fresh
budget. the fix:
- puts the same budget on the second door
- reads top-level from the one signal a brain cannot fake: a tty
- counts every no-tty spawn as one level down

**one level below every top-level clone, at every door** — bar the three named edges under the
rule table.

## .the contract we propose

- **one read of depth:** `asCloneSpawnDepth({ env, isTty, door })` returns the depth the new
  clone or brain carries:
  - `door: 'enroll'` with a tty on stdin → `0` — a top-level clone, whatever var is set
  - else → caller depth + 1, where the caller depth is `0` when the var is absent or unparseable
    (or when the caller has a tty), else the var
  - so every no-tty spawn is at least depth 1. the repl door never mints 0: a review brain is
    always a spawn (Q8). no `CLAUDECODE` read. `CLONE_SPAWN_DEPTH_MAX = 1` unchanged.
- **a raw `claude` session starts at depth 0:** the repo brain dir's settings
  (`.agent/.actors/actor.via.slug=.default/brain/.claude/settings.json`, read by an unenrolled
  `claude` as `<repo>/.claude`) set `RHACHET_CLONE_DEPTH=0` for the session. an enrolled clone
  reads its actor's brain dir instead, so its own marker is untouched. this matters only in an
  inherited pane — in a clean pane the absent var already reads as a depth-0 caller. whether a
  settings `env` overrides an inherited var is Q11. if it does not, a SessionStart hook that
  writes `CLAUDE_ENV_FILE` is the fallback.
- **two doors, one check:** `rhx enroll` (extant, `invokeEnroll.ts:269-275`) and
  `asBrainReplWithContextBound` (new) both refuse when child depth > max, with one message:
  ```
  ✋ ConstraintError: clone spawn depth limit reached
    depth: 1 (the limit to spawn is depth 0)
    hint:  a clone at depth 1 may not spawn another — ask the clone that spawned you, or a human
  ```
- **`--async`:** the depth is decided in the foreground, where the tty is, and handed to the
  detached host, which has no tty and must not re-read.
- **propagation at the repl door:** for the duration of a repl `ask`/`act`, `process.env` carries
  the child depth and no parent serial/socket. it is restored after the last concurrent call
  returns.
  - 🔴 **the caller's depth is read once, before the scope opens, and held by the scope.** a call
    that starts while a peer's scope is open checks against that held caller depth, never against
    the env the peer set. otherwise a depth-0 caller's second parallel rubric would read depth 1,
    mint depth 2, and be refused (the worst failure).
  - enroll paths already propagate (`genBrainCliPtyClone`, `genBrainCliPlainClone`,
    `genCloneEnrollDetached`).
  - the depth half is what the wish requires. the serial/socket drop is a safe ride-along (F5),
    not a wish requirement, and the council may strike it.
- **atoms pass:** one api request, no process, no tools.

## .evaluation

- **goals:**
  - depth 0 spawns ✅
  - depth 1 refused loud, names the limit ✅
  - marker survives enroll (extant) and repl (new) ✅
  - a clone a human starts at a tty is top-level, whatever env it inherited ✅ for `rhx enroll` ·
    🟡 for a raw `claude` in an inherited pane, gated on Q11 and on a repo whose brain dir is
    rendered (F7)
  - a raw `claude`'s reviewers, a cron job's clones, and a human's review brains are depth 1 ✅
  - tests prove cases 1–6 and case 7 [t0]–[t2] ✅; case 7 [t3]–[t4], the raw `claude` reset, is
    deferred with F7 (see F8) and has no test in this pr 🟡
- **pros:** one seam per door; no supplier change; the extant enroll check and tests stay; no
  launcher or flag for a human to learn.
- **cons:**
  - a process-wide env mutation for the length of a repl call (F2)
  - a no-tty caller can never start a top-level clone. a cron job that wants one must run under a
    tty
- **edge cases + pit of success:**
  - concurrent repl calls → refcounted scope, restored only after the last
  - unparseable depth var → reads as a depth-0 caller, so its child is depth 1. a smudge never
    locks out a tty enroll, and never mints a fresh budget
  - slug reuse at depth 1 → still refused first (dimensions file explains why kept)
  - `--async` → depth decided in the foreground, handed to the host

## .open questions & assumptions

- **assumption:** every repl a role package calls goes through `genContextBrain`. a role that
  imports a supplier directly bypasses the seam (named as impossible in the inventory).
- **assumption:** a brain's tool shell has no tty on stdin, so a brain-run `rhx enroll` never
  mints depth 0. measured 2026-10-07: `test -t 0` exits 1 from the `Bash` tool of `@:mechanic`, an
  enrolled clone that itself runs in a pty (F6).
- **Q9 [answered — wisher, S1]** — a raw `claude` is a top-level clone, the same as a top-level
  `rhx enroll`. its spawns have no tty, so they are depth 1.
- **Q8 [answered — wisher, S1]** — a human's own `rhx review` mints its brain at depth 1. a review
  brain is a spawn, never top-level.
- **Q7 [answered — wisher, S1]** — (a) the wisher's launch terminal carries no depth var, so the
  inherited pane is an edge, not the wisher's path. (b) a `!rhx enroll` typed into a clone's
  session has no tty, so it is that clone's spawn: depth 1. this follows the rule; no flag.
- **Q1 [research — gated on Q11]** — a `claude` opened in an inherited pane is no longer refused
  *if* its session starts at depth 0 (contract). that rests on Q11, and on the repo brain dir's
  settings rendered in the repo where the `claude` opens. a repo without that render gets no
  reset, so its raw `claude` in an inherited pane is still refused — the refusal hint must say so,
  and execution must test it.
- **Q11 [research]** — does a `claude` settings `env` key override a var the process already
  inherited? measure in execution before the contract relies on it. if not, the SessionStart
  `CLAUDE_ENV_FILE` hook is the fallback.
- **Q10 [research]** — does any other brain CLI's shell tool hand its commands a tty? if so, its
  depth-1 clone's `rhx enroll` would mint depth 0. measure each installed supplier in execution,
  as `test -t 0` was measured for claude. the same edge: a cron job a human runs at a terminal
  passes its tty stdin to an `rhx enroll` it shells out to — accepted, as a human at the keyboard.
- **Q2 [answered]** — should atoms count? no: an atom is one api request with no process and no
  tools, so it cannot spawn (logic). F3 holds it for the council.
- **Q3 [answered]** — does the review skill go through `genContextBrain`? yes:
  `review.js:349`, `genReviewBrainSupply.js:63`, and `choice` is wrapped at
  `genContextBrain.ts:246-252` (code).
- **Q4 [answered]** — does `act` need the same check as `ask`? yes: `act` grants `Bash`
  (`genBrainRepl.js:67`), so it is the more able spawner (code).
- **Q5 [research]** — do the other installed suppliers (e.g. `rhachet-brains-openai`) read
  `process.env` within the call, as anthropic does? to check in execution, before the seam
  relies on it; if one snapshots env early, the scope misses it (F2).
- **Q6 [research]** — how does bhrain's `rhx review` render a `ConstraintError` thrown from
  `choice.ask` — loud with exit 2, or wrapped as a malfunction? the refusal must reach the
  reviewer legibly; check in execution with a depth-1 env.

## .what is awkward

- **a mutation of `process.env` in a library seam** — it works because suppliers read the env,
  but it is a side effect a reader would not expect from a context binder. F2 names the cleaner
  supplier-contract alternative and why it is deferred.
- **a tty as a depth signal** — it marks a human at a keyboard, not a human's intent. a human who
  pipes into `rhx enroll` loses the tty and is counted one level down. the wisher set this trade
  (S1): no tty is depth 1.
- **a cron job cannot start a top-level clone** — by design. a scheduled driver that must run
  reviews has to start under a tty (e.g. a tmux pane).
- **the spawn vocab** — the depth read and its limit bound both doors, so they are named for a
  spawn, never an enroll: `asCloneSpawnDepth` and `CLONE_SPAWN_DEPTH_MAX`.
- **two impossibles stay open** — direct supplier imports and claude `Task` subagents spawn
  outside rhachet's seams. the fix bounds rhachet clones, not every brain a brain can start.
  the bound: rhachet's two spawn seams are `invokeEnroll` and `asBrainReplWithContextBound`
  (`rhx grepsafe --pattern 'asBrainReplWithContextBound\(' --path src`: every repl that
  `genContextBrain` hands out is wrapped there, at `genContextBrain.ts:251,273,282`); a role
  package that imports a supplier's repl directly, or a `Task` subagent claude runs in-process,
  calls neither.

# 1.vision — keyrack mints the beaver github-app token on a grove off ec2

## .the claim

a box with no aws identity mints `EHMPATH_BEAVER_GITHUB_TOKEN` the way an ec2 box does: it holds the
github-app **blob** behind a door it can open, and mints an installation token at unlock. on ec2 the
door is the instance role over aws.params. off ec2 the door is the box's own ssh key over os.secure.

most of that world already exists. `os.secure` already supports `EPHEMERAL_VIA_GITHUB_APP`
(`vaultAdapterOsSecure.ts:97-99`), and its `get` hands the decrypted blob to the same
`mechAdapterGithubApp.deliverForGet` that aws.params uses. the box already needs an ssh identity to
decrypt its host manifest, so os.secure adds no new prerequisite. what is absent:

1. a way to **file** the blob onto a box that has no tty, no gh login, and no aws identity
2. an error that points a stuck box at that door

## .the outcome world

### before

- the blob lives in aws.params alone. a hetzner grove's rung 4 unlocks the key and gets
  `✋ ConstraintError: aws.params found no AWS identity`. its hint says "use an ec2 box" or "unlock an
  AWS_PROFILE" — two roads that do not exist off ec2
- the guided `keyrack set --vault os.secure --mech EPHEMERAL_VIA_GITHUB_APP` exists, but it asks gh
  to discover the app (the box has no github token — the very thing it lacks) and prompts a tty for a
  pem path (the provision is unattended, and a pem file on the box is one more secret on disk)
- so crews moved to hetzner run without a beaver github token: no private clones, no gh login

### after

- the commander runs **one command**, once per box: the blob streams from aws.params, over ssh, into
  `rhx keyrack set … --vault os.secure --mech EPHEMERAL_VIA_GITHUB_APP --source @stdin` on the box.
  the mech checks its shape; keyrack encrypts it to the box's recipients, verifies the roundtrip, and
  never shows it (`case=4`)
- every rung after that runs `get --unlock` and gets a fresh `ghs_` (`case=1`). after the 55m expiry
  the daemon drops it and the next unlock mints anew
- an ec2 grove is untouched: same host manifest, same aws.params read, same snapshots (`case=2`)
- a box that missed the command fails with a hint that names the command (`case=3`)

### the aha

the box never holds a token. it holds the *ability to mint one*, behind its own key. that is the
same contract an ec2 grove already keeps — only the lock changed.

## .the contract we testdrive

| surface | change | kind |
|---|---|---|
| `keyrack set --source @stdin` (sketch name) | read the source credential from stdin in place of the mech's guided setup; check it with `mech.validate({ source })` before any write; never echo it | new flag |
| os.secure + github-app unlock/get | none — it already mints from a filed blob | none |
| aws.params `found no AWS identity` hint | add the off-ec2 cure for a github-app key | hint text — beyond the wish's letter; earned by `case=3`: today's hint names two roads that do not exist off ec2 |
| host manifest | none — it is per box, so an off-ec2 box maps the key to os.secure and an ec2 box keeps aws.params | none |

the clamp: one cli acceptance suite, one box shape (no aws identity, a real ssh identity in a temp home).
it runs at the acceptance grain because jest's vm cannot load the aws sdk's lazy credential
providers, so the no-identity refusal is observable only from the built cli; the green half is also
held at the vault's integration grain:

- red — blob only in aws.params → unlock yields no grant, with the no-identity refusal
- green — the same blob piped into os.secure via `--source @stdin` → unlock reaches the mint with the
  decrypted blob (see q5 for how far a ci test can follow the mint)

## .mental model

- to a friend: *"the hetzner box gets its own locked copy of the github-app key file, and makes its
  own hour-long github tokens from it, same as the ec2 boxes do from aws"*
- analogy: a cut key vs a key-cut machine. we never leave a cut key on the box (it expires within
  the hour); we leave the machine, locked to the box's owner
- their words vs ours: "github app creds" = our **blob** / source credential · "token" = our minted
  `ghs_` / grant · "copy the creds over" = our **file** (set) into a **vault**

## .evaluation

| goal (wish `done means`) | how the vision meets it |
|---|---|
| off-ec2 `keyrack get` returns a token github accepts | `case=1`; os.secure + github-app already mints once the blob is filed. the proof github *accepts* it is the issue's own: rung 4 green on `grove-ahbode-hetzner-v20261022`, both seats. that proof is owed **after** the release and the commander's one command — the pr can name it, not produce it, since no driver here may file a credential onto a box |
| ec2 still mints as today | `case=2`; no change on the aws.params path except hint text on a refusal |
| clamp red with blob only in aws.params, green with the new source | `case=3` + `case=1`, one cli acceptance suite |
| pr green on ci | the change is small: one flag on `set`, one hint, tests |
| no credential value in tree, pr, or log | f2 invariant; `--source @stdin` never echoes; tests use a malformed fixture pem, never a real one |
| no credential provision onto any box | the pr names the one command; the commander runs it |

pros
- reuses the extant vault, mech, recipient encryption, and roundtrip verify — no new vault, no new mech
- box-agnostic: an ec2 grove may adopt it later; no rule forces it
- `--source @stdin` is generic over mechs whose source is a plain value (a replica key piped from a
  secret store works the same way)

cons
- a second home for the blob: a rotation of the app's private key now means a re-pipe per off-ec2
  box. aws.params stays the source of truth; the box holds a replica of the blob
- the blob on the box is a long-lived *secret* (the app private key), though no long-lived *token*
  is. it is age-encrypted to the box's ssh identity, so whoever holds that ssh key can mint — the same
  blast radius as an ec2 instance role today

edgecases and their pit of success
- malformed or empty stdin → refused before write (`case=5`)
- `--source @stdin` while stdin is a tty (no pipe) → refuse with a hint to pipe, never block on a
  read (diverges on purpose from the extant `@stdin` readers, which wait; see the answered questions)
- `--source @stdin` with a mech whose source is not a plain value (aws sso) → refuse, name the mech
- valid shape, wrong app (github 401 at mint) → set accepts; first unlock fails loud (m3, q4)

## .open questions & assumptions

assumptions
- a1: an off-ec2 grove has a keyrack-discoverable ssh identity for owner ehmpath (`~/.ssh/ehmpath`,
  then the agent, then `~/.ssh/id_*` — `discoverIdentities.ts:17-48`) with no passphrase, and
  `keyrack init --owner ehmpath` ran there, so its host manifest has recipients. any box where unlock
  works at all already meets this
- a2: the blob in aws.params is the json `{ appId, installationId, privateKey, mech }` that
  `asGithubAppSource` writes and `parseGithubAppCredentials` accepts, so it pipes into os.secure as-is
- a3: the grove's rung reads the key through keyrack unlock + get, not by its own aws.params call
- a4 — **unverified, and the command must not guess it**: the slug's org on the grove. two forms fit
  the evidence:
  - machine-wide, `@all.prep.EHMPATH_BEAVER_GITHUB_TOKEN` — its aws.params identity is the grove's
    instance role (`asKeyrackAwsParamIdentity.ts`), which matches "only a box with an aws identity
    can mint"
  - repo-org, `ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN` — the slug this repo's cli fixtures use
    (`asKeyrackStatusKeyBranch.test.ts:32`)

  the box answers it: `rhx keyrack list --owner ehmpath` on the box prints the slug its host manifest
  holds. the one command then files under that exact slug (`set` takes a full slug as `--key`). it
  matters because over ssh the cwd is `$HOME`, and `set` refuses a repo-scoped key from a non-repo cwd
  (`invokeKeyrack.ts:1433-1438`, `onNoRepo: 'refuse'`): a machine-wide slug runs as is; a repo-org slug
  needs `cd <a clone of that org's repo> &&` first
- a5: the commander's own aws profile can read and decrypt the blob param (`ssm:GetParameter` +
  `kms:Decrypt`) — a read, which the prod-is-read-only bound permits
- a6: the hetzner box reaches `api.github.com` (it must, to clone at all)

questions answered now, from code or logic
- **[answered] which mechs may take `--source @stdin`?** those whose stored source is a plain value
  the vault holds as-is: `PERMANENT_VIA_REPLICA` and `EPHEMERAL_VIA_GITHUB_APP` (os.secure's
  `mechs.supported`, `vaultAdapterOsSecure.ts:97-99`). `EPHEMERAL_VIA_AWS_SSO` stores a pointer, not
  a value, so the flag refuses it and names the mech
- **[answered] what does `@stdin` do on a tty?** the extant `@stdin` readers (`clone say --what`,
  `invokeCloneSay.ts:123`; `enroll --reason`, `invokeEnroll.ts:388-390`) wait on a tty with a hint.
  for a secret that is the wrong default: a human who then pastes a private key echoes it to the
  screen (f2). so `set --source @stdin` refuses a tty at once and says to pipe. a deliberate
  divergence, named here so the blueprint does not "fix" it into parity
- **[answered] reuse the extant stdin read?** yes. keyrack would be the third `@stdin` reader, and
  both extant readers carry a rule-of-three note that the third earns a shared `readStdin`
  (`invokeCloneSay.ts:42`, `invokeEnroll.ts:111`). the blueprint extracts it
- **[answered] does a re-file over the extant aws.params entry refuse?** no. `setKeyrackKeyHost`
  relocks the daemon for the slug (`setKeyrackKeyHost.ts:151-157`), then replaces an entry whose
  attrs differ (:159-199)
- **[answered, at file time] the slug's org (a4)** — not knowable from this repo; the box's own
  `keyrack list` answers it, and the command reads it there
- **[answered] where does the commander find the blob's param path?** the default is
  `/keyrack/infra/vault/aws.params/v1/{owner}/{org, @all → _all_}/{env}/{key}`
  (`asKeyrackAwsParamName.ts:35`); an explicit `--exid` at set overrides it, so the truth is the exid
  an ec2 grove's host manifest holds for the slug. case=4 names both
- **[answered] should a stdin set also findsert the app into the keyrack-infra registry?** no. the
  registry is a discovery aid for the guided set; the mint reads only the stored `installationId`
  (`mechAdapterGithubApp.ts:225-229`), and a registry write needs the gh auth the box lacks. the app
  is already registered by the ec2-side set
- **[answered] should keyrack detect a stale replica after a key rotation?** no detection ahead of
  time; a rotated key fails loud at mint (github 401). that refusal names its cure: the github-app
  mech maps a 401 to a ConstraintError whose hint is the same one re-file command
  (`asGithubAppMintFaultRefusal.ts`)

questions for external research
- **[research]** none. the one external fact the vision rests on (github's 1h installation token)
  is cited below

questions for the commander (at the pr, each with options and a lean)
- **[wisher] q1 — where does the blob live off ec2?**
  - (a) os.secure on the box, age-encrypted to its ssh identity ← lean: already supports the mech,
    headless, cached by the daemon, no new infra
  - (b) os.envvar — works today with no code change, but the blob (with its pem) sits in the
    process env in plaintext and is minted on every get. to survive a reboot or a new crew shell it
    must be written to an env file on the box: a plaintext private key on disk, the exact shape
    os.secure exists to avoid
  - (c) 1password via a service account — the service-account token is a second long-lived secret
    to file anyway, and `assertAccountIsKeyrack` is unproven for a service account
- **[wisher] q2 — how is it filed?**
  - (a) `keyrack set --source @stdin`, piped from aws.params ← lean: one command, no tty, no pem on disk
  - (b) the guided set over `ssh -t`, with gh auth forwarded and a pem copied to the box — two
    extra secrets touch the box
  - (c) a new `keyrack copy` verb — it would have to write to a remote box's vault, since the
    hetzner box can read only one side
- **[wisher] q3 — the flag's name.** `--source @stdin` (names the mech's source concept) ← lean ·
  `--from @stdin` (precedent: `keyrack firewall --from`) · `--value @stdin`. the `@stdin` value form
  itself is settled by precedent (`clone say --what @stdin`, `enroll --reason @stdin`)
- **[wisher] q4 — probe the mint at set time?** (a) no; shape check only, the first unlock surfaces a wrong
  app ← lean: set stays offline and fast · (b) yes; mint once at set, discard the token, refuse on 401
- **[wisher] q5 — how far does the ci clamp follow the mint?** no test in this repo mints a real `ghs_`:
  a grep for `createAppAuth` and `auth({ type: 'installation' })` finds no call in `src/**/*.test.ts`,
  and its two `blackbox/` hits mint with a deliberately bad key that throws before any network call
  (`mechAdapterGithubApp.test.ts:140-164` states the same: a real mint is unreachable without credentials).
  - (a) the clamp proves the route to the mint — blob decrypted from os.secure, handed to
    `deliverForGet` (a malformed fixture pem → the extant bad-pem `ConstraintError`,
    `mechAdapterGithubApp.ts:255-268`, marks arrival with no network call; a well-formed throwaway
    pem would reach github and fail there instead); "github accepts it" is proven on the grove's rung 4 ← lean
  - (b) the clamp mints for real against a test github app whose blob sits in the test keyrack —
    a new ci secret and a network call per run. measured: no github-app blob reaches this repo's ci
    today. ci's keys are filtered to `.agent/keyrack.yml` (`.test.yml:231`), its env.test declares
    only three llm keys, and a grep for `GITHUB_APP`, `github_app`, and `privateKey` across `.github/`
    and for `GITHUB_APP` / `PRIVATE KEY` in `.agent/keyrack.yml` finds no match

to validate with the wisher before criteria
- q1 + q2 leans; they decide the shape of all that follows
- q5; it decides what "a clamp that passes with the new source" means

## .groundwork

### external research

- github installation access tokens expire after one hour — github docs, "generating an
  installation access token for a github app"
  (docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app).
  the mech sets `expiresAt = now + 55m` (`mechAdapterGithubApp.ts:272-275`)
- `@octokit/auth-app` mints that token from `{ appId, privateKey, installationId }` via
  `createAppAuth(...)` then `auth({ type: 'installation' })` (`mechAdapterGithubApp.ts:224-240`);
  already a dependency, loaded lazily

### internal research

- mint: `src/domain.operations/keyrack/adapters/mechanisms/mechAdapterGithubApp.ts` — `validate`
  (:112-134) checks a source blob or a cached `ghs_`; `parseGithubAppCredentials` (:47-95) names each
  absent field; `deliverForGet` (:212-276) mints
- guided acquire: `mechanisms/genGithubAppSource.ts` — keyrack-infra discovery via gh, then a tty pem
  prompt; `acquireForSet` throws `ConstraintError` when stdin is not a tty (:174-181)
- os.secure: `vaults/os.secure/vaultAdapterOsSecure.ts` — supports the mech (:97-99); `get` decrypts
  with the context identity, then `deliverForGet`; `set` calls `mech.acquireForSet`, encrypts to
  `hostManifest.recipients`, verifies the roundtrip
- aws.params: `vaults/aws.params/vaultAdapterAwsParams.ts:69-130` (get), the blob as one SecureString
  json (`setKeyrackAwsParamGithubApp.ts`), path `/keyrack/infra/vault/aws.params/v1/{owner}/{org}/{env}/{key}`
  (`asKeyrackAwsParamName.ts:100-128`), no-identity refusal (`asKeyrackAwsParamErrorGate.ts:187-201`)
- host manifest: `src/domain.objects/keyrack/KeyrackKeyHost.ts` — one vault + one mech per address,
  per box, per owner; the only lookup fallback is env → `all` (`src/domain.objects/keyrack/getEnvAllFallbackSlug.ts`)
- get vs unlock: `getKeyrackKeyGrant.ts` reads the daemon then os.envvar, never a vault; unlock
  (`session/unlockKeyrackKeys.ts:360-402`) calls `adapter.get`, where the mint happens; the daemon
  drops an entry at `expiresAt` (`daemonKeyStore.ts:60-74`)
- set cli: `src/contract/cli/invokeKeyrack.ts:1269-1305` — no value-on-stdin flag today
- tests to extend: `blackbox/cli/keyrack.vault.osSecure.githubApp.acceptance.test.ts`,
  `vaults/aws.params/asKeyrackAwsParamErrorGate.test.ts`, `vaults/os.secure/vaultAdapterOsSecure.integration.test.ts`
- vocab to reuse: vault, mech, source, grant, host manifest, recipient; stdout = the 🔐 set tree with
  `roundtrip verified`; errors = `✋ ConstraintError:` with a hint

## .what is awkward

- the blob now has two homes, and the box copy can drift on a key rotation. aws.params stays the
  source of truth and the re-file is one command, but the box learns its replica is stale only when
  github refuses the mint. that refusal names the re-file command (see the answered questions)
- `--source @stdin` skips the keyrack-infra registry findsert the guided set does. correct here (the
  app is registered, and the mint never reads the registry), but a first-ever filing via stdin would
  leave the app unregistered for members who discover via the registry
- the commander's command reaches into aws.params by hand (`aws ssm get-parameter`), which shows the
  human keyrack's param path layout. a keyrack verb that prints the raw blob would hide that, but a
  verb that prints a private key is a footgun the vision declines
- the wish's "returns a token github accepts" cannot be proven in ci without a live app credential
  (q5); the vision proves the route in ci and the acceptance on the grove

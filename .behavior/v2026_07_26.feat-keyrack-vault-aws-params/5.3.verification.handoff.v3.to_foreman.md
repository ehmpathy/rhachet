## the wall — an expired AWS SSO test-profile session

this branch adds `AWS_PROFILE` to `env.test` in `.agent/keyrack.yml` (the G8 org-scope work),
so the jest integration env-setup (`jest.integration.env.ts:97` → `sourceAllKeysIntoEnv`)
strictly requires `ehmpathy.test.AWS_PROFILE` unlocked for EVERY integration worker, before any
test body runs. that key is an aws.config SSO key; its unlock opens a browser SSO prompt.

## what i tried (each exhausted)

1. `rhx git.repo.test --what integration --scope aws.params --mode apply --env test`
   → the harness auto-unlock hit `keyrack unlock ehmpathy.test.AWS_PROFILE` → **aws sso login
   timed out: human did not respond to browser sso prompt** (exit 2, malfunction).
2. `npm run test:integration -- aws.params` (jest directly, no harness auto-unlock)
   → the jest integration ENV setup itself calls `sourceAllKeysIntoEnv`, which fail-fasts
   (`process.exit(2)`) on the locked `ehmpathy.test.AWS_PROFILE` for every worker →
   "some keys were not granted, yet are strictly required." the suite cannot even initialize.
3. `rhx keyrack unlock --owner ehmpath --env test` (direct, generous timeout, to give a present
   human the chance to complete SSO)
   → **aws sso login timed out — human did not respond to browser sso prompt** (exit 2). keyrack
   itself printed: "robot: halt and escalate — do not proceed, do not find workarounds, do not
   skip credentials."

## why this is fundamentally foreman-only

- the unlock requires an interactive AWS SSO browser login. no robot can complete it; it needs a
  human at the browser to approve the session.
- the keyrack subsystem explicitly instructs a halt-and-escalate on this exact state, and forbids
  a workaround or a credential skip. to weaken the env-setup to lenient, or a mock of the profile,
  would be a credential dodge the verification gate forbids.
- this is a transient credential expiry, NOT a code defect: the integration code is unchanged
  this session, and it last ran green when the SSO session was live.

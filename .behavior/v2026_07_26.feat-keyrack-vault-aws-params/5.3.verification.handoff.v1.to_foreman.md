## the full-integration result + diagnosis (34 failures, all environmental, 0 logic defects)

`rhx git.repo.test --what integration --mode apply --env test` → 344 passed, **34 failed**.
diagnosed to two environmental classes, each verified:

### class A — daemon-spawn load flake (NOT this PR, NOT aws.params)

- suites: `unlockKeyrackKeys`, `os.daemon/vaultAdapterOsDaemon`, `fillKeyrackKeys`,
  `envAllHostingStrategies`. error: `keyrack daemon did not become reachable within 5000ms`
  at `findsertKeyrackDaemon.ts:40` — the 5s spawn budget is starved under the 42-way
  parallel storm.
- **1. what i tried:** re-ran the two representative suites in isolation.
- **2. result:** `unlockKeyrackKeys` → **8/8 green** (`--scope 'path://unlockKeyrackKeys'`);
  `os.daemon` → **7/7 green** (`--scope 'path://os.daemon/vaultAdapterOsDaemon'`).
- **3. why it is not mine to fix:** `git diff --stat main` on
  `adapters/vaults/os.daemon/` + `daemon/` is **EMPTY** — the daemon subsystem is untouched
  by this branch. the one session file i changed (`unlockKeyrackKeys.ts`, the G5 per-key
  loop) runs AFTER the daemon spawn; the spawn timeout is upstream and the suite passes
  alone. this is a prior parallel-runner clock artifact of the full local run, not a
  regression and not a deliverable defect. a serial / less-parallel integration run avoids it.

### class B — foreman-held AWS SSO credential (the real wall)

- suites: `setKeyrackAwsParamGithubApp`, `getOneKeyrackAwsParam`, `vaultAdapterAwsParams`.
- error: `vendAwsTestCredentials` runs `keyrack unlock && keyrack get --key AWS_PROFILE
  --value` → returns **`absent 🫧`** → no AWS creds → the downstream SSM call fails with an
  unmapped `MalfunctionError`.
- **1. what i tried:** ran `keyrack unlock --owner ehmpath --env test` then
  `keyrack get --owner ehmpath --env test --key AWS_PROFILE --value` directly.
- **2. why it failed:** the ehmpath/test keyrack holds only OPENAI/XAI/ANTHROPIC keys;
  `AWS_PROFILE` (an aws.config-vault SSO profile) is **not registered/filled** on this
  machine. the `keyrack get` returns `status: absent 🫧` with the tip
  `rhx keyrack set --key AWS_PROFILE --env test --vault aws.config`.
- **3. what makes it impossible alone:** to vend a real AWS identity needs an **AWS SSO
  account login** — a credential the foreman possesses and a clone cannot obtain, mock (the
  gate demands a REAL decrypt, per the blueprint credential strategy — a mock would be
  fraud), or fabricate.
- **4. is this truly a "foreman possesses the key" situation?** yes. the fix is an
  `aws.config` SSO profile + `keyrack fill` against the human's AWS SSO account. no clone can
  perform an interactive SSO login for an account it does not own.

## matrix 3 — `unlock`: precondition gates (fail-fast chain, NOT a cartesian product)

covers uc5, uc10–uc15.

> **decomposition:** these conditions are not independent — `unlock` checks them in a
> fail-fast order and the FIRST unmet gate decides the outcome. so this is an ordered chain
> (first-failing-gate → outcome), not a 2^N product of 6+ booleans. this is the natural,
> legible shape and matches how a fail-fast surface behaves.

| ind: first unmet gate (in precedence order) | dep: unlock outcome | dep: fix named | uc |
|---|---|---|---|
| aws capability not installed | fail loud | the one install command | uc14 |
| no ambient AWS identity | fail loud | SSO login / attach a role | uc10 |
| region not determinable | fail loud | where a region must be supplied | uc15 |
| identity may not READ the param | fail loud (access denied) | the read grant + names param & identity | uc11a |
| param absent | fail loud (absent) | create/place the param, or fix the reference | uc12 |
| param present but plaintext (not a secret) | fail loud (refused) | the param must be a decryptable secret | uc13 |
| identity may not DECRYPT the param | fail loud (DISTINCT decrypt-denied) | the decrypt grant | uc11b |
| — all gates pass — | unlock succeeds, NO human prompt | — | uc5 |

## gaps flagged

- **G1 — github-app + explicit `--exid`.** matrix 1 lets `--exid` override the path for any
  mech, but uc3 (github-app persist) only shows the autocomputed path. is `--exid` honored
  when persisting a github-app blob (persist at a foreign path), or is the override
  reference-only? not specified — flag for the blueprint / wisher.
- **G2 — `--max-duration` vs the github-app token's own ~1h TTL.** matrix 4 bounds the
  unlocked window by `--max-duration`; matrix 5 says a github-app read yields a ~1h token.
  which bounds the effective lifetime when both apply, and does a re-unlock re-mint? not
  specified — flag.
- **G3 — exact precedence order within matrix 3 (rows 4–7).** the criteria specify each error
  but not their relative order (e.g. read-denied vs absent vs type-check vs decrypt-denied).
  the order affects which error a human sees first — flag as a blueprint decision.
- **G4 — `--owner` when omitted.** the matrices assume owner is supplied. the vision requires
  owner always in the path and fail-loud if absent; there is no blackbox usecase for an
  omitted owner (does it default to the caller's identity, or fail?). minor — flag to confirm.

## decomposition assessment

- `set` (matrices 1–2), `unlock` (matrix 3), `get` (matrices 4–6) are cleanly separable
  boundaries — each has ≤2 real independent dimensions once the unlock chain is read as a
  precedence chain rather than a product. no matrix explodes.
- the only place that LOOKED like an explosion — unlock's 6+ preconditions — is resolved by
  the fail-fast-chain framing. no usecase is too broad; no decomposition into narrower
  behaviors is required.

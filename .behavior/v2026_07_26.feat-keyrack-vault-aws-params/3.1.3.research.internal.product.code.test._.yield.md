## [3] vault adapter INTEGRATION test pattern — [REUSE] as pattern → new integration test

**This is the key precedent. How does aws.config's integration test authenticate to AWS?**

[3a] the answer — it does NOT authenticate. It shells out to the real `aws` CLI and accepts BOTH outcomes — `vaultAdapterAwsConfig.integration.test.ts:83-120`:
```ts
given('[case4] aws sts service call (real external contract)', () => {
  when('[t0] aws sts get-caller-identity is called', () => {
    then('either returns identity or auth error (proves network call)', () => {
      const result = spawnSync('aws', ['sts', 'get-caller-identity', '--output', 'json'],
        { encoding: 'utf8', timeout: 30000 });
      if (result.status === 0) {
        const parsed = JSON.parse(result.stdout);
        expect(parsed).toHaveProperty('Account');
        expect(parsed).toHaveProperty('Arn');
      } else {
        const output = result.stderr || result.stdout;
        expect(output).toMatch(
          /Unable to locate credentials|ExpiredToken|InvalidClientTokenId|AccessDenied|NoCredentialProviders|credentials|session.*expired|reauthenticate/i,
        );
      }
    });
```
The rationale is stated at `:6-40`: the SSO browser flow is human-gated and cannot run in CI (`:25-29`, `:123-136`), so the integration test proves only that (a) the `aws` CLI is present (`:43-62`), (b) the adapter derives `null` for an absent profile with NO mocks (`:64-76`), and (c) a real network call reaches `sts.amazonaws.com` whether or not creds are present. The failure branch — the regex over the no-creds error — is what "proves real network call to external contract" (`:88-91`).

[3b] no-mocks declaration in this file — `vaultAdapterAwsConfig.integration.test.ts:68`:
```ts
// real adapter call — no mocks
```

[3c] 1password integration — the conditional-skip precedent — `vaultAdapter1Password.integration.test.ts:9-14`:
```ts
beforeAll(async () => {
  opAvailable = await isOpCliInstalled();
  if (!opAvailable) {
    console.log('skipped 1password integration tests: op cli not available');
  }
});
```
and inside a case, `:19-27` / `:87-93`:
```ts
if (opAvailable) { expect(true).toBe(true); return; }
...
if (!isUnlocked) { console.log('skipped ... op cli not authenticated'); expect(true).toBe(true); return; }
```
**relates to aws.params** — this is the design tension. aws.config's precedent (dual-outcome, tolerate absent creds) and 1password's precedent (probe availability, soft-skip) BOTH soft-tolerate an absent tool/creds. The team's stated rule for aws.params is stricter: fail-fast with a `ConstraintError` when creds are absent (see [5]). So the aws.params integration test can adopt the aws.config `spawnSync` + real-endpoint structure, but for its DECRYPT path it needs a real SSM SecureString + a real identity with `ssm:GetParameter` + `kms:Decrypt`. That provision is the open question ([summary NOTE]).

[3d] the os.secure integration test — the round-trip-through-real-crypto precedent — `vaultAdapterOsSecure.integration.test.ts:62-81` sets up a real temp home via `withTempHome`, seeds a real age identity/recipient from `@src/.test/assets/keyrack/age/testAgeKeys`, and does a full set→get round-trip against real on-disk age files (`:160-172`), then proves the ciphertext lacks the plaintext (`:271-288`). aws.params has an analogous round-trip: `setSsmParameterSecure` → `getOneParameter` → assert the decrypted value equals the input.

## [5] credential fail-loud vs skip in integration tests — [REUSE]

[5a] fail-loud with `ConstraintError` + actionable hint — `getKeyrackKeySecrets.integration.test.ts:28-38`:
```ts
const assertKeyGranted = async (keySlug: string): Promise<void> => {
  const granted = await keyrack.get({ for: { key: keySlug }, env, owner })
    .then(({ attempt }) => attempt.status === 'granted').catch(() => false);
  if (!granted)
    throw new ConstraintError(
      `keyrack not set up for ${keySlug} on this host`,
      { hint: 'run: rhx keyrack unlock --owner ehmpathy --env test' },
    );
};
```
A precondition (a not-granted key) throws loud with a `rhx keyrack unlock` hint rather than a silent skip. This is the exact posture the aws.params integration test needs for absent AWS creds.

[5b] `ConstraintError` = caller-fix, exit code 2 — `getKeyrackKeySecrets.integration.test.ts:53-62`:
```ts
// absent key is caller-fix, not a server malfunction
expect(error).toBeInstanceOf(ConstraintError);
expect(error.code.exit).toEqual(2);
expect(error.metadata.attempts[0].status).toEqual('absent');
```
The taxonomy: `ConstraintError` (✋ caller must act, exit 2) versus a server `MalfunctionError` (💥). aws.params absent-creds → `ConstraintError`.

[5c] the tolerant counter-precedent in aws.config — `vaultAdapterAwsConfig.integration.test.ts:108-117` (the no-creds branch is EXPECTED, asserted via regex, not thrown). [note] this is the tension to settle for aws.params: aws.config's own integration test tolerates absent creds; the team rule wants aws.params to fail-fast. The `[5a]` util is the model to adopt over the `[5c]` tolerance.

## [9] region + identity for AWS-adjacent tests — [REUSE] / [EXTEND]

[9a] region is NOT auto-derived and is explicitly UNSET in isolation — `envIsolated.ts:11-12` unsets both `AWS_REGION` and `AWS_DEFAULT_REGION`. [EXTEND] — aws.params fixtures set `meta.region`.

[9b] identity comes from the real `aws` CLI (`sts get-caller-identity`), asserted by a parse of `Account`/`Arn` — `vaultAdapterAwsConfig.integration.test.ts:103-107`; the mock CLI mints the same shape at `mock-aws-cli/aws:87-93`. aws.params integration reuses `sts get-caller-identity` to confirm a live identity before the SSM decrypt.

[9c] a dedicated `aws.whoami`/`getStripeCredentials`-style credential util was NOT found in the keyrack tree — the repo's approach is the inline `spawnSync('aws', [...])` probe ([3a]) plus the `assertKeyGranted` guard ([5a]), not a shared credentials util. aws.params should follow that inline-probe + guard style.

## NOTE — the single most important open test question

How will the aws.params INTEGRATION test provision a REAL SSM SecureString + REAL AWS identity + region in CI?

The prior art gives no clean answer. aws.config's integration test dodges this — it never provisions AWS state; it accepts the no-creds branch as a pass ([3a], [5c]). 1password soft-skips when its tool is absent ([3c]). But aws.params' whole value (`getOneParameter` that decrypts a SecureString via KMS, and `setSsmParameterSecure` that writes one) cannot be proven by a dual-outcome probe: a genuine assertion requires a real param that exists, a real identity with `ssm:GetParameter` + `kms:Decrypt`, and an explicit region (which `envIsolated` deliberately unsets, [9a]). Open sub-questions to settle in the blueprint:

1. does CI carry an OIDC/assume-role identity with SSM+KMS scope, or must the integration test soft-skip (aws.config-style) when creds are absent while it still fails loud in local dev per the team rule ([5])?
2. who seeds the SecureString the test decrypts — a `setSsmParameterSecure` write in `beforeAll` (self-provisioned round-trip, akin to os.secure at [3d]) then teardown-delete, or a pre-provisioned fixture param?
3. where does the region come from in the test — the key's `meta.region` ([9a]) — and is there a CI default region the SSM+KMS grant is scoped to?

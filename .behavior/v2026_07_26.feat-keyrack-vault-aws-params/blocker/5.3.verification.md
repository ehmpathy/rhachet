# blocker — 5.3.verification (aws.params org-scope identity hardcut)

## what blocks you 🪘

the aws.params identity design was re-cut this round to the **org-scope hardcut**: `--org @all`
= grove-wide -> the grove's own IMDS role; a specific org = tree-wide -> that org's `AWS_PROFILE`
from the keyrack itself, failfast if absent, never ambient SSO. i propagated the hardcut into
the briefs, vision, and blueprint, and landed the decision-independent code (verified green,
below).

the rest of the credential wiring gates on ONE design decision i cannot make unilaterally: the
specific-org path must obtain "that org's `AWS_PROFILE` from the keyrack itself", but the adapter
`get()` (which derives the org from the slug and receives an `identity`) has NO seam that hands
it the org's keyrack-declared `AWS_PROFILE`. the two clean ways to supply it each change a
DIFFERENT SHARED surface, so the pick is a wisher/architecture call above the settled blueprint
scope — and the behavior is not locally verifiable (it needs real SSM / IMDS / multi-profile AWS):

1. **peer-key via the batch (recommended)** — `AWS_PROFILE` is already an `aws.config` keyrack
   key (`inferKeyrackVaultFromKey` maps it so; `.agent/keyrack.yml` declares it per env).
   `unlockKeyrackKeys` derives that org's `AWS_PROFILE` grant and threads it into the aws.params
   `get()` input (additive — extant vaults ignore the field). respects the invariant
   (keyrack-declared, not an ambient env-grab). SHARED surface changed: the `unlockKeyrackKeys`
   driver + the `KeyrackHostVaultAdapter` get-input type.
2. **new manifest field** — add an explicit `profile:` per org to `.agent/keyrack.yml` + its
   DAO/schema; `get()` reads it direct. SHARED manifest-SCHEMA change (`daoKeyrackRepoManifest`
   + hydrate + schema tests).

a read of `process.env.AWS_PROFILE` would dodge both, but it VIOLATES the invariant just written
(never grab an ambient session that happens to sit in the env) — so it is not defensible.

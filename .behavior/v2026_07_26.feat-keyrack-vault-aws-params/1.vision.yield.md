# 1.vision — keyrack `aws.params` vault (set → unlock → get), built on `declastruct-aws`

> wish: `ehmpathy/rhachet#432` — add an aws vault so a cloud box bootstraps from its IAM
> role. this route delivers the `aws.params` vault end-to-end: **`set`** (register + autocompute
> path — the crux; persists an owned-source mech into SSM, or points at a param placed
> out-of-band), **`unlock`** (pull the value into the daemon via the ambient IAM identity),
> **`get`** (read the daemon). keyrack keeps no secret at rest; the grove only ever reads —
> mirrors how `os.secure` / `1password` behave, with SSM as the backing store.

## scope (decided with the wisher)

- **only `aws.params`** — SSM Parameter Store `SecureString` (`GetParameter --with-decryption`).
- **`aws.secrets` (Secrets Manager) is OUT of scope** for now — deferred to a later route.
  param store is materially cheaper at low volume and alone unblocks the bootstrap case.
- **`declastruct-aws` is a REQUIREMENT, not a bonus.** the vault adapter MUST read AND write
  through `declastruct-aws`'s SSM seams (`sdkSsm.getOneParameter` for read,
  `setSsmParameterSecure` for persist); it must NOT hand-roll a `@aws-sdk/client-ssm` call.
- **`declastruct-aws` is an OPTIONAL PEER dependency** (`peerDependencies` +
  `peerDependenciesMeta.optional: true`), lazy-imported by the adapter — so a user who
  never uses an aws-backed vault never installs the AWS SDK weight. this matches how
  keyrack already treats vault backends (`1password` needs the `op` cli, `aws.config` needs
  AWS SSO): the backend is an optional host capability, and its absence fails loud with a
  fix hint, never a cryptic crash.
- **the GET path is UNCHANGED — `get` reads the daemon only, never the vault.** `unlock`
  pulls the value into the daemon via the ambient IAM identity (no human prompt); `get`
  serves from the daemon exactly as for every other cred. aws.params aligns exactly with how
  every extant vault is used; the in-code invariant (`getKeyrackKeyGrant.ts:21`) holds.
- **`--exid` is OPTIONAL** — autocomputed from the key's coordinates by default; explicit
  only as an escape hatch for a param under a foreign path.
- **mechanisms = `PERMANENT_VIA_REFERENCE` + `EPHEMERAL_VIA_GITHUB_APP` (both reused, none
  new)** — aws.params lists both in `mechs.supported`, exactly as `os.secure` / `1password`
  do. no new mech; aws.params is a new VAULT on extant mechs:
  - `PERMANENT_VIA_REFERENCE` — the SSM param value IS the secret (e.g. `ANTHROPIC_API_KEY`);
    passthrough, fetched on unlock.
  - `EPHEMERAL_VIA_GITHUB_APP` — the SSM param holds the github-app private-key json blob.
    on `set` (from a trusted machine) keyrack persists that blob INTO SSM via
    `mechAdapterGithubApp.acquireForSet` → declastruct `setSsmParameterSecure`, exactly as
    `os.secure` persists it locally / `1password` writes it via `op item edit`. on `unlock`
    (on the grove) keyrack reads the blob and `mechAdapterGithubApp` mints a ~1h installation
    token into the daemon. this is the wish's github case: the app private key lives in SSM,
    the grove's role reads it, the grove mints its own short-lived token — no master key ever
    placed on the box.
  - **the two modes mirror `1password`** (which supports both): `PERMANENT_VIA_REFERENCE`
    points at a param placed out-of-band (no write); `EPHEMERAL_VIA_GITHUB_APP` persists the
    owned source into SSM on set, then mints on unlock.

## the org-scope identity hardcut (which AWS identity unlocks)

the vault's AWS identity is NOT an inference waterfall and NOT a picker. it is a **hardcut on
the `--org` scope** — a general keyrack invariant (see
`.agent/repo=.this/role=keyrack/briefs/define.keyrack-org-scope.grove-vs-tree.md`), applied to
aws.params:

| `--org` scope | AWS identity used |
|---------------|-------------------|
| `@all` (grove-wide) | **IMDS only** — the EC2 instance role, the grove's own badge |
| a specific org (tree-wide) | **that org's `AWS_PROFILE`, sourced from the tree's `.agent/keyrack.yml`** |

- `@all` means the credential belongs to the **grove** itself → the grove's own ambient
  identity (IMDS) is the root of trust; keyrack never consults a profile or an ambient SSO
  session for an `@all` key.
- a specific org means the credential belongs to **that org's tree** → keyrack authenticates as
  the `AWS_PROFILE` the tree's `.agent/keyrack.yml` declares for that org, and **failfasts** if
  the manifest declares none — never a silent fall back to IMDS or an ambient session.

so the identity is decided by the scope the human already typed, deterministically. **no
`--account` flag, no `meta.account` pin, no runtime picker.** the vault persists only `region`
(captured at set) and `exid`; the identity is derived at unlock from `--org` + (for a specific
org) the manifest's `AWS_PROFILE`. never ambient SSO.

the day-in-the-life below is the `@all` grove path (u1). the specific-org path (u2/u3) uses the
tree's manifest `AWS_PROFILE` instead of IMDS — otherwise identical.

## the org-scope namespace grain (`@all` = machine-wide vs default = repo-wide)

the `--org` scope cuts a SECOND, distinct axis: the **param namespace** — WHERE the org segment
of the computed SSM name comes from, and whether a repo manifest is needed at all. this is a
**separate concern from the AWS identity** above (that axis picks IMDS vs `AWS_PROFILE`; this axis
picks the namespace + the no-repo-manifest posture). both branch on the same `--org` scope.

| `--org` scope | namespace grain | org segment in the SSM name | repo manifest |
|---------------|-----------------|-----------------------------|---------------|
| `@all` | **machine-wide** (the box / grove) | the legalized sentinel `_all_` | **NEVER consulted** — works with no repo manifest at all |
| a specific org | **repo-wide** (the tree) | that org | the source of the org |
| omitted (default) | **repo-wide** | the repo's own org | required (failfast if absent) |

- **`@all` = machine-wide.** the key belongs to the box itself. it is set + read from **any repo,
  or none** — only the host manifest (`~/.rhachet/`) is needed, never a repo `.agent/keyrack.yml`.
  the `@all` sentinel's `@` is outside SSM's legal charset, so the org segment is legalized to a
  reserved `_all_` segment (stable across set/get; `@all` keys are keyrack-owned, so no
  out-of-band writer must match it).
- **org default = repo-wide.** with no `--org @all`, the org resolves from the repo's manifest, so
  the key is scoped to that repo's org tree.
- **`@all` ignores a present repo manifest.** even inside a repo tree, `--org @all` resolves to the
  machine-wide `_all_` namespace — the manifest org is not consulted.

### why machine-wide, no-repo-manifest matters (the bootstrap root)

the **github-app install token** is vaulted under `--org @all` precisely so it can be retrieved
from anywhere — **even outside any repo, before any repo is cloned**. it is the credential used to
get auth to **clone the repos in the first place**; at that moment there is not even a repo
manifest on the box. a repo-manifest requirement on the `@all` path would be circular — you would
need a cloned repo to obtain the credential that clones the repo. so `@all` set/unlock/get MUST
work with zero repo context, and the vault is proven so (see the org-scope matrix below).

this namespace grain is **vault-agnostic** — a machine-wide `@all` key behaves the same for
`os.secure` (a static machine-wide key) as for aws.params. see the general
`.agent/repo=.this/role=keyrack/briefs/rule.require.org-scope-grain-hardcut.md`; the
aws.params-only `_all_` sentinel legalization is
`.agent/repo=.this/role=keyrack/briefs/rule.require.aws-params-sentinel-legalization.md`.

## the outcome world

### day-in-the-life

a headless EC2 box (a **grove**) boots. it carries exactly one credential: its IAM
instance role, readable over IMDS with no secret placed on it. it needs a github token and
an anthropic key to do any work.

```sh
# on the grove, no human, no manifest clone
rhx keyrack unlock --env prod    # no prompt — the IAM identity IS the unlock
rhx keyrack get --key ANTHROPIC_API_KEY --env prod --value
# → sk-ant-...   (served from the daemon; the value was pulled from SSM on unlock)
```

the box answered no unlock prompt (its identity is the unlock), decrypted no local file, read
no private repo. `unlock` pulled the value from SSM by proof of the instance role and placed
it in the daemon; `get` read the daemon — exactly as for every other cred.

### before / after

| | before (today) | after (this wish) |
|---|---|---|
| root of trust | a secret placed on the box | the box's own IAM identity |
| bootstrap step | `keyrack fill` reads `$org/keyrack-infra` **private** repo | none — the role IS the credential |
| the circle | grove needs a github token to read the repo that holds the github token | broken — one credential obtainable with zero credentials |
| on-box compromise | inherits whatever secret is at rest | inherits a live read of a referenced parameter, revocable by role detachment |
| unattended operation | impossible (unlock prompt has no human) | native (identity needs no unlock) |
| AWS integration | none in keyrack for param store | rides `declastruct-aws`'s tested `sdkSsm` communicator |

### the "aha" moment

> the credential the box needs is not one we *place* on it — it is one the box *derives* by
> proof of the identity it already carries.

the aha clicks when you realize `aws.params` stores **no secret in keyrack at all**. keyrack
holds only a *reference* — the SSM parameter path. the value lives in AWS, encrypted at rest
by KMS; the box's ambient AWS identity is what unlocks the decrypt. "always unlocked" stops
being a feature we build and becomes a fact of the environment.

## user experience

### usecases & goals

| # | actor | goal |
|---|---|---|
| u1 | grove (unattended EC2) | fetch `ANTHROPIC_API_KEY` via `--org @all` → the grove's IMDS role |
| u2 | grove | fetch a github app private key → mint a ~1h installation token |
| u3 | laptop dev | fetch a specific-org key → that org's `AWS_PROFILE` from the tree's `.agent/keyrack.yml` |
| u4 | operator | register a param-referenced key once, share it across all envs |
| u5 | CI | fetch a specific-org key → that org's `AWS_PROFILE`, named in the tree's manifest |

### contract inputs & outputs

`set` (register + autocompute) is the **most important part** of this route — it is the
config entry point and where the autocompute path is built.

**register a reference — common case (`PERMANENT_VIA_REFERENCE`, no `--exid`; path autocomputed):**

```sh
rhx keyrack set --key ANTHROPIC_API_KEY --vault aws.params --owner mechanic --env prod --org ehmpathy
# --mech omitted → keyrack prompts "which mechanism?" (aws.params has 2); pick
#   PERMANENT_VIA_REFERENCE. keyrack derives the SSM path from the template:
#   /keyrack/infra/vault/aws.params/{owner}/{org}/{env}/{key}
#   → /keyrack/infra/vault/aws.params/mechanic/ehmpathy/prod/ANTHROPIC_API_KEY
# (hierarchy segments only — chars stay within SSM's allowed [a-zA-Z0-9_.-/])
# points at a param placed out-of-band; keyrack writes no value.
```

**persist a github app — (`EPHEMERAL_VIA_GITHUB_APP`, keyrack WRITES the blob into SSM):**

```sh
rhx keyrack set --key EHMPATHY_SEATURTLE_GITHUB_TOKEN --vault aws.params \
  --mech EPHEMERAL_VIA_GITHUB_APP --owner mechanic --env prod --org ehmpathy
# acquireForSet guides the app-cred input → declastruct setSsmParameterSecure writes the
# blob to the autocomputed path, exactly as os.secure persists locally / 1password writes.
```

**register — escape hatch (explicit `--exid` for a prior / foreign path):**

```sh
rhx keyrack set --key ANTHROPIC_API_KEY --vault aws.params \
  --exid /legacy/anthropic/token --env prod --org ehmpathy
```

- `--vault aws.params` — SSM Parameter Store `SecureString`, decrypted on read
- `--mech` — **OPTIONAL**. `PERMANENT_VIA_REFERENCE` (point at a param) or
  `EPHEMERAL_VIA_GITHUB_APP` (persist an app blob, mint a token on unlock). when omitted,
  keyrack prompts via the shared `inferKeyrackMechForSet` — since aws.params supports two
  mechs, it lists them with descriptions and asks "which mechanism?", exactly as os.secure
  does. NO silent default; a one-mech vault auto-selects, a two-mech vault prompts.
- `--exid` — **OPTIONAL**. the SSM parameter name/path. when omitted, keyrack autocomputes
  it from the key's coordinates — always `{owner, org, env, key}`, owner never omitted — via
  the stable template, so the common case needs no path at all (pit of success). when
  supplied, it overrides the convention (for a param that lives under a foreign path).
- `--env`, `--org`, `--owner`, `--key` — scope, and the inputs the autocompute derives from
- `--max-duration` — caps how long a fetched value is cached in the daemon

keyrack's **manifest** stores only the reference (computed or explicit), never a value. for
an owned-source mech the value is written to SSM at `set`, then forgotten by keyrack.

**read (this route):**

```sh
rhx keyrack get --key ANTHROPIC_API_KEY --env prod --value
rhx keyrack source --env prod          # export statements for shell eval
```

output conforms to the extant grant contract (`KeyrackKeyGrant`): `{ slug, key, source,
env, org, expiresAt }`. no new output shape.

### timeline — u1 (grove fetches anthropic key)

aws.params behaves EXACTLY like every other vault: `unlock` pulls the value into the daemon,
`get` reads the daemon. the only special trait — `unlock` needs no human, because the ambient
IAM identity is the unlock.

```
grove boots
  ├─ rhx keyrack unlock --env prod          # no human prompt — the IAM identity IS the unlock
  │    ├─ host manifest: key → vault=aws.params, exid=<computed or explicit>, maxDuration=…
  │    ├─ build ContextAwsApi { aws: { credentials: { account, region }, … } }
  │    │    (AUTH is ambient — never passed; REGION is NOT ambient — keyrack supplies it)
  │    ├─ declastruct-aws → sdkSsm.getOneParameter({ name: exid, withDecryption: true })
  │    │    └─ GetParameterCommand; SSMClient built with region only → default cred
  │    │       chain (IMDS instance role) supplies auth + KMS decrypt
  │    ├─ assert type === 'SecureString' (fail loud on a plain String)
  │    └─ push the value into the daemon, held per maxDuration
  │
  └─ rhx keyrack get --key ANTHROPIC_API_KEY --env prod --value
       └─ read from the daemon (NEVER the vault) → emit KeyrackKeyGrant → sk-ant-…
```

the get path never touches the vault — the extant invariant holds. all AWS i/o happens on
`unlock`, exactly as os.secure decrypts on unlock and the daemon then serves get.

## the declastruct-aws requirement — how it's satisfied

`declastruct-aws` is already the org's declarative AWS surface (a local repo; sibling of
`declastruct-github`, which keyrack already depends on). requiring it keeps keyrack's AWS
integration on one tested, org-owned seam rather than a hand-rolled SDK call.

**two directions, two seams.**

| keyrack direction | declastruct-aws seam | why |
|---|---|---|
| **read** (unlock: pull value → daemon) | `sdkSsm.getOneParameter({ name, withDecryption })` | issues `GetParameterCommand WithDecryption: true`, returns `{ name, value, type, … }` — **the value**. the DAO's `get` will NOT serve this (see below) |
| **write** (set persist, owned-source mechs only) | `setSsmParameterSecure` (the DAO's `set` / domain op) | writes a `SecureString` value into SSM — exactly what persisting a github-app blob needs |

**the DAO's GET is the wrong seam for read** — `getOneSsmParameterSecure` reads metadata
only (DescribeParameters + ListTagsForResource); `value` is `@writeonly`, by deliberate
zero-attack-surface design. so keyrack's read goes through the raw `sdkSsm.getOneParameter`
communicator (an explicit "raw i/o communicator" the package publishes for reuse), while its
persist goes through `setSsmParameterSecure` (the DAO's write — precisely its purpose). the
DAO's *reconcile-read* is the only piece we skip.

**why this is the right requirement, not a workaround:**

- `getOneParameter` already builds the `SSMClient` with region only, so the ambient
  credential chain (IMDS/SSO/profile) supplies auth — exactly the "identity IS the unlock"
  posture the wish wants, with zero delivered secrets.
- `@aws-sdk/client-ssm` arrives transitively via `declastruct-aws`; keyrack does not add a
  raw AWS SDK dependency of its own.
- one AWS-SDK integration surface for the org, already tested, already handling
  `ParameterNotFound` → `null`.

**how it's declared: optional peer + lazy import.**

- `package.json` declares `declastruct-aws` in `peerDependencies` and marks it
  `peerDependenciesMeta: { "declastruct-aws": { "optional": true } }`, so a plain
  `rhachet` install does NOT pull the AWS SDK. a user opts in only when they configure an
  aws-backed vault (`pnpm add declastruct-aws`).
- the adapter loads it via a lazy `await import('declastruct-aws')` inside its read path
  (invoked by `unlock`), NOT a top-level import — so merely importing keyrack never
  force-loads the AWS SDK, and the cost is paid only on an actual unlock.
- when the peer is absent and an aws.params key is unlocked, the adapter fails loud and
  names the fix (`rule.require.errors-name-the-fix`): "aws.params needs declastruct-aws —
  run `pnpm add declastruct-aws`", never a raw module-not-found.
- **dual-runtime caveat (q7):** rhachet ships both a `tsx` jit path and a bun-compiled
  binary. per `bin.dispatcher.pattern`, the bun binary cannot resolve target-repo
  node_modules — so a lazy-imported optional peer likely works on the jit path but not from
  the compiled binary. the blueprint must settle whether aws.params is jit-path-only, or
  the peer is bundled, or another seam is used.

## mental model

### how a user describes it to a friend

> "instead of copying the password onto the server, i tell keyrack the *name* of the
> parameter in AWS. the server proves who it is to AWS — with the badge it already wears —
> and AWS decrypts the parameter back to it. i never put a secret on the box."

### analogies

- **a numbered locker, not a copied key.** keyrack holds the *locker number* (the parameter
  path), not the contents. your AWS identity is the attendant who checks your badge at the
  locker.
- closest sibling in the codebase: **1password `PERMANENT_VIA_REFERENCE`** — `exid` is an
  `op://vault/item/field` pointer and `get` reads it live. `aws.params` is the same
  reference shape with SSM Parameter Store as the backing store.

### their terms vs our terms

| user says | we say |
|---|---|
| "the server's identity" | IAM instance role via IMDS / the default AWS credential chain |
| "where the secret lives" | `exid` = the SSM parameter name/path |
| "look it up" | `sdkSsm.getOneParameter({ name, withDecryption: true })` |
| "it's always unlocked" | `unlock` runs but needs no human — the ambient IAM identity is the unlock; the value then lives in the daemon, and `get` reads it like any other cred |

## evaluation

### how well it solves the goals

- **breaks the bootstrap circle** (the wish's core goal): the grove needs zero delivered
  secrets — the one credential it already has (the role) is the root of trust. ✅
- **unattended operation**: no unlock prompt, so a headless box works by construction. ✅
- **least-privilege blast radius**: a compromised grove yields a live read of referenced
  parameters scoped to its role, revocable centrally by role detachment — never a master
  key at rest. ✅

### pros

- no new output contract — reuses `KeyrackKeyGrant`, `keyrack get`, `keyrack source`
- no secret stored in keyrack — reference-only, so none to encrypt, rotate, or leak on-box
- rides the extant vault-adapter pattern — a new adapter, not a new subsystem
- rides `declastruct-aws`'s tested `sdkSsm` communicator — one org-owned AWS surface
- SSM standard params are materially cheaper than Secrets Manager at low volume

### cons / tradeoffs

- **`unlock` does a live AWS round-trip** — the AWS API call + KMS decrypt happen on
  `unlock`, not on `get`; `get` stays a fast daemon read. latency + AWS availability matter
  at unlock, amortized across the session per `maxDuration`.
- **region is not ambient, and not encoded in a parameter path** (unlike an ARN) —
  `getOneParameter` takes region explicitly from `context`, NOT from the SDK's ambient
  region chain, so keyrack MUST source and supply region itself. a bare grove that carries
  only an instance role may have no `AWS_REGION` set; region needs a definite source (q5).
- **`ContextAwsApi` is heavier than the read needs** — its type requires cache dirs for
  VPC/SSH tunnels that `getOneParameter` never touches; keyrack must supply filler values.
- **IAM + KMS policy is out-of-band** — the box's role must be granted `ssm:GetParameter`
  AND `kms:Decrypt` on the key; keyrack cannot grant that. a gap surfaces as AccessDenied.

### edgecases & pit-of-success

| # | edgecase | pit-of-success behavior |
|---|---|---|
| e1 | `--org @all` key, no IMDS (not on an EC2 box) | fail loud: "no ambient grove identity — run on a box with an instance role, or re-set under a specific --org", not a silent empty value |
| e1b | specific-org key, no `AWS_PROFILE` declared for that org in `.agent/keyrack.yml` | fail loud + guide: declare the org's `AWS_PROFILE`, or use `--org @all`; never fall back to IMDS/ambient |
| e2 | role lacks `ssm:GetParameter` (AccessDenied) | surface AccessDenied with the param path + role, name the IAM fix |
| e3 | role has GetParameter but lacks `kms:Decrypt` | distinct AccessDenied — name the KMS-grant fix specifically, not a generic denial |
| e4 | `exid` not a valid SSM name/path | constraint error at `set` (fail before storing a broken reference) and at `get` |
| e5 | parameter absent (`ParameterNotFound`) | `getOneParameter` returns null → `absent` status with a `set`/create-param fix |
| e6 | parameter is type `String`, not `SecureString` | assert `type === 'SecureString'`, fail loud — never emit a plaintext String as a secret |
| e7 | region not derivable from ambient config or meta | fail loud naming that region must come from AWS config or the key's meta |
| e8 | parameter rotated in AWS between fetches | daemon cache honors `maxDuration`; a fetch after TTL sees the rotated value |
| e9 | transient SSM 5xx / throttle | fail loud (retry policy TBD in blueprint), never emit stale-past-TTL as if fresh |
| e10 | value present but empty string | decide reject-vs-allow in blueprint; never silently emit `""` as a valid grant |

## open questions & assumptions

### assumptions made

- **a1** — the AWS identity is chosen by the `--org` scope hardcut, NOT a blind default chain:
  `--org @all` → IMDS only (the grove's instance role); a specific org → that org's
  `AWS_PROFILE` from the tree's `.agent/keyrack.yml`, failfast if absent, never ambient SSO. see
  the "org-scope identity hardcut" section + `define.keyrack-org-scope.grove-vs-tree.md`. keyrack
  supplies the chosen identity to declastruct's SSMClient (built with region only) via the
  environment — a profile's exported creds, or bare IMDS for `@all`.
- **a2** — `aws.params` is a **read-by-reference** vault: `keyrack set` stores only the
  parameter path in `exid`; the value never enters keyrack. mirrors 1password
  `PERMANENT_VIA_REFERENCE`.
- **a3** — `set` IS in-scope and central (wisher-confirmed). `set` registers the
  host-manifest entry + autocomputes the path. it WRITES a value into SSM only for an
  owned-source mech (`EPHEMERAL_VIA_GITHUB_APP`, via declastruct `setSsmParameterSecure`);
  for `PERMANENT_VIA_REFERENCE` it only points at a param placed out-of-band. mirrors
  `1password`. the route covers set → unlock → get.
- **a4** — requiring `declastruct-aws` is satisfied via its `sdkSsm.getOneParameter`
  communicator; the write-only `DeclaredAwsSsmParameterSecureDao` is deliberately NOT used.
- **a5** — `declastruct-aws` is an **optional peer** (not a hard dependency), lazy-imported,
  so non-aws users pay no AWS SDK weight; absence fails loud with a fix hint.

### open questions (for the wisher / blueprint)

- **q1 — the get-path fulcrum. [answered — wisher chose (B)]** the wisher settled this: the
  get path STILL never touches the vault. `unlock` pulls the value into the daemon (via the
  ambient IAM identity, no human prompt), and `get` reads the daemon — exactly as every
  other vault behaves. this preserves the in-code invariant (`getKeyrackKeyGrant.ts:21`) and
  removes the awkwardness the first draft carried.
- **q2 — daemon caching semantics. [answered — best-guess: cache under maxDuration]** cache the fetched value under `maxDuration`, or
  re-fetch every get? *best guess: cache under maxDuration* (the wish keeps `--max-duration`).
- **q3 — is `set` in-scope for this route. [answered — YES, and it is the most important part]**
  the wisher settled it: `set` (register + autocompute) is in-scope and the crux. `set`
  always registers the host-manifest entry (vault + SSM path). whether it WRITES a value into
  SSM depends on the mech (mirrors `1password`): `PERMANENT_VIA_REFERENCE` points at a param
  placed out-of-band (no write); `EPHEMERAL_VIA_GITHUB_APP` persists the app blob into SSM on
  set (via declastruct `setSsmParameterSecure`), just as `os.secure` persists locally. the
  route covers set → unlock → get.
- **q4 — mechanism. [answered — reuse `PERMANENT_VIA_REFERENCE`]** verified in code:
  `PERMANENT_VIA_REFERENCE` maps to `mechAdapterReplica` (a passthrough), documented as
  "1password: passthrough, exid is fetched on unlock" (`genContextKeyrackGrantGet.ts:56`) —
  precisely the aws.params flow (external pointer, fetched on unlock, value IS the secret).
  the mech encodes the TRANSLATION method (reference = pointer-to-external-vault), identical
  for 1password and SSM; only the VAULT differs. so aws.params reuses
  `PERMANENT_VIA_REFERENCE` and lists it in `mechs.supported`. a new `PERMANENT_VIA_AWS_PARAM`
  would map to the same passthrough — a redundant name with no distinct logic.
- **q5 — region source (sharper than it first looks). [answered — best-guess; confirm in research]** `getOneParameter` passes region
  explicitly from `context`, so it does NOT auto-derive region the way the SDK auto-derives
  credentials. keyrack must source region itself — from `AWS_REGION`/profile, from key
  `meta`, or a `--region` flag — and a bare grove with only an instance role may have none
  set. *best guess: read `AWS_REGION`/profile, overridable via key `meta`; fail loud if
  absent.* the asymmetry (auth ambient, region not) must be explicit in the blueprint.
- **q6 — how keyrack constructs `ContextAwsApi`. [research]** it needs `account`, `region`,
  and (unused here) tunnel cache dirs. what supplies `account`, and can the cache dirs be
  filler? answerable by a read of how `declastruct-aws` callers build the context.
- **q7 — optional-peer access across rhachet's dual runtime (a REQUIREMENTS TENSION). [research → then wisher if bun]** two
  requirements may collide: (a) `declastruct-aws` as an **optional lazy peer** (to keep the
  core lean), and (b) the vault must work **unattended on a grove** (the whole point). the
  bun-compiled binary cannot reach target-repo node_modules (`bin.dispatcher.pattern`), so a
  lazy optional peer loads on the `tsx` jit path but likely NOT from the bun binary. **so the
  severity turns on one unverified fact: does `rhx keyrack get` run via jit or the bun
  binary on a grove?** if jit → the tension dissolves. if bun → the optional-peer requirement
  defeats the grove use case, and we must bundle, or make the peer non-optional for aws
  builds, or use another seam. *no best guess — the blueprint MUST verify keyrack's runtime
  path first; that fact decides whether (a) and (b) can both hold.*
- **q8 — the autocompute path template. [answered]** the wisher set it:
  `/keyrack/infra/vault/aws.params/{owner}/{org}/{env}/{key}`
  (e.g. `/keyrack/infra/vault/aws.params/mechanic/ehmpathy/prod/ANTHROPIC_API_KEY`). **owner
  is ALWAYS in the param name — a mandatory segment, never omitted.** so `--owner` must be
  known at `set` time (supplied or defaulted to the caller's identity); an absent owner is a
  fail-loud, not a skipped segment. `vault/aws.params` is a hierarchy segment (not
  `vault=aws.params`) so every char stays within SSM's allowed set `[a-zA-Z0-9_.-/]` — the
  `=` form would be rejected. this template is a stable contract the value-writer
  (out-of-band) must match; the blueprint should treat it as versioned so a later change does
  not strand prior params.

## what is awkward?

> note: the wisher's (B) decision — get stays vault-free, unlock pulls into the daemon —
> DISSOLVED the two biggest awkwardnesses the first draft carried (get touching the vault;
> unlock as a no-op). aws.params now aligns exactly with every extant vault. what remains:

- **we use two different declastruct-aws seams for one vault.** persist goes through the DAO's
  write (`setSsmParameterSecure`, its intended purpose), but read goes through the raw
  `sdkSsm.getOneParameter` communicator — because the DAO's *get* is a metadata-only
  reconcile-read that never returns the value (zero-attack-surface by design). so the vault
  straddles the DAO (for write) and the raw sdk (for read); coherent once you see why, but it
  warrants a clear note so a reviewer does not expect one uniform seam.
- **`ContextAwsApi` is heavier than the read needs.** it demands `account` and tunnel cache
  dirs that `getOneParameter` never reads; keyrack must supply filler. a forced fit against a
  context shaped for declastruct's broader surface.
- **region is not ambient the way auth is.** `getOneParameter` takes region explicitly, so a
  bare grove with only an instance role may have no region source (q5). the "identity is the
  unlock" line holds for auth but NOT for region — an asymmetry a reader must hold in mind.
- **the autocompute template becomes a hidden contract.** once `--exid` defaults to a computed
  path, that template silently binds the read to wherever the value was written; a later
  change to the template would strand prior params. the convenience (q8) carries a durability
  cost — the blueprint must pin a stable, versioned convention.

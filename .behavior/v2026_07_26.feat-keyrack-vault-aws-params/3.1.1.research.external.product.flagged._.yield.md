- CONVERGENCE: sources [1], [2], [5], [6], [7] all agree — Standard tier caps a value at 4 KB (4096 bytes) and Advanced at 8 KB. Five independent sources concur.
- CONVERGENCE: sources [1] and [5] independently state the dual-grant rule — `kms:Decrypt` is a distinct grant on top of `ssm:GetParameter`. The official IAM example policy in [1] shows `ssm:GetParameter*` and `kms:Decrypt` as two separate statement blocks, which is the same claim as the practitioner blog [5].
- CONFLICT: none of the sources contradict on the charset. [2] and [3] both list `a-zA-Z0-9_.-` plus `/` for hierarchy. The `=` character does not appear in any allowed-character list; therefore `=` is barred. No source claims `=` is allowed, so there is no cross-source conflict — only an absence that settles the question negatively.

### key claims

- [FACT] `GetParameter` with `WithDecryption: true` makes Parameter Store call KMS `Decrypt` on your behalf and return the plaintext value. [1][5]
- [FACT] To read a SecureString you need two distinct grants: `ssm:GetParameter` (SSM API) AND `kms:Decrypt` (on the key). [1][5]
- [FACT] Standard tier value cap = 4 KB / 4096 bytes; Advanced tier value cap = 8 KB. [1][2][6]
- [FACT] Parameter name charset is `a-zA-Z0-9_.-` plus `/` for hierarchy; spaces barred; `aws`/`ssm` prefixes barred. [2][3]
- [FACT] The `=` character is NOT in the allowed-character set, so it is barred in parameter names. [2][3]
- [FACT] A SecureString requires a KMS key (`KeyId`); if omitted, the account default `aws/ssm` AWS-managed key applies. [1][2]
- [SUMP] A GitHub App private-key PEM (a 2048-bit RSA PEM is on the order of ~1.7 KB, a 4096-bit ~3.2 KB) fits inside the 4 KB Standard cap; a large JSON blob that bundles multiple keys could threaten the 4 KB cap and force Advanced. See synthesis.
- [KHUE] Does the vault store the raw PEM alone, or a JSON envelope (PEM + app id + install id + metadata)? The envelope form pushes closer to the 4 KB edge and merits a measure before we commit to Standard tier.

### convergence + conflict

- CONVERGENCE (credentials): sources [1], [4], [5], [7], [8] all agree that EC2 role credentials are delivered over IMDSv2 with zero secrets stored on the box, IMDSv2 is the default session-token flow, and the SDK default credential chain picks these up automatically. Five-plus independent sources concur.
- CONVERGENCE (region NOT auto-derived in JS v3): sources [2] and [3] agree — [2]'s official precedence list has no IMDS step, and [3] is an open feature request that exists precisely because JS v3 does NOT fetch region from IMDS. Two independent official/practitioner sources concur.
- CONFLICT (cross-SDK region behavior): source [3] states OTHER SDK languages (e.g. Java) DO derive region from IMDS, while source [2] shows the JavaScript v3 SDK does NOT. This is a real cross-SDK divergence, not a contradiction within one SDK — [3] explicitly frames JS v3 as the outlier. So [2]/[3] together settle it: region auto-derive from IMDS is language-SDK-dependent and is absent in JS v3.

### key claims

- [FACT] The AWS SDK default credential provider chain obtains EC2 instance-role credentials over IMDS (IMDSv2 by default) with no delivered/stored secrets on the box. [1][4][8]
- [FACT] IMDSv2 needs a PUT to `/latest/api/token` to mint a session token, then that token on every metadata GET. [5][6]
- [FACT] EC2 role credentials fetched via IMDS are temporary and auto-refreshed by the SDK provider. [4][8]
- [FACT] The AWS SDK for JavaScript v3 does NOT select a region by default and its region precedence is: constructor arg > `AWS_REGION` env var > shared `config` file. There is NO IMDS step. [2]
- [FACT] Region auto-derive from IMDS is weaker/less automatic than credential auto-derive in JS v3 specifically; it must be supplied explicitly. [2][3]
- [SUMP] Some SDK languages (e.g. Java) auto-derive region from IMDS; do not assume our JS/TS runtime shares that behavior. [3]
- [KHUE] On a bare EC2 box that runs our JS/TS vault client, will `AWS_REGION` be set? If not, region must come from an explicit constructor arg, an env var we set at launch, or a manual IMDS region-endpoint call — because the JS v3 default chain will not derive it for us. This is the load-bearing open question for topic 2.
- [OPIN] Treat region as a required explicit config input for the vault client rather than trust auto-derive; this avoids a class of "works on my Lambda, fails on bare EC2" surprises.

### key claims

- [FACT] A GitHub App installation access token expires after 1 hour. [1][3][6][7][8]

- [OPIN] The 1-hour token TTL is a strong argument to mint installation tokens on demand inside the vault and never persist them, so a leaked derived token self-expires.

## synthesis — the three flags mapped back

### topic 1 verdict — does the GitHub App blob fit SSM Standard tier?
Standard tier caps a SecureString value at 4 KB / 4096 bytes; Advanced caps at 8 KB [1][2]. A single RSA private-key PEM is well under 4 KB (2048-bit ~1.7 KB, 4096-bit ~3.2 KB), so a lone PEM fits Standard comfortably. VERDICT: a raw PEM fits Standard tier. CAVEAT: if the vault stores a JSON envelope that bundles the PEM plus app id, installation id, and other metadata, a 4096-bit key envelope can approach the 4 KB edge — measure the actual serialized blob; if it exceeds 4096 bytes you MUST use Advanced tier (which also switches to envelope encryption via the AWS Encryption SDK). Also note: parameter names may use only `a-zA-Z0-9_.-` and `/`; the `=` character is barred [2][3] — so any key-label scheme must avoid `=`. To read the SecureString needs BOTH `ssm:GetParameter` and `kms:Decrypt` as two separate grants [1][5].

### topic 2 verdict — is region auto-derived on a bare EC2 box like credentials are?
NO — not in the AWS SDK for JavaScript v3. Credentials ARE auto-derived from the EC2 instance role over IMDSv2 by the default credential chain with zero stored secrets [1][4]. Region is NOT: the JS v3 region precedence is constructor arg > `AWS_REGION` env var > shared `config` file, with NO IMDS step [2]. An open feature request [3] exists precisely because JS v3 (unlike, e.g., Java) does not fetch region from IMDS. So on a bare EC2 box, region auto-derive is strictly weaker than credential auto-derive and must be supplied explicitly (constructor arg, `AWS_REGION`, config file, or a manual IMDS region-endpoint call). Treat region as a required explicit input to the vault client.

### topic 3 verdict — installation token TTL and the security property
The installation access token TTL is 1 hour, confirmed by the official GitHub doc plus six converging sources [1][3][6][7][8]; one outlier blog claims 8 hours [4] and is outweighed. The mint chain is app private key -> RS256-signed JWT (<=10 min) -> exchanged for the 1-hour installation token [1][2]. Security property holds: a compromised box with a derived installation token loses at most ~1 hour of scoped access, not the master app private key [3]. This dovetails with topic 1 — if the private key itself lives in an SSM SecureString, the key's blast radius equals the SecureString read-grant, so guard that grant tightly; the 1-hour property only bounds the derived token.

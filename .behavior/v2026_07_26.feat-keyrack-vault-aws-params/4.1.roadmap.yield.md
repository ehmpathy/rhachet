# 4.1.roadmap — keyrack `aws.params` vault (execution plan)

> a checklist-style, dependency-ordered execution plan for the approved blueprint
> (`3.3.1.blueprint.product.yield.md`). each phase declares: what it depends on, which briefs to
> read first, the build checklist, the behavioral acceptance criteria (bound to the blueprint's
> `c#` cases and the criteria's `uc#` usecases), and the exact verification command to run before
> the phase is marked done.
>
> the blueprint is the contract. this roadmap sequences it so each phase lands on a green test
> gate before the next begins — no phase starts until its dependency's verification passes.

---

## how to drive this roadmap

- **strict dependency order.** phases 0→9 are a chain; a later phase imports earlier phases' units,
  so do NOT start a phase until its dependency's verification is green.
- **test-first per unit.** each unit ships with its test in the same phase (unit for transformers,
  integration for communicators/orchestrators, acceptance for the CLI contract). a unit without its
  test is not done — `philosophy.verification-strictness` (zero tolerance).
- **read the briefs listed at each phase BEFORE writing that phase's code.** they are the durable
  rules the reviewers already hold you to.
- **condense the blueprint's sketch comments.** the §1–§7 sketches carry long review-rationale
  prose; ship the terse repo discipline instead — `.what`/`.why` at 1–3 lines, no round-IDs, no
  reviewer citations (`rule.require.what-why-headers`, `rule.require.timeless-comments`). this is a
  standing instruction for every phase that writes code.
- **verification command legend:** `rhx git.repo.test --what <unit|integration|acceptance> --scope <path|name> --mode apply`. run the narrow scope first, then widen to a full `--what` pass before the phase's `--as arrived`.

## phase 6 — shared-driver changes: G5 fault isolation + G6/G7b residual

**depends on:** phase 5. **this phase touches shared, all-7-vault infra — highest care.**

**read first:**
- `rule.prefer.most-common-denominator`, `rule.forbid.scope-leaks` (architect) — the cross-vault blast radius
- `3.1.3.research.internal.product.code.prod._.yield.md` — `unlockKeyrackKeys`, `emitKeyrackKeyBranch`, `setKeyrackKeyHost`, `delKeyrackKeyHost`
- `rule.require.exit-code-semantics` — the 0/1/2 convention for the G5 exit code

**⭐ RECOMMENDED REFINEMENT (r11 i024 — adopt if execution confirms it holds):** the blueprint
widens the `KeyrackHostVaultAdapter` `del`/`set` contract across all 7 adapters so aws.params can
report a residual. r11's final review argues this widening is UNNECESSARY: `isKeyrackAwsParamMechOwnsSecret`/
`asKeyrackAwsParamResidual` are pure functions of `(mech, exid)`, and `delKeyrackKeyHost`/
`setKeyrackKeyHost` ALREADY look up the manifest entry (`{mech, exid}`) before they mutate — so the
residual is computable in the ORCHESTRATOR directly, with the predicate + helper LIFTED to shared
keyrack infra (mech-level, vault-agnostic). adopting it:
- removes the 7-adapter contract change (no `| void`, no `result?.residual` optional-chain burden)
- dissolves the aws.params-only narrowing (the check is vault-agnostic for free — every manifest entry carries `mech`)
- shrinks the "extract G5+G6/G7b" open item to just G5
**execution decision:** confirm `delKeyrackKeyHost`/`setKeyrackKeyHost` truly hold `{mech, exid}` at the
call site (prod research [26][27] indicate they do). IF confirmed → take the orchestrator-level path
(lift `isKeyrackMechOwnsSecret`/`asKeyrackAwsParamResidual` to shared infra, call from the two host
orchestrators, DROP the adapter-contract widening). IF a snag surfaces → fall back to the blueprint's
adapter-contract path. either way the observable behavior (c46/c48/c52/c57 + c59) is identical; this
is an internal-shape choice, so the acceptance cases are unchanged.

**build checklist:**
- [ ] G5: `unlockKeyrackKeys` — try/catch each slug's `unlock()`+`get()`; widen `keysOmitted` to carry `reason: …|'errored'; cause?`; the loop CONTINUES past a live fault
- [ ] G5: `emitKeyrackKeyBranch` — add the `{ type: 'errored'; slug; tip }` arm + a render branch (WITHOUT it the `never` exhaustiveness throw crashes unlock)
- [ ] G6/G7b residual (adapter-contract OR orchestrator-level per the refinement above): `setKeyrackKeyHost` threads prior `{mech, exid}` + surfaces `residual`; `delKeyrackKeyHost` passes `mech` + surfaces `residual`; both thread it to the CLI

**acceptance criteria:**
- c45 (mixed-vault batch: healthy 1password + throttled aws.params → per-key errored, batch survives, exit non-zero)
- c56 (non-aws vault throw → isolated, not batch-abort)
- c60 (all-succeeded + all-absent-benign unlock → exit 0)
- c59 (1password/os.secure set+re-set+del post-change → plain "removed", `result?.residual` handles undefined/void)
- c27 (del residual for owned mech + stored-mech guard), c46 (del residual CLI signal)

**verification:** `rhx git.repo.test --what integration --scope 'name://unlockKeyrackKeys' --mode apply` + `--scope 'name://delKeyrackKeyHost'` + `--scope 'name://setKeyrackKeyHost'` (green) + a FULL `rhx git.repo.test --what integration --mode apply` to prove no other vault regressed.

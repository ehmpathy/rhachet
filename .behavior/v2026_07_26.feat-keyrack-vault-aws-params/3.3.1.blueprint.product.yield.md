## summary

we add one new vault kind, `aws.params`, to keyrack. it behaves exactly as every extant
vault:

- **set** registers the host-manifest entry (vault + autocomputed SSM path in `exid`). for an
  owned-source mech (`EPHEMERAL_VIA_GITHUB_APP`) it also persists the credential blob into SSM
  via declastruct `setSsmParameterSecure`, mirrors how `os.secure` persists locally and
  `1password` writes via `op item edit`. for `PERMANENT_VIA_REFERENCE` it writes no value —
  it points at a param placed out-of-band.
- **unlock** pulls the SSM value into the daemon via `declastruct-aws`'s
  `sdkSsm.getOneParameter({ name, withDecryption: true })`. auth is ambient (the IAM
  identity IS the unlock — no human prompt); region is supplied by keyrack from key meta.
- **get** reads the daemon, never the vault — the extant invariant
  (`getKeyrackKeyGrant.ts:21`) holds with zero change.

the AWS SDK weight arrives only for users who opt in: `declastruct-aws` is an **optional peer
dependency**, lazy-imported inside the adapter's unlock/set paths. its absence fails loud with
a one-command fix hint.

no new output contract, no new mech, no new CLI flag. the surface is a new adapter plus its
support transformer and communicator, wired into the extant vault-adapter map.

## key resolutions (from vision open questions + criteria gaps)

| id | question | outcome |
|----|----------|---------|
| q5 | region source (auth ambient, region NOT) | region rides in the key's `meta.region`. set requires it (flag or default from `AWS_REGION`/profile at set time); unlock reads `meta.region`. absent at unlock → fail loud (uc15). external research confirmed SDK v3 does NOT auto-derive region from IMDS. **reader-clarity note:** the vision's headline "the identity IS the unlock" holds for AUTH ONLY — auth is ambient (IMDS), region is NOT. a bare EC2 grove usually has no `AWS_REGION` exported, so region MUST be captured at set-time into `meta.region` (or supplied via `AWS_REGION`); it is the one input the ambient identity does not carry. this asymmetry is deliberate and load-bearing — do not read "always unlocked" to mean "needs no input", it needs a region. |
| q8 | autocompute path charset + VERSION marker | template `/keyrack/infra/vault/aws.params/v1/{owner}/{org}/{env}/{key}`. `vault/aws.params` is a hierarchy segment (not `vault=aws.params`) so every char stays within SSM's allowed `[a-zA-Z0-9_.-/]`. owner is a mandatory segment. **the `/v1/` segment is the VERSION MARKER vision q8 explicitly required** ("treat it as versioned so a later change does not strand prior params", r11 i021 blocker 3): without it a future template change would silently orphan every extant param (a `get` on the new template reads "absent", indistinguishable from a never-registered key). with `v1`, a future change is ADDITIVE (`/v2/`) not destructive — v1 params stay readable, a migration reads v1 + writes v2 deliberately. `v1` is a FIXED literal in `asKeyrackAwsParamName` (§1), not a caller input, so every autocomputed name carries it uniformly and the out-of-band value-writer matches the versioned path. bound by c20 (the version segment is in the asserted template shape). |
| G1 | github-app + explicit `--exid` | `--exid` overrides the computed path for BOTH mechs. for `EPHEMERAL_VIA_GITHUB_APP` the blob is persisted AT the explicit path. the override is not reference-only. |
| G2 | `--max-duration` vs github-app token TTL | `--max-duration` bounds the daemon cache of whatever unlock placed. for the github-app mech, unlock places a freshly minted ~1h token; the effective lifetime is `min(max-duration, token TTL)`. a re-unlock past the window re-mints. **repeat-unlock-within-TTL is idempotent (r12 i016 #7):** unlock first checks `adapter.isUnlocked` (unlockKeyrackKeys.ts:203) and SKIPS the SSM fetch/mint when the daemon still holds a live grant — so a second `keyrack unlock` inside the window does NO new SSM read and mints NO new token; it converges to the extant daemon state (rule.require.idempotent-operations). the re-mint happens ONLY after the TTL lapses, exactly as the extant vaults behave. |
| G3 | unlock gate precedence order | fail-fast chain: (0) exid name legal → (1) peer absent → (2) no AWS identity → (3) region absent → (4) read-denied → (5) param absent → (6) not SecureString → (6b) empty value → (7) decrypt-denied. first unmet gate decides the outcome. the chain spans the `unlock()`→`get()` sequence (unlockKeyrackKeys calls unlock THEN get, prod [35]). the three PRE-SSM gates (0 → 1 → 3, in order) live in ONE shared helper, `getOneKeyrackAwsParamReadyContext`, which BOTH `unlock()` and `get()` call as their first step — so gate 0 is enforced for both by construction, not duplicated at two call sites (r11 nitpick 1). because the helper runs gate 0 FIRST, a malformed exid fails loud ahead of an absent-region error (gate 3), and because there is only ONE copy of the three gates the two call sites cannot drift. `get()` then continues with the AWS-side gates 2/4/5/6/6b/7. case c35 asserts the precedence on the unlock→get path (a malformed `--exid` AND an absent region, two gates unmet at once → the gate-0 name error surfaces first) — now regression coverage on top of the structural guarantee, so a future reorder trips a test rather than a silent drift. |
| G4 | `--owner` supplies the mandatory owner segment | owner is a MANDATORY segment of the path. it is supplied via `--owner` and threaded to the adapter as `context.owner`; the adapter reads `context.owner` and fails loud (`ConstraintError`) if it is absent — never a skipped segment (c21). **`--owner` is an EXTANT flag, so NO new CLI flag is added:** `keyrack set` already declares `--owner <owner>` and its `--for` alias (invokeKeyrack.ts:728-729) and resolves the value via `deriveOwner` (invokeKeyrack.ts:760, with a fallback to the top-level `keyrack --owner`) into the set flow that populates `context.owner` — so the mandatory-owner path is implementable on today's surface. the prod-research flag enumeration (prod [31], which lists `--key --vault --exid --env --org --max-duration --at --prikey`) OMITTED `--owner` from its list; that enumeration is incomplete, not the flag — verified directly at invokeKeyrack.ts:728-729,760. the adapter itself does NO defaulting: it does not invent an owner from a caller identity. whether the CLI layer defaults an omitted `--owner` to the caller's identity is a set-flow concern OUTSIDE this adapter's scope and is not claimed here (no such upstream default is cited in the prod research, so the blueprint does not assert one). the positive path — `context.owner` present → the computed path carries that exact owner segment — is bound by c37. |
| G8 | which AWS identity unlocks (the org-scope hardcut) | **the AWS identity is a HARDCUT on the `--org` scope — not a default-chain grab, not an inference waterfall, not a picker, no `--account`, no `meta.account`** (the general keyrack invariant, `define.keyrack-org-scope.grove-vs-tree.md`, applied to aws.params). `--org @all` (grove-wide) → **IMDS ONLY** — the EC2 instance role; keyrack builds the AWS env with NO profile and NO ambient SSO, lets the default chain derive the instance role, and failfasts if IMDS is absent (b2/m2). a **specific org** (tree-wide) → **that org's `AWS_PROFILE`, sourced from the keyrack itself**: the profile name is the `exid` of the peer host-manifest entry `{org}.{env}.AWS_PROFILE` (an `aws.config`-vault key the tree already manages). `unlockKeyrackKeys` reads that peer entry inline from the already-loaded `hostManifest.hosts` and threads its exid as the additive `orgAwsProfile` input into `adapter.get()`. the adapter maps `orgAwsProfile` → a scoped `process.env.AWS_PROFILE` overlay for the one SSM read (set in `getOneKeyrackAwsParam`, restored in finally), so declastruct's SSMClient + the AWS SDK default chain derive that profile's creds — NO shell to `export-credentials` in the prod path. if the peer `AWS_PROFILE` entry is absent for that org → failfast + guide (b4/m4), NEVER a fall back to IMDS or a cached SSO session. **never ambient SSO** — SSO is reachable only when the org's peer `AWS_PROFILE` names an SSO profile (a deliberate designation). the decision is a PURE transformer `asKeyrackAwsParamIdentity({ org, profileForOrg }) → { source: 'imds' } \| { source: 'profile', profile }` (`@all` → imds; a specific org → the threaded profile, failfast if absent), fed by a second PURE transformer `asKeyrackAwsParamCredsEnv({ identity }) → { AWS_PROFILE: string | undefined }`. **mechanism (1) — peer-key via the batch — was chosen over a new manifest field (2), which the wisher judged a domain smell**: the org's AWS_PROFILE already lives in the keyrack as its own key, so a duplicate `meta` field would be a redundant second home for one fact. the identity is NOT persisted on the aws.params key — only `region` + `exid` live in its manifest entry; identity is derived at unlock from `--org` + the peer `AWS_PROFILE` key. gate 2 ("no AWS identity") is now "the scope-chosen identity is absent": for `@all` = no IMDS (b2), for a specific org = the peer profile could not derive creds (a distinct failfast from b4's "no profile declared"). bound by c61–c67 (the org-scope matrix, below). |
| q7 | optional-peer across dual runtime | **best-guess: jit path for the peer-backed unlock/set on a grove — CONFIRMED by the pre-execution gate, not asserted as settled here.** the bun-compiled binary cannot reach target-repo node_modules (`bin.dispatcher.pattern`), so the lazy peer loads on the `tsx` jit path. best guess: the grove invokes keyrack via jit. **NO runtime-detection code exists, and none is claimed** — `getOneDeclastructAws` has ONE catch branch that emits the SAME generic peer-absent message on every runtime (`aws.params needs the declastruct-aws peer` / hint `run pnpm add declastruct-aws`); there is no `process.execPath`/argv0 branch that emits a distinct "use the jit entry" hint, so the blueprint does NOT assert one. on the bun binary the peer-import simply fails, and IF that failure is shaped like a node module-not-found it surfaces as the SAME generic peer-absent `ConstraintError`; IF bun's bundler throws a differently-shaped error it falls through to the rethrow-unchanged arm (a raw malfunction, never masked). WHICH of those two happens on a real grove — and whether the grove runtime is jit at all — is EXACTLY the q7 pre-execution gate (open items), NOT a settled fact. so c31 binds only the jit arm as a positive assertion (jit resolves the peer + unlock succeeds); the bun-binary arm asserts only that it fails loud with the generic peer-absent message (no distinct jit-entry hint claimed), and the runtime-path decision is deferred to the pre-execution gate. this row is deliberately consistent with the open-item: the design STANDS ONLY ONCE the pre-execution gate confirms jit; if it turns out bun-only, the seam is re-shaped (bundle the peer) before the adapter is written. |
| e4 | malformed `--exid` (the uc2 escape hatch) validation | an explicit `--exid` is validated by `isKeyrackAwsParamName.assure` at BOTH set and get (vision e4). a malformed name fails loud as a `ConstraintError` before any SSM call — never a raw SDK `ValidationException`. the autocomputed path is legal by construction, so only the explicit-exid arm needs the guard. bound by cases c2/c32. |
| e9 | transient SSM throttle / 5xx retry policy | v1 does NOT auto-retry (vision left it "TBD"). a throttle or 5xx error maps to a `MalfunctionError` whose hint reads "transient — retry the unlock". a deliberate decision: safe (never emit stale-past-TTL), and a bounded retry is a clean later extension (open item). bound by case c29. |
| e10 | empty-string SSM value | gate 6b: a `value === ''` fails loud (vision e10 — "never silently emit an empty value as a valid grant"). bound by case c30. |
| del | owned-secret lifecycle (v1 scope) | **WISHER DECISION (2026-07-30): `del` DESTROYS what keyrack created.** for an owned-source mech (`EPHEMERAL_VIA_GITHUB_APP`) the adapter destroys the SSM param keyrack wrote at set — via `delKeyrackAwsParam` → declastruct `delSsmParameterSecure` (idempotent + type-guarded: a no-op if absent, refuses a non-SecureString). this realizes the "keyrack destroys what it created" symmetry: a key removed from the manifest strands no secret in SSM. a REFERENCE mech points at an out-of-band value keyrack never wrote, so its del touches no remote secret (the operator's param is untouched). the destroy targets ONLY the computed-namespace name (`asKeyrackAwsParamName`), so a key set with a foreign explicit `--exid` (u4 shared/out-of-band param) resolves to a DIFFERENT name and is never destroyed. BUT the destructive mutation MUST be visible (status-feedback + safe-by-default): the adapter del RETURNS `{ destroyed: { exid } }` for the owned mech, threaded up so the CLI echoes `the SSM secret at {exid} was destroyed` — never a silent destructive delete. a reference key returns null → plain `removed`. see G6. |
| G5 | per-key fault isolation on `unlock` (shared-driver change) | aws.params is the FIRST vault whose `get()` throws on a LIVE, transient condition as a matter of course (SSM throttle/5xx, decrypt-denied, absent param) — every extant vault resolves its faults INSIDE `unlock()` (bad file, missing 1password item, expired SSO) and rarely propagates past it. so the shared batch driver `unlockKeyrackKeys` (which loops each slug calling `adapter.unlock()` then `adapter.get()` with NO try/catch, verified at unlockKeyrackKeys.ts:140-275) would let ONE flaky aws.params key hard-abort the WHOLE `keyrack unlock --env prod` batch — taking down every co-batched healthy 1password/os.secure credential, directly undercutting the vision's grove-reliability premise. FIX (in the shared driver, NOT the adapter — it is vault-agnostic and benefits every network-prone vault) — a COMPLETE render path, all four touch-points (a partial fix would crash, since the omit-render has a `never` exhaustiveness `throw`): (1) `unlockKeyrackKeys.ts:136` — widen the `keysOmitted` tuple to `{ slug; reason: 'absent'|'lost'|'remote'|'errored'; cause?: unknown }`; (2) `unlockKeyrackKeys.ts:140-275` — a try/catch around each slug's `unlock()`+`get()` that routes a caught error to `keysOmitted` with `reason: 'errored', cause` and CONTINUES the loop; (3) `emitKeyrackKeyBranch.ts:106-113` — add an `{ type: 'errored'; slug; tip }` arm to the `KeyrackKeyBranchEntry` union AND a render branch in `formatKeyrackKeyBranch` (WITHOUT it, the `never` exhaustiveness check at emitKeyrackKeyBranch.ts:88-89 THROWS at runtime — the first errored key would crash the whole `keyrack unlock`, the OPPOSITE of isolation); (4) `invokeKeyrack.ts:1218` — map the new `'errored'` reason into the branch entry with a tip that states the cause. **EXIT CODE (r11 i020 #4 — the automation hazard):** the grove use case chains `unlock && start-app`, so `keyrack unlock`'s PROCESS EXIT CODE when a key lands in `'errored'` is load-bearing — a silent exit 0 with a missing credential would let the app start credential-less. so an `'errored'` omission forces a NON-ZERO exit (per this repo's 0/1/2 convention: exit 1 = MalfunctionError-class, since a batch fault is server/transient-side), DISTINCT from the all-succeeded case (exit 0) and from an all-absent-benign case (a key legitimately not registered — exit 0, not a fault). the exit-code decision lives in the CLI unlock branch (`invokeKeyrack.ts`), which already has the omitted-reason tally: if ANY omitted key has reason `'errored'`, exit non-zero. bound by c45 (mixed-vault partial failure: a healthy 1password key + a throttled aws.params key in one `unlock --env prod` → the aws.params key omitted `errored` and rendered distinctly, the 1password key still unlocked, batch does NOT abort, the render does not throw, AND the process exits NON-ZERO so a chained `&& start-app` does not run credential-less). **SCOPE (r11 i021 #1 — a flagged fulcrum, best-guessed inline):** G5 is a CROSS-CUTTING, vault-AGNOSTIC change — it alters the shared driver's failure semantics for ALL 7 vaults (before: any vault's unlock/get throw aborted the whole batch; after: per-key isolation), qualitatively unlike G6/G7 (which only widen SHAPES with zero-blast-radius `\| void`/optional fields). aws.params is the NATURAL motivator — it is the FIRST vault whose `get()` throws on a live transient condition as a matter of course — but the fix benefits every network-prone vault. best-guess: keep it INLINE (a bare grove unlock is exactly where batch-abort would be most harmful, so the aws.params route needs it to hold its grove-reliability premise), reframed as the vault-agnostic resilience improvement it is, and LOCK the cross-vault behavior with c56 (a NON-aws vault — os.secure — that throws is now isolated, not batch-aborting, so no other vault's failure-visibility contract silently regresses). the "should G5 be extracted into its OWN prerequisite route (own vision + criteria), landed independently, with aws.params merely depending on it?" question is a SCOPE decision above this blueprint's authority — flagged for the wisher in open items; if the wisher prefers extraction, it is a CLEAN lift (G5 is already isolated in unlockKeyrackKeys/emitKeyrackKeyBranch, no aws.params coupling), so best-guessing inline now costs no teardown later. |
| G6 | `del` must make the destructive SSM delete VISIBLE for the owned mech | for `EPHEMERAL_VIA_GITHUB_APP` keyrack ITSELF wrote the app private-key blob into SSM at set, and (per the wisher decision) del DESTROYS it — so a bare `{slug} removed` would HIDE a destructive, irreversible remote mutation: the operator gets no signal that a live SSM secret was just destroyed. FIX — a COMPLETE data path, all THREE wiring points: (1) `KeyrackHostVaultAdapter.ts` — del's INPUT type carries a `mech` field (so the adapter knows the owned mech to destroy) AND its RETURN widens `void → { destroyed: { exid } } | null | void` (the `| void` arm keeps all 7 extant adapters, which return an implicit void, unedited); (2) `delKeyrackKeyHost.ts` — pass `mech: hostFound.mech` into `adapter.del`, and thread the adapter's `{ destroyed }` return up into `delKeyrackKeyHost`/`delKeyrackKey`'s own return (`{ effect; destroyed?: { exid } | null }`); (3) `invokeKeyrack.ts` del CLI branch → `asKeyrackDelReport`, when `result.destroyed` is present, renders a DISTINCT line — `{slug} removed` + `   └─ the SSM secret at {exid} was destroyed`. the adapter `del` RETURNS `{ destroyed: { exid } }` for an owned mech (the name `delKeyrackAwsParam` actually destroyed); a reference key returns null (keyrack wrote no value → destroyed no remote secret), so it keeps the plain `removed`. bound by c46 (owned-mech del → the destroyed-secret line; reference-mech del → plain removed; snapshotted both arms). |
| G7 | mech-switch on re-`set` (reference↔github-app) | c42 covers a reference re-point (same mech), c39 a github-app re-set (same mech); a re-`set` of an extant slug with a DIFFERENT `--mech` was undefined (r12 i017 #4 — a plausible path: an operator first points at an out-of-band param, later decides keyrack should own it). DEFINED behavior, via the SAME idempotent manifest upsert (setKeyrackKeyHost, prod [26]) that already overwrites the entry: (a) **reference → github-app** — the new github-app arm runs (acquire blob → write to the path → roundtrip verify), the manifest mech flips to github-app; the old reference wrote NO value, so there is NO orphan. (b) **github-app → reference** — the manifest mech flips to reference (now points at the out-of-band param), and the OLD keyrack-written blob is ORPHANED in SSM (v1 del is a no-op, so keyrack does not auto-destroy it) — the SAME deferred-cleanup class as the owned re-point orphan; the set confirmation carries a residual-secret note (the operator is TOLD a blob survives at the old path), never a silent orphan. this note is FULLY WIRED (not a bare narrative claim), a mirror of G6's three-point del pattern: (1) `KeyrackHostVaultAdapter.ts` set INPUT gains `priorMech?`/`priorExid?` and set RETURN gains `residual?: { exid } | null`; (2) `setKeyrackKeyHost.ts` — which already looks up the current manifest entry before its upsert — threads that entry's `mech`/`exid` into set as `priorMech`/`priorExid`, and threads the returned `residual` up to the CLI; (3) `invokeKeyrack.ts` set-branch prints the residual note when present (the SAME copy G6 uses for del). **the residual is computed by the ONE shared seam `asKeyrackAwsParamResidual` (§6e), NOT a per-arm check (r11 i020 blocker fix):** `set` computes it once from `(priorMech, priorExid, currentExid=exid)` before dispatch, so it covers the github-app→reference switch (c48) AND a same-mech github-app re-point to a NEW path (c52 — the case the earlier reference-arm-only check missed, which orphaned the old blob silently), while a same-path re-persist (rotation, c39) yields null. `del` (G6) routes through the SAME helper with `currentExid=null`, so a single seam answers "did we strand a keyrack-written secret?" for both operations — no duplicated mech check to drift. bound by c48 + c52. |

## domain decomposition + implementation sketches

twelve new units, each a single grain. all use `(input, context)`/`(input)`, arrow-only, inline
i/o types, and only sanctioned verbs — `del`/`get`/`set` + the `as*`/`is*` transformer prefixes
(per rule.require.get-set-gen-verbs); assertions use the `.assure` method on an `is*` type-check,
never a standalone `assure*` operation.

### 1. `asKeyrackAwsParamName` — transformer (pure)

computes the SSM path from key coordinates. the ONLY place the template lives.

```ts
/**
 * .what = derive the SSM parameter name from a key's coordinates
 * .why  = the autocompute path is a stable, versioned contract the out-of-band
 *         value-writer must match; one source of truth avoids drift
 */
export const asKeyrackAwsParamName = (input: {
  owner: string;
  org: string;
  env: string;
  key: string;
}): string => {
  // owner is mandatory (G4) — an absent segment would strand the param
  if (!input.owner)
    ConstraintError.throw('aws.params requires an owner in the param name', {
      input,
      hint: 'pass --owner so the param name is complete',
    });

  // hierarchy segments only, so every char stays within SSM's [a-zA-Z0-9_.-/] (q8). the `/v1/`
  // segment is the VERSION MARKER vision q8 required ("treat it as versioned so a later change does
  // not strand prior params") — without it, a future template change would silently orphan every
  // extant param and a `get` on the new template would read "absent", indistinguishable from a
  // never-registered key (no drift-detection possible). with `/v1/`, a future template change is
  // ADDITIVE (a `/v2/` prefix) rather than destructive: `v1` params stay readable, and a migration
  // can read v1 + write v2 deliberately. the version is a FIXED literal in this template (NOT a
  // caller input), so every autocomputed name for this blueprint's era carries `v1` uniformly; the
  // out-of-band value-writer matches the same versioned path.
  const name = `/keyrack/infra/vault/aws.params/v1/${input.owner}/${input.org}/${input.env}/${input.key}`;

  // self-validate the OUTPUT: owner/org/env/key are free-form strings from upstream, so
  // "legal by construction" is an unverified assumption — a stray char (a space, an '=') in a
  // coordinate would produce an illegal name. run the SAME gate the explicit-exid arm uses, so
  // BOTH call sites (set/get) collapse onto one validation source, not one-path-by-convention.
  return isKeyrackAwsParamName.assure(name);
};
```

- unit-tested: template shape, owner-absent throw, a stray char in a coordinate → `.assure` throw,
  charset stays legal.

### 1b. `isKeyrackAwsParamName` — type-check (pure, `withAssure`)

validates that an SSM parameter name is legal, per `rule.require.assure-via-type-checks`. the
autocomputed path is legal by construction; this guards the ONE arm that is not — an explicit
`--exid` a human typed (uc2 escape hatch, vision e4). used at set AND get, so a malformed name
fails loud as a `ConstraintError` before any SSM call, never as a raw SDK `ValidationException`.

```ts
import { withAssure } from 'type-fns';

/**
 * .what = assess whether a string is a legal SSM parameter name
 * .why  = an explicit --exid is human-typed; validate it at the boundary so a malformed name
 *         fails loud with a fix BEFORE any SSM call, not as a raw SDK ValidationException (e4)
 */
export const isKeyrackAwsParamName = withAssure(
  (value: string): value is string => {
    // SSM name rules (topic1 [2][3]): a leading '/', segments of [a-zA-Z0-9_.-], '/' separators,
    // no 'aws'/'ssm' prefix. a full-path name (with '/') must start with '/'.
    if (value.length === 0 || value.length > 2048) return false;
    if (value.includes('/') && !value.startsWith('/')) return false;
    return /^[a-zA-Z0-9_.\-/]+$/.test(value) && !/^\/?(aws|ssm)\//i.test(value);
  },
  {
    name: 'isKeyrackAwsParamName',
    // .assure throws AssureIsOfTypeRejectionError (a HelpfulError) — caught + re-thrown as a
    // ConstraintError at the call site so the human sees the fix (rule.require.failloud).
  },
);
```

- unit-tested: legal names pass; a name with `=` / a space / an `aws`-prefix / empty is rejected
  by `.assess`, and `.assure` throws on each (c32).

### 2. `getOneDeclastructAws` — communicator (lazy optional-peer loader)

isolates the lazy `import('declastruct-aws')` so both unlock and set share one fail-loud path.

```ts
/**
 * .what = load the declastruct-aws optional peer at call time
 * .why  = aws.params needs the AWS SDK only when actually used; a lazy import keeps
 *         the core lean and pays the cost only on a real unlock/set (vision a5, q7)
 */
export const getOneDeclastructAws = async (): Promise<typeof import('declastruct-aws')> => {
  try {
    return await import('declastruct-aws');
  } catch (cause) {
    // ALLOWLIST — only a module-not-found for the peer is caller-fixable (install it).
    // every OTHER error (a syntax error in the peer, a transitive-dep failure) is a real
    // malfunction: rethrow it UNCHANGED so it is never masked as "install the peer".
    // this keeps the catch a fail-loud allowlist, not a fail-hide catch-all
    // (rule.forbid.failhide; uc14).
    // narrow WITHOUT an as-cast: `'code' in cause` refines the Error to carry `code`, which we
    // then compare to the node module-not-found code — no `as` bypass (rule.forbid.as-cast).
    const peerAbsent =
      cause instanceof Error &&
      (cause.message.includes("Cannot find module 'declastruct-aws'") ||
        ('code' in cause && cause.code === 'ERR_MODULE_NOT_FOUND'));
    if (!peerAbsent) throw cause; // rethrow real malfunctions untouched

    // the one allowlisted case → name the one-command fix (uc14). the fix rides in a `hint`
    // field, the one uniform convention across every throw site here.
    throw new ConstraintError('aws.params needs the declastruct-aws peer', {
      hint: 'run `pnpm add declastruct-aws`',
      cause,
    });
  }
};
```

- integration-tested: peer present returns the module; peer absent (module-not-found) throws the
  fix-hint `ConstraintError`; a NON-absent error (e.g. a forced throw inside the module) rethrows
  UNCHANGED — the assertion that confirms the catch is an allowlist, not a fail-hide catch-all
  (c18 gains a rethrow assertion).

### 3. `getOneKeyrackAwsParam` — communicator (raw SSM read + boundary error translation)

the ONE seam where the raw `sdkSsm.getOneParameter` boundary is called and where a raw AWS
denial becomes a classed, fix-naming keyrack error. this keeps the adapter `get` a clean
narrative and satisfies `rule.require.failloud` — a bare SDK error never reaches the caller.

```ts
/**
 * .what = fetch + decrypt one SSM SecureString via declastruct, translating any raw AWS
 *         boundary error into a classed keyrack error that names the fix (gates 2/4/7)
 * .why  = a raw sdk denial must never reach the caller bare (rule.require.failloud); this is
 *         the single seam where an AWS denial becomes a keyrack unlock gate
 */
export const getOneKeyrackAwsParam = async (
  input: { exid: string; region: string; endpoint: string | null },
  context: { declastruct: typeof import('declastruct-aws') },
): Promise<{ value: string; type: string } | null> => {
  try {
    // raw i/o: WithDecryption:true → the decrypted value, or null on ParameterNotFound.
    // endpoint is null in prod (the SDK resolves real AWS); under test it points the real
    // SSMClient at a local SSM emulator — a real backend swap, not a mock.
    return await context.declastruct.sdkSsm.getOneParameter(
      { name: input.exid, withDecryption: true },
      asContextAwsApi({ region: input.region, endpoint: input.endpoint }),
    );
  } catch (cause) {
    // classify the raw AWS error into the keyrack gate it represents via a PURE transformer —
    // unit-tested against captured fixture error shapes, prefers the SDK `error.name`
    // over free-text regex. the communicator stays a clean i/o boundary; it only throws what
    // the transformer classifies. never a bare sdk error (rule.require.failloud).
    throw asKeyrackAwsParamErrorGate({ cause, exid: input.exid, region: input.region });
  }
};
```

- integration-tested: a real decrypt returns the value+type; an unknown error surfaces as a
  `MalfunctionError`. the gate CLASSIFICATION (no-identity / read-denied / decrypt-denied) is
  unit-tested in `asKeyrackAwsParamErrorGate` against fixture error shapes (c13/c14/c15), so those
  gates no longer require misconfigured IAM in a shared account to prove.

### 3b. `getOneKeyrackAwsParamEndpoint` — communicator (the ONE SSM-endpoint source)

the single source of the optional SSM endpoint — the ONE boundary that reads the test-only env var
`KEYRACK_AWS_SSM_ENDPOINT`. both the read path (`getOneKeyrackAwsParamReadyContext`, §6) and the
github-app persist path (`setKeyrackAwsParamGithubApp`, §7b) call THIS, never an inline env read, so
the two sites cannot drift — a rename of the var, or a second endpoint source added later, updates
one place and both callers inherit it (the same "can't drift" property the shared readiness helper
gives gate 0, now extended to endpoint). null in prod (the SDK resolves the real AWS endpoint); the
local emulator URL under test.

**why a boundary env read and NOT a `context.aws.endpoint` DI field (r11 i020 #3 — considered, held
with evidence):** the DI seam r11 proposed does not reach the read path. verified in source: the
adapter's `get` and `unlock` methods receive ONLY `input` — NO `context` (`KeyrackHostVaultAdapter.ts:59-66`
unlock, `:95` get via `KeyrackHostVaultGetMethod`); only `set` takes `(input, context?)` (`:115-122`).
so no context seam exists to inject an endpoint through for `get`/`unlock` — the exact read path r11
flags. to create one would change the SHARED cross-vault adapter contract — a `context` arg on
`get`/`unlock`/`del` across all 7 extant adapters + `KeyrackHostVaultGetMethod` — a far larger blast
radius than a test-only endpoint warrants, and a change no other vault needs. the prod cost of the
boundary read is a SINGLE `process.env.NODE_ENV !== 'test'` comparison that returns null at once
(below); it is a one-comparison gate that makes the override prod-UNREACHABLE by construction
(c44/c50), not test-scaffold that executes real work in prod. so the boundary read is the correct
minimal design given the read path carries no context — the DI consistency r11 wants for region/owner
(which DO ride `set`'s context) genuinely cannot extend to an endpoint the read path never receives a
context for.

```ts
/**
```

### 4. `asKeyrackAwsParamErrorGate` — transformer (pure: AWS error → keyrack gate)

maps a raw AWS SDK error to the classed keyrack error it represents. pure, so the gate
precedence + wording are unit-tested against captured fixture error shapes. an `op` discriminator
(`'read'` default | `'write'`) picks the grant the hint names: the READ path (unlock/get) names
`ssm:GetParameter` / `kms:Decrypt`; the WRITE path (github-app persist) names `ssm:PutParameter` /
`kms:Encrypt`. every OTHER arm — no-identity, throttle/5xx, unknown — is shared verbatim, so ONE
seam classes both directions and neither can propagate a bare SDK error (rule.require.failloud).

```ts
/**
 * .what = map a raw AWS SDK error to the keyrack gate it represents (a classed, fix-naming
 *         ConstraintError, or a MalfunctionError for the unknown), for a read OR a write op
 * .why  = gate 2/4/7 classification is PURE logic; extracted so it is unit-tested against
 *         fixture error shapes, not only via misconfigured IAM/KMS in a shared account. one
 *         seam classes BOTH the unlock/get read and the github-app persist write, so a raw
 *         PutParameter/GetParameter denial never reaches the caller bare
 */
export const asKeyrackAwsParamErrorGate = (input: {
  cause: unknown;
  exid: string;
  region?: string; // echoed in EVERY throw context below (r11 i017 nitpick) — a cross-region grant
                   // mismatch is legible no matter which gate (2/4/5/6/6b/7) catches it, uniform with
                   // the gate-5/6/6b region echo, not just some gates
  op?: 'read' | 'write';
}): ConstraintError | MalfunctionError => {
  const name = input.cause instanceof Error ? input.cause.name : '';
  const message = input.cause instanceof Error ? input.cause.message : String(input.cause);

  // every ConstraintError/MalfunctionError constructed below includes `region: input.region ?? null`
  // in its context alongside `exid` — so gates 2/4/7 (and the throttle/unknown malfunctions) carry
  // the SAME region context the adapter's gates 5/6/6b already echo (r11 i017: uniform, not partial).
  const region = input.region ?? null;

  // AWS SDK v3 carries the HTTP status on the STRUCTURED `error.$metadata.httpStatusCode` field,
  // NOT as literal digits embedded in the message prose — so a genuine 5xx is detected via that
  // field, never a `5\d\d` regex over free text (which would never match a real SDK error and
  // would silently fall through to the generic unknown branch). narrow WITHOUT an as-cast:
  // successive `in`/`typeof` refinements read `$metadata.httpStatusCode` with no `as` bypass — the
  // same idiom `getOneDeclastructAws` uses for `'code' in cause` (rule.forbid.as-cast).
  const httpStatus =
    input.cause instanceof Error &&
    '$metadata' in input.cause &&
    typeof input.cause.$metadata === 'object' &&
    input.cause.$metadata !== null &&
    'httpStatusCode' in input.cause.$metadata &&
    typeof input.cause.$metadata.httpStatusCode === 'number'
      ? input.cause.$metadata.httpStatusCode
      : null;

  // the op decides WHICH grant a denial names — the only difference between the read and write
  // classification. read = unlock/get; write = github-app persist. defaults to read.
  const op = input.op ?? 'read';
  const ssmAction = op === 'write' ? 'ssm:PutParameter' : 'ssm:GetParameter';
  const kmsAction = op === 'write' ? 'kms:Encrypt' : 'kms:Decrypt';

  // gate 2 — no ambient identity (uc10); prefer the SDK error name.
  // every throw below carries an explicit `hint` field — one uniform convention across every
  // throw site: the fix is a structured field, not prose embedded in the message.
  if (name === 'CredentialsProviderError' || /could not load credentials|no identity/i.test(message))
    return new ConstraintError('aws.params found no AWS identity', {
      exid: input.exid,
      region,
      hint: 'run an SSO login, or attach an instance role, so the ambient chain has an identity',
      cause: input.cause,
    });

  // gate 7 — kms denied (uc11b on read; the write twin is a kms:Encrypt denial), DISTINCT,
  // matched BEFORE the generic denial. the op picks Decrypt (read) vs Encrypt (write).
  if (/kms|encrypt|decrypt/i.test(message) && (name === 'AccessDeniedException' || /AccessDenied|not authorized/i.test(message)))
    return new ConstraintError(`aws.params identity cannot ${kmsAction} this param`, {
      exid: input.exid,
      region,
      hint: `add a ${kmsAction} grant on the KMS key that encrypts this param`,
      cause: input.cause,
    });

  // gate 4 — ssm denied (uc11a on read; the write twin is a PutParameter denial). op picks the action.
  if (name === 'AccessDeniedException' || /AccessDenied|not authorized/i.test(message))
    return new ConstraintError(`aws.params identity cannot ${ssmAction}`, {
      exid: input.exid,
      region,
      hint: `add an ${ssmAction} grant on this param to the identity`,
      cause: input.cause,
    });

  // gate for e9 — a transient throttle / 5xx. v1 does NOT auto-retry; surface it loud as a
  // malfunction with a retry hint (a deliberate decision — never emit stale-past-TTL). a bounded
  // retry is a clean later extension (open item). matched by the SDK throttle/5xx error names.
  if (name === 'ThrottlingException' || name === 'TooManyUpdatesException' || (httpStatus !== null && httpStatus >= 500) || /throttl|rate exceeded|InternalServerError/i.test(message))
    return new MalfunctionError(`aws.params SSM ${op} hit a transient throttle or 5xx`, {
      exid: input.exid,
      region,
      hint: `transient — retry the ${op === 'write' ? 'set' : 'unlock'}; v1 does not auto-retry`,
      cause: input.cause,
    });

  // unknown → a real malfunction, surfaced with context + a hint, never masked
  return new MalfunctionError(`aws.params SSM ${op} failed`, {
    exid: input.exid,
    region,
    hint: 'an unexpected SSM error — inspect the cause; this was never mapped to a known gate',
    cause: input.cause,
  });
};
```

- unit-tested against fixture error shapes: each of gate 2/4/7 for BOTH ops (read names
  Get/Decrypt, write names Put/Encrypt — c14/c15 gain a write variant), the throttle/5xx→malfunction
  path (c29 — the 5xx arm asserted via a fixture with `$metadata.httpStatusCode` >= 500, the
  structured field, so the arm actually fires instead of a dead `5\d\d` prose regex), and the
  unknown→malfunction path (c13/c14/c15/c25/c29), credential-free.

### 5. `asKeyrackRegion` — transformer (pure: region precedence)

picks the region by precedence (context > `AWS_REGION` > `AWS_DEFAULT_REGION`), fail-loud if
none. pure — set() reads the boundary values and hands them in.

```ts
/**
 * .what = pick the region by precedence: context > AWS_REGION > AWS_DEFAULT_REGION
 * .why  = region is NOT ambient (q5); the precedence is pure logic, extracted so all branches
 *         get a fast credential-free unit test, while the env READ stays at the boundary
 */
export const asKeyrackRegion = (input: {
  fromContext: string | null;
  fromEnv: string | null;
  fromEnvDefault: string | null;
}): string =>
  input.fromContext ?? input.fromEnv ?? input.fromEnvDefault ?? ConstraintError.throw(
    'aws.params requires a region (q5)', {
      input,
      hint: 'set AWS_REGION (or AWS_DEFAULT_REGION), or pass a region on the context',
    },
  );
```

- unit-tested: each of the four branches (context wins, env wins, env-default wins, none → throw).

**note on the set/unlock region asymmetry (a deliberate, acknowledged narrowing of e7).**
`asKeyrackRegion`'s ambient precedence (context > `AWS_REGION` > `AWS_DEFAULT_REGION`) runs ONLY at
`set` — it captures region ONCE and records it in `meta.region` (per q5). at `unlock`/`get`, gate 3
reads `meta.region` ALONE, with NO ambient re-resolution even if the grove itself has `AWS_REGION`
set. this is intentional (region is a set-time fact, so the read path is deterministic and does not
drift if the grove's env changes between set and unlock), but it IS a narrowing of vision e7's
wording ("region not derivable from ambient config **or** meta") — at unlock we consult meta only,
not ambient. stated here explicitly so the asymmetry is on the record, not implicit. **this
deliberate divergence is LOCKED BY A REGRESSION TEST (c51), not prose alone:** c51 sets a key with
`meta.region` = R1, then unlocks with a DIFFERENT ambient `AWS_REGION` = R2, and asserts the read
honors R1 (meta) and ignores R2 (ambient) — so a future change that re-resolves ambient region at
unlock trips a test rather than silently altering the documented behavior. a later extension (read
ambient as a fallback at unlock when `meta.region` is absent) is a clean, surface-free rework if a
use case ever wants it — c51 would be updated alongside it.

### 6. `getOneKeyrackAwsParamReadyContext` — the shared PRE-SSM readiness precheck (name + peer + region)

the ONE place gates 0 + 1 + 3 live, used by BOTH `unlock` and `get` so the three pre-SSM guards
cannot drift — the "can't drift" guarantee is now STRUCTURAL (one function, one order), not merely
asserted by a test. gate 0 (exid-name-legal) folds in HERE as the first line rather than being
duplicated byte-for-byte at both `unlock()` and `get()` call sites (r11 finding 1): two independent
copies could silently diverge; one shared source cannot.

> **scope of this precheck — the pre-SSM gates only, not AWS-side authorization:** it guards
> exactly the three gates knowable BEFORE any SSM call — exid name legal (gate 0) + peer present
> (gate 1) + region present (gate 3), IN THAT ORDER. the identity / read / decrypt / absent / type /
> empty gates are AWS-side and are discovered inside the actual `getOneKeyrackAwsParam` call, NOT
> here. the `.why` says so explicitly, so a maintainer never reads this as "fully validates
> readiness" and skips a check.

```ts
/**
 * .what = the shared PRE-SSM readiness prechecks for an aws.params op — exid name legal (gate 0)
 *         + peer present (gate 1) + region present (gate 3), the three gates knowable before any
 *         SSM call, in precedence order — plus the resolved optional SSM endpoint (real AWS in
 *         prod; a local emulator under test)
 * .why  = unlock and get both need gates 0 + 1 + 3 before any SSM call; ONE source enforces the
 *         order structurally so the two call sites cannot drift (r11 finding 1). this does NOT
 *         cover AWS-side authorization (identity/read/decrypt) — those surface inside the SSM
 *         call itself; this is a pre-SSM precheck only
 */
export const getOneKeyrackAwsParamReadyContext = async (input: {
  exid: string; // gate 0 subject — a human-typed explicit --exid may be malformed
  meta?: KeyrackKeyHostMeta | null; // the OPEN stored union — narrowed below, no as-cast
}): Promise<{
  declastruct: typeof import('declastruct-aws');
  region: string;
  endpoint: string | null;
}> => {
  // gate 0: the exid is a legal SSM name — a malformed one (a human-typed explicit --exid from a
  // prior set) fails loud FIRST, before the peer-load or region-narrow, so the declared precedence
  // (0 → 1 → 3) holds by construction for EVERY caller (rule.require.failfast, e4).
  isKeyrackAwsParamName.assure(input.exid);

  const declastruct = await getOneDeclastructAws(); // gate 1: peer absent → fail loud (uc14)

  // gate 3: region recorded at set + carried in meta; NOT ambient (q5). narrow the stored
  // open-union meta to { region: string } via the type-check — NO as-cast (rule.require.shapefit).
  // fail loud with the gate-3 fix if the narrow fails.
  if (!isKeyrackAwsParamMeta.assess(input.meta))
    ConstraintError.throw('aws.params requires a region (q5)', {
      input,
      hint: 're-run set with a region in scope (AWS_REGION) so it is recorded in meta.region',
    });

  // the SSM endpoint: null in prod (the SDK resolves the real AWS endpoint), or a local SSM
  // emulator URL under test. sourced from the ONE shared communicator getOneKeyrackAwsParamEndpoint
  // (§3b) — the read path's get/unlock receive NO context (KeyrackHostVaultAdapter.ts:59-95), so
  // there is no DI seam to inject it through here; the boundary read (gated by NODE_ENV==='test',
  // §3b) is the correct minimal source, and this + the github-app persist site read the SAME
  // communicator so they cannot drift. the endpoint is the ONE injection point the
  // acceptance/journey harness uses to point the real SSMClient at the emulator (a real backend
  // swap, not a mock — rule.forbid.acceptance.mocks holds). read here once so every downstream call
  // (get, and the github-app write + roundtrip) inherits it.
  const endpoint = getOneKeyrackAwsParamEndpoint();

  // input.meta is now narrowed to { region: string } — region reads as string with no cast
  return { declastruct, region: input.meta.region, endpoint };
};
```

- integration-tested (peer load) + the name/region branches unit-covered: malformed exid → gate 0
  (c35), peer absent → gate 1, region absent → gate 3 (c18/c19). the endpoint pass-through is
  exercised by the acceptance journey (the emulator swap, c31/c7 + both journeys) and asserted
  present-when-set / null-when-unset.

### 6c. `asKeyrackAwsParamRoundtripDefect` — transformer (pure: classify a write-verify)

the null-check / mismatch-check pair (with the two distinct hints) was meaty
pure logic inline in `set()`. extracted to a pure transformer so it gets a cheap direct unit test
(c23), not only the full adapter integration path — the same fewer-paths move used for
`asKeyrackAwsParamErrorGate` and `asKeyrackRegion`. it RETURNS the classified defect (or null when
the roundtrip is clean); the `set()` orchestrator throws. the `as*` prefix is the sanctioned
transformer verb (it casts one shape — `{ written, readback }` — into another — a defect
classification, per rule.require.get-set-gen-verbs), which makes it consistent with its peer
transformer `asKeyrackAwsParamErrorGate` (also a pure "inputs → defect|gate" cast); the throw
stays at the orchestrator boundary (rule.require.narrative-flow).

```ts
/**
 * .what = classify a just-written SSM value's read-back: null when it matches, else the defect
 *         (message + the RIGHT hint) for the caller to throw
 * .why  = a broken write/grant must fail at SET, not later at unlock; the two failure modes
 *         (absent read-back vs value mismatch) have distinct causes, so distinct hints. CRUCIAL:
 *         BOTH hints state that a value WAS written and REMAINS at exid despite the reported
 *         failure — the write already landed BEFORE the verify ran, so a "failed" set has changed
 *         live state (r12 i017 #2). without that, a write-only-grant operator sees "failed", does
 *         not realize a blob now sits in SSM, and a later re-set silently overwrites it (c39)
 */
export const asKeyrackAwsParamRoundtripDefect = (input: {
  written: string;
  readback: { value: string } | null;
  exid: string;
}): { message: string; hint: string } | null => {
  // absent read-back — a path/consistency defect (the write landed but the read-back did not return
  // it; a value MAY now sit at exid)
  if (input.readback === null)
    return {
      message: 'aws.params roundtrip verify: the just-written param did not read back',
      hint: `a path/consistency issue — confirm the param name and that the write landed. NOTE: the write ran BEFORE this check, so a value may now sit at ${input.exid}; a re-set will overwrite it, or remove it out-of-band`,
    };

  // value mismatch — a decrypt/grant defect (the write DID land — a value now sits at exid — but the
  // read-back could not be decrypted/matched)
  if (input.readback.value !== input.written)
    return {
      message: 'aws.params roundtrip verify: read-back value did not match the written blob',
      hint: `a decrypt/grant issue — confirm the kms:Decrypt grant on the key the SSM param uses. NOTE: the write DID land, so a blob now sits at ${input.exid}; a re-set will overwrite it once the grant is fixed`,
    };

  // clean roundtrip — no defect
  return null;
};
```

- unit-tested: match → null; absent read-back → the path/consistency defect; mismatch → the
  decrypt/grant defect (c23, a direct unit test instead of only the adapter integration path).

### 6e. `isKeyrackAwsParamMechOwnsSecret` + `asKeyrackAwsParamResidual` — the residual seam (SET-path orphan detection)

> **UPDATE (wisher decision 2026-07-30 — del is now DESTRUCTIVE):** the `del` side of this seam is
> SUPERSEDED. because del now DESTROYS the owned SSM param (G6, §7) and REPORTS `{ destroyed }`,
> there is no del-side residual to compute — a del strands no secret, so it does not route through
> `asKeyrackAwsParamResidual`. the seam below therefore serves the SET path ONLY: the orphan a
> re-`set` to a CHANGED owned path leaves behind (set does not auto-clean a superseded path). in the
> CURRENT build, the re-`set` pointer change is surfaced by the informational re-point echo
> (invokeKeyrack.ts set branch, keyed on the pre-set manifest exid — c57), and set-time cleanup of a
> superseded owned path is the named follow-up (open items). the collapsed-seam narrative below is
> retained for the SET-path rationale; read every `del` reference in it as superseded by the
> destructive-del decision.

`del` (G6) and `set` (G7) answer ONE underlying question — *does this operation strand a
keyrack-written SSM secret?* — but the prior draft wired that question TWICE, ad hoc: `del` had its
own `mech === 'EPHEMERAL_VIA_GITHUB_APP'` check + `{ residual }` shape, and `set`'s reference arm had
a SEPARATE `priorMech === 'EPHEMERAL_VIA_GITHUB_APP' && priorExid` check. that duplication is exactly
why a case slipped: the `set` github-app arm (a same-mech re-point to a NEW path — legal per G1, the
realistic "rotate to a new path" workflow) never went through either check, so it ORPHANED the old
blob at the old path with ZERO warning — the precise hazard G6/G7 exist to prevent. this collapses
BOTH call sites onto ONE predicate + ONE pure helper, so a new case cannot forget the check and the
"unwired narrative" defect class is structurally foreclosed:

```ts
import type { KeyrackGrantMechanism } from '...';

/**
 * .what = assess whether a mech means keyrack ITSELF wrote a secret into the vault
 * .why  = only an owned-source mech leaves a keyrack-written blob that a later del/re-point can
 *         strand; a reference mech points at an out-of-band value keyrack never wrote, so it can
 *         never orphan one. the ONE predicate both del + set consult (G6+G7)
 */
export const isKeyrackAwsParamMechOwnsSecret = (
  mech: KeyrackGrantMechanism | null,
): boolean => mech === 'EPHEMERAL_VIA_GITHUB_APP';

/**
 * .what = compute the residual-secret descriptor: the PRIOR owned path that this operation abandons,
 *         or null when no secret is stranded
 * .why  = the SINGLE seam for "did we just strand a keyrack-written secret?" — used by del (which
 *         passes currentExid=null, so any prior owned path is abandoned) AND by set (which passes the
 *         just-settled path, so an owned prior path is abandoned only when it DIFFERS). this covers
 *         every stranding case uniformly: a github-app→reference switch, a same-mech github-app
 *         re-point to a new path (the case the prior duplicated checks missed), and a del of an owned
 *         key. a same-path re-persist (rotation, c39) strands no blob → null (rule.require.get-set-gen-verbs: as* pure cast)
 */
export const asKeyrackAwsParamResidual = (input: {
  priorMech: KeyrackGrantMechanism | null;
  priorExid: string | null;
  currentExid: string | null;
}): { exid: string } | null =>
  isKeyrackAwsParamMechOwnsSecret(input.priorMech) &&
  input.priorExid !== null &&
  input.priorExid !== input.currentExid
    ? { exid: input.priorExid }
    : null;
```

why the `priorExid !== currentExid` condition is exactly right, case by case:
- **del of an owned key** — `currentExid = null`, `priorExid = /the/path` → differ → `{ exid: /the/path }`. correct (c27/c46).
- **del of a reference key** — `priorMech` owns no secret → null. correct (c46).
- **set github-app→reference switch** — prior owns, `priorExid = /old`, `currentExid = /new-ref` → differ → `{ exid: /old }`. correct (c48).
- **set same-mech github-app re-point to a new path** — prior owns, `priorExid = /old`, `currentExid = /new` → differ → `{ exid: /old }`. **THE FIX for the r11 blocker** — previously null (c52).
- **set same-mech github-app re-persist at the SAME path (rotation, c39)** — `priorExid === currentExid` → null. correct — the overwrite strands no blob.
- **set reference→github-app, or a fresh set** — prior owns no secret (or absent) → null. correct.

- unit-tested (c53): the predicate (owned vs reference), and the helper across all six rows above —
  a direct table-driven unit test, so a future 7th call site inherits the proven seam instead of a
  duplicated check.

**accepted narrowing — the residual safety net is aws.params-scoped in v1, and this is deliberate
(r11 i022 finding B).** `EPHEMERAL_VIA_GITHUB_APP` is a SHARED mech: the vision states 1password
persists an app blob too ("exactly as 1password writes it via `op item edit`") and os.secure
persists it locally. so a `del`, or a mech-switch `set`, on a 1password- or os.secure-backed
github-app key carries the SAME orphan-secret risk this seam warns about — yet in v1 ONLY aws.params
consults `asKeyrackAwsParamResidual`; the sibling vaults keep their extant silent "removed" behavior.
this is a KNOWN, accepted narrowing, NOT an oversight, for three reasons:
  - **scope** — this route is "only aws.params" (vision). the interface widening that carries the
    residual (`KeyrackHostVaultAdapter`'s `del`-input `mech` + the `residual` return) was done
    vault-AGNOSTICALLY and correctly, so EVERY adapter CAN populate it later — but rewriting
    1password's + os.secure's `del`/`set` to actually do so is a cross-vault behavior change those
    vaults' own criteria never validated, exactly the class of leak finding A caught for the CLI copy.
  - **the mech-level lift is the RIGHT eventual home, and it is named as a follow-up** — because
    "owns a secret" is a property of the MECH not the VAULT, the durable fix is to lift
    `isKeyrackAwsParamMechOwnsSecret` to a vault-agnostic `isKeyrackMechOwnsSecret` in shared keyrack
    infra (alongside the extant mech→adapter map in `genContextKeyrackGrantGet`), and let every
    github-app-capable vault's `del`/`set` consult it. that is a CLEAN lift (the predicate is already
    pure + vault-free), so deferring it now costs no teardown later — flagged in open items.
  - **honesty over false-safety** — the blueprint states plainly that the safety net is aws.params-only
    in v1, so a reader never assumes it is vault-agnostic when it structurally is not (the same
    accepted-narrowing discipline used for the "identity not named" and "v1 del is a no-op" deferrals).

### 7. `vaultAdapterAwsParams` — orchestrator (the adapter)

composes the transformer + communicator into the `KeyrackHostVaultAdapter` shape. per the
adapter contract (`KeyrackHostVaultAdapter.ts:38-80`): `{ mechs, unlock, isUnlocked, get,
set, del, relock? }`.

```ts
/**
 * .what = keyrack vault adapter for AWS SSM Parameter Store SecureString
 * .why  = a cloud box bootstraps from its ambient IAM identity — no secret placed on it
 */
// two generic args: mode + the pinned vault kind, so meta is strongly typed
// (per prod research [16], matches vaultAdapterAwsConfig's declaration)
export const vaultAdapterAwsParams: KeyrackHostVaultAdapter<'readwrite', 'aws.params'> = {
  // both mechs listed → inferKeyrackMechForSet prompts when --mech omitted (uc1, uc4).
  // reads from the ONE source array KEYRACK_AWS_PARAM_MECHS (§6d) that isKeyrackAwsParamMech also
  // derives from — so mechs.supported and the get() membership guard cannot list different sets.
  // SPREAD the readonly tuple into a fresh mutable array: KEYRACK_AWS_PARAM_MECHS is declared
  // `as const satisfies readonly KeyrackGrantMechanism[]` (a readonly tuple), but mechs.supported is
  // typed `KeyrackGrantMechanism[]` (mutable, per the adapter contract) — TS will not assign a
  // readonly tuple to a mutable field, so `[...KEYRACK_AWS_PARAM_MECHS]` copies it into a mutable
  // array. the single-source-of-truth property is untouched: isKeyrackAwsParamMech still derives
  // from the same `as const` source, so the array and the guard cannot drift.
  mechs: {
    supported: [...KEYRACK_AWS_PARAM_MECHS],
  },

  // the adapter receives { slug, mech, exid, priorMech?, priorExid? } + context (per prod research
  // [27]); priorMech/priorExid are the manifest's CURRENT entry (threaded in by setKeyrackKeyHost
  // BEFORE its upsert, G7b) so the reference arm can detect a github-app→reference switch and report
  // the orphaned owned blob. it derives owner from context.owner and org/env/key from the slug utils.
  // set's RETURN is `{ mech; exid?; meta?; residual?: { exid } | null }` — residual is the G7b/G6
  // owned-blob-survives descriptor (null for every non-switch set), which setKeyrackKeyHost threads
  // to the CLI set-branch.
  set: async (input, context) => {
    // derive the path coords from the slug + context (per prod research [36-38])
    // owner is mandatory (G4); the adapter reads context.owner (populated upstream from --owner)
    // and fails loud if absent. it does NO defaulting of its own — it never invents an owner.
    // OPTIONAL-CHAIN the read: the adapter's second arg is `context?: ContextKeyrack` (optional,
    // per the interface), so `context.owner` would trip strictNullChecks ("object is possibly
    // undefined") — `context?.owner` narrows safely and, when context itself is absent, falls
    // through to the same fail-loud, consistent with the `context?.aws?.region` read below.
    const owner = context?.owner ?? ConstraintError.throw(
      'aws.params requires an owner in the param name', {
        input,
        hint: 'pass --owner so the set-flow supplies context.owner',
      },
    ); // G4
    // explicit --exid wins for either mech (uc2, G1). it is human-typed, so VALIDATE it here
    // (e4) — a malformed name fails loud as a ConstraintError before any SSM call, never as a
    // raw SDK ValidationException. the autocomputed path is legal by construction, so it needs
    // no guard. `.assure` throws a HelpfulError; the set orchestration surfaces it with the fix.
    const exid = input.exid
      ? isKeyrackAwsParamName.assure(input.exid)
      : asKeyrackAwsParamName({
          owner,
          org: asKeyrackKeyOrg({ slug: input.slug }),
          env: asKeyrackKeyEnv({ slug: input.slug }),
          key: asKeyrackKeyName({ slug: input.slug }),
        });

    // region source (q5): the precedence (context > AWS_REGION > AWS_DEFAULT_REGION) is PURE
    // logic, extracted to `asKeyrackRegion` so all branches get a fast credential-free unit test.
    // set() only READS the boundary values (the env is the ONE boundary read) and hands
    // them in. fail loud if none; stored in meta so unlock/get reuse it for BOTH mechs.
    // the `fromContext` arm reuses the EXTANT `context.aws` shape the aws.config adapter
    // established (prod [15][16]); for the aws.params prod path the effective source is the env
    // (a grove/CI carries AWS_REGION), and the context arm is the shared-shape + future-wire path
    // (exercised by the c26 unit test). it is not dead — it is the shared-shape arm.
    const region = asKeyrackRegion({
      fromContext: context?.aws?.region ?? null,
      fromEnv: process.env.AWS_REGION ?? null,
      fromEnvDefault: process.env.AWS_DEFAULT_REGION ?? null,
    });

    // mech arrives ALREADY SETTLED by the shared set orchestration upstream — that layer runs
    // inferKeyrackMechForSet (prompt when --mech omitted) and applies the --exid → REFERENCE
    // default before the adapter is called (prod [11][22][27]). the adapter receives the settled
    // mech and NEVER re-derives it here — that keeps the prompt out of the adapter and this line
    // free of decode-friction. an absent mech is a caller-contract violation → fail loud.
    const mech = input.mech ?? MalfunctionError.throw(
      'aws.params set received no mech — the set orchestration must settle it first', { input },
    );

    // RESIDUAL — the ONE seam BOTH arms flow through (G6+G7, r11 i020 blocker fix). computed FIRST,
    // before dispatch, because it is PURE and arm-independent: it depends only on (priorMech,
    // priorExid, currentExid=the just-settled exid), all known here. the earlier draft computed
    // residual ONLY inside the reference arm and ONLY for a github-app→reference SWITCH, so a
    // same-mech github-app re-point to a NEW path (legal per G1, the realistic "rotate to a new path"
    // workflow) fell through the github-app arm and ORPHANED the old blob with ZERO warning — the
    // exact hazard G6/G7 exist to prevent. now the shared pure helper (§6e) decides it once, so
    // NEITHER arm can forget it: a prior OWNED path this set abandons (priorExid !== exid) yields a
    // residual; a same-path re-persist (rotation, c39) or a prior reference mech yields null. `set`
    // and `del` route through the SAME helper, so the "unwired narrative" duplication that let this
    // slip is structurally foreclosed. priorMech/priorExid are the manifest's CURRENT entry, threaded
    // in by setKeyrackKeyHost BEFORE its upsert (the SAME entry the upsert overwrites, G7); the CLI
    // set-branch prints the residual note when present (the SAME copy G6 uses for del).
    const residual = asKeyrackAwsParamResidual({
      priorMech: input.priorMech ?? null,
      priorExid: input.priorExid ?? null,
      currentExid: exid,
    });

    // a switch over the settled mech, one explicit arm per supported mech + a fail-loud default,
    // so a future third mech in mechs.supported cannot silently mis-route into a credential write
    // (rule.forbid.behavior-hazards). NOTE: the default arm cannot be a compile-time assertNever,
    // because `mech` is the BROAD shared `KeyrackGrantMechanism` union (every vault's mechs), not
    // an aws.params-only type — `mechs.supported` is a runtime array, so the type system cannot
    // know this vault's subset. the runtime fail-loud default is therefore the correct guard, and
    // c28 asserts it. EACH arm returns directly with the ONE residual spread in — no mutable local.
    switch (mech) {
      // reference mech: register only, write no value; still record region in meta (uc1).
      // reference mode INTENTIONALLY skips an existence-check at set — the param may not be placed
      // out-of-band yet (per vision), so set only records a valid pointer (the e4 name-check above
      // already ran). an absent target first surfaces at unlock (uc12/e5), where gate 5 names the
      // fix. this asymmetry with the owned mech (which DOES roundtrip-verify) is deliberate: you
      // can only verify a value you wrote.
      //
      // RE-POINT semantics (a re-set on an already-registered reference key with a DIFFERENT
      // --exid): this returns the new exid, and the shared set-flow's idempotent manifest upsert
      // (setKeyrackKeyHost, prod [26]) overwrites the stored pointer to the new path — a silent,
      // deliberate re-point. because reference mode WRITES NO VALUE, there is NO orphaned blob to
      // clean up: only the manifest pointer moves; the old and new SSM params (both placed
      // out-of-band) are untouched, exactly as this vault never writes a reference value. (contrast
      // the OWNED mech, where a re-point DOES abandon the old blob — now caught by the shared
      // residual seam above, c52.) keyrack does not warn-on-re-point for a reference key because
      // there is no orphan and no data loss — a re-point is just a pointer edit. bound by c42.
      case 'PERMANENT_VIA_REFERENCE':
        return { mech, exid, meta: { region }, residual };

      // github-app mech: persist the app blob into SSM (uc3). the whole persist+verify flow is a
      // named orchestrator (setKeyrackAwsParamGithubApp, §7b) so this arm is a one-liner peer to
      // the reference arm — the switch reads as a narrative dispatcher, not a dispatcher-plus-one-
      // large-inline-case, and the persist+verify flow is independently testable + reusable. the
      // SAME residual is spread in, so a same-mech re-point to a new path warns just like a switch.
      case 'EPHEMERAL_VIA_GITHUB_APP':
        return { ...(await setKeyrackAwsParamGithubApp({ slug: input.slug, exid, region }, context)), residual };

      // a mech in mechs.supported with no set-path reached here → fail loud, never silent-open
      default:
        return MalfunctionError.throw('aws.params set: unhandled mech', { mech, input });
    }
  },

  // unlock = the prechecks that need NO aws call, fail-fast (G3 gates 0 + 1 + 3). the SSM read
  // itself is in `get` below, which unlockKeyrackKeys calls next (prod [35]).
  unlock: async (input) => {
    // gates 0 + 1 + 3, in precedence order, ALL live in the one shared readiness helper — so gate 0
    // (exid-name-legal) is NOT duplicated here as a separate line (r11 nitpick 1). the helper runs
    // gate 0 first, so unlock()'s precedence (0 → 1 → 3) holds by construction; a malformed exid
    // fails loud ahead of an absent-region error, and unlock() cannot drift from get() because
    // there is only ONE copy of the three gates (c35 is now regression coverage, not the sole
    // guard against drift).
    //
    // WHY unlock() exists as a distinct step: the adapter contract
    // (`KeyrackHostVaultAdapter.ts:38-80`) is unlock() THEN unlockKeyrackKeys calls get()
    // (prod [35]) — every vault has this shape. get() re-runs the SAME shared helper as its own
    // first line, so the two calls are back-to-back. that redundant re-check is a cheap idempotent
    // no-op (a name check + a peer-load + a meta read, no aws i/o); to keep unlock() a real step
    // (not a merge into get) holds the shape identical to every other vault, which is the
    // pit-of-success the contract intends. a hoist of the check up to unlockKeyrackKeys would fork
    // the shared driver for one vault — a worse trade than one idempotent re-check.
    await getOneKeyrackAwsParamReadyContext(input);
  },

  // get = the VAULT read. IMPORTANT: this is the ADAPTER's get, invoked by unlockKeyrackKeys
  // DURING `keyrack unlock` (prod [35]: unlock → get → push grant to daemon). it is NOT the
  // top-level `keyrack get` — that is getKeyrackKeyGrant, which reads the daemon only and never
  // calls this (prod [19]). the grant returned here is what gets pushed into the daemon.
  // mirrors 1password's get (prod [9]): read by exid, then deliver via the mech adapter.
  get: async (input) => {
    // shared PRE-SSM prechecks — gate 0 (exid name legal) → gate 1 (peer present) → gate 3
    // (region present), in precedence order, ALL inside the one shared helper, plus the resolved
    // SSM endpoint (null in prod; the local emulator URL under test). gate 0 is NOT a separate
    // line here — it lives in the helper as its first step, so a malformed exid fails loud FIRST
    // (before the peer-load or region-narrow), matching the declared chain (0 → 1 → 3 → …), and
    // get() cannot drift from unlock() because both run the identical helper (r11 nitpick 1; e4).
    const { declastruct, region, endpoint } = await getOneKeyrackAwsParamReadyContext(input);

    // fetch + decrypt via the communicator, which maps any raw AWS denial to a classed error
    // that names the fix (gates 2/4/7, and throttle/5xx → malfunction e9) so a bare SDK error
    // NEVER propagates (rule.require.failloud). endpoint is threaded so the acceptance/journey
    // harness can point the real SSMClient at the local emulator (a real backend swap, not a mock).
    const result = await getOneKeyrackAwsParam({ exid: input.exid, region, endpoint }, { declastruct });

    // gate 5 — param absent (getOneParameter returns null on ParameterNotFound) (uc12).
    // the error echoes `region` alongside `exid`: an SSM param is a REGIONAL resource, and region
    // rides in meta (not in the exid path), so a region MISMATCH (the exid points at a real param
    // that lives in a DIFFERENT region) produces the identical "absent" result as a genuinely-absent
    // param. echoing region makes the two distinguishable at a glance (r11/r12 i016) — the deeper
    // region-as-identity fix is a named open item, but the error is legible now.
    if (result === null)
      ConstraintError.throw('aws.params param is absent', {
        exid: input.exid,
        region,
        hint: 'create/place the param at this path IN THIS REGION, or fix the reference (--exid) / region it points at',
      });

    // gate 6 — a plaintext String is never emitted as a secret (uc13); region echoed (see gate 5)
    if (result.type !== 'SecureString')
      ConstraintError.throw('aws.params param must be a SecureString (a decryptable secret)', {
        exid: input.exid,
        region,
        type: result.type,
        hint: 're-store the param as a SecureString (type String is never emitted as a secret)',
      });

    // gate 6b — a present but empty value is never emitted as a valid grant (e10); region echoed
    if (result.value === '')
      ConstraintError.throw('aws.params param is present but empty', {
        exid: input.exid,
        region,
        hint: 're-store a non-empty SecureString value at this path',
      });

    // the mech comes from the STORED manifest entry (recorded at set, threaded by
    // unlockKeyrackKeys — prod [27][35]); it is NEVER defaulted. a default would be a behavior
    // hazard: a github-app key read as a reference would emit the app master-key BLOB instead of
    // a minted ~1h token (rule.forbid.behavior-hazards). an absent mech means a corrupt manifest
    // entry — a server-side invariant violation — so fail loud as a malfunction, never guess.
    const mech = input.mech ?? MalfunctionError.throw(
      'aws.params grant has no mech — the manifest entry is incomplete', { input },
    );

    // the READ-SIDE twin of set()'s unhandled-mech default guard. set() computes the mech inline
    // and fail-loud-guards it; get() reads mech from the STORED manifest — data that could be
    // stale, hand-edited, or corrupted — so it MUST be guarded too, and arguably more so (a
    // mismatched stored mech could misroute a reference key through github-app delivery, or vice
    // versa, instead of a fail-loud). the guard reuses the SAME named type-check the rest of the
    // blueprint uses — `isKeyrackAwsParamMech.assess` (§6d), derived from the ONE
    // KEYRACK_AWS_PARAM_MECHS source array `mechs.supported` also reads — so this membership test
    // shares the idiom of isKeyrackAwsParamName/isKeyrackAwsParamMeta and gets a direct unit test
    // (c43) instead of only an adapter-integration path. fail loud, never guess
    // (rule.forbid.behavior-hazards, rule.require.assure-via-type-checks).
    if (!isKeyrackAwsParamMech.assess(mech))
      MalfunctionError.throw('aws.params grant has an unsupported mech', { exid: input.exid, mech });

    // reference mech: the decrypted value IS the secret; github-app: mint a ~1h token.
    // both flow through the mech adapter's deliverForGet (prod [9][24]).
    const { secret, expiresAt } = await getMechAdapter(mech).deliverForGet({ source: result.value });
    return new KeyrackKeyGrant({
      slug: input.slug,
      key: { secret, grade: /* per extant adapters */ },
      source: { vault: 'aws.params', mech },
      env: /* from slug */, org: /* from slug */, expiresAt,
    });
  },

  isUnlocked: /* daemon presence check, per extant adapters */,

  // del DESTROYS the SSM param keyrack wrote (owned mech) — the wisher's "keyrack destroys what it
  // created" symmetry. manifest-entry removal is the shared orchestrator's job
  // (`delKeyrackKeyHost.ts`), which runs regardless; the adapter cleans its OWN external resource.
  //
  // WHY destroy the owned (github-app) SSM param here — the wisher decision (2026-07-30):
  //   - a key removed from the manifest should strand no secret in SSM. keyrack wrote the blob at
  //     set (owned mech), so keyrack destroys it at del. a REFERENCE mech points at an out-of-band
  //     value keyrack never wrote → its del touches no remote secret (operator-owned param safe).
  //   - the destroy targets ONLY the computed-namespace name (`asKeyrackAwsParamName`), so a key
  //     set with a foreign explicit `--exid` (a u4 shared/out-of-band param) resolves to a
  //     DIFFERENT name and is never destroyed — the operator's shared param is untouched.
  //   - idempotent + type-guarded via declastruct `delSsmParameterSecure`: a no-op if the param is
  //     already absent, and it refuses a non-SecureString (a repurposed plaintext is safe).
  //
  // BUT (G6) a destructive, irreversible remote mutation MUST be visible: a bare "removed" would
  // HIDE that a live SSM secret was just destroyed. so del RETURNS `{ destroyed: { exid } }` for the
  // owned mech, threaded up so the CLI echoes `the SSM secret at {exid} was destroyed` (status
  // feedback + safe-by-default). a reference key returns null (keyrack wrote no value → no remote
  // secret to destroy or report), so it keeps the plain `removed`. bound by c46.
  del: async (input): Promise<{ destroyed: { exid: string } } | null> => {
    // reference mech: keyrack wrote no value → destroy no remote secret. return null so the CLI
    // knows there is no destroyed-secret disposition to echo (the operator-owned param is untouched)
    if (input.mech !== 'EPHEMERAL_VIA_GITHUB_APP') return null;

    // owner is a segment of the computed param name; it must be known to target the param
    const owner =
      input.owner ??
      ConstraintError.throw('aws.params del requires an owner to compute the param name', {
        slug: input.slug,
        hint: 'the manifest entry must carry the owner used at set',
      });

    // region rides in the stored meta (set-time capture); it targets the regional param
    const region = isKeyrackAwsParamMeta.assure(input.meta).region;

    // destroy the SSM secret keyrack wrote, then REPORT what was destroyed so the CLI can echo it —
    // a destructive remote mutation must be visible to the operator (status feedback)
    const { name } = await delKeyrackAwsParam({ slug: input.slug, owner, region });
    return { destroyed: { exid: name } };
  },
};
```

- integration-tested: real unlock→get decrypt (a real SecureString), real github-app set persist
  with roundtrip read-back verify (c23); the AWS denial paths live in the `getOneKeyrackAwsParam`
  communicator test (c13/c14/c15/c25), so the adapter test asserts composition + gates 5/6 + the
  manifest-mech fail-loud.

**note on the two seams:** persist uses the DAO's write (`setSsmParameterSecure`, its intended
purpose); read uses the raw `sdkSsm.getOneParameter` communicator — wrapped by
`getOneKeyrackAwsParam`, which owns the boundary-error translation (the DAO's get is a
metadata-only reconcile-read whose `value` is `@writeonly` by zero-attack-surface design). the
vault straddles both by design — a reviewer should expect two seams, not one.

**note on `ContextAwsApi` filler + endpoint:** `getOneParameter` reads only
`aws.credentials.region`, but the type demands `account` + tunnel cache dirs. `asContextAwsApi`'s
signature is `({ region: string; endpoint?: string | null }) → ContextAwsApi`: it supplies filler
for the `account` / cache-dir fields, each commented inline as `unused-by-this-call` (NOT merely
"filler") — so a future maintainer who touches those values does not assume they are load-bearing
for the SSM read path; only `region` (and, under test, `endpoint`) is.

the OPTIONAL `endpoint` is now THREADED end-to-end, not merely accepted by `asContextAwsApi` in
isolation (this closes the gap where the field existed but no call site could inject it). the
full injection path:

- `getOneKeyrackAwsParamReadyContext` reads the test-only env var `KEYRACK_AWS_SSM_ENDPOINT` at
  the boundary and returns `endpoint: string | null` alongside `region`;
- `vaultAdapterAwsParams.get` threads that `endpoint` into `getOneKeyrackAwsParam({ exid, region,
  endpoint }, …)`, whose input type now carries `endpoint: string | null`, which hands it to
  `asContextAwsApi({ region, endpoint })`;
- `setKeyrackAwsParamGithubApp` reads the same env var at its boundary and threads `endpoint` into
  BOTH its write (`setSsmParameterSecure` via `asContextAwsApi({ region, endpoint })`) and its
  roundtrip read (`getOneKeyrackAwsParam({ …, endpoint })`).

so `endpoint` is `null` in prod (the SDK derives the real AWS endpoint) and the local emulator URL
under test — every live-SSM acceptance/journey case (c3, c6, c7, c8, c10–c12, c16, c17, c24, c30,
c31 jit-success, c39, both journeys) has a real injection point, so the "real backend, not a mock"
claim (`rule.forbid.acceptance.mocks`) is now backed by an actual code path, not a dangling field.
the ONE remaining external unknown — whether declastruct's `SSMClient` construction threads an
`endpoint` through its ctor — stays an open item to confirm when the peer version is pinned; if it
does NOT, the acceptance/journey falls back to the real-credential fail-fast posture (same as
integration), a clean rework of the harness with no change to these signatures.

**note on the lazy peer vs dependency-injection (a documented, unavoidable trade-off):** the
adapter loads `declastruct-aws` via `getOneDeclastructAws()` (a lazy `import()`) rather than accept
the module through `context`. this is a DELIBERATE trade-off the vision requires, not an
oversight of `rule.require.dependency-injection`:
- **why not inject** — to inject the module via `context`, the composition root
  (`genContextKeyrack`) would have to import `declastruct-aws` EAGERLY to place it in context.
  that force-loads the AWS SDK for every keyrack user, defeating the optional-peer requirement
  (vision a5) — a plain `rhachet` install must pull no AWS SDK weight — and the dual-runtime
  constraint (q7): the lazy import is what lets the jit path load the peer only on a real
  unlock/set.
- **matches extant convention** — this is NOT a novel hidden dep. the `aws.config` adapter
  imports its AWS SDK DIRECTLY in-adapter (prod [15]), not via context; a vault's backend SDK
  living inside the adapter is keyrack's established pattern. the lazy import is the aws.params
  variant of that same convention, forced by optionality.
- **testability preserved** — the peer boundary is exercised at the real module level: c18
  toggles peer present / absent / non-absent-error against the actual `import()`, per the
  no-mocks convention (test [6]). the runtime dependency is still observable and controllable in
  a test, just at the module seam rather than a context field.

so the trade-off is the one the reviewer's rule explicitly permits when documented as
unavoidable: the optional-peer + dual-runtime requirements (a5, q7) make context-injection
defeat the goal, and the in-adapter SDK precedent (aws.config) makes the lazy import the
convention-consistent choice.

### 7b. `setKeyrackAwsParamGithubApp` — orchestrator (persist + verify the app blob)

the `EPHEMERAL_VIA_GITHUB_APP` set arm, extracted so both switch arms are one-liner peers and the
persist+verify flow is testable/reusable on its own. it also OWNS the overwrite semantics (c39).

```ts
/**
 * .what = persist a github-app credential blob into SSM at exid, then verify it read back
 * .why  = keep set()'s switch a narrative dispatcher; own the owned-mech write + its overwrite
 *         semantics + the roundtrip verify in one testable place
 */
export const setKeyrackAwsParamGithubApp = async (
  input: { slug: string; exid: string; region: string },
  context: KeyrackHostVaultAdapterContext,
): Promise<{ mech: 'EPHEMERAL_VIA_GITHUB_APP'; exid: string; meta: { region: string } }> => {
  // acquire the blob (per os.secure [13])
  const { source: blob } = await mechAdapterGithubApp.acquireForSet(
    { keySlug: input.slug }, context?.mech,
  );
  const declastruct = await getOneDeclastructAws();

  // the SSM endpoint via the SAME shared communicator the read path uses
  // (getOneKeyrackAwsParamEndpoint, §2b) — null in prod (the SDK derives the real AWS endpoint); a
  // local emulator URL under test. ONE source, so the read path and this persist path cannot drift.
  // threaded into BOTH the write and the roundtrip read below, so the github-app persist path is
  // emulator-swappable too (a real backend swap, not a mock — rule.forbid.acceptance.mocks holds
  // for c3/c39 + the [case2] journey).
  const endpoint = getOneKeyrackAwsParamEndpoint();

  // persist via the idempotent upsert (setSsmParameterSecure). OVERWRITE SEMANTICS (c39): a
  // re-set of an already-persisted github-app key OVERWRITES the blob at this path — a deliberate
  // re-persist / rotation, NOT an error. this is the ONE mech that writes; the reference mech
  // never writes, so only the owned mech carries overwrite semantics. the write is confirmed loud
  // (rule.require.status-feedback) so an accidental re-set is a VISIBLE overwrite, not a silent
  // clobber. an operator who wants the old blob preserved keeps a distinct exid; keyrack does not
  // diff-or-prompt on re-set because the mech's contract is "persist the current app credential."
  //
  // the write is a WRITE op, so its denials differ from the read path: an ssm:PutParameter or a
  // kms:Encrypt denial, NOT a Get/Decrypt one. wrap it so a raw SDK error NEVER propagates bare
  // (rule.require.failloud) — the SAME classification seam (asKeyrackAwsParamErrorGate) with
  // op:'write' names the write grant (PutParameter/Encrypt); no-identity / throttle / unknown are
  // shared verbatim with the read path. the catch is a fail-loud re-throw of a classed error, NOT
  // a fail-hide swallow (rule.forbid.failhide).
  try {
    await declastruct.setSsmParameterSecure(
      { name: input.exid, value: blob },
      asContextAwsApi({ region: input.region, endpoint }),
    );
  } catch (cause) {
    throw asKeyrackAwsParamErrorGate({ cause, exid: input.exid, region: input.region, op: 'write' });
  }

  // roundtrip-verify (rule.require.vault-roundtrip-verify): read the blob back WITH decryption
  // right after the write, so a broken write/grant fails loud at SET, not later at unlock. reuses
  // the get seam; the null-vs-mismatch classification + its two DISTINCT hints live in the pure
  // asKeyrackAwsParamRoundtripDefect transformer (unit-tested), which RETURNS the defect; this
  // orchestrator throws it at the boundary (narrative-flow).
  const readback = await getOneKeyrackAwsParam({ exid: input.exid, region: input.region, endpoint }, { declastruct });
  const defect = asKeyrackAwsParamRoundtripDefect({ written: blob, readback, exid: input.exid });
  if (defect) MalfunctionError.throw(defect.message, { exid: input.exid, hint: defect.hint });

  return { mech: 'EPHEMERAL_VIA_GITHUB_APP', exid: input.exid, meta: { region: input.region } };
};
```

- integration-tested: real persist + roundtrip read-back verify (c3), and a re-set over an
  already-persisted blob → overwrite/rotation confirmed loud (c39). the overwrite is snapshotted at
  acceptance so the confirmed-overwrite copy is visible for review. the write-denial classing (a
  raw `ssm:PutParameter`/`kms:Encrypt` denial → a classed `ConstraintError` that names the write

  shared account.

### 7c. non-interactive `set` — the no-TTY mech contract (uc4, c40)

aws.params exists for UNATTENDED bootstrap, so `set`'s mech selection must never trap a script on
a prompt no process can answer. two paths:

- **the paved unattended path** — a provisioning script passes `--mech` explicitly (uc4); no
  prompt is ever reached. this is the documented way to `set` unattended, and the help text names
  it.
- **the guardrail (the concrete detection, specified now — not deferred to discovery)** — if
  `--mech` is omitted AND the vault has >1 mech, the shared `inferKeyrackMechForSet` must, BEFORE it
  reaches the interactive readline prompt, check `process.stdin.isTTY`. when stdin is NOT a TTY (a
  provisioning process, a piped/redirected stdin — `process.stdin.isTTY` is `undefined`/falsy), it
  FAILS LOUD with a `ConstraintError` naming the fix (`pass --mech <PERMANENT_VIA_REFERENCE|EPHEMERAL_VIA_GITHUB_APP>`),
  NEVER blocks on a read no process can answer (rule.require.safe-by-default,
  rule.require.errors-name-the-fix). the guard is a single `if (!process.stdin.isTTY) ConstraintError.throw(...)`
  placed at the top of the multi-mech prompt branch. bound by c40 (acceptance, no-TTY subprocess:
  stdin redirected from `/dev/null`) and snapshotted.
- **whose change this is** — `inferKeyrackMechForSet` is shared set-flow infra (prod [22]), so this
  no-TTY guard is a vault-agnostic set-flow enhancement, NOT an aws.params-local hack — every
  multi-mech vault (os.secure, 1password, aws.params) benefits. the execution's FIRST step for this
  slice is to read the current `inferKeyrackMechForSet`: if it ALREADY guards no-TTY, c40 simply
  asserts the extant behavior; if it does NOT, execution adds the one-line guard above. either way
  the guard is specified here, not left to discovery. this is recorded as a named open item (below)
  so the wisher sees the one shared-helper touch aws.params implies.

### vision usecase disposition (u1–u5)

the vision names five usecases; each has a disposition here so none reads as silently dropped
(r11 i021 #6, r12 i021 #2):

- **u1 (grove fetches ANTHROPIC_API_KEY, unattended)** — the primary path. reference mech, autocompute
  path, ambient IAM unlock. covered by c6/c7 + the `[case1]` journey.
- **u2 (grove fetches a github-app key → mint token)** — github-app mech. covered by c8 + the `[case2]`
  journey.
- **u3 (laptop dev, ambient SSO/profile)** — same read path as u1, ambient chain = SSO/profile.
  covered by c47 (region-in-profile) + the read cases.
- **u4 (operator: register once, share across ALL envs)** — the autocompute template mandates an
  `{env}` segment (q8), which STRUCTURALLY contradicts "one param shared across envs". so u4 is
  reached NOT via autocompute but via the explicit `--exid` escape hatch (c2): the operator points
  every env's key at ONE env-agnostic `--exid` path (e.g. `/org/shared/anthropic`), running `set`
  once per env against the same path. the CAVEAT: SSM params are REGIONAL, so a param shared across
  envs must live in one region and every env's `meta.region` must match — a cross-region env would
  read "absent". u4 is thus SUPPORTED but deliberately via `--exid`, not autocompute; bound by c55.
- **u5 (CI, ambient = a CI role)** — IDENTICAL mechanism to u1 (the ambient credential chain supplies
  the CI role over env vars / OIDC), so it needs NO special handling — the same read path serves it.
  no separate case; it rides u1's coverage.

### credential strategy

integration tests need real AWS creds (a real SecureString param, a real KMS key). per the
test-code research, the `aws.config` dual-outcome dodge is NOT sufficient here — aws.params
must prove a real decrypt. so:

- integration tests fail-fast via `ConstraintError` when creds are absent (per
  `getKeyrackKeySecrets.integration.test.ts:28-38` precedent), never a silent skip.
- a test fixture param is placed out-of-band in the test account at a known path; the read
  test asserts the decrypted value equals the fixture.
- the blackbox acceptance suite unsets `AWS_REGION` (per `envIsolated.ts:11-12`), so region
  MUST arrive via key meta — this exercises q5 by construction.
- **acceptance-layer backend (explicit, to settle the c7 unlock-success cascade):** any acceptance
  case where `unlock` must actually SUCCEED (c7, and the journey) needs a real backend, since a
  fake `aws` on PATH cannot intercept the SDK read. the acceptance suite points the real
  `SSMClient` at a LOCAL SSM emulator (LocalStack/moto) via the `asContextAwsApi` endpoint
  override — a real backend swap, not a mock (`rule.forbid.acceptance.mocks` holds) — seeded with
  the fixture SecureString + a local KMS key. if the emulator is unavailable, the acceptance
  suite fail-fasts via `ConstraintError`, same posture as integration; it never silently skips or
  hits real AWS.
- **grove-runtime acceptance (q7, c31 — the primary use case gets a bound test):** the whole
  point of this vault is unattended grove bootstrap, and q7 is the flagged tension (jit vs
  bun-binary). c31 binds the JIT arm as a positive assertion: an acceptance case invokes keyrack
  the way a grove does (the jit entry) and asserts the lazy peer resolves + unlock succeeds against
  the local emulator. the BUN arm asserts ONLY fail-loud with the GENERIC peer-absent message
  (`aws.params needs the declastruct-aws peer` / `run pnpm add declastruct-aws`) — it does NOT
  assert a distinct "use the jit entry" hint, because `getOneDeclastructAws` has one catch branch
  and NO runtime-detection code (no `process.execPath`/argv0 branch); to claim a bun-specific
  message would be an unwired narrative. the bun arm's precise behavior (whether bun's dynamic
  `import()` failure is shaped like a node module-not-found and hits that generic catch, or throws a
  differently-shaped bundler error that rethrows unchanged) is EXACTLY what the q7 pre-execution
  gate confirms — so c31 does not overstate it. best-guess jit (per the q7 resolution); the q7
  pre-execution gate (open items) is the real settling step — if the grove turns out bun-only, the
  seam is re-shaped (bundle the peer) before the adapter is written, and c31's bun arm is revisited.

### mask non-deterministic fields before snapshot

several checkpoints emit VOLATILE values that would flake a raw snapshot — the github-app minted
installation token, and every `expiresAt` timestamp on a grant. per
`rule.require.acceptance-journey-coverage`, each volatile field is MASKED to a stable placeholder
BEFORE `toMatchSnapshot()`, so the snapshot proves the deterministic SHAPE while the live flow is
still exercised end-to-end (a real unlock→get through the emulator; only the rendered field is
replaced for the snap):

| volatile field | where it appears | mask |
|----------------|------------------|------|
| a minted github-app installation token | c8 / `[case2]` get-after-unlock | `<token>` |
| `expiresAt` on any grant | every get/source grant checkpoint | `<ts>` |
| a daemon-cache TTL deadline (if rendered) | c10/c11, `[t5]` past-window | `<ts>` |

the reference-mech value (c7) is NOT volatile — it equals the seeded fixture SecureString, so it is
snapshotted verbatim (that determinism is the whole point of a seeded emulator). only the minted
token + timestamps are masked. the acceptance suite applies the masks via a small
`maskKeyrackGrantVolatiles(stdout)` helper (regex-replace of the token + iso-timestamp shapes) so
the mask is one shared, testable transform, not ad-hoc per assertion.

### journey acceptance test

beyond the per-case snapshots, the blueprint declares ONE end-to-end journey acceptance test
(`keyrack.aws-params.journey.acceptance.test.ts`) that walks the grove's day-in-the-life
through multiple timesteps as a subprocess, with a snapshot at each checkpoint and the final
state verified.

**backend for the journey:** the read path is an SDK/HTTPS call, NOT a shelled
`aws` binary, so a fake-`aws`-on-PATH mock cannot intercept it. instead the journey points the
REAL `SSMClient` at a LOCAL SSM emulator (LocalStack / moto) via the `endpoint` override on
`asContextAwsApi` — a real backend SWAP (a genuine HTTPS call to a local endpoint), so
`rule.forbid.acceptance.mocks` stays satisfied AND the journey runs in CI without real AWS. the
emulator is seeded with the fixture SecureString + a local KMS key so the decrypt path is real.
if the emulator is unavailable, the journey fail-fasts via `ConstraintError` (never a silent
skip), the same real-dependency posture the integration suite uses. `envIsolated` (test [7b])
still unsets `AWS_REGION` so region MUST come from meta.

```
given('[case1] a grove bootstraps an aws.params reference key end-to-end')
  when('[t0] initial — key not registered, not unlocked')
    then('get reports locked/absent, names the fix')            → snapshot (blocked state)
  when('[t1] set the reference key with no --exid')
    then('keyrack echoes the autocomputed path, writes no value') → snapshot (positive)
  when('[t2] get before unlock')
    then('locked — names the unlock command')                    → snapshot (blocked/edge)
  when('[t3] unlock with an ambient identity (local SSM emulator via endpoint override)')
    then('unlock succeeds with NO human prompt')                 → snapshot (identity-is-unlock)
  when('[t4] get after unlock --value')
    then('the decrypted value is served, grant shape matches')   → snapshot (positive)
  when('[t5] get after the --max-duration window elapses')
    then('locked again — needs a fresh unlock')                  → snapshot (ttl edge)
  when('[t6] the param is rotated upstream, then re-unlock')
    then('the newly rotated value is served')                    → snapshot (rotation edge)
  when('[t7] region unset + a key with no meta.region')
    then('fail loud — names where region must come from')        → snapshot (error path)
  when('[tN] journey complete')
    then('final daemon + manifest state is the expected end state') → snapshot (final)
```

a parallel `[case2]` journey covers the github-app mech with the SAME per-`[tN]` rigor as
`[case1]` — it handles the app's master private key, so the highest-blast-radius path gets no
less coverage than the reference path:

```
given('[case2] a grove bootstraps an aws.params github-app key end-to-end')
  when('[t0] initial — key not registered')
    then('get reports absent, names the set fix')                → snapshot (blocked state)
  when('[t1] set --mech EPHEMERAL_VIA_GITHUB_APP — supply the app cred once')
    then('keyrack persists the blob into the emulator, confirms; the blob value is NOT in stdout') → snapshot (positive, masked blob)
  when('[t2] get before unlock')
    then('locked — names the unlock command')                    → snapshot (blocked/edge)
  when('[t3] unlock with an ambient identity (emulator via endpoint override)')
    then('unlock reads the blob + mints a ~1h installation token, NO human prompt') → snapshot (identity-is-unlock, <token> masked)
  when('[t4] get after unlock --value')
    then('the ~1h token is served, never the app master key')     → snapshot (positive, <token> masked)
  when('[t5] get after the token TTL (~1h) elapses, within a 2h --max-duration')
    then('locked again at the token TTL — the tighter bound wins (G2)') → snapshot (dual-bound edge, c36)
  when('[t6] re-unlock past the TTL')
    then('a FRESH ~1h token is minted, distinct from the t4 token') → snapshot (re-mint edge, <token> masked)
  when('[t7] region unset + a key with no meta.region')
    then('fail loud — names where region must come from')         → snapshot (error path)
  when('[tN] journey complete')
    then('final daemon + manifest state is the expected end state; the master key never left AWS') → snapshot (final)
```

the `[case2]` journey exercises the happy path, two blocked states (t0, t2), two edges (t5
dual-bound TTL, t6 re-mint), and an error path (t7), with a snapshot at every checkpoint and a
verified final state — a mirror of `[case1]`'s rigor, per the journey-test requirements.

**snapshot determinism:** the volatile fields at these checkpoints — the minted
github-app token (`[case2]` get) and every `expiresAt` timestamp — are MASKED to `<token>` / `<ts>`
via `maskKeyrackGrantVolatiles(stdout)` BEFORE each `toMatchSnapshot()` (see "mask
non-deterministic fields" above). the live flow still runs end-to-end against the seeded emulator;
only the rendered volatile field is replaced, so the snapshot is stable across runs while the real
unlock→mint→get path is genuinely exercised. `[case1]`'s reference value is the seeded fixture
SecureString, so it snapshots verbatim (deterministic, not masked).

## adherence notes

- **timeless traceability (a convention, not a one-off strip)** — this blueprint cites ONLY durable
  anchors: criteria usecases (uc1–uc15), vision edgecases (e4/e9/e10), vision questions (q5/q7/q8),
  blueprint resolutions (G1–G4), rule names, and research indices (prod [N], topic [N]). it does NOT
  bake review iteration-numbers, reviewer-round-numbers, or finding-labels into any shipped surface —
  headers, table columns, code comments, or prose. those session artifacts live in the `.taken`
  review trail alone, where a reader with the trail can follow them; a reader WITHOUT the trail (the
  test of rule.require.timeless-comments) still reads every blueprint line as a statement of what IS
  and why. this convention is what stops the recurrence: a citation keyed to a durable theme cannot
  leak a round-ID into shipped text, because the round-ID has no home here.
- **directional deps** — the adapter lives under `domain.operations/keyrack/adapters/vaults/`;
  it imports `declastruct-aws` (an access-layer peer) and keyrack domain objects. no upward
  import.
- **get-set-gen verbs** — every unit uses a sanctioned prefix: `asKeyrackAwsParamName` /
  `asContextAwsApi` / `asKeyrackRegion` / `asKeyrackAwsParamErrorGate` /
  `asKeyrackAwsParamRoundtripDefect` / `asKeyrackAwsParamResidual` (transformer casts — the last
  three cast inputs to a defect/gate/residual classification, one consistent shape),
  `isKeyrackAwsParamName` / `isKeyrackAwsParamMeta` / `isKeyrackAwsParamMech` /
  `isKeyrackAwsParamMechOwnsSecret` (type-checks + predicate, `is` prefix), `getOneDeclastructAws`
  (loader, One cardinality), `getOneKeyrackAwsParamEndpoint` (the ONE SSM-endpoint source, One
  cardinality), `getOneKeyrackAwsParam` (SSM read), `getOneKeyrackAwsParamReadyContext`
  (assembles the ready {peer, region, endpoint} context), and the adapter `set`/`unlock`/`get`/`del`
  per the contract. `KEYRACK_AWS_PARAM_MECHS` is a const source array, not an operation. no
  standalone `assure*` operation — an assertion rides the `.assure` method on an `is*` type-check
  (rule.require.get-set-gen-verbs).
- **fail loud, name the fix** — every error path throws a classed error with an explicit `hint`
  field (one uniform convention across all new throw sites): a `ConstraintError` when the caller
  can fix it (missing identity/grant/region, malformed exid, absent/plaintext/empty param), a
  `MalfunctionError` for a server-side/transient cause (throttle/5xx, unknown SSM error, a broken
  roundtrip-verify). no bare failures, no swallowed errors (`rule.require.failloud`,
  `rule.forbid.failhide`).
- **assure via type-check** — an explicit `--exid` is validated with `isKeyrackAwsParamName.assure`
  at set AND get, not an ad-hoc throw-guard (`rule.require.assure-via-type-checks`).
- **del scope (v1) — destructive (wisher decision 2026-07-30)** — `del` DESTROYS the SSM param
  keyrack wrote for the owned mech (the single rationale lives on the adapter's `del` in §7 — the
  `key resolutions` `del`/G6 rows and this note both defer to it, rather than restate it, so the
  decision has one home to update). the net: aws.params destroys what it created — a removed key
  strands no secret. a reference mech destroys no remote secret (keyrack wrote none; the
  operator-owned param is untouched). AND del makes the destructive mutation VISIBLE: for the owned
  mech it returns `{ destroyed: { exid } }` so the CLI echoes `the SSM secret at {exid} was
  destroyed`, never a bare "removed" that would hide an irreversible remote delete
  (`rule.require.safe-by-default` via visibility + `rule.require.status-feedback`).
- **IAM grants named (operator completeness)** — the read path (unlock/get) needs
  `ssm:GetParameter` + `kms:Decrypt` (uc11a/uc11b); the write path (github-app persist) needs
  `ssm:PutParameter` + `kms:Encrypt`. **the github-app `set` arm needs ALL FOUR**: after the write
  it does a read-back roundtrip verify (§7b, `getOneKeyrackAwsParam`), so a WRITE-ONLY operator role
  (Put/Encrypt but no Get/Decrypt) would pass the write then fail loud on the verify. this is stated
  so the operator grants read+write together for a key they will `set` via github-app — the verify's
  Get/Decrypt denial is classed with `op:'read'` and names the read grant, so the failure is legible,
  but the note prevents the confusing "my write role can't set" surprise up front. EVERY denial —
  read OR write — is caught and routed through the ONE classification seam
  (`asKeyrackAwsParamErrorGate`, with `op:'read'|'write'`), so it surfaces as a classed, fix-naming
  error that names the EXACT grant to add — never a bare SDK error at either boundary
  (rule.require.failloud). the owned-mech `del` performs an AWS delete, so it needs
  `ssm:DeleteParameter` (+ `kms:Decrypt` for the type-guard) on the identity — `delKeyrackAwsParam`
  names exactly that grant in its failure hint; a reference-mech del performs no AWS delete and
  needs no delete grant.
- **idempotent** — `set` for the github-app mech uses declastruct's idempotent
  `setSsmParameterSecure`; a re-run converges. reference `set` is a pure register. `del` is an
  idempotent delete (a no-op if the manifest entry / param is already absent).
- **wet-over-dry** — the adapter follows the `1password` reference-vault shape and the
  `aws.config` AWS-in-a-vault shape; no premature abstraction across them.
- **optional peer** — `declastruct-aws` in `peerDependencies` + `peerDependenciesMeta.optional`;
  lazy import; a plain `rhachet` install pulls no AWS SDK.

- **the role/identity is not a NAMED error field (r12 i021 #3 — held with reasoning).** the boundary
  errors name `exid` + `region` as structured fields, but not the ambient identity/role. this is
  deliberate, not an omission: keyrack does NOT resolve the ambient identity's NAME — the AWS default
  chain (IMDS/SSO/profile) resolves it OPAQUELY inside the SDK, and the read path (`get`/`unlock`)
  carries no context that could hold it (see §3b). so a named identity field would be null-or-a-guess.
  instead the error names the GRANT to add ("add `ssm:GetParameter` to the identity") — the
  ACTIONABLE fix — which is the correct ergonomic choice when the identity's name is unknowable
  pre-resolution. if a future path surfaces the caller identity (e.g. an STS `GetCallerIdentity` the
  operator opts into), adding the field is a clean, additive rework.
- **declastruct `SSMClient` endpoint override (the ONE external unknown; the keyrack-side wiring is
  DONE, not deferred).** the keyrack-side injection path is now a NAMED codepath change, not an open
  item: `endpoint` is threaded through `getOneKeyrackAwsParamReadyContext` (reads
  `KEYRACK_AWS_SSM_ENDPOINT`) → `getOneKeyrackAwsParam` input → `asContextAwsApi` → and through
  `setKeyrackAwsParamGithubApp`'s write + roundtrip (see the "ContextAwsApi filler + endpoint" note
  and the filediff). the acceptance/journey harness sets that env var to point the real `SSMClient`
  at a local SSM emulator. the sole REMAINING unknown is EXTERNAL: whether declastruct's
  `getOneParameter` / `setSsmParameterSecure` thread the `endpoint` from `ContextAwsApi` into the
  `SSMClient` ctor (the AWS SDK v3 supports it natively). must confirm when the peer version is
  pinned; if declastruct does not expose it, the clean fallback is the real-credential fail-fast
  posture for acceptance (same as integration) — a clean rework of the harness, no change to the
  keyrack-side signatures, no teardown.
- **q7 dual-runtime — a PRE-EXECUTION GATE, not a background item.** this is the load-bearing
  assumption under the WHOLE grove/bootstrap premise: does a grove invoke `keyrack` via the jit
  path (where a lazy optional peer loads) or via the bun-compiled binary (where target-repo
  node_modules is unreachable, so the peer does NOT load)? best guess: jit. but because the entire
  feature's reason-for-being collapses if it is bun-only, the FIRST step of execution — before any
  adapter code — is to confirm the grove's keyrack runtime path (a one-command check on a grove-like
  box, bound to c31). only once jit is confirmed does the lazy-peer design stand; if it is bun-only,
  the design pivots to bundling the peer (or a hard dep for aws builds) BEFORE the adapter is
  written, not after. this gate is called out to the wisher explicitly: it is the one assumption
  whose failure is not a clean late rework but a re-shape of the peer-loading seam.
- **no-TTY guard in the shared `inferKeyrackMechForSet` (§7c).** aws.params is the first vault whose
  UNATTENDED bootstrap makes a hung multi-mech prompt a real hazard, so the no-TTY guard (a single
  `if (!process.stdin.isTTY) ConstraintError.throw('pass --mech …')` at the top of the multi-mech
  prompt branch) is specified in §7c. it is a SHARED set-flow touch, not aws.params-local: every
  multi-mech vault gains the fail-loud-on-no-TTY behavior. best guess: the guard is a clean one-line
  addition (or already present — execution's first step reads the helper). flagged so the wisher
  sees the one shared-helper change aws.params implies; a clean rework either way (c40 asserts the
  behavior regardless of whether the guard was extant or added).
- **github-app blob size vs SSM tier.** the app private-key json may exceed SSM Standard's 4KB.
  best guess: use the Advanced tier (8KB) for github-app params, Standard for reference. a
  clean rework (a tier flag on set) if the blob overflows.
- **`ContextAwsApi` filler durability.** the filler for unused `account`/cache fields is a fit
  against a context shaped for declastruct's broader surface. best guess: filler is safe since
  `getOneParameter` reads only region. a clean rework if a later declastruct version validates
  those fields.
- **read-denied vs decrypt-denied distinguishability (G3 gates 4 vs 7).** the blueprint assumes
  the SDK error distinguishes an `ssm:GetParameter` denial from a `kms:Decrypt` denial (topic1
  [1][5] confirm they are two grants, but not that the thrown error names which). best guess:
  the error message/code distinguishes them (kms denials name the key/kms); fallback if not is
  a message-parse in the adapter. the execution's error-path integration tests (c14, c15) settle
  it — a clean rework of the two catch arms if the errors prove indistinguishable.
- **region source — DECIDED.** region comes from
  `AWS_REGION` / `AWS_DEFAULT_REGION` (the AWS-canonical env vars) or the context; NO `--region`
  flag is added. rationale: the vision decided "no new flags" (a `--region` flag would duplicate the
  SDK's own region resolution), and `AWS_REGION` is the universal AWS convention every operator
  already knows — a laptop dev exports it for a one-off `set`, exactly as they would for any AWS
  CLI/SDK call. this is the deliberate close, not a silent deferral. the ONE remaining rough edge —
  a laptop whose region lives ONLY in `~/.aws/config` (not env) — is a named clean follow-up: extend
  `asKeyrackRegion` to also read the shared-config-file region via the SDK's resolver, no surface
  change. `set` fails loud with the exact fix (`set AWS_REGION`) until then, so the edge is legible,
  not cryptic.
- **declastruct-aws built export map + `setSsmParameterSecure` signature.** the blueprint assumes
  `sdkSsm.getOneParameter` and `setSsmParameterSecure` are reachable from the package's published
  entrypoint with the signatures read from source (vision groundwork). must confirm the built
  `exports` map + the exact `setSsmParameterSecure` input shape (region in input vs context) when
  the peer version is pinned. (no SSM `del` seam is needed — del is a v1 no-op.)
- **owned-secret cleanup — RESOLVED by wisher decision (2026-07-30): del DESTROYS what keyrack
  created.** for the owned mech, `del` destroys the SSM param keyrack wrote (via
  `delKeyrackAwsParam` → declastruct `delSsmParameterSecure`, idempotent + type-guarded), so a key
  removed from the manifest strands no secret. the destructive mutation is made VISIBLE — the
  adapter returns `{ destroyed: { exid } }` and the CLI echoes `the SSM secret at {exid} was
  destroyed` (G6, c46) — so a destructive remote delete is never silent (safe-by-default via
  visibility, not via a no-op). the destroy targets ONLY the computed-namespace name, so a foreign
  explicit `--exid` (a u4 shared param) is never destroyed. the ONE residual edge that REMAINS a
  follow-up: a re-`set` to a CHANGED owned path leaves the OLD blob in place (set does not auto-clean
  a superseded path); the re-pointed echo makes the pointer change visible, and set-time cleanup of a
  superseded owned path is a clean, additive follow-up.

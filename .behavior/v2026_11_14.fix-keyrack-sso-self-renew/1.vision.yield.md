# 1.vision — keyrack renews an aws sso key before it expires

## the outcome world

### before

- a human runs `rhx keyrack unlock --owner ehmpath --env camp` at the start of the day. the cli proves the sso session silently, reads the role creds' expiry, and hands the daemon a grant whose value is the aws profile name and whose `expiresAt` is that role session's expiry, ~1h out.
- an hour later the daemon purges the grant on read. every consumer of `ahbode.camp.AWS_PROFILE` now reads a locked key; one of them is grove 0901's tunnel, whose reconnect needs the camp creds.
- the sso portal session is still live (~8h). a hand unlock would renew silently, with no browser. no one fires it.
- overnight, 0901 goes dark and stays dark until a human unlocks by hand.

### after

- the human unlocks once, as today.
- before the grant expires, the daemon renews it on its own: it proves the portal session silently, re-reads the role creds' expiry, and stores the grant again with the new `expiresAt`. it never calls the browser login.
- every consumer keeps its access across the expiry. the daemon stays alive, since it holds a live key.
- a renew never extends a key past the bound the human set at unlock (`--duration`, 9h by default). when that cap arrives, the key expires as it does today.
- when the portal session itself lapses, the renew fails fast, once. `keyrack status` names the lapse and the one command that cures it. the daemon does not retry a lapse on each tick and never waits on a browser.
- a human's `relock` always wins: a renew in flight never brings a relocked key back.

### the aha

`rhx keyrack status` at 3am shows the camp key with `expires in: 52m` and `renewed = 4x`. no one touched it.

## mental model

- **to a friend:** "the keyrack keeps my aws creds topped up while my sso login is good. when the sso login runs out, it tells me once instead of a hang."
- **analogy:** a car that refuels from the tank you already paid for. it never drives to the gas station by itself; the browser login is the gas station.
- **their words vs ours:** they say "refresh", "keep alive". we say **renew** (the wish's word) and **lapse** (the portal session ended). `lapse` already names the daemon's idle-lease end in `scheduleAutoTermination`; see fulcrum F4.

## evaluation

- **solves the goal:** yes, while the portal session lives and inside the human's unlock bound. the portal bound is the wish's own; the unlock cap is a best guess, held for the wisher (fulcrum F1).
- **pros:**
  - consumers change naught. `AWS_PROFILE` keeps the same value; only its daemon lifetime extends.
  - the renew reuses the extant silent proof (`validateSsoSession`) and expiry read (`deliverForGet`), so it cannot drift from what unlock does.
  - no new secret enters the daemon: the grant's value is already the profile name.
- **cons:**
  - the daemon gains its first outbound call (aws cli + sso sdk). today it is pure memory.
  - the daemon must hold a renew record per sso grant: the unlock cap, the renew count, the last renew, and any lapse.
- **edgecases + pit of success:**
  - a lapsed portal cannot hang the daemon, by construction: the renew calls the silent proof alone and has no path to `triggerSsoLogin`.
  - a non-sso grant is never renewed: the renew selects on `source.mech === 'EPHEMERAL_VIA_AWS_SSO'`.
  - a fault is not a lapse: only the silent proof's `{ valid: false }` marks lapse; any other error is logged and retried next tick, at most one try per tick (case 7).
  - a fault that persists is not left quiet: once the error has held for one full window (10 consecutive ticks), the key is marked `halted` with its last error, and no renew is tried again. status names it with the same cure. inside the window that lands at about the grant's expiry; after a late wake it still grants 10 tries, so a blip at wake never halts a key. retries are bounded, and a stall is as loud as a lapse (case 7).
  - a renew may not move the expiry. `export-credentials` can hand back the cli's cached role creds unchanged while they sit outside the cli's own refresh margin. an unchanged expiry is neither a lapse nor a renew: the tick writes naught, counts naught, and tries again next tick, when the creds sit closer to their end.
  - a relock mid-renew wins: the renew writes back only if the grant it read is still the one stored, and a relock clears the renew record (case 5).
  - a hand unlock mid-renew wins for the same reason: its newer grant does not match what the renew read.
  - a grant that expired while the laptop slept is still renewable: the store purges on read, so the renew record, not the store, is what the tick walks (case 3).
  - a lapse must stay visible until the human acts. the grant expires minutes after the lapse, and the daemon exits 15m after its last live key, so a lapse mark that held naught alive would vanish before an overnight human ever looked (case 1, [t5]). the lapse mark therefore keeps the daemon alive until an unlock cures it or a relock clears it. it holds no secret, only the mark (fulcrum F5).
  - a renew must not change which user the key acts as. the profile is the same and no browser login runs, so the portal token's user cannot change under it (fulcrum F3).

## open questions & assumptions

- **assumption:** the daemon hosts the renew tick, since it is the one process alive across the expiry (fulcrum F2).
- **assumption:** renew window = 10m before `expiresAt`, tick = 1m. the keyrack already treats < 5m as expired (`define.aws-sso-vs-sts-credentials`), so 10m leaves several ticks of margin.
- **assumption:** the cap is the expiry `computeExpiresAt` would give with no grant clamp, i.e. min(requested duration, maxDuration) from the unlock moment. this keeps the human's `--duration` meaningful.
- **assumption:** the renew does not re-check `meta.awsSsoUsername`: the daemon does not hold it, and a silent renew cannot switch users (fulcrum F3). the silent proof does return a username, so a check costs only a field on the grant if the council wants one.
- **contract gap, owed by the design:** the daemon never learns the cap today. `daemonAccessUnlock` sends `{ keys: KeyrackKeyGrant[] }` alone, and the stored `expiresAt` is already min(cap, STS expiry), so the cap is lost at unlock. the UNLOCK payload must carry it per sso key (an optional field). a key that arrives with no cap is never renewed: renew is opt-in by the cli that knows the human's bound. the cli and the daemon ship in one package, so skew is not a live path.
- **assumption:** the daemon may import the vault adapter's silent proof, since the daemon svc already imports from the shared `@src` tree (`handleUnlockCommand.ts:1-2`). the import is lazy, inside the renew, so a daemon with no sso key never loads the aws sdk (`rule.require.thinnest-import-path`).

### questions, triaged

1. **[wisher]** should the renew obey the unlock's `--duration` cap (9h default), or run unbounded while the portal lives? best guess: obey the cap. it is the bound the human chose, and the ~8h portal session ends first in the default case anyway. but the portal length is the org admin's choice; where it outlasts 9h, the cap ends the key while the portal lives. a middle path obeys only an explicit `--duration` (fulcrum F1).
2. **[answered]** how long must a lapse stay visible? until the human acts. the wish asks that status name it, and the overnight case only works if it outlives the grant and the 15m idle exit. so the lapse mark keeps the daemon alive until an unlock or a relock (fulcrum F5, for the council to overrule).
3. **[answered]** which process hosts the renew? the daemon, the one process alive across the expiry; the cli exits after each call (fulcrum F2).
4. **[answered]** does a renew change which user the key acts as? no. same profile, no browser login, so the portal token's user cannot change (fulcrum F3).
5. **[answered]** does `export-credentials` report the new expiry? yes: `deliverForGet` reads `AWS_CREDENTIAL_EXPIRATION`, with a now + 55m fallback (`mechAdapterAwsSso.ts:137-185`). the live proof in verification confirms it on the real cli.
6. **[answered]** why ~45s in the wish's evidence when src holds a 180s login timer? irrelevant to the design: the renew never reaches the login path.
7. **[answered]** the word for a portal-session end: `lapse`, scoped by its key branch in status; the overload with the idle lease is weighed in fulcrum F4.
8. **[answered]** does the daemon's STATUS reply break a consumer when it grows the renew count and the lapse? no: the fields are additive on each key entry (`handleStatusCommand.ts:13-65`), and the one reader is the cli render in the same package.
9. **[answered]** when does the live proof run? early in execution, as soon as the renew builds, so its ~2h (two expiries) overlaps the rest of the work instead of trails it.
10. **[research]** what refresh margin does the aws cli use before it re-derives cached role creds on `export-credentials`? it decides how often a renew returns an unchanged expiry, and whether a 10m window renews on its first tick or a later one. answer by a live probe in execution: run `export-credentials` at several distances from the cached expiry and record when the expiry moves. the design tolerates any margin (an unchanged expiry retries next tick), so this tunes the window and blocks naught.

## groundwork

### external research

- `define.aws-sso-vs-sts-credentials` (keyrack brief): the portal token lasts ~8h; the role creds derived from it last ~1h. `aws configure export-credentials` re-derives role creds from a live portal token with no browser, and fails when the portal token has lapsed (aws cli docs, cited there).
- `lesson.aws-sso-browser-session-reuse`: `aws sso login` is the step that can open a browser. the renew never calls it.
- `@aws-sdk/credential-provider-sso` `fromSSO`: calls GetRoleCredentials with the cached portal token; no browser. already used by `validateSsoSession`.

### internal research

- **the daemon store** — `src/domain.operations/keyrack/daemon/svc/src/domain.objects/daemonKeyStore.ts`
  - a `Map<address, KeyrackKeyGrant>` keyed by slug + reach (:24-42)
  - TTL is enforced on read, never by timer (:19, :60-71); `entries()` purges expired grants (:97-115)
  - `del` without a reach sweeps every reach of the slug, and argues that a token which outlives a relock is unacceptable (:117-146)
- **the grant** — `src/domain.objects/keyrack/KeyrackKeyGrant.ts`: `{ slug, key: { secret, grade }, source: { vault, mech }, env, org, reach?, expiresAt? }`. for an sso key, `key.secret` is the aws profile name (`vaultAdapterAwsConfig.ts:634-641`).
- **the daemon process** — `daemon/svc/src/contract/startKeyrackDaemon.ts:18-98`, spawned detached with the caller's env (:107-148), so `aws` on PATH and `~/.aws` are reachable.
- **the daemon's one timer** — `daemon/svc/src/domain.operations/scheduleAutoTermination.ts:71-92`: every 15m, exits when no live grants and no demand for 15m. a held live grant keeps it alive (:76).
- **the server setup** — `daemon/svc/src/infra/createKeyrackDaemonServer.ts:37-45`: builds the store and the activity clock, schedules termination. the renew tick belongs beside it.
- **the unlock payload** — `daemon/sdk/src/domain.operations/daemonAccessUnlock.ts:25-29` sends `{ keys }` alone; `daemon/svc/src/domain.operations/handleUnlockCommand.ts:18-21` stores each grant as given. no cap or duration crosses the socket.
- **what a consumer holds** — the grant's secret is the profile name, so a consumer's own aws sdk re-derives role creds from the portal token. the daemon's `expiresAt` gates keyrack's handout of the name, and the renew's silent proof is what detects a lapse.
- **commands** — `src/domain.objects/keyrack/KeyrackDaemonCommand.ts:11`: `UNLOCK | GET | STATUS | RELOCK`. no renew command today; none is needed, since the tick is internal.
- **the silent proof** — `adapters/vaults/aws.config/vaultAdapterAwsConfig.ts` `validateSsoSession` (:170-263): `fromSSO` → `export-credentials` → `sts get-caller-identity`. returns `{ valid: false }` on an expired-style error, throws `MalfunctionError` on any other. no browser. module-private today.
- **the browser path** — same file, `triggerSsoLogin` (:273-332), reached only from `unlock` after the silent proof fails (:520). 180s kill timer.
- **the expiry read** — `adapters/mechanisms/aws.sso/mechAdapterAwsSso.ts` `deliverForGet` (:137-185): `expiresAt = AWS_CREDENTIAL_EXPIRATION`, else now + 55m.
- **the unlock bound** — `src/domain.operations/keyrack/computeExpiresAt.ts:51-94`: min(requested duration, maxDuration, grant expiry). cli default duration is 9h, 30m for sudo (`src/contract/cli/invokeKeyrack.ts:1953-1956`).
- **status** — the daemon side is `daemon/svc/src/domain.operations/handleStatusCommand.ts:13-65` (`{ slug, env, org, reach?, expiresAt, ttlLeftMs }`); the render is `src/domain.operations/keyrack/cli/asKeyrackStatusKeyBranch.ts:15-38` (`└─ expires in: Nm`). snaps live at `cli/__snapshots__/asKeyrackStatusKeyBranch.test.ts.snap` and `blackbox/cli/__snapshots__/keyrack.status.acceptance.test.ts.snap`.
- **test seams** — `blackbox/.test/assets/mock-aws-cli/aws` is a PATH shim for `sso login`, `sts get-caller-identity`, `configure export-credentials`, driven by `MOCK_AWS_*` env vars, with `AWS_SDK_MOCK=1` to skip `fromSSO`. `scheduleAutoTermination.test.ts` already drives a daemon timer with jest fake timers.
- **vocab** — `renew`, `lease`, `lapse` appear today only for the daemon's idle lease (`handleKeyrackDaemonConnection.ts:108-113`, `scheduleAutoTermination.ts:54`). no credential renew exists anywhere.

## what is awkward?

- the daemon was pure memory; the renew makes it call aws. that is a real change to its nature, and the honest cost of the one process alive across the expiry.
- the renew writes the store from a timer, beside two human verbs that also write it. the conditional write-back (case 5) is what keeps a human's act authoritative.
- `lapse` is already in use for the idle lease. a second sense risks an overload; fulcrum F4 weighs a different word for the portal session end.
- the wish observed a ~45s browser wait on lapse; src holds a 180s login timeout and no 45s one. the renew avoids the browser path entirely, so the gap does not affect the design. it is noted so no one hunts for a 45s timer.

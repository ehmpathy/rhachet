## live proof — two expiries passed

the done clause names `ahbode.camp.AWS_PROFILE`. the proof ran on a host that holds it via aws sso.

it ran in a private daemon (F6), so the shared daemon was never restarted, on the build with the renew in the mech adapter (the dist it loaded holds `getOneGrantRenewal` and `mechAdapterAwsSso.renewForDaemon`, and no daemon-side sso code):

```sh
rhx keyrack.private --dir /tmp/krp --repo-key ahbode.camp.AWS_PROFILE -- unlock --owner ehmpath --env camp --duration 24h
rhx keyrack.private --dir /tmp/krp -- status --owner ehmpath --json    # read after each expiry
rhx keyrack.private --dir /tmp/krp -- daemon prune --owner ehmpath
```

| read | `renewedCount` | `expiresAt` | `mark` |
|---|---|---|---|
| after unlock | 0 | the role creds' real expiry, from the cli (F7) | none |
| after the first expiry | 1 | a fresh role session's expiry, ~12h on | none |
| after the second expiry | 2 | the unlock's 24h cap — the fresh session ran past it, so the renew clipped to it (F1) | none |

no hand unlock, no browser, no lapse, no halt. the reads, as `status --json` printed them, are posted on #759: https://github.com/ehmpathy/rhachet/pull/759#issuecomment-6916720900 and https://github.com/ehmpathy/rhachet/pull/759#issuecomment-6934603393

why `--duration 24h`: a role session on this host lasts ~12h, longer than the default 9h duration. with 9h, the stored expiry is the cap itself (min of cap and role session, F1), so the key ends at 9h as designed and no renew is due. the 24h duration puts two role-session ends inside the cap, which is what the done clause asks to see. where role sessions last ~1h (the vision's common case), the default 9h cap leaves room for several renews.

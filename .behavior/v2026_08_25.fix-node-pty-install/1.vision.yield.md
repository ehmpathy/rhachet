# 1.vision — node-pty is reliably usable on linux, with no manual step by the human

> ⚠️ **a note on one word.** this yield quotes npm registry output, `package.json` field names, and
> real cli flags verbatim (`--ignore-scripts`, `npm view … scripts`, pnpm's `Ignored build scripts`).
> that word is forbidden under `rule.forbid.term-script`. it is retained **only inside quoted
> evidence blocks and literal flag names**, where paraphrase would falsify the citation. every prose
> sentence says **install hook** / **lifecycle hook** instead.

---

## the outcome world

### day-in-the-life

a human on linux runs one command and the clone reach socket just works:

```bash
$ pnpm add -g rhachet
$ rhx enroll claude
🔌 reach this clone: rhx clone say @:<serial> --what "…"
```

that breadcrumb is the **real** extant stdout — `invokeEnroll` emits it on a bare enroll
in tree mode. today on linux the human never reaches that line; the ConstraintError fires first.

no allowlist. no rebuild. no toolchain. no knowledge that a transitive native addon exists.

### before / after

| moment | before (today) | after |
|--------|----------------|-------|
| `pnpm add -g rhachet` on linux | the build hook is gated, the addon never compiles, and node-pty is unusable | the build hook is a no-op; its block decides naught. **the global install exits 0 at BOTH majors** — 10.24 reports a WARN, 11.18 reports no gate line at all, and neither raises `ERR_PNPM_IGNORED_BUILDS`. ⚠️ that holds for the GLOBAL command only; the local `pnpm install` diverges at the next major — see awkward #4 |
| `rhx enroll claude` (interactive) | ❌ **loud** `the reach socket is unavailable — node-pty failed to load` | ✅ socket stands up |
| the named cure | `pnpm rebuild node-pty` → exits 0, changes naught (it has no `--global`; see groundwork) | there is no cure to name — the capability is present |
| `rhx clone say` | un-runnable on linux, because the enroll above never produced a clone | works |
| a human's mental state | "the tool told me the fix and the fix is a lie" | never enters the loop |

### the "aha"

the aha is **the absence of an aha**. today's defect costs hours precisely because it presents as a
*fixable* condition — a confident error, a named command, a clean exit. the value clicks when a linux
human who never heard of node-pty enrolls a clone and none of it asks a step of them.

the secondary aha is for us: **the root cause is not "linux has no prebuild."** it is *"the package
needs an install hook to produce a binary at all, and a gate blocks that hook."* framed that way, the
cure is to **make the binary already be there** — then no hook is needed, and no gate can block it.

and the tertiary aha, which decides the shape and which no amount of design would have found:
**upstream already shipped that binary.** node-pty added linux prebuilds ten days after the release
we pin. the whole cure is a version bump.

### 🚨 there is not ONE blocker — there are THREE surfaces

the wish frames the defect around `pnpm add -g`. that is one of three, and **the second is our own
code**:

| # | surface | who blocks the hook | cured by the bump? |
|---|---------|---------------------|-------------------|
| 1 | `pnpm add -g rhachet` | **pnpm ≥10's build gate**; the allowlist belongs to the project that installs, so rhachet's own `pnpm.onlyBuiltDependencies` does not travel | ✅ yes — the prebuild is in upstream's tarball; the hook is a no-op |
| 2 | `rhx upgrade` (local) | 🚨 **rhachet itself** — `execNpmInstallLocal` passes `--ignore-scripts` unconditionally | ✅ yes — an opt-out of a hook that need not run is a non-event |
| 3 | a consumer's own `pnpm install` | their manifest carries no allowlist for a dep they never declared | ✅ yes — same reason as 1 |

> ✅ **one cure closes all three.** that is the property that decided the shape: it does not address
> the gate, it makes the gate **irrelevant**, on every package manager, at every version, for every
> install path.

surface 2 is worth a second read. the diagnosed shape, in `execNpmInstallLocal`'s spawn — quoted by
**symbol** rather than by line, since a line number is a second owner of a location that the cure
itself moves (`rule.require.timeless-comments`):

```ts
// .note = --ignore-scripts avoids pnpm v10 ERR_PNPM_IGNORED_BUILDS
//         rhachet-roles packages don't need lifecycle scripts to function
const result = spawnSync(pm, ['install', '--ignore-scripts', ...packagesLatest], …);
```

> ⚠️ **the comment's justification is true for roles and FALSE for rhachet itself.** role packages
> are pure content and need no hook. rhachet carries node-pty, which at `1.1.0` needs its hook to
> produce a linux binary at all. so `rhx upgrade` **guarantees** an unbuilt node-pty — on **every**
> package manager and **every** pnpm version, allowlist or no. it is not gated by pnpm's policy; it
> opts out directly.
>
> note the asymmetry: `execNpmInstallGlobal` passes **no** `--ignore-scripts` — so the two
> upgrade paths fail for two entirely different reasons. a fix aimed at one would leave the other
> live, which is why the cure had to make the hook unnecessary rather than make it run.

## 🎯 the recommendation — bump node-pty to `1.2.0-beta.15`

the wish delegates the how and names four candidate shapes — *"a declare-time change, an install-time
change, a load-time fallback, or a vendored prebuild."* **this vision picks the first, in its
smallest possible form: a version bump, plus the removal of the allowlist entry that masked the
defect.**

```diff
  "optionalDependencies": {
-   "node-pty": "1.1.0"
+   "node-pty": "1.2.0-beta.15"
  },
  "pnpm": {
    "onlyBuiltDependencies": [
      "bun",
-     "node-pty"
    ]
  }
```

that is the entire change. **no copy step, no ci change, no fallback branch, no tarball growth, no
new artifact we own, no new trust relationship.**

### 🚨 the second edit is not cosmetic — it is what restores our ability to SEE the defect

`pnpm.onlyBuiltDependencies` applies in the **root project's** manifest only. so our own entry never
helped a consumer — it only ever made **our** tree the one place on earth where node-pty built
successfully. that is precisely why the defect shipped: every local check, and every ci job, ran
against the one tree immune to it.

the removal buys three things at once:

1. **our dev tree now behaves exactly like a consumer's.** the build gate fires here too, so a
   regression is visible where we work rather than only where users install
2. **the extant integration test regains teeth for free** — `getPtyModuleOrNull.integration.test.ts`
   was green under the defect because the allowlist made it green. with the entry gone, that same
   test now genuinely asserts *"the addon loads with no build hook run"*
3. **it is itself the proof that no step beyond a plain install is required.** an allowlist entry is
   an extra step; its removal, with the suite still green, demonstrates the step was retired rather
   than relocated

**a plain deletion is the whole edit — no `ignoredBuiltDependencies` counterpart is needed.** pnpm 10
blocks every build hook by default; `onlyBuiltDependencies` is a pure allowlist, so to drop the entry
is to restore the default. an explicit ignore-list entry would be redundant declaration.

⚠️ **one observation this vision does not explain.** after the change, pnpm's ignored-build notice
lists four packages — `simple-in-memory-cache`, `with-simple-cache`, `simple-log-methods`,
`with-simple-caching` — and **node-pty is not among them**, confirmed in `node_modules/.modules.yaml`
under `ignoredBuilds`. the outcome is the one we want, but the **mechanism is unverified**, so it is
recorded as an observation rather than claimed as a guarantee. a blueprint that leans on the quiet
install should confirm it from a cold store.

⚠️ **and an adjacent find, out of scope:** those four packages are ours, and their build hooks are
blocked in exactly the way node-pty's were. they are pure-js so the risk is likely nil — but that is
the same sentence anyone would have written about node-pty a month ago. worth its own look.

### why this works — measured, and CLAMPED rather than recounted

the bump is applied in this worktree and its effects are measured, never assumed. each probe is an
assertion in `getPtyModuleOrNull.consumer.integration.test.ts`, re-measured every run — so **the
test file is the owner**, and this section states only the shape of the proof. a probe recounted in
prose here would be a second copy that no run can redden:

| claim | how it is held |
|-------|----------------|
| `pnpm install` completes clean; the install hook compiles naught — `node-pty/build/` never exists | clamp, structural |
| all six prebuilds present; `linux-x64/pty.node` is a real ELF addon | clamp |
| rhachet's own specifier loads it AND a live pty spawns — presence is not proof of function, so bytes are read back off the pty | clamp |
| `--what integration --scope 'path://clone/pty'` and `--what types` pass | CI, every run |

**🚨 the one that settles it — a HERMETIC CONSUMER INSTALL, at BOTH versions.** every check above ran
against *this* tree; a `genTempDir` project with its own manifest and **no allowlist** is the real
consumer condition, so the proposition was put to both versions there:

```
=== node-pty@1.1.0 ===                      === node-pty@1.2.0-beta.15 ===
  build gate fired   : true                   build gate fired   : true
  prebuilds/linux-x64: false                  prebuilds/linux-x64: true
  addon loaded       : false                  addon loaded       : true
  spawn              : (none)                 spawn              : accepted
  VERDICT            : BROKEN                 VERDICT            : USABLE
```

the `1.1.0` failure reproduced the field report **verbatim**, doubled slash included:
`Cannot find module './prebuilds/linux-x64//pty.node'`.

> ✅ the defect reproduced and the cure proven in one run. it confirms the wish's record #4 and
> **corrects** it: the package was **present but unbuilt**, never absent, since node-pty's own
> `lib/utils.js` was reached and ran.

### 🚨 why this was invisible until now — the upstream timeline

the defect is not that linux is unsupported. it is that **we pin the last release before the fix**.

| date | upstream event |
|------|----------------|
| 2025-10-08 | `#804` adds prebuilds to the npm tarball |
| 2025-10-09 | `#805` **excludes linux**, because the ci runner's glibc (2.35) is newer than node's floor (2.28), so the binary would fail on older hosts |
| **2025-12-22** | **`1.1.0` publishes — with the linux exclusion in place. this is what we pin.** |
| 2026-01-01 | `#853` adds a glibc-2.28 sysroot to the linux build, which retires the portability objection |
| 2026-01-02 → | linux-x64 and linux-arm64 prebuilds ship |
| 2026-08-03 | `1.2.0-beta.15` publishes, with all six platforms |

> ⚠️ **the exclusion was deliberate and correct at the time.** upstream declined to ship a linux
> binary that would `dlopen`-fail on any host older than their runner — which is the same *"silently
> wrong binary"* hazard the wish's scope bound names. the sysroot in `#853` is what made a portable
> linux prebuild possible, and it landed **ten days after** the release we depend on.
>
> so the whole defect is a ten-day pin gap. no design was needed; only a look upstream.

### the beta and its provenance, weighed honestly

`1.2.0-beta.15` is a prerelease, and the wish's bound asks for *"an explicit account of provenance"*.
one section answers both, because the answer to each is the same fact: **the chain of custody does
not change.**

| property | `1.1.0` (today) | `1.2.0-beta.15` (proposed) |
|----------|-----------------|---------------------------|
| publisher | `microsoft1es` | **same** |
| build system | microsoft 1es pipelines | **same** |
| source repo | `microsoft/node-pty` | **same** |
| registry signature (`dist.signatures`) | ✅ present | ✅ present |
| npm provenance attestation | ❌ **404** | ❌ **404** — no regression |
| our pin | exact | exact |

> ✅ **no new trust relationship** — same party, same pipeline, same registry signature. the one
> change is *which artifact of theirs we consume*.
>
> ⚠️ **the honest gap: neither version carries an npm provenance attestation.** the registry's
> attestations endpoint returns 404 for both. `dist.signatures` attests that the registry *received*
> the tarball, never that a named workflow *produced* it — distinct, and easy to conflate. **not a
> regression**, and the one axis on which a copy we build ourselves would be strictly stronger; that
> option is recorded below as a separable refinement.

**what makes the prerelease safe enough, beyond the unchanged custody:**

- **the pin is exact** — no range, no `^`. npm forbids a republish under a tag past the 72-hour
  unpublish window, long closed (published 2026-08-03), so this tarball cannot move under us
- **645,342 weekly downloads** at the time of this read — production-scale usage for a prerelease
- 🚨 **`microsoft/vscode` pins this exact version.** its `package.json` (read 2026-08-28) carries
  `"node-pty": "^1.2.0-beta.15"` **and** an explicit `"allowScripts": { "node-pty@1.2.0-beta.15":
  true }`. vs code's integrated terminal is node-pty's largest consumer, and it runs this build
- **our own gates pass** — types, the pty integration suite, and a real spawn probe

**what it genuinely costs:**

- **optics** — a prerelease in a published dependency invites a reasonable question from any consumer
  who reads our manifest. a real cost, paid in trust rather than in defects
- **win32 lost winpty** — `1.2.0` drops the legacy backend for conpty only. conpty needs windows 10
  1809+, past end-of-life, so practical exposure is near zero, but it is a real behavior change and
  it is why the version is major-bumped
- **the package shrank** — 286 files / ~64mb → 49 files / ~26.9mb, largely dropped win32 `.pdb`
  debug symbols

**one property improves outright:** the bump **removes an arbitrary `node-gyp` compile from every
linux consumer's install.** at `1.1.0` a successful linux install runs a c++ toolchain over source on
the consumer's machine; at `1.2.0-beta.15` no compile occurs at all. fewer parts in motion at install
time is a supply-chain win in its own right.

### the platform matrix

the bound's second half. **every row is upstream's binary; we add none.**

| platform | `1.1.0` | `1.2.0-beta.15` |
|----------|---------|-----------------|
| **linux-x64 (glibc)** | ❌ **no prebuild** — the defect's home | ✅ **prebuild present**, glibc-2.28 sysroot |
| **linux-arm64 (glibc)** | ❌ no prebuild | ✅ **prebuild present** — a free second platform |
| darwin-x64 | ✅ prebuild | ✅ prebuild |
| darwin-arm64 | ✅ prebuild | ✅ prebuild |
| win32-x64 | ✅ prebuild | ✅ prebuild (conpty only) |
| win32-arm64 | ✅ prebuild | ✅ prebuild (conpty only) |
| **linux musl (alpine)** | ❌ none | ❌ **still none** — out of scope per A9; the glibc binary may install, then `dlopen` fails → `ERR_DLOPEN_FAILED` → null → the loud ConstraintError |
| freebsd, linux-riscv, other | ❌ none | ❌ none — loud ConstraintError |

**three properties deserve plain statement:**

1. **we publish no binary of our own.** every row is upstream's artifact, so there is naught new for
   us to attest and no platform we enter the business of support for
2. **linux-arm64 arrives free.** the bundled-copy design would have needed a second ci target for it
3. **every out-of-scope platform fails LOUD, never quietly** — verified through `isPtyAddonLoadError`
   (`getPtyModuleOrNull`'s catch), which matches `ERR_DLOPEN_FAILED` and returns null rather than
   swallow it

⚠️ **the honest gap:** a **musl host on x64** may install the glibc binary (the `os` gate says
`linux`; there is no `libc` gate) and fail at `dlopen` rather than at install. that is a *later* and
*louder* failure than an absent file, and it is acceptable per A9 — but it is a real edge, and it is
why the alpine row reads "may install, then fail" rather than "is skipped."

### acceptance #5 — the pty LOAD path is unchanged

the wish reads: *"darwin and win32 are unregressed — they have prebuilds today and must keep them."*

**they keep them, from the same upstream tarball, by the same in-package lookup, through the same
unchanged specifier at `getPtyModuleOrNull`'s import specifier.** so the claim owed is not *"the new binaries
also work on mac"* (an empirical claim that needs a darwin runner we lack) but *"the mac load path
is unchanged"* — a structural claim, checkable by a read of the three files that decide a load:

| file | what it decides | changed? |
|------|-----------------|----------|
| `getPtyModuleOrNull.ts` | the specifier and the load-error allowlist | ❌ unchanged |
| node-pty's own `lib/utils.js` | which of six candidate dirs holds the addon | ❌ upstream's, unchanged in shape |
| `isCloneSocketAvailable.ts` | whether a socket is even attempted | ❌ unchanged |

🚨 **the claim is structural, and diff size is not its instrument.** the change carries real
source elsewhere — the class split, the platform-support read, the hint repair, and their clamps
— so *"a small diff cannot move a code path"* would be an unsound inference here. what holds is
narrower and checkable: **no file on the darwin or win32 load path moves.** the platform read
(`getPtyPlatformSupport`) is downstream of the load — it decides which report to raise *after* a
load already failed — so it cannot alter a load that succeeds.

⚠️ **the caveat, stated rather than buried:** win32's *backend* changes (winpty dropped, conpty
only). that is upstream's change, not ours, and it is documented in the beta ledger above.

### what this does NOT fix

a cure that closes three surfaces still leaves three items open, and each is named rather than
implied.

| open item | why it stays open |
|-----------|-------------------|
| **the two-store trap** | the wish records that `rhx` execs from a stale `<pnpm-root>/.pnpm/` while pnpm writes to `<pnpm-root>/node_modules/.pnpm/`. **a version bump cannot cure that** — a correct new tree still lands in a store the shim never reads. an independent defect, and the single biggest risk to verification of acceptance #1 |
| **alpine / musl** | no upstream binary exists. out of scope per A9; fails loud |
| **four of our own packages have blocked build hooks** | `simple-in-memory-cache`, `with-simple-cache`, `simple-log-methods`, `with-simple-caching` sit in pnpm's `ignoredBuilds`. pure-js, so likely harmless — but it is the same defect class, and out of this wish's scope. worth its own look |

### the bundled-copy refinement, recorded

a copy of node-pty built in our own ci and carried in our tarball is **not** the recommendation —
the bump satisfies every acceptance criterion without it. but it buys one property the bump does
not, and that property is real enough to record rather than drop:

> a copy in **our** tarball cannot be substituted by a compromised registry publish or a poisoned
> mirror. a copy we fetch at install time can.

what it costs, on top of the bump: a ci copy step, a `files` entry, a load-time fallback branch,
~280k of tarball for linux alone, and a clamp that fails loud when the copy's source is absent. it
would also want an **inversion on linux only** (ours first, upstream second) to actually claim the
property — because per `term=fallback`, only the copy the primary loads is the copy an attacker
must reach.

⚠️ **and its sharper bound: it defends against a REGISTRY-level substitution, never a local one.** an
attacker who can write into `node_modules` can equally write into our `bin/`.

**recorded as a separable, clean rework** — it composes on top of the bump rather than competes with
it, and it is the wisher's call whether the property is worth the branch. it is not folded into the
recommendation because the bump alone satisfies every acceptance criterion, and
`rule.require.fewer-paths-via-idempotency` says a branch must earn itself.

### the contingency

if the beta proves unacceptable for reasons of optics rather than defects, `@lydell/node-pty` remains
available: mit, zero lifecycle hooks, zero runtime deps, the same pinned `1.1.0` upstream source, and
a platform matrix that already covers linux-x64 and linux-arm64.

it is **not** the recommendation. its binaries carry **no** provenance attestation (a 404, same as
upstream's) **and** are hand-published from a developer machine (`_nodeVersion = 20.12.1`) by a repo
with **no ci at all** — so it is strictly weaker than upstream on the axis the wish's bound asks
about. it also carries an unverified dependency of its own (**R1**: how its parent locates the peer
package's binary is undocumented).

## user experience

### who, and what goal

| user | goal | today |
|------|------|-------|
| a linux human who installs rhachet globally | enroll a reachable clone | blocked, with a false cure |
| a linux human who installs rhachet locally in a repo | same | blocked unless their *own* `package.json` allowlists a dep they never declared |
| a ci runner on `ubuntu-latest` | run acceptance tests that need a socket | blocked |
| the learner's subconscious (`bhrain#367`, built on `rhx clone say`) | dispatch a say into a live clone | ⚠️ blocked, but **not** "silently" — see the trace below |
| a darwin/win32 human | unchanged | already works |

> ⚠️ **the wish's "silently degrades" phrase does not match the traced behavior.**
> `isCloneSocketEligible` gates on `socketCapable && interactive && !noSocket`, and
> `genCloneOndisk` skips the loud error when that is false. so there are two paths, and
> only one is node-pty's:
>
> | enroll | on linux today | node-pty's fault? |
> |--------|----------------|-------------------|
> | **interactive** | `wantsSocket` true, addon absent → **LOUD ConstraintError**, no clone made | ✅ yes |
> | **non-interactive** (cron / dispatch handler) | `interactive` false → the pty is never loaded → a **DEAF** clone | ❌ no — identical on a healthy macos host |
>
> **the enroll fails LOUD; it is the INSTALL that is quiet.** the deaf path is by design and
> platform-independent. the #367 dependency is still real — its clones need a socket, and on linux an
> interactive enroll cannot make one — but the *mode* of failure should be re-verified before it is
> designed against.
>
> one find the same trace surfaced, and it proved to be IN scope: a deaf clone's `say` hint
> (`computeCloneUnreachableHint`) listed brain / posix / `--no-socket` as though they were every
> condition, so on a linux host a reader could satisfy all three and still fail — pointed *away*
> from the real cause. the hint now names a pty addon that will not load, marks its list `one of
> several` so it reads as partial, and routes to the enroll as the diagnostic, since only the
> enroll knows which row fired.

### the contract they leverage

they leverage **no new contract**. that is the point of this wish: the surface that must change is
`package.json`, not the cli. the contracts they touch are the extant ones:

```bash
rhx enroll claude                              # stands up a clone with a reach socket
rhx clone say @:<slug|serial> --what "…"       # the dispatch primitive
rhx enroll claude --no-socket                  # the deliberate opt-out, unchanged
```

⚠️ these are the **verified** signatures, not paraphrases. `invokeCloneSay` declares
`.command('say <address>')` with a `.requiredOption('--what <message>')` — the address is
**positional**, and the message flag is `--what`, never `--to`/`--msg`.

the one user-visible contract that changes is the error `genCloneOndisk` raises when no socket
can be opened, and it changes in **both** of its halves — the class and the hint.

`genCloneOndisk` throws `asCloneSocketOmissionReasonError(...)`, which yields a `MalfunctionError`
(exit 1, ours to fix) on a platform that ships a prebuild, and a `ConstraintError` (exit 2, the
caller's to amend) elsewhere. the hint names a move that works on the host it is read on:
`rhx clone get` to observe, or a re-enroll to make the clone reachable. `pnpm rebuild node-pty`
is named by no production line.

### timeline

```
t0  human runs `pnpm add -g rhachet` on linux-x64
t1  pnpm unpacks our tarball; node-pty arrives with prebuilds/linux-x64/pty.node inside
t2  node-pty's install hook is gated by pnpm — and it would have exited 0 anyway
t3  human runs `rhx enroll claude`
t4  getPtyModuleOrNull() -> require('node-pty') -> lib/utils.js probes
       ../prebuilds/linux-x64/pty.node -> found -> non-null
t5  isCloneSocketAvailable -> true -> pty clone spawns with a live socket
t6  human runs `rhx clone say` -> the clone hears it
```

the contrast with today is entirely at **t1–t2**. all downstream already works.

⚠️ note what t2 says: the gate still fires, and pnpm still prints its ignored-build line. we do not
defeat the gate, argue with it, or ask the human to lift it — its outcome simply stops to matter.

## mental model

### how a human would describe it to a friend

> "rhachet needs a real terminal to talk to a clone. it used to try to *compile* one on your machine
> at install time, and on linux your package manager wouldn't let it. now the terminal bit just comes
> in the box, already built — the upstream folks started to ship one right after the version we were
> stuck on."

### the analogy that fits

**a prebuilt vs a kit.** we shipped ikea flat-pack for linux (a gyp manifest plus a compiler
invocation) and a fully assembled chair for mac and windows. pnpm 10 confiscates the screwdriver at
the door.

⚠️ **and the twist: the manufacturer started to ship the assembled linux chair ten days after our
order.** we did not need to build a workshop. we needed to reorder.

the industry name for the assembled-chair pattern is **prebuilds** — a binary per `platform-arch`,
carried in the package, selected at load time with zero compile. node-pty at `1.2.0-beta.15` ships
six of them.

### their words vs ours

| they say | we say |
|----------|--------|
| "the terminal bit" | the pty / node-pty native addon |
| "it can't talk to the clone" | the reach socket is unavailable |
| "it didn't install right" | the install hook was blocked by pnpm's build gate |
| "my mac coworker doesn't have this" | darwin ships a prebuild in-tarball; linux did not, until `1.2.0` |

⚠️ **the vocabulary gap is itself part of the defect.** the current error speaks entirely in *our*
words (`node-pty failed to load`, `pnpm rebuild node-pty`) and hands the human a term they cannot act
on. whatever cure ships, the residual error must speak in theirs.

## evaluation

### how well it solves the goals

against the wish's five acceptance criteria:

| # | criterion | how the vision meets it |
|---|-----------|------------------------|

### what this section owns

**1es is microsoft's own build platform** — the provenance detail the account above cites but does
not itself hold. node-pty's `pipelines/prebuilds.yml` extends
`v1/1ES.Official.PipelineTemplate.yml@1esPipelines` with `sdl.tsa.enabled: true`; `publish.yml`
extends the npm-package template from microsoft's vscode build-infra repo with
`publishRequiresApproval: true` for stable releases. so the prebuilds come off hardened
microsoft-internal pools with compliance scans, and a stable publish is gated on an approval —
upstream's own infrastructure, unchanged between the two versions.

**🚨 `pnpm rebuild` has no `--global` flag at all**, and this is the decisive half of why the named
cure is a dead end. `pnpm help rebuild` lists only `-C, --dir <dir>` as a scope flag, whereas
`pnpm approve-builds` *does* carry `-g`.

> so `pnpm rebuild node-pty` cannot reach a global install by ANY invocation. a human who ran
> `pnpm add -g rhachet` and then follows the hint verbatim asks pnpm to rebuild a dependency of an
> unrelated local project — which of course exits 0 and changes naught. the hint is not merely
> *gated* by an allowlist; it is **categorically incapable** of the case it was written for.

**a stopgap exists today with no code change**, for the common case (linux, pnpm ≥10, global
install, toolchain present):

```bash
pnpm ignored-builds        # the one-line diagnostic that surfaces the whole defect
pnpm approve-builds -g     # allowlist node-pty in the GLOBAL config
pnpm add -g rhachet        # re-install, so the now-approved build hook runs
```

this does **not** retire the wish — acceptance #2 forbids a manual allowlist step. its value is that
it makes **acceptance #3 separable from the bump**: a human on a broken host can reach a live socket
by hand, so the report they read matters on its own timeline. that separability is what let the class
split ship as its own concern rather than as a rider on the version bump.

**the addon lookup, which is why no patch is needed.** node-pty's own `lib/utils.js`,
`loadNativeModule`, probes six candidates — `['build/Release', 'build/Debug', "prebuilds/" +
process.platform + "-" + process.arch]` crossed with `['..', '.']` — each a **relative** specifier
resolved against `node_modules/node-pty/lib/`. at `1.1.0` on linux all six miss; at
`1.2.0-beta.15` the third hits. **the lookup is identical across the bump; only what sits on disk
changed.** that is the mechanism behind acceptance #5's structural claim.

**no install-time handler of ours exists anywhere.** a grep of `src/` for
`onlyBuiltDependencies|allowBuilds|node-pty|pnpm rebuild` returns only the loader, the error
strings, and type imports — no postinstall of our own, no self-heal, no allowlist write. a negative
result, and it is what makes the declare-time cure the whole cure.

### two term notes the blueprint had to obey

- **`notice` vs a blocked report.** the pty-absent error is a `ConstraintError` carrying a `hint`,
  which this glossary calls a **blocked report** (`term=blocked`). it is **not** a `notice` —
  that noun is reserved for a nullable render a *successful* command leaves behind (`term=notice`).
  so the artifact was named as a report, never `asPtyAbsentNotice`.
- **`vendor` is overloaded, so it is barred from contracts.** `term=flag` fixes `vendor` here as
  *the third party we did not write*; the npm sense — to bundle a copy into our own tree — is the
  reverse. inherited from the wish, so **safe in prose and forbidden in a contract**: no dobj, dop,
  field, flag, or path segment may be named `vendor*`. recorded in
  `term=fallback._.choice.reason.md`. ✅ `fallback` is itemized for the same round's reason — the
  recorded bundled-copy refinement rests on its ORDER alone, and a fallback promoted to primary
  voids the property it was meant to buy with no test to go red.

## what is awkward?

🚨 **this section holds only what it OWNS.** the prerelease's optics and the forgone supply-chain
property are both genuinely awkward, and both are already stated in full by the sections that own
them — a second copy here would be the exact defect class this change spent the round to retire
(`rule.forbid.revision-accretion-in-deliverables`). they are named rather than restated:

| the awkward part | its owner above |
|---|---|
| we depend on a prerelease, and it cannot be made to feel clean | `### the beta and its provenance, weighed honestly` → *what it genuinely costs* |
| the stronger supply-chain property is forgone | `### the bundled-copy refinement, recorded` |

### 1. a workaround for an open upstream gap is indistinguishable from one for a closed gap

the whole cure is a version bump. a self-built copy in our own ci is the design a reader reaches
for who takes the `1.1.0` platform matrix as fixed — it is sound, it satisfies every criterion,
and it is **unnecessary**, because upstream shipped linux prebuilds ten days after the release we
pin.

the awkward property is structural, not incidental: **the two designs look identical from the
inside.** a workaround for an open gap and a workaround for a gap already closed have the same
shape, the same justification, and the same tests. what separates them is one fact about someone
else's release history — a fact that lives outside the repo, and one `npm view` away.

> **before a design that works around an upstream gap, check whether upstream has closed it.**
> a pinned version is a snapshot of a moment, and the moment moves.

### 2. ⚠️ the two-store trap is a SEPARATE defect this vision does not cure

the wish records that `rhx` execs from a stale `<pnpm-root>/.pnpm/` while every `pnpm` command writes
to `<pnpm-root>/node_modules/.pnpm/`, and that neither is a symlink. `bin/rhx:10-25` faithfully
follows whatever symlink chain it is given — it is not the cause.

**if that trap is live, this wish's cure will appear not to work**, because a correct new tree gets
installed into a store the shim never reads. worse, it will fail the same opaque way. this vision
deliberately does **not** claim to fix it. it is a distinct defect that likely deserves its own wish,
and it is the single biggest risk to verification of acceptance #1.

### 3. the install's exit code is a property of the PACKAGE MANAGER — of its major AND its command — never of this cure

after the change, node-pty does **not** appear in pnpm's ignored-build notice in this tree, and
`node_modules/.modules.yaml` confirms it is absent from `ignoredBuilds`.

the measured behavior in a **bare consumer project** — its own manifest, no allowlist — is not one
fact but **four**. the report varies on two axes, and the second was the surprise:

| the consumer runs… | pnpm **10.24** (our pin) | pnpm **11.18** |
|---|---|---|
| `pnpm install` (local) | quiet WARN · **exit 0** | `ERR_PNPM_IGNORED_BUILDS` · **exit 1** |
| `pnpm add -g` (global) | quiet WARN · **exit 0** | **no gate line at all** · **exit 0** |
| the addon loads + spawns | ✅ every cell | ✅ every cell |

🚨 **the global row is the one that matters most.** the wish's literal entrypoint is
`pnpm add -g rhachet`, and on that command pnpm exits **0 at both majors** — so
`execNpmInstallGlobal`, which classifies a NONZERO exit, has none to classify. a blocked build
hook cannot be reported to a human as a failed global install.

the noisy exit-1 cell is pnpm 11's **local** install alone. it is identical at both node-pty
versions and both depths, so this cure neither causes nor cures it.

**the capability is INVARIANT across every cell; only the report differs.** the gate's outcome
stops to matter for whether the socket works, while pnpm's exit code is a separate subject.

⚠️ **so a claim about the report is only ever true of ONE cell.** each axis carries load on its
own: the version, because a measurement taken on an ambient pnpm says naught about the pinned one;
and the command, because `pnpm install` and `pnpm add -g` diverge sharply at pnpm 11. a result
measured in one cell and quoted for another is the same shape as the defect this wish exists to
retire — a convenient fact, honestly labelled, carried past its own subject.

that is why the whole matrix is held as **data the clamp re-measures every run**, never as prose:
`getPtyModuleOrNull.consumer.integration.test.ts` pins the `packageManager` from our own manifest
and confirms the pin took — twice, the second time from the install's own output, since
`pnpm add -g` skips the manifest check — and keys the report by `(target, major)` so no cell can
borrow another's answer. the local rows are `[case6]`/`[case8]`, the global rows `[case9]`.

### 4. 🚨 the class split — acceptance #3 was never a string swap, and the awkward part is why

with the prebuild in the tarball, a supported platform should never see this report at all. so the
two conditions that remain are **not the same kind of event**, and one `ConstraintError` for both
conflates them. `asCloneSocketOmissionReasonError` picks the class from the platform:

| addon absent on… | what it means | class |
|------------------|---------------|-------|
| a **supported** platform (linux/darwin/win32, glibc) | the prebuild ships in the tarball, so this should be impossible. if it happens, **our artifact or the install is broken** | 🔴 `MalfunctionError`, exit 1 — *we* must fix |
| an **unsupported** platform (alpine/musl, freebsd, riscv) | expected forever; no binary exists and none is planned. the caller can only amend the request | 🟡 `ConstraintError`, exit 2 — `--no-socket` |

⚠️ **the awkward part is what the one-line criterion invited.** the wish's #3 reads *"the degraded
notice … names a fix that WORKS"*, which sounds like a string edit — swap a dead command for a live
one and the criterion is met. it is not. a hint is only half the report; the **class** is the other
half, and the class was wrong in the first row: it told every human *"you can fix this"*, which is
true on alpine and false on a broken ubuntu install. that is loud about the wrong party, which is
the failure mode `rule.forbid.failhide` names, produced by a report written to retire it.

so a criterion phrased around a *message* concealed a defect in a *type*. worth recorded, because
the same shape recurs: a small-sounding acceptance line can sit on top of a structural change, and
the size of its phrasing says naught about the size of its subject.

⚠️ and the residual shrug narrows to one row: on a genuinely unsupported platform, `--no-socket` is
the only move, and it is an opt-out rather than a repair. honest, narrow, and worth stated plainly.

### 5. the `set.package.upgrade` skill could not perform this bump

`rhx set.package.upgrade --package node-pty --to 1.2.0-beta.15` failed with `package not installed.
use set.package.install instead.` — because its manifest read covers `dependencies` and
`devDependencies` only, never `optionalDependencies`. the bump was applied by a direct edit plus
`pnpm install`, which bypassed the skill's security audit step.

**that is a real skill gap**, out of this wish's scope, and worth its own report: the one dependency
class most likely to hold a native addon is the one class the upgrade skill cannot see.

## the fulcrum

per `rule.always.defer-fulcrums-to-last`, the design fork is best-guessed and the reversal is named
rather than escalated.

**the fork is: do we accept a prerelease pin to get the fix now, or hold at a stable version that is
broken on linux?** this vision takes the prerelease, for the evidence in A12.

**it does not go to the wisher, because the wish already decided who decides.** the how is delegated
outright, and the bound on it — *"an explicit account of provenance and of the platform matrix"* — is
a deliverable, produced above, never a permission to request.

**what genuinely remains human:** the stone's own approval gate. that is the route's checkpoint, not
a question of mine, and it is relayed rather than invented.

### the recorded rework offer

| if the wisher prefers | the rework |
|-----------------------|------------|
| to wait for stable `1.2.0` | hold the pin at `1.1.0` and ship acceptance #3 alone (a truthful hint), then bump when stable lands. **clean** — but linux stays broken meanwhile |
| the platform-package contingency (`@lydell/node-pty`) | swap the specifier at `getPtyModuleOrNull`'s import specifier plus two type imports. **clean** — R1 must be verified first, and its provenance is weaker |
| 🔓 **the bundled copy** (the supply-chain refinement) | additive on top of the bump: a ci copy step, a `files` entry, a linux-only load fallback, and a clamp on the copy's source. **clean** — it composes rather than competes |
| our own `node-gyp rebuild` at enroll time | drop the bump, add a probe-and-build to the enroll path. **clean**, and strictly worse: needs a toolchain on every host, helps no bare `pnpm add -g`, and moves a ~60s compile to first enroll |

each is a clean reversal, so per the rule the drive continues rather than halts.

### the dream

**drop the prerelease pin the moment `1.2.0` publishes stable.** a one-line reversal, no design
attached, and the discipline that keeps `beta` from a permanent address in our manifest. filed as a
task so it does not depend on anyone's memory.

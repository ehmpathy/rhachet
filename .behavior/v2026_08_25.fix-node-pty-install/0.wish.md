# wish: node-pty is reliably usable on linux, with no manual step by the human

**seeded as `ehmpathy/rhachet#475`.** this is the local wish for the sprout of that task.

## .what

`rhx upgrade`, and the install generally, must leave **node-pty usable on linux** — no manual
allowlist edit, no rebuild command, no human who has to know a transitive optional dep exists.

today `rhx enroll claude` degrades with:

```
✋ the reach socket is unavailable — node-pty failed to load
   └─ run `pnpm rebuild node-pty` to enable it, or pass --no-socket to enroll without one
```

**and the named fix is a dead end** — `pnpm rebuild node-pty` exits 0 with no effect.

## .why

### it silently disables a whole capability, and names a cure that does not work

this is `rule.require.errors-name-the-fix` inverted: the error names a fix **with confidence**, the
fix runs clean, and naught changes. an operator who trusts it re-runs it, and re-runs it again.

that is worse than an unhelpful error — a bare failure sends a human to look, while a confident
wrong cure sends them in a circle. the exit-0 rebuild is the part that costs hours.

### it gates the clone reach socket — so it blocks work already dispatched

the loader lives at `dist/domain.operations/clone/pty/getPtyModuleOrNull.js`. **node-pty IS the
clone reach socket.** so every `rhx clone` capability that needs a live socket degrades with it.

that is not hypothetical: **`ehmpathy/rhachet-roles-bhrain#367`** (the learner's subconscious
distillation) is built on `rhx clone say` — a message dispatched into a live clone. if the socket
silently degrades on linux, that behavior cannot work on linux, and its failure would present as
the subconscious quietly never notifying rather than as an install defect.

**so this is upstream of #367.** worth stated ordering, and it is a fact about the dependency, not
a claim about their priority.

## .acceptance

1. **a clean install on linux yields a usable node-pty** — proven by a load of the addon through
   rhachet's own module lookup, never by a `pnpm ls`
2. **no manual allowlist step is required of the human** — the ask is explicitly that the install
   handle it
3. **the degraded notice, if it can still fire, names a fix that WORKS** — a cure that exits 0 with
   no effect is the defect, not merely a symptom of it
   (`rule.require.errors-name-the-fix`)
4. **a clamp goes RED on the current code** — per `rule.require.clamp-edge-cases`, the proof and
   the guard are one artifact. the edge case is the CLASS (a native optional dep on a platform with
   no prebuild), never the single version
5. **darwin and win32 are unregressed** — they have prebuilds today and must keep them

## .scope

**in scope:** how rhachet declares, installs, and loads node-pty; the notice it prints when the
load fails.

**out of scope, and these bind:**

- **do NOT answer this with a default of `--no-socket`.** that turns a broken capability into an
  absent one and makes the degradation permanent
- **do NOT vendor a prebuilt binary** without an explicit account of provenance and of the platform
  matrix — a silently wrong binary is worse than an absent one
- **do NOT edit the consumer repos' lockfiles as the fix.** the ask is that rhachet's own install
  is correct; a per-consumer patch is the workaround this task exists to retire

## .what was already verified — carried from #475

**these are that task's findings, recorded there from a live diagnosis. re-verify at your HEAD.**

1. rhachet declares `node-pty@1.1.0` as an **optionalDependency** — confirmed independently:
   `npm view rhachet@1.47.2 optionalDependencies` → `{ 'node-pty': '1.1.0' }`
2. node-pty 1.1.0 ships prebuilds for **darwin-arm64, darwin-x64, win32-arm64, win32-x64 only** —
   no `linux-x64`. on linux it must compile via `node prebuild.js || node-gyp rebuild`
3. **pnpm >= 10 blocks dependency lifecycle commands** unless allowlisted
   (`pnpm.onlyBuiltDependencies` in v10, `allowBuilds` in v11)
4. so at `pnpm add -g rhachet` time the build is blocked, the optional dep fails, and **pnpm drops
   it quietly** — node-pty ends up ABSENT from the global store, not merely unbuilt
5. `getPtyModuleOrNull` catches the load failure and prints a notice naming a command that cannot
   work, because a human has no way to know a transitive optional dep needs an allowlist entry

### ⚠️ the second trap — TWO global stores

recorded in #475 as the part that cost the most time, and it deserves a direct guard:

- `<pnpm-global-root>/node_modules/.pnpm/` — the current store, where every `pnpm` command writes
- `<pnpm-global-root>/.pnpm/` — a **stale** store, which the `rhx` bin shim actually `exec`s from

**neither is a symlink.** so `pnpm add -g` + `pnpm rebuild` repaired a tree that `rhx` never loads,
while every direct check reported the addon fine.

the one read that saw it was a replay of rhachet's own module lookup from its real dist path, which
returned:

```
FAIL: Cannot find module './prebuilds/linux-x64//pty.node'
```

**note the doubled slash** in that path — worth a look on its own, and yours to judge whether it is
incidental or a second defect.

### a data point from the dispatcher's host — it does NOT contradict the above

on this machine `node_modules/node-pty/build/Release/pty.node` **exists**, so a local project
install did compile it.

⚠️ **that is a read of a LOCAL store, and #475's defect is in the GLOBAL one.** the two are
different subjects, so this neither confirms nor refutes the report — it is recorded to stop a
later reader who runs the same check from a conclusion that the defect is absent. per
`partial audit`: an artifact records the state of the subject it IS.

# vision — fix-config-blend

vocab (wish appendix B): **roles** are ambient · specific. **actors** are repo · hash · slug.
readers: folks alias `claude` → `rhx enroll claude`, so every reader of a brain dir is an enrolled clone.

## the outcome world

### before

- a bare `rhx enroll claude` derives a HASH actor for the ambient roles (measured: `actor.via.hash=bb10e9fb`),
  so the ambient roles live in two actors — the repo actor and a hash twin
- every actor dir holds a real `settings.json`. `rhx init` writes EVERY linked role's hooks into each one
  (`syncHooksForLinkedRoles.ts:178-207`), whatever roles the actor holds
- a clone spawns with `CLAUDE_CONFIG_DIR=<its actor dir>` and the `user,local` config sources plus a filtered
  `--settings` file. so the all-roles `settings.json` rides in as the user layer and undoes the filter
  (inferred from the code path)
- the `local` source reaches a clone through its cwd, so a clone also reads the repo actor's
  `settings.local.json` — a read across actors (measured: claude logged it dropped 14 of that file's
  `permissions.allow` entries as untrusted)
- trust lives per actor, so a fresh actor starts untrusted even when the human trusted the repo long ago
- the human's `~/.claude/settings.json` (model, env, deny rules) never reaches a clone
- the repo actor is named `actor.via.slug=.default`, and "default" names both an actor and a roleset

a human asks "why does my `-driver` peer still get route.drive stop hooks?", "why does my clone ignore the
model i set?" — and the answer is a blend no file name shows.

### after

the actors:

```
.agent/.actors/
  actor.via.repo=ambient/     # the repo actor — the ambient roles, and the only home of them. tracked
  actor.via.hash=<h>/         # a hash actor — specific roles, from `rhx enroll --roles …`
  actor.via.slug=<s>/         # a slug actor — specific roles, declared in actors.yml
```

🔴 a bare `rhx enroll claude` — what an aliased `claude` runs — lands in the repo actor. structurally: one
derivation maps a roleset to its actor, and a clamp refuses to mint a hash actor for the ambient roleset.

every actor dir, one layout:

```
.agent/.actors/<any actor>/brain/.claude/
  CLAUDE.md            -> AGENTS.md
  AGENTS.md                                       # @boot.md
  boot.md                                         # REAL: this actor's roles, rendered; opens with the rhachet intro
  settings.repo.json                              # REAL: this actor's roles' hooks + permissions
  settings.grove.json  -> ~/.claude/settings.json # the grove (the box); gitignored — a home path
  settings.json        -> settings.grove.json     # claude's fixed name → our clear name
```

every clone spawns with `CLAUDE_CONFIG_DIR=<its actor dir>/brain/.claude`, the `user` config source only, and
`--settings <its actor dir>/brain/.claude/settings.repo.json`:

| slot | file | rank |
|---|---|---|
| `--settings` | `settings.repo.json` | high — 🔴 the repo outranks the grove (requirement) |
| user | `settings.json` → `settings.grove.json` → `~/.claude/settings.json` | low — the grove fills every key the repo leaves unset |

- each clone reads exactly ONE actor dir — its own. no project or local source, so the cwd never reaches the
  repo actor's dir
- 🔴 every actor and clone trusts the repo: each enroll grants trust outright (under the repo path and, in a
  worktree, its main checkout), which subsumes an inherit from the repo actor
- every `boot.md` opens with a few lines from rhachet: you are enrolled, `rhx list` shows your skills,
  `rhx <skill> --help` shows how to call one, and a tactic worth repeat becomes a skill

### the aha

`ls -l .agent/.actors/*/brain/.claude/` shows the SAME six names in every actor, the same arrows, and two
real files whose content differs by roles. the human edits `~/.claude/settings.json` once and every clone on
the box picks it up; a role hook they add, then `rhx init`, lands in exactly the actors that hold that role.
the human trusts the repo once, and no clone asks again. and the dir names answer "which actor?" on sight —
the everyday `claude` is always the repo actor.

## mental model

- to a friend: "every clone gets the box's settings, with its roles' settings on top; the file names say
  which is which."
- grove and tree — keyrack's words already (`define.keyrack-org-scope.grove-vs-tree`): the grove is the box.
- actors vs roles: "which identity" (repo · hash · slug) and "which roles" (ambient · specific) are two
  questions, each with its own words (`term=ambient`). the everyday `claude` = ambient roles = the repo actor.

## evaluation

- goals: kills the blend (a clone reads only its own actor dir, with only its roles); delivers box defaults
  to every clone, shadowed by the repo; makes provenance legible (`ls -l`); retires "default"; routes every
  bare enroll to the repo actor with no way to miss; one trust grant covers every clone.
- pros: one layout → one code path; symlinks are live reads, so the sync invariant holds; one derivation +
  a clamp makes the ambient route structural; enroll's config moves to the actor that owns it.
- cons:
  - the file claude calls `settings.json` is the per-box grove, the reverse of its usual "shared project" role
  - `/model` or `/config` in a clone forks the grove for that actor alone (claude renames a temp over
    `settings.grove.json`), and the next layout findsert keeps the fork aside and relinks — a durable default
    belongs in the box or a role
  - the rename moves a tracked dir, so the first `rhx init` after upgrade shows a git diff in every repo
  - extant hash twins of the ambient roles become orphans, reaped by prune once their clones are DEAD
- pit of success: the writer names `settings.repo.json` as a constant, so no path writes through an arrow;
  the clamp makes a hash twin impossible; a grove link is skipped when `~/.claude/settings.json` is absent;
  a forked arrow is detected and relinked; trust is carried, never re-asked.

## open questions & assumptions

- **which outranks, the repo or the grove?** the repo — the wisher's requirement (2026-09-27).
  → **[answered]** by the wisher

- **is there a slot below user, or does `--settings` stack?** no slot ranks below user (docs). a second
  `--settings` replaces the first whole — measured: `{model:haiku}` then `{env:{…}}` ran on the default
  model. so the grove rides the user layer, and the repo rides `--settings`.
  → **[answered]** by docs + probe

- **where does a bare enroll land?** the repo actor, always, by one derivation + a clamp.
  → **[answered]** by the wisher: "structurally fixed … impossible to fail … clamped"

- **does a `--roles` list whose resolved set equals the ambient roles land in the repo actor too?** yes —
  identity by roleset, so the route follows from the roles, not the flags.
  → **[answered]** by the wisher (2026-09-27): identity by roleset — a `--roles` list whose resolved set equals
  the ambient roles lands in the repo actor, same as a bare enroll

- **does a new actor trust the repo?** yes — every enroll grants trust outright, into the actor's
  `.claude.json` beside the first-run state, which subsumes an inherit from the repo actor.
  → **[answered]** by the wisher (2026-09-28: the blanket grant stays)

- **where do claude's own writes land?** `/model` or `/config` in a clone: claude resolves `settings.json`
  one link and renames a temp over `settings.grove.json` — a fork for that actor alone, which the next
  layout findsert keeps aside. where a clone saves an "always allow" with no local source is not observable
  via `clone say` (it needs a human at a live pty).
  → **[answered]** for `/config` (measured 2026-09-28; the wisher chose keep-aside) · **[research]** for
  "always allow"

- **does claude follow a symlinked `settings.json` in `CLAUDE_CONFIG_DIR`?** yes — measured 2026-09-27 on the
  raw binary: user `settings.json` → a scratch grove with `model: haiku`, plus `--settings` with no model,
  ran on haiku (it hit haiku's 200k window); the same with `--settings {model: sonnet}` ran on
  `claude-sonnet-5`. so the arrow is followed, the grove fills unset keys, and the repo wins a key both set.
  → **[answered]** by probe

- **does claude write `/model` in place or by temp+rename, and where does a clone save an "always allow"?**
  both need an interactive session (`-p` runs neither), so they are verified in the execution stone. case 6
  fails safe under either write mode.
  → **[research]** — at execution

- **what does the grove link target?** `join(getHomeDir(), '.claude', 'settings.json')` — the root the
  credential link uses (`findsertBrainCredentialSymlink.ts:22`).
  → **[answered]** from extant code

- **is `~/.claude/settings.json` safe to share with every actor?** a clone runs as the same os user, who
  can already read the file; the arrow grants no new read.
  → **[answered]** by logic

- **when are stale `settings.enroll.*.local.json` files pruned?** only once their actor has no live clone.
  → **[answered]**

- **is the per-actor all-roles sync a defect or a design?** a design (`syncHooksForLinkedRoles.ts:178-180`,
  usecase.9). every init still visits every actor; only the content changes — each actor's own roles.
  → **[answered]** from extant code

### external research

- https://code.claude.com/docs/en/settings (fetched 2026-09-27): precedence managed > `--settings` > project
  local > shared project > user; `CLAUDE_CONFIG_DIR` relocates the user files; lists merge across scopes; a
  git-tracked `settings.local.json` goes through workspace trust.
- https://code.claude.com/docs/en/cli-reference (fetched 2026-09-27): says naught reliable about repeated
  `--settings`; settled by probe instead.
- probe, 2026-09-27, three `claude -p` runs (aliased → `rhx enroll claude`, so each an enrolled clone):
  `--settings {model:haiku} --settings {model:sonnet}` → sonnet; reversed → haiku;
  `--settings {model:haiku} --settings {env:{PROBE:repo}}` → the default model. ⇒ the last `--settings` wins,
  whole. each run spawned under `actor.via.hash=bb10e9fb`; each logged the repo actor's `settings.local.json`
  read through the cwd, its allow rules dropped because that actor's `.claude.json` held no trust.

## what is awkward?

- the file claude calls `settings.json` carries the per-box grove, not shared project config. the clear
  names (`grove`, `repo`) are what make that legible.
- "identity by roleset" means a hand-typed `--roles` list that happens to equal the ambient roles lands in
  the repo actor — correct by the model, perhaps a surprise to a human who typed flags.
- the intro is the one brief that comes from no role. it must stay tiny, or it becomes an unowned role.

# case 11 — an init role delta re-derives a delta actor, live clone and all (e22)

## narrative

kai keeps a lean peer: `rhx enroll claude --roles -architect --as @:lean`, a delta actor that stands for
"the repo's roles, minus architect". its clone is live in another pane. later the repo drops driver:
`rhx init --roles -driver`. kai expects the lean peer to drop driver too — it was never "mechanic and
driver", it was "the repo, minus architect". so the init re-derives every delta actor from the new ambient
set: its `actor.json` roles, its `settings.repo.json`, and — since the actor has a live clone — its
`boot.md`. the delta itself never moves (it is the actor's identity), and the live clone is left alone; it
reads the new `boot.md` and settings on its next read. a second `enroll --roles -architect` lands in the
same actor, never a second hash dir.

## timeline

```
given a repo whose ambient roles are mechanic, architect, driver
  and a delta actor enrolled as `--roles -architect`, with a live clone @:lean
when [t0] before the init
  then the actor's boot.md holds driver and mechanic, never architect
when [t1] kai runs `rhx init --roles -driver` while @:lean lives
  then the actor's boot.md drops driver and keeps mechanic
  and actor.json reads roles = [mechanic], rolesDelta = [-architect]
  and settings.repo.json holds mechanic's hooks only — no driver, no architect
  and the init report a human reads is locked to a snapshot
  and @:lean still reads LIVE — the init never touched the clone
when [t2] kai runs `rhx enroll claude --roles -architect` again
  then it lands in the same actor — one hash dir, no twin
```

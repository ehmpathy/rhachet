# case 8 — a fresh actor inherits the repo actor's trust (e18, sharp, fail-safe spotlight)

## narrative

vlad trusted this repo the first time he opened `claude` in it; the repo actor's `.claude.json` records that.
he now enrolls a peer with specific roles — a fresh hash actor with its own config dir. today that peer starts
untrusted: claude drops the repo's allow rules and would prompt again (measured — "14 permissions.allow
entries" dropped). after the fix, enroll carries the grant into the new actor beside the first-run state, so
the peer is trusted from its first breath. and when the repo actor has NOT been trusted, the peer is not
either — rhachet never grants trust the human did not.

## timeline

```
given the repo actor's .claude.json has projects[<repo path>].hasTrustDialogAccepted = true
when [t0] `rhx enroll claude --roles -driver` spawns a fresh hash actor
  then that actor's .claude.json has projects[<repo path>].hasTrustDialogAccepted = true
  and the clone raises no trust prompt and drops no allow rule
when [t1] a second clone of the same hash actor spawns
  then it reads the same trust — carried once per actor, never per clone

given the repo actor's .claude.json holds no trust for the repo
when [t2] `rhx enroll claude --roles -driver` spawns a fresh hash actor
  then that actor's .claude.json holds no trust either
  and claude prompts, as it would for the repo actor
```

fail-safe: drops no data silently (the grant is carried whole), never over-grants (trust only flows from a
repo actor that holds it), and teaches the fix (an untrusted peer prompts exactly as the repo actor would).

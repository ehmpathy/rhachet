## ⚠️ amendment — 2026-08-03: a reach is PLAINTEXT, not a uri

**the body below was written against a uri-shaped reach (`{ scheme, org }`, parsed from
`github://org=$org` on every surface). that is superseded.** the wisher corrected it mid-build:

> "for os.secure it should not have any special treatment — just like a `.`. it just acts as a
> qualifier on the key name. so, we just look in a different spot for the value. thats it"
>
> "no url. no schemes. none of that for os.secure. its just plaintext … that only gets
> persisted in the encrypted host manifest"
>
> — the wisher

### what changed

> ⚠️ **the FIELD this section names `label` is `exid` since 2026-08-12** — see the amendment
> further down. the plaintext argument is unchanged; only the field's name moved.

| was | is |
|-----|-----|
| `KeyrackKeyReach = { scheme, org }` | `KeyrackKeyReach = { exid: string }` — plaintext |
| `asKeyrackKeyReach({ uri })` parses a scheme, rejects unknown ones | `asKeyrackKeyReach({ exid })` — rejects only empty / whitespace |
| `KEYRACK_KEY_REACH_SCHEMES = ['github']`, a closed set to extend | **deleted.** keyrack has no schemes; a territory is whatever a human calls it |
| the host-manifest zod schema validates `scheme` + an org regex | validates a non-empty, whitespace-free string |
| `--reach` refused on `PERMANENT_VIA_REPLICA` (e13) | **allowed** — see the derived / declared / refused split below |

### the rule that replaces the scheme

a reach label is **opaque to keyrack**. every vault and the daemon file a value under it and
look it back up; not one of them parses it. exactly one mech reads meaning into a label:

| kind | mech | what the reach does |
|------|------|---------------------|
| **derived** | `EPHEMERAL_VIA_GITHUB_APP` | the mech MINTS a token for one org's installation, so it needs an org it can look up. it requires the `github://org=$org` convention and parses the org out — in `asGithubOrgFromReach`, a **mech-local** parser. that convention now lives in the mech, not in the domain |
| **declared** | `PERMANENT_VIA_REPLICA` | a human pastes a secret and asserts which territory it opens. the mech carries the label through untouched; the vault files the value under it. **this is the os.secure claude-account juggle** — one key name, N copies, one per account |
| **refused** | `EPHEMERAL_VIA_AWS_SSO` | mints against an sso profile, its own territory axis. a reach here would move where the value is filed yet leave what it opens untouched — a label that lies. `assertKeyrackReachAbsent` still fires |

### the claude-account juggle, concretely

```sh
# cut one key per account — os.secure + PERMANENT_VIA_REPLICA, no scheme in sight
rhx keyrack set --key ANTHROPIC_API_KEY --env test --reach beav@ehmpathy.com
rhx keyrack set --key ANTHROPIC_API_KEY --env test --reach vlad@ehmpathy.com

# each lands in its own .age file — getCredentialPath hashes the ADDRESS, not the slug
rhx keyrack unlock --key ANTHROPIC_API_KEY --env test --reach beav@ehmpathy.com

🔓 keyrack unlock
   └─ ehmpathy.test.ANTHROPIC_API_KEY
      ├─ env: test
      ├─ org: ehmpathy               ← provenance, unchanged
      ├─ reach: beav@ehmpathy.com    ← destination, the plaintext label
      ├─ vault: os.secure
      └─ expires in: 540m
```

`@` is deliberately **allowed** in a label — an email is the obvious name for an account. the
address `$slug@$label` stays injective anyway, because a slug never holds an `@` except as its
leading `@all` wildcard, and no reader ever splits an address back apart (it is construct-only).

### what the amendment does NOT change

- **e1 still holds everywhere.** a reachless call takes zero new branches, writes the same
  bytes, and reads the same files
- **reach is still an identity axis**, not a modifier. one key per lock; a reach-key that was
  not cut does not exist, so there is no peer to silently fall back to
- **e6 still throws** on an unlock at a territory no key was cut for
- **e2's guarantee survives, relocated.** a bare word is no longer rejected by the domain
  parser — it is a legal label. but a github-app key still refuses one, in
  `asGithubOrgFromReach`, so a bare `ehmpathy` is never read AS an org. the guarantee moved
  from the parser to the mech; it did not weaken
- **q8's manifest `reaches:` block** is unchanged in shape; its entries are now plaintext
  labels rather than uris

### why this is better, not merely different

the uri was carrying a job it should not have. keyrack does not know what territories exist —
a github org, a claude account, a vpn profile — and it does not need to. the moment the domain
held a `scheme` enum, every new kind of territory became a contract change in a closed set. as
plaintext, the domain holds a name and the *one* mech that must act on a territory holds the
convention for reading it. the closed set is gone, and with it the migration it implied.

## ⚠️ amendment — 2026-08-05: a declared reach carries NO strength word

**q8 and q10 below settle on a `require` / `prefer` pair beside each declared reach, and that
pair is cut.** the wisher removed it mid-build:

> "seems like overkill for today" · "yagni" · "keep it simple" — the wisher

### what changed

| was | is |
|-----|-----|
| `reaches:` is a MAP — `require: [...]` / `prefer: [...]` | `reaches:` is a **flat list** of plaintext labels |
| `KeyrackKeyReachDirective` (dobj) + `KEYRACK_KEY_REACH_DIRECTIVES` | **deleted** |
| `KeyrackFillTarget = { reach?, directive }` | `KeyrackFillTarget = { reach? }` |
| a `prefer` target warns and carries on; `fill` exits 0 | **every** declared target halts; `fill` exits non-zero |
| `isKeyrackFillSkippable` (the soft-arm allowlist) | **deleted** — inlined into `isKeyrackFillProbeMiss`, the only consumer left |
| `asKeyrackFillSkipReason` (the skip render) | **deleted** |
| `FillKeyResult.status: 'set' \| 'skipped' \| 'skipped-preferred'` | `'set' \| 'skipped'` |
| `summary.skippedPreferred` | **deleted** |

```yaml
# was
reaches:
  require:
    - beav@ehmpathy.com
  prefer:
    - vlad@ehmpathy.com

# is
reaches:
  - beav@ehmpathy.com
  - vlad@ehmpathy.com
```

### what did NOT change — the half that carries the weight

**q8's core answer stands: the repo manifest DOES declare reaches, and `fill` DOES provision
them.** only the strength tier is gone. so the whole q8 argument — the requirement/possession
split, the FLOOR-never-a-cap rule, the "no keyrack command writes a repo manifest" line —
holds unchanged. q10's conclusion that `fill` provisions declared reaches holds too.

**and e1 is untouched.** a key that declares no reach takes one target, renders flat, and
behaves byte for byte as it does today.

### why the cut is an improvement, not merely a simplification

the soft arm carried the worse failure mode. a `prefer` skip **exits 0** and prints a yellow
line, so a human whose eye slid past it reads a partly-provisioned checkout as complete. an
unconditional halt cannot be misread — the render *is* the exit code, and there is no line to
miss (`rule.require.safe-by-default`).

it also cost six parts to express one word no manifest had said yet: a catch around the whole
per-target body, an allowlist to keep that catch from a failhide, a skip renderer, a third
result status, a fourth summary bucket, and a paired acceptance A/B to prove the two arms
differed.

### the clamps that replaced it

- **`hydrateKeyrackRepoManifest [case11][t2]`** — a `reaches:` block still authored as a MAP
  **throws**, never flattens. dogfooded: a lenient `Object.values(...).flat()` turns it red.
  this is the regression guard that matters, since old-shape manifests may sit on real machines
- **`keyrack.fill [case10]` / `[case11]`** — the same fumbled prompt at the LAST and at the
  FIRST declared territory. both halt, neither renders a skip. dogfooded: a restored tier turns
  both red on the exit code AND on the skip render. the pair proves position does not grade
- **`getAllKeyrackFillTargets [case2]`** — a declared target's shape is exactly `{ reach }`, so
  a strength field added beside a label shows up here

the full reversal, with the condition under which it would flip back, is recorded at
[`term=prefer._.choice._.md`](../../.agent/repo=.this/role=any/briefs/domain.terms/term=prefer._.choice._.md).

## ⚠️ amendment — 2026-08-12: the reach field is `exid`, not `label`

`KeyrackKeyReach.label` → `KeyrackKeyReach.exid`. the plaintext decision of 2026-08-03 is
untouched; only the field's NAME moved. the wisher settled it after two of my reversals:

> "since the Reach is used to route which key to mint at unlock time, its perhaps better
> identified as an exid after all … otherwise, label looks like it implies for display purposes
> only" — the wisher

### the argument that decided it

a **label** names something so a human can pick it out. an **exid** is the id the EXTERNAL
system knows, and it is what you address by. this value does the second job: the github-app
mech reads it (`asGithubOrgFromReach`) to choose **which installation to mint against**, so it
routes the mint. a name that routes is an exid.

⚠️ **both of my counters were wrong, and they are recorded rather than tidied away** (the full
record lives in [`term=reach._.choice.reason.md`](../../.agent/repo=.this/role=any/briefs/domain.terms/term=reach._.choice.reason.md)):

- *"it is never handed out"* — **false.** `asGithubOrgFromReach` consumes it, which is the very
  fact that makes it an exid
- *"`exid` asserts a grammar keyrack does not validate"* — **proves too much.** it would condemn
  `KeyrackKeyHost.exid` equally, which is an unvalidated external id by design

### what changed

| was | is |
|-----|-----|
| `KeyrackKeyReach = { label: string }` | `KeyrackKeyReach = { exid: string }` |
| `asKeyrackKeyReachLabel` | `asKeyrackKeyReachExid` |
| `asKeyrackKeyReach({ label })` | `asKeyrackKeyReach({ exid })` |
| `--reach <label>` in cli help | `--reach <exid>` |
| *"a reach label may not be empty"* | *"a reach exid may not be empty"* |

⚠️ **two `exid`s now sit near each other, and they are NOT one concept.**
`KeyrackKeyHost.exid` is the external id of the **key's storage** (a 1password item id, an
aws.params path). `KeyrackKeyReach.exid` is the external id of the **reach**. they live on
different objects and are never compared — but a reader who meets both deserves the note.

### the migration it owed

the host manifest is **encrypted on disk** and cannot be regenerated, so a machine that already
holds a reach-key holds it spelled `label`. an `exid`-only schema would reject that human's
**whole rack** — every key, not merely the reach one — with an error that points at a file they
cannot open.

so `schemaKeyrackKeyReach` **reads both spellings and writes only `exid`**: a `z.preprocess`
maps a pre-rename `{ label }` to `{ exid }`, and the dobj carries only `exid`, so a manifest
converts the first time keyrack rewrites it and never again.

clamped at `daoKeyrackHostManifest/schema.test.ts [case5]` — legacy read, native read, both
spellings at once (native wins), and an empty legacy value still refused (the read is a RENAME,
never a relaxation). **dogfooded:** with the preprocess reverted, `[t0]` and `[t2]` go red;
restored, all 10 green.

⚠️ **the schema is the WHOLE migration surface, verified rather than assumed.**
`schemaKeyrackHostManifest.safeParse` has exactly ONE call site —
[`daoKeyrackHostManifest/index.ts:102`](../../src/access/daos/daoKeyrackHostManifest/index.ts) —
so every host-manifest read on every machine funnels through the preprocess. that is why a unit
clamp suffices and no acceptance duplicate is owed.

### ⚠️ the rename was NOT confined to the field — two live defects it had left open

a compiler-driven rename catches every TYPED site and **no other**. two assertions read the
manifest as untyped `JSON.parse` output, so `tsc` was green while both were red:

| site | what it read | why the compiler could not see it |
|------|--------------|-----------------------------------|
| `keyrack.del.acceptance [case-reach]` | `parsed[…].reach.label` | `JSON.parse` yields `any`; `.label` is `undefined`, so the peer-survives clamp asserted naught |
| `keyrack.list.acceptance` (e16) | `.reach` `toEqual({ label: … })` | same — the e16 shape clamp compared against the pre-rename shape |

**the first is the worse of the two**, because `[case-reach]` exists precisely to prove a del at
one reach leaves its peer whole — a clamp that reads `undefined` would have gone quiet exactly
when a credential was destroyed silently. both now read `exid` and both suites are green.

> the lesson generalizes past this rename: **a field renamed in a dobj is only half-renamed until
> every untyped read of its serialized form is swept too.** grep the wire shape, not just the type.

### the sweep the rename also owed

- **the vocabulary, not merely the field.** `label` survived in ~40 comments, test names, local
  vars and fixture manifests. left alone, a reader who greps `label` finds a live vocabulary for a
  field that no longer exists — the exact ambiguity the rename was for. swept, with three
  categories deliberately **kept**: `KeyrackKeyRecipient.label` (a genuine display name, a distinct
  concept), `rule.forbid.ambiguous-labels` (a rule's name), and every line that names the
  pre-rename spelling ON PURPOSE (the migration notes, this amendment, the dispute record)
- **the fixtures.** three host-manifest fixtures spelled `reach: { label }`. they passed — which was
  accidental evidence the preprocess works end to end — but a fixture models what keyrack WRITES,
  and keyrack writes `exid`. flipped; the legacy read keeps its deliberate clamp at `[case5]`
- **an orphan removed.** `blackbox/.test/assets/with-keyrack-reach-declared/` had **zero** references
  repo-wide — it existed only for `keyrack.source.reach.enumerate.acceptance.test.ts`, which the
  announce-cut amendment (below) deleted. the test went; the fixture stayed. removed

### why the reversal, when r010 raised this across eight rounds

the argument that cut it is **new**, and it addresses the notice's own cost rather than the
hazard's severity:

- the notice fired on **every** call for any repo that holds a reach, always the same lines, never

- its real cost is that it trains a human to ignore **keyrack stderr** — which weakens the two
  notices that DO vary and DO demand action: the `assertKeyrackExportNamesDistinct` refusal
  (e23/q11) and the uncut-reach throw (e6)
- ⚠️ **and this was never e18.** the reachless value a flat sweep emits is the CORRECT one. this is
  *"fewer than exist"*, never *"the wrong one"* — far weaker cause to shout than the
  wrong-territory failure the design forbids. q11's tally of three loud paths still holds; what
  changed is that a fourth, quieter case stopped to shout

### where the fact lives now — one home, and a human consults it on purpose

`keyrack list` renders a `reach:` leaf per key, **one branch per (slug, reach)**
([`asKeyrackListTreestruct.ts:31`](../../src/domain.operations/keyrack/cli/asKeyrackListTreestruct.ts)).
the rack IS the disclosure. a human who asks *"what do i hold?"* is answered in full; a human who
runs `source` gets on with their day.

⚠️ **the `--help` caveat was ALSO cut** the same day — `source`'s description is back to
`'output export statements for shell eval'` — so the rack is now the single home. do not add a
second one without a reason that outweighs the fatigue argument above.

two corrections, both from the i060 peer round.

### 1. the bulk sweep is no longer reach-blind — the wisher chose ENUMERATE

r010 raised, across eight review rounds, the one hazard this vision never closed: **the bulk
sweep drops a territory in silence.** `keyrack source --env`, `keyrack get --for repo`, and the
sdk `sourceAllKeysIntoEnv` all returned the reachless credential and reported **not one word**
about the territories held beside it — with, in r010's words, *"zero runtime signal"*.

the wisher picked **enumerate** over warn-only and over refuse. what that means differs by the
NAMESPACE a surface emits into, and the split is the whole decision:

| surface | namespace | what "enumerate" means there |
|---------|-----------|------------------------------|
| `keyrack get --for repo` (tree / json), sdk `keyrack.get({ for: { repo } })` | **structured** — one entry per key | **literal.** every declared territory is its own attempt, with its own status and its own `reach` label |
| `keyrack source`, sdk `sourceAllKeysIntoEnv` | **flat** — `export FOO=`, one slot per bare name | **an announcement.** the namespace physically cannot hold two values under one name, so it emits the reachless one and prints a `⚠️` notice per territory it could not carry, which names the one-at-a-time fix |
| `keyrack firewall --into github.actions` | flat, and CI-only | **unchanged.** reach is a host-machine concept (q8) and CI holds no host manifest, so it has no territory to name |
| `getKeyrackKeySecrets` (brain creds) | flat | **unchanged this round** — see the flag below |

**why the flat surfaces do not simply refuse.** a throw was the attractive shape, since e23's
collision guard already exists and already names the fix. it is wrong here: a repo that declares
ONE territory would then be unable to source ANY of its keys, so the human loses every credential
to gain one fact. the notice reports the identical fact and costs them nought — and no wrong
credential is handed back on either branch, so the loud-and-usable form wins.

⚠️ **and the collision guard must be fed the FILTERED set.** `assertKeyrackExportNamesDistinct`
receives only the reachless attempts. to hand it the raw enumerate would make it throw for every
repo that declares a territory — the refusal above, arrived at by accident. that filter carries
weight, and it is why r010's *"dead-but-guarded"* read of the reach axis stays true.

### ⚠️ the boundary the enumerate does NOT cover, stated plainly

the sweep enumerates from **`KeyrackKeySpec.reaches`** — the REPO manifest's declared set, the one
`fill` provisions for every developer here (q8/q10). so:

- a **declared** territory is enumerated and announced ✅
- an **ad-hoc** territory — unlocked on the host, named in no manifest — is still invisible ⚠️

that is a cost, not an oversight. the daemon's `get` answers **one address at a time**

whose stdout is eval'd by a shell. the earlier in-code note that judged that unaffordable still
holds for this half; what it got wrong was the claim that a repo-manifest-derived check *"catches
no real case"*, since a declared reach is precisely the case `fill` exists to provision.

**the boundary is now tested from both sides**, so the uncovered half is a documented edge rather
than a silence found later:

- `keyrack.source.reach.enumerate` — a **declared** territory: enumerated, announced
- `keyrack.source.reach [t3]/[t5]` — an **ad-hoc** territory: still reach-blind, and its notes

**flagged for the wisher:** whether `source` should also announce ad-hoc held territories (one
extra daemon query, which would feed the same notice operation), and whether
`getKeyrackKeySecrets` should announce at all. both are clean, additive reworks.

## the outcome world

### a day in the life

a beaver is at work in `ahbode/svc-quotes`. mid-task it needs to file an issue into
`ehmpathy/rhachet` — a different org entirely. today that is a wall.

**before**

```sh
# inside ahbode/svc-quotes — manifest says org=ahbode
$ rhx keyrack unlock --owner ehmpath --env prep --key EHMPATH_BEAVER_GITHUB_TOKEN
🔓 keyrack unlock
   └─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
      ├─ env: prep
      ├─ org: ahbode          ← the app's ahbode installation
      ├─ vault: os.secure
      └─ expires in: 540m

$ rhx radio.task.push --via gh.issues --into ehmpathy/rhachet --title '...'
✋ HTTP 404: Not Found (https://api.github.com/repos/ehmpathy/rhachet/issues)
```

> the `404` is github's deliberate behavior, not a bug: an installation token that lacks
> reach to a repo is told the repo **does not exist**, rather than that it is forbidden.
> that is exactly why this failure is so expensive to diagnose today — the error names an
> absent repo, when the truth is an absent installation.

the token is real, the app is installed in `ehmpathy` too — but the minted token is bound
to the **ahbode installation**, so `ehmpathy` is simply unreachable.

**after** — two steps, and the first happens once

```sh
# step 1 — a human, once, cuts a key for the ehmpathy lock
$ rhx keyrack set --owner ehmpath --env prep --key EHMPATH_BEAVER_GITHUB_TOKEN \
    --reach github://org=ehmpathy
🔑 keyrack set
   └─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
      ├─ reach: github://org=ehmpathy
      ├─ mech: EPHEMERAL_VIA_GITHUB_APP
      └─ stored ✓
```

```sh
# step 2 — from then on, any caller names the territory
$ rhx keyrack unlock --owner ehmpath --env prep --key EHMPATH_BEAVER_GITHUB_TOKEN \
    --reach github://org=ehmpathy
🔓 keyrack unlock
   └─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
      ├─ env: prep
      ├─ org: ahbode
      ├─ reach: github://org=ehmpathy    ← the app's ehmpathy installation
      ├─ vault: os.secure
      └─ expires in: 55m

$ rhx radio.task.push --via gh.issues --into ehmpathy/rhachet --title '...'
🎙️ task enqueued → ehmpathy/rhachet#443
```

### the "aha"

> **you do not scope a key down. you cut a key per lock.**

the aha lands the first time a human runs `status` and sees the rack:

```sh
$ rhx keyrack status --owner ehmpath
🔐 keyrack status
   ├─ owner: ehmpath
   ├─ recipients:
   │  └─ vlad@laptop (ssh)
   ├─ daemon: active ✨
   ├─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
   │  ├─ env: prep
   │  ├─ org: ahbode
   │  └─ expires in: 55m
   ├─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
   │  ├─ env: prep
   │  ├─ org: ahbode
   │  ├─ reach: github://org=ehmpathy
   │  └─ expires in: 55m
   └─ ahbode.prep.EHMPATH_BEAVER_GITHUB_TOKEN
      ├─ env: prep
      ├─ org: ahbode
      ├─ reach: github://org=seaturtle
      └─ expires in: 55m
```

**three keys, one name.** same owner, same org, same env — the sole difference is which
territory each opens. neither evicts the other because they were never the same key.

> car keys for the tacoma vs car keys for the scout. same name, same owner, same garage.

> ✅ **these trees are not invented.** the leaf order, the `vault: os.secure` value and the
> ttl format were read off a live unlock run in this worktree
> (`rhx keyrack unlock --owner ehmpath --env prep --key XAI_API_KEY` →
> `ehmpathy.prep.XAI_API_KEY / env: prep / org: ehmpathy / vault: os.secure / expires in: 540m`),
> then cross-checked against the renderers at
> [`emitKeyrackKeyBranch.ts:68-74`](../../src/domain.operations/keyrack/cli/emitKeyrackKeyBranch.ts)
> and [`invokeKeyrack.ts:1344-1381`](../../src/contract/cli/invokeKeyrack.ts).
> only the `reach:` leaf is new. the `55m` is **not** a typo for `540m` — see **e17**.

## the term moved

the wish coined `--scope`. two disputes moved it to `--reach`, both settled 2026-08-02 and
both recorded in full at
[`term=reach._.choice.reason.md`](../../.agent/repo=.this/role=any/briefs/domain.terms/term=reach._.choice.reason.md).

**dispute 1 — the word.** oauth/oidc `scope` is a **capability** list that only ever
**narrows** what you may do. ours is **lateral** — a different territory, never a smaller
grant. a reader who knows oauth reads the flag exactly backwards. (github itself keeps the
words apart: it calls the capability axis **`permissions`** for apps and reserves "scopes" for
oauth apps and classic PATs.)

**dispute 2 — the world, and the decisive one.** `scope` reads as a *modifier applied to one
key*. the design is the opposite: a key is **set per reach**, so reach is an **identity axis**,
beside `owner` / `org` / `env` / `name`. you do not scope the tacoma key into the scout key —
you hold two keys.

⚠️ **the uri form outlived the word.** `github://org=$org` was argued on published-contract
grounds (a cli flag is a contract; `--org` would collide with `KeyrackKeyGrant.org`), never on
the word `scope`. so the rename costs the uri no ground.

**what is now forbidden:** `scope`, `org`, `resource`, `audience`, `target`, `destination`,
`context`, `realm`. one repo, one word.

## user experience

### who uses it, and for what

| user | goal | how they reach it |
|------|------|-------------------|
| a human, once per territory | authorize this repo to reach another org | `keyrack set --reach github://org=$org` |
| beaver in a cross-org task | file an issue / push into another org | `--reach github://org=$org` on the unlock |
| a radio skill dispatched cross-org | know which territory it needs | passes the `--reach` its target implies |
| human who audits reach | "what can this repo touch?" | `keyrack status` — one branch per reach |
| every other caller (the vast majority) | today's behavior | **no change** — no flag, no new requirement |

### the contract

**input** — one new optional flag, on **three** commands:

```sh
rhx keyrack set    [...today's flags] [--reach <uri>]
rhx keyrack unlock [...today's flags] [--reach <uri>]
rhx keyrack get    [...today's flags] [--reach <uri>]
```

⚠️ **`get` was absent from this list until 2026-08-02, and its absence was the largest gap in the
contract.** `get` is the command **consumers actually call** — `set` and `unlock` are human acts,
but a radio skill that dispatches cross-org calls `get`. it already takes `--org` (*"target org:
@this or @all"*, [`invokeKeyrack.ts:418-422`](../../src/contract/cli/invokeKeyrack.ts)) — a
**provenance** filter — so without `--reach` a reach-key is unreachable by the one command that
hands secrets to callers. see **q11**.

| flag | form | default | meaning |
|------|------|---------|---------|
| `--reach` | `github://org=$org` | absent | this key opens `$org`'s installation of the app |

on `set` it **declares** the territory the stored credential is cut for. on `unlock` it
**selects** which of the stored keys to hand back. the two must agree — an unlock for a reach
that was never set is a `ConstraintError`, never a fallback (**e6**).

**output** — the extant `🔓 keyrack unlock` / `🔐 keyrack status` trees, plus a `reach:` leaf
when (and only when) a key has one. absent `--reach`, every tree is byte-for-byte what it is
today.

⚠️ the two trees already differ today, and must stay apart: **unlock** renders
`env → org → vault → expires in`
([`emitKeyrackKeyBranch.ts:69-74`](../../src/domain.operations/keyrack/cli/emitKeyrackKeyBranch.ts)),
while **status** renders `env → org → expires in` with **no** `vault:` leaf
([`invokeKeyrack.ts:1379-1381`](../../src/contract/cli/invokeKeyrack.ts)). the `reach:` leaf
slots directly after `org:` in both — reach and org are the same kind of fact (which
territory / whose manifest), so they belong adjacent; `vault:` is a storage fact and keeps its
extant place.

**errors** — an unusable reach fails fast, never silently falls back:

```sh
$ rhx keyrack unlock --owner ehmpath --env prep --reach ehmpathy
🐢 bummer dude — blocked by constraints

   ├─ ✋ --reach is not a recognized uri: 'ehmpathy'
   ├─ why: a reach must name its scheme so its address rules are unambiguous
   └─ fix: use the github form —
      --reach github://org=ehmpathy
```

```sh
$ rhx keyrack unlock --owner ehmpath --env prep --reach gitlab://group=acme
   ├─ ✋ --reach scheme 'gitlab' is not supported
   ├─ supported: github://org=$org
   └─ fix: --reach github://org=$org
```

```sh
$ rhx keyrack unlock --owner ehmpath --env prep --key EHMPATH_BEAVER_GITHUB_TOKEN \
    --reach github://org=ehmpathy
   ├─ ✋ no key is set for reach 'github://org=ehmpathy'
   ├─ why: a reach is never derived — a key must be cut for the territory it opens
   └─ fix: set one —
      rhx keyrack set --owner ehmpath --env prep \
        --key EHMPATH_BEAVER_GITHUB_TOKEN --reach github://org=ehmpathy
```

that third error is the heart of the design. under the wish's mint-time shape, an unset reach
would have been *derived* — and the derivation could quietly hand back the wrong org's token
(**e18**, now dead). under reach-as-identity, an unset reach is an **absent key**, and an
absent key is loud by construction.

### the timeline a caller walks

**set — once, by a human who holds the pem**

| t | the human does | the system does |
|---|----------------|-----------------|
| s0 | `set --reach github://org=ehmpathy` | parse the uri → `{ scheme: 'github', org: 'ehmpathy' }` |
| s1 | supplies the pem path | reads the pem (as today) |
| s2 | — | derives ehmpathy's `installationId` from **ehmpathy's `keyrack-infra`** — the same admin-free lookup used for any org (**q7**) |
| s3 | — | stores the blob `{ appId, privateKey, installationId }` under `(slug, reach)` |

**unlock — every time, by anyone**

| t | the caller does | the system does |
|---|-----------------|-----------------|
| t0 | `unlock --reach github://org=ehmpathy` | parse the uri → the reach |
| t1 | — | vault yields the blob stored **for that reach** |
| t2 | — | mint the installation token against its baked-in id → `ghs_…` — **the extant mint path, unchanged** |
| t3 | — | daemon stores the grant under `(slug, reach)` |
| t4 | `radio.task.push --into ehmpathy/…` | reads the grant at that reach; the push lands |
| t5 | `keyrack status` | one branch per reach, each with its own ttl |

**note what row t2 no longer holds:** no app JWT, no `GET /orgs/{org}/installation`, no
network call the extant unlock path does not already make. the whole late-lookup apparatus
moved to `s2`, where it runs **once** and where the human already holds the credential it
needs.

## mental model

### how a human describes it to a friend

> "the github app is one master key that can be cut for several buildings. we used to only
> ever cut it for the building you're standing in. now you cut a copy per building, label it
> with the building's name, and hang all of them on the same rack."

### the analogy that fits

**car keys, one per vehicle.** the tacoma key and the scout key have the same name ("car
keys"), the same owner, the same hook by the door. they are still two keys, because they open
two vehicles. `reach` is the label on the fob.

this is why the isolation is legible: to take away ahbode's reach into ehmpathy, you remove
one key — the reach into seaturtle is untouched, because it was never the same key.

### their words vs ours

| a human says | we say | why the gap |
|--------------|--------|-------------|
| "let this repo reach ehmpathy" | `keyrack set --reach github://org=ehmpathy` | the scheme disambiguates future non-github reaches |
| "which orgs can this repo touch?" | the `reach:` leaves on `keyrack status` | one branch per key, so the rack *is* the answer |
| "the ehmpathy token" | the key at reach `github://org=ehmpathy` | one name, N reaches |
| "revoke ehmpathy" | remove that one key | reach is identity, so removal is surgical |

⚠️ **the one term that already carries baggage:** `KeyrackKeyGrant.org` exists TODAY and means
*"whose manifest declared this key"*, derived from the slug's first segment
([`asKeyrackKeyOrg.ts:5`](../../src/domain.operations/keyrack/asKeyrackKeyOrg.ts)). that is
**provenance**, not destination. a key declared by `ahbode` that opens `ehmpathy` keeps
`org: ahbode` the whole way. to conflate them would be `rule.forbid.ambiguous-labels` — one
word, two senses — and would break a live read filter (see groundwork).

## evaluation

### how well it meets the goals

| wish acceptance | met by | confidence |
|-----------------|--------|------------|
| token valid for `$org` from a repo whose manifest says otherwise | a key cut for that org's installation, stored under `(slug, reach)` | high |
| two reaches coexist, each reads back independently | reach is part of key identity, so they were never one entry | high |
| absent `--reach`, byte-identical to today | reach is **absent** by default (`undefined`, never `null` — **e16**); every new branch sits behind `reach !== undefined` | high |
| unparseable/unsupported reach → `ConstraintError`, never silent fallback | parse at the cli boundary; an unset reach is an absent key, which cannot silently substitute | **higher than the wish's shape** — see below |
| held grants surface the reach | a `reach:` leaf on the `status` / `unlock` tree | high |

**the fourth row deserves its own note.** the wish demanded "never a silent fallback to the
manifest org, which would hand back a token for the wrong org and defeat the whole feature."
under the wish's mint-time shape that had to be *enforced* — and i found a place where it
already leaks (**e18**). under reach-as-identity it is **structural**: there is no peer key to
fall back to, because a reach-key that was not set does not exist. the wish's hardest guarantee
stops being a rule we uphold and becomes a shape we cannot violate.

### why not something simpler? (the alternatives, and why each fails)

**alt-1 — store a second credential under the target org's slug.** `keyrack set` a separate
`ehmpathy.prep.EHMPATH_BEAVER_GITHUB_TOKEN`, then unlock that. **zero code change.** it fails
on a hard gate: [`unlockKeyrackKeys.ts:172-173`](../../src/domain.operations/keyrack/session/unlockKeyrackKeys.ts)
skips any slug absent from the current repo's `keyrack.yml` —

```ts
const spec = repoManifest?.keys[slug];
if (env !== 'sudo' && !spec) continue;   // ← the gate
```

so from inside an `ahbode` repo, `ehmpathy.prep.…` is unreachable.

⚠️ **note how narrowly the chosen design differs from this dead one, because it is the crux.**
both store a second credential. alt-1 carries the destination in the **slug's first segment**,
which is the provenance field — so it trips the manifest gate *and* overloads `org`. the
chosen design keeps the slug at `ahbode.prep.KEY` and carries the destination on a **fourth
axis**. provenance is untouched, the gate passes, and the two concepts stay apart. one axis of
difference, and it is the difference between dead and alive.

**alt-2 — use the extant `--env sudo` channel.** sudo is already a manifest bypass:
[`getAllSudoSlugsForKeyAsk.ts:12-33`](../../src/domain.operations/keyrack/getAllSudoSlugsForKeyAsk.ts)
searches the **host** manifest directly and even expands to a cross-org wildcard
`@all.sudo.$KEY`. so `@all.sudo.EHMPATH_BEAVER_GITHUB_TOKEN` really is unlockable from any
repo today, with no new code.

it still fails, and the reason is the crux of the whole wish. `@all.sudo` makes the
**credential reachable from any repo**; it does **not** make the **token reach any org**. the
stored blob still carries exactly one `installationId`, so the minted `ghs_` still opens
exactly one territory. sudo solves *where you may ask from*; the wish is about *which
territory opens*. those are orthogonal.

> **every extant mechanism can move the key around. only a per-reach key changes the lock.**

**alt-3 — the wish's own shape: one key, `installationId` swapped at mint time.** this was
this vision's design until 2026-08-02. it works, and it is worse on four counts: it needs an
installation lookup on **every** unlock, in a context where no human is present to answer a
registry prompt; it leaves **e18** open, where an unset reach silently falls through to the
ambient wrong-org token; it makes `relock` ambiguous (one key, N partitions — see **q1**); and
it lets a caller *request* reach into an org no human ever authorized. per-reach keys cost one
`set` and buy all four back.

⚠️ **and the first count is fatal, not merely costly.** a per-unlock lookup cannot go through
`keyrack-infra` — `getKeyrackInfraCandidateApps` may **prompt a human to pick an app**, which no
unlock path can do. so alt-3 would have been forced onto the app-JWT route, which q7 has since
made a **blocker**. the wish's own shape is incompatible with the invariant; reach-as-identity
is what makes the invariant keepable, because the lookup happens where a human already stands.

### pros

- **the isolation is the data structure.** ahbode→ehmpathy and ahbode→seaturtle are separate
  credentials. to grant, revoke, or audit one has no effect on the other, and the rack renders
  the whole authorization surface with no new command.
- **an unauthorized reach is impossible, not merely rejected.** a caller cannot reach a
  territory a human never cut a key for. under the mint-time shape, a caller could *request*
  any org and the system would try.
- **the unlock hot path does not change at all.** no lookup, no new latency, no new http
  precedent, no new dependency. the extant `deliverForGet` mints exactly as it does today.
- **it keeps the admin-free invariant keepable.** the installation lookup lands at `set`, where
  a human stands and `keyrack-infra` can prompt — so every lookup can go through the admin-free
  gate ([`rule.require.github-app-org-lookup-via-keyrack-infra`](../../.agent/repo=.this/role=keyrack/briefs/rule.require.github-app-org-lookup-via-keyrack-infra.md)).
  a per-unlock lookup could not.
- **the manifest default stays put.** absent `--reach`, byte-identical behavior — which is
  every call that exists today, since the flag is net-new.
- **it composes forward.** `github://` names its scheme, so `aws://account=…` slots in later
  without a second flag or a contract break.

### cons

- **a human must run `set` per territory.** the wish's shape needed no setup step. this is a
  real cost, and it is the price of the "unauthorized reach is impossible" property — the
  setup step *is* the authorization. i judge that trade clearly worth it, but it is a trade.
- **reach must thread through the read side.** `daemonAccessGet` grows an optional `reach`, and
  consumers that want a reach-key must ask for it. *measured, not guessed:* one optional field
  at **3** read paths (see **r3**), on an operation that already takes optional `org?` / `env?`.
- **a key's slug no longer implies its territory.** reading `status`, you must look at the
  `reach:` leaf, not the slug. mitigated by a leaf on every surface, but it is a thing a human
  learns once.
- **consumers must know which territory they need.** a radio skill dispatched at
  `ehmpathy/rhachet` has to pass the matched `--reach`. that is honest — a cross-org action
  *should* name its target — but it is new plumbing at each call site.

**the pit-of-success spine:** every failure above is a `ConstraintError` that names the fix,
and **no** failure path ever hands back a token for the wrong territory. one rule at every
branch: **if the requested reach has no key, throw. never substitute.**

#### e18 — retired, and worth a record of why

under the wish's mint-time shape this was the worst failure in the design, because it
*succeeded*. `attemptGrantKey` falls through:

```ts
// getKeyrackKeyGrant.ts:36-79 — the order of attempts
const daemonResult = await daemonAccessGet({ slugs: [slug], owner });   // 1. daemon
…
const envGrant = await context.envvarAdapter.get({ slug });             // 2. os.envvar (ci fallback)
```

`os.envvar` is keyed by **slug alone** — an env var is a flat namespace and always will be. so
a consumer that asked for a *scoped* grant, when that partition was absent, would silently
receive the **ambient reachless token** — a working credential for the wrong org.

reach-as-identity removes the seam rather than guards it: there is no reachless peer to fall
through to, because the reach-key is a different key. **e20 is the residue** — the env var
*name* must also carry the reach, or the flat namespace re-creates the collision one level
down. that is a naming question with a loud answer, not a silent-substitution hazard.

#### e17 — the ttl the daemon advertises is not the ttl github honors

the mech adapter mints a token and reports its true life: `expiresAt = now + 55 minutes`,
because github installation tokens die in an hour
([`mechAdapterGithubApp.ts:224`](../../src/domain.operations/keyrack/adapters/mechanisms/mechAdapterGithubApp.ts)).

`unlockKeyrackKeys` then **discards that value**. it computes its own expiry from the
*requested* duration alone —
[`computeExpiresAt`](../../src/domain.operations/keyrack/computeExpiresAt.ts) takes
`{ requestedDurationMs, maxDurationMs }` and never sees the grant's `expiresAt`
([`unlockKeyrackKeys.ts:244-252, 265-274`](../../src/domain.operations/keyrack/session/unlockKeyrackKeys.ts)).
so unless the host entry happens to carry a `maxDuration`, the daemon stores a `ghs_` token
under a **9-hour** ttl and `status` prints `expires in: 540m` for a secret github kills at 60.

this **predates the wish** — it is true of every github-app key today, reach or no reach. but it
lands on the wish's coexistence criterion: the reaches coexist for an hour, then all rot into
`401`s while `status` still reports hours of life. the headline demo becomes a lie on a timer,
and the human who debugs it is sent to look at reach partitions when the cause is expiry.

**✅ decided (q5): clamp to the shortest applicable bound.**

```
expiresAt = min(
  requested duration,          // --duration, or the 30m/9h default
  hostConfig.maxDuration,      // the per-key cap, when set   (already honored)
  grant.expiresAt,             // the mech's TRUE life         (← currently discarded)
)
```

**why min is the only defensible choice:** a ttl is a promise about a secret. too-short is a
re-unlock — an inconvenience. too-long is a credential that reads alive and is dead, which
sends a human to debug the wrong subsystem. the asymmetry is total, so the safe direction is
the shortest bound —
[`rule.require.safe-by-default`](../../.agent/repo=ehmpathy/role=ergonomist/briefs/fundamentals/rule.require.safe-by-default.md)
applied to time. it also **cannot regress a caller**: min() only ever shortens a value that is
currently a lie.

it **generalizes past github**: `deliverForGet` returns an optional `expiresAt` on the
[mech adapter contract](../../src/domain.objects/keyrack/KeyrackGrantMechanismAdapter.ts), so
the clamp is written against **the contract, not the github mech** — `EPHEMERAL_VIA_AWS_SSO`
and `EPHEMERAL_VIA_GITHUB_OIDC` get the same honesty for free.

#### e20 — the ci read path cannot see a reach

the residue of e18, in the `os.envvar` vault — **the keyrack firewall path, used by github
actions**.

⚠️ **i had this framed wrong, and a read of the adapter corrects it.** i wrote that a reach-key
"exports a distinct env var name." **keyrack never exports an env var at all** —
`vaultAdapterOsEnvvar.set` and `.del` both `throw UnexpectedCodePathError`
([`:123-137`](../../src/domain.operations/keyrack/adapters/vaults/os.envvar/vaultAdapterOsEnvvar.ts));
the vault is **read-only**, and env vars are set by the *caller* (a ci workflow, a shell export).
so the question is not what we write. it is **what we read, and whether a reach-ask can find the
right variable.**

the real shape, verified:

```ts
// vaultAdapterOsEnvvar.ts:72-73 — the name drops BOTH org and env
const keyName = asKeyrackKeyName({ slug: input.slug });   // ahbode.prep.FOO → FOO
const source = process.env[keyName] ?? null;
```

```ts
// :101 — the blob's baked-in installationId is what gets minted
const { secret, expiresAt } = await mechAdapter.deliverForGet({ source });
```

so in ci the env var holds a github-app **json blob**, and that blob is **implicitly
reach-bearing** — its `installationId` points at exactly one org — while the *variable name*
carries no reach, no env, not even the org. three facts follow:

1. **a reach-ask that falls through to `os.envvar` reads the reachless name** and mints from
   whatever blob ci placed there. that is e18's failure, alive on the ci path.
2. **the grant it returns has no reach** — `os.envvar` builds `KeyrackKeyGrant` with
   `env`/`org` from the slug and no reach field ([`:107-116`](../../src/domain.operations/keyrack/adapters/vaults/os.envvar/vaultAdapterOsEnvvar.ts)),
   so no consumer downstream can tell a reach-ask was answered by a reachless value.
3. **ci that needs two reaches needs two env vars**, and there is no convention for the second
   name.

*best guess, revised:* **a reach-ask must not silently accept a reachless `os.envvar` value.**
either the reach is encoded in the variable name by a convention keyrack *reads* (never writes),
or a reach-ask that reaches this vault fails with a `ConstraintError` naming the fix. a
reachless ask is **unchanged**, so **e1** holds. **clean rework** — one guard, one derivation.

⚠️ this is the single most important thing the blueprint must settle, because it is the one
place where the flat-namespace hazard survives the redesign — and because it is on the **ci**
path, where no human is watching.

## what is awkward?

### 1. ~~`org` already means something else~~ — **RESOLVED 2026-08-02; it is FROM vs INTO**

> "org = the organization **from** which they're authorized, reach = the resource **into** which
> they're authorized. only one definition right?" — the wisher

**right, and this retires the awkwardness rather than merely softens it.** i had filed this as
a live discomfort. it is not one, and the wisher's words are why:

| term | one sense | direction |
|------|-----------|-----------|
| `org` | the organization a credential is authorized **from** | source |
| `reach` | the territory a credential is authorized **into** | destination |

**each word has exactly one definition.** that is not an overload — it is the *opposite* of one.
`rule.forbid.ambiguous-labels` forbids one word with two senses; here we have two words with one
sense each, on a single axis (direction of authorization) that they split cleanly between them.

**verified against the code, not merely asserted.** `KeyrackKeyGrant.org` is documented as
*"which org this grant belongs to"*
([`KeyrackKeyGrant.ts:48-52`](../../src/domain.objects/keyrack/KeyrackKeyGrant.ts)); it is
derived from the slug's first segment (`asKeyrackKeyOrg`) and used to filter reads
(`handleGetCommand.ts:31`). every use is **source**. no use is destination. one sense, confirmed.

⚠️ **the `'@all'` wildcard deserves an explicit note**, because it is the one place a reader
might suspect a second sense. `org: '@all'` means *"authorized from any org"* — still the source
axis, just unbounded on it. the grant's own comment says *"enables org-scoped access and
cross-org credentials"*, which reads ambiguous — but the code only ever tests it as a **read
filter** on provenance. it is a wildcard on `from`, never a claim about `into`.

**what actually remains, and it is small:** the *wish* pointed at `KeyrackKeyGrant.org` as
evidence that "the model anticipates cross-org", which invites a reader to reuse that field for
destination. the field is the one we most need to leave alone — if reach overwrote it, an
`ahbode`-repo consumer that asks for `ahbode.prep.KEY` would stop to match its own grant. so
this is a **hazard in how the wish reads**, not a tension in the design. recorded as such.

### 2. a setup step where the wish promised none

the wish's shape needed no `set`. this one does, per territory. i think it is right — the setup
step *is* the authorization, and that is what makes an unauthorized reach impossible rather than
merely rejected. but a human who read the wish will meet a step the wish did not describe, and
that deserves a flag rather than a smoothing-over.

### 3. the env var namespace is still flat (e20)

reach-as-identity fixes the daemon. it does **not** fix `os.envvar`, which is a flat
name→value map by nature. the fix is a distinct derived name, and until the blueprint settles
its shape, the one hazard the redesign did not structurally remove is still open. i would rather
say that plainly than let the "e18 is dead" headline imply more than it does.

### 4. `--reach` on a per-key flag, applied to a bulk command

`keyrack unlock` with no `--key` unlocks *every* key for an env. a reach is meaningful for
exactly one mech. so "unlock everything, at one reach" is a slightly incoherent ask (**q2**).

**q1 — e12: what should `relock --key <slug>` do when reach-keys exist?**
**✅ [wisher: DECIDED 2026-08-02 — relock ALL reaches of that slug]**

a human who says "lock this key" means the key, not one of its territories. a token that
survived an explicit relock would be a `rule.forbid.surprises` violation with security weight.
a `--reach` filter on `relock` can be added later without a teardown.

⚠️ **i had this partly wrong, and a full read of the two files corrects it — in the decision's
favor.** i wrote that "the render still needs the `reach:` distinction." under relock-all it
does **not**. the three relock paths behave differently, and only two of them carry a hazard:

| path | code | under composite keys |
|------|------|----------------------|
| `--key <slug>` | [`handleRelockCommand.ts:24-32`](../../src/domain.operations/keyrack/daemon/svc/src/domain.operations/handleRelockCommand.ts) — one `del({ slug })` per named slug, pushes the slug **once** | ✅ **render unchanged.** the human named one key; one `🔒 pruned` line is the truth |
| `--env <env>` | [`:35-42`](../../src/domain.operations/keyrack/daemon/svc/src/domain.operations/handleRelockCommand.ts) — iterates `entries()`, pushes `key.slug` **per entry** | ⚠️ N reaches of one slug → the same slug N times → **duplicate `🔒 pruned` lines** |
| (neither) | [`:45-51`](../../src/domain.operations/keyrack/daemon/svc/src/domain.operations/handleRelockCommand.ts) — same per-entry push, then `clear()` | ⚠️ same duplication |

so the fix is a **dedupe on the two sweep paths**, not a reach axis on the render. that is
markedly smaller than what i described, and it falls out of relock-all: because relock reports
per-**key**, and reach is below the key, reach never needs to appear in relock output at all.

**the one signature note:** `del({ slug })` is `store.delete(slug)`, which yields a `boolean`
([`daemonKeyStore.ts:100-102`](../../src/domain.operations/keyrack/daemon/svc/src/domain.objects/daemonKeyStore.ts)).
under relock-all it must purge **every** entry for the slug. keep the `boolean` result (= "any
purged") and `handleRelockCommand`'s shape is untouched.

**q2 — e14: should `--reach` be allowed on a bulk (`--key`-less) unlock?**
**✅ [wisher: DECIDED 2026-08-02 — require `--key` alongside `--reach`]**

a `ConstraintError` names the fix. a reach is meaningful for exactly one mech; to apply it to
some keys and not others is the ambiguity `rule.forbid.ambiguous-labels` forbids. to loosen a
requirement later is clean; to tighten one is not — so this is both the safe direction and the

**note it pairs with q1 rather than contradicts it.** `unlock --reach` requires `--key`;

narrow, to revoke is wide.** you must name precisely what you open, and one word takes away all
that sits under it. that asymmetry is the safe-by-default shape, not an inconsistency.

### the distinction that reconciles them

i had argued for a repo-manifest line as an **authorization** surface — "this repo *may* touch
that org." pass 1 killed that, correctly: authorization varies by **human**, so a repo-scoped
grant would force one union onto every developer in the checkout.

pass 2 is a different axis entirely — a **requirement**, not a grant:

| axis | question | surface | who it varies by |
|------|----------|---------|------------------|
| **requirement** | "which reaches do you need to work in this repo?" | **repo** manifest | the repo — every developer here needs them |
| **possession** | "which reaches does this machine hold?" | **host** manifest | the human at the machine |

a requirement genuinely *is* a property of the repo: if this repo dispatches into `ehmpathy`,
then **everyone** who works here needs `ehmpathy` reach. that is not the ahbode↔whodis case —
that was a human who bridges two orgs *for their own reasons*, which stays ad-hoc and
host-only.

### the repo declares a FLOOR, never a ceiling

this is what makes the two passes fully compatible:

- the repo says **"at minimum, fill these"** — a floor, and the wisher's word for it is
  *"recommend or require"*
- a human may hold **more** reaches than any repo declares (the ad-hoc ahbode↔whodis case)
- **no repo ever declares a maximum**, so no repo-manifest line can take a reach away

so the reach set a machine holds is still per-human, exactly as pass 1 requires. the repo only
raises the floor.

### the shape

reaches hang **under a key**, not on the repo — the wisher's *"under BEAVER token"*:

```yaml

      reaches:
        require:
          - github://org=ahbode
        prefer:
          - github://org=ehmpathy
```

⚠️ **this is a real manifest schema change**, and it is bigger than one field. today every env
bucket is a **flat list of key-name strings**

so the entry type must widen from `string` to `string | { <name>: { reaches } }`, and **every**
reader of that list must accept both. that touches the manifest parser, the `extends` merge, and
`fill`'s enumeration. it belongs in the blueprint's filediff as its own item.

### what `fill` does with them (this supersedes q10's answer)

| directive | `fill` behavior | rationale |
|-------|-----------------|-----------|
| `require` | provision it; **fail** if it cannot | the repo does not work without it — a silent skip would hand someone a half-working checkout |
| `prefer` | provision it; **warn** and continue if it cannot | useful but not load-bearing; a warn keeps `fill` usable for a partial setup |

⚠️ **these are the repo's extant directive pair, not new words.** the wisher first said
*"recommend or require"*; `recommend` was dropped for **`prefer`** the same day, because
`require`/`prefer` is already this repo's published severity pair (blocker / nitpick) and the
reach directives map onto it exactly.

⚠️ **and they are `directive`s, never "grade"s** — keyrack already spends `grade` on

[`term=grade._.choice.reason.md`](../../.agent/repo=.this/role=any/briefs/domain.terms/term=grade._.choice.reason.md).
the dobj is `KeyrackKeyReachDirective`. settled at
[`term=prefer._.choice.reason.md`](../../.agent/repo=.this/role=any/briefs/domain.terms/term=prefer._.choice.reason.md).

this **reverses q10's conclusion** that reach-keys sit outside bulk provisioning. they sat

declaration. the term brief's *"`fill` fills what a manifest declares"* holds unchanged; the
manifest simply declares more.

**q13 — `keyrack del` must take `--reach`, and it addresses ONE territory.**
**✅ [DECIDED 2026-08-03 — a `del` names one address, exactly as a `set` does]**

a `del` addressed by the bare slug has two failure shapes, both silent:

- a key cut **only** for a territory is invisible to it — it reports `not_found` while the
  credential sits on disk
- a slug that holds **both** a reachless key and reach peers loses only the reachless one, with
  no signal that peers were left behind

so `del` addresses the manifest by `(slug, reach)`, never by the bare slug. it is the DESTROY
half of the identity axis `set` already threads.

⚠️ **this is NOT the `relock` case, and the contrast is the whole point.** `relock` deliberately
sweeps every territory of a slug (**q1**) because a human who locks a key means *the key*. a
`del` is **addressed**: it removes the one key it was pointed at and leaves its peers alone. the
two are not inconsistent — **to grant is narrow, to revoke is wide, and to destroy is exact.**

**four writes must be inverted by address, and one must NOT be:**

| what `setKeyrackKeyHost` wrote | how `del` inverts it |
|--------------------------------|----------------------|
| host manifest entry, under the address | delete by **address** |
| the vault secret | `adapter.del({ slug, reach })` — **reach-scoped** |
| the live daemon grant | `daemonAccessRelock({ slugs, reach })` — **reach-scoped**; absent that, a del at one territory purges every peer's live grant |
| the inventory entry, under the address | `daoKeyrackInventory.del({ slug: address })` |
| the `keyrack.yml` declaration | **not inverted for a reach del** — see below |

the last row is the one a careless sweep gets wrong. a REACH key is **never written into
`keyrack.yml`** — `setKeyrackKeyHost` declines to, because a `reaches:` line is hand-authored
and no keyrack command mutates a repo manifest (**q8**). so the entry a reach-del would strip
belongs to the **reachless** key it was never aimed at; to remove it would undeclare a key that
still exists on the host. the removal is guarded by `!input.reach`.

**and the inventory row is not cosmetic.** `inferKeyrackKeyStatusWhenNotGranted` reads that
entry to tell *"this territory was cut and is locked"* from *"never cut at all"*. an inventory
row left behind under the bare slug would report a **deleted** key as merely **locked**, forever
— a silent wrong answer on the read side, produced by an incomplete delete.

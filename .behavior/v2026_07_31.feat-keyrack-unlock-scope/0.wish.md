# wish: `--scope github://org=$org` on keyrack unlock, persisted partitioned by scope

## .source of record

**`ehmpathy/rhachet#441`** — read it FIRST and in full. it is the authoritative spec. this
wish only bounds the scope.

## .what

1. **`--scope` on `keyrack unlock`** — parse `github://org=$org`, mint/derive the github app
   credential for THAT org's installation rather than the manifest's org
2. **scope-partitioned persistence in the daemon** — grants at different scopes coexist;
   neither evicts the other, each reads back independently
3. **the manifest default is unchanged** — absent `--scope`, behavior is byte-identical to
   today. a per-call override, never a new requirement at the call site

## .why

one github app, installed in several orgs, must reach ALL of them — the caller's choice, per
call. the concrete case: **dispatch a task into an `ehmpathy` repo while inside an `ahbode`
repo**, where the manifest says `org=ahbode` and cross-org reach is otherwise unreachable
without departure from the repo.

## .what was already verified in-repo (2026-07-31)

keyrack lives in `ehmpathy/rhachet` under `src/domain.objects/keyrack/`.

`KeyrackKeyGrant.ts` ALREADY carries `org` as a first-class grant field, and its own comment
already claims the intent:

```ts
/**
 * .what = which org this grant belongs to
 * .why = enables org-scoped access and cross-org credentials
 * .example = 'ehmpathy', '@all' (for cross-org)
 */
org: string;
```

so the model anticipates cross-org. the gap is that no path lets a CALLER choose the org per
unlock, plus whatever the daemon's persistence key does today.

`KeyrackKeyAsk.ts` is the CLI-facing ask — `KeyrackKeySlug` is already `org.env.key`, so its
first segment is already an org.

## .acceptance

- `keyrack unlock --scope github://org=$org` yields a credential valid for `$org`, run from
  within a repo whose manifest declares a DIFFERENT org
- two unlocks at different scopes coexist in the daemon; each reads back independently
- absent `--scope`, behavior is byte-identical to today
- an unparseable/unsupported scope fails fast with a `ConstraintError` that names the
  expected form — **never a silent fallback to the manifest org**, which would hand back a
  token for the wrong org and defeat the whole feature
- whatever surfaces held grants (`keyrack status` or equivalent) shows the scope, so a human
  can see which orgs are unlocked

authoritative; the shape below is a guess from outside the repo. settle these in-repo:

- what is the daemon's current persistence key, and is `org` already in it?
- how does `'@all'` (already named in `KeyrackKeyGrant.org`'s example) relate to an explicit
  per-call scope — complement, or overlap to reconcile?
- does the github app installation lookup need a new `KeyrackGrantMechanism` / adapter, or
  does an extant one cover it?

**why a URI and not a bare org:** `github://` names its scheme, so the flag extends to other
scoped credential kinds later without a second flag or a breaking reinterpretation. it
mirrors the `duct:///` convention the repo already uses. if a better in-repo pattern exists,
prefer it and say why in the vision yield.

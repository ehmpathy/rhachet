## ⚠️ scope addition — the cli spawn cost (human-directed, this branch)

**this is NOT the wish's scope.** it rides here on a human directive — *"we should make those tests
faster, zero reason for the slowness"* — with the human's call to land it on this branch rather
than a separate one.

⚠️ **the human directive is the WHOLE reason — there is no structural link to `KeyrackCommand`,
and a claim that there is would be false.** the render guarantee comes from commander's
`createCommand` hook on the subclass, which reaches every descendant whether `invokeKeyrack` is
imported eagerly or through a thunk. the two changes are independent: one closes a
within-keyrack render-consistency class, the other is a cli-wide spawn-cost rework that shares a
branch because a human said to land it here, and because this wish's own new suites made the
spawn cost newly expensive. recorded so the honest reason outlives the convenient one.

### the cause, measured

| what | before | after |
|---|---|---|
| `require('dist/contract/cli/invoke')` | 633ms | — |
| `./bin/run keyrack --help`, min | 659ms | **548ms** |
| `./bin/run keyrack --help`, mean/10 | 1248ms | **841ms** |
| `./bin/run update --help`, min (the floor) | — | 485ms |
| full acceptance suite | 1346s | **1163s** (−14%) |

`bin/run` sends only `run` and `roles boot|cost` to the bun binary (~35–70ms); every other command
falls to `run.jit`, which required `invoke.ts` — and that imported all 16 command modules eagerly,
because each `invokeX({ program })` REGISTERS its subcommand and all must run for `--help`. so a
spawn that ran one command paid for sixteen, and the suite spawns the cli many hundreds of times.

### the fix

`CLI_COMMAND_REGISTRARS` (`getAllCliCommandRegistrars.ts`) maps each command name to thunks that
`await import()` their module, and `invoke.ts` registers only the command `getCommandFromArgv`
finds in argv.

**`getCommandFromArgv` is reused, never re-implemented** — it already skips a global value flag
AND its value (`-c <path>`) to find the subcommand, and is already clamped by
`invoke.globalValueFlags.test.ts`. a second hand-rolled argv scanner would have been a copy of the
exact logic that rule exists to keep in one place.

### the safety property that makes this low-risk

**a name ABSENT from the map degrades to full registration** — slow, never broken. so a map miss
is a speed cost, not a defect; only a WRONG value could break a command. clamped by
`invoke.lazyRegistrars.test.ts` (36 rows): each key registers exactly its own command, the full
path yields the whole set, and an unknown name falls back to everything.

⚠️ **`repo` is registered by TWO modules and the order is load-bearing** —
`invokeRepoIntrospect` plainly CREATES it; `invokeRepoCompile` find-or-creates it. reversed, `repo`
registers twice — a duplicate subcommand, not an error. pinned by its own row.

### what did NOT change

`--help` lists every command in the same order, `keyrack --help` renders identically, and an
unknown command still yields commander's own suggestion. the one snapshot delta is a stack-trace
line number (`invoke.ts:90` → `:70`) from the 20 removed import lines — resnapped narrowly, one
line, per `rule.forbid.blanket-resnap-after-rebase`.

### the honest limit

the remaining ~485ms floor is `invoke.ts`'s own base imports plus node boot, NOT the command
modules — `update` (a 1ms module) still costs 485ms. keyrack now adds only ~63ms over that floor.
to cut further means dissecting `genContextConfigOfUsage` and the node boot flags, which is a
project of its own and is left undone.

⚠️ **the per-module sum is not the bill — it overstates by ~12x.** the figures sum to 7412ms, but
each is taken in a FRESH process, so every module re-pays for deps its peers share. the real
whole-tree cost is 633ms. a 16-module rewrite justified on the 7.4s figure would rest on a cost no
spawn ever pays.

⇒ **measure the whole, never the sum of parts.** the skill now reports both, with the overstatement
named beside them, so the two figures cannot be confused
(`rhx show.cli.import.costs`, `define.cli-spawn-cost`).

⚠️ **never run two suites at once, and never build while either is inflight.** `dist/` is shared
state: the pty-based acceptance rows spawn `bin/run.jit`, which loads `dist/` at call time, and
`jest.integration.env.ts:6` imports `rhachet/keyrack` from it at setup. an overlapping build hands
either a half-emitted tree.

⚠️ **`npm run test:acceptance` IS a build** — its command opens with `npm run build`, which
`rm -rf dist/` first. so the two suites cannot run in parallel even though neither names a build.

the symptom is a failure that names a MODULE rather than a behavior — `Cannot find module
'../../domain.objects/RoleManifest'` from an acceptance row, or 118 suites failed at
`jest.integration.env.ts:9` from integration. that shape is the tell; re-run serially against the
settled build.

| `blackbox/sdk/keyrack.get` | 14 failed | **32 passed / 0 failed** (34s) |

3. the failure mode is `status: 1` with `stdout: ""` — a **spawn/crash signature**, never an

#### ⚠️ the deeper half: the orphans are unreapable, by construction

the obvious remedy is the product's own scoped verb — `rhx keyrack daemon prune --owner <owner>`.
it does not work. against a daemon proven alive in `ps`, it reports:

```
🔐 keyrack daemon prune
   └─ no daemon active for owner=test-owner-590731
```

the cause is in `killKeyrackDaemon.ts:47-59`, which is the one operation whose whole job is to make
the kill true:

```ts
try { process.kill(pid, 'SIGTERM'); } catch (error) { … }

// cleanup files
delFileSync({ path: socketPath });
delFileSync({ path: pidPath });

return { killed: true, pid };
```

the pid file is deleted **unconditionally**, and `killed: true` is returned **without one check
that the process died**. so a daemon that outlives its `SIGTERM` loses its only handle in the same
breath: the next prune reads the pid path, gets `ENOENT`, and takes the honest-looking branch
`return { killed: false, pid: null }` — "no daemon active" — while the process runs on forever.

⚠️ this is `rule.forbid.failhide` at its most expensive: the report is not merely wrong, it is
wrong in the direction that **destroys the evidence**. one unproven `killed: true` converts a
recoverable leak into a permanent orphan, and every later prune agrees the box is clean.

⇒ the two operations disagree about the same daemon, and the disagreement is undetectable from
either side: `ps` says alive, `prune` says absent, and no third reader reconciles them.

#### scope

`killKeyrackDaemon.ts` and `pruneKeyrackDaemon.ts` are **untouched by this branch**
(`git diff origin/main --stat` on both = empty). pre-branch defect ⇒ recorded as a follow-on,
not fixed inside a bounded wish (`rule.forbid.scope-leaks`).

⇒ **the checks this leaves.** three, and the third is the one that generalizes:

1. a failure count that moves while the code stands still is environmental — diagnose the
   environment before you bisect the diff
2. a test helper that mints a per-test identity owes a teardown keyed to that same identity; a
   teardown keyed to the default owner reaps none of what it created
3. **a cleanup that deletes its own handle before it confirms the work is done cannot be retried.**
   an unproven success is worse than a reported failure — the failure leaves you the handle.
   delete the handle **after** the proof, never before it

### 60. ⚠️ a credential mask keyed on the FIELD NAME, in the one place every refusal converges

`getKeyrackBlockedReport` renders every metadata field a throw site names, and masks a value only
when its KEY matches `/secret|password|passphrase|token|credential|prikey|privatekey/i`. two
independent l3 lanes raised it against code **this wish wrote**.

⚠️ **a key-name mask is only as strong as the name discipline of every throw site that will ever
exist.** the day one stores a vault-returned secret under `value`, `body`, `data`, or `context` —
the four ordinary words a throw site reaches for — the renderer prints the credential to a terminal
and a ci log. this is a CREDENTIAL tool and this renderer is the ONE place every keyrack refusal
converges, so it is the highest-leverage leak available.

**the reviewer's proposed fix was an allowlist of renderable keys, and it is the wrong fix** — it
is `rule.forbid.failhide` in renderer form, the exact defect the render loop exists to close (the
throw site looks correct, the field is real, only the render eats it). it was already weighed and
overruled by the human this round, which is what `rule.require.refusals-carry-context` records.

⇒ the fix is a SECOND mask, value-shaped rather than key-gated: `isKeyrackSecretShaped` reads the
value's own shape — pem block, 22 known vendor prefixes (`ghs_` among them: the github-app install
token is the `@all` bootstrap credential this whole wish exists to make readable), jwt, and an
opaque high-entropy run. the two masks are OR'd, so a leak now needs BOTH to miss, and every field
still renders.

⚠️ **the opaque-token rule is where a value-shaped mask usually goes wrong**, so it demands
length ≥ 32 AND lowercase AND uppercase AND a digit, all four. that is what keeps it off the real
context: a git sha is lowercase+digits (no uppercase); a slug, a path, and a sentence carry
`.`/`/`/` `; an env var name is uppercase+`_` with no lowercase. each renders. the asymmetry is what
sets the tune — an over-report costs one leaf that reads `__REDACTED__`; an under-report costs a
credential in a ci log.

clamped both ways (`isKeyrackSecretShaped.test.ts` + `[case10]`), and the negative rows are the
ones that matter: `[case10][t1]` asserts `not.toContain('__REDACTED__')` on ordinary context under
those same four keys. dogfooded: value mask removed ⇒ **1 red**; restored ⇒ green.

### 61. ⚠️ a keyed ask emptied by a FILTER refused as "not found" — a falsehood about a held key

`unlock --key FOO --org @this` where `FOO` is held as `@all.sudo.FOO` threw `sudo key not found:
FOO`. the key exists. the filter excluded it.

⚠️ **the two states are the same EMPTY SET**, and on a SWEEP the empty set is the honest answer —
`--org otherorg` genuinely selects none, which `[case1][t3]` already clamps. on a KEYED ask it is
not: the human named ONE key, the box holds it, and the refusal sends them to `rhx keyrack set` to
re-mint a credential they already have.

⇒ the two extant verdicts — a resolved set, or "not found" — cannot express *"held, but excluded"*.
so the fix is a THIRD verdict split in ABOVE the not-found, never a softening of it (that refusal
is correct when the key truly is absent, and `[case4][t3]` clamps that it still stands).
`assertKeyrackKeyAskSurvivedOrgFilter` reads the set before the filter AND after it — the
difference between the two IS the reported fact — and names the orgs the key IS held under, so the
`fix:` line can name the flag to correct. applied at all three unlock scopes.

dogfooded: the guard inverted ⇒ **3 red**; restored ⇒ green.

### 62. ⚠️ a filter drop that is correct, silent, and reads as an absent credential

an `--org`/`--env` filter narrows on a slug's `<org>.<env>.<key>` segments, so a host-manifest row
that is not a full slug (`MY_KEY`, `my.api.KEY`, `@all.badenv.FOO`) survives NO filter. the drop is
CORRECT — a bare key names no org, so no org filter may claim it, and to keep it would hand a key
of unknown provenance to a provenance question. but it is invisible: exit 0, and a rack that looks
smaller than it is.

⚠️ **the reviewer's cited mechanism does not reach the filter.** the report named
`unlockKeyrackKeys.ts:351-356`'s `keyOrg ?? slugOrg ?? repoManifest?.org ?? 'unknown'` as the source
of an unfilterable row. read at the line: `'unknown'` is the `org` FIELD of a `KeyrackKeyGrant`,
never a slug string — and the filters read the SLUG. so that path cannot produce the row.

⇒ the class is real anyway, one hop over: a host manifest's `hosts` keys are **hand-authored yaml**,
so an unparsable row is reachable there in practice. a repo manifest's slugs are derived and full by
construction. so the fix names the drop rather than softens it — `getAllKeyrackSlugsWithNoScope` +
`emitKeyrackUnscopableRowsNotice`, on stderr, only when a filter is active AND a row was
unfilterable, at both sweep surfaces (`list`, `status`).

⇒ **the check this leaves:** when a report's cited mechanism does not hold, read one hop further
before you decline it. the mechanism was wrong and the hazard was real, and only the line-level read
told the two apart.

## the pattern

sixty-two defects, one shape: **a decision taken at the wrong grain, whose failure is a silent
wrong answer rather than a throw.**

⚠️ **defect 29 is the set's mildest failure and its widest lesson**: the decision was not wrong,
was not undocumented, and was not even unreachable — it was recorded in a comment beside code
that no ask ever executes. a decision a human cannot reach is a decision only a reader of the
source holds. **to decline a flag, DECLARE it** — silence refuses too, but it refuses without a
reason and without the fix.

⚠️ **defect 25 is the one this round's own fix CREATED**, and it is the sharpest lesson of the
set: when you move a rule to a boundary, the point-fixes it supersedes do not become harmless —
they become **contradictions**. three ops still rendered and hard-exited after `KeyrackCommand`
already caught every `ConstraintError`, so one refusal had two renders again, and the
`process.exit(2)` fought the emitter's own documented flush guarantee. **a boundary is not done
until what it replaced is deleted.**

⚠️ **defect 26 is the same lesson, one layer down** — a fourth site of that same emit-then-exit
pair survived the deletion of the three ops, inline in `set`. it is the shape's own moral applied
to itself: "delete what the boundary replaced" is a claim about the WHOLE TREE, so what closes it
is a tree-wide sweep, never a fix of the instances one happens to remember. the sweep found
exactly one residue, which is the only way to know there was exactly one.

⚠️ **defect 27 turns the set's own moral on the TEST suite.** every prior entry is about a
production codepath that misreports its cause. 27 is a test that does it — an unobserved seed
whose failure borrowed the next assert's subject, so a broken setup read as a broken feature. the
harm is the same and the fix is the same: whoever detects a fault must be the one who names it.
that a suite this heavily reviewed carried three of them is the point — a setup line is the last
place anyone looks, precisely because it is not the subject.

⚠️ defects 22 and 23 are the sharpest cases of *"silent"* in the set, and they arrived last: the
refusal **did** exit 2 and **did** name its own cause. only the RENDER was wrong. so every
exit-code assert a clamp could carry was green over it — which is why a render-only defect
survives every gate built on exit codes, and why their clamps assert the tree, never the code.

another way elsewhere, the fix is a NAMED cast, never a copy of the condition. each of these was a
rule that lived in a call site instead of in a name — and the call site that forgot it was the
defect every time.

⚠️ **defects 23 and 24 are the pair worth a carry forward, because each hid from a whole class of
test.**

- **23 is the CLASS behind 22.** ten review rounds each closed the one raw throw they could see;
  none asked why there was always another. the answer: the render rule had no home. it lived in
  human memory at ~16 call sites, so site 17 was always one edit away. the fix had to be a
  boundary (`KeyrackCommand`, via commander's `createCommand` hook), never a seventeenth patch —
  `rule.require.solve-at-cause`. an opt-in HOF would have been the same shape, one layer up.
- **24 is what 23's fix EXPOSED.** the assert was green for its whole life by a match on the
  `[args]` echo of its own flag rather than on the message. correct the render, and the echo is
  gone — so the row went red and revealed it had also never reached the guard it claimed to test
  (the fixture declares the key in two envs, so it refused at `--env required` first).

⇒ **the second check, then:** an assert against a raw error dump can match incidental output —
an args echo, a class name, a metadata key. assert against the RENDER a human reads, never the
debug spill. and the lesson this round has now taught three times holds again: **an exit-code
assert had no teeth on any of this**, since the generic handler already exited 2. only the
render assert bites.

defects 8 and 9 sharpen that into its strongest form: **a duplicated definition is a defect that
has not happened yet.** 8 has already happened — silently, on a slug shape no test named. 9 has
not, and sits one edit away. the cure for both is the same: one classifier over a closed set,
every predicate derived from it, and an exhaustive sweep that proves the derivation holds
(`term=kind._.choice._.md`).

defect 7 is the counterexample worth a place beside them: a rule that IS in the right spot, and
still ships a crash, because the render goes unread. a functional assert proves the outcome; only
a snapshot proves the sentence.

### the two probes, re-runnable

```
$ GH_HOST=localhost:59999 GH_TOKEN=fake gh api user
Get "https://localhost:59999/api/v3/user": dial tcp [::1]:59999: connect: connection refused
```
⇒ `GH_HOST` is honored; the scheme is https and the path is the enterprise `/api/v3/`.

```
$ SSL_CERT_FILE=<empty file> SSL_CERT_DIR=/nonexistent gh api rate_limit
Get "https://api.github.com/rate_limit": tls: failed to verify certificate:
  x509: certificate signed by unknown authority
```
⇒ the Go trust pool follows `SSL_CERT_FILE`. an empty pool rejects github's *real* cert, so a pool
that holds a local self-signed cert would accept a **local** one.

### therefore

**for the `PERMANENT_VIA_REPLICA` rows — the majority of the suite — a backend swap needs ZERO
prod code change.** the real `gh` binary would run: it looks up the host, negotiates TLS,
authenticates, serializes, and POSTs. that is a **swap**, the exact category this same lane
*accepted* for aws.params (`term=swap`).

only `[case5]` (`EPHEMERAL_VIA_GITHUB_APP`) genuinely needs the cross-vault
`KEYRACK_GITHUB_API_ENDPOINT` seam in `mechAdapterGithubApp`. **one row, not the suite.**

### ⚠️ but the HARNESS cost is not trivial — I probed further and corrected myself again

my first draft of this handoff said *"two env vars and a local HTTPS fake."* the env-var half is
wrong. three more probes, output verbatim:

```
$ GH_HOST=http://localhost:59999        gh api user  → error connecting to http
$ GITHUB_API_URL=http://localhost:59999 gh api user  → gh: Bad credentials (HTTP 401)   ← hit the REAL api
$ GH_API_URL=http://localhost:59999     gh api user  → gh: Bad credentials (HTTP 401)   ← hit the REAL api
```

⇒ **`gh` refuses a scheme in `GH_HOST` and ignores `GITHUB_API_URL` outright.** it always dials
`https://`. so unlike the SSM stand-in — which is plain HTTP, because the AWS SDK accepts an
`http://` endpoint override — a github swap needs **real TLS**.

⚠️ **and that estimate was ALSO wrong. rather than quote a fourth number, I built it.**

I stood up a Node HTTPS fake and ran the **real `gh` binary** against it. it works, end to end,
hermetically:

```
gh auth status    → exit 0   ✓ Logged in to localhost:33319 account faker (GH_ENTERPRISE_TOKEN)
gh secret set X   → exit 0
gh secret delete  → exit 0
```

the requests `gh` actually made, and what the fake answered:

```
POST /api/graphql                                    ← {"query":"query UserCurrent{viewer{login}}"}
GET  /api/v3/
GET  /api/v3/repos/{owner}/{repo}/actions/secrets/public-key
PUT  /api/v3/repos/{owner}/{repo}/actions/secrets/MY_SECRET
     body: {"encrypted_value":"sPsBSV4BxN/7EDR6+LEQzYzw…","key_id":"568250167715278791"}
DELETE /api/v3/repos/{owner}/{repo}/actions/secrets/MY_SECRET
```

⚠️ **that `encrypted_value` is a genuine libsodium sealed box, produced by the real `gh`.** which
kills the second dependency: the fake never decrypts (this vault is **write-only** — `get: null`,
`vaultAdapterGithubSecrets.ts:85`), so it only has to *serve* a public key. an X25519 public key is
32 bytes, and `crypto.randomBytes(32).toString('base64')` is a valid one. **no libsodium dep.**

and the first dependency dies too: the cert is a **committed fixture**, generated once with
`openssl` locally and checked into `blackbox/.test/assets/`. no runtime host binary, so
`rule.forbid.bare-host-deps` is not engaged.

### the actual, measured cost

| piece | what |
|---|---|
| deps | **none** |
| prod code change | **none** |
| new files | a committed self-signed localhost cert + key, and one `genFakeGithubApiServer` peer to `genFakeSsmServer.ts` (~50 lines) |
| test env | `GH_HOST`, `GH_ENTERPRISE_TOKEN` (with `GH_TOKEN` **unset**), `SSL_CERT_FILE`, `GH_CONFIG_DIR` |

⚠️ two env details the probes surfaced, which a naive attempt would trip on:

- **`GH_TOKEN` must be unset**, or `gh auth status` also checks github.com, fails there, and exits 1
  even though the fake host authenticated fine. use `GH_ENTERPRISE_TOKEN` alone
- **`GH_CONFIG_DIR` must point at a temp dir**, or `gh` reads the developer's real credential store
  and the suite is no longer hermetic — it would pass on my box and fail in ci

escalation*. the yield already enumerates four and splits them into two shapes; this is shape A —
an **absence claim** (*"no cheap seam exists"*) — disproved by a probe that took under a minute.

is the most expensive place to be wrong, because the reviewer who would normally catch it has been
routed around by design.

⇒ the rule this earns, and it is narrower than the extant one:
**`rule.require.search-before-you-claim-absence` binds hardest at the moment you escalate.** an
escalation converts your claim into someone else's premise. verify it there even if you verified it
nowhere else.

the honest note for the record: the escalation itself was still right to file — the question is a

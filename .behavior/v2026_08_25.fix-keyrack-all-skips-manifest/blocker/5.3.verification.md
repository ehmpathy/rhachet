### the mechanism — a veto and a grant are different

read from `git.commit.operations.sh` + `git.commit.uses.local.sh`:

| meter | what it is | this tree |
|---|---|---|
| global | a **veto** — `blocked` stops all commits | not blocked ✅ |
| org (`check_org_blocker`, ops:139-166) | a **veto** — reads `.agent/keyrack.yml#org`, returns 0 when allowed | `org: ehmpathy` → **allowed** ✅ |
| local `STATE_FILE` | the **GRANT** — the count of commits conferred | **absent** ⛔ |

these are **AND**-ed, never OR-ed. an allowed org **removes a veto; it does not confer a quota.**
row 5 of the precedence is what applies here — *unset = blocked (safe default)*.

⚠️ **and this is why the supervisor's own repo printed `unlimited`.** `git.commit.uses.local.sh`
:314-322 prints `no quota set` whenever `STATE_FILE` is absent, **before it consults any other
meter** — the local handler holds not one reference to `org`. so a bare `get` can print
`left: unlimited` only when a **local** state file says so. that repo held a local grant; the org
fallthrough is not what produced it.

⇒ the supervisor's correction was right about the org meter and right to demand I re-read it. the
inference it carried — *allowed org ⇒ quota* — is the one step the code does not take.

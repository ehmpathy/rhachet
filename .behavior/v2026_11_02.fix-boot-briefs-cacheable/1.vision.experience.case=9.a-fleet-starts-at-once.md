# 1.vision.experience.case=9.a-fleet-starts-at-once

> cell `session.concurrent × unchanged` · actor driver · feel happy · care critipath

## .narrative

a driver fans out six peers on one role set at once: six `rhx enroll claude --as @:peerN --roles -driver
--async` calls in one breath, then a first `rhx clone say` to each. the boot now sits in the system prompt,
so it is shareable across sessions — but no session has written it yet. the api makes a cache entry readable
only once the first response starts, and its docs advise that parallel requests wait for the first response
to get cache hits. so six cold first requests in flight together each write the boot: six writes where one
would do.

with the fix, the fleet's first request goes alone. a spawn sends no request, so all six spawn at once; the
gate sits at each clone's first say (F5). the first say claims the lead and goes. the other five each print
one stderr line that names the lead and the bound, then wait until the lead's first response begins (up to
45s, then they go unheld). `rhx clone.cache.usage` on peers 2–6 shows the boot as a read on call 1. one
write, five reads, for the price of one wait the driver can see.

the gate is keyed by the boot's content (the actor's `boot.md` hash), so two fleets on two role sets never
wait on each other, and a lone clone never waits at all. the lead record lives under one worktree's
`.agent/.actors/`, so a fleet spread across worktrees is not gated; each worktree's first clone writes.

## .[tn] sketch

```
given a role set whose boot has no warm cache entry
  [t0] the driver enrolls six clones of it with --async, in parallel
    then all six spawn at once; no spawn sends a request
  [t1] the driver says to all six at once
    then clone 1's say claims the lead and goes
    then clones 2–6 each print a hold line on stderr and wait
  [t2] clone 1's first response begins — the entry is readable
    then the says to clones 2–6 go
  [t3] calls 1 of clones 2–6 run
    then each reads the boot from cache
    then the fleet's total boot write is one boot, not six
  [t4] within the TTL, the driver says first to six more clones in parallel
    then none is held; every call 1 reads the boot
  [t5] at the same moment, a fleet on another role set gets its first says
    then it is held only on its own lead, never on this fleet's
```

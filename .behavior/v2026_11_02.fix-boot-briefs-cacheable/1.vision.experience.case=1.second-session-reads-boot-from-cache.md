# 1.vision.experience.case=1.second-session-reads-boot-from-cache

> cell `session.same-actor.same-tree × unchanged` · actor driver · feel happy · care critipath

## .narrative

the driver starts a clone, closes it, and starts another a minute later in the same worktree with the
same roles — and a different first prompt, as every real session has. the second clone's first call
should read the whole boot from cache.

today it does not. measured 2026-11-02 on haiku, actor `-driver`, `rhx boot.cache.probe`:

| door | session 2 cache write | session 2 cache read |
|---|---|---|
| `CLAUDE.md` (today) | 125,844 | 11,237 |
| system prompt (after) | 4,779 | 132,116 |

why: claude places a cache breakpoint on the system block and on the last block of the first message, and
the `CLAUDE.md` boot sits between them. a new session can read the boot only if its first message matches
an earlier one byte for byte — prompt and hook output included. an early probe (same prompt, small hook
output) did hit; that hit was the identical message, not a shareable boot.

after: the boot rides in the system prompt, ahead of the system breakpoint, so the second clone reads it
whatever its prompt, hooks, or git status.

## .[tn] sketch

```
given an actor with an unchanged boot.md, in one worktree, no warm cache entry
  [t0] clone A starts with prompt "reply OK"
    then A's call 1 writes the boot (cache_creation_input_tokens >= the boot's tokens)
  [t1] A's first response has begun — the entry is now readable
  [t2] clone B starts within the TTL, with prompt "reply YES"
    then B's call 1 cache_read_input_tokens >= the boot's tokens
    then B's call 1 cache_creation_input_tokens is under 5% of the boot's tokens
  [t3] the driver runs `rhx boot.cache.probe --roles <spec>`
    then it reports ✅ the second session read the boot from cache
  [t4] the TTL lapses, clone C starts
    then C's call 1 writes the boot again (correct; session.after-ttl)
```

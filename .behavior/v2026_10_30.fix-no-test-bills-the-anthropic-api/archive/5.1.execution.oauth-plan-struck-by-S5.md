## .open questions — for the commander

### Q1. how does the clamp reach the five repos beyond rhachet?

rhachet keeps its own `jest.*.globalSetup.ts`. the other five repos get `jest.*.env.ts` from the
`declapract-typescript-ehmpathy` practice, so a clamp written only into rhachet reaches one repo of six.

| option | what lands | cost | risk |
|---|---|---|---|
| **A. a manifest `forbid` list, enforced by `keyrack.source`** | rhachet gains `env.test.forbid: [ANTHROPIC_API_KEY]` in the keyrack manifest grammar; `keyrack.source` refuses when a forbidden key sits in `process.env`. each repo adds the line to the manifest it already edits | one rhachet contract change + one line per repo; each repo needs a rhachet bump | a new manifest grammar to support; it is supplier-neutral (no anthropic name in the framework) |
| B. a clamp in the declapract practice | `declapract-typescript-ehmpathy` adds the clamp to its jest env template; each repo runs `declapract.upgrade` | a 7th repo and a practice release; an upgrade pr in each repo pulls in all other practice drift | the upgrade drags in unrelated changes |
| C. rhachet only, for now | the five repos get only the manifest swap; no clamp | least work today | a key that comes back (a manifest edit, a human shell) bills again in five repos, unseen |

**lean: A.** the manifest is already the one file each repo must touch, and it is where the cure
sits (F4). a `forbid` list makes the clamp travel with the manifest, keeps the framework free of
any supplier name (`rule.forbid.supplier-assumptions-in-the-framework`), and needs no practice
release. rhachet's own clamp then becomes that same `forbid` line, not a hand-written check.

until Q1 is answered: rhachet's clamp is built inside its globalSetup as the vision states; under
A it moves into `keyrack.source` with no change in behavior.

### Q2. two repos hand the key to tests outside the keyrack firewall — how do we cut that path?

read from origin/main, 2026-10-30:
- rhachet-roles-rhight `.github/workflows/.test.yml:243,253` set `ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}` on the test steps; `test.yml:28` and `publish.yml:25` pass it in

these are an older shape of the practice's workflows. rhachet's own `.test.yml` has no such line: it runs `keyrack firewall`, which lifts only what the manifest declares. so in these two repos a manifest swap alone cures naught in ci.

| option | what lands | cost | risk |
|---|---|---|---|
| **A. `declapract.upgrade` the two repos to the firewall workflows** | the practice's current `.test.yml` / `test.yml` / `publish.yml`; the manifest becomes the one gate in ci, as in rhachet | an upgrade route per repo | it pulls in other practice drift with it |
| B. hand-edit the workflows | drop the `ANTHROPIC_API_KEY` lines and pass the token the same way | small diffs | the files drift from the practice; the next upgrade rewrites them anyway |

**lean: A.** the workflow files are practice-owned, so a hand edit is overwritten by the next upgrade. the upgrade lands the firewall, which makes every later manifest change (this one, and any Q1 `forbid` line) reach ci with no workflow edit.

### Q3. where does a brains-anthropic atom suite get its key, if not from the shared env?

F2 keeps the atom suites on a suite-local key (they need the api; they stay red until credit returns). `genBrainAtom` reads `process.env.ANTHROPIC_API_KEY` unless a client is injected via `context.anthropic` (`genBrainAtom.ts:212`). the same jest run also holds that repo's `genBrainRepl` suites, which spawn claude code, and jest workers share a process across test files, so a key set in `process.env` by one suite can reach a later one.

| option | what lands | risk |
|---|---|---|
| **A. a distinct key, injected as a client** | env.test declares `ANTHROPIC_ATOM_API_KEY`; each atom suite builds `new Anthropic({ apiKey })` from it and passes it as `context.anthropic`. `ANTHROPIC_API_KEY` is absent from every env, so the clamp holds whole | one more key name to fill; the suites change their context setup |
| B. atom suites set `process.env.ANTHROPIC_API_KEY` in their own `beforeAll`, and unset it after | no new key name | a worker that runs a repl suite after an atom suite in the same process can still see it if a teardown is skipped; the clamp cannot see a suite-local write |
| C. atom suites leave ci; run by hand only | no key in ci at all | the atom path goes unproven on every pr |

**lean: A.** it is the only option where the key that claude code reads never exists in a test env, so the clamp stays the whole proof. the injected-client seam already exists.

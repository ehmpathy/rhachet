## the find — a controlled comparison, on one machine, at one time

this host ran **two versions of the daemon code side by side**, in two login sessions, for
the whole of this gate. that is an experiment i did not design and could not have staged.

| | session 4 — **this branch** | session 3 — **unfixed** (the neighbour worktree) |
|---|---|---|
| code | `hasEverHadKeys` replaced by idle-demand timeout, + e19 exit cleanup | `hasEverHadKeys` latch still present |
| daemons spawned across this gate | hundreds, over three full suite runs | (its own workload) |
| **sockets left behind at halt** | **2** | **794** |
| trend over the gate | 1155 → 0 (pruned) → 13 → **2** | 782 → 794, **still climbs** |

the session-3 figure moved **1576 → 1588 files** while i worked, so those daemons are not a
frozen relic of an old census — they are minted now, by live code that lacks this fix.

### why this is a controlled comparison and not a guess

- **same kernel, same uid, same runtime dir, same hour.** every confound a cross-machine
  comparison would carry is absent.
- **the divergence is the code.** session 4 ran a 1915 s suite that spawns a daemon per temp
  `HOME` and finished with **2** sockets. session 3 holds 794 and climbs.
- **it is the acceptance criterion, measured rather than argued.** the wish asks that "the
  count plateaus and then decays". session 4 decayed to 2 from a peak of hundreds; session 3
  is the control that shows what the same workload does without the fix.

### the corollary the vision predicted, now observed

the vision's q1 decision — widen `@all` past `homeHash` but keep the `sessionId` pin — is
what makes those 794 unreachable to me. that was the wisher's call on 2026-08-02, and the
reason holds exactly as written: to reap them would silently drop another login session's
cached credentials. they run pre-fix bytecode, so they cannot self-terminate either. this is
the q11 migration note's whole point, and it is now demonstrated rather than asserted:
**an already-leaked machine gets no relief from the fix alone; it needs one manual
`rhx keyrack daemon prune --owner @all` per affected session.**

### the four boundary cases the vision did **not** predict

the table above closes on the vision's 19. but the clamp set is larger than the vision's

| the case | the clamp | how it was found |
|---|---|---|
| the **successor-vs-orphan race** — daemon A idle-exits while daemon B already owns the socket path, and A's cleanup deletes B's files | `daemon.integration [case11]` + an ownership check in `startKeyrackDaemon` | reviewer, mid-build. e19 created it: bind cleanup to `exit` and a *late* exit reaps a *live* successor |

| the **session check ran eagerly on every connect**, so a probe paid the `ss -xp` cost | `handleKeyrackDaemonConnection.integration [case1]` | my own regression, caught in round 5 |

**the honest read**: the vision predicted 19 boundaries and the build found 4 more — a hit
rate worth stated rather than hidden, because it calibrates how much a future gate should
trust an edge-case list as complete. an e-table proves *the predicted* boundaries are held.
it says not one word about the unpredicted ones, and three of these four were consequences of
the fixes themselves rather than of the defects.

that last point generalizes: **e19 is the one that spawned its own new boundary case.** to
bind cleanup to the exit path is correct, and it immediately created the successor race,
because "clean up my files" and "clean up the files at my path" are the same statement only
while no successor exists. a fix that repairs damage a fix caused can itself cause damage.

**a defect this review found and closed**: the coverage section had only the deliverable-grain
table above. every e-case was in fact clamped — but that was true by accident of thorough
build rounds, not by any check at this gate. a gate that verifies the coarse grain and calls
it coverage is a gate that would pass a missed boundary case silently. the table now exists so
the claim is checkable rather than trusted.

### the one red left — and it is the `ss -xp` mechanism this document already named

all 5 failures are in `keyrack.status.acceptance.test.ts`, `[case3] set invalidates daemon
cache (relock)`. **four of the five are consequences of the first**, which is:

```
● ... [case3] ... [t1] set overwrites with new value › then: set exits with status 0
  Expected: 0
  Received: 1
```

the `set` exited **1** with empty stdout. its stderr, captured by the harness:

```
UnexpectedCodePathError: daemon RELOCK command failed
{
  "error": "UnexpectedCodePathError: ss command failed\n\n{\n  \"inode\": \"2408661564\",\n  \"signedInode\": -1886305732\n}"
}
    at daemonAccessRelock (.../daemonAccessRelock.ts:45:11)
    at async setKeyrackKeyHost (.../setKeyrackKeyHost.ts:119:5)
    at async setKeyrackKey (.../setKeyrackKey.ts:43:21)
```

the chain is `keyrack set` → `setKeyrackKeyHost` → `daemonAccessRelock` (invalidate the cached
key) → daemon → `verifyCallerLoginSession` → `getSocketPeerPid` → **`ss -xp` under a 5 s
timeout**. that is precisely the mechanism named two sections above. the downstream four
failures follow mechanically: the `set` never landed, so `[t2]`'s `get` still read `granted`
with the stale value, and the (correct, unchanged) snapshot reported it.

**the four facts that place this defect:**

1. **it is not new.** `main` carries the same `getSocketPeerPid`
   (`git diff origin/main...HEAD` over that file → empty; last changed in `1fea8f7`, #340)
2. **it is not deterministic.** it moved suites between runs — 5 occurrences in `20-53-00Z`
   (against `keyrack.fill` / `env-all`), **1** in `07-52-50Z` (against `keyrack.status`)
3. **this branch made it strictly rarer, and that is measurable.** 5 → 1 across two comparable
   full runs. ⚠️ **stated as consistent-with, not proven-by**: the two runs differ in code
   *and* in host state, so the drop has more than one candidate cause. the p8 lazy gate is the
   mechanism that would produce it, and the direction matches
4. **it cannot be cured by the lazy gate alone.** p8 removed the session check from *byte-less
   probes*; a `RELOCK` is a real command and must still be authenticated. so a residual
   dependence on `ss -xp` is inherent until `SO_PEERCRED` replaces it

**the error does not name its own fix, and that is a second, smaller defect.**
`getSocketPeerPid.ts:78-83` passes `cause` into the error, but the serialized output carries
only `inode` and `signedInode`. so the log cannot distinguish the two mechanisms `execSync`
throws on — a **timeout** (SIGTERM at 5 s) from a **maxBuffer overrun** — and a reader is left
to infer. under `rule.require.errors-name-the-fix` the metadata should carry `error.signal`
and `error.code`. i have NOT made that change; see the scope call below.

the cause is a chain that hides itself completely:

and the failure appears only on a developer box configured the way this repo tells you to
configure it.

the loop at all — `rule.forbid.bare-host-deps`, `rule.require.hermetic-tests`. verified: 2

repo's own setup guide (`howto.test-local-rhachet`) instructs a developer to define an `npx()`

## the reap — cleared by the human, and what it did and did not do

the human cleared the reap. **176 live daemon processes** were found, every one of them
spawned from `rhachet.vlad.feat-keyrack-vault-aws-params` — the neighbour worktree, exactly
as the root-cause diagnosis predicted. all were sent SIGTERM so each ran its own shutdown
handler.

### what the reap actually changed — measured, not projected

| measure | before | after |
|---|---|---|
| live daemon processes | **176** | **1** |
| thread count | ~6 800 | ~4 960 |
| load average (1 min) | 63–71 | **47** |
| MemFree | 1.78 GB | 2.88 GB |
| session-3 socket files | 794 | 679 |
| session-4 socket files | 4 | **0** |
| /swapfile2 (KB used) | 36 773 728 | 36 208 396 |
| /swapfile (KB used) | 15 976 948 | 14 187 752 |
| **disk swap, summed** | 52 766 780 KB ≈ **50.3 GB** | 50 412 252 KB ≈ **48.1 GB** |
| **delta** | — | **down ~2.2 GB only** |
| **zram0** | 16 772 484 KB (99.97 %) | 16 420 284 KB — **still ~98–100 %** |

### the correction, recorded because i got it wrong

an earlier draft of this document claimed the reap would "free ~50 GB of swap pressure."
**that was a projection, not a measurement, and it is false.** disk swap fell by roughly
**2.2 GB** — from ~50.3 GB to ~48.1 GB — and zram stayed pinned near 100 %. i had taken the
*total* swap in use and asserted a kill would release it, which conflates the size of a
backlog with the rate at which the thing that built it was still building.

that is expected behavior rather than a failure of the fix: **swap pages are not released
when a process dies.** they stay resident until something touches them or until a
`swapoff`/`swapon` cycle reclaims them. so the honest statement of the outcome is:

> **the processes were reaped and the cause was removed. the accumulated swap remains until
> a swap cycle.**

the recovery signals that *are* real and immediate are the ones tied to live processes —
thread count, load, and MemFree — and all three moved in the right direction. the swap
figure is a backlog, not a live cost, and it will not clear on its own.

this correction matters beyond bookkeeping: it is the same class of error the vision warned
about when it separated the *socket file* count from the *live process* count (q6/e19). a
count that lags reality is easy to quote as though it were current. swap is a third such
quantity, and i quoted it as if a kill would move it.

### what remains on the machine

679 session-3 socket files are left as orphans — no process, no poll, no `ss` cost, since
the kernel drops a dead daemon's socket regardless of whether its file is unlinked. they are
inert directory entries. 117 of the reaped daemons removed their own files on SIGTERM (the
pre-fix code does bind cleanup to SIGTERM — what it lacks is the **exit** path, which is
precisely e19); the rest died earlier without one.

they are left in place deliberately: a mass delete under `/run/user/1000` is a destructive
act with no benefit that this gate needs, and the neighbour's own
`rhx keyrack daemon prune --owner @all` will reap them once that worktree upgrades — which
is exactly the q11 migration note in action.

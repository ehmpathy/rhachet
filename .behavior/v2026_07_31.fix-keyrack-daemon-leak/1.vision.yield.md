# vision: fix(keyrack) — bound the daemon leak via an idle-demand timeout, widen `@all` past the caller's own HOME

## .what

two holes in two already-shipped defenses compose into an unbounded daemon leak. close both, plus
the defect the first fix exposes the moment it lands, plus two the wisher approved into scope:

**the two the wish names:**

1. **`scheduleAutoTermination` gains an idle-demand timeout** and drops the `hasEverHadKeys`
   latch, so a daemon that never receives a key can still exit — while the startup race the latch
   guarded stays closed.
2. **`getAllKeyrackDaemonSocketPaths` drops the caller's own `homeHash` from its prefix**, so
   `rhx keyrack daemon prune --owner @all` can finally see the daemons whose divergent
   `homeHash` *is* the leak.

**the one fix 1 owes:**

3. **`startKeyrackDaemon` binds its extant cleanup to the exit path**, not only to `SIGTERM` /
   `SIGINT`. today `process.exit(0)` is a near-dead branch, so the gap is invisible; fix 1 makes it
   the common exit, and every self-terminated daemon would orphan a `.sock` and a `.pid` (e19).

**the two the wisher approved (2026-08-02):**

4. **`unlockKeyrackKeys` findserts the daemon last** — the call moves from `:48` to just before
   `daemonAccessUnlock` at `:279`, inside the `keysToUnlock.length > 0` branch. this collapses the
   startup race from minutes to milliseconds (e16), and a keyless daemon is never spawned when
   every key is omitted (e17). conforms to `vaultAdapterOsDaemon.ts:117`. **q8**
5. **`killKeyrackDaemonForTests` rebuilds the real socket path** — it constructs
   `keyrack.${sessionId}.sock` with no `homeHash` segment (`:32-35`), a shape the path builder has
   not produced since `homeHash` entered it, so every blackbox test's cleanup is a silent no-op.
   **q5**

no new subsystem, no new feature. one boolean latch replaced by a clock, one over-narrow glob
prefix widened by one segment, one extant cleanup bound to one more exit route, one statement moved,
and one stale path string corrected.

> **why item 3 rode along while items 4 and 5 were asked** — item 3 repairs damage fix 1 itself
> causes, which is completeness. items 4 and 5 repair adjacent defects that pre-date this change,
> which is scope expansion and therefore the wisher's call. both were put to the wisher and both
> were approved. see a10 and the council list.

## the outcome world

### day-in-the-life

**before** — a human works a normal day: a few `rhx keyrack unlock` calls, a few test runs.
each test run mints a throwaway `HOME` (`src/.test/infra/withTempHome.ts:20`), which mints a
fresh `homeHash` (`infra/getHomeHash.ts:12-18`), which mints a fresh socket path
(`infra/getKeyrackDaemonSocketPath.ts:52-56`), which spawns a fresh daemon that **no client
ever unlocks against**. that daemon sets `hasEverHadKeys = false` and can never satisfy its
own exit branch (`scheduleAutoTermination.ts:30`). it wakes every 15 minutes, forever, to ask
a question whose answer is structurally fixed.

the human notices no keyrack symptom at all. what they notice is that the desktop stalls.
weeks later someone counts: **1561 daemon sockets in `/run/user/1000` on this very machine**
(see groundwork). the human reaches for the tool built for exactly this —
`rhx keyrack daemon prune --owner @all` — and it reports *"no daemon active for any owner"*,
because `@all` matches only sockets that share the pruner's own `homeHash`
(`getAllKeyrackDaemonSocketPaths.ts:27-30`), and a shared `homeHash` is precisely what the
leaked population does not have. the one lever that exists is aimed at the one population
that is not the problem.

**after** — the same day. each throwaway-`HOME` daemon spawns, waits out its idle window
without serving a single command, and exits on its own. the count plateaus at roughly "one
per live session that actually unlocked something" and decays from there. and for the
backlog already on the machine, `rhx keyrack daemon prune --owner @all` now enumerates every
`homeHash` in the session and reaps them in one command.

### before/after contrast

| dimension | before | after |
|---|---|---|
| daemon that never receives a key | immortal — exit branch structurally unreachable | exits after the idle window |
| daemon whose client connects inside the startup window | survives (via `hasEverHadKeys` latch) | survives (via the q8 reorder — spawn lands milliseconds before the UNLOCK, not minutes before it; e16) |
| daemon holding live keys | survives | survives (unchanged) |
| daemon whose keys expired | exits on next 15 min tick | exits on next tick once also idle |
| `daemon prune --owner @all` reach | only sockets with the pruner's own `homeHash` | every `homeHash` in the caller's login session |
| observed *process* count | monotonic climb (issue measured 641 live) | plateau, then decay toward live sessions |
| observed *socket file* count | monotonic climb (1561 here) | decays too — **only with e19**; without it the files outlive the processes that made them |
| how it presents when broken | whole-desktop stall, never a keyrack symptom | n/a |

### the "aha" moment

the value clicks when someone reads the old exit condition out loud:

> `if (hasEverHadKeys && entries.length === 0) process.exit(0)`

and realizes the leak population is *defined* by `hasEverHadKeys === false`. the guard does
not merely fail to catch the leak — it **selects for it**. every daemon that survives 76 days
survives *because* the guard protected it. and the second aha lands right after: the cleanup
tool named `@all` never meant "all".

## user experience

three audiences:

1. **the human at the machine** — wants the stall to stop and a lever that actually reaps
2. **the test harness / any caller that sets `HOME`** — wants a safety net it need not think about
3. **future rhachet maintainers** — want the daemon's lifecycle to be legible without a census

### usecases fulfilled

| usecase | goal | today | after |
|---|---|---|---|
| run a test suite that mints a temp `HOME` | leave no residue | one immortal daemon per run | daemon self-reaps within the idle window |
| unlock a key, walk away, come back | keys still cached | ✅ | ✅ (keys present ⇒ never idle-exits) |
| unlock, keys expire | daemon releases its memory | ✅ | ✅ (once also idle) |
| clean up the machine now | reap the backlog | ✋ `@all` sees none of it | ✅ `@all` reaps every `homeHash` in session |
| a fresh daemon spawns, unlock is in flight | must not die mid-handshake | ✅ (latch) | ✅ the q8 reorder puts spawn milliseconds before the UNLOCK (e16) |

### contract inputs & outputs

**public CLI contract is unchanged.** the only user-visible delta is that `@all` now finds
things it previously could not:

```bash
# before — the lever that could not reach the leak
$ rhx keyrack daemon prune --owner @all

🔐 keyrack daemon prune
   └─ no daemon active for any owner

# after — same command, same output shape, real reach
$ rhx keyrack daemon prune --owner @all

🔐 keyrack daemon prune
   ├─ pruned daemon for owner=default (pid: 214431)
   ├─ pruned daemon for owner=mechanic (pid: 214987)
   ...
   └─ pruned N daemons
```

> `N` is left symbolic on purpose. this machine holds **1067 in-session socket files**, but
> how many back a *live* process is unmeasured here (q6) — so no concrete count is claimed as
> an outcome.

> ⚠️ **the wish and the issue both write `rhx keyrack prune --owner @all`. that command does
> not exist.** the real surface is `rhx keyrack daemon prune`
> (`src/contract/cli/invokeKeyrack.ts:1491-1545`); the top-level `keyrack relock` is a
> different operation (purges *keys*, not *daemons*). acceptance should be read against the
> real command. see q4.

**internal contracts** — three leaves change. two change *shape*; the third gains a handler.

`scheduleAutoTermination` gains an activity source and loses its latch:

```ts
/**
 * .what = periodically exit when the daemon holds no keys and has served no demand
 * .why  = a daemon nobody asks anything of serves no purpose; keying on demand
 *         (not on key *history*) is what lets a never-unlocked daemon exit at all
 */
export const scheduleAutoTermination = (input: {
  keyStore: DaemonKeyStore;
  activity: { getLastAt: () => number };   // <- new; starts at daemon start
}): NodeJS.Timeout => { ... };
```

```ts
// the exit condition, in full
const entries = keyStore.entries();          // purges expired as a side effect
if (entries.length > 0) return;              // holds live keys -> keep
const idleMs = Date.now() - activity.getLastAt();
if (idleMs < idleTimeoutMs) return;          // recent demand (or startup grace) -> keep
process.exit(0);
```

`getAllKeyrackDaemonSocketPaths` widens its prefix by exactly one segment:

```ts
// before — pins the PRUNER's own HOME
const prefix = `keyrack.${sessionId}.${homeHash}`;

// after — every homeHash in this login session
const prefix = `keyrack.${sessionId}.`;
// filename tail is now `${homeHash}[.${owner}].sock` -> parse homeHash, then owner
```

`startKeyrackDaemon` binds its extant cleanup to the exit path as well as to the signals (e19):

```ts
// before — cleanup reachable only via SIGTERM / SIGINT (:46-47)
process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);

// after — the self-exit path cleans up too
process.on('exit', () => {
  // sync only: an 'exit' handler cannot await. the OS reclaims the listener,
  // so server.close() stays out of here and only the unlinks run.
  unlinkSyncIfPresent(socketPath);
  unlinkSyncIfPresent(pidPath);
});
```

> **why here and not in `scheduleAutoTermination`.** the timer knows only `keyStore`; it does not
> know `socketPath` or `pidPath`, and to hand them over would couple the exit clock to the socket
> layout. `startKeyrackDaemon` already holds both in scope, so the seam is free.

### what leverage looks like

```ts
// createKeyrackDaemonServer.ts — the activity signal already has a home
const activity = genDaemonActivityClock();          // starts at daemon start
scheduleAutoTermination({ keyStore, activity });

const server = createServer((socket) => {
  handleKeyrackDaemonConnection({ socket }, { keyStore, homeHash, activity });
  // ^ activity.touch() fires on the socket's 'data' event — on *inbound bytes*, not on a bare
  //   TCP connect (e10) and not only on a fully parsed request (e18)
});
```

### timelines

**a leaked daemon, after the fix (idle window = 15 min, check tick = 15 min):**

| t | event |
|---|---|
| 0 s | caller mints a temp `HOME`, `findsert` spawns the daemon, probes reachability |
| 0–5 s | `isDaemonReachable` connects and destroys — a probe, **not** demand (e10) |
| 5 s | caller finishes/fails without ever sending `UNLOCK` |
| ~15 min | tick 1: no keys, idle 15 min ≥ window → **exit** |
| worst case | ~30 min (tick lands just before the window closes) |

**a legitimate daemon:**

| t | event |
|---|---|
| — | the interactive vault flow runs first (`:203-229`): yubikey / SSO / browser prompts, human-paced |
| 0 s | keys now in hand → `findsert` spawns and probes (q8 order) |
| +ms | `UNLOCK` arrives → `activity.touch()`, keys present |
| 0–9 h | keys live → `entries.length > 0` → never idle-exits, regardless of query rate |
| 9 h | last key TTL lapses; `entries()` purges |
| ≤ 9 h 30 m | no keys **and** idle → exit (was: exits on the next tick after expiry) |

## mental model

### how a human describes it to a friend

> "we had a little background process that caches your credentials. it was supposed to shut
> itself off when the credentials expired — but it only checked *'did I ever hold one?'*, and
> the ones piling up had never held one. so the shutdown check could never fire for exactly
> the processes that needed it. and the cleanup command was scoped to your current home
> directory, but the runaway ones each had their own fake home — so cleanup couldn't see them
> either. now it shuts off if nobody's asked it anything in a while, and cleanup looks at all
> of them."

### analogies / metaphors

- **the night watchman who can only clock out after his first visitor.** the rule was "go home
  once everyone you let in has left." a watchman nobody ever visited had no one to see out,
  so he stayed at his post for 76 days. the fix changes the rule to "go home if nobody has
  knocked in a while" — which retires the visitor-less watchman *and* still keeps the one
  whose visitor is walking up the drive.
- **a lost-and-found sorted by the finder's address.** `@all` searched the shelf labelled with
  the *searcher's* home, but every lost item was filed under a different one. widening the
  prefix is opening the whole shelf.
- **the smoke alarm wired to the light switch.** the poll is what makes them expensive — 606
  dormant processes are nearly free; 606 processes that wake every 15 minutes to run an
  impossible check drag swapped-out heaps back into RAM 0.67 times a second.

### terms — theirs vs ours

| they say | we say |
|---|---|
| "my machine is crawling" | zram at 99.6 %, `pgmajfault` in the billions, PSI-memory 4.4 h |
| "zombie processes" | leaked daemons — live, polling, keyless |
| "the cleanup command doesn't work" | `@all` resolves to `keyrack.$sessionId.$homeHash*` |
| "it never shuts down" | `hasEverHadKeys` is a latch that never sets |
| "shut down when unused" | idle-demand timeout on served commands |
| "fake home directories" | caller-set `HOME` → divergent `homeHash` → mint-per-call socket |

## evaluation

### how well it solves the wish's acceptance

| acceptance | verdict | why |
|---|---|---|
| a daemon that never receives a key terminates within the idle window | ✅ | `hasEverHadKeys` deleted; the sole gates are "no keys" + "no demand" — both reachable from birth |
| the startup race does NOT return | ✅ **via the q8 reorder** (agreed 2026-08-02) | the race window is **not** findsert's 5 s wait — it is spawn→first-served-command, and `unlockKeyrackKeys.ts:48` today findserts *before* the entire interactive vault flow (`:203-229`), which is minutes-scale and human-paced. the approved q8 reorder collapses that to milliseconds, so any sane idle window clears it. see q8/e16 |
| `daemon prune --owner @all` reaches divergent `homeHash` | ✅ | prefix drops the `homeHash` segment; verified 1067 in-session sockets become reachable here. *(the wish writes `keyrack prune`; the real command is `keyrack daemon prune` — q4)* |
| regression clamp: run the suite twice, count does not double | ✅ **plus a stricter inner clamp** — q9 | the wish's criterion holds as the outer bound (measure `keyrack.*.sock` in a test-scoped `XDG_RUNTIME_DIR` across two runs — e11); q9 adds a full-reap assertion under a short idle window, which proves *bounded* rather than merely *not worse* |
| count plateaus then decays | ✅ **for processes; for files only with e19** | requires a real observation window, not a unit assertion — a build-phase verification, see v4. and note e19: without the exit-path cleanup the *files* accumulate even as the processes die |

### pros

- **tiny diff, large blast radius reduction** — one latch → one clock, one prefix segment
- **the guard's purpose is preserved** — the wish is explicit that the latch is *not unreasonable*.
  idle-from-start protects the same race, because the approved q8 reorder shrinks the race to
  milliseconds. *(without q8 the window is the whole interactive vault flow and no idle window is
  safely wide enough — which is why q8 was the first fulcrum raised.)*
- **demand is the honest proxy** — key *history* cannot separate "unlock inbound" from "no
  client ever came"; "has anyone asked me anything" separates them exactly
- **`entries()` stays the purge trigger** — the extant TTL-on-read behavior
  (`daemonKeyStore.ts:76-94`) is untouched; the tick still drives it
- **backlog and bleed are addressed by complementary levers** — fix 1 stops new leaks; fix 2 reaps
  the backlog already here (1561 socket files, of which an unmeasured subset back live processes —
  q6; the rest are orphans that prune unlinks)
- **blast radius is measured, not hoped** — `handleKeyrackDaemonConnection` has **exactly one**
  call site (`createKeyrackDaemonServer.ts:43`), so the `activity` thread is a one-site change;
  and `createKeyrackDaemonServer`'s own signature need not move at all (the activity clock is born
  inside it), which spares its 7 call sites (1 prod + 6 test — see internal research)
- **no CLI flag added, no output *shape* changed** — the treestruct and `--json` modes stay as
  they are. *(two honest caveats: a new env var `KEYRACK_DAEMON_IDLE_TIMEOUT_MS` is a surface —
  test-only and undocumented, per q10 — and the output **volume** spikes once, on the backlog reap,
  before it settles back down. see e14/q7.)*

### cons

- **fix 1 cannot retire the extant backlog.** leaked daemons run the *old* bytecode; a new
  exit rule does not reach them. the backlog on this machine — 1561 socket files, an upper bound on
  the live daemons behind them (q6/e19) — is cleared only by fix 2 (or a manual `pkill`). the two
  fixes are therefore genuinely complementary, not redundant.
- **worst-case lifetime is 2× the idle window** (tick granularity). acceptable — the point is
  boundedness, not promptness.
- **the residual is a burst, not a trickle.** expiry bounds *lifetime*, not *concurrency*. a full
  suite run that mints ~100 temp HOMEs still spawns ~100 daemons, each alive up to ~30 min — so
  peak concurrency is unchanged, only the tail is cut. that is the wish's intended trade (root
  cause is issue item 3, out of scope; caller-side teardown is filed elsewhere), but it means the fix
  **bounds** the leak rather than prevents it. **the approved q8 reorder is the exception that does
  prevent** — on the all-omitted path (e17) no daemon is spawned at all, so that share of the burst
  disappears rather than expires.
- **a keyless-but-busy daemon lives forever.** if something connects and issues commands every
  few minutes while never unlocking, it never idles out. no such caller is present today, and
  the alternative (an absolute max lifetime) trades a real regression risk for a hypothetical.
- **the extant unit test encodes the defect as intent.** `scheduleAutoTermination.test.ts:35`
  literally asserts *"does not terminate (no keys were ever present)"*. that assertion is the
  bug, written down as a promise. it must be rewritten, not merely extended — a change that
  will look, in the diff, like weakening a test. it is not; see `rule.require.review-test-changes`.
- **fix 2 widens by one axis and leaves another.** the `sessionId` pin stays. on this machine
  that leaves 494 of 1561 sockets unreachable by `@all` — see the fulcrum in q1.

|---|---|---|---|

| e3 | daemon holds live keys, nobody queries for hours | `entries.length > 0` short-circuits before the idle check | unit: keys present + long idle → no exit |
| e4 | keys expire, client still active | `entries()` purges → 0; idle small → survives one more window | unit |
| e5 | keys expire, client gone | 0 keys + idle → exits | integration case7 (extant, retargeted) |
| e6 | `@all` with sockets across several `homeHash` | all enumerated; each killed by its own `socketPath` | unit: `getAllKeyrackDaemonSocketPaths` with 3 hashes |
| e7 | `@all` must NOT match another `sessionId` | prefix carries a **trailing dot** (`keyrack.3.`), so `keyrack.34.…` cannot match | unit: extant fixture at `getAllKeyrackDaemonSocketPaths.test.ts:59-64` still passes |
| e8 | owner parse after the widen — `${homeHash}.${owner}.sock` vs `${homeHash}.sock` | parse `homeHash` as the first segment, remainder (if any) is `owner`; validate `homeHash` as 8 hex | unit: both shapes, plus a malformed name is skipped |
| e9 | stale `.sock` with a dead pid | `killKeyrackDaemon` SIGTERMs, swallows `ESRCH`, unlinks both files (`killKeyrackDaemon.ts:39-58`) — but reports `killed: true` for an already-dead pid | unit; **cosmetic pre-existing wart**, flagged not fixed (q5) |

| e15 | `@all` spans owners, not only the default | **measured: 7 distinct `homeHash` values carry a session-4 `…mechanic.sock`** — owner-suffixed sockets leak too (219 of 1561 overall). e8's owner-parse path is therefore hot, not incidental | unit: parse both shapes across many hashes |

**e10 is the design-decisive edge case.** it is the reason the vision proposes *"a command was
served"* rather than the more obvious *"a socket connected"*. the obvious choice defeats itself:
the very act of watch-for-death would prevent the death.

| e16 | **the real startup race: spawn → interactive vault flow → UNLOCK** | `unlockKeyrackKeys.ts:48` findserts the daemon **before** the vault loop at `:203-229`, where `adapter.unlock` drives yubikey / SSO / browser prompts at human pace (extant per-adapter timeouts are ~3 min: `vaultAdapterAwsConfig.ts:287-291`, `setupAwsSsoProfile.ts:397-401`, and a bulk unlock loops over many keys). `daemonAccessUnlock` fires only at `:279`. so the window between spawn and first-served-command is **minutes, not seconds** — and under any modest idle window the daemon could exit mid-unlock. **q8 proposes the reorder that collapses this window to milliseconds** | integration: slow-vault fixture, assert the daemon survives to the UNLOCK |
| e17 | **a prod path spawns a daemon that can never receive a key** | `unlockKeyrackKeys.ts:278` gates `daemonAccessUnlock` on `keysToUnlock.length > 0`. if every key resolves `absent` / `lost` / `remote` (`:159,194,234`), the daemon spawned at `:48` receives **no command, ever** — under today's latch it is immortal. this is a **first-party production** leak path, not a test artifact | integration: unlock where all keys are omitted → daemon exits (and, with q8, is never spawned) |

**e14 is the ergonomics hazard the fix appears to create — until you date it.** it is easy to miss
because the defect hides it: the per-daemon print loop has never had more than a couple of daemons
to print. widen the glob and that loop becomes a wall of text. but the wall is **transitional, not
structural** — it exists once, on the reap of a backlog that fix 1 + e19 then stop from re-forming.
q7 takes the decision on that basis: leave the print alone rather than pay permanent complexity for
a one-day symptom.

| e18 | **a client mid-request must not be cut off** | `handleKeyrackDaemonConnection.ts:48-54` buffers and **returns early** on unparseable JSON — "incomplete json, wait for more data". so a client can hold an open socket with a partial write while the daemon awaits the rest. if activity were touched only on a *fully parsed* request, that tick could fire mid-request, `process.exit(0)`, and the client would see `ECONNRESET` on a legitimate call. **the signal must therefore be inbound bytes (`'data'`), not a completed parse** | unit: touch on `'data'` before the parse attempt; integration: chunked write across a tick |

| e19 | **self-termination orphans its own socket and pid files** | the cleanup that unlinks `.sock` + `.pid` lives in `startKeyrackDaemon.ts:30-44` and is bound **only** to `SIGTERM` / `SIGINT` (`:46-47`). `scheduleAutoTermination.ts:32` calls `process.exit(0)` directly, which fires neither. so **every daemon that auto-terminates leaves both files behind.** today that path is nearly unreachable, so the wart is invisible; once fix 1 makes it the common exit, the *process* count decays while the *file* count still climbs — and `@all` then enumerates thousands of dead sockets and reports each as a phantom kill (e9). **the exit path must clean up.** the cleanest seam is `startKeyrackDaemon.ts`, which already holds `socketPath` and `pidPath` in scope: register `process.on('exit', …)` there with the **sync** unlinks only. two nuances for the build: (a) an `'exit'` handler may run only synchronous work, so `server.close()` (async) must stay out of it — the OS reclaims the listener at exit anyway; (b) `scheduleAutoTermination` holds only `keyStore`, so it must **not** be the site of the cleanup — it does not know the paths, and to hand them over would couple the timer to the socket layout | integration: daemon self-terminates → assert both files are gone |

**e16 is the acceptance-critical edge case.** the wish's second acceptance criterion — "the race
the original guard prevented does NOT return" — turns entirely on how wide that race really is.
the intuitive answer (findsert's 5 s reachability wait) is **wrong**; the true window spans the
interactive vault flow. any idle-timeout design that does not account for this either reintroduces
the race or needs an absurdly wide window. q8 is the way through.

**e19 is what makes acceptance #5 true of files as well as processes.** "the count plateaus and
then decays" is measured on the process table — but a human greps `/run/user/$uid`, and prune reads
that directory. without the cleanup, fix 1 succeeds invisibly: processes die, files pile up, and
`@all` reports a thousand phantom kills. it is a small addition (one more handler bound to the
extant `shutdown`) that the fix cannot honestly ship without.

**e10 and e18 together fix the activity signal's grain.** e10 rules the grain *coarser* than a TCP
connect (a probe sends no bytes and must not count); e18 rules it *finer* than a completed request
(a partial write is a real client and must count). the two constraints meet at exactly one place:
**the `'data'` event.** that is not a preference — it is the only grain that satisfies both.

## open questions & assumptions

### assumptions

- **a1** — the connection callback in `createKeyrackDaemonServer.ts:42-44` and the parsed-request
  path in `handleKeyrackDaemonConnection.ts:44-65` are the only routes by which a client reaches
  the daemon, so a `touch()` at the parsed-request point captures all demand. *verified by reading
  both files; no other server entry point is present.*
- **a2** — the idle window is measured with `Date.now()` deltas and a raw-ms constant, to match the
  extant `checkIntervalMs` style in this file. *this read "flagged, not decided" in an earlier draft
  — an undecided item dressed as an assumption. it is now decided; see q12.*
- **a3** — every leaked socket has a companion `.pid` file, so `killKeyrackDaemon`'s pid-file path
  works for the widened set. **evidence: 1561 `.sock` and 1561 `.pid` on this machine.** note the
  evidence is an *aggregate count match*, not a per-pair check — it is strong but does not strictly
  exclude one orphan of each kind. a per-pair assertion belongs in v2's fixture, where the pairing
  is constructed rather than observed.
- **a4** — killing a daemon does not require passing `verifyCallerLoginSession`; kill is
  pid + `SIGTERM` (`killKeyrackDaemon.ts:40`), not a socket command. *verified by reading; this is
  why a cross-`homeHash` (and, if chosen, cross-session) prune is mechanically possible at all.*
- **a5** — the two fixes belong in **one PR**. they touch one subsystem, share the one integration
  test file, and the wish's own acceptance list spans both. splitting doubles the release cycle for
  a single coherent repair. *(the wish cites `rule.require.one-pr-per-worktree`; that brief is
  **absent** from this repo's `.agent/` tree — grep found no match. the recommendation stands on
  its own merits, not on the citation.)*
- **a6** — item 3 of the issue (re-key identity off login session + owner instead of `HOME`) stays
  **out of scope**, per the wish. neither fix forecloses it later.
- **a7** — **self-termination is the right mechanism** for bounding the leak. this is inherited
  from the wish, not derived: the wish asks for an idle timeout *inside the daemon*. the untaken
  alternative is an **external reaper** — e.g. every `rhx keyrack` invocation opportunistically
  reaps sockets whose daemons are keyless and idle. its one real advantage is that it reaches
  daemons that already run pre-fix bytecode, which self-termination structurally cannot (q1).
  *why the wish's choice still holds:* a reaper cannot read another daemon's key store without a
  socket command that `verifyCallerLoginSession` may refuse (`:30-39`), so it would have to guess
  idleness from file mtimes — a weaker signal than the daemon's own clock — and it would put a
  destructive action on every CLI invocation, against `rule.require.safe-by-default`. recorded
  because it is an inherited assumption rather than a proven one.
- **a8** — **the daemon holds live keys ⇒ it is worth keeping**, so `entries.length > 0`
  short-circuits before the idle check. this also protects the `os.daemon` vault, where the daemon
  *is* the storage (`vaultAdapterOsDaemon.ts:117-134`), and where a grant with a null `expiresAt`
  never purges (`daemonKeyStore.ts:47,81`) and so pins the daemon alive indefinitely. that is the
  intended read — but note it means a null-TTL grant makes a daemon immortal by design. no such
  grant is minted on the unlock path today (`unlockKeyrackKeys.ts:245` always computes an
  `expiresAt`), so this is a code-level property, not a live one.
- **a9** — **wall-clock `Date.now()` deltas are adequate for the idle measure.** a suspend/resume
  jumps the clock forward, which makes keyless daemons exit sooner on resume — the desirable
  direction, and consistent with key TTLs, which are wall-clock ISO stamps
  (`daemonKeyStore.ts:46-49`). a clock set *backwards* would delay an exit, never cause a wrong
  one. a monotonic source would be marginally more correct and materially less consistent with the
  extant TTL comparisons; not worth the divergence.
- **a10** — **an exit cleans up after itself.** i had assumed the daemon's socket/pid files are
  removed whenever it dies. **false, and it matters** (e19): the cleanup is bound only to
  `SIGTERM`/`SIGINT` (`startKeyrackDaemon.ts:46-47`), while `scheduleAutoTermination.ts:32` exits
  via `process.exit(0)`. so the very path fix 1 makes common is the one path that leaves its files
  behind. the vision now treats the exit-path cleanup as part of fix 1, not as a separate concern.
  **why this is in scope while q8 must be asked** — both edit a prod file the wish never names, so
  the asymmetry needs its line drawn: **e19 repairs damage fix 1 itself causes; q8 repairs damage
  that pre-dates fix 1.** a fix that introduces a regression must clean up after itself — that is
  completeness, not scope creep. a fix that also repairs an adjacent, independent defect is scope
  expansion, and scope belongs to the wisher. by that line e19 rides along and q8 gets asked.

- **q3 [answered] — does "client connected" have an extant server-side signal, or must one be added?**
  **it is already present**: `createServer((socket) => …)` at `createKeyrackDaemonServer.ts:42`

  event is the unique grain that satisfies both. no new plumbing — only a `touch()` at an extant
  point, threaded through `context`.

## what is awkward?

- **the extant test asserts the bug.** `scheduleAutoTermination.test.ts:35` promises
  *"does not terminate (no keys were ever present)"*. the fix must delete a green assertion — the
  single most uncomfortable move here, and precisely the shape `rule.require.review-test-changes`
  warns about. the discomfort is correct and should be resolved by *articulating* the inversion in
  the diff, not by softening it.
- **the obvious activity signal is the wrong one** (e10). "touch on connect" is what anyone would
  reach for, and it is self-defeating: watching for the daemon's death would prevent it. the
  correct signal — "a command was served" — is one layer deeper and reads as an odd choice until
  you know why. the `.why` comment carries the whole weight of that decision.
- **the leak spans two sessions, and the wish's frame has one axis.** the wish says the divergent
  `homeHash` *is* the leak. on this machine it is one of two divergences. a `homeHash`-only widen
  is faithful to the wish and leaves 494 sockets stranded — a partial victory presented as complete
  unless it is named out loud. it is named (q1), and **the wisher chose the `homeHash`-only widen
  on 2026-08-02**. so the 494 stay stranded by design: they belong to a prior login session, and to
  reap them would drop that session's cached credentials. they need a manual `pkill`, and that is
  the right kind of awkward — a limit chosen with the cost known, rather than one discovered later.
- **"the count plateaus and decays" cannot be proven in CI.** it needs a real machine and real
  hours. the honest clamp is the narrower e11 ("does not double across two runs"); the plateau
  claim rests on a manual observation (v4). that gap between what we assert and what we can prove
  is uncomfortable and should not be papered over.
- **the wish's own framing of the startup race is too narrow, and i inherited it.** the wish says
  "a daemon whose client connects inside the startup window survives" — which invites the reading
  that the window is the few seconds findsert waits. it is not: it is spawn→first-served-command,
  and rhachet's main unlock path stretches that across every interactive vault prompt. i had this
  wrong in the first draft and asserted a "180× margin" that does not exist. the correction (q8)
  reaches into a prod file the wish never names, so the honest repair to the *most* load-critical
  acceptance criterion was also the change most likely to be called scope creep. **the wisher
  approved it on 2026-08-02, which settles the tension but does not erase the lesson**: the most
  load-bearing correction in this vision was one i first argued *against* myself, and it only
  surfaced because r1 asked what the startup window actually spans instead of trusting the phrase
  the wish used for it.
- **the repair to `@all` briefly degrades `@all`'s output** (e14/q7). the same widen that makes the
  command useful turns its first report into ~1000 lines. my first instinct was to redesign the
  print loop — and that instinct was the awkward part, not the output: it would have added a UX
  change the wish never scoped, to solve a symptom that lasts one reap. the discomfort resolved
  once i dated the problem instead of only sizing it. what remains awkward is how naturally a
  correct domain fix invites an adjacent redesign, and how easily that redesign passes for
  diligence.
- **a third leak source was found that the wish did not file** (q5, the stale blackbox cleanup).
  to include it was scope the wisher had not authorized; to exclude it meant we ship a leak fix
  while a known-dead cleanup path stays dead. best-guessed toward inclusion, flagged, **and approved
  2026-08-02**. the residual awkwardness is that it was only found by accident — a cleanup that
  silently no-ops leaves no trace in any test result, so this class of defect is invisible until
  someone reads the path builder and the path consumer side by side.
- **worst case is 2× the window, and no rule enforces an absolute ceiling.** a keyless daemon that
  is *touched* regularly never idles out. no such caller is present — but the fix bounds the leak
  by argument about caller behavior, not by construction. an absolute max lifetime would close it
  by construction and would also risk killing a legitimately busy daemon. the tradeoff is taken
  deliberately toward the safer regression profile; it still feels slightly unfinished.

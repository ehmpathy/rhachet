fix(keyrack): bound the daemon leak via idle-demand timeout, widen `@all` past homeHash

UPGRADE NOTE:
daemons spawned BEFORE this version run the old bytecode and cannot self-terminate —

## peer review round 2 — the wall clock

round 2 cleared 8 of 9 at l1. one blocker remained, from `arch-hazards-behavior`, and it is the
sharpest critique this branch received: **the idle delta read `Date.now()`.**

### my vision had weighed this and gotten it wrong

assumption **a9** argued against a monotonic source in as many words:

> *"a clock set **backwards** would delay an exit, never cause a wrong one. a monotonic source
> would be marginally more correct and materially less consistent with the extant TTL
> comparisons."*

**a backward jump is not a delay — it is this branch's own defect, restored.** it makes
`Date.now() - lastAt` negative, so `idleMs < idleTimeoutMs` holds and the daemon does not exit
on that tick, or any tick until wall time catches back up. i had replaced a boolean latch that
could never open with a gate that a clock adjustment can weld shut.

**and the consistency argument was a category error:**

| quantity | example | correct clock |
|---|---|---|
| absolute deadline | a key granted until 5pm expires at 5pm | wall clock — the keystore's iso stamps |
| elapsed duration since an event | 15 minutes with no demand | monotonic |

a TTL names a moment in the world. an idle window names no moment at all. uniformity between the
two is not a virtue — it is the mistake. **my strongest argument for `Date.now()` was an argument
for the wrong quantity.**

### what changed

`performance.now()` on both sides of the pair — the birth stamp, every `touch()`, and the delta.
`getLastAt`'s docblock now states the value is **monotonic, not epoch**: meaningful only as a
difference against another read of the same clock, never to be formatted, stored, or compared
against a `Date`. that is the one hazard the change introduces, so it is named at the contract.

### the clamp

| clamp | reverted | went red | discriminates |
|---|---|---|---|
| `[case6]` — clock set 1h into the past, daemon must still terminate | both sides to `Date.now()` | ✅ `Expected: true, Received: false` | ✅ the other 10 cases stayed green |

the discrimination is the part worth the record: the clamp guards the *monotonic property*
alone, not time-advance in general. a clamp that had gone red across the whole file would have
proven only that i broke the clock.

### the detour: the global `performance`, not the import

the first attempt imported `performance` from `node:perf_hooks` and the two exit-path cases went
red. jest's fake timers patch `globalThis.performance`; a module-scoped import escapes them, so
the clock stayed frozen while the timers advanced. the code now reads the global deliberately,
with a `.note` that says why — so the next reader does not re-run that experiment.

### blocker 1: i hardened the replica and left the original

round 1 had me allowlist five bare catches in the blackbox **replica**,
`killKeyrackDaemonForTests.ts`. i hardened the copy and left the original — even though three
of the four catches in `killKeyrackDaemon.ts` already allowlisted, so the pid read was the sole
holdout in a file where the correct pattern appears three times below it.

that is verbatim the argument i had written into my own `[case5][t1]` comment two rounds
earlier: *"a guard applied to one of a symmetric pair is a guard not applied."* i wrote the
principle, applied it to an env-var pair, and did not apply it to the four catches in front of
me.

### blocker 2: the reviewer's diagnosis was wrong, and it found the worst defect anyway

the report predicted that two spawns in a race collide on `bind`, one fails, and orphans are
left behind. **that is not what happens.** `createKeyrackDaemonServer.ts:40-45` unlinks any
stale socket *before* it binds — so there is no `EADDRINUSE`. the later daemon **takes the path
over**, and the earlier one lives on with a socket file it no longer owns.

**the loser of this race is the FIRST daemon, not the second.** and that reframe is what
exposed the regression: my new `process.on('exit', unlinkOwnFiles)` unlinked **by path**. so
the earlier daemon's exit — the exit this branch introduces — would delete the *live*
successor's socket and pid file.

i predicted the damage: an invisible zombie, the successor alive with no file on disk. **the
clamp proved it worse.** with the ownership check reverted, `[case11]` fails one line before
the file assertions:

```
expect(isProcessAlive(pidLater)).toBe(true)
Expected: true    Received: false
```

**the successor dies too** — its socket gone, its commands fail to connect, it receives no
demand, it starves and idles out. a cascade. the branch would have converted a prior leak into
that leak *plus* a way to kill a healthy daemon that holds live credentials.

`unlinkOwnFiles` now earns its name: the pid file is the ownership record, and the handler
stands down when it names another process.

### what the clamp itself taught

`[case11]`'s first draft held the successor in demand with `isDaemonReachable`. that renews no
lease — a bare connect is deliberately **not** demand (e10) — so both daemons idled out together
and the case was vacuous. it needs a real `STATUS` command. **my own design decision defeated
my own test**, and only a red run that failed for the wrong reason surfaced it.

### the lock is declined, and filed

`findsertKeyrackDaemon.ts` has an empty diff against `origin/main`; the check-then-spawn is
`main`'s. the q8 reorder *reduces* the collision window (each process findserts after its own
human-paced vault flow rather than at process start), and fix 1 is what makes a lost race
benign — the loser now costs one daemon for one idle window.

an atomic `O_EXCL` pid-file claim would close it by construction and is a **clean rework**
(two files, no contract change). filed for the council, not built here — per the same `a10`
line: **a fix must repair the damage it causes; an adjacent independent defect is the wisher's
scope.** the ownership check is the first kind. the lock is the second.

### the one remedy declined, and why

r011's item 2 asked that `touch()` be gated on session verification. that was **taken** — but not
where it proposed. it suggested the touch move *into* `processRequest`, after the check. that would
have re-broken e18: a client mid-write has no parsed request yet, so its bytes would stop renewal of
the lease and a slow caller would be cut off with `ECONNRESET`.

the resolution keeps both: the session verdict is computed **once, at connection open** — peer
credentials are stamped by the kernel at connect and cannot change mid-connection — and the touch
stays on `'data'`, before the parse. one gate for *who*, one grain for *how much*.

r011 had in fact already seen this itself, and said so:

> "this doesn't collide with e10/e18 (grain of *how much* counts as demand ...). it's an orthogonal
> axis: ***who*** can generate demand."

it named the right axis and then proposed a remedy that would have collapsed the two axes back
together. the item was right; the remedy was not. to take one without the other is the whole job.

### what is NOT clamped, said plainly

the denial gate's **negative** branch — a caller from a different login session — has no test. it is
not clampable on a single-session host: it needs two real login sessions, and `/proc/$pid/sessionid`
is kernel-managed and unforgeable by design (which is the entire point of its use).

this is an **inherited** gap, not a new one: `verifyCallerLoginSession.ts` has never had a test file
in this repo. i do not widen the gap, and i will not claim coverage i do not have. the gate's
*positive* branch is clamped — `[case10]`'s drip is a same-session caller that renews its lease
across ~50 termination ticks, which cannot pass unless the gate admits a legitimate caller.

### one real defect met while these closed

three integration cases (`[case7]`, `[case9]`, `[case10]`) went red once the suite grew heavier.
the shape was identical in all three: the daemon **never became reachable**, or died between the
probe and the first command.

my first hypothesis was the new session gate — it was the newest change and all three failures
involved sockets. **it was wrong**, and the check was cheap: run `[case9]` alone. it passed. a gate
that rejects callers does not pass in isolation and fail under load.

**the real cause:** those cases set idle windows of 500–600 ms, and — correctly, per e10 — a probe
does **not** renew the lease. so the daemon's clock runs from its own boot no matter how many times
the test polls. under a loaded host the poll cadence stretched past the whole window, and all 50
probes missed a daemon that had come and gone between two of them.

the windows now exceed each case's own setup latency, with a `.note` at each site that names the
constraint. `[case10]`'s is pinned from both sides — longer than its setup, shorter than its drip —
and re-proven red at the new constants (`SyntaxError: Unexpected end of JSON input`: the daemon exits
mid-drip and the client's response is empty).

**the lesson is the same shape as the fix itself.** the tests assumed a probe keeps the daemon alive.
it does not — *by design*, because that is exactly what e10 exists to prevent. i wrote that design
and then wrote three tests that leaned on its opposite. a correct guarantee will break the code that
quietly assumed the bug.

### and one the type-checker caught that the test run did not

a green test is not a correct test. `--what types` is not a formality.

## handoff to `5.3.verification` — the one acceptance criterion no test can settle

four of the wish's five acceptance criteria are clamped by tests and RED-verified:

| criterion | clamp |
|---|---|
| a keyless daemon terminates within the idle window | `scheduleAutoTermination.test.ts [case2]`, `[case9]` |
| the startup race does NOT return | `unlockKeyrackKeys.integration.test.ts [case7]` |
| `@all` reaches a divergent `homeHash` | unit `[case3]`, integration `[case8][t4]`, acceptance `[t0]` |
| two runs must not double the count | `[case9]`, plus q9's stricter return-to-baseline |

the fifth — **"the count plateaus and then decays"** — cannot be settled by a test. it needs a real
machine over real time, and it is the one criterion 5.3 must actually measure.

**i attempted the measurement here, found it unusable, chased WHY it was unusable, and the answer
turned out to be a regression of my own plus a feedback loop nobody had named.** the counting was a
dead end; the cause behind the counts was not:

- `/run/user/1000` now holds **1867** `keyrack.*.sock`, against the vision's census of 1561
- of those, **763** carry `sessionId=3` against the census's 494 — while `/proc/self/sessionid`
  confirms the current session is still **4**

both numbers are confounded, on two counts, and neither supports a conclusion in either direction:

1. **a full acceptance suite was running during the count.** it spawns a daemon per temp-HOME test,
   and a post-fix daemon needs up to 2× the idle window (~30 min) to reap itself. an in-flight suite
   inflates the population by exactly the daemons that have not yet had time to exit.
2. **a socket file is not a live daemon.** q6/e19 already establish that the file count is an *upper
   bound* — orphans from pre-e19 exits are counted too. the live-process count needs
   `pgrep -fc startKeyrackDaemon`, which is outside this session's permitted commands.

### the session-3 growth was the tell — and it was not a dormant session at all

a dormant login session cannot gain sockets, so that number was either wrong or my model was. i
chased it instead of counting again, and the answer came in three cheap steps:

1. **sort the session-3 sockets by mtime.** the newest were *seconds* old — `keyrack.3.bd1b6643.case4.sock`
   and siblings, spaced 5–20 s apart, the exact cadence of a test file that runs four cases
2. **read the pid file, then that pid's `/proc/<pid>/sessionid`.** it really was session 3, and alive
3. **read `/proc/<pid>/cmdline`.** the decisive line:

```
.../rhachet.vlad.feat-keyrack-vault-aws-params/src/.../startKeyrackDaemon.ts
```

**a different worktree.** session 3 is not a prior login whose leftovers linger — it is a *concurrent,
active* test run in `rhachet.vlad.feat-keyrack-vault-aws-params`, on this machine, right now. and
that worktree runs the **unfixed** code: `hasEverHadKeys` is still on its `scheduleAutoTermination`.

so this machine is an unplanned A/B of the very defect this branch repairs:

| session | code | sockets at census | now |
|---|---|---|---|
| 3 — the other worktree | **unfixed** (`hasEverHadKeys`) | 494 | **763** (+269) |
| 4 — this worktree | **fixed** (idle timeout) | 1067 | **1109** (+42) |

that contrast is suggestive and i am deliberately **not** claiming it as proof: i cannot measure the
other worktree's test volume, socket files remain an upper bound on live daemons, my count includes
daemons from before the fix existed, and my newer tests scope `XDG_RUNTIME_DIR` to `/tmp` so their
daemons never land in this directory at all. it is a data point, not a verdict.

**what the census note in the vision must be corrected to say:** session 3 was read as "a prior
login session" whose daemons "predate this branch" and would need a manual `pkill`. that is wrong.
it is a live neighbour.

### and that correction turns q1 from a judgment call into a demonstrated one

the vision defended the `sessionId` pin by argument: to reap another session's daemons "would
silently drop that session's cached credentials — a textbook `rule.forbid.surprises` violation."
that was hypothetical when written.

it is not hypothetical now. had q1 gone the other way, **the `prune --owner @all` inside my own new
acceptance test would have killed a colleague's live daemons mid-suite** and broken their run, on
this machine, today. the pin is the only reason it did not.

note the two defenses cover different neighbours, which is why both were needed:

- the **`sessionId` pin** protects the other worktree (session 3)
- the **`XDG_RUNTIME_DIR` scope** i added to the acceptance test protects concurrent work in *my own*
  session (4), which the pin does not cover at all

### the feedback loop nobody had named: the leak degrades the session check

the full acceptance suite surfaced a crash the counting never would have:

```
UnexpectedCodePathError: daemon GET command failed
  { "error": "UnexpectedCodePathError: ss command failed
              { \"inode\": \"2395507931\", \"signedInode\": -1899459365 }" }
```

`getSocketPeerPid` resolves the caller's pid by a shell-out — `ss -xp | grep`, under a **5 s
timeout** (`getSocketPeerPid.ts:73-76`). `ss -xp` enumerates *every* unix socket on the machine. so:

> **the more daemons leak, the more work the session check does — until the shell-out fails and the
> daemon refuses callers it should serve.**

that is a loop that feeds itself, between the two halves of this subsystem, and it is the sharpest
argument yet for why the leak had to be bounded: at 1867 sockets the *authentication path itself*
starts to fail.

**the precise failure mode is NOT established, and i will not write one down that i did not see.**
what the evidence supports:

- the shell-out threw — the `ss command failed` branch is the `execSync` catch, and `|| true` in the
  command means a grep no-match cannot reach it
- the cost is load-proportional by construction — `ss -xp` scans every socket, read from the source
- the machine carried 1867+ sockets and two concurrent suites at the time
- the lazy fix removed the failure and cut the time (numbers below)

what it does **not** establish: whether the throw was the 5 s timeout, a fork failure under load, or
another cause entirely. the error passes `cause` into `UnexpectedCodePathError` but the rendered
output shows only `{ inode, signedInode }` — so the errno never reached the log. i grepped for
`ETIMEDOUT` and found none, which is absence of evidence, not evidence of absence.

**that diagnostic gap is itself worth a line**: an error named `ss command failed` that cannot tell
you *how* it failed sent me to a confidently wrong-shaped conclusion on the first pass. filed with
the `SO_PEERCRED` rework below — whatever replaces this should surface the errno.

(the signed-32-bit inode wrap in the same error's metadata is a distraction — it is already handled
at `:60-69`, and the grep pattern covers both representations.)

**the `ss`-based lookup is a pre-existing design i am not rewriting here** — per the same `a10` line
that governed e19 vs q8, an adjacent independent defect is the wisher's scope. it is filed for the
council: `getSocketPeerPid` should read `SO_PEERCRED` directly rather than shell out to a
whole-machine scan, which would make the check O(1) instead of O(sockets).

### the part of that loop that was MY regression

p8 moved `verifyCallerLoginSession` to run when the connection **opens**. that was wrong, and the
`ss` cost is why:

- `isDaemonReachable` connects and destroys **without a byte sent** (e10). under p8 as first written,
  that probe still paid a full `ss -xp` machine scan
- the reachability polls in this repo's own tests run **up to 50×** per case
- so i had multiplied the cost of the cheapest operation in the subsystem by the most expensive

**this also re-explains the three failures i had diagnosed as "a loaded host".** i was half right —
there was genuine contention, from the neighbouring worktree — but i missed that *my own change* had
made every probe enormously expensive, which is what stretched the poll cadence past the idle window.
the idle-window widening was still correct; it was treating a symptom whose other half was mine.

**the fix:** evaluate the verdict lazily, on first bytes, memoized per connection.

```ts
let sessionDenial: string | null | undefined;   // undefined = not yet evaluated

socket.on('data', (chunk) => {
  if (sessionDenial === undefined) sessionDenial = getSessionDenial();
  if (sessionDenial !== null) { /* refuse, and do NOT touch */ return; }
  context.activity.touch();
```

this keeps every property r011.2 asked for — the verdict still precedes the first byte that could
count as demand, and it is still computed once, since peer credentials are kernel-stamped at connect
— while a probe that sends no bytes now pays nothing.

**measured, before → after the lazy fix:**

| suite | before | after |
|---|---|---|
| `integration path://keyrack/daemon` | 78 s | **57 s** |
| `acceptance keyrack.env-all` | **failed**, 764 s for one file | **68 passed**, 198 s for three |

### the clamp for this regression exists but is load-dependent — said plainly

`keyrack.env-all` **was** observed red under the eager check and green under the lazy one, which is
genuine RED verification and it arrived unbidden. but it is not a clamp i would trust:

> it went red **because this machine held 1867 sockets**. on a clean machine, an eager check would
> likely pass every suite — exactly as it did across every targeted run i made before the full
> acceptance suite caught it.

so the property "the session check must not run for a caller that sends no bytes" has **no
deterministic clamp**. that is the same defect class as my eager mistake itself: a property that
holds today for reasons the suite does not pin.

a deterministic clamp needs the verifier **injected**, so a unit test can count its invocations and
assert a byte-less connection yields zero. today `handleKeyrackDaemonConnection` imports
`verifyCallerLoginSession` directly, so the only way to observe the call is a mock — forbidden by
`rule.forbid.unit.remote-boundaries`, and rightly.

**filed for the council, not built here** (per the `a10` line — DI of a prod collaborator is a
design change no reviewer asked for): thread the session verifier through `context`, as
`activity` already is. it is a **clean rework** — one more context field, one call-site edit at
`createKeyrackDaemonServer` — and it would let this cost property be clamped rather than argued.

it is on the record as a known gap rather than an argued-away one, because the honest summary is:
**i cannot presently prove the lazy property holds; i can only show that its violation was caught
once, by luck of scale.**

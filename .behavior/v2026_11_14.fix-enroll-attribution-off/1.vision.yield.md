# 1.vision: no enrolled clone adds a Claude footer or trailer

## .the contract

every write of an actor's `settings.of.repo.json` upserts one key:

```json
"attribution": { "commit": "", "pr": "" }
```

that file sits in the actor's brain dir (the clone's `CLAUDE_CONFIG_DIR`) and reaches the clone at
the `--settings` rank, which outranks the user rank where the grove sits. claude resolves the
attribution text from its merged settings, finds both strings empty, and emits no attribution
reminder. with no reminder, the clone has no instruction to add a footer or a trailer.

one writer owns it: `setActorSettingsRepoWithinLock` in `genBrainCliConfigArtifact.ts`. every
enroll (attended or `--async`) calls it for the actor it spawns, the repo actor too
(`invokeEnroll.ts:628`); `rhx init`'s hook sync calls it for every actor on disk, the repo actor
included, via `setActorSettingsDerived` (`syncHooksForLinkedRoles.ts:233-236`). no new file, no new
spawn flag, no env var.

## .the outcome world

**before.** a human types `claude`, asks for a commit. mid-session, claude injects a
system-reminder: *"End git commit messages with: Co-Authored-By: Claude …"*. `--system-prompt ''`
cannot reach it — it rides an attachment, not the system prompt. the trailer lands (ehmpathy/rhachet#641).
this very route's driver session received that reminder at boot: a live repro.

**after.** the same `claude` boots a clone whose `--settings` file says attribution is empty. claude
skips the reminder entirely (with no remote session url and empty `commit` + `pr`, the attachment
builder returns early). commits and PR bodies carry only what the clone writes.

**the aha.** the fix is not a prompt rule that asks the brain to resist an instruction — it removes
the instruction at its source, in the one config every clone of the actor shares by reference. so a
peer clone, a cron seat, and an everyday `claude` are all fixed by one key, and every next spawn of
an actor inherits it.

## .mental model

- to a friend: *"rhachet turns off claude's 'co-authored by claude' line for every clone it spawns,
  in the clone's own config — your personal claude config stays yours."*
- analogy: a ship's posted orders. the captain (actor config) posts them once; every sailor
  (clone) reads the same board. the harbor master's notice (the grove) is outranked aboard.
- their terms vs ours: *"the claude footer / co-author line"* = our `attribution` key; *"my claude
  config"* = the grove; *"the clone's config"* = the actor's `settings.of.repo.json`.

## .evaluation

| goal (wish `.outcome`) | met by |
|---|---|
| enroll writes attribution-off into the config the actor's CLAUDE_CONFIG_DIR boots | the actor's `settings.of.repo.json`, in that dir, passed via `--settings` |
| an extant actor gets it on next enroll, upsert of that key alone | the writer spreads the derived settings and sets one key; clamp 2 |
| no clone receives the attribution instruction | empty `commit` + `pr` → claude's attachment builder returns before it emits |

what "every other key kept" means, per actor form: the repo actor's file is the source, so every
key in it is kept as-is. any other actor's file is re-derived from that source on every enroll
(extant behavior: hooks narrowed to its roles, clone env dropped, `claudeMdExcludes` set), so a hand
edit to it was never durable. for those, clamp 2 asserts the derived keys are unchanged and only
`attribution` is new — the fix adds no loss the derivation did not already have.

pros: one writer, one key, no new surface; init and enroll both covered; the grove stays untouched.

cons: the repo actor's `settings.of.repo.json` is tracked in git, so the first enroll after upgrade
shows a one-key diff in a consumer repo. acceptable: that file is already rewritten by every hook
sync.

edgecases and their pit of success:

- grove asks for attribution → `--settings` outranks it (case=4)
- a hand edit asks for attribution in the repo actor's file → the next write forces it off (fulcrum F3)
- an older claude that predates the boolean form → we write the object form, which the schema
  itself names as the cross-version shape
- a live pre-fix clone → keeps the reminder it already received (a live re-read of `--settings` by
  claude is unverified); its next spawn is clean

## .open questions & assumptions

- **[answered]** which key, which shape? `attribution: { "commit": "", "pr": "" }` — read from the
  claude 2.1.325 schema and resolver (see `.groundwork`); `includeCoAuthoredBy` is deprecated and
  not written (fulcrum F2)
- **[answered]** which file in CLAUDE_CONFIG_DIR? `settings.of.repo.json` — the `settings.json`
  there is the grove arrow the bound forbids (fulcrum F1)
- **[answered]** does `--settings` reach the reminder? yes — the resolver reads the merged settings,
  and empty `commit` + `pr` make the attachment builder return before it emits
- **[answered]** does init's hook sync drop the key from the repo actor's file? no — it spreads
  `...settings` and replaces only `hooks` (`genBrainHooksAdapterForClaudeCode.ts:176-179`, `229-232`)
- **[answered]** is an invalid `settings.of.repo.json` in scope? no — claude has its own fail-closed
  path for a flag file that fails to parse yet names attribution keys (`lJa`), and the writer only
  ever emits valid json
- **[answered]** does the ban cover a human's own unenrolled session? no, by logic: the wish bounds
  us off `~/.claude/settings.json`, the one place that session's attribution lives
- **[answered]** do org-managed settings set attribution here? no — managed settings would outrank
  `--settings`, and claude would then close the reminder with its managed clause; this session's
  reminder carried the user-chosen clause (*"the user's own instructions … take precedence"*)
- **[research]** which claude version first honored `attribution`? matters only for a host on an
  old claude; the verification stone can probe an older version with `rhx claude.cli.probe`
- **[wisher]** should `sessionUrl: false` ride along (a session link, web / Remote Control sessions
  only)? best-guessed no, fulcrum F4 — a clean one-line add if the commander counts that link as
  attribution
- **[wisher]** may a repo opt its clones back into attribution by a hand edit? best-guessed no —
  the next write forces `commit` and `pr` to `""`, other subkeys kept (fulcrum F3); a clean rework
- no question blocks the drive; both [wisher] items are best-guessed and flagged for the pr review

## .groundwork

### external research

checked against `@anthropic-ai/claude-code@2.1.325` (latest), via `rhx claude.cli.probe` +
`rhx claude.cli.strings`:

- settings schema: `attribution` = `boolean | { commit?, pr?, sessionUrl? }`. *"Empty string hides
  attribution."* the schema's own note: older versions reject the boolean form, so the object form
  is the one to write in a file shared across versions
- `includeCoAuthoredBy`: *"Deprecated: Use attribution instead."* a read of `false` fires
  `tengu_dead_probe_include_coauthored_by`
- the text resolver (`eFr`) reads the merged settings (`bt()`, every source, `flagSettings` =
  `--settings` among them); `attribution.commit` / `.pr`, when set, replace the default trailer
- the reminder builder (`t_`) returns no attachment when there is no remote url and both
  `commit` and `pr` are empty — so no reminder text at all

### internal research

- spawn argv: `src/domain.operations/enroll/asBrainCliSpawnArgs.ts:30-41` —
  `--setting-sources user --settings <configPath> --system-prompt ''`
- the writer: `src/domain.operations/enroll/genBrainCliConfigArtifact.ts:96-151`
  (`setActorSettingsRepoWithinLock`), called from `invokeEnroll.ts:628` and, for init, from
  `syncHooksForLinkedRoles.ts:288` → `setActorSettingsDerived.ts:41`
- the layout: `define.brain-dir-layout-is-one-for-every-actor` — `settings.json` is an arrow to the
  grove (never write it); `settings.of.repo.json` is the one real settings file per actor, at the
  `--settings` rank
- test seam: `genBrainCliConfigArtifact.integration.test.ts` (clamps 1 and 2 land beside it);
  `asBrainCliSpawnArgs.test.ts` already pins which file the spawn names

## .what is awkward

- the wish names *"the settings that the actor's CLAUDE_CONFIG_DIR boots"*. in that dir, the file
  claude calls `settings.json` is an arrow to the human's `~/.claude/settings.json` — the one file
  the wish forbids us to touch. the key therefore lands in `settings.of.repo.json`, the peer real
  file in the same dir. same dir, higher rank, no conflict with the bound — but the word
  `settings.json` in a reader's head points the wrong way (fulcrum F1)
- the repo actor's file is both the hook-sync source and a clone config, so the key also shows up
  in git for a consumer repo
- rhachet dogfoods itself: its own tracked repo-actor `settings.of.repo.json` carries the
  `attribution` key, so rhachet's own clones are clean on merge

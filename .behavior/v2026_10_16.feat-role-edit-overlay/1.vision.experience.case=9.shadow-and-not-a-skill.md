# 1.vision.experience.case=9.shadow-and-not-a-skill — sharp critipath

## .narrative

vlad wants the mechanic's `git.commit.sponsor` skill to print one more line, and he wants
`declapract.upgrade` gone from this repo's clones. he copies the skill to its same path in the mod
dir and changes it, and adds a `not:` for the other:

```yaml
# .agent/repo=.mods/role=mechanic/boot.yml
of: ehmpathy/mechanic@1.39.5

always:
  skills:
    not:
      - skills/declapract.upgrade.sh
```

the shadow sources `output.sh`, `keyrack.operations.sh` and `git.commit.operations.sh` from its own
dir. had it run from `.agent/repo=.mods/role=mechanic/skills/git.commit/`, it would find none of
them. it runs instead from the mechanic's materialized view, where its peers link into
`node_modules` beside it — so it works, and `rhx git.commit.sponsor` finds exactly one file.

a week later he tries to `not` the mechanic's `git.commit.uses` skill too. suppose one of the
mechanic's own hooks invokes it (the sketch below is illustrative; which skills a hook names is the
census question 8 leaves open), so a `not` there would leave that hook to fail at its next event — far from the
mod that broke it. the render refuses at once, names the hook, and offers the shadow instead.

**why critipath**: the wisher put skills in scope. a skill shadow that breaks on its first `source`
line would be a shadow in name only, and a `not` that silently breaks a hook would surface hours
later as a mystery.

**the sharp edges, and how each fails safe**:

| edge | fails safe how |
|---|---|
| a shadow whose peers live beside the original | the merged view puts them beside the shadow too, so `source` finds them ([t1]) |
| a `not` of a skill that is gone from the view | `run --skill` names the mod's `not:` as the cause, never a bare "not found" ([t2]) |
| a `not` of a skill a role hook invokes | refused at render, the hook named, the shadow offered ([t4]) — fast, loud, teaches the fix |

## .bdd `[tn]` timeline

```
given the mechanic ships skills/git.commit/git.commit.sponsor.sh and its peer files
  and skills/declapract.upgrade.sh

  when [t0] vlad copies git.commit.sponsor.sh to the same path under .agent/repo=.mods/role=mechanic/
   and adds `not: [skills/declapract.upgrade.sh]` under always.skills
    then `rhx init` re-materializes .agent/repo=ehmpathy/role=mechanic/skills/
     and skills/git.commit/git.commit.sponsor.sh links into .mods, its peers into node_modules
     and no skills/declapract.upgrade.sh is present

  when [t1] a clone runs `rhx git.commit.sponsor get`
    then the shadow runs, its `source "$SCRIPT_DIR/output.sh"` finds the published peer,
         and its new line prints
     and run --skill meets one match, never two

  when [t2] a clone runs `rhx declapract.upgrade`
    then it is not found, and the message names the mod's `not:` as the cause

  when [t3] vlad shadows output.sh too
    then every mechanic skill in that dir sources his output.sh

  when [t4] vlad adds `skills/git.commit/git.commit.uses.sh` to `not:`, and a mechanic hook invokes it
    then `rhx init` refuses the render for actors with the mechanic, and exits 2
     and stderr names the hook that invokes the skill
     and suggests a shadow in place of the `not`
     and no clone boots with the broken hook
```

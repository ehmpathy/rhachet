## .summary

five deliverables, one release:

1. **the mod dir** — `.agent/repo=.mods/role=<r>/` with one `boot.yml` (the role's schema, plus
   `of: repo/role[@version]`, less `budget`). a new subdomain, `src/domain.operations/mods/`, parses
   it, plans it (shadow · add · not), and refuses each case in the vision's refusal table
2. **the modded view** — a modded role's `briefs/` and `skills/` become real dirs of per-file links
   (F8 b, ruled), so every reader of the role dir sees the modded role with no mod logic of its own.
   a stale view fails loud (F8 clamp, ruled)
3. **the boot merge + visibility** — the mod's sections are read before the role's (F9), each
   modded resource is tagged, the role section carries a notice, and `rhx roles cost` marks the row
   `[~] modded`
4. **the version pester** — the onStop sweep compares `of:`'s `@version` with the installed role
5. **same-slug roles boot apart** (F11, ruled) — the per-slug drop is removed; `.mods` joins `.this`
   as a reserved repo slug, behind one predicate every scanner calls

## .open questions for the commander

each is a call the vision and the verdicts leave open. options are stated fairly; the lean is mine
and is **not** applied above — each tree that depends on one names it.

**Q1 — a role and its mod in different boot.yml modes.** a role's boot.yml is simple (top-level
`briefs`/`skills`) or subject (`always` + `subject.*`); some roles have none.
- (a) the mod must use the role's mode; a mismatch is refused, and a role with no boot.yml takes a
  simple-mode mod
- (b) either mode; a simple-mode side is read as an `always:` section before the merge
- (c) the mod is always subject mode
- **lean (a).** the vision says the mod is "the role's schema", and one mode per merge keeps
  `computeBootPlan`'s first-say-wins rule as is. (b) is friendlier, but a simple spec's absent `say`
  means "say all", which has no faithful `always:` form

**Q2 — where the modded view is written.**
- (a) one orchestrator, `syncRoleModdedViews`, called by each render path (enroll, init, upgrade,
  roles link); `execRoleLink` stays as is
- (b) inside `execRoleLink`, plus a call from enroll (which never links today)
- **lean (a).** enroll must re-materialize and does not link, so (b) needs the second call anyway;
  (a) keeps link and mods apart and leaves an unmodded role's path byte-identical

**Q3 — a stale view at boot: fail, or heal.** the F8 verdict requires it to fail loud "at boot or
re-materialize". the bun `roles boot` path does not write files today.
- (a) boot fails loud and names `rhx init`; every render path re-materializes, so the next render
  heals it
- (b) boot heals it in place (re-materializes), then boots; a heal it cannot do fails loud
- **lean (a).** boot stays read-only and fast, and the verdict is met at both moments. the cost: an
  author who adds a mod file must run a render before the next boot — the onStop sweep names it

**Q4 — release order: a1 vs the nheuron move.** after a1, nheuron boots two learners until its
`.this` learner moves into `repo=.mods` (stone 6).
- (a) one release; the nheuron pr merges right after the rhachet release lands
- (b) the nheuron pr first, then a1 — not possible: the mod dir needs this release, so an older
  rhachet would ignore the moved brief and nheuron would boot no learner mod at all
- (c) ship the mod dir first, a1 in a later release
- **lean (a).** (b) loses the brief for a window. (c) splits a fix the wisher asked to land here
  (S4). the window under (a) is one merge long, in one repo

**Q5 — which hook command forms the `not` refusal reads.** research found five forms on disk:
`./node_modules/.bin/rhx <skill>`, `bash .agent/repo=X/role=Y/…sh`, `rhachet run --repo X --role Y
--init <name>`, `rhachet roles …` (framework), and `node -e "import('<pkg>')…"`.
- (a) the first two — the only forms that name a skill file
- (b) all five, with the `node -e` form treated as "invokes package code, never a skill"
- (c) (a), plus a scan of each skill body for a call to the not'd skill
- **lean (a).** `--init` reaches `inits/`, which a mod cannot touch; `roles …` is the framework;
  `node -e` runs package code that no mod changes. (c) is the indirect case F10 already names as a
  residual, and a body scan is a guess at bash

**Q6 — delete `asRoleRefsFirstSeenPerRole`, or keep it.** after F11 its two callers
(`getAllLinkedRoleRefs`, `asRoleRefsForEnrolledSlugs`) no longer dedupe.
- (a) delete it and its test
- (b) keep it, unused, for a later caller
- **lean (a).** an unused transformer is dead code; the cli ambiguity refusals
  (`findUniqueRoleDir`, `findUniqueSkillExecutable`) never used it

**Q7 — may a mod target a `.this` role?** (`of: .this/architect`)
- (a) refused — a `.this` role is this repo's own; edit it in place
- (b) allowed, same as a package role
- **lean (a).** a mod exists to change a role you did not make; a mod of your own role is a second
  copy of one truth

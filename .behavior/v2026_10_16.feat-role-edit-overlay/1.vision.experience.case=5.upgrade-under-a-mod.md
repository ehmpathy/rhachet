# 1.vision.experience.case=5.upgrade-under-a-mod — sharp critipath (fails safe)

## .narrative

two weeks after vlad's mods, ehmpathy ships mechanic@1.40.0. that release rewrites
`rule.prefer.short-sentences.md` — a new caveat — and removes `rule.prefer.active-simple-tense.md`,
which vlad had also shadowed.

`rhx upgrade` relinks the role and re-materializes the modded view. without a reminder, vlad's
shadow would keep the newer original out of sight, and nobody would re-read it. his mod `boot.yml`
declares `of: ehmpathy/mechanic@1.39.5`, so the next stop fails fast and lists every mod to review — the same
shape as the budget pester.

the removed path needs no special state: the role no longer holds it, so vlad's file there is now a
file at an unheld path that no `say:` names — the same refusal as a typo (case 3), named at the
first stop rather than at the next enroll.

**why critipath**: every mod outlives a release sooner or later. if this broke, mods would rot in
silence — the drift a per-clone copy causes, one grain up.

## .bdd `[tn]` timeline

```
given the mod boot.yml declares `of: ehmpathy/mechanic@1.39.5`
  and shadows of short-sentences and active-simple-tense

  when [t0] `rhx upgrade` lands mechanic@1.40.0, which changes short-sentences and removes active-simple-tense
    then the relink completes, and stdout notes the modded role moved 1.39.5 → 1.40.0; exit 0

  when [t1] the session next stops
    then the onStop sweep exits 2 with the version pester: role, 1.39.5 → 1.40.0, every mod listed
     and it names active-simple-tense as a file the role no longer holds — neither shadow nor addition

  when [t2] vlad folds the new caveat into his short-sentences shadow, deletes the active-simple-tense
       file, and sets `of: ehmpathy/mechanic@1.40.0`
    then the next stop passes, and the memo holds until the mod or the role changes again

  given a mod boot.yml whose `of:` carries no `@version`
  when [t3] the role moves
    then no pester fires; the refusals still do
```

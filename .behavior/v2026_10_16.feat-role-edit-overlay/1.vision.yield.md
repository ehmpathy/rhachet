# 1.vision — mod an extant role in place, via `.agent/repo=.mods/role=<role>/`

## .the outcome world

### before

vlad thinks a mechanic brief is wrong for his repo. to let one clone try his fix he must: edit
`rhachet-roles-ehmpathy`, open a pr, get it reviewed, merge, release, then `rhx upgrade` here. a
day, minimum — before the first clone has read a word of it. so he does not try. or he copies the
brief into `.agent/repo=.this/role=any/briefs/` beside the original, and every clone now boots two
contradictory rules, for every role, with no mark of which one is the experiment.

the one whole-role escape that exists today is `.agent/repo=.this/role=mechanic/` with a `boot.yml`:
it shadows `ehmpathy/mechanic` whole, by name collision (`init/roles/link/getAllLinkedRoleRefs.ts:42`
— native refs first, then `asRoleRefsFirstSeenPerRole`). that is a fork, not a mod — every
upstream fix stops to arrive. and the same collision drops a role silently whenever two package repos
ship one slug: a clone enrolled with `mechanic` boots `acme/mechanic` and never sees
`ehmpathy/mechanic`, while `rhx roles boot --role mechanic` refuses the name as ambiguous.

### after

```
.agent/repo=.mods/role=mechanic/
  boot.yml                                                    # the role's boot.yml shape, + of
  briefs/practices/lang.prose/rule.prefer.short-sentences.md  # SHADOW — the role holds this path
  briefs/rule.require.commit-scope-from-diff.md               # ADD — said by the mod's boot.yml
  skills/git.commit/git.commit.sponsor.sh                     # SHADOW — a skill, same path
```

```yaml
# .agent/repo=.mods/role=mechanic/boot.yml
of: ehmpathy/mechanic@1.39.5   # the role, and (optional) the version these mods were made against

always:
  briefs:
    say:
      - briefs/rule.require.commit-scope-from-diff.md
    not:
      - briefs/practices/lang.tones/rule.forbid.buzzwords.md
  skills:
    not:
      - skills/declapract.upgrade.sh
```

vlad copies one brief and one skill to their same paths and changes them, adds one brief, `not`s a
brief and a skill, and enrolls a clone. it boots the mechanic as published — except his shadows in
their original slots, his addition where his `boot.yml` says it, no buzzwords rule and no
`declapract.upgrade`; each change tagged as a mod. a week later the change
earned its keep; he opens a pr upstream with the same files. when he `rhx upgrade`s to the release,
the stop hook says the mechanic moved from `1.39.5` and asks him to review his mods. he sees his
shadow now equals upstream, deletes it, and bumps the `@1.39.5` in `of:`.

### the aha

**the release roundtrip moves from before the experiment to after it — and only for the mods that
earned it.** a repo tunes a role live with the one file shape it already knows — a `boot.yml` — plus
the files it wants changed, without a fork of the role and without a silent divergence from it.

## .the contract

### the declaration — the role's own `boot.yml`, plus one key

the mod dir holds one `boot.yml`, in **exactly the schema of a role's `boot.yml`** — the
`always` and `subject.<slug>` sections, each with `briefs` / `skills` and their `say` / `ref` /
`not` globs. one key is added, and one is withheld:

| key | in a role's boot.yml | in a mod's boot.yml |
|---|---|---|
| `of` | absent | **required** — `repo/role[@version]`, the role this mod is over and, optionally, the version the mods were made against (`of: ehmpathy/mechanic@1.39.5`). the `@version` drives the onStop pester |
| `budget` | allowed | **refused** — the budget is the role's; it is checked over the modded payload |
| `always` / `subject.<slug>` · `say` / `ref` / `not` | as today | as today |

no content hashes, no per-file records. the files are the payload; the `boot.yml` is the plan.

### the three operations — decided by the file and the plan

| op | how | effect |
|---|---|---|
| **shadow** | a file at a path the role holds | replaces the original, content and all. it keeps the original's slot unless the mod's `boot.yml` names it |
| **add** | a file at a path the role does not hold, **and** said or ref'd by the mod's `boot.yml` | joins the role in the slot the mod names |
| **not** | a glob in the mod's `not:` | removes each original it matches from the role — never booted, never run |

- the key is the **path relative to the role dir** (`briefs/practices/lang.prose/x.md`) — the same
  key the role's own `boot.yml` globs use (`cwd = role dir`). never the bare filename: two briefs in
  one role may share a basename
- **the mod's sections are read before the role's.** boot semantics are "first section to say a
  resource wins" (`computeBootPlan.ts`), so the merge needs no new rule: a mod's `ref:` of a brief
  the role says demotes it, a mod's `say:` of a brief the role refs promotes it, and a mod's
  `not:` drops it. the mod's `boot.yml` reads as a diff because it is consulted first, never because
  its schema differs
- a shadow of `x.md` replaces both `x.md` and its `x.md.min` peer. the boot prefers `.min` for
  content (`getRoleBriefRefs`), so a shadow that left the published `.min` live would render the
  original — the most silent failure available. a mod may ship its own `.min`; an orphan `.min`
  throws, as today

### what is refused — loud, never a guess

| the file or glob | why it is refused | the fix it names |
|---|---|---|
| a file at a path the role does not hold, which no mod `say:` / `ref:` glob names | a typo would else become an addition (case 3) | the nearest held path ("did you mean"), or the `say:` line that would add it |
| a `not:` glob that matches no original | a typo would else remove naught, in silence | the nearest held path |
| an `of:` that names no linked role, or a bare slug where two repos ship it | the mod would land on no role, or the wrong one (case 6) | the linked `repo/role` forms |
| a `not:` of a skill that one of the role's own hooks invokes | the hook would fail at its next event, far from the mod that broke it (case 9) | the hook that names it, and the choice: shadow the skill rather than `not` it |
| a `budget:` key | the budget is the role's | delete the key |
| a readme, an `inits/` file, a `keyrack.yml` | out of scope (see below) | a `.this` role or an upstream pr |

a glob is an explicit rule: `say: [briefs/local/**/*.md]` adds every file under it, by intent. that is
the wish's own escape — *"or is declared an extension by an explicit rule"*.

**a refusal is scoped to the modded role.** it fails the render of an actor that carries that role,
and only that actor. an enroll of a clone without the mechanic is never blocked by a bad mechanic
mod; `rhx init` and `rhx upgrade`, which render every actor, report each refused actor and exit 2
once all others are rendered.

### scope

| artifact | v1 | why |
|---|---|---|
| briefs | ✅ shadow · add · not | the wish's first scope |
| skills | ✅ shadow · add · not | the wisher's call. a skill runs from the merged view (below), so its peer files are still found |
| the mod's `boot.yml` | ✅ the plan | placement, additions, removals — the role's schema |
| readme | ⛔ refused loud | no behavior changes |
| inits / hooks | ⛔ refused loud | hooks come from the role package (`getLinkedRolesWithHooks.ts`), not `.agent/`, and write `settings.of.repo.json`; a mod there changes actor config |
| `keyrack.yml` | ⛔ refused loud | a credential manifest is a security surface |

### same-slug roles boot apart — the drop this wish removes

a mod names its role by `repo/role`, so the boot must too. today it does not: a `boot.md` keeps
the first ref per slug and drops the rest (`asRoleRefsFirstSeenPerRole.ts:7-13`), with no notice. this
wish removes the drop (S4, requirement 10, case 10):

- **each `repo/role` is its own role** in a `boot.md` — its own section, its own tags, its own hooks
  (a hook author is already `repo=X/role=Y`, `asRoleSlugOfHookAuthor.ts`)
- **a bare slug carries every repo's role of that slug.** `--roles mechanic` boots `acme/mechanic` and
  `ehmpathy/mechanic`; `--roles ehmpathy/mechanic` pins one
- **an actor's identity stays put.** the enrollment hash keys roles as they were named
  (`genEnrollmentHash.ts:21-29`); a bare slug hashes as before, so no extant actor dir moves. only a
  pinned `repo/role` is a new identity
- **a `.this/role=<x>` boots apart too** — it is a role of this repo, not an override. the targeted
  override is the mod dir (F11, the one dirty call here)
- **the cli answer stands.** `roles boot --role mechanic` and a skill name two such roles both ship stay
  refused ambiguities that ask for `--repo` (`findUniqueRoleDir.ts:78-85`,
  `findUniqueSkillExecutable.ts:57-66`); the boot and the cli now agree that two roles exist

### the merged view — why a skill shadow needs one

a skill finds its peers by its own location: `git.commit.sponsor.sh` sets
`SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` and sources `output.sh`,
`keyrack.operations.sh` and `git.commit.operations.sh` from it (lines 29–37). a shadow run from
`.agent/repo=.mods/role=mechanic/skills/git.commit/` would find none of them.

so a modded role is **materialized**: its `briefs/` and `skills/` in
`.agent/repo=ehmpathy/role=mechanic/` become real dirs of per-file symlinks — each original links into
`node_modules` as today, each shadow and addition links into `.mods`, each `not` is simply absent.
then:

- a shadowed skill runs from the role's own dir, so `SCRIPT_DIR` holds its peers — and a shadow of a
  peer file (`output.sh`) is honored too
- `run --skill` sees one file per name, so its ambiguity refusal (`findUniqueSkillExecutable.ts:63`)
  never meets the mod as a second candidate
- every reader that already reads the role dir — the bun `roles boot`, the brain-dir `boot.md`, the
  skill scan — sees the modded role with no mod logic of its own. a symlink whose target sits under
  `.agent/repo=.mods/` is how a render knows to tag it
- a content change to a mod file is live at once (the link points at it). a new, removed, or
  renamed mod file needs a re-materialize, which every render path runs, and the onStop check
  catches a view that lags the mod dir

an unmodded role keeps its per-dir symlinks, exactly as today.

### the version pester — onStop, like the budget

when `of:` carries an `@version` and the installed role's version differs (read from the role package's
own `package.json`, which the role dir's links point into), the onStop sweep fails fast:

```
🧢 roles cost --all --when hook.onStop
   └─ ✋ ConstraintError: the modded role moved
      ├─ role    = ehmpathy/mechanic
      ├─ mods   = 1.39.5   (declared in .agent/repo=.mods/role=mechanic/boot.yml)
      ├─ now     = 1.40.0
      ├─ review each mod against the new release
      │  ├─ shadow  briefs/practices/lang.prose/rule.prefer.short-sentences.md
      │  ├─ shadow  skills/git.commit/git.commit.sponsor.sh
      │  ├─ add     briefs/rule.require.commit-scope-from-diff.md
      │  ├─ not     briefs/practices/lang.tones/rule.forbid.buzzwords.md
      │  └─ not     skills/declapract.upgrade.sh
      └─ then set of: ehmpathy/mechanic@1.40.0
```

- it rides the same sweep as the budget pester: `rhx roles cost --all --when hook.onStop`
  (`getOneRepoThisBootFingerprint.ts` — this repo's own specs; a mod's `boot.yml` is a real file,
  never a foreign symlink, so it is this repo's own), memoized by fingerprint
  (`getOneRepoThisBootBudgetMemoPath.ts`) so it costs naught on a stop where naught changed
- with no hashes it cannot say *which* shadow's original moved — only that the role did. that is the
  point: a release is the one moment to re-read every mod, and the list is short by nature
- no `@version` in `of:` → no pester. the mods still apply; the author opted out of the reminder
- `rhx upgrade` prints the same notice when it moves a modded role, and exits 0 — the stop hook is
  the gate, not the upgrade

the onStop sweep also re-checks the refusals above (a role path the release removed turns a shadow
into an undeclared file; a `not:` may now match naught), so an upgrade that breaks a mod is caught
at the first stop, never at the next enroll.

### visibility

| reader | sees |
|---|---|
| clone | a notice atop the role section of `boot.md` (*"role ehmpathy/mechanic@1.39.5 is modded in this repo — 2 shadow, 1 add, 2 not"*), and per-resource tags: `mod="shadow"`, `mod="add"`. a `not` leaves no resource, so the notice lists it |
| reviewer | the mod dir is real files and one `boot.yml`, so the pr diff shows every mod. a shadow is read against upstream with a plain `diff` of the two paths |
| human | `rhx roles cost` marks a modded role `[~] modded · 2 shadow · 1 add · 2 not`, and the onStop pester names drift |

### `.mods` is a reserved repo literal

`repo=.mods` is not a role supplier. every scanner that skips `.this` today must also skip `.mods`
as a source of roles — else `discoverLinkedRoles` tries to upgrade `rhachet-roles-.mods` and the
skill, init, keyrack and cost scans each meet a `role=mechanic` that is not a role. one predicate (a
reserved-slug check) serves every scanner, so the next scanner cannot forget it.

## .mental model

**to a friend**: *"it's a patch layer over a role. put a file at the same path and it replaces the
role's; put a new one and say it in the mod's boot.yml, and it's added; `not` it and it's gone. when
the role ships a new version, the stop hook nags you to re-read your patches."*

| analogy | fits | breaks |
|---|---|---|
| `patch-package` | a local change to a dependency, kept in the repo, promoted upstream later | patch-package stores diffs; a mod stores whole files, so it reads plainly and still applies after upstream moves |
| overlayfs / docker layers | an upper layer, same path wins, lower layer untouched; a whiteout deletes | overlayfs adds any new file silently; here an addition must be said |
| css cascade | the earlier-read sheet wins here | the cascade is silent; here every win is tagged |

| we say | a human may say | why ours |
|---|---|---|
| **mod** (the dir, and its files) · **modded** (the role) | edit, patch, override, overlay | the wisher's call (S6). a mod is a layer over a role you did not make, and upstream still moves under it — the model a game mod already teaches. "edit" reads as a change to the original, which a mod never makes |
| **shadow** | overwrite, replace | the wisher's word: a same-path entry hides the original — the grain the old `.this` whole-role shadow worked at, one level down, and the one shadow left once roles boot apart |
| **add** / addition | extend, append | the wisher's word |
| **not** | remove, whiteout | the role `boot.yml`'s own key, so one word serves both files |

## .evaluation

**goals**

| wish asks | answered by |
|---|---|
| modify a role without a publish | the mod dir, materialized into the role's view |
| match rule; a typo must not become an extension | path relative to the role dir; an addition must be said or matched by an explicit glob (case 3) |
| scope | briefs and skills: shadow, add, not. readme, inits, keyrack refused loud |
| boot say/ref + budget | the mod's `boot.yml` is the role's schema, read first; the budget is the role's, over the modded payload |
| shared role names | `of: repo/role`, required (case 6) |
| visibility | boot notice + tags, `roles cost` marker, the pr diff |
| lifecycle | `of: repo/role@version` + the onStop pester at each release; drop a mod by deletion of its file or line |
| same-slug roles (S4) | each `repo/role` boots apart; a bare slug carries every repo's role; a bare-slug actor's hash is unchanged (case 10) |
| done-when: acceptance test | cases 1 + 2 + an untouched brief in one fixture repo; case 3 refusal; case 9 skill shadow; case 10 two same-slug roles both boot; boot + `roles cost` snapshots |

**pros**
- an experiment costs one file, not a release — and the file shape is one the author already knows
- the modded role keeps every upstream change it does not touch — unlike the old `.this` whole-role shadow
- no role is dropped from a clone's boot because another repo shipped its slug
- no new state for a human to keep in sync: no hashes, no records, no mod verbs
- every reader of the role dir sees the modded role for free, via the merged view

**cons**
- the version pester is coarse: it fires for every release, even one that touched no modded path.
  the wisher chose that for simplicity; the list it prints is the review
- a new mod file is not live until a render re-materializes the view. every render path does it, and
  the onStop check catches a lag
- every scanner must learn `.mods`; a forgotten one is a defect, which is why it is one predicate

**pit of success**
- copy a file to its same path → a shadow, no declaration to forget
- a new file with no `say:` → refused with "did you mean", never a silent addition
- a release under a mod → the next stop names every mod to re-read

## .open questions & assumptions

assumptions
- a mod is a **repo** fact, so every actor in the repo that carries the role sees it. it derives
  from the roleset + this repo, never from a run, so it never lives under `clones/`
  (`rule.forbid.per-clone-config`)
- the mod dir is committed (no `.gitignore`), unlike `repo=<slug>/` which ignores its symlinks —
  settled by the wisher (S3)
- a shadow renders the mod's full `.md`, so the role's token cost rises by the gap between the
  published `.min` and the mod's `.md`, unless the mod ships its own `.min`. `roles cost` shows it
- a live clone keeps the boot it read at session start; a re-enroll picks up the mod

## .what is awkward

- **one file name, two readers** — the mod's `boot.yml` shares its name and schema with a role's,
  plus `of`. that is the point (the author knows the shape), but a role's own `boot.yml` parser must
  refuse `of`, and the mod's must refuse `budget`
- **the merged view is a new layout for a modded role** — per-file links where every other role has
  per-dir links. it is what makes skills work and every reader mod-blind, at the cost of a
  re-materialize on each change of the mod's file set
- **the pester is coarse** — every release asks for a review of every mod. simple by choice
- **the `.md` / `.md.min` pair** — the author mods `.md`; the published `.min` must vanish. correct,
  but a shadow silently drops a hand-tuned minification. the boot notice should say so
- **a `.this` role that used to replace a published role now boots beside it** (F11). a repo that
  relied on `.this/role=mechanic` to hide `ehmpathy/mechanic` sees two mechanics after this wish. the
  repair is to move the divergence into `.agent/repo=.mods/role=mechanic/`, or unlink the package
  role — the release notes owe that line
- **a clone with two same-slug roles carries more briefs** — the boot budget of each still applies,
  and `rhx roles cost` shows both rows
- **one mod dir per slug** — `role=mechanic` cannot say which of two mechanics it mods by name, so
  `of:` carries it, and two same-slug roles cannot both be modded in v1 (case 6 `[t3]`)

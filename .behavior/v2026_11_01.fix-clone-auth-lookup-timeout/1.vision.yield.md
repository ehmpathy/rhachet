# 1.vision — the peer-cred lookup waits 60s, and the auth gate bound sits above it

closes ehmpathy/rhachet#678.

## the outcome world

### before

a human runs a clone graph on a busy box: three brains, a test tier, a build. they dispatch a peer:

```
$ rhx clone say @:reviewer --what 'review the diff'
💥 MalfunctionError: the caller is not the same unix user as the clone — a clone socket accepts
   only its own user; run the say as the user that enrolled the clone
```

(the reject copy is `CLONE_OPERATIONAL_REJECT_COPY['auth-denied']`,
`computeCloneOperationalRejectClass.ts:65-66`; `auth-denied` is classed server-fault, so exit 1.
the frame around it is a sketch.)

they ARE that user. the clone's terminal shows the real cause, two hops away:

```
clone socket auth error: Command failed: ss -xp | grep -E "228577435" || true
clone socket ack dropped — peer no longer writable: rejected (auth-denied)
```

`ss -xp` walks every process's fds; on a loaded box it ran past its 5s exec bound. the exec
rejected as killed, the gate failed closed, and a slow lookup read as a deny — before the gate's
own 8s bound could say `auth-gate-timeout`.

### after

the same say, on the same busy box:

```
$ rhx clone say @:reviewer --what 'review the diff'
😶🎙️ said to @:reviewer
   └─ 🟡 screen probe unanswered (a loaded box) — verified by transcript; no action needed
```

the message landed. the say cli's own screen probes (a 5s baseline, then 1s observe probes) gave up
on the slow gate; `getCloneInputState` names that reply timeout `CloneProbeReplyTimeoutError`, and
`getCloneInputStateOrBlind` folds it into `probe-unanswered`, so the say was verified by transcript
alone and the 🟡 leaf names the true cause, the loaded box. on a box where `ss` settles under 5s the
line is the bare `😶🎙️ said to @:reviewer`. the live tree is pinned in
`blackbox/cli/__snapshots__/clone.say.slowbox.realbrain.acceptance.test.ts.snap`.

it took a few seconds longer while `ss` crawled. no false deny. and a caller that gives up before
the gate settles is never typed: the server drops the frames of a peer that hung up, so a retry
after a wedge cannot land the message twice.

| | before | after |
|---|---|---|
| peer-cred lookup exec bound | 5s | **60s** |
| auth gate bound | 8s (above the lookup — but a lookup rejected as killed before 8s read as deny) | **65s** — lookup bound + 5s slack, derived from it |
| same-user say, lookup takes 9s | `rejected (auth-denied)` | `said to @:reviewer` (+ the `screen probe unanswered (a loaded box)` note) |
| other-user say | `accepted` — the gate read the reader's own pid, so it passed any caller (S3/F8) | `rejected (auth-denied)` — the gate reads the peer's pid |

### the aha

a deny is a claim about the caller. a slow `ss` is a claim about the box. the old bounds let the
box's claim speak as the caller's. with the lookup given a minute and the gate set above it, a slow
box costs time, never a false deny.

## the contract

no new flag and no new wire reply reason. the two bounds change, and one derives from the other:

```ts
// src/infra/socket/constants.ts
export const SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS = 60_000;

// src/domain.operations/clone/socket/constants.ts
export const CLONE_AUTH_GATE_TIMEOUT_MS = SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS + 5_000;
```

the derivation is the invariant: the gate bound can never again drift below the lookup bound.

beyond the two bounds, the change ships:

- **the peer pid is read from the peer's line** (seed S3, fulcrum F8) — the `ss` line whose peer
  column holds our inode, read from the right (`asSocketPeerPidFromSsPeerLine.ts`). the old read
  took our own line and returned the reader's pid, so the same-user gate compared the reader to
  itself and passed every caller. so the gate now fails closed for real: another user's process,
  and a same-user caller `ss` cannot attribute (F13), get `auth-denied`. the keyrack daemon's
  reader is #686
- **`ss` runs with no shell** (F7) — `execFile('ss', ['-xp'])` with a 64 MiB buffer, so
  the bound's kill lands on `ss`, and an absent, killed, or failed `ss` rejects by name rather than
  reads as an invisible peer
- **a caller that hung up before the gate settled is not typed** — its frames are dropped and the
  drop traced, so the retry its wedge report invites lands the message once (case=3)
- **a loaded box reads as a loaded box** — a probe whose reply outlasts its window degrades to a
  new client-side reason, `probe-unanswered`, whose copy says wait, never re-enroll; and an
  `unreadable` say (always post-write) never hints "retry". the success tree on a loaded box gains
  `🟡 screen probe unanswered (a loaded box) — verified by transcript; no action needed`
  (`blackbox/cli/clone.say.slowbox.realbrain.acceptance.test.ts`)

## the clamp

a fake `ss` on `PATH` that sleeps 9s, then execs the real `ss -xp`. 9s sits above both old bounds
(5s kill, 8s gate) and below the say's 30s window. a new case in
`genCloneSocketServer.integration.test.ts`: the extant `genServerWithCapture` harness stands up a
real server in-process, with the real gate wired (`isCallerSameUser` is not injected), and
`sayClone` dispatches to it from the same uid:

- before: `sayClone` rejects with a non-pass reason — `auth-denied`, or `auth-gate-timeout` if the
  kill does not settle the pipeline before the fake `ss` exits (see F7). the red run records which
- after: `sayClone` resolves delivered, the capture sink holds `<message>\r`, and the trace holds
  no `clone socket auth error` line — green

this is the outcome the wish names (a same-user say on a loaded box is accepted), at the grain
that holds it: the real accept path, the real gate, the real exec, the real `ss`.

the wish names a range (> 5s and < 60s); one 9s point proves the lower end against both old
bounds. the upper end is pinned cheaply rather than with a 59s test: a unit assertion that
`SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS === 60_000` and that
`CLONE_AUTH_GATE_TIMEOUT_MS > SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS`. the integration point proves the
exec honors the constant; the unit proves the constant's value and order.

## mental model

how a human would say it: *"clone say used to tell me I was the wrong user when the box was just
busy. now it waits for the box."*

analogy: a bouncer who checks id against a slow database. before, if the lookup took over 5
seconds, he turned you away as underage. now he waits up to a minute, and his own patience is set
longer than the database's, so the database always answers (or times out) before he decides.

| human term | our term |
|---|---|
| "it said I'm the wrong user" | `rejected (auth-denied)` |
| "the box is busy" | `ss -xp` exceeds the lookup exec bound |
| "it gave up" | `auth-gate-timeout` |

## evaluation

- **goals**: all three outcomes of the wish land — lookup 60s, gate above it, same-user say on a
  loaded box accepted (up to the client's wedge window; see awkward)
- **pros**: the derivation stops a repeat inversion; the gate's fail-closed promise now holds in
  fact (it read its own pid before); the clamp drives the real `ss` path, not a mock, at the server
  and through the cli
- **cons**: a truly hung host now holds a connection open ~65s server-side, not 8s. the gate timer
  is `unref`'d and per-connection, so it never pins the daemon, but a slow box with many callers
  holds more sockets open longer
- **cons — abandoned scans pile up longer.** each `clone say` cli call opens probe connections
  beside its dispatch: a baseline probe (5s reply), then an observe probe every ~1.25s (1s reply +
  250ms poll — `getCloneSayObservation.ts:64-147`, `constants.ts:198,211`) until the transcript
  rises. each connection's gate runs its own `ss -xp`, and that scan outlives the probe that asked
  for it. the old 5s bound killed only the shell and left `ss` to run (F7); now the kill lands on
  `ss` itself, but at 60s, so a scan runs until `ss` finishes, up to 60s. on a box where `ss` takes T seconds, about T / 1.25 scans run at once per
  observed say — ~7 at T = 9s, ~32 at T = 40s. a slow box gets slower from its own lookups. accepted for this
  wish: the observe loop exits once the transcript rises (usually a few cycles), and every scan is
  bounded. the cure — kill a gate's in-flight `ss` when its peer hangs up — is fulcrum F6, caught
  as a dream
- **edgecases**
  - other uid → still `auth-denied` (case 2)
  - lookup throws fast (no fd, not a socket) → still deny, fail closed
  - lookup exceeds 60s → `ss` killed by name, deny, before the 65s gate fires — as the wish asks.
    measured: `getSocketPeerCred.integration.test.ts [case2]` settles near its bound with
    `metadata.killed = true`
  - lookup promise never settles at all → gate fires at 65s, `auth-gate-timeout`
  - lookup between ~30s and 60s → the client's 30s wedge fires first (case 3)

## open questions & assumptions

- **[answered]** how far above the lookup bound must the gate bound sit? by logic: any margin that
  covers the post-kill `/proc` stat and settle; 5s (65s total), derived from the lookup constant so
  the order holds by construction. clean rework if the wisher prefers another margin (F1)
- **[answered]** does the keyrack daemon's `getSocketPeerPid` 5s bound change too? from the wish
  text: no — it names the clone socket's peer-cred lookup only. caught as a dream (F2)
- **[answered]** does CI have `ss`, so the clamp can run? from extant code: yes — the extant
  `genCloneSocketServer.integration.test.ts` drives real says through the real gate, which runs
  the real `ss`, and passes in CI today
- **[answered]** at what grain does the clamp sit? by logic + extant code: at the server, via
  `sayClone` → `genCloneSocketServer` in-process (`genCloneSocketServer.integration.test.ts:36-80`
  wires the real gate). that grain holds the wish's outcome itself; a gate-only test would prove
  the parts and leave the wire unproven. the value and order of the two constants are pinned by a
  unit test beside it
- **[wisher]** the client's 30s wedge floor stays, so a lookup of 30s–60s reads as a wedge, not a
  delivery. does "a same-user say on a loaded box is accepted" need to hold past 30s, in this PR?
  default if unanswered: no; caught as a dream (F3)
- **[answered — F7]** the lookup bound is real: `ss -xp` runs with no shell (`execFile`), its inode
  filter runs in node, and its buffer holds a full table (64 MiB), so node's timeout signals `ss`
  itself and the lookup settles at its bound, never at the gate above it
  (`getSocketPeerCred.integration.test.ts [case2]`). a shell pipeline would hand the kill to `sh`
  and leave `ss` to run on
- **[wisher]** an abandoned probe's `ss` scan runs to completion rather than be killed on hangup,
  so on a slow box scans pile up (see cons). is that acceptable for this PR, or should the abort
  ride along? default if unanswered: defer; caught as a dream (F6)
- **[answered]** adopt the issue's other cures (kernel-perm fallback, a distinct
  `auth-lookup-fault` reason, an `ss`-free pid read)? from the wish text: no — it scopes to the two
  bounds. caught as a dream (F4)

## what is awkward?

- 🔴 **the client gives up before the server does.** a short `say` waits 30s for its first ack; the
  gate now waits up to 65s. a lookup between ~30s and 60s passes server-side, then finds the caller
  gone — the client reports a wedge with `acksSeen: []`. the wish's outcome holds for every lookup
  the client will wait for; past that, the failure is a wedge, honestly reported, not a false deny.
  better than before, not perfect. caught as a dream (F3)
- a lookup kill at 60s still reads as `auth-denied`, the same mislabel, now past a far higher bar. the issue's
  `auth-lookup-fault` cure would fix the label; out of this wish's scope (F4)
- 60s is a bound picked by the wisher, not measured. it is a guard against a hang, not a latency
  target, so the precise value matters less than the order of the two bounds

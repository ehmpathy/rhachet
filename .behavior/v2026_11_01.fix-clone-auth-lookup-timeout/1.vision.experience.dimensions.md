# 1.vision.experience.dimensions

the server gate runs once per connection on its first frame (`genCloneSocketServer.ts:343-349`),
for every verb. so the experience space is cut by what the server sees per connection.

## .dimensions

| dimension | positions |
|---|---|
| **caller uid** | `same` (owns the clone) · `same, unattributable` (owns the clone, yet `ss` shows no process tuple for it: another pid namespace, or non-dumpable — the gate sees it as `other`, F13) · `other` |
| **connection kind** | `say-dispatch` (window ≥ 30s) · `probe-baseline` (the say cli's first probe, 5s reply — `invokeCloneSay.ts:209`) · `probe-observe` (the say cli's poll probes, 1s reply — `getCloneSayObservation.ts:111`, `CLONE_SAY_PROBE_REPLY_MS`) · `get` (a direct `clone get`, 5s reply — `CLONE_PROBE_REPLY_DEFAULT_MS`). both probe kinds degrade a fault to blind, and so does the surface read `get --what buffer|queue` (through `getCloneInputStateOrBlind`); its renders are itemized per reply in `case=_` `.get --what buffer|queue` |
| **lookup outcome** | `fast` (< 5s) · `slow-short` (5s–30s) · `slow-long` (30s–60s) · `killed` (> 60s, `ss` killed at the bound by name — F7 resolved by `execFile`) · `hung` (promise never settles) · `throws-fast` (no fd, not a socket, no pid in `ss`, `ss` absent or failed) · `overflow` (the `ss -xp` table outgrows the 64 MiB read buffer, ~400k sockets — named apart, since its cure is a larger buffer, never a longer wait; `getSocketPeerCred [case6]`) |
| **concurrency** | `solo` (this connection's scan is the only one in flight) · `concurrent` (other gates' scans in flight — the say's own probes, or other callers' says and gets) |

## .why each axis is orthogonal to the rest

- **caller uid ⟂ the rest.** uid is a fact of the peer process; it does not choose the verb, the
  scan's duration, or how many other scans run. any uid can open any connection kind, on a quiet
  or a busy box. it decides only WHICH verdict a settled lookup yields (pass vs deny)
- **connection kind ⟂ lookup outcome.** the kind fixes the CLIENT's window; the lookup's duration
  is a fact of the host (`ss` cost under load). a 9s scan is a 9s scan whether a probe or a say
  asked for it. what the kind changes is where the client gives up — so the two multiply: the
  product cell `probe-baseline × slow-short` exists and has its own verdict (the client gave up at
  5s, the scan ran on). the client windows are bounds on the kind axis, not a fourth axis; they
  explain why several cells share a verdict, which the inventory groups with its why
- **lookup outcome ⟂ uid and kind**, as above. `killed` and `hung` are distinct positions: the
  lookup runs `ss` with no shell, so its bound kills `ss` itself and settles the promise at 60s
  (`getSocketPeerCred.integration.test.ts [case2]`), well before the 65s gate
- **concurrency ⟂ uid and kind.** how many scans run is a fact of the host and of other callers,
  not of this caller
- **concurrency ⟂ lookup outcome — a shift of odds, not a function.** concurrency raises the odds a
  scan runs slow; it does not fix where it lands. both axes stay free to land in every cell: a
  `solo` scan can be `slow-long` on a box loaded by a build or a test tier (the issue's traces are
  of this kind), and a `concurrent` scan can be `fast` on a box with few fds. so every
  `concurrency × lookup` pair is reachable. what concurrency never does is change the verdict a
  given lookup duration earns — so the inventory walks it as scenes that name which lookup cell
  each lands in, rather than a second copy of every row

## .the actor axis, folded

actors: a human at `rhx clone say` / `rhx clone get`, or a machine (cron, peer clone, comms
webhook) at the same commands. the actor folds: the gate never sees who typed the command, only
the connection, and the machine and the human get the same exit code, the same classed error,
and the same success line. a machine reads the exit code and the json envelope where a human reads
the tree; both channels carry the same verdict. no cell differs by actor, so actor is not
multiplied in.

## .the walked product

3 × 4 × 7 × 2 = 168 cells (uid × kind × lookup × concurrency). many collapse, each group with its why, in
`1.vision.experience.case=_.md`:

- `uid = other`: every cell is a non-pass — forbidden by nurture (the gate must reject)
- the probe kinds and `get`: every lookup past the kind's own reply bound (1s for
  `probe-observe`, 5s for the others) ends at that bound, before and after alike
- `concurrent`: shifts the odds of where a cell lands on the lookup axis; it adds no verdict of its own

# blocker.1: auth-denied snapshots carve out the metadata instead of masking the volatile path

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.verification/rule.require.contract-snapshot-exhaustiveness.md

**locations**:
- src/domain.operations/clone/socket/genCloneSocketServer.integration.test.ts:1488
- src/domain.operations/clone/socket/genCloneSocketServer.integration.test.ts:1549

the two new snapshots in [case20] and [case21] snapshot only the first paragraph of the error via `outcome.error.message.split('\n\n')[0]`, and the inline comment states the reason: `the metadata below it holds a per-run socket path`.

this is precisely the carve-out the rule forbids. the rule states: non-deterministic outputs are MASKED, then snapped live — never carved out. the volatile bytes here (a per-run socket path, and in the CLI render a per-run debugLog / serial) are a maskable field, not a reason to drop the whole block.

the cost of the carve-out is a real coverage blind spot: the metadata block is user-faced contract output (the JSON a machine consumer reads under `--output json`, and the error frame a human sees). by discarding it, the snapshot proves nothing about `metadata.reason: 'auth-denied'`, `verdict`, `delivered`, or the key order — the very fields this PR's deny path exists to guarantee. the sibling `clone.say.slowbox` acceptance snapshot does it correctly: it passes the full output through `asSnapshotSafe` (masking `__SERIAL__`, tmpdir, `__DATE__`) and snaps live.

fix: run the full `outcome.error.message` through `asSnapshotSafe` (or an equivalent mask of the socket path) and snapshot the whole message, so the deterministic structure around the volatile path stays under snapshot.

**snippet**:
```ts
          // the copy alone: the metadata below it holds a per-run socket path
          expect(outcome.error.message.split('\n\n')[0]).toMatchSnapshot();
```

# nitpick.1: concurrency axis is admitted non-orthogonal to lookup outcome

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.vision/rule.require.dimensional-decomposition.md

**locations**:
- .behavior/v2026_11_01.fix-clone-auth-lookup-timeout/1.vision.experience.dimensions.md:29
- .behavior/v2026_11_01.fix-clone-auth-lookup-timeout/1.vision.experience.dimensions.md:13

The rule requires the axes be orthogonal — 'a value on one does not imply a value on another; if two correlate, they are one axis'. The driver's own orthogonality note for concurrency concedes the opposite: it says concurrency 'does not add a new verdict; it moves a connection ALONG the lookup axis (a scan that would be `fast` solo turns `slow-short` under contention)'. That is a functional correlation between `concurrency` and `lookup outcome` — the very entanglement the rule's orthogonality test warns against. `concurrent` does not strictly determine one lookup value, but the axis is only meaningful because it perturbs lookup outcome; as multiplied (2×3×6×2 = 72) it double-counts a factor already carried by `lookup outcome`. It does not hide an experience (the inventory maps concurrent cells), so this is not a blocker — but the axis is not clean. Resolve it: either fold concurrency in as the box-load cause from which lookup-outcome is a function (the resource-state framing the rule prefers), or restate the orthogonality in terms the rule accepts (a distribution shift that still leaves both axes free to land in every cell) rather than 'moves a connection along the lookup axis'.

**snippet**:
```md
- **concurrency ⟂ uid and kind.** how many scans run is a fact of the host and of other callers,
  not of this caller. concurrency does not add a new verdict; it moves a connection ALONG the
  lookup axis (a scan that would be `fast` solo turns `slow-short` under contention). so its cells
  map onto lookup cells; the inventory walks that map
```

# nitpick.3: the `fast` (<5s) lookup position is not homogeneous for `probe-in-say` (observe probes have a 1s reply)

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.vision/rule.require.dimensional-decomposition.md

**locations**:
- .behavior/v2026_11_01.fix-clone-auth-lookup-timeout/1.vision.experience.case=_.md:30
- .behavior/v2026_11_01.fix-clone-auth-lookup-timeout/1.vision.experience.dimensions.md:11
- .behavior/v2026_11_01.fix-clone-auth-lookup-timeout/1.vision.experience.dimensions.md:12

The `connection kind` axis lumps the say's baseline probe (5s reply) and its observe probes (1s reply) into one `probe-in-say` kind, while the `lookup outcome` axis buckets everything under `fast` as `< 5s`. Those granularities do not align: an observe probe whose lookup takes 2s is `fast` (<5s) but already past its own 1s reply bound, so it degrades to blind — yet the inventory verdicts `same × fast` as 'probe `capable` / demoed — case=4'. So the cell `probe-in-say × same × fast` contains two distinct experiences with different verdicts (capable at <1s, blind at 1–5s) and is mis-verdicted for the observe sub-range. This is a real (lower-severity, delivery-succeeds) experience hidden inside a coarse cell — an un-split axis position. Fix by splitting the kind (baseline 5s vs observe 1s) or the lookup position (<1s vs <5s), or by recording the observe 1–5s sub-verdict explicitly in the cell rather than 'capable'. The same review of `get` is consistent because its 5s reply matches the `fast` boundary.

**snippet**:
```md
| same | fast | probe `capable` | probe `capable` | happy | critipath | **demoed — case=4** (walked inside the one say call) |
```

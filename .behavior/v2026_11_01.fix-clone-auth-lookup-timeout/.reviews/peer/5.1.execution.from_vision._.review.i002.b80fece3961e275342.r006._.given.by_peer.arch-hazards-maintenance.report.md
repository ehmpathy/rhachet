# nitpick.1: injected lookupTimeoutMs has no guard — 0/negative/NaN silently removes the bound

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:80

`context.lookupTimeoutMs` is now an injected override on the only bound that keeps the `ss -xp` scan from running unbounded. node's `child_process` only arms its kill timer when `timeout > 0`, so a caller (i.e. a future test) that passes `0`, a negative, or `NaN` gets NO timer at all and the exec waits for `ss` to finish on its own — the exact unbounded wait the bound exists to retire (the same class as ehmpathy/rhachet#678's symptom, only now silent rather than loud).

per failfast, the procedure should halt on an invalid bound rather than silently continue: guard `context.lookupTimeoutMs` before the exec (a positive finite number, e.g. `Number.isFinite(n) && n > 0`) and `MalfunctionError.throw` with the supplied value.

**snippet**:
```ts
      timeout: context.lookupTimeoutMs,
```

# nitpick.2: header claims 'a lookup break is a MalfunctionError' — the exec-fault path rejects raw

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:26

the module header states `.note = linux-specific (needs /proc + ss); a lookup break is a MalfunctionError (a real infra fault to diagnose, not a caller fault)`. that holds for the three guarded states (no fd, not a socket, no pid) but NOT for the exec itself: `await execAsync(...)` has no try/catch, so a killed/`ss`-missing/failed pipeline rejects with node's raw `Command failed: ...` error — and this PR's own `[case2]` codifies exactly that (`expect(outcome.error).toMatchObject({ killed: true })`, no `MalfunctionError`).

so the doc asserts a contract the code does not keep, and a reader (or the clone gate, which folds a throw into `verdict: 'deny'`) is left with the raw errno-less error — the failloud gap that made #678 hard to diagnose. either wrap the exec fault in a `MalfunctionError` carrying the inode + exit code/stderr, or narrow the note to say the exec fault propagates raw (label deferred per #683).

**snippet**:
```ts
 * .note = linux-specific (needs /proc + ss); a lookup break is a MalfunctionError
 *   (a real infra fault to diagnose, not a caller fault)
```

# nitpick.3: PATH swap adds an empty path element (CWD) when PATH was unset

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/.test/assets/genSlowSsOnPath.ts:43

`[binDir, pathBefore ?? ''].join(delimiter)` yields `"<binDir>:"` when `process.env.PATH` was undefined. on POSIX an empty PATH element means "search the current directory", so the worded intent (fake `ss` first, then the real PATH) silently widens the search to the CWD — a stray `ss` in the working dir would win over the real binary. the fixture already computes `dirsSearched` with `.filter((dir) => dir !== '')` for exactly this reason; compose the swap from that same filtered list (or filter the composed value) so the swap and the lookup search agree.

**snippet**:

# nitpick.4: restore is order-dependent — a second overlapping swap is silently dropped

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/.test/assets/genSlowSsOnPath.ts:44

`restore` writes back the value captured at generation time, with no record that a swap is active. it is safe to call twice (idempotent with its own snapshot), but it is not reentrant: if two scenes ever hold a swap at once (any future second `genSlowSsOnPath` in a file), restoring the first writes back the pre-second PATH and silently discards the later fake — the reverse of what the caller asked for, with no error. as a shared test asset this is a footgun waiting for the second user.

fail fast on the unsupported state (throw/named error if a swap is already active) or track a stack so restores unwind LIFO.

**snippet**:
```ts
  const restore = (): void => {
    if (pathBefore === undefined) {
      delete process.env.PATH;
      return;
    }
    process.env.PATH = pathBefore;
  };
```

# nitpick.5: socket-pair fixture has no reject path or 'error' listeners — a fault hangs or crashes unattributed

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/infra/socket/getSocketPeerCred.integration.test.ts:24

`genSocketPairSameProcess` awaits `server.listen(...)` and a `'connection'` event through promises that can only resolve: a listen fault (EADDRINUSE, no abstract-namespace support, ENAMETOOLONG) never rejects the promise, and neither socket carries an `'error'` listener, so the failure surfaces as an uncaught emitter throw (attributed to whichever test is running) while the awaited promise is left unsettled. the same for `connect(path)`.

this is the class the suite's own harnesses already guard (`[case13]`'s bounded race, `[case15]`/`[case16]`/`[case19]`'s named `ConstraintError`s): a fixture fault should fail fast with a named cause, not hang the scene or land on a sibling test. wire `reject` on both promises (and destroy the server on a listen fault) so the fault names itself.

**snippet**:
```ts
  const serverSideAccepted = new Promise<Socket>((done) =>
    server.once('connection', done),
  );
  const path = `\0rhachet-peer-cred-test-${getUuid()}`;
  await new Promise<void>((done) => server.listen(path, () => done()));
  const client = connect(path);
  const serverSide = await serverSideAccepted;
```

**locations**:
- src/infra/socket/getSocketPeerCred.integration.test.ts:47

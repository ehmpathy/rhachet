# nitpick.1: `statSync('/proc/<pid>')` is an unguarded TOCTOU — a peer that exits between the `ss` snapshot and the stat throws a raw errno, not the named MalfunctionError

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.behavior-hazards.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:109

`getSocketPeerCred` now derives `pid` from the TRUE peer's `ss` line (the F8 fix) rather than the reader's own pid, and the `ss` scan bound grew to 60s. That combination widens a pre-existing race: the pid is read from the `ss` table at time T, then `statSync('/proc/<pid>')` runs at time T+ε. If the peer process exits in that window (a dispatching client that hangs up mid-dispatch is exactly the scenario the longer scan now tolerates for up to a minute), `/proc/<pid>` is gone and `statSync` throws a bare `ENOENT`/`ESRCH`. That raw throw is NOT one of the guarded breaks the docblock promises as a `MalfunctionError`; the clone gate folds any throw into a deny, so it fails closed (no security hole), but the caller receives an unnamed infra fault instead of the classified MalfunctionError the contract advertises. Guard the stat (try/catch → `MalfunctionError.throw('peer pid vanished before cred read', { pid })`) so the fault names itself, consistent with the file's other guarded breaks.

**snippet**:
```ts
  // the owner of /proc/<pid> carries the peer's real uid + gid
  const stat = statSync(`/proc/${pid}`);
  return { pid, uid: stat.uid, gid: stat.gid };
```

# nitpick.2: `[case2]` leaves a ~20s orphaned `sleep`/`ss` grandchild after the 1s exec kill — a side effect that outlives the test

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.behavior-hazards.md

**locations**:
- src/infra/socket/getSocketPeerCred.integration.test.ts:91
- src/infra/socket/getSocketPeerCred.integration.test.ts:128

`[case2]` sets `SS_DELAY_SECONDS = 20` and a 1s lookup bound. When node's `exec` `timeout` fires, it signals only the direct child (`sh -c 'ss -xp | grep …'`), not the pipeline's grandchildren. The fake `ss` shim (`sleep 20` then `exec "<real ss>"`) and `grep` are orphaned and keep running: `sleep` finishes at 20s, then the real `ss` executes. The test reaps the peer child and destroys `serverSide`, but nothing reaps this abandoned scan — a hidden side effect that lingers into subsequent files the worker runs (harmless reads of `/proc`, but an untracked process per run). Since the property only needs `SS_DELAY_SECONDS > LOOKUP_TIMEOUT_MS`, a much smaller value (e.g. 3s, still > the 1s bound, so the `elapsedMs < SS_DELAY_SECONDS * 1000` assertion still holds) would prove the same thing while shrinking the orphan window ~6x. Alternatively, spawn the shim in its own process group so the timeout kill reaches the whole pipeline.

**snippet**:
```ts
    const SS_DELAY_SECONDS = 20;
    const LOOKUP_TIMEOUT_MS = 1_000;
```

# nitpick.3: `sleep ${input.delaySeconds}` interpolated raw into the shim — an invalid value yields a broken zhô that faults for an unrelated cause

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.behavior-hazards.md

**locations**:
- src/.test/assets/genSlowSsOnPath.ts:66

The fake-`ss` shim writes `sleep ${input.delaySeconds}` verbatim into a `/bin/sh` script. `delaySeconds` is typed `number`, but `NaN`, a negative, or a value `sleep` cannot parse produces a shim that faults when the shell runs it — so a dependent lookup test would red for a reason unrelated to the property it holds (a silent fixture break rather than a real verdict). Guard the input at the boundary (`Number.isFinite(input.delaySeconds) && input.delaySeconds > 0`, else a named ConstraintError) so a bad delay fails by name at fixture construction rather than as an opaque shim fault downstream. (The sibling `${ssReal}` interpolation is already quoted; this numeric one is not validated.)

**snippet**:
```ts
    `#!/bin/sh\nsleep ${input.delaySeconds}\nexec "${ssReal}" "$@"\n`,
```

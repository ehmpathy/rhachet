# nitpick.1: [case19] trace assertion uses a broad `'auth'` substring instead of the criterion's `clone socket auth error`

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.require.behavior-intent-coverage.md

**locations**:
- src/domain.operations/clone/socket/genCloneSocketServer.integration.test.ts

The vision's clamp criterion specifies: 'the trace holds no `clone socket auth error` line'. The test instead filters every traced line for the substring `'auth'`.

This is both broader than the criterion and more brittle: any benign server diagnostic that happens to contain the letters 'auth' (e.g. a future 'auth gate accepted'/'auth gate listening' line) would make this negative assertion false-red even though no `clone socket auth error` occurred. The test currently passes only because no benign 'auth' line is traced today.

To match the specified criterion and stay robust, assert against the actual error text (e.g. `line.includes('clone socket auth error')` or `'auth-denied'`) rather than the bare `'auth'` token. The rest of [case19] (delivered, elapsed >= 9s, exact write stream) is sound and does prove the same-uid acceptance the wish names.

**snippet**:
```ts
      then('the trace holds no auth error', () => {
        expect(scene.traced.filter((line) => line.includes('auth'))).toEqual(
          [],
        );
      });
```

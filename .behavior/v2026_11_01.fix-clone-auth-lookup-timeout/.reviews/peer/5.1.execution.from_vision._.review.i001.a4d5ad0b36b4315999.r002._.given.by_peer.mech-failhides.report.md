# blocker.1: case19 teardown masks the setup ConstraintError (unguarded afterAll, no optional chain)

**rule**: practices/code.test/pitofsuccess.errors/rule.forbid.failhide.md

**locations**:
- src/domain.operations/clone/socket/genCloneSocketServer.integration.test.ts:1425

case19's setup throws a `ConstraintError` BY DESIGN when the host lacks `ss` (`if (!ssReal) throw new ConstraintError(...)`), and it also mutates the process-global `process.env.PATH` before its final `await genServerWithCapture()`. If that `useBeforeAll` ever rejects — the missing-`ss` branch, or a bind/genServer failure — `scene` is never assigned / is a failed ref, so this `afterAll` runs `process.env.PATH = scene.pathBefore` on an uninitialized `scene` and throws a bare `cannot read 'pathBefore' of undefined`.

That cleanup throw (a) replaces the named ConstraintError with a generic type error — the exact 'cleanup fault masking the real verdict' this very file warns about in `[case13]`/`[case15]`/`[case16]`, whose `afterAll`s all use the optional-chain guard (`afterAll(async () => scene?.server?.close())` / `await scene?.unclaimed?.close()`) for precisely this reason; and (b) leaves `process.env.PATH` pointing at the fake `ss` binDir — a process-global leak that can bleed the 9s-sleeping `ss` into neighbouring suites in the same worker.

This is a failhide pattern (`rule.forbid.failhide`), and the fix is right next door: guard the teardown so it can never mask the setup verdict, e.g. restore PATH only when `scene?.pathBefore` is defined and `await scene?.close?.()` — matching the `[case15]`/`[case16]` precedent.

**snippet**:
```ts
    afterAll(async () => {
      process.env.PATH = scene.pathBefore;
      await scene.close();
    });
```

# nitpick.1: genSlowSsOnPath mixes four grains in one operation (PATH introspection, ss discovery, bin write, process-wide env swap + teardown)

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.prefer.decomposable-architecture.md

**locations**:
- src/.test/assets/genSlowSsOnPath.ts:45
- src/.test/assets/genSlowSsOnPath.ts:48
- src/.test/assets/genSlowSsOnPath.ts:66

`genSlowSsOnPath` is a new operation and it carries more than one grain at once:

1. PATH introspection — `getAllPathDirs` / `getOneFileOnPathDirs` (pure-ish, fs `existsSync`)
2. real-binary discovery — finds the extant `ss` before the swap
3. filesystem WRITE — mints the fake `ss` script into a temp dir
4. process-wide state mutation — assigns `process.env.PATH` and returns a hand-rolled `restore` closure whose correctness rests on an unstated caller pairing ("one swap at a time", enforced by a substring probe on the PATH string).

That is a communicator (i/o + global state) and an orchestrator (compose the discovery/write/swap steps) folded into one body, so none of the pieces can recompose independently. The concrete consequences: a second PATH fake (a slow `git`, a slow `iptables`) cannot reuse the swap half, and two callers cannot nest or overlap, because the state and its teardown live inside the ss-specific generator.

suggest: split the ss-specific half from the PATH-swap half, e.g. `genSlowSsBin({ dir, delaySeconds, ssReal })` (writes the script) and a reusable `genPathSwap({ dir })`/`withPathDir(...)` returning `restore` (owns the env mutation + the nested-swap guard). `genSlowSsOnPath` then reads as a three-line composer: resolve dirs → find real ss → write bin → swap. Do NOT extract the `try/catch` + `restore()` dance shared by the two new integration scenes — that is 2 usages, below the rule-of-three, and tolerating the duplication is the correct call.

**snippet**:
```ts
  // a fake `ss` that sleeps, then execs the real one with every arg
  const binDir = genTempDir({ slug: SLOW_SS_DIR_SLUG });
  writeFileSync(
    join(binDir, 'ss'),
    `#!/bin/sh\nsleep ${input.delaySeconds}\nexec "${ssReal}" "$@"\n`,
    { mode: 0o755 },
  );

  // prepend the fake to the non-empty dirs, and hand back the exact undo
  process.env.PATH = [binDir, ...dirsSearched].join(delimiter);
```

# nitpick.2: getSocketPeerCred reaches for the global `process.env` instead of taking env via context, forcing process-wide PATH mutation in tests

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.prefer.decomposable-architecture.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:85
- src/infra/socket/getSocketPeerCred.ts:88

The new `env: process.env` argument bakes the global environment into the communicator rather than accepting it through the `(input, context)` contract the operation already has. That choice is what forces the clamp to mutate `process.env.PATH` for the whole jest worker (a real side effect that outlives the scene, needs an explicit `restore`, needs a one-swap-at-a-time guard, and is documented as a hazard in `genSlowSsOnPath`).

Per the rule's recomposition test ("explicit inputs and outputs; dependency injection via context"), the environment is an input of this operation, and an injectable env would let each scene scope its own PATH with zero global mutation and no ordering constraint. As written, the seam is one-way: the communicator reads global state, so every test that wants a different PATH must write global state.

suggest: thread it, e.g. `context: { lookupTimeoutMs: number; env?: NodeJS.ProcessEnv }` defaulting to `process.env`, and pass `env: context.env` to `execAsync`. Then `genSlowSsOnPath` could hand back the swapped PATH value for the caller to inject, rather than assigning `process.env.PATH` itself (keep the global-assign path only for the acceptance scene that truly needs a real shell PATH).

**snippet**:
```ts
  // .note = `env: process.env` equals the default in prod; it is explicit so the `PATH` a test
  //   sets reaches the shell (jest hands each test file its own copy of `process.env`, which
  //   node's core child_process never reads unless it is passed)
  const { stdout: ssOutput } = await execAsync(
    `ss -xp | grep -E "${grepPattern}" || true`,
    {
      encoding: 'utf-8',
      timeout: lookupTimeoutMs,
      env: process.env,
    },
  );
```

# nitpick.3: the lookup bound has two owners: the context parameter default and an in-body `??` fallback

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.prefer.decomposable-architecture.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:41
- src/infra/socket/getSocketPeerCred.ts:69

The new bound resolution states the default twice: once as the `context` parameter default (`{ lookupTimeoutMs: SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS }`) and again as `context.lookupTimeoutMs ?? SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS` in the body. The parameter is typed as a required field, so the `??` branch is only reachable by a caller who explicitly passes `undefined` — i.e. it is a second, unreachable owner of one contract value.

This is decode-friction at the top of the communicator: a reader has to simulate which of two defaulting sites wins before they can trust the guard that follows, and a future change to the default can be applied to one site and not the other (the exact drift the derived-constant work in `constants.ts` was written to prevent at the module level).

suggest: pick one owner — either make `context` optional with an in-body resolution (`context?: { lookupTimeoutMs?: number }` then one `const lookupTimeoutMs = context?.lookupTimeoutMs ?? SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS`), or keep the parameter default and drop the `??`.

# nitpick.4: the touched credential lookup still inlines three i/o leaves (readlink, exec, stat) plus one compute step

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.prefer.decomposable-architecture.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:60
- src/infra/socket/getSocketPeerCred.ts:88
- src/infra/socket/getSocketPeerCred.ts:112

The hunk edits the `execAsync` call, so this is the moment to note the grain: `getSocketPeerCred` composes three distinct i/o reads and one compute step inline — `readlinkSync('/proc/self/fd/…')` (inode), `execAsync('ss -xp | grep …')` (pid), `statSync('/proc/<pid>')` (uid/gid), plus the inode → signed-inode → grep-pattern derivation that is transformer work sitting inside the communicator. The pid parse was just correctly lifted to `asSocketPeerPidFromSsPeerLine`; the other leaves were not.

Why it matters for recomposition: the signed-inode conversion and the grep pattern are the only pieces a test can exercise with no kernel, and they are currently reachable only by running a real socket + real `ss`; and the `/proc/<pid>` ownership read cannot be reused by the daemon's pid-only reader. The body reads as an orchestrator whose leaves are inlined, so each step must be re-read in full to be understood.

suggest (nitpick, not a blocker): the same treatment the pid parse got — `getOneSocketInode(input: { fd })` (readlink + regex), `asSsInodeQuery(input: { inode })` → `{ inode, signedInode, grepPattern }` (pure transformer, unit-testable with no kernel), `getOneProcOwner(input: { pid })` (stat). `getSocketPeerCred` then reads as four prose lines. Left as-is it is not wrong, only less recomposable.

**snippet**:
```ts
  const { stdout: ssOutput } = await execAsync(
    `ss -xp | grep -E "${grepPattern}" || true`,
    {
      encoding: 'utf-8',
      timeout: lookupTimeoutMs,
      env: process.env,
    },
  );
```

# nitpick.1: invalid caller-supplied lookup bound is thrown as a MalfunctionError (exit 1), not a ConstraintError (exit 2)

**rule**: .agent/repo=ehmpathy/role=mechanic/briefs/practices/code.prod/pitofsuccess.errors/rule.require.exit-code-semantics.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:70
- src/infra/socket/getSocketPeerCred.integration.test.ts:265

`getSocketPeerCred` takes `context.lookupTimeoutMs` from the caller and rejects a value that would arm no kill timer (0, negative, NaN). That is an invalid argument supplied by the caller — the exit-code-semantics rule lists 'invalid arguments' and 'missing required config' under constraint errors (exit 2, ✋), while `MalfunctionError` (exit 1, 💥) is reserved for system faults the caller cannot fix.

As written, a caller who passes `lookupTimeoutMs: 0` gets a `MalfunctionError`, which tells them the server must fix it and signals 'retry may help' — the opposite of the truth. This should be `ConstraintError.throw(...)` (the same `helpful-errors` import already brings in the class). The sibling test `[case3]` in `getSocketPeerCred.integration.test.ts` enshrines the same wrong class with `expect(outcome.error).toBeInstanceOf(MalfunctionError)` and would need to move to `ConstraintError` alongside the source change.

This is a nitpick per the rule's own enforcement ('constraint error using exit 1 = nitpick'), not a blocker.

**snippet**:
```ts
  if (!Number.isFinite(lookupTimeoutMs) || lookupTimeoutMs <= 0)
    return MalfunctionError.throw(
      'peer-cred lookup bound must be a positive number of ms',
      { lookupTimeoutMs },
    );
```

# nitpick.2: fixture fault `peer child exited before it connected` carries context but no actionable hint

**rule**: .agent/repo=ehmpathy/role=mechanic/briefs/practices/code.test/pitofsuccess.errors/rule.require.failloud.md

**locations**:
- src/infra/socket/getSocketPeerCred.integration.test.ts:46

`genSocketWithChildPeer` fails fast when the spawned child dies before it connects — good class (`MalfunctionError` = infra/test fault) and good context (`{ code }`). But it carries no `hint`, so a developer who hits this sees a bare message with an exit code and no next move.

The code.test failloud rule asks test/infra errors to include the resolution: there are only a handful of causes here (the abstract socket name is malformed, `process.execPath` could not run, or the child's own connect errored), and stating them — e.g. `hint: 'check the abstract socket name and that the spawned node process can bind/connect; the child calls process.exit(3) on a connect error'` — turns a stall into a fix. Enforcement: 'error without hint = nitpick'.

**snippet**:
```ts
    child.once('exit', (code) =>
      fail(
        new MalfunctionError('peer child exited before it connected', { code }),
      ),
    );
```

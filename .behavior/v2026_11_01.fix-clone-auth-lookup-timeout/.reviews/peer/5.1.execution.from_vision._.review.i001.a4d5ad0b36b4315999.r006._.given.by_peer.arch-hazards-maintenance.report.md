# blocker.1: [case19] afterAll masks the setup's named ConstraintError with a bare TypeError (failhide)

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/domain.operations/clone/socket/genCloneSocketServer.integration.test.ts:1430

The new `[case19]` scene throws a named, actionable `ConstraintError` in its `useBeforeAll` when `ss`/iproute2 is absent (`if (!ssReal) throw new ConstraintError('...`)`, per the `rule.require.failfast`/`failloud` intent. But its `afterAll` unconditionally dereferences `scene.pathBefore` and `scene.close()`. When the setup throws, `scene` is `undefined`, so the teardown throws `Cannot read properties of undefined (reading 'pathBefore')`, which replaces the informative ConstraintError with an opaque TypeError: the caller loses the "install iproute2" cause and the verdict the row exists to report.

This is exactly the failhide masking that `[case15]` in this same file already documents and guards against with an optional chain (`afterAll(async () => scene?.server?.close())`) and a comment citing `rule.forbid.failhide`. `[case19]` reintroduces the hazard it should have copied the guard for.

Fix: guard the teardown so the setup error survives — e.g. `afterAll(async () => { if (!scene) return; process.env.PATH = scene.pathBefore; await scene.close(); })` (and restore PATH only when it was actually swapped).

**snippet**:
```ts
    afterAll(async () => {
      process.env.PATH = scene.pathBefore;
      await scene.close();
    });
```

# nitpick.1: `|| true` in the ss lookup discards the real ss failure (failloud gap)

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.maintenance-hazards.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:69

The shell pipeline `ss -xp | grep -E "..." || true` throws away `ss`/`grep`'s exit status and stderr. When `ss` genuinely fails (binary missing, permission denied while walking /proc, OOM), `execAsync` resolves with empty stdout, `asSocketPeerPidFromSs` returns null, and the code reports the generic `MalfunctionError('could not read peer pid from ss', { inode })` — with no stderr, no exit code, and no distinction between "the socket truly has no matching peer" and "the ss scan itself broke". That is a failloud gap: a generic message where the actionable cause should be. (The PR's own narrative in #678 is a lookup that mislabels its cause; this line is the surviving source of the same ambiguity.) The line predates this change but sits inside the exec call this PR edits, so it is worth addressing fix-forward: drop the `|| true` and distinguish "no match" from "ss failed", or capture/attach the stderr + exit status to the throw.

**snippet**:
```ts
  const { stdout: ssOutput } = await execAsync(
    `ss -xp | grep -E "${grepPattern}" || true`,
    {
      encoding: 'utf-8',
      timeout: SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS,
      env: process.env,
    },
  );
```

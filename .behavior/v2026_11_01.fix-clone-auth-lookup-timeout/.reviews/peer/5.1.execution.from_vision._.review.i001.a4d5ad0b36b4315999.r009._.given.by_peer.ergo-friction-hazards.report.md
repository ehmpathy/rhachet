# blocker.1: slow-lookup window now ends in an unexplained 30s client wedge, and the box does accumulating `ss` scans — neither acceptance tested

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.friction-hazards.md

**locations**:
- src/domain.operations/clone/socket/constants.ts:150
- src/infra/socket/constants.ts:14
- src/domain.operations/clone/socket/genCloneSocketServer.integration.test.ts:1388

this pr raises `SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS` to 60s and derives `CLONE_AUTH_GATE_TIMEOUT_MS` to 65s. the vision itself admits the friction this creates:

1. **unclear error / unclear flow on the 30s–60s window (blocked state not named).** the client's first-ack wedge floor stays at 30s (`CLONE_WEDGED_TIMEOUT_FLOOR_MS`), while the gate now waits up to 65s. a lookup that takes between ~30s and 60s passes server-side and then finds the caller gone; the human sees a 30s wedge with `acksSeen: []` and no cause at all — the same opaque failhide the change was written to cure, just pushed to a higher bar. the vision flags this under `.what is awkward?` and defers it (F3/S1), but the friction still ships. per the rule, every blocked/degraded state a human can hit must be named with an actionable message (what went wrong AND how to fix) — a bare `acksSeen: []` after 30s does not tell the human the box's `ss` was slow.
2. **flow friction — the box gets slower from its own lookups.** the vision's cons: on a box where `ss` takes T seconds, about T/1.25 `ss` scans run at once per observed say (≈7 at T=9s, ≈32 at T=40s), and each connection's gate now runs its scan to completion instead of being reaped at 5s. a slow box is made slower by the very dispatches meant to relieve it. accepted for this wish, but it is an unaddressed ergonomic cost.

neither of these user-facing consequences has an acceptance test or snapshot. `[case19]` proves only the 9s point (the happy end of the range). there is no test that drives a 30s–60s lookup and shows the reviewer what the human actually sees on the wedge, and no test that observes the scan pile-up. per the rule, `friction hazards without test coverage block merge.` add acceptance coverage for the 30s–60s wedge path (assert the exact stderr/hint the caller reads) and for a lookup that outlasts the gate, and snap what the human sees.

**snippet**:
```ts
export const CLONE_AUTH_GATE_TIMEOUT_MS =
  SOCKET_PEER_CRED_LOOKUP_TIMEOUT_MS + 5_000;
```

# blocker.2: no snapshot of the new slow-lookup success variant, and the new ≥60s / never-settles edge cases are untested

the new `[case19]` proves the delivery path with structured `toEqual` assertions on internal fields (`outcome.result`, `scene.written`, `scene.traced`) — not a snapshot of the caller-visible output. the vision's `.after` block shows the human now sees `😶🎙️ said to @:reviewer` followed by the `🟡 feed not live — verified by transcript` degrade on a 9s box. that is a new user-facing output variant this behavior routes callers into, and there is no snapshot proving what the CLI actually prints for it (`rule.require.contract-snapshot-exhaustiveness`: 'every variant that a caller could encounter must be snapped').

further, the change introduces new edge variants that are neither tested nor snapped:
- a lookup that exceeds 60s → the exec is killed and the gate reads the kill as `auth-denied` (the vision concedes the mislabel persists at the higher bar — `.edgecases`, F4); no test asserts this
- a lookup promise that never settles → the gate fires at 65s as `auth-gate-timeout`; no test asserts this
- the 30s–60s client-wedge path (see the friction blocker) — no snapshot of the wedge output

the rule warns: 'if you find yourself about to skip a variant, that is the variant that will break in prod.' these are exactly the variants this behavior newly exposes. add snapshot coverage (masked where needed) for the delivered-but-feed-not-live output and the two new fault verdicts.

  expect(outcome.error?.message ?? null).toEqual(null);

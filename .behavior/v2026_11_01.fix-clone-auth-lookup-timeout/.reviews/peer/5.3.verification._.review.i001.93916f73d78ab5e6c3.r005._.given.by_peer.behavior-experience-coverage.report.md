# nitpick.1: ss-table-overflow false-deny boundary revealed by a test, not itemized in the catalog

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.vision/rule.require.experience-catalog-evolution.md

**locations**:
- src/infra/socket/getSocketPeerCred.integration.test.ts:225

`getSocketPeerCred.integration.test.ts [case6]` exercises a boundary the experience contract does not hold: an `ss -xp` table larger than the read buffer (70 MiB past `SS_TABLE_MAX_BYTES`) makes the peer-cred lookup reject (`ERR_CHILD_PROCESS_STDIO_MAXBUFFER`, `` `ss` table exceeds the read buffer ``), so a SAME-user caller is denied — a false deny with no workable fallback for the caller (they cannot shrink the host's socket table).

This is a real experience surfaced at verification: same-uid caller × a lookup that fails on table overflow → `auth-denied`. The catalog's lookup-outcome axis (`1.vision.experience.dimensions.md`: fast / slow-short / slow-long / killed / hung / throws-fast) and its `throws-fast` note in `case=_.md` enumerate the causes as "no fd, not a socket, no pid in `ss`, `ss` absent" — an overflow is not among them, and it has a distinct cure (a larger read buffer, not a longer wait), so it does not fold cleanly into an extant row.

Per the evolution rule (`discovered at verification — itemize; demo if critipath`) the contract should gain this boundary: add the value/item to the lookup-outcome axis, itemize it in `case=_` (with verdict and feel×care), and demo it if it earns critipath. By the catalog's own precedent a same-uid lookup failure is a near-zero-frequency alterpath (like the other `throws-fast` causes), so this is a discovered alterpath left un-itemized — a nitpick, not a blocker. Confirm the care once the row is written; if it is judged a critipath (a same-user success has no fallback here), the demo requirement escalates to a blocker.

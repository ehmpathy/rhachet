# blocker.1: wish outcome #3 (slow lookup ends at the lookup, never at the gate) is asserted only by a prose measurement that contradicts the vision's own mechanism analysis, and no test exercises the kill path

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.require.behavior-intent-coverage.md

**locations**:
- src/infra/socket/getSocketPeerCred.ts:73
- src/infra/socket/constants.ts:11
- .behavior/v2026_11_01.fix-clone-auth-lookup-timeout/5.1.execution.from_vision.yield.md

the wish's second outcome is: 'the auth gate bound sits above the lookup timeout, so a slow lookup ends at the lookup, never at the gate first.' the vision correctly derives the ORDER (gate = lookup + 5s), and the unit test pins that order. but the requirement that a lookup which actually exceeds the 60s exec bound ENDS at the lookup (fail-closed `auth-denied` before the 65s gate) depends entirely on one claim: that `exec`'s `timeout` settles the `sh -c 'ss -xp | grep -E … || true'` pipeline AT the bound.

that claim lives only in prose: the `.note` in `src/infra/socket/constants.ts` ('a 1000ms bound over a 4s `ss` rejected at 1010ms, `killed`, SIGTERM') and the `[x] F7` todo in the execution artifact. the vision's own open-question text says the opposite is plausible:
  'node's timeout signals the `sh`, not `ss` or `grep`, and `exec` settles on `close` — when every holder of the stdout pipe has let go. `grep` inherits that pipe and lives until `ss` ends. if so, the "kill" settles only when `ss` finishes, and a lookup past 60s would end at the 65s gate first — against the wish's "a slow lookup ends at the lookup".'

if that reading is right, the documented 1010ms measurement is invalid (it likely measured a different command shape, e.g. a bare `sleep` without the piped `grep`), and the PR would NOT deliver outcome #3 for a >60s lookup — a hung `ss` would run past the lookup bound and be cut by the 65s gate (`auth-gate-timeout`), the exact inversion the wish set out to remove.

no test in the target exercises the kill-at-bound path. `[case19]` uses a 9s `ss` under the 60s bound, so it never reaches the timeout; it proves the lower end of the range, not the 'ends at the lookup' mechanism. this is exactly the kind of criterion that is cheap to prove (a fake slow `ss` on `PATH` with an injected small timeout), so the gap should be closed by a committed test rather than a prose measurement, and the measurement's command shape should be verified against the real `sh | grep` pipeline before the constant's `.note` and the F7 verdict are trusted.

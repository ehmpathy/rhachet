│  │  **1. A say can land, then report as a failure that says "retry".** This is the same duplicate-delivery class the server guard just closed, one layer up. It is not covered by any test.
│  │
│  │  F12 says "a slow `ss` changes when `delivered` arrives, not what it renders". That premise is wrong. It changes which verdict branch runs:
│  │
│  │  - After `delivered`, `getCloneSayObservation` probes on a new connection each cycle. Each probe pays its own `ss` scan and gives up at 1s (`CLONE_SAY_PROBE_REPLY_MS`).
│  │  - If `ss` takes more than 1s, every observe probe reads blind, so `screen` is null. The `enqueued` short-circuit (`computeCloneSayPollStep.ts:117`) can never fire.
│  │  - Only a transcript rise within `CLONE_SUBMIT_VERIFY_TIMEOUT_MS` (15s) ends the poll as success. A busy brain on a loaded box is the vision's own scenario.
│  │  - Without a rise, the poll ends at the deadline as `unreadable feed-not-live`. That is a failure with exit 1. Its hint is "wait a moment and retry … the message may have landed" (snapshot lines 92–99).
│  │  - Before this change that box got `auth-denied` and nothing was delivered. Now the message is delivered, the CLI reports failure, and a retry types it twice.
│  │  - `invokeCloneSay.ts:273` already knows `dispatch.delivered === true` at that point, so the hint could say "delivered, do not retry".
│  │
│  │  No test drives the CLI loop with a slow `ss`. The report snapshots exist only at the pure `computeCloneSayReport` grain.
│  │
│  │  **Suggested fix:** an acceptance case through `enrollCloneHarness` with a 7s fake `ss` and a snapshot. Plus either a different hint for `unreadable` after a delivered ack, or a named acceptance of the gap in the vision.
│  │
│  │  **2. Same-user callers that `ss` cannot attribute are now denied, and the catalog has no cell for them.**
│  │
│  │  - Before the fix the gate passed everyone. Now a null pid is a deny (`asSocketPeerPidFromSsPeerLine.ts:43`).
│  │  - Same-user callers `ss` can't attribute include a caller in a pid namespace the clone's `/proc` cannot see, such as a sandboxed tool with the socket bind-mounted, and a non-dumpable process.
│  │  - The catalog's `same × throws-fast` row says "near zero for a live same-uid caller". It only considers a peer that exited before the scan, not an unattributable one.
│  │  - [case20] equates "invisible" with "other user". A same-user invisible caller would get the other-user copy, "run the say as the user that enrolled the clone", which is wrong advice.
│  │  - I did not verify that such callers exist in this repo's flows. The 72 `enroll.reach` acceptance tests show plain same-host callers pass.
│  │
│  │  **Ask:** does the wisher support a say from a sandboxed or other-namespace same-user caller? If yes, add an axis value (caller visibility) to the dimensions and a cell to the catalog.
│  │
│  │  **3. Case 21 depends on pid 1 being a different uid, and its failure message would mislead** (`genCloneSocketServer.integration.test.ts:~1480`).

│  │  - **Fix:** replace the root check with `statSync('/proc/1').uid === process.getuid()` and throw `ConstraintError` with a hint. This covers root too.

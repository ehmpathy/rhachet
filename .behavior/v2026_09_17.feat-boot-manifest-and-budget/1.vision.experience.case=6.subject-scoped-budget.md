## .the narrative

Bo sits down to a review round. he wants the driver role's review rubrics and no more, so he types
the command he always types:

```sh
rhachet roles boot --repo bhrain --role driver --subject review
```

the rubrics arrive. one line in the `<stats>` block is new:

```
  └── tokens ≈ 6000 / 8000 budget   (75% used)
```

he glances at it and carries on. that is the whole encounter, and that is the point: **Bo asked for
6,000 tokens, he got 6,000 tokens, and the receipt told him he has headroom.**

an hour later he wants the fulcrum briefs beside the rubrics:

```sh
rhachet roles boot --repo bhrain --role driver --subject review,fulcrums
```

this time it refuses:

```
🧢 roles boot --repo bhrain --role driver --subject review,fulcrums
   ├─ ✋ over budget
   │  ├─ budget   = 8,000 tokens   (declared in boot.yml)
   │  ├─ payload  = 11,000 tokens  (full emitted payload, o200k_base)
   │  └─ over by  = 3,000 tokens   (138% of budget)
   │
   ├─ in scope — 2 subjects
   │  ├─ always             2,000
   │  ├─ subject.review     4,000
   │  └─ subject.fulcrums   5,000
   │
   ├─ some resources must go — you choose which
   │
   └─ fix — five strategies, cheapest first
      ├─ narrow        --subject review          ← drop a subject
      ├─ catalogize    replace a set with one catalog that indexes it
      ├─ condense      author an x.md.min beside x.md
      ├─ reference     move a say entry to ref
      └─ eliminate     delete what does not earn its boot
                       ⇒ or raise budget.tokens deliberately — it lands on the diff
```

**and this one he can act on.** he drops `fulcrums`, re-boots, and reads the fulcrum briefs by path
when he needs them. the refusal cost him ten seconds and named the subject to cut.

### 🔴 the session he did NOT have, and why it would have made no sense

the driver spec is in subject mode — an `always:` section plus four `subject.*` sections
(`review`, `fulcrums`, `entoolment`, `pavement`). the **whole spec** is perhaps 24,000 tokens.

under the rival read of `budget: { tokens: 8_000 }` — the spec as a whole — Bo's first command
refuses:

```
🧢 roles boot --repo bhrain --role driver --subject review
   └─ ✋ over budget
      ├─ budget   = 8,000 tokens
      ├─ payload  = 24,000 tokens   (the whole spec — every subject)
      └─ over by  = 16,000 tokens   (300% of budget)
```

🔴 **and Bo has no move.** he never asked for 24,000 tokens. `--subject review` — the remedy such a
halt would name first — is the command he already typed. it cites a payload he did not request and
prescribes a fix he already applied.

⇒ **that is the felt difference between the two reads**: one refusal hands Bo a subject to cut, the
other hands him a dead end. it is why the fork below is not a matter of taste.

### .the fork the two sessions part on

> **so which number does a `budget: { tokens: 8_000 }` cap?**

both reads are defensible on paper, and they disagree by 4x:

| the read | an 8,000 cap means | Bo's session |
|---|---|---|
| **the spec as a whole** | the sum of always + every subject must fit | 🔴 refused at 24,000, with no move left. a subject-mode role could never declare a useful cap |
| **this invocation's render** | what this boot actually emits must fit | ✅ passes at 6,000 with a receipt; the two-subject boot refuses with a subject to cut |

⇒ **best-guess: the render, never the spec.** the budget caps **what is actually emitted into
context**, because that is the quantity the ~46% incident measured. a cap on the un-rendered
whole would refuse boots that cost naught.

### 🔴 the aha — the budget is a property of an INVOCATION, not of a file

this reframes the whole feature. `budget.tokens` reads like a static attribute of a spec; it is
in fact a **bound on a render**. the spec declares the bound; the invocation determines what is
measured against it.

⇒ that distinction is invisible in simple mode (one spec, one render) and decisive in subject
mode (one spec, 2ⁿ renders). the grid is the only reason it surfaced before implementation.

### 🔴 .this cell stated F12's PRINCIPLE a round before F12 was measured

the best-guess above reads: *"the budget caps **what is actually emitted into context**, because
that is the quantity the ~46% incident measured."*

🔴 **that is exactly `F12`'s claim, written here first — and the vision never checked whether the
extant counter implements it.** `totalChars` sums say content only, so it measures **36.5%** of
what the boot emits. ⇒ **the principle this cell argues for and the mechanism the vision planned to
gate on are two different quantities**, and one `wc -c` from this sentence would have found it.

and `[t3]` below is sharper still:

> `then the cap applies to always + every subject + the <also> section`

🔴 **this is the only bdd `then` in the whole vision that names the `<also>` section as within the

this cell; it is the cell that was already right, and `F12` is what makes it true.

🟡 **so `case=6` is F12's strongest corroboration rather than a victim of it.** it names the right
unit, and it asserts the one omission by name.

## .the bdd sketch

```
given [case6] a subject-mode spec that declares budget.tokens: 8_000
  # always:            ~2_000 tokens
  # subject.review:    ~4_000 tokens
  # subject.fulcrums:  ~5_000 tokens
  # subject.pavement: ~13_000 tokens

  when [t0] one small subject is booted
    $ rhachet roles boot --repo bhrain --role driver --subject review
    then it exits 0                      # 2_000 + 4_000 = 6_000 < 8_000
    then <stats> reports  tokens ≈ 6000 / 8000 budget

  when [t1] two subjects are booted, and together they exceed the cap
    $ ... --subject review,fulcrums
    then it exits 2                      # 2_000 + 4_000 + 5_000 = 11_000 > 8_000
    then the halt names WHICH subjects were in scope
    then the halt names the per-subject cost, so the author can drop one

  when [t2] every subject is booted
    $ ... (no --subject)
    then it exits 2                      # the whole spec far exceeds the cap
    then the halt lists FIVE strategies, with `narrow` first   # mode adds one; cheapest-first
    then the halt names NO individual resource                 # F13 — cost is knowable, value is not

  when [t3] the spec declares a budget and NO subject is asked for
    then the cap applies to always + every subject + the <also> section
```

## 🟡 .the remedy set grows for this cell

`case=2`'s halt offers **four strategies**. a subject-mode halt has a **fifth**, and it is often the
right one — so it sorts **first**, as the cheapest:

```
└─ fix — five strategies, cheapest first
   ├─ narrow        --subject review          ← the subject-mode addition
   ├─ catalogize    replace a set with one catalog that indexes it
   ├─ condense      author an x.md.min beside x.md
   ├─ reference     move a say entry to ref
   └─ eliminate     delete what does not earn its boot
                    ⇒ or raise budget.tokens deliberately — it lands on the diff
```

⇒ **the halt's remedy list is therefore not static** — it is a function of the spec's **mode**. a
hardcoded four-item list would offer the wrong advice to the cell that most needs the fifth.

🔴 **and `narrow` sorts first for the same reason the base ladder sorts as it does** — it is the one
remedy that costs the reader **naught**: no doc is restructured, condensed, dereferenced, or
deleted. the author simply asks for less of a spec that stays entirely intact. it is a rung *below*
`catalogize` on the ladder of loss, which is why it heads the list rather than joins the end of it.

🟡 **the owner axis is NOT a second input.** requirement 8 leaves a foreign spec ungated, so there is
no foreign halt whose remedies could vary — the function is `(mode)`, and a builder who branches on
owner writes a branch that cannot fire (`F10`).

## 🔴 .what this cell forbids — cell F

the grid's one nurture-forbidden cell falls directly out of this narrative.

if the budget caps a **render**, then a **per-subject budget** is incoherent:

```yaml
# 🔴 forbidden
always:
  budget: { tokens: 2_000 }       # a cap on... what? always alone never renders alone
subject.review:
  budget: { tokens: 4_000 }       # and a boot of two subjects has two caps?
```

⇒ the sum of section caps is not the render's cap, so a reader would compute the wrong bound.
**one budget, at the top level, per spec.** the schema must refuse the nested form — and today it
would silently *accept and discard* it (`RoleBootSpec.ts:39-43`, the `catchall`).

## .why this is an alterpath, not a critipath

**care = freq × cost.**

- **freq: low.** subject mode is rare — **at least 1 of the 15 extant boot specs** uses it today
  (`repo=bhrain/role=driver`, verified by a full `Read`). ⚠️ **a census of all
  15 was NOT performed** — 13 are symlinks into `node_modules`, which defeats a cheap count — so
  the numerator is a floor, never a total
- **cost: high.** the wrong read makes budgets unusable for exactly the roles big enough to
  need them, and the error is *silent* (a refused boot reads as a legitimate halt)

⇒ low frequency keeps it off the critipath; high cost earns it a demo anyway. it is the
worthwhile few the method asks for.

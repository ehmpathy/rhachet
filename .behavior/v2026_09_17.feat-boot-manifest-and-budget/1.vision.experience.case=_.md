## .the rejection invariants — the secondary grid

each is attemptable, so each owes a refusal that names the fix.

### axis D — the `--manifest` value

| value | verdict | the refusal |
|---|---|---|
| `inside-repo` | **demoed** (`case=3`) | — |
| `outside-repo` | **forbidden** | must refuse a path that escapes the repo. the repo already holds this invariant for every file-touch skill (`cpsafe`, `rmsafe`, `teesafe`); a boot that reads an arbitrary absolute path would be the one exception |
| `absent-value` | **forbidden** | `--manifest` as the last token must belay, never read a flag as a path |
| `with-role` | **forbidden** | `--manifest` and `--role` name two different specs. silently to prefer one is the ambiguity `rule.forbid.ambiguous-labels` forbids — refuse, and name which to drop |
| 🔴 `with-if-present` | **forbidden** | `--if-present` exists because a caller boots a **set** of roles, some unlinked in this repo — it means *"boot whichever of these are here."* a `--manifest` names **one** path the caller chose, so there is no set to be tolerant across, and tolerance converts a typo into an empty boot. ⇒ refuse the pair, and say the manifest path is not optional. asserted at `case=4` `[t6]` |

⚠️ **`with-if-present` hides in plain sight beside `with-role`**, which sits one row above and reads
almost identically — so a demo can assert the refusal, state that this table carries it, and be
wrong with nobody the wiser. ⇒ 🔴 **a claim that a record exists is not a record.**

**5 values = 1 demoed + 4 forbidden.** ✅ the 4 are this axis's rejection invariants.

## 🔴 .the blocker this walk exposed — a `budget` key is SWALLOWED today

the walk forced me to ask what happens to a `budget` key right now, before any code is written.
**it is silently discarded, twice over.**

| the mechanism | the file | the effect |
|---|---|---|
| `computeBootMode` reads only `briefs`/`skills`/`always`/`subject.*` | `computeBootMode.ts:19-24` | a spec with **only** `budget` returns mode `none` → `parseRoleBootYaml` returns `null` → no config at all |
| `schemaRoleBootSpecSubjected` ends `.catchall(schemaSubjectSection)`, and zod objects are non-strict | `RoleBootSpec.ts:39-43` | `budget: { tokens: 5000 }` parses **as a subject section**, then is dropped because extraction keeps only `subject.*` keys (`parseRoleBootYaml.ts:116-129`) |

⇒ **this is precisely the silent pass requirement 2 forbids** — an author declares a cap, the boot
renders unbudgeted, and no line of output says the cap was ignored. so the schema work is
**load-bearing rather than incidental**, and it is the reason cell **F** needs an explicit guard
rather than an accident of validation.

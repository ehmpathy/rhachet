# case 4 — live-rotate-moves-a-capped-clone · cron · clone host · happy · critipath

🔴 the densest walk: read → limit hit → pick → rewrite → re-read → verify, across a capped account,
on a live clone, with no restart and no human.

**narrative**

the clone `@:feat` is mid-task on alice's account. alice hits her 5-hour cap; claude-code paints
"You've hit your limit · resets …" on the clone's screen, with a reset about an hour out. the clone
host, which already mirrors that screen, sees the banner and does not wait for the next tick: it asks the pool for the
next pick, gets bob (uncapped, resets soonest among the rest), and rewrites the clone's own
credential file with bob's token. claude-code notices the new mtime on its next request and re-reads
it (the vision's Q4 measures this re-read; where it fails, case 6 is the walk). the clone keeps its
session, its context, its turn.

the host then compares accounts: before = alice, after = bob, read from the live clone's next
status-line `rate_limits`, which must track bob's window, not alice's — the file only proves what
the host wrote. only that compare marks the move as landed (`term=auth.swap`).

when no banner fires, the 15-minute tick does the same for any clone whose member reads capped or
dead, so a swap reaches every live clone within the ttl (09-29 seed S3).

who feels it: the host and the cron act, but the clone and its operator live it — the clone's turn
runs on with no restart and no lost context, and the operator who checks back later finds the work
moved forward instead of a session frozen on "You've hit your limit".

critipath: this is the whole of "no clone idles on a capped account while a peer has headroom".

**bdd `[tn]` timeline** (sketch)

```
given clone @:feat live on alice; pool 'default' = [alice, bob]; bob uncapped
  when [t0] alice hits her 5h cap and the clone's screen shows "You've hit your limit"
    then the clone host requests a pick at once (no wait for the tick)
    and  the pick returns bob
  when [t1] the host rewrites @:feat's credential file with bob's token (atomic rename)
    then claude-code re-reads the file on its next request (mtime moved); the process is not restarted
  when [t2] the host verifies
    then before = alice, after = bob → `🔁 @:feat moved alice → bob (5h cap, resets in 1h)`
given no banner fired, and the 15-minute tick finds a clone on a dead member
  when [t3] the tick runs
    then that clone moves the same way, within 15 minutes of the member's state change
given @:feat on bob (healthy, resets in 4h); carol uncapped, 60% left, resets in 30m; no clone on carol
  when [t4] the tick runs
    then @:feat moves to carol — her 60% would expire unspent in 30m, and a move spends it
         (no capacity left unused; fulcrum F5)
given the same, but another clone already draws on carol
  when [t5] the tick runs
    then @:feat stays on bob — carol's window is already spent by a peer; a move would churn for no gain
given @:feat live on alice, whose status line reads 80% (no cap), and bob uncapped
  when [t6] a request from @:feat meets a provider `429 rate_limit_error` with `Retry-After: 900`
    then enroll classifies it as the ratelimit class (#531), never as a crash or a generic error
    and  alice is marked `cooled` until Retry-After lapses; no pick returns her meanwhile
    and  @:feat moves to bob at once, the same rewrite + verify as t1–t2 — the banner never fired,
         and the status line never read 100%, so this trigger alone catches a transient throttle
    and  the host prints `🔁 @:feat moved alice → bob (429, cooled for 15m)`
  when [t7] the 429 carries no Retry-After
    then alice is cooled until the next tick re-reads her, so a throttle never pins her out for good
```

# 1.vision — brain credential pool rotation

> a fleet with N claude subscriptions behaves like one pool. no grove waits on a human oauth paste;
> no clone idles on a capped account while a peer in its pool has headroom.

source: `0.wish.md` · ehmpathy/rhachet#575 · the commander's amendment (seed S4) · research in `appendix/`.

## the answer to #575's open question — per box, actor, or clone?

**per clone.** each clone may be pointed, ad hoc, at a pool (`--brain-pool <name>`) or at one
account (`--brain-reach <email>`); with no flag, it takes the automatic pick from its actor's default
pool. the box holds the credentials (keyrack), the repo names the pools, the clone chooses.

---

## the outcome world

### before

one claude login per box (`~/.claude/.credentials.json`, shared by every clone since #571). when that
account caps, every clone stalls at once. recovery is a human: `git.grove.auth`, an oauth url, a
browser, a code paste. on a grove at 3am, no human comes; the fleet idles while a second subscription
the operator pays for sits unspent.

### after

the operator mints one long-lived token per account, once, at a laptop (`claude setup-token`), and
fills each into the grove's keyrack at the account's email as the reach. a committed pool file names
the emails.

- **at spawn**, each clone draws the member whose window resets soonest and still has headroom — or the
  pool or account its operator named — and says which account it drew
- **when a clone hits its limit**, the clone host sees the limit banner and moves that clone at once:
  it rewrites the clone's own credential file, and claude-code re-reads it on its next request. no
  restart, no lost turn
- **every 15 minutes**, a tick re-reads capacity and moves any clone left on a capped or dead account,
  so a swap reaches every live clone within the ttl
- **when no member has headroom**, no capped account is handed out; the refusal names the soonest reset
- **when a token dies**, the member drops out loud, with the re-mint command

### the aha

alice is 70% used and resets in 40m; bob is 20% used and resets in 4h20m. the old box burns
whoever is logged in and lets alice's last 30% evaporate in 40m. the pool spends alice first,
because her capacity is the one about to expire — and when she caps 32m later, the clone on her is on
bob by its next request. **soonest-reset-first turns a reset from a loss into a refill.**

## how the four parts compose

```
keyrack (per reach)          pool file (repo)         clone (per run)
┌────────────────────┐       ┌──────────────┐        ┌───────────────────────────────┐
│ setup-token  ──────┼──┐    │ default: a,b │──┐     │ --brain-pool / --brain-reach  │
│ usage cred   ──┐   │  │    │ redteam: c   │  │     │   or the auto pick            │
└────────────────┼───┘  │    └──────────────┘  │     └──────────────┬────────────────┘
                 │      │                      ▼                    │
                 ▼      │           ┌─────────────────────┐         │
       capacity read ───┼─────────▶ │ rank: drop capped / │ ◀───────┘
       (usage api, per  │           │ dead, soonest reset │
        reach; headers; │           │ first, idle last    │
        status line)    │           └──────────┬──────────┘
                        │                      ▼
                        └──────────▶ the clone's credential file  ◀── rewrite on limit
                                     (claude-code re-reads on mtime)    or each 15-min tick
                                                   │
                                                   ▼
                                     verify: account before ≠ after == target
```

### 1. long-lived tokens in keyrack, fetched per `--reach` (S1; 09-29 seed S2)

```sh
claude setup-token | rhx keyrack set --owner ehmpath --key CLAUDE_CODE_OAUTH_TOKEN \
  --env all --org @all --reach alice@ahbode.com --mech PERMANENT_VIA_REPLICA
```

- one key name, one reach per subscription. keyrack's reach axis was built for this case:
  `src/domain.objects/keyrack/KeyrackKeyReach.ts:23` names "a claude account juggle", exid = email (#462)
- the 09-29 seed S2 waterfall (the org's credential, else the machine default) stands for a clone with
  **no** pool: it keeps today's shared login. a pooled clone takes the pool's pick
- **vault now:** `os.secure` under the robot owner, unlocked by a passphrase-less prikey on the grove
  (`initKeyrack.ts:150-163`). the pool reads each member with the sdk's
  `keyrack.get({ for: { key }, reach, with: { unlock: true } })` (`src/contract/sdk.keyrack.ts:74-92`) at each use, so the grove dream's warn — a ~9h unlock that undercuts a one-year token
  (`.dream/v2026_09_29.reseed.grove-crews-should-spawn-with-the-setup-token.md`) — does not bite: the
  unlock is re-made headless whenever it lapses, and the token's year is the only lifetime that counts
- **vault next:** `aws.params` via the instance role, no secret at rest on the box — once its path gains
  a reach segment (`KeyrackVaultReachPolicy.ts:77-80` plans it; #432's amendment names aws.params for
  this token)
- an absent or locked member refuses the spawn with the pool's own `keyrack set … --reach <email>` —
  never keyrack's generic tip, which on a rack that holds another reach points at that one
  (`asKeyrackOmittedKeyTip.ts:137-138`)

### 2. per-clone choice (S4)

```yaml
# .agent/brain.pools.yml  (repo-owned, committed; names reaches, holds no secret)
brain: claude
key: CLAUDE_CODE_OAUTH_TOKEN
pools:
  default: [alice@ahbode.com, bob@ahbode.com]
  redteam: [carol@ahbode.com]
```

- `rhx enroll claude` → the auto pick from `default` · `--brain-pool redteam` → the auto pick within it ·
  `--brain-reach carol@ahbode.com` → pinned, no pick
- a pinned clone is never moved to another account; its cap is reported (case 10)
- a reach in no pool is refused: the pool file is the one list of accounts a clone may bill
- no pool file → today's shared login, unchanged; the pool is opt-in and composes with #571

### 3. capacity per credential — left and reset (S4: the way `brains.auth.usage` reads it)

- **primary:** the oauth usage endpoint, per reach — the source `uladkasach/dev-env-setup`
  `brains.auth.usage` reads today (`GET api.anthropic.com/api/oauth/usage`, `five_hour` / `seven_day` /
  `seven_day_opus` utilization and reset times). it refuses a setup-token (`sk-ant-oat01`, rejected since
  ~2026-02-20), so — as dev-env-setup does — keyrack holds a second credential per reach: a refresh token,
  captured from an isolated `CLAUDE_CONFIG_DIR` login so the global session is never touched
- **one source for the board and the pick** (bhuild#522): each read lands in the durable usage log
  (`brains.auth.usage` jsonl, a 5-minute poll floor). the pick and `pool status` read that log — never a
  live call per spawn — so the board and the pick can never disagree
- **its hazard, held:** a refresh token is single-use and rotated on each mint. two holders lock each
  other out (dev-env-setup `creds/hazard.claude-oauth-*`; the 2026-07-31 lockout). so it has exactly one
  holder — the usage reader — which writes each rotated value back to keyrack before it uses the new
  access token. clones never hold it; they run on the setup-token
- **a false throttle, ruled out:** the usage endpoint answers a wrong user agent with a 429 that never
  clears. the reader pins the agent dev-env-setup pins, and a persistent 429 there reads as a malfunction
  of the reader, never as a capped member
- **free reads:** each live clone's status line carries `rate_limits.five_hour` / `seven_day` (documented);
  the clone host writes those into the same per-reach cache, so a busy member is seldom read twice
- **fallback:** a one-token probe with the setup-token returns the
  `anthropic-ratelimit-unified-{5h,7d}-*` headers (undocumented; observed). used when the usage read is
  throttled (~30/h/account observed) or absent
- every read carries its age; a failed read keeps the last one, marked stale (case 9)

### 4. rotation by usage and expiry — the soonest reset spent first

- **rank:** drop dead, capped, and cooled members (a 7d cap rules over a 5h reset; a cooled member —
  one a provider 429 named a Retry-After for — returns when it lapses, case 4 t6) → each member left is
  keyed by its **tight window**: of its 5h and 7d windows, the one nearer its cap (higher used %), so a
  member at 5h 70% but 7d 98% is keyed by its week → among the rest, the tight window that resets
  soonest first, since its unspent capacity is the next to expire → idle members (no open window) last,
  since theirs keeps (fulcrum F7; case 3 t4)
- **channel — a credential file per clone that rhachet writes** (option O7 of
  `.behavior/v2026_09_29.fix-shared-brain-credential-blanking/refs/inventory.of=options._.md`, at the
  clone grain): the clone spawns with its secure-storage dir set to its own runtime dir, and that dir's
  `.credentials.json` holds the picked setup-token with no refresh token and a far `expiresAt`.
  the design assumes claude-code re-reads the file when its mtime moves, so a rewrite reaches a live
  clone on its next request — unmeasured, and two first-party sources disagree (nheuron `term=auth.swap`:
  hot-reloaded; dev-env-setup `brains.auth` help: open sessions keep the old token). Q4 measures it; if
  the re-read fails, the restart fallback below is the rotation. a setup-token never refreshes, so the
  refresh race #571 cured cannot return
- **triggers** (09-29 seed S3): at once when the clone host sees the limit banner on the clone's screen
  ("You've hit your limit · resets …" — the cli's cap signal per nheuron, `appendix/research.priors.md`
  q1; its text is no contract, so the clone's status-line `rate_limits` at 100%, a documented field,
  fires the same move), or when enroll classifies a provider 429 / `rate_limit_error` as
  the ratelimit class #531 asks for — its `Retry-After` becomes that member's cooldown; else a
  15-minute tick, run by the box's cron
  (`invokeEnroll.ts:726-730` already assumes an outer supervisor; rhachet has no scheduler). #575's
  hourly re-pick is a subset of the tick
- **who moves:** a clone on a capped or dead member, always. a healthy clone moves only to spend
  capacity that would otherwise expire: onto a member with headroom whose window resets sooner than
  its own, and that no clone draws on yet. every other healthy clone stays put, so the fleet is not
  churned for a marginal rank win (fulcrum F5; case 4 t4, t5)
- **fallback:** if a rewrite does not land, restart the clone on the new member with its session resumed
  (a wake), at an idle input (case 6)

### 5. verify — an account compare, never an exit code

- before the move, read the account the clone is on; after, read it again. a move is reported only when
  the two differ and the after equals the target (`uladkasach/nheuron` `term=auth.swap`: a swap can exit
  0 and move naught; only a compare of email and orgId proves it)
- the read, by logic: the account of the token in the file is known by construction — rhachet wrote it
  from the target's reach — so a read of the file proves only the write, never the move. the proof must
  come from the live process, and its one per-process signal is the status line: after the move, the
  clone's next `rate_limits` must track the target's window (as the usage log records it), not the
  source's. `/api/oauth/profile` per reach (`appendix/research.priors.md` l.99) labels each member once,
  at fill, so a token filed at the wrong reach is caught before it is drawn
- `[research]` (Q7): does the status line refresh `rate_limits` on the first request after the move,
  and how to part two members whose windows read alike; and can the profile read label the setup-token
  itself (its scope is `user:inference` only), or only the reach's refresh credential beside it

## mental model

- **to a friend:** "the boxes share a stack of claude accounts. each agent grabs whichever account resets
  soonest — or the one you tell it — and the moment it hits a limit it hops to another, mid-task."
- **the analogy:** use the groceries that expire first; when one shelf is bare, reach for the next.
- **their words → ours:** "account" → pool **member** (a keyrack **reach**) · "how much is left" →
  **capacity** · "maxed out" → **capped** · "switch account" → **rotate** (a move of one clone; distinct
  from `term=auth.swap`, a box-wide account swap, and from a token renewal of one member)

## evaluation

| done-when (S2 of this route) | how the contract meets it |
|---|---|
| declare a default pool and a custom set; draw with no human sign-in | §2 pools + per-clone flags; §1 headless keyrack |
| capacity per credential is read and shown | §3; `rhx brains pool status` (case 8) |
| soonest reset first; re-runs hourly; no capped pick while a peer has headroom | §4 rank; 15-minute tick ⊃ hourly; case 5 |
| swap verified by an account compare | §5 — the read is `[research]` |
| tested against two real subscriptions | the verify stone; two accounts on a grove (`[wisher]` Q6) |

**pros**
- live rotation with no restart, no daemon in the request path, no write to the shared login
- keyrack's reach axis already models one account = one reach
- opt-in: a repo with no pool file behaves exactly as today

**cons**
- the usage read is an undocumented endpoint, throttled; the header fallback is undocumented too
- a second credential per reach (the usage-scoped refresh token) is a sharp object: single holder or lockout
- O7's shape at the clone grain is unverified on today's claude-code build

**pit-of-success edges**
- absent / locked / dead member → loud refusal with the exact repair (cases 2, 7)
- all capped → no capped pick, the soonest reset named (case 5)
- a swap that moved naught → reported failed, then a restart fallback (case 6)
- a stray `CLAUDE_CODE_OAUTH_TOKEN` / `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` in the enroller's
  shell → cleared at spawn for a pooled clone, and an `apiKeyHelper` in the settings it reads →
  refused at spawn, since each outranks the pooled credential file in claude-code's order (the three
  env keys are the ones `isBrainAuthViaEnv.ts:8-12` already names)
- a reach outside every pool → refused (case 10)

## what is awkward

- **the capacity read is the soft floor.** the documented signal (the status line) needs a live clone;
  the read that covers idle members leans on an endpoint anthropic closed as "not planned" to document,
  and it needs a refresh token that is unsafe in two hands.
- **the O7 file is borrowed behavior.** live rotation rests on claude-code's mtime re-read, a detail of
  one build; a bump could drop it, which is why case 6's verify and restart fallback are owed, not optional.
- **the terms question sits under the whole design.** if Q1's answer is no, the right shape is api keys or a
  team plan, and most of this collapses to "pick an api key from keyrack".
- **the tight window is a heuristic.** a member is keyed by whichever window is nearer its cap, which
  keeps a week-spent member from the front of the rank (case 3 t4). it compares two percents of two
  different budgets, so a member at 5h 96% and 7d 95% is keyed by its 5h window though its week is
  near spent too. a weighted rank (headroom left in tokens, per window) would be truer and needs the
  window sizes the api does not publish (fulcrum F7).

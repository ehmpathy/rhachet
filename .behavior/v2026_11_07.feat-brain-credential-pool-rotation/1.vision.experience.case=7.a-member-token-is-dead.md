# case 7 — a-member-token-is-dead · cron · sharp · critipath

**narrative**

eleven months in, bob's one-year token expires (or bob re-minted and voided it). the next tick's read
gets a 401 on bob's probe. the pool does not retry bob forever, and does not treat a 401 as "capped
until later": it marks bob `dead`, drops him from every pick, and says so in the rotate log and in
`pool status`, with the fix — a fresh `claude setup-token` for bob, then the `keyrack set` at his
reach. the fleet keeps on alice in the meantime.

critipath: a dead member read as merely capped never comes back, and the pool shrinks with no one
told.

```
💥 pool 'default' member is dead (401)
   ├─ member = bob@ahbode.com
   ├─ since = 2026-10-02
   └─ fix — re-mint, then refill
      ├─ claude setup-token            (at a laptop, signed in as bob)
      └─ rhx keyrack set --owner ehmpath --key CLAUDE_CODE_OAUTH_TOKEN … --reach bob@ahbode.com
```

**bdd `[tn]` timeline**

```
given pool 'default' = [alice, bob], and bob's token now returns 401
  when [t0] the 15-minute rotate reads capacity
    then bob is marked dead, not capped; no pick returns bob
    and  the rotate exits 1 (a malfunction a human must repair) after it has moved what it can
  when [t1] a clone on bob is live
    then it is treated as on a capped account and moves to alice (case 4)
  when [t2] the operator refills bob's token and the next read gets 200
    then bob is live again; no flag needs to be cleared by hand
```

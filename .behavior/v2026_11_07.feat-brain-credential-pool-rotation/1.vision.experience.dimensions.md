# 1.vision.experience.dimensions

the axes the pool experience varies over. each is a small closed set. they are orthogonal but for three
declared correlations — **goal → actor**, **credential state → capacity**, and **member capacity →
pool state** — stated below rather than hidden in the walk.

| # | dimension | values | why it is its own axis |
|---|---|---|---|
| D1 | **actor** | `operator` (a human who declares the pool, fills keyrack, enrolls clones) · `clone` (a brain-cli process that draws a credential) · `clone host` (the enroll process that mirrors a live clone's screen and rewrites its credential file) · `cron` (the 15-minute tick on a box, no human present) | each meets the pool at a different moment, and only `operator` can type a secret |
| D2 | **goal** | `declare` (name the pool) · `fill` (put a token in keyrack) · `read` (see capacity) · `pick` (choose an account for a spawn) · `rotate` (move a live clone off its account) · `verify` (prove the account changed) | the six verbs of the done-when clauses (S2); the same actor with two goals is two experiences |
| D3 | **pool state** | `headroom` (≥1 member uncapped) · `all-capped` · `empty` (declared with zero members) · `undeclared` (no pool file: the opt-out every repo has today) | the pool grain alone: decides whether the pick may return aught. a member's own window is D10. `empty` is a pool that exists with no member; `undeclared` is no pool file at all, so today's shared login stands; both are distinct from a pool name the file lacks (case 10 t5) |
| D4 | **credential state** | `held` (keyrack has it, unlockable) · `absent` (pool names a key keyrack lacks) · `locked` (keyrack has it, and the headless unlock fails) · `dead` (expired or revoked: 401) · `cooled` (a provider 429 named a Retry-After) | the answers a `keyrack.get` + a call can give; each one is a different repair |
| D5 | **capacity read** | `fresh` (read since the last 15-minute tick) · `stale` · `unreadable` (probe throttled, header absent) | the probe is undocumented upstream, so its failure is a real path, not a hypothetical |
| D6 | **box** | `laptop` (a human at the keyboard) · `grove` (headless; a human only at an ssh tty, and only to fill) | the wish's whole point: a grove must never wait on a human paste |
| D7 | **time** | `first` · `repeat` (the same pick again) · `concurrent` (two clones spawn at once) | surfaces the idempotency and race cells a happy-path list skips |
| D8 | **clone liveness** | `not-yet-spawned` · `live` · `exited` | a live clone's env is frozen at spawn (`asBrainCliSpawnEnv.ts:61-74`), so `pick` writes a credential before the process starts and `rotate` rewrites it under a live one — two mechanisms. `exited` is where `wake` applies (case 10 t4) |
| D9 | **path variant** | `auto` (the actor's default pool, ranked) · `pool` (`--brain-pool`, ranked within it) · `pinned` (`--brain-reach`, no rank) | the three routes to a credential that S4 asks for; each crosses the rest of the space differently (a pinned clone is never moved) |
| D10 | **member tight window** | `5h-tight` (the 5h window is nearer its cap) · `7d-tight` (the week is nearer its cap) · `idle` (no open window: `resets_at` null) | the member grain of capacity. the rank keys each member by its tight window's reset (vision §4); a `7d-tight` member with a 5h reset soon is the cell where a naive "soonest reset" rank draws an account that caps on its week minutes later (case 3 t4). `idle` reads as "no data", never as "capped" |
| D12 | **member capacity** | `headroom` (its tight window is under its cap) · `capped` (at its cap: the banner, or `rate_limits` at 100%) | the per-member state the rank drops and the rotate fires on (case 4 t0). D4 `held` says the key works; D12 says whether it has room. D3 is this axis summed over the pool. a D10 `idle` member reads `headroom` by definition: no open window means no use against any cap, so the two axes stay orthogonal |
| D13 | **member draw** | `drawn` (≥1 live clone bills it) · `undrawn` (no clone bills it yet) | decides whether a healthy clone moves (fulcrum F5): onto an `undrawn` member whose window resets sooner, never onto one a peer already spends (case 4 t4 vs t5). distinct from D10 `idle`, which is a member with no open window |
| D11 | **verify outcome** | `landed` (the live status line names the new account) · `no-op` (the rewrite exited 0, the account did not change) | the two results a verify can report; each takes a different next step (case 4 vs case 6) |
| D14 | **usage credential state** | `held` (the reach's usage-scoped refresh token mints) · `locked-out` (a lost write-back left keyrack with a spent token) · `absent` (never captured for this reach) | the SECOND credential per reach (vision §3), apart from D4's setup-token a clone bills with: it governs only the capacity read, never the draw. a member whose usage credential is `locked-out` or `absent` stays drawable, read by its clones' status lines and the header probe (case 9 t2) |

## .the declared correlation — goal → actor

a goal names who can perform it: only an `operator` declares or fills; a `rotate` is performed by the
`clone host` (on the banner, the status line, or a 429), by `cron` (on the tick), or by an `operator`
at a tty who runs `rhx brains pool rotate` by hand — `--mode plan` to preview the moves, `--mode
apply` to make them, the same step the tick runs. this is a real
correlation, so the walk does not claim the full product. it walks each goal against the actors that
can perform it — and, per the first review, against the actor who **meets its refusal**: a `pick`
refused before the brain starts (cases 2, 5, 10) is met by the `operator` who ran the enroll, since no
clone yet exists.

## .the declared correlation — credential state → capacity

a member that is `absent`, `locked`, or `dead` (D4) answers no read, so it has no tight window (D10),
no capacity (D12), and no clone can draw it (D13 = `undrawn`). those crossings are **impossible** by
nature, not walked: such a member is shown with its state and its fix (case 8 t3) and dropped from
the rank. a `cooled` member keeps its last read, so D10 and D12 still apply to it, marked stale until
its Retry-After lapses. only a `held` or `cooled` member spans D10 × D12 × D13 in full.

## .the declared correlation — member capacity → pool state

D3 is D12 summed over the pool's members: `headroom` when ≥1 member reads `headroom`, `all-capped`
when every member reads `capped`, `empty` when there is no member to sum. `undeclared` sits outside
the sum: with no pool file there is no member set at all. the two stay separate axes
because they sit at different grains and fire different paths — D12 decides which member the rank
drops and which clone a rotate moves (case 4); D3 decides whether a pick may return aught at all
(case 5). a walk crosses D3 only with D12 values that sum to it.

## .the walk

the unconstrained product is 4 × 6 × 4 × 5 × 3 × 2 × 3 × 3 × 3 × 3 × 2 × 2 × 2 × 3 = 5,598,720 tuples. the correlations above
and the axes each goal ignores collapse it to the rows below; each row is walked by group in the
inventory (`1.vision.experience.case=_.md`), and a group lists every value of each axis it spans.

| goal | actors (perform · meet a refusal) | axes that vary for it |
|---|---|---|
| declare | operator | D3 {`empty`, `undeclared`}, D6 — D4 collapses: a declare reads no keyrack, so the inventory itemizes each D4 row only to show the pick it becomes (case 2, case 7) |
| fill | operator | D4 {absent → held, dead → held, held → held}, D6 |
| read | operator, cron | D3, D4, D5, D7, D10, D14 |
| pick | clone · operator (refusal at spawn) | D3, D4, D5, D6, D7, D9, D10, D12 — D8 fixed `not-yet-spawned` |
| rotate | clone host, cron, operator (by hand, `--mode plan` or `apply`) | D3, D4, D5, D7, D9, D10, D12, D13 — D8 fixed `live` |
| verify | clone host, cron | D4 {held, dead}, D11 — D8 fixed `live` |
| pick, on a `wake` | operator | D9 — D8 fixed `exited` |

# 🌙 dream: the sdk `keyrack.get` holds a github-app key in os.secure, at the acceptance grain

- kind = feat
- owner = ehmpathy/rhachet (keyrack sdk acceptance)
- caught = 2026-11-16

## .the cue that fired

peer round i001 of `5.3.verification` on `beav/feat-keyrack-github-app-off-ec2`, r001 nitpick.1:
the off-ec2 mint scenarios are proven at the cli only, while `keyrack.get` is also an sdk surface.

## .the gap, precisely

the pr's new surface, `keyrack set --source @stdin`, is cli-only; the sdk has no `set`. but the
sdk's `keyrack.get({ with: { unlock: true } })` reaches the same github-app mint from os.secure,
and no `blackbox/sdk` suite holds that path.

## .the shape of the fix

a `blackbox/sdk/keyrack.githubApp.acceptance.test.ts` files a blob for an app no github app holds
via the cli pipe, then calls the sdk `keyrack.get` with unlock from a node child process, as the
`keyrack.get` sdk suite does, and asserts the real github's 404 refusal and its cure reach the sdk
caller as a locked grant, with no key echoed.

## .why it is not done in this round

the pr adds no sdk surface and leaves the sdk `get` path unchanged; the cli suites hold the route.
a nitpick, conceded at `better` severity.

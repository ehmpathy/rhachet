# 🌙 dream: a temp repo's bun install stalls under a full acceptance run

kind = fix · owner = rhachet (blackbox test infra) · caught 2026-10-26

## .the cue that fired

one full `upgrade` acceptance run (`git.repo.test --what acceptance --scope path://blackbox/cli/upgrade`)
went 101 passed, 28 failed. all 28 sat in `upgrade.default-actor-migration.journey.acceptance.test.ts`,
and every one failed the same way:

```
spawnSync /bin/sh ETIMEDOUT
  at execSync('bun install', { cwd: repoPath, stdio: 'inherit', timeout: 120000 })
  blackbox/.test/infra/genTestTempRepo.ts:145
```

then the cascade: `usePrep: tried to access value before setup completed`, once per `then`.

the same file, alone, right after: 28 passed, 0 failed, 285s.

## .the gap, precisely

- `genTestTempRepo` with `install: true` runs `bun install` with a 120s timeout, three tries, 2s apart
- under a full parallel acceptance run, three installs in a row each ran past 120s
- ⇒ one slow registry window or a starved box fails a whole journey file at setup, before any
  assertion runs. the fault reads as 28 product defects and is none
- the retry does not help against a slow window: three tries inside ~6 minutes meet the same window

## .the shape of the fix

- measure first: log each attempt's duration and exit, so a stall and a hard fail read apart
- then one of:
  - a shared install cache warmed once per run in globalSetup (`howto.put-per-run-test-setup-in-globalsetup`),
    so each temp repo links from a warm store and never reaches the registry
  - or a longer per-attempt timeout with backoff between tries, if the measure shows a slow registry
    and not a hang
- a clamp: a case that forces a first-attempt stall and asserts the retry recovers, or fails loud
  with the attempt durations named

## .why it is not done in this round

- safe: yes. clean: no. `genTestTempRepo` serves every acceptance suite; a change to how it installs
  moves the setup of each one, and the fix wants a measure before a shape. this pr does not touch it
- the run that stalled is not this pr's code: the journey passed 28/28 alone at the same build

# 🌙 dream: the 8 perf suites starve a co-scheduled network install past its 120s limit

**kind** = repair
**owner** = this repo (`ehmpathy/rhachet`) — test infrastructure
**caught** = 2026-09-07

---

## .the cue that fired

the `5.3.verification` gate demanded zero skips. the acceptance tier reported **8 skipped**, gated on
`RUN_PERF_TEST`, so I spent the lever the gate implied and re-ran the full tier with `PERF=true`.

**the 8 rows ran and all 8 passed.** but the run went from `0 failed` to `7 failed` — and none of
the 7 was a perf row.

## .the gap, precisely

with `PERF=true`, `blackbox/cli/upgrade.acceptance.test.ts` `[case4]` fails in **setup**:

```
● rhachet upgrade › given: [case4] repo with rhachet-roles-ehmpathy@1.17.20 installed
    spawnSync /bin/sh ETIMEDOUT

    > 122 |         execSync('bun install', {
          |                 ^
      123 |           cwd: repoPath,
      124 |           stdio: 'inherit',
      125 |           timeout: 120000, // 2 minute timeout

      at genTestTempRepo (blackbox/.test/infra/genTestTempRepo.ts:122:17)
```

that is **1 root failure + 6 cascades**, each of the 6 reporting
`UnexpectedCodePathError: usePrep: tried to access value before setup completed` — the downstream
`then` rows reach for a `scene` that setup never produced.

🚨 **the setup already retries, and all three attempts timed out.** the loop at
`genTestTempRepo.ts:120` is `for (let attempt = 1; attempt <= 3; attempt++)`, each with a 120s
limit — so the install was given **360 seconds** and never completed.

### the isolation that proves it is contention, never the registry

I did **not** re-run the failed command in hope of green. I ran a **different** command that removes
one variable — the co-scheduled perf load — and holds the rest:

```
$ rhx git.repo.test --what acceptance --against local --env test --mode apply --scope 'path://upgrade.acceptance' ; echo "exit=$?"
   ├─ files
   │  └─ blackbox/cli/upgrade.acceptance.test.ts
   ├─ status
   │  └─ 🎉 passed (53s)
   ├─ stats
   │  ├─ suites: 1 files
   │  ├─ tests: 78 passed, 0 failed, 0 skipped
   │  └─ time: 53s
exit=0
```

| condition | `bun install` in setup | result |
|---|---|---|
| co-scheduled with the 8 perf suites | ✗ `ETIMEDOUT` × 3 attempts (360s) | 7 failed |
| alone | ✓ well inside one attempt | **78 passed, 0 failed** — whole suite in **53s** |

⇒ **the whole suite finishes in 53s uncontended, and its install alone cannot finish in 360s
contended.** that is not a slow registry and it is not a flaky test. it is starvation.

### why the perf suites are the starver

each of the 8 spawns the compiled binary **30 times** and asserts a wall-clock average
(`measureAverageMs({ runs: 30, … })`). eight of those in parallel is ~240 process spawns that
compete for the same cpu and disk as a network install which must unpack a dependency tree.

## 🚨 .the correction — measured later the same day, and it narrows the fix

**the claim that this fires only under `PERF=true` is refuted.** a later run of the plain default
command reproduced it with the perf rows **skipped**:

```
$ rhx git.repo.test --what acceptance --against local --env test --mode apply
   ├─ tests: 3115 passed, 7 failed, 8 skipped
```

the **8 skipped** ARE the perf rows, so they did not run — and the signature is identical:
`spawnSync /bin/sh ETIMEDOUT` at `genTestTempRepo.ts:122`, one root plus six `usePrep` cascades.

the isolation held too, on the same case alone:

```
$ rhx git.repo.test --what acceptance … --scope 'path://upgrade' --scope 'name://case4'
   ├─ tests: 7 passed, 0 failed
   └─ time: 19s
```

⇒ **the starver is the ordinary 123-suite parallel tier, never the perf rows alone.** the perf rows
aggravate the contention; they are not required to produce it.

🔴 **this narrows the fix below.** option 1 (perf rows serial) would NOT have prevented this run, so
it is necessary and **not sufficient**. whatever a taker picks must protect a network install from
the tier's OWN default parallelism — the most direct shape is to stop `genTestTempRepo`'s install
from contention with its neighbours at all (a pre-warmed store, or an offline fixture), rather than
to re-order one class of neighbour.

## 🔴 .why this matters beyond a local flag

```ts
// blackbox/.test/infra/RUN_PERF_TEST.ts:9
export const RUN_PERF_TEST = !!(process.env.CI || process.env.PERF);
```

**`CI` turns them on.** so the exposure is not confined to a developer who opts in — the condition
that produced 7 failures here is the **default condition in ci**, and ci runners are typically
smaller than a dev box, not larger.

⚠️ **I have no ci measurement, and I will not infer one.** what is established is the mechanism and
the flag that enables it; whether ci currently flakes on it is unmeasured and is the first item a
taker should check (`gh run list` over the acceptance job).

## .the shape of the fix

three candidates, and the choice is a real tradeoff rather than a lookup:

| option | what it costs |
|---|---|
| **run the perf suites serially** (a jest project/shard that pins `maxWorkers: 1` for `*.performance.acceptance.test.ts`) | most correct — a wall-clock benchmark under parallel load measures the load, not the subject. costs tier wall-clock |
| **raise `genTestTempRepo`'s install timeout** | 🔴 papers over. it does not make the install faster, it just waits longer, and it leaves the benchmark on a contended box |
| **shard perf away from install-heavy suites** | `jest.acceptance.shards.jsonc` already exists, so the mechanism is present; needs a rule that keeps the two classes apart |

⇒ **option 1 repairs both halves at once** — it stops the starvation AND it makes the perf numbers
mean what their thresholds claim. a benchmark co-scheduled with 100+ other suites does not measure
`roles boot`; it measures the machine.

## .why it is not done in this round

- **not safe·clean.** it changes jest scheduling for the whole acceptance tier — the blast radius is
  every suite's runtime and every threshold's sense. that is not a fix that rides a diff about a
  native addon's install
- **out of scope.** the wish is node-pty on linux. `genTestTempRepo.ts` is untouched by this branch
  (`git status` shows `blackbox/.test/infra/invokeRhachetCliBinary.ts` and
  `spawnRhachetCliBackground.ts` modified; `genTestTempRepo.ts` is not) — `rule.forbid.scope-leaks`
- **the option choice is a real judgment**, and option 1 changes what every perf threshold means.
  that is an owner's call, not a rider on an unrelated pr

## ⚠️ .what this does NOT excuse

**the branch did not introduce this.** `genTestTempRepo.ts` is untouched by it, and the timeout
fires in setup BEFORE the cli under test is ever invoked — so no change to `execNpmInstallLocal`,
`execUpgrade`, or the resolvers can reach it. this dream is a **discovery**, never a regression.

⚠️ **but it does NOT excuse a green claim on the default run.** the correction above measured
`7 failed` with no `PERF` set, so the earlier *"the default acceptance run is `0 failed`"* is
withdrawn. what holds is narrower and checkable: the seven are **one** transient setup timeout plus
six `usePrep` cascades, and the same seven pass in **19s** when run alone.

and it retires one claim outright: *"the 8 perf rows are opt-in locally"* is true and
**incomplete**. they are opt-in locally **and on by default in ci**, and the reason they deserve a
gate is not that they are slow — it is that they **destabilize their neighbours**.

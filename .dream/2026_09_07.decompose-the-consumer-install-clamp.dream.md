- **owner** = `ehmpathy/rhachet`

## .the cue that fired

the r004 `arch-opport-decomposition` lane, at i076 (scoped re-run), nitpick.2:

> `genConsumerInstall` … is one ~400-line procedure that: writes manifests, spawns `pnpm pack`,
> spawns the install, parses install output, re-derives the pnpm version, scans the global dir,
> writes + spawns a probe, parses the probe verdict, and computes `prebuiltOnDisk`/`builtOnDisk`.

it closes by noting that the orchestration is glued into one body rather than decomposed into
named communicator/transformer steps that could be reused or reordered.

## .the gap, precisely

`src/domain.operations/clone/pty/getPtyModuleOrNull.consumer.integration.test.ts`, from line 500.

the lane's read of the SHAPE is correct and its read of the STATUS is not — worth both stated,
since the second is what makes this a refactor rather than a deletion:

| the lane's claim | measured |
|---|---|
| *"single monolithic orchestrator"* | ⚠️ **15 call sites** across 9 `given` cases. it is the most-reused artifact in the file, which is exactly what earns an abstraction — the nitpick is about its INTERNAL fusion, never about whether it should exist |
| many independent reads fused into one wide result | ✅ true. version-pin confirmation, install outcome, and probe outcome are three separable axes returned as one object |
| hard to evolve one axis without a touch of the whole | ✅ true. the probe's byte-vs-exit verdict cannot be changed without a read of the install path |

## .the shape of the fix

split along the three axes the result object already implies, each a named step in its own
right:

1. **`genConsumerProject`** — writes the manifest + `packageManager` pin, packs the parent
   (`pnpm pack`), returns the project dir and the tarball path
2. **`execConsumerInstall`** — spawns the install for a `(target, packageManager)` pair and
   returns its raw outcome: exit code, stdout, stderr
3. **`asPnpmVersionRanFromInstallOutput`** — already extracted; keep as is
4. **`asBuildGateVerdictFromInstallOutput`** — the gate-fired / ignored-builds read, today
   inline and duplicated across the local and global branches
5. **`execPtyLoadProbe`** — writes the probe file, spawns it under `process.execPath`, returns
   its verdict; this is the axis the lane singles out as hardest to evolve
6. **`getPtyAddonPresence`** — the on-disk scan that yields `prebuiltOnDisk` / `builtOnDisk`

then `genConsumerInstall` becomes an orchestrator that composes those six and returns the same
wide object, so **no call site changes** — which is what makes the refactor checkable: the 15
sites and their assertions stay byte-identical, and a green run means the decomposition
preserved behavior.

## .why it is not done in this round

⛔ **the SAFE half fails, and it fails on a credential block rather than on judgment.**

this file is the clamp that holds the wish's acceptance #1 and #4 — the red-at-`1.1.0` /
green-at-`1.2.0-beta.15` proof and the `pnpm add -g` consumer-path rows. it runs at the
INTEGRATION tier, and that tier is unreachable at this head:

```
✋ keyrack unlock
   └─ aws sso login timed out
      └─ human did not respond to browser sso prompt
```

⇒ a ~400-line decomposition of the one artifact that carries the wish's proof, applied with
**no ability to run it**, is the change most likely to break a proof silently while types and
lint stay green. a refactor whose whole safety argument is *"the assertions are unchanged, so a
green run proves it"* cannot be landed in a round with no green run available.

the CLEAN half passes — the fix is additive and touches no caller — so this is a deferral for
**safety alone**, and it retires the moment the integration tier is reachable.

⚠️ per `rule.always.catch-dreams-for-followups`, a deferral for dirt owes a fulcrum too. this
one is deferred for an **unrunnable gate**, never for ripple, so no fulcrum is owed — the
decision is not a design call, it is a measurement of what this round can verify.

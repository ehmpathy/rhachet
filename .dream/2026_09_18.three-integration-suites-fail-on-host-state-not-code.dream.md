### 🔴 .extended 2026-09-19 — FIVE keyrack acceptance suites, and the cause is UNDIAGNOSABLE from their output

the full-tier triage found the same host-state class at the acceptance grain, across five suites:

| suite | rows red |
|---|---|
| `blackbox/sdk/keyrack.get.acceptance.test.ts` | 23 of 32 |
| `blackbox/sdk/keyrack.source.acceptance.test.ts` | — |
| `blackbox/sdk/keyrack.source.is-optional-if-has.acceptance.test.ts` | — |
| `blackbox/sdk/keyrack.machine-wide-skips-manifest.acceptance.test.ts` | — |
| `blackbox/sdk/keyrack.reach.acceptance.test.ts` | — |

🔴 **the signature is a trap.** every row on a **grant** path exits 1; every row on a **refusal**
path passes — a refusal returns before the crypto or the daemon is reached. so the suite reports
*"the error cases work, the happy cases are broken"*, which reads exactly like a real regression in
the feature under test. it is not: the same split appears with an untouched keyrack tree.

#### 🔴 the real defect is that the cause CANNOT be read from the failure

each suite spawns a child, captures `stderr`, and **asserts only on `status` and `stdout`**. so the
child's own explanation is collected and thrown away:

```ts
return { status: spawnResult.status, stdout: spawnResult.stdout, stderr: spawnResult.stderr };
...
then('exits with code 0', () => { expect(result.status).toEqual(0); });   // stderr never read
```

⇒ the reader gets `Expected: 0 / Received: 1` and **not one character of why**. 23 red rows, zero
diagnostic content.

⚠️ **and that is what makes the cause genuinely unsettled here.** two host facts are each sufficient
to produce this exact split, and the suites distinguish them not at all:

| candidate | status |
|---|---|
| the keyrack **daemon** cannot bind its socket | 🔴 **measured in a prior round** — `connect EINVAL … connectToKeyrackDaemon`, quoted verbatim |
| the **`age` binary is absent** (`which age` → `age not found`), and it gates the crypto path (`sshPrikeyToAgeIdentity.ts:90`, `ageRecipientCrypto.ts`) | 🟡 **host fact confirmed; NOT tied to these five suites by measurement** |

🔴 **the second row is an inference and is labeled as one** (`rule.forbid.mechanism-inferred-from-outcome`).
`age` really is absent on this host, and it really does gate the grant path — but no measurement
here shows it is what these five suites hit. **a plausible mechanism that fits the outcome is not
the mechanism.**

⇒ so the honest finding is not *"`age` is missing"*. it is: **a suite that discards the child's
stderr cannot tell two host defects apart**, and the repair below is owed before any diagnosis of
which one it is.

### 🟡 .extended 2026-09-19 — two more host-state classes, both snapshot drift

the same triage found two failures that are neither an env leak nor an absent binary. they share a
shape: **a snapshot pinned to a value the HOST supplies.**

| # | suite | what it pins | the drift |
|---|---|---|---|
| 5 | `blackbox/sdk/genContextBrain.discoveryNotFound.realRegistry.realnode.acceptance.test.ts` | the **installed** brain registry, verbatim | a dependency bump added `fireworks/glm/5.3`, `fireworks/kimi/k3`, `fireworks/glm/5.3-flash` and dropped two ⇒ `(and 6 more)` → `(and 8 more)` |
| 6 | `blackbox/sdk/importEsmSafe.realnode.acceptance.test.ts` | node's cjs/esm interop key set | the runtime now enumerates `"module.exports"` beside `default` |

🟡 **#5 is the more defensible of the two**, and its own comment says why — it is a `realRegistry`
suite whose whole claim is *"driven against the REAL installed registry"*. ⇒ so the drift is the
subject, and the defect is that it is pinned **verbatim** rather than by an invariant (a header, a
count bound, one known-present brain). its peer rows that assert exactly that (`the message
enumerates the real registry (header + a real brain)`) **stayed green** — the shape is already in
the file, one row up.

🔴 **#6 is the sharper one, because it pins somebody else's contract.** `"module.exports"` is a node
interop detail, so the snapshot fails on a node upgrade and reports it as a defect in
`importEsmSafe` — which behaved correctly, and whose eight behavioral rows all passed.

⇒ both take the same repair as #5: **assert the invariant the suite is about, and let the host's
value vary.** a snapshot is the right instrument for a surface WE render and the wrong one for a
surface a dependency renders.

the rules: `rule.require.hermetic-tests` (a test must not depend on host state) and
`rule.forbid.bare-host-deps` (a suite must not require an un-provisioned binary), both
`code.test/pitofsuccess.portability/`.

### 🔴 .extended 2026-09-20 — a SEVENTH class: a threshold pinned to a host's throughput

measured at `5.1.execution` while a third perf suite was authored. it is the same family as #5/#6 —
a value the HOST supplies, pinned as though we owned it — but the pinned quantity is neither a

| # | suite | what it pins | the drift |
|---|---|---|---|
| 7 | `blackbox/cli/roles.boot.performance.published.acceptance.test.ts` | `avgMs < 250` — **this host's throughput**, as a literal | 🔴 measured **1061ms ALONE, uncontended — 4.2x over** |

🔴 **the trap is that it reads as contention and is not.** a co-scheduled run shows it red beside

(`.dream/2026_09_07.perf-suites-starve-a-cosheduled-network-install`). the **alone** column refutes

```
1061ms alone  →  955ms paired  →  621ms with three
```

⇒ **it gets FASTER under more load.** a starved benchmark cannot do that, so the bound does not
measure this machine at all. ⚠️ its peer `collocated` **is** a genuine contention case (passes
alone, 406ms paired) — so the two sit in one file-name family, fail in one shape, and belong to two
different dreams.

🟡 **and this class is worse than #5/#6 for the reader, not better.** a drifted snapshot prints a
diff that names the field which moved; a drifted threshold prints `Expected: < 250 / Received:

*"is this mine?"* cost this dream was written to record.

⇒ the repair is the one #5/#6 take, in the one form a latency assertion permits: **assert a ratio
against a baseline the suite measures in-process**, never a literal fitted to the author's box. the
third suite added in that round does exactly this — both its bounds are ~3.7x over a measured
baseline — and it is the only one of the three that passes alone.

## .the shape of the fix

one repair per class, and the classes do not share one:

1. **the env leak (#1)** — scrub `RHACHET_CLONE_*` from the child env the suite spawns, in that
   suite's own infra rather than at each call site. the case that asserts *"outside a clone"* must
   construct that condition rather than assume it
2. **the host binary (#2, #3)** — decide one contract for an absent `age` and hold it in both suites.
   the extant pair already disagrees: #2 has a `[t1] age CLI is NOT on PATH` arm that is green, so
   the capability to run without it exists and #3 refuses to use it. ⚠️ a **silent skip** is
   forbidden here (`rule.forbid.failhide`) — the sanctioned shape is a `ConstraintError` that names
   the install command, which #3 nearly has and throws at the wrong scope
2b. 🔴 **the discarded stderr (the five keyrack acceptance suites)** — surface the child's `stderr`
   in the failure. the cheapest form costs one argument: assert the pair rather than the code, e.g.
   `expect({ status: result.status, stderr: result.stderr }).toEqual({ status: 0, stderr: '' })`,
   so a red row prints the child's own words. ⚠️ **this is owed BEFORE the cause is named** — it is
   what makes the cause nameable at all, and with it the daemon-vs-`age` question above is settled
   by reading one failure rather than by a diagnosis pass
3. **the socket syscall (#4)** — read whether `chmod` is reachable at all on the runner's filesystem,
   then assert the syscall the platform actually produces rather than the one the author's did
4. 🔴 **the host-supplied snapshot (#5, #6)** — replace the verbatim pin with the invariant the suite
   is about. #5 already carries the shape one row up (`header + a real brain`); #6 wants a subset
   assertion on the keys it cares about rather than a whole-object snapshot

⇒ and one clamp over all five: a **cicd-parity check** that fails loud when a suite's outcome
depends on a variable the repo does not provision.

🔴 **the clamp is what makes this worth the dream.** five distinct classes, eleven suites, and the
one property they share is that **each was diagnosed by hand, after the fact, by a reader who had
to first rule out their own diff.** the triage that produced rows 5 and 6 spent its whole cost on
that question — *"is this mine?"* — and answered no, eight times.

🔴 **and #2b is the one to do first, because it is the only repair that lowers the cost of the
next diagnosis.** the other four each fix one suite; 2b fixes the **reading** of every keyrack
failure thereafter — which is why a triage that could not name the keyrack cause is still a triage
that found the real defect.

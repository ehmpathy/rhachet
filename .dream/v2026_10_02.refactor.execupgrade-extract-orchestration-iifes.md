# 🌙 dream: extract `execUpgrade`'s two orchestration IIFEs into named operations

- kind = refactor
- owner = ehmpathy/rhachet
- caught 2026-10-02, at `.behavior/v2026_09_17.feat-boot-manifest-and-budget` stone `5.1.execution.from_vision`

## .the cue that fired

peer review i036, `enroll-impl-arch-defects` nitpick 1: `execUpgrade.ts` holds two sizable
orchestration sequences as anonymous IIFEs inside the exported function.

## .the gap, precisely

`src/domain.operations/upgrade/execUpgrade.ts`:
- `upgradedGlobal` — attempts the global install and classifies its failure
- `boots` — re-inits linked roles, re-renders brain-dir boots, syncs hooks

neither can be tested apart from the whole of `execUpgrade`, so a change to one (a new upgrade
target, a reorder of boot and hook sync) must be reasoned about across the full function.

## .the shape of the fix

1. `execGlobalUpgradeOrAbsorb({ whichTargets }, context)` — the global install plus its failure
   classification, which returns the same shape `upgradedGlobal` holds today
2. `syncRolesAfterUpgrade({ whichTargets, roleExpanded }, context)` — the re-init, the boot
   re-render, and the hook sync, which returns `{ boots, hookErrors }`
3. `execUpgrade` composes the two; its test narrows to the composition, and each new operation
   gets its own test

## .why it is not done in this round

safe, but not clean: two new operations and their tests, plus a reshape of `execUpgrade.test.ts`,
in a flow this feature only extends. the deferral is a judgment, recorded as fulcrum F68.

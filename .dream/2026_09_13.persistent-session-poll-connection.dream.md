# 🌙 dream: the say poll loop holds one authenticated connection, over reconnect-per-tick

- **kind**: feat
- **owner**: ehmpathy/rhachet (this repo)
- **caught**: 2026-09-13

## .the cue that fired

i004 r011 (arch-defects) item 1: `getCloneSayObservation`'s poll loop opens a brand-new
socket connection every `pollMs`, and each connection re-runs the same-user auth
(`isCallerSameUser` → `getSocketPeerCred`), which shells `sh → ss -xp → grep` and scans the
WHOLE host's unix socket table. worst case (`say --await release`, ~60 polls over the 15s
bound) that is ~180 spawned processes + ~60 whole-host scans, worse under concurrency — a
direct hit on the wish's "cheap, pollable read channel" thesis.

## .the gap, precisely

`getCloneInputState` is a one-shot: `connectToClone` → send one frame → `finish` destroys the
socket. the poll loop calls it repeatedly, so the per-call connect + per-connection auth cost
multiplies by the poll count. the cost is bounded (default `--await enqueue` short-circuits at
~2 cycles) but real on `--await release` against a busy brain.

## .the shape of the fix

1. add a session-scoped read: authenticate once, hold the connection open, send repeated
   `probe` frames over it, close at the end of the poll loop
2. `getCloneInputState` stays the one-shot API (pre-dispatch baseline + any standalone caller)
3. the poll loop in `getCloneSayObservation` uses the session variant
4. the natural home is the shared client-wire communicator of the coupled dream
   (`extract-shared-clone-wire-communicator`) — the persistent-session mode lands there
5. a regression clamp that proves the loop opens ONE connection, not N (spy the connect count)

## .why it is not done in this round

it clears the ONE bar `rule.forbid.deferrals-short-of-a-dedicated-pr` leaves open: a massive
dirty refactor that deserves its own dedicated PR. it is not a scope-cut, a rule-of-three, or a
measurement-gate (the three excuses that rule forbids) — it is a wire-LAYER rework:

- it re-shapes the exchange lifecycle from ONE connect→write→settle→destroy into a MULTIPLEXED
  held connection — authenticate once, send N `probe` frames over the SAME socket, read N
  framed replies, close at the end of the poll loop. that is a different frame contract
  (request/reply correlation, mid-session liveness, cleanup-on-abort), not a parameter tweak
- it lands in `exchangeOnCloneSocket` (now extracted) AND changes `getCloneSayObservation`'s
  poll loop AND touches the connect-send-destroy contract `getCloneInputState` rests on — a
  ripple across three files with its own review surface (multiplexed frame correctness)

⇒ it fails the CLEAN test (`rule.always.fix-forward-under-scouts-honor`) and must not land late
in this stone with no independent review. the decision to defer is recorded as fulcrum F14.

**and the reconnect-per-tick loop is correct to ship now:** it is a bounded OPTIMIZATION, never
a correctness fix — the default `--await enqueue` short-circuits at ~2 cycles, and the
per-connection auth cost PREDATES this wish. to ship it is defensible; the session mode is a
follow-on PR, not a gap this PR leaves broken.

## .also folded in — the per-probe read cost (r011 i006 informational)

i006 r011 (arch-defects) informational item: independent of the reconnect auth cost, each probe
call also does an `O(scrollback)` grid materialization — `readScreen` runs `translateToString`
per row (up to `scrollback: 1000`) and `computeCloneInputState` scans lines with
`countNeedleInLines`. this compounds F14's per-tick cost on the `--await release` path.

⇒ note: this stone's r011-i006-n1 fix already narrowed the `countOnScreen` scan to the live
VIEWPORT (never the full scrollback), so the needle scan is now viewport-bounded. what remains
`O(scrollback)` is the `readScreen` materialization itself (`translateToString` per buffered row).
so the eventual option-A rework should ALSO bound the scrollback materialization per probe — not
only the connection lifecycle. F14 owns this; recorded here so the rework bounds both.

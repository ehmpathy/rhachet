## .the cue that fired

a local `declapract upgrade` rewrote `.husky/` in this tree. peer review of the route that carried it
(r4 blocker.3, r7 blocker.1, r9 nitpick.1) flagged `.husky/check.timestamps.lock.sh`.

## .the gap, precisely

- `timestamps_lock_halt "$TIMESTAMPS_LOCK_DISK" 'on disk'` passes two positional args, read as
  `$1` / `$2` (`rule.forbid.positional-args`)
- the `.why` header drops its copula mid-claim: "a timestamp in a tracked file a privacy leak"
- the `⛔ do not edit` line shouts where a plain `.note` would serve

## .the shape of the fix

in the practice's husky template:

- name the args: `timestamps_lock_halt found="$x" where='on disk'`, parsed by `key=value`
- repair the header to "a timestamp in a tracked file is a privacy leak"
- recast the warn as `.note = the only sanctioned change is a practice upgrade, which rewrites both`
- re-stamp `TIMESTAMPS_LOCK_EXPECTED`, since the lock pins the hook's blob id

## .why it is not done in this round

the files are practice-owned and blob-locked: a hand edit here trips the lock, and the next upgrade
reverts it. they ship as the practice emits them, beside the `declapract-typescript-ehmpathy` bump
that carries them; the practice owns the repair.

# 🌙 dream: should a skill under `.scratch/` or `.archive/` reach the boot corpus?

- kind  = ask
- owner = ehmpathy/rhachet
- caught 2026-09-24

## .the cue that fired

a peer review asked why `asRoleSkillFiles` had no unit test while its brief-side peer
`asRoleBriefFiles` did. the test got written — and the act of authorship surfaced a
difference between the two that no test, review, or docblock had named.

## .the gap, precisely

the two are declared peers. `asRoleSkillFiles.ts` says so in its own `.why`:

> the peer of `asRoleBriefFiles`, so the boot renderer splits a role dir by name

but they do not treat the same dirs the same way:

| operation | drops `.scratch/` and `.archive/` |
|---|---|
| `asRoleBriefFiles` | ✅ yes, with a stated `.why`: *"a `.scratch/` or `.archive/` brief must never reach a boot corpus"* |
| `asRoleSkillFiles` | 🔴 no — a bare `startsWith(skillsDir)` |

⇒ so a draft skill at `skills/.scratch/draft.sh` reaches the corpus today, while a draft
brief at `briefs/.scratch/draft.md` does not. the reason the brief peer gives — a
work-in-progress artifact must not ship to a clone — applies verbatim to a skill.

⚠️ it is an **ask**, not a fix, because the asymmetry may be deliberate and undocumented:
a skill is executable, and a `.scratch/` skill dir may simply be a convention nobody uses,
so the filter would guard a case that never arises.

## .the shape of the fix

if the answer is *"yes, drop them"* — lift the block-list out of `asRoleBriefFiles` into a
shared `isRoleResourceDirBlocked`, and call it from both:

```ts
// src/domain.operations/boot/isRoleResourceDirBlocked.ts
const DIRS_BLOCKED = ['.scratch', '.archive'];
export const isRoleResourceDirBlocked = (input: { file: string }): boolean =>
  DIRS_BLOCKED.some((dir) => input.file.includes(`/${dir}/`));
```

then flip the pinned case in `asRoleSkillFiles.test.ts` (the `.scratch/` row, which
records the current behavior on purpose) from kept to dropped.

if the answer is *"no, leave it"* — the fix is a `.note` on `asRoleSkillFiles` that says
why the peer relationship stops short of the block-list, so the next reader does not read
it as an oversight, and the test's pinned row cites that note rather than this dream.

## .why it is not done in this round

- **SAFE?** 🔴 no. it changes what reaches a live boot corpus, and the answer to *"does a
  `.scratch/` skill exist anywhere today?"* is unknown. a silent drop of a skill a role
  depends on is a worse defect than the one it would fix.
- **CLEAN?** ✅ yes — one shared predicate, two call sites, one test row.

⇒ unsafe, so it defers. the round it surfaced in carried a 0-blocker judge threshold and
this is a behavior change, not a coverage gap, so it is not the round to make it in.

# 🌙 dream: a contended on-disk key lock must read as a lost race, never a mutex fault

- kind = reseed
- owner = ehmpathy/simple-on-disk-cache (local key lock) · ehmpathy/with-simple-mutex (acquire classify)
- caught 2026-11-16

## .the cue that fired

a 5.3 integration run of `src/infra/lock` on the brains auth branch (the same suites ran green at
5.1, 94 of 94): `withFileMutex` and
`withHostMutex` [case1], twenty bumps on one key at once, each failed with
`💥 MalfunctionError: withSimpleMutex: the cache backend faulted while it acquired the lock`. the
cause was `UnexpectedCodePathError: could not acquire the local cache key lock within 5s`. the
same three suites, rerun on a quieter box, passed 18 of 18.

## .the gap, precisely

- `simple-on-disk-cache` wraps each conditional `set` in a per-key file lock with a fixed 5s
  deadline, and no option sets it
- under heavy same-key contention a put-if-absent can wait past that deadline. the backend then
  throws a bare `UnexpectedCodePathError`, not a `SimpleCacheConditionError`
- `with-simple-mutex` treats only a condition error as a lost race; all else is a fault. so a
  contended acquire, which should poll until its own two-minute bound, fails at once as a malfunction
- the failure is load-dependent, so it surfaces as a flake in a parallel ci run

## .the shape of the fix

- in `simple-on-disk-cache`: a key-lock timeout inside a conditional write throws a typed,
  exported contention error (or the condition error itself, since no write happened)
- in `with-simple-mutex`: classify that contention error as a lost race and poll on
- then rhachet bumps both, and `withFileMutex` needs no change
- a clamp, upstream: many concurrent put-if-absent calls on one key under a short key-lock
  deadline; assert each either wins or polls, none faults

## .why it is not done in this round

the fix sits in two other repos. a local catch in `withFileMutex` would have to match the error by
its message text, a brittle seam over a dependency's misclassification. see fulcrum F23.

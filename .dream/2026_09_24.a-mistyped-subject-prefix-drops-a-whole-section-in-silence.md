# 🌙 dream: a mistyped `subject.` prefix drops a whole section in silence

- **kind** = fix
- **owner** = `ehmpathy/rhachet` (this repo)
- **caught** = 2026-09-24, at `5.1.execution` i020, by `enroll-impl-arch-defects` nitpick.2

---

## .the cue that fired

this round built `assertNoInertBudget` + `isBootSectionKey` for one reason: a mistyped top-level
`budget` key is swallowed by the zod catchall, parsed as a subject section, and means **naught**.
the guard makes that loud.

⇒ the reviewer pointed two lines away in the same file: **a mistyped `subject.` prefix hits the
identical hazard, and no guard covers it.**

---

## 🔴 .the gap, precisely

`src/domain.objects/RoleBootSpec.ts`:

```ts
export const schemaRoleBootSpecSubjected = z
  .object({ always: schemaSubjectSection.optional() })
  .catchall(schemaSubjectSection);
```

the catchall accepts **any** top-level key as a subject section. downstream, only keys that carry
the `subject.` prefix survive the filter in `parseRoleBootYaml`. so:

| the author typed | what happens |
|---|---|
| `subject.security:` | ✅ parsed, booted under `--subject security` |
| 🔴 `subjet.security:` | **validates cleanly, then is filtered away.** the section never boots, and no line says so |

⇒ **it is the exact shape `assertNoInertBudget` exists to forbid**, at the adjacent key. the spec
is accepted, the author believes a section is declared, and the payload silently omits it.

🔴 **and the budget gate sharpens the cost.** a dropped section is a smaller payload, so a spec
with a typo'd subject **passes a cap it should have breached** — a silent pass, which is precisely
what requirement 2 exists to refuse.

🟡 **it is not a regression this behavior introduced.** the catchall predates it. what this round
changed is that one adjacent key now has a guard and this one does not, so the asymmetry is newly
visible.

---

## .the shape of the fix

the repair is a **closed top-level key set** rather than a fuzzy near-miss check:

1. enumerate the legal top-level keys — `always`, `briefs`, `skills`, `budget`, and `subject.*`
2. refuse any other top-level key at parse, with a `ConstraintError` that names the key it found,
   the path it found it in, and the legal set (`rule.require.errors-name-the-fix`)
3. reuse `isBootSectionKey` — it already answers *"is this a section key?"*, which is the same
   question one negation away
4. clamp it: a fixture whose spec carries `subjet.security:` must refuse, and a fixture whose spec
   carries `subject.security:` must boot. the pair brackets the predicate from both sides

⚠️ **a fuzzy edit-distance check is the wrong instrument.** it cannot part a typo from a section a
repo deliberately named, so it would refuse legitimate specs. the closed set is decidable.

---

## .why it is not done in this round

**it fails CLEAN** (`rule.always.fix-forward-under-scouts-honor`). the catchall sits on the parse
path **every extant boot flows through** — the one path requirement 4 pins byte-identical — and a
closed key set narrows the contract: any spec in any consumer repo that today carries an extra
top-level key would begin to refuse. that is a blast radius this stone's diff does not open.

⇒ and it is a **scope call rather than a mechanical one**: whether an unknown top-level key should
refuse or warn is a decision about how strict the boot schema is, which `F18` already reserved
(*"how strict is the top-level parse"*). to settle it inside an execution stone would settle by
side effect a question that fulcrum holds open.

🟡 **the reviewer graded it a nitpick and named this disposition:** *"Pre-existing behavior, not a
regression, but worth a fulcrum/dream given how directly adjacent it sits to code this PR already
reasoned about."* this dream is that record.

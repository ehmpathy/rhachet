# 🌙 dream: a keyrack daemon spawned under jest should not transpile its whole graph cold

- kind = fix
- owner = rhachet (this repo)
- caught 2026-10-24

## .the cue that fired

`envAllHostingStrategies.integration` went red on one case per run with `keyrack daemon did not
become reachable within 20000ms`, while its green cases took 14–26s each on a box at ~600% load
(log `.log/role=mechanic/skill=git.repo.test/what=integration/2026-10-24T03-26-34Z.stderr.log`).

## .the gap, precisely

`spawnKeyrackDaemonBackground` (`src/domain.operations/keyrack/daemon/svc/src/contract/startKeyrackDaemon.ts`)
detects a `.ts` module and spawns `tsx/cli -e "require('<startKeyrackDaemon.ts>')"`. each spawn
transpiles the daemon's whole import graph from cold, so every test case that needs a fresh daemon
pays it, and the 20s window in `findsertKeyrackDaemon` is the only bound.

## .the shape of the fix

1. count the modules the daemon entry loads (`rhx cli.load.profile` covers the cli; the daemon
   entry needs the same `Module._load` count)
2. thin the daemon's graph per `rule.require.thinnest-import-path` — lazy loaders for what a
   start does not run
3. or spawn a prebuilt daemon entry under jest, if the build is fresh (`dist/.build.stamp`)
4. clamp: a cold spawn under a cpu ballast reaches the socket inside a bound well under 20s

## .why it is not done in this round

not safe and clean in this diff: it changes how every daemon spawns under test, and the measure
that would pick between steps 2 and 3 is not taken. this pr's route already closed.

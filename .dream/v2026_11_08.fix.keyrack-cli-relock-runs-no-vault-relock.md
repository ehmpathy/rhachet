# 🌙 dream: `rhx keyrack relock` runs each vault's relock

- kind = fix
- owner = rhachet (keyrack)
- caught 2026-11-08, on `beav/fix-keyrack-export-single-flight` (#656)

## .the cue that fired

acceptance [case20] ran `rhx keyrack relock` after two unlocks and found the cached aws export still
on disk: the cli never reaches any vault relock.

## .the gap, precisely

- #656 closed the export half: `relockKeyrack` reads each held aws.config grant's profile before the
  purge and drops keyrack's cached export of it (acceptance [case20] [t1])
- the rest predates #656: `src/contract/cli/invokeKeyrack.ts` calls `relockKeyrack` with no context,
  so no vault relock runs from the cli, for any vault. after a cli relock these rest on disk:
  - the aws cli's own credential cache (`~/.aws/cli/cache`)
  - the sso token (`~/.aws/sso/cache`)

## .the shape of the fix

1. build the keyrack context in the relock action, the way `unlock` does. it decrypts the host
   manifest, so a relock would meet the passphrase prompt it does not meet today
2. pass it to `relockKeyrack`
3. decide whether the aws vault relock's sso token drop belongs on every cli relock. it ends the
   human's browser sso session (`lesson.aws-sso-logout-clears-browser-session`), so it may want an
   explicit flag

## .why it is not done in this round

both open steps change what a relock does for every vault: a new passphrase prompt, and an sso
session that ends. that is a behavior call for the wisher, past #656's wish (fulcrum F15).

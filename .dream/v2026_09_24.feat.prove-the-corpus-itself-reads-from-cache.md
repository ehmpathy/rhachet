# 🌙 dream: prove the boot corpus itself reads from cache, not only the system prompt

kind: feat · owner: ehmpathy/rhachet · caught 2026-09-24

## .the cue that fired

peer review r8 (behavior-intent-coverage) of stone 5.1 flagged that the journey's M2 claim, a cache
read that covers the corpus, was asserted only as `cacheRead > 0`. the assertion now demands
`cacheRead >= ceil(bootChars / 4)`, which is a floor and still not a proof.

## .the gap, precisely

- the journey's second `claude -p` launch reads 14,601 and 14,588 cached tokens (runs of
  2026-09-24, `07-06-09Z` and `08-35-42Z`) over a 3,859-char corpus, about 965 tokens
- the claude-cli system prompt and tool schemas cache too, and they alone exceed that floor
- ⇒ a regression that dropped the corpus from the cached prefix, but kept the system prompt cached,
  would still pass

## .the shape of the fix

- in the same journey, launch a baseline clone whose brain dir holds an empty `boot.md` (or no
  `CLAUDE.md`), twice, and read its second-launch `cache_read_input_tokens`
- assert the corpus launch reads at least `baseline + ceil(bootChars / 4)` tokens from cache
- the two launches must share the model and the cli version; a real-haiku pair costs about one more
  minute of the journey

## .why it is not done in this round

it adds two real-brain launches to a journey already ~10 minutes long, and the transport's cache
eligibility is documented fact (`define.claude-md-vs-system-prompt`: a user-message prefix is
cached). the floor catches a corpus absent from the prompt; only a mid-prompt cache break slips
past. see fulcrum F39.

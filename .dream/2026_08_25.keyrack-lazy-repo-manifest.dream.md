dream = the repo manifest should load LAZILY, so no keyrack read ever pays for a manifest it does not consult

> **caught from:** the `v2026_08_25.fix-keyrack-all-skips-manifest` drive, `1.vision` (shape "D").
> the wisher said *"catch a dream for lazy manifest"* rather than build it there.

## the itch

`genContextKeyrackGrantGet` loads the repo manifest **eagerly**, at context build. so every read
pays for it — a file read, a yaml parse, a zod `safeParse`, and a recursive `extends` walk — even
when the ask is machine-wide and will never consult it.

that eagerness is the root of the `@all`-read defect (`ehmpathy/rhachet#467`): a manifest that
cannot hydrate kills a read that never needed it. it has **four** ways to kill one:

| # | throw | site |
|---|---|---|
| 1 | `keyrack manifest has invalid yaml` | `loadManifestExplicit.ts:35-39` |
| 2 | `keyrack manifest has invalid schema` | `loadManifestExplicit.ts:44-48` |
| 3 | `circular extends detected in keyrack chain` | `hydrateKeyrackRepoManifest.ts:312-316` |
| 4 | `extended keyrack not found` | `hydrateKeyrackRepoManifest.ts:333-338` |

## the dream

make `repoManifest` **lazy** — derived at first read rather than at context build.

then *every* manifest-free path is free **by construction**. no predicate to write, no ask to
carry into the builder, no set of load sites to patch, and — the real prize — **no future path
can regress**, because the branch that could be mis-keyed stops to exist.

it is the shape that answers the root question rather than the symptom
(`rule.require.solve-at-cause`). the 2026-08-25 wish answers *"which asks may skip the load?"*;
this dream retires the question.

## why it is a dream, not that behavior

three grounds, in descending weight:

1. **it breaks a published sdk type.** `ContextKeyrackGrantGet.repoManifest` is exported at
   `sdk.keyrack.ts:55` as a **value**, `KeyrackRepoManifest | null`. a thunk or getter changes the
   shape every downstream consumer reads. the shipped fix adds only *optional inputs*
2. **it scatters the throw.** today a bad manifest fails at context build — one predictable place.
   lazily it surfaces from wherever the first read happens, which for a repo sweep is
   mid-enumeration. that trades a clear failure for a scattered one, against
   `rule.require.failfast`
3. **it is a refactor of a shared context object**, on a wish scoped to one read path —
   `rule.forbid.scope-leaks`

## the work is not wasted either way

the 2026-08-25 fix builds `isKeyrackSlugMachineWide` + `isKeyrackAskMachineWide` and a canonical
`asKeyrackAskOrg` cast. **this dream wants exactly those** — it just consults them later (or not
at all). and the eager branch deletes cleanly once the lazy load lands, so the two compose rather
than collide.

## the wisher call this dream asks for

- does the sdk break justify a major? or should `repoManifest` stay a value and gain a **sibling**
  lazy accessor, so the published shape is untouched?
- should the throw stay eager (validate at build, hydrate at read) — a middle path that keeps
  `rule.require.failfast` while it drops the `extends` walk?

# 🌙 dream: three `syncHooksForLinkedRoles` unit cases time out on a COLD cache

- **kind** = defect
- **owner** = `ehmpathy/rhachet`
- **caught** = 2026-09-19, at `v2026_09_17.feat-boot-manifest-and-budget` `5.1.execution`, on the
  unit tier run that followed the `i004` repairs

---

## .the cue that fired

the unit tier ran red on its first invocation and green on its second, with **no edit between
them**:

| run | result | tier time |
|---|---|---|
| 1st — cold | 🔴 **3 failed**, 1673 passed | **38s** |
| the 3 in isolation | ✅ 5/5 | **1s** |
| 2nd — warm, identical tree | ✅ **1676 passed, 0 failed** | **10s** |

⇒ 🔴 **the cue is the 38s → 10s tier time, not the failure itself.** a 3.8x wall-clock difference
across two runs of an unchanged tree is a resource signal, and it is the one fact that separates
"the code is wrong" from "the box was busy" without a guess.

⚠️ **and a flake that heals on re-run is the most expensive kind to leave uncaught**, because the
remedy that works — run it again — is also the habit that hides the next real regression.

---

## .the gap, precisely

all three failures are the same shape, in `syncHooksForLinkedRoles (error paths) › [case1]`:

```
Exceeded timeout of 5000 ms for a hook
```

the timeout is on a **jest hook** (`beforeAll`/`beforeEach`), not on a `then` body. so what ran out
of budget is the case's SETUP, and the setup does real filesystem work.

🔴 **the 5000ms is jest's default, never a declared bound.** nobody chose it against a measurement
of what this setup costs on a cold page cache, so the suite carries an implicit assumption that the
filesystem is warm — which is true on a re-run and false on the first run of a session, in CI, and
on any box under concurrent load.

⚠️ **this is a UNIT tier**, which is the sharpest part. `rule.forbid.unit.remote-boundaries` says a
unit test must not cross a remote boundary, and the filesystem **is** one. so the timeout is a
symptom of a classification defect one level up: a case that needs a warm page cache to finish in
5s performs i/o, and i/o belongs in the integration tier.

⇒ two candidate defects stack here, and they have different repairs:

| # | the defect | whose |
|---|---|---|
| 1 | the setup's cost is unbounded and unmeasured against jest's default | the suite's |
| 2 | 🔴 a **unit** case performs filesystem work at all | the classification's |

---

## .the shape of the fix

**measure first, then pick.** the one command that settles which defect is live:

```sh
rhx git.repo.test --what unit --scope 'path://syncHooksForLinkedRoles' --mode apply
```

run it on a cold cache (a fresh boot, or after a large unrelated build) and read the setup time. if
the setup is inherently i/o-bound, defect 2 is the real one and defect 1 is a symptom.

| if the measurement shows | the repair |
|---|---|
| setup does real fs work | 🔴 **re-tier it** — rename to `.integration.test.ts`, where a filesystem boundary is sanctioned and the timeout budget is already wider |
| setup is cheap and the timeout is co-scheduled starvation | declare an explicit `jest.setTimeout` on the suite, with a comment that names the measured cold-cache cost |
| setup can be made pure | inject the fs boundary and keep it a unit test — the best outcome, and the most work |

🟡 **do NOT reach for a bare timeout bump first.** a raised timeout makes the symptom rare rather
than absent, and it keeps a filesystem-bound case in a tier that forbids one. the re-tier is the
repair that closes the class.

---

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

| question | answer |
|---|---|
| **SAFE?** | ✅ yes — a re-tier or a declared timeout changes no production code |
| **CLEAN?** | 🔴 **no** |

**CLEAN fails on scope, and the reason is specific rather than generic.** the repair needs a
**cold-cache measurement** to choose between two defects, and a cold cache is a machine state this
session cannot produce on demand — the page cache is warm precisely because the tier has been run
repeatedly. ⇒ a repair picked without that measurement would be a guess dressed as a fix, and the
guess most likely to be reached for (a timeout bump) is the one the table above forbids.

🟡 **and the file is not in this behavior's diff for this reason.** `syncHooksForLinkedRoles.ts`
was touched here, but the failure is in a case that predates the change and passes in isolation
against the changed code — so the diff opened no door this dream would owe the frame of.

⚠️ **the honest residual**: this leaves a unit tier that can run red on a cold box, and a reader who
meets it will re-run and move on. that is the habit this dream exists to interrupt, and it is why
the measurement command is written down rather than left to be re-derived.

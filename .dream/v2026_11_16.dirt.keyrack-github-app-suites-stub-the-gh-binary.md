# 🌙 dream: the keyrack github-app acceptance suites stub the `gh` binary on PATH

- kind = dirt
- owner = rhachet
- caught 2026-11-16

## .the cue that fired

two peer lanes of `v2026_11_14.fix-acceptance-suite-shares-the-box` (5.3.verification, i001
r003 and r009) flagged a stub `gh` on PATH in two keyrack suites that the behavior touched only
for a temp-path mask. the peer suite `keyrack.vault.githubSecrets.acceptance.test.ts` already
swapped its stub for the real `gh` against a local https stand-in, after the same rule blocked it.

## .the gap, precisely

- `blackbox/cli/keyrack.vault.osSecure.githubApp.acceptance.test.ts` puts `MOCK_GH_CLI_DIR` first
  on PATH, and its [case2] writes an inline bash `gh`
- `blackbox/cli/keyrack.aws-params.githubApp.acceptance.test.ts` puts `MOCK_GH_CLI_DIR` first on
  PATH for its github-app half (its ssm half already uses a real detached fake)
- neither carries the `.mock / .why / .real` note `rule.forbid.acceptance.mocks` asks of an
  unavoidable stub
- `blackbox/cli/install.age.acceptance.test.ts` stubs `age`, `apt-get`, `sudo` for a safety reason
  it documents (`.why`), with no `.real` pointer

## .the shape of the fix

per keyrack suite: run the real `gh` with `GH_HOST` + `SSL_CERT_FILE` against
`genFakeGithubApiServer`, through `asGhSwapEnv`, as the githubSecrets suite does; extend the
stand-in with the github app routes these suites call (installation lookup, token mint), and pin
each route against real github in `verify.githubSecrets.wirehop.sh`. for `install.age`, add the
`.real` pointer (a byhand install on a disposable vm), since a real root install per run is the
harm the stub exists to avoid.

## .why it is not done in this round

the behavior is bounded to how the acceptance suite shares the box; the `gh` boundary is a
separate contract with its own stand-in routes to build and pin (fulcrum F12).

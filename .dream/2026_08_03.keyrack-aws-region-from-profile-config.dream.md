dream = treat the AWS profile as a first-class source for BOTH region and identity on aws.params set

## the itch (from a real playtest, 2026-08-03)

a `keyrack set --vault aws.params` on a laptop that already has a live AWS profile hit TWO
fail-loud gates back to back, each of which the profile could have satisfied:

1. `aws.params requires a region` — hint: `set AWS_REGION (or AWS_DEFAULT_REGION)`
2. `aws.params found no AWS identity` — hint: declare + unlock that org's AWS_PROFILE

but the human's `~/.aws/config` profile ALREADY carries a `region`, and the profile IS the
identity. so keyrack asked for two things the profile already knows. that is friction the
profile could have removed (rule.prefer.defaults-match-common-case).

## fix A — derive region from the active AWS profile's shared config

`asKeyrackAwsParamRegion` today reads ONLY the env (`AWS_REGION` > `AWS_DEFAULT_REGION` > throw).
extend the precedence to ALSO read the active profile's `region` from `~/.aws/config`:

    context/env  >  AWS_REGION  >  AWS_DEFAULT_REGION  >  <profile>.region (shared config)  >  throw

use the SDK's own shared-config resolver, not a hand-rolled ini parse:
`loadSharedConfigFiles()` from `@aws-sdk/shared-ini-file-loader` (already transitive via
declastruct-aws), keyed by `process.env.AWS_PROFILE ?? 'default'`. this is a SURFACE-FREE
rework — no new flag, precedence-only — and it is ALREADY flagged in the blueprint open items
("a laptop whose region lives ONLY in ~/.aws/config … extend asKeyrackAwsParamRegion to also
read the shared-config-file region via the SDK's resolver"). the throw stays as the final
fallback, so a bare grove with no profile still fails loud with the same fix.

## fix B — the identity error should NAME the unlock command (name-the-fix)

on a SPECIFIC-org set, `aws.params found no AWS identity` tells the human to "declare + unlock
that org's AWS_PROFILE in the keyrack" — but does NOT give the copy-paste command
(rule.require.errors-name-the-fix wants the exact next move). it should emit the concrete
`rhx keyrack unlock --owner <owner> --env <env>` (and, if the org's AWS_PROFILE key is not yet
declared, the `keyrack set … AWS_PROFILE` step). the human should recover in one paste, not
infer the command from prose.

## why this is durable, not speculative

both are already-flagged clean follow-ups in
`.behavior/v2026_07_26.feat-keyrack-vault-aws-params/3.3.1.blueprint.product.yield.md` open
items (region-from-profile is named verbatim; the identity fail-loud is where the unlock guide
belongs). this dream just promotes them from "open item" to a dispatched todo, prompted by a
real human who hit both gates in one session.

## touch points

- `src/domain.operations/keyrack/adapters/vaults/aws.params/asKeyrackAwsParamRegion.ts` (fix A)
- the specific-org identity gate (`asKeyrackAwsParamIdentity` / the "found no AWS identity"
  ConstraintError hint) (fix B)
- add a unit branch: profile-config region resolves; and an acceptance assertion that the
  identity error names `keyrack unlock`

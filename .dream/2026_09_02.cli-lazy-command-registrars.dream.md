# dream: the cli registers only the command it was asked to run

## .what

`src/contract/cli/invoke.ts` imports all 16 top-level command modules EAGERLY, because each
`invokeX({ program })` call registers its subcommand and all must run for `--help` to list them.
so one spawn pays for sixteen commands.

the dream: a dispatch table whose values defer their module to an `import()` inside a thunk, so a
spawn loads only the command argv names — with a full-registration fallback for `--help`, a bare
call, and an unknown command (which commander must still report with its own suggestions).

## .why it is a dream and not this wish

it was BUILT, it worked, and it was lifted back out of
`v2026_08_25.fix-keyrack-all-skips-manifest` — because two independent l3 reviewers (i024 r010
and r011) each ranked it a blocker, on the same three grounds:

- **outside the wish's declared bounds.** the wish's `.what` is *when a repo keyrack manifest
  loads for a keyrack ask*. this is module-load laziness for the whole program — a different
  axis, touching 15 commands unrelated to keyrack
- **never reviewed.** 23 review rounds across 11 lenses; a grep of every review file for
  `getAllCliCommandRegistrars`, `setCliCommandsOnProgram`, `lazyRegistrars` returns zero. the
  files were untracked and post-dated i021's `arch-smell-scopeleaks` pass, so the one lens that
  exists to catch a scope leak never saw the scope leak
- **its own docstring names the motive**, and the motive is a test-suite one: *"the acceptance
  suite spawns the cli many hundreds of times, so that import tree was essentially the whole
  suite runtime."* a real gain, and not the wish's

⚠️ **the precedent is this wish's own.** Shape D (a lazy repo manifest) was declined the same way
and preserved at `.dream/2026_08_25.keyrack-lazy-repo-manifest.dream.md` — and r011 cited that
choice approvingly in the round before it caught this one. the same rule twice, applied
consistently: *good idea, wrong wish.*

## .what it measured

`require('dist/contract/cli/invoke')` cost **~633ms of a ~659ms spawn** — so the import tree was
essentially the whole cost of every CLI invocation, `--help` included.

### 2. what replaces it in `invoke.ts`

```ts
import { getCommandFromArgv } from '@src/domain.operations/roles/deltas/getCommandFromArgv';
import { setCliCommandsOnProgram } from './getAllCliCommandRegistrars';

// register the commands this invocation needs; each uses
// context.config.usage.get.* just-in-time
//
// .why = only the named command's module is loaded, so a spawn no longer pays
//   the import cost of all 16 (see define.cli-spawn-cost). when argv names no
//   known command — `--help`, a bare call, an unknown command — every command
//   is registered, so help still lists them all and commander still reports an
//   unknown command with its own suggestions
await setCliCommandsOnProgram({
  program,
  context,
  command: getCommandFromArgv({ args }),
});
```

`getCommandFromArgv` predates this work and is tracked (`24d9547`) — the dream adds no dependency.

### 3. `src/contract/cli/getAllCliCommandRegistrars.ts`, in full

```ts
import type { Command } from 'commander';

import type { ContextConfigOfUsage } from '@src/domain.operations/config/ContextConfigOfUsage';

/**
 * .what = registers one command's subcommand tree onto the program
 * .why = each registrar loads its own module lazily, so a spawn pays only for
 *        the command it was actually asked to run
 */
export type CliCommandRegistrar = (input: {
  program: Command;
  context: ContextConfigOfUsage;
}) => Promise<void>;

/**
 * .what = every top-level cli command name, mapped to the registrars that declare it
 *
 * .why = `invoke.ts` used to import all 16 command modules EAGERLY, because each
 *        `invokeX({ program })` call registers its subcommand and all must run for
 *        `--help` to list them. that made one spawn pay for sixteen commands:
 *        `require('dist/contract/cli/invoke')` costs ~633ms of a ~659ms spawn.
 *        the acceptance suite spawns the cli many hundreds of times, so that
 *        import tree was essentially the whole suite runtime.
 *
 *        each entry here defers its module to an `import()` inside the thunk, so
 *        the module loads only when its command is the one invoked.
 *
 * .note = a name maps to a LIST because `repo` is declared by two modules, and the
 *   order matters: `invokeRepoIntrospect` plainly CREATES `repo`, while
 *   `invokeRepoCompile` find-or-creates it. reverse them and `repo` is registered
 *   twice — a duplicate subcommand, not an error.
 *
 * .note = a name ABSENT from this map is safe: `invoke.ts` falls back to full
 *   registration when argv names no key here, so a miss costs speed, never
 *   correctness. the VALUES are what must be right.
 *
 * .note = kept in sync by `invoke.lazyRegistrars.test.ts`, which asserts this map
 *   registers exactly the command set the eager path does.
 */
export const CLI_COMMAND_REGISTRARS: Record<string, CliCommandRegistrar[]> = {
  init: [
    async ({ program }) =>
      (await import('./invokeInit')).invokeInit({ program }),
  ],
  repo: [
    // ⚠️ introspect FIRST — it creates `repo`; compile find-or-creates it
    async ({ program }) =>
      (await import('./invokeRepoIntrospect')).invokeRepoIntrospect({
        program,
      }),
    async ({ program }) =>
      (await import('./invokeRepoCompile')).invokeRepoCompile({ program }),
  ],
  roles: [
    async ({ program, context }) =>
      (await import('./invokeRoles')).invokeRoles({ program }, context),
  ],
  list: [
    async ({ program, context }) =>
      (await import('./invokeList')).invokeList({ program }, context),
  ],
  readme: [
    async ({ program, context }) =>
      (await import('./invokeReadme')).invokeReadme({ program }, context),
  ],
  run: [
    async ({ program }) => (await import('./invokeRun')).invokeRun({ program }),
  ],
  enroll: [
    async ({ program }) =>
      (await import('./invokeEnroll')).invokeEnroll({ program }),
  ],
  actor: [
    async ({ program }) =>
      (await import('./invokeActor')).invokeActor({ program }),
  ],
  clone: [
    async ({ program }) =>
      (await import('./invokeClone')).invokeClone({ program }),
  ],
  choose: [
    async ({ program }) =>
      (await import('./invokeChoose')).invokeChoose({ program }),
  ],
  ask: [
    async ({ program, context }) =>
      (await import('./invokeAsk')).invokeAsk({ program }, context),
  ],
  act: [
    async ({ program, context }) =>
      (await import('./invokeAct')).invokeAct({ program }, context),
  ],
  upgrade: [
    async ({ program }) =>
      (await import('./invokeUpgrade')).invokeUpgrade({ program }),
  ],
  update: [
    async ({ program }) =>
      (await import('./invokeUpdate')).invokeUpdate({ program }),
  ],
  keyrack: [
    async ({ program }) =>
      (await import('./invokeKeyrack')).invokeKeyrack({ program }),
  ],
};

/**
 * .what = registers the commands the program needs for this invocation
 * .why = one place owns the choice between a targeted registration (the fast path,
 *        for an argv that names a known command) and a full one (the correct path,
 *        for `--help`, a bare call, or an unknown command that commander must
 *        report with its own suggestions)
 *
 * .note = the order of a full registration matches the extant eager order, so a
 *   duplicate `repo` cannot appear and `--help` lists commands as it always has
 */
export const setCliCommandsOnProgram = async (input: {
  program: Command;
  context: ContextConfigOfUsage;
  command: string | null;
}): Promise<void> => {
  const registrars =
    (input.command === null ? null : CLI_COMMAND_REGISTRARS[input.command]) ??
    Object.values(CLI_COMMAND_REGISTRARS).flat();

  // sequential, never parallel: `repo`'s two registrars must run in order
  for (const register of registrars)
    await register({ program: input.program, context: input.context });
};
```

## .the clamps a restore owes

`invoke.lazyRegistrars.test.ts` pinned the map against the eager set — that drift test is the
minimum, and it is not sufficient. what a real review of this change would demand:

- **the fallback is the risk, not the fast path.** an argv that names no key falls back to FULL
  registration, so a map MISS costs speed and never correctness. the values are what must be
  right — a name mapped to the WRONG module registers the wrong subcommand silently
- **`repo`'s two registrars are order-dependent** (introspect creates, compile find-or-creates) —
  reversed, `repo` registers twice with no error. that ordering wants its own clamp
- **`--help` must still list all 16**, and an unknown command must still get commander's
  suggestions. both flow through the fallback, so both want an acceptance row
- ⚠️ **the async conversion is the unexamined part.** registration became `await`ed where it was
  synchronous. not one line in this diff proves that no caller depended on registration completed
  by the time `_invoke` returned control — a review of this change should start there

## .the measurement half, lifted with it

`define.cli-spawn-cost.md`, `show.cli.import.costs.sh`, and that skill's integration test +
snapshot were the measurement half of this same initiative. they were lifted too, for the same

to decompose it *inside* a keyrack wish would be more unreviewed out-of-scope work on an artifact
three reviewers said does not belong. so the whole initiative goes, and the durable knowledge is
recorded here.

### the figures — measured against v1.47.2, which is still current behavior

taken on a settled `dist/`, min-of-N kept (a require is deterministic work, so the floor is the
true cost and any excess is scheduler noise).

| what | figure |
|---|---|
| `require('dist/contract/cli/invoke')` — the whole eager tree | **633ms** |
| `./bin/run keyrack --help` end-to-end, min | **659ms** |
| ⇒ node boot + commander parse + config context | **~26ms** |
| `./bin/run keyrack --help` end-to-end, mean over 10 | 1248ms (stddev 523ms) |

per-module standalone cost, each in a **fresh** node process: `invokeKeyrack` 1376ms ·
`invokeAct` 1194ms · `invokeAsk` 1172ms · `invokeInit` 762ms · `invokeChoose` 574ms ·
`invokeEnroll` 424ms · (10 more) 17–301ms each · **sum 7412ms**.

⚠️ **the 7412ms sum OVERSTATES the real bill by ~12x.** each figure is measured in its own fresh
process, so every module re-pays for deps its peers also import (`commander`, `helpful-errors`,
`domain.operations`, …). in one real spawn the module cache is shared, so the whole tree costs
**633ms**, not 7412ms. the rank is the right guide to *which* trees are heaviest; it is the wrong
guide to *how much* is on the table.

> **measure the whole, never the sum of parts.** a 16-module refactor justified on the summed
> figure rests on a cost no spawn ever pays.

### why it matters

`bin/run` sends only `run` and `roles boot|cost` to the bun binary (~35–70ms). **every other
command falls to `run.jit`**, which does `require('../dist/contract/cli/invoke')`. so a spawn that
runs exactly one command still pays for sixteen, and the acceptance suite multiplies that by its
spawn count.

### what a rebuilt skill owes

the measurement tool is worth a rebuild on restore, but **not** in its lifted shape:

- **decompose it** — the five grains above want separate operations, per r004's blocker
- **derive the module list from `invoke.ts`'s own imports**, so a new command is measured the
  moment it is added rather than when someone remembers to add it
- **measure each module in a fresh process**, so no module cache is shared
- **keep the min, never the mean** — and print the whole-tree baseline beside the rank, so a
  reader cannot take the sum-overstates trap off the output by accident
- **refuse `--top 0`** (it asks for zero rows; unrefused it prints the full rack) and **cap
  `--runs`** (cost is runs × modules, one node process each)

## .the vocabulary this dream minted

`registrar` was itemized as a domain term while the design was in-tree. with the design lifted,
no declared object in this repo composes the word, so its `domain.terms/` cluster was lifted with
it rather than left aimed at absent code. the substance, so a restore need not re-derive it:

- **`registrar`** (noun) — a procedure that declares one command onto a cli program (its name,
  options, action) and loads that command's module lazily when it runs
- **discovered, not invented** — `invoke.ts` already carried *"register all commands
  unconditionally"*, and commander's own contract is `program.command(name)`, an act of
  registration
- **forbidden synonyms, each of which names a different act** — `loader` (names only the
  `import()`, the smaller half) · `factory` (returns a constructed value; a registrar returns
  `void` and mutates in place) · `installer` (overloaded — `rhachet init` installs roles, keyrack
  installs manifests) · `provider` (supplies on demand; a registrar is a one-time side effect) ·
  `initializer` (collides with the declared `init` command)
- **why the type is `CliCommandRegistrar` and not `CliCommand`** — the map is name →
  registrar**s** because `repo` breaks the 1:1, so the word had to name the *procedure* rather
  than the *command*

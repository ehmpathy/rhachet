# 🌙 dream: the per-unlock `aws sts get-caller-identity` runs once per unlock, uncached

- kind = fix
- owner = rhachet (keyrack, vault aws.config)
- caught 2026-11-08

## .the cue that fired

a peer reviewer of ehmpathy/rhachet#656 noted that `validateSsoSession` still runs
`aws sts get-caller-identity` on every unlock, after the export went single-flight.

## .the gap, precisely

- `vaultAdapterAwsConfig.ts` `validateSsoSession` spawns the sts cli per unlock, to read the username
  from the arn. a burst of N unlocks of one profile still spawns N python processes
- the hang guard and the single-quoted profile landed in #656; only the per-unlock cost rests

## .the shape of the fix

- read the username without a cli spawn: from the sso token cache the sdk already validated, or via
  a typed sdk sts client under the same `fromSSO` creds
- never cache the caller identity beside the export: the sts call is the wrong-user detector
  (`[case19]`), and a cached identity would mask a re-login as another user

## .why it is not done in this round

the per-unlock sts call is the wrong-user check, a contract of its own; a change to how the
username is derived is a behavior change past #656's bound (fulcrum F10). a cache, the cheap form,
would break that check, so the cure is a different read, not a memo.

# 🌙 dream: the timestamps lock must halt a staged deletion of the hook it guards

- kind = reseed
- owner = ehmpathy/declapract-typescript-ehmpathy (`practices/husky/best-practice/.husky/check.timestamps.lock.sh`)
- caught 2026-11-16, in `ehmpathy/rhachet` @ `beav/fix-acceptance-suite-shares-the-box`

## .the cue that fired

a peer review (arch-hazards-maintenance, r006) of #748 read the lock this repo's declapract upgrade
landed, and named two gaps in it.

## .the gap, precisely

1. the index check reads an empty index entry as a pass:
   `[ -z "$TIMESTAMPS_LOCK_INDEX" ] || [ ... = "$TIMESTAMPS_LOCK_EXPECTED" ] || timestamps_lock_halt`.
   so `git rm --cached .husky/check.timestamps.sh` (the file left on disk) passes the disk check
   and the index check both, and the commit strips the hook from every later clone
2. the lock opens with no `set -eu`, unlike `check.timestamps.sh` and `check.secrets.sh`. a failed
   `git hash-object` leaves the var empty, and the lock reports "changed on disk" where git failed
   to read

## .the shape of the fix

- in the practice's lock: an empty index entry halts, with its own line ("the hook was removed
  from the index"), unless the file is also absent on disk and untracked by design
- `set -eu` at the head, with the extant `|| timestamps_lock_malfunction` paths kept, so a read
  fault reports as a malfunction
- a test in the practice that stages a deletion and asserts exit 2

## .why it is not done in this round

the file is the practice's output: a fix in this repo is overwritten by the next
`declapract upgrade`. the cure belongs where the file is born. #748 carries the upgrade as a
`chore(deps)` commit of its own (F7), and does not edit the practice's files.

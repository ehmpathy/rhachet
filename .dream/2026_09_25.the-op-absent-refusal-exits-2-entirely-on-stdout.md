# 🌙 dream: the op-absent refusal exits 2 and renders entirely on stdout

- **kind** = fix
- **owner** = `ehmpathy/rhachet`
- **caught** = 2026-09-25

---

## .the cue that fired

a snapshot was added to `[case6]` of `blackbox/cli/keyrack.vault.1password.acceptance.test.ts`
over `result.stderr`, per the shape every peer refusal in that suite takes. the resnap wrote:

```
exports[`… then: the refusal matches its snapshot: stderr-op-cli-absent 1`] = `""`;
```

🔴 **an empty-string snapshot** — green forever, and it proves naught
(`rule.forbid.failhide`). the snapshot was moved to `stdout` and now carries the real render, so
the test is repaired. **the defect it revealed is not.**

## .the gap, precisely

`src/domain.operations/keyrack/adapters/vaults/1password/vaultAdapter1Password.ts:407-440` — the
`set` path's op-absent refusal:

```ts
const opInstalled = await isOpCliInstalled();
if (!opInstalled) {
  console.log('');
  console.log('🔐 keyrack set');
  console.log('   └─ ✗ op cli not found');
  …                       // ~30 more console.log lines of install route
}
```

every line is `console.log`, and the process exits **2**. so:

| stream | carries |
|---|---|
| stdout | the whole refusal — the fault line, and the entire install route |
| stderr | 🔴 **empty** |

⇒ this contradicts `rule.forbid.stdout-on-errors` (rhachet/enroller), and it breaks the
discriminator every machine-readable consumer relies on: a caller that pipes stdout to a parser
gets 33 lines of prose on a failure, while a caller that reads stderr for the reason gets an
empty string.

🟡 **it is inconsistent with its own sibling.** `[case1]`'s exid-format refusal is a
`ConstraintError` and lands on **stderr**, correctly. one command, two refusal paths, two streams.

## .the shape of the fix

1. route the block through `console.error` (or the extant `emitCliErrorAndExit` seam, which
   already owns the stderr render for this cli)
2. check the peer at `:264` (`isUnlocked`) and any other `console.log` under this adapter for the
   same shape
3. the three acceptance `then`s at `[case6]` read `result.stdout + result.stderr`, so they survive
   the move untouched — **but the new snapshot key does not.** it is `stdout-op-cli-absent`, and a
   move to stderr makes it `""` again, in the other direction. ⇒ rename the key to
   `stderr-op-cli-absent` **in the same commit as the stream move**, or the repair re-creates the
   exact failhide it fixed
4. sweep for other consumers of this render before the move — a `--json` caller that reads stdout
   on a nonzero exit would change behavior

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

| half | SAFE? | CLEAN? | verdict |
|---|---|---|---|
| the **snapshot** — pin the real render rather than `""` | ✅ | ✅ | 🔴 **done this round** |
| the **stream move** | 🟡 a caller-visible stream contract change on a command this behavior never opened | 🔴 **no** — it ripples into the adapter, its snapshot key, and any consumer that reads stdout on a nonzero exit | dream it |

⇒ the branch's scope is the boot manifest + budget. `vaultAdapter1Password.ts` is opened here only
because a verification-stone blocker asked for a snapshot of its refusal, and a stream migration is
not what that blocker asked for.

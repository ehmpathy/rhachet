dream = keyrack output should not wear the mechanic seaturtle mascot — keyrack is a domain, not a role

## the itch (from a real playtest, 2026-08-03)

a blocked `keyrack set` rooted its failure on the mechanic mascot:

    🐢 bummer dude...
    ⠀
    🐚 keyrack set
       └─ ✋ blocked: aws.params requires a region

the human's read: the turtle is WRONG here. keyrack is a credential DOMAIN with its own
signature glyph (the lock `🔐`), not a rhachet ROLE. a role mascot (the mechanic `🐢`) in a
domain tool's output blurs which tool speaks.

## the tension with today's rule

`.agent/repo=.this/role=any/briefs/rule.require.keyrack-emoji-palette.md` CURRENTLY makes this
by-design: keyrack SUCCESS roots on `🔐` (its domain glyph), but keyrack BLOCKED deliberately
reuses the shared ergonomist failure grammar (`🐢 bummer dude...` + `🐚`) so keyrack failures
"read the same as every other tool's failures." so the turtle in a blocked report is, per the
rule as written, NOT a defect.

## the wisher call this dream asks for

the human (wisher) wants keyrack's OWN domain glyph to root the blocked path too — no role
mascot in a credential-domain tool, success OR blocked. that means:

- the keyrack blocked report roots on the keyrack domain glyph (`🔐`, or a domain-appropriate
  blocked variant), NOT `🐢 bummer dude...`
- OR at minimum, drop the `🐢` mascot header from keyrack blocked output while the shared
  `✋ blocked` phrase stays under a neutral/domain root

## why this is wisher-scope, not a per-behavior edit (the rule says so)

the palette rule itself states: "conversion of a single keyrack vault's root … is a
keyrack-wide UX decision (wisher scope), not a per-behavior edit." this change touches:

- `getKeyrackBlockedReport.ts` + `getKeyrackInfraInitErrorReport.ts` (the blocked roots)
- `rule.require.keyrack-emoji-palette.md` (rewrite the blocked-root row + the .why rationale)
- EVERY keyrack blocked snapshot across all vaults (resnap)

so it is a deliberate keyrack-wide UX decision + a rule rewrite + a cross-vault resnap — one
coherent change, not a detail to sneak into the aws.params behavior. dispatch it as its own
todo so the wisher's decision (what replaces the turtle) is settled up front.

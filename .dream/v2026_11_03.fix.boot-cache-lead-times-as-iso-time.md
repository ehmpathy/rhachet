# 🌙 dream: the boot cache lead record keeps its times as iso-time, not raw epoch ms

kind · fix
owner · rhachet, `src/domain.operations/clone/fleet/`
caught 2026-11-03

## .the cue that fired

a peer review of the fleet gate flagged `claimedAtMs`, a persisted raw epoch number, against
`rule.forbid.any-time`.

## .the gap, precisely

- the lead record `.agent/.actors/.boot.leads/<bootHash16>.json` stores `claimedAtMs: number`
- `asBootCacheLeadDecision`, `holdFirstSayForBootCache`, `getOneLeadProgressToJudge`, and the wait
  compare it with `Date.now()` against `BOOT_CACHE_LEAD_*_MS` bounds, by hand-rolled ms arithmetic
- six files read the field

## .the shape of the fix

- the record stores `claimedAt: IsoTimeStamp` (via `asIsoTimeStamp(now())`)
- the bounds become `IsoDuration` constants; the decision asks `getDuration({ of: { range } })` and
  compares with `isIsoDuration`-style checks, or converts once via `toMilliseconds` at the one api edge
- `asBootCacheLeadDecision.test.ts` keeps its cases; inputs move to iso stamps
- a record from before the change (numeric field) reads as absent, so a stale lead is never trusted

## .why it is not done in this round

the field feeds the bound math in six files; the switch is a rewrite of that math, not a rename, and the
round's work is the review's blockers. the record is local and gitignored, so no migration is owed.

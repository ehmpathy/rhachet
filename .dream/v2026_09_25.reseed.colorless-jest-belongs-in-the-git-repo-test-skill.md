# 🌙 dream: colorless-when-piped belongs in `git.repo.test`, not in each repo's package.json

- kind  = reseed
- owner = ehmpathy/rhachet-roles-ehmpathy
- caught 2026-09-25

## .the cue that fired

a wisher asked that acceptance tests "run colorless", after a `[t6]` failure dump arrived as
several thousand bytes of terminal paint. the measurement found jest itself was the second
source: the unit log at `2026-09-25T05-27-35Z` carried SGR color on **56 lines**.

the cure applied in `ehmpathy/rhachet` was `--no-colors` on all four `test:*` npm commands. it
works — the same suite then carried **0** — and it is in the wrong tree.

## .the gap, precisely

`rhx git.repo.test` is the paved path. it **pipes** jest into `.log/role=mechanic/…`, prints its
own treestruct, and hands the human a log **path** — the raw jest bytes never reach a terminal.

⇒ so the rule a human actually wants is *"colorless when I am the one piping it"*, and the only
party that knows a pipe is happening is the skill that opens it.

🔴 **an npm command cannot express that rule.** it has no view of its own stdout, so `--no-colors`
is unconditional: it also strips color from a human who runs `npm run test:unit` by hand in a
terminal, where color is a real aid and no pipe is in play.

| lever | colorless in a log | color kept for a tty | reaches every repo |
|---|---|---|---|
| `--no-colors` in each repo's package.json | ✅ | 🔴 no | 🔴 no — one repo at a time |
| `NO_COLOR=1` on the skill's pipe | ✅ | ✅ | ✅ — every repo that links the role |

the third column is the larger half. every repo that links `ehmpathy/mechanic` has the same
colorized logs today, and each would otherwise need its own four-command edit.

## .the shape of the fix

in `rhachet-roles-ehmpathy`, `skills/git.repo.test/git.repo.test.sh`:

1. find where the jest invocation is piped to the `.log/…` capture
2. set `NO_COLOR=1` (and `FORCE_COLOR=0`, since a pty upstream may already have forced it on) in
   the env of **that invocation only** — never exported for the whole skill, so the skill's own
   turtle treestruct keeps its color
3. leave a direct `npm run test:*` untouched, so a human by hand still gets color — that is the
   whole advantage this placement buys over the one taken downstream
4. once it lands and the role is bumped, **revert the four `--no-colors` tokens** in
   `ehmpathy/rhachet`'s `package.json`, so one rule has one home

⚠️ step 4 matters: left in place, the two cures overlap and the downstream one keeps costing a
human their terminal color for a benefit the skill already supplies. a concept in two homes is
`rule.forbid.domain-term-inconsistency` at the mechanism grain.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`) fails on **clean** for the one
reason that admits no argument: **the file is in another repo.** `rhachet-roles-ehmpathy` reaches
this tree through a link, so no edit here can touch it, and a tree adopts only what is scoped to
itself (`rule.always.scope-onetime-lessons-to-the-behavior`).

the safe, clean half WAS taken in-tree: the four `--no-colors` tokens, plus `asLegibleScreen` for
the pty dump — which is the larger win and which **no color flag could have delivered**, since
most of that payload is cursor motion rather than color.

🟡 the deferral is an OWNERSHIP call, so it owes this dream **and** a fulcrum — the choice to cure
it downstream was a judgment with a named cost (`F46`).

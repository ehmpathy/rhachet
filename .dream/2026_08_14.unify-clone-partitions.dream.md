dream = unify the two clone (and actor) partitions into one

---

today each identity grain lives in two separate partitions (see
`.agent/repo=.this/role=any/briefs/define.actor-clone-partitions.md`):

```
Actor{ Ondisk, Inmem }        Clone{ Ondisk, Inmem }
```

- **on-disk** — the durable filesystem record under `.agent/.actors/` (serial, socket, config, roles
  log, history). the CLI (`rhx enroll`, `rhx clone list/say/get`) operates on this partition.
- **in-mem** — the live in-process object (`genClone(...).ask/.act/.run`). the SDK operates on this
  partition.

they are two representations of the same concept, but NOT yet bound to each other.

## the dream

bind an in-mem process to an on-disk clone, so the two partitions collapse into ONE clone.

concretely:

- an SDK `genClone(...)` process could **attach to** an on-disk clone — reach its socket, resume its
  `exid`/history, share its identity — instead of a separate, ephemeral in-mem object.
- an on-disk clone's live process (the one enroll spawned) IS an in-mem clone — so `rhx clone say` and
  an in-process `clone.ask` land on the same active brain.
- the four dobjs (`CloneOndisk`/`CloneInmem`, `ActorOndisk`/`ActorInmem`) unify into one `Clone` and one
  `Actor` — the partition suffix disappears, and the contract ubiquity we already speak (`Clone`/`Actor`
  everywhere) becomes literally true internally too.

## why it's a dream, not this behavior

the bind requires a live in-process brain to reach an on-disk clone's socket + resume its native session
— a real lift (session-resume wire-up, socket attach from the SDK, identity reconciliation). the
`v2026_08_07.enroll-with-interface` behavior deliberately ships the partitions SPLIT (dobjs separated,
contracts ubiquitous) precisely so this unification is a clean follow-on, not a teardown.

## the payoff

- one `Clone`, one `Actor` — no partition split to reason about.
- the SDK can drive a durable, revivable, dispatchable clone (not just an ephemeral in-mem one).
- crons/comms (which reach on-disk clones) and SDK apps (which drive in-mem clones) speak the exact same
  live object.

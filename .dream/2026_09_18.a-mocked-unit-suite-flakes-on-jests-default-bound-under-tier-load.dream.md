# 🌙 dream: a fully-mocked unit suite flakes on jest's DEFAULT 5s bound under tier load

- **kind** = repair — the suite lives in this repo
- **owner** = `src/domain.operations/keyrack/adapters/vaults/aws.config/vaultAdapterAwsConfig.test.ts`
- **caught** = 2026-09-18, at `.behavior/v2026_09_11.fix-clone-say` stone `5.3.verification`

## .the cue that fired

a thorough unit run, taken in the minutes right after a 47-minute realbrain acceptance tier:

```
tests: 4050 passed, 1 failed, 0 skipped
time: 35s

● vaultAdapterAwsConfig › [case3b] cross-username recovery via confirmSsoSessionForUser
  › [t0] mode 2: wrong user, retry recovers to correct user › completes without error after retry

  thrown: "Exceeded timeout of 5000 ms for a test."
```

⇒ the cue was not the red. it was that **the failing test performs no i/o at all** — `exec`, `spawn`,
`fromSSO`, and the sso-cache read are each mocked in its own `beforeEach`. a test with no real
boundary cannot take 5 seconds of work, so the bound was not spent on work.

## .the gap, precisely — a default bound is a wall-clock bet, and the tier collects on it

three measurements, same commit, same suite, no source edit between them:

| run | context | suite time | tier time | verdict |
|---|---|---|---|---|
| 1 | full unit tier, minutes after the acceptance tier | 8.977s | **35s** | 🔴 1 failed |
| 2 | that one suite, scoped, alone | — | **5s** | ✅ 50 passed |
| 3 | full unit tier, machine settled | — | **21s** | ✅ 4051 passed |

run 1 against run 3 is the whole finding: **the identical 467-suite tier ran 67% slower**, and the
one test that fell over is the one whose assertion awaits several event-loop hops
(`process.nextTick` → `close` → the recovery loop's repeated `validateSsoSession`). under starvation
those hops are scheduled late, and jest's per-test bound counts wall-clock rather than work.

⇒ so the defect is `rule.forbid.time-assumptions` at the test-harness grain: the suite carries **no
`jest.setTimeout`**, so every test in it inherits jest's 5000ms default — a number chosen by a
framework that knows neither the machine nor what else runs on it.

🟡 **and the cause is corroborated, never proven.** event-loop lag was not instrumented directly;
what is measured is the 67% tier slowdown and the pass in isolation. a bound raise chosen against
this evidence is a bound raise chosen against a symptom.

## .the shape of the fix

the naive repair — raise this one file's bound — is available and is the wrong grain, because the
suite is a **sample**: any all-mocked test whose assertion crosses several event-loop hops carries
the same bet, and no artifact in the repo names the policy.

1. measure, do not guess. instrument the tier for event-loop lag (`perf_hooks.monitorEventLoopDelay`)
   in a run co-scheduled with a realbrain tier, so the bound is set against a measured p99 rather
   than against this one red
2. declare the policy once — a unit-tier `testTimeout` in `jest.unit.config.ts`, so a per-file
   `jest.setTimeout` becomes the exception that must argue for itself
3. then sweep the per-file bounds that the policy makes redundant

⇒ step 2 is the durable half: a default the repo chose beats a default jest chose, and it fixes every
suite rather than the one that happened to fall over.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`), answered rather than assumed:

| question | answer |
|---|---|
| **safe?** | ✅ a bound raise cannot mask a logic defect — the assertions are unchanged |
| **clean?** | 🔴 **no.** the honest fix is a tier-wide `testTimeout` in `jest.unit.config.ts` plus a sweep of the per-file bounds it makes redundant — a config change that governs all 467 suites, in files this wish never opened |

and the one-line variant is refused on its own terms: **the right number is unknown.** 5s → 15s is a
guess, and a guessed bound that happens to hold is indistinguishable from a fix
(`rule.forbid.mechanism-inferred-from-outcome`).

⇒ the file is **untouched by this branch** — `git diff origin/main --stat` against
`src/domain.operations/keyrack/adapters/vaults/aws.config/` is empty — so it predates the wish and
is out of its bounded scope.

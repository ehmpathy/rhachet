# 🌙 dream: `findsertFile`'s if/else returns one value, and `'updated'` is unreachable

- **kind** = fix
- **owner** = `ehmpathy/rhachet`
- **caught** = 2026-09-23, in the `3.3.1.blueprint.product` self-review `has-consistent-mechanisms`

## .the cue that fired

i opened `findsertFile.ts` to judge whether `setActorBriefCorpus` should reuse it. it should not —
that verdict is in the review. but the read surfaced a blemish beside the answer.

## .the gap, precisely

`src/domain.operations/invoke/link/findsertFile.ts:26-32`

```ts
// File exists - check if it matches template
const existingContent = readFileSync(path, 'utf8');
if (existingContent === template) {
  return { path: relativePath, status: 'unchanged' };
} else {
  return { path: relativePath, status: 'unchanged' }; // preserved with custom changes
}
```

**both branches return the identical value.** so:

| the defect | what it costs |
|---|---|
| a branch that decides naught | a reader traces a conditional to learn it changes no outcome — and `rule.forbid.else-branches` forbids the `else` outright |
| `readFileSync` runs only to feed a comparison nobody acts on | a filesystem read per call, for no effect |
| `LinkResult`'s **`'updated'`** status is **unreachable** from this operation | a declared state no codepath produces — a reader cannot tell whether it is dead or merely not-yet-used (`rule.require.read-the-record-not-the-correlate`'s own *"why has this codepath no coverage?"* row) |

🟡 **the behavior is almost certainly intentional** — the docblock says *"without overwriting custom
changes"*, and the trailing comment names the preserve case. **the defect is in the expression, not
the decision.**

## .the shape of the fix

1. collapse the branch — the extant behavior is one return:
   ```ts
   // the file exists: PRESERVE it, whether or not it matches the template
   return { path: relativePath, status: 'unchanged' };
   ```
   drop the `readFileSync` with it, since the comparison decides nothing.
2. **then settle `'updated'` deliberately.** two honest outcomes, and the choice is the real work:
   - it is **dead** across every producer ⇒ remove it from `LinkResult`
   - another operation produces it ⇒ leave it, and say so in `LinkResult`'s own docblock, so the
     next reader is not left to grep
3. ⚠️ **check the consumers before either step.** `LinkResult` is a shared return type; a status
   removal is a contract change, and a caller may switch on it.

## .why it is not done in this round

**SAFE** — ⚠️ **partly.** step 1 alone is behavior-preserving. step 2 touches a **shared return
type**, so it is a contract change with unknown callers.

**CLEAN** — 🔴 **no.** `findsertFile.ts` is not in this wish's diff, and the wish fences it outright:
*"do not widen into unrelated boot work the refactor may have left nearby — catch it as a dream
instead."* the file serves readme scaffolding at `rhx init`, never the brief boot path.

🟡 **and a one-of-two fix would be worse than none**: collapse the branch without the `'updated'`
decision, and the unreachable status loses the one clue that a reader would have followed to find it.

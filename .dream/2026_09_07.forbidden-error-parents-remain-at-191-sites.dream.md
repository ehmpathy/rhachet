## .the shape of the fix

**not a find-and-replace.** the rule forbids that outright, and states why: the two parents do
not map one-to-one onto the two leaves. so the shape is a **per-area sweep, one area per pull
request**, each with the owner question re-asked at every site:

1. pick one area from the table above
2. at each site ask *"who fixes this?"* — caller → `ConstraintError` (exit 2), server →
   `MalfunctionError` (exit 1). cannot answer → leave it and say so
3. add a `hint` that names the fix where one is absent (`rule.require.errors-name-the-fix`)
4. **run the acceptance tier and expect red** — each move changes an exit code, so any suite that
   pins the old one reddens. resnap it and say in the message that the redness IS the fix rendered
5. re-derive the inventory line in `rule.forbid.helpful-error-parents` and update it in place

⚠️ **step 4 is the whole risk, and it is why this cannot be one pull request.** an area at a time
keeps each exit-code delta small enough for a human to read the resnap and tell a fix from a
regression.

## .why it is not done in this round

**it is forbidden.** `rule.forbid.helpful-error-parents`'s own enforcement line: *"a bulk
find-and-replace across untouched sites = **blocker** (each site owes the owner question)."* the
rule this dream serves bans the act in the same breath it names the debt. the on-contact half is
the only half a round may take, and this round took it — `getRoleFromManifests.ts`, 4 sites, plus
`assertZeroOrphanMinifiedBriefs.ts` and `invokeUpdate.ts` when later lanes reached them.

⇒ **one reason, and it is sufficient on its own.**

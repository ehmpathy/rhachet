# dream: a batch-unlock row pairs `💥` with whatever class it caught

## .what

`emitKeyrackKeyBranch.ts:103` hardcodes the row glyph:

```ts
lines.push(`${indent}${entry.tip ? '├' : '└'}─ status: errored 💥`);
```

so a **`ConstraintError`** isolated into a per-key row renders under `💥` — the
`MalfunctionError` glyph. a caller-fixable refusal reads as *"we broke"*.

`asKeyrackErroredKeyTip.test.ts` `[case1]` constructs exactly that: a `ConstraintError`
whose tip lands in a `💥` row.

## .why it is a defect

`rule.require.unabridged-error-prefix` grades a mismatched pair a **blocker**:

> a glyph paired to the wrong class (`✋ MalfunctionError`, `💥 ConstraintError`) = **blocker**

the two halves name one fact between them — who must fix it, and what the exit code is. paired
wrong, they assert both answers at once, and a reader who trusts the glyph hunts their own input
for a server-side fault (or, here, files a defect against a refusal that was theirs to fix).

## .why it is NOT fixed in `v2026_08_25.fix-keyrack-all-skips-manifest`

both files are **untouched by that branch** — `git diff HEAD --stat` returns empty for
`emitKeyrackKeyBranch.ts` and `asKeyrackErroredKeyTip.ts`. the item sits outside every `+` hunk,
so it predates the branch and stays a follow-on (`rule.forbid.scope-leaks`).

the branch's own surface — `getKeyrackBlockedReport`, `getKeyrackInfraInitErrorReport` — was
brought into conformance: both now read glyph **and** class off the error's constructor.

## .the shape the fix likely wants

one named transformer that reads a glyph off any error, so the pair law has ONE implementation
rather than a copy per render:

```ts
// asKeyrackFaultGlyph.ts
export const asKeyrackFaultGlyph = (input: { cause: unknown }): string =>
  (input.cause as { constructor?: { emoji?: string } })?.constructor?.emoji ?? '💥';
```

then `getKeyrackBlockedReport` and `emitKeyrackKeyBranch` both consume it, and a third render
cannot drift from either.

⚠️ **the row's glyph is a real UX decision, not only a bug.** `💥` in a batch row currently
denotes *"this key errored while its peers succeeded"* — a **status**, distinct from `🚫` blocked
and `🫧` absent. to make it class-derived means a batch can show `✋` and `💥` rows side by side,
which is arguably clearer AND a change to a documented palette slot
(`rule.require.keyrack-emoji-palette`). that is a keyrack-wide call (wisher scope), so it wants a
decision before an edit.

## .the clamps it needs

| clamp | asserts |
|---|---|
| a `ConstraintError` isolated into a row | renders `✋`, never `💥` |
| a `MalfunctionError` isolated into a row | renders `💥` |
| a batch with one of each | both rows render, each under its own glyph |

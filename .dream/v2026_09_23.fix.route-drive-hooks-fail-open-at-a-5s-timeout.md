# 🌙 dream: route.drive hooks fail open at a 5s timeout

- kind  = fix
- owner = `ehmpathy/rhachet-roles-bhrain` — `src/domain.roles/driver/getDriverRole.ts`
- caught 2026-09-23 · patched locally in `node_modules` + `.claude/settings.json`

## .the defect

the driver declares `route.drive --when hook.onStop` and `--when hook.onBoot` with `timeout: 'PT5S'`.
Claude Code treats a hook killed at its timeout as a **non-fatal** error: no exit 2, no stderr, the
stop proceeds. so the stop hook holds the route only while it runs under 5s.

## .evidence — this session's transcript, cli 2.1.280

| `durationMs` | `hookErrors` | result |
|---|---|---|
| < 5000 | the stone guidance (exit 2) | held — a continuation turn |
| **5078** | `[]` · `hasOutput: false` | **released** — the brain stopped mid-stone |

- `route.drive` itself never releases a push stone early: `stepRouteDrive` holds until `state.count > 21`.
- the release was the harness's timeout, not the driver's logic.
- the run is heavy for a hook: `computeRouteBouncerCache` + `setRouteBouncerCache` + passage read +
  stone reads, behind the `rhx` → `rhachet` dispatch. 5s sits at its measured tail.

## .the fix

1. `onStop` and the `onBoot` `route.drive` hooks → `timeout: 'PT60S'`. a stop hook that times out
   silently defeats its one purpose; latency on a stop costs seconds, a released stop costs a human.
2. hold the onStop path under 1s — skip the bouncer cache recompute in `hook.onStop` (the stop decision
   reads only passage + stones), so the timeout is a cap, never the norm.
3. a test that pins the declared timeouts, so a regression to `PT5S` fails loud.

## .also exposed, same shape

the driver's `PreToolUse` guards — `route.bounce`, `route.mutate.guard`, `route.foreground.guard` —
also run at `PT5S`. a timed-out guard lets the tool call through: the seal fails open under load.
same remedy: a faster path, and a cap that is not the tail of the normal run.

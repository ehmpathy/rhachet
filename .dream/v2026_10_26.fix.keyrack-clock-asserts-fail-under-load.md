# 🌙 dream: the keyrack daemon integration suite breaks its own premises on a loaded box

kind = fix · owner = rhachet (keyrack tests) · caught 2026-10-26

## .the cue that fired

a full impacted integration run (`rhx git.repo.test --what integration --mode apply`, 376s, where the
run before took 229s) failed 3 of 2128, each on a clock, not a behavior:

- `unlockKeyrackKeys.integration.test.ts` [case3] — `expiresIn > fiveMinMs - 5000`, received 290217
- `unlockKeyrackKeys.integration.test.ts` [case4] — `expiresIn > fifteenMinMs - 5000`, received 891415
- `daemon.integration.test.ts` [case11] — `pidLater` equal to `pidEarlier`: the successor did not write
  its pid inside the 50 x 100ms handover poll

a later scoped run of `daemon.integration` alone, on a loaded box (202s vs 95s), failed two more:

- [case9] — `ENOENT` on `readFileSync(pidPath)` at line 887: a spawned daemon's pid file read before
  it exists, with no retry
- [case11] — the whole case exceeded its 60s timeout

## .already fixed, in pr #659

the two `unlockKeyrackKeys` reds: the four TTL asserts that read `Date.now()` after the call now
bracket it (`askedAtMs` before, `answeredAtMs` after), the form [case2] in the same file already used.
the slack is now the call's own span, never the box's load. 17/17 green.

## .the gap that remains, precisely

- [case9]: an unguarded pid read right after a spawn. the same file guards the identical read in
  [case11] (ENOENT → retry); [case9] does not
- [case11]: its budgets interlock — reach poll + handover poll + an 18s demand loop must fit 60s, and the
  handover poll must stay under the 15s idle window. a wider handover poll was tried and reverted: it
  could not be proven, and it eats the timeout margin the demand loop needs under load

## .the shape of the fix

- [case9]: poll the pid file with the ENOENT guard [case11] already uses, bounded by
  `DAEMON_REACHABLE_POLL_LIMIT`
- [case11]: hold the overlap by construction (start the successor only once the predecessor is
  reachable, then await the successor's pid via the reachability probe, not a file poll), and derive the
  test timeout from the declared budgets so one edit cannot break the sum
- a clamp for each: a run under synthetic load (a busy loop in a peer worker) stays green

## .why it is not done in this round

- safe: yes. clean: no. the daemon suite is keyrack's, untouched by this pr; [case11]'s budgets
  interlock, and a tweak that cannot be proven green on a loaded box is a guess, not a fix

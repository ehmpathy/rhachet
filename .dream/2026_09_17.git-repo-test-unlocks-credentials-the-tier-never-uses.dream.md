# 🌙 dream: `git.repo.test` must not fail a whole tier on a credential that tier never reads

- kind = reseed **and** fix — it has two owners, measured 2026-09-20 (see the in-repo section below)
- owner = ehmpathy/rhachet-roles-ehmpathy (`role=mechanic`, skill `git.repo.test`) — the acceptance leg
- owner = ehmpathy/rhachet (`jest.integration.env.ts` + the `sourceAllKeysIntoEnv` contract) — the
  integration leg, which no fix to the foreign skill reaches
- caught = 2026-09-17

## .the cue that fired

`rhx git.repo.test --what acceptance --against local --env test --mode apply` refused to run at
all:

```
🐢 bummer dude...
🐚 git.repo.test --what acceptance
   ├─ status: malfunction
   └─ error: keyrack unlock failed

✋ keyrack unlock
   └─ aws sso login timed out
      └─ human did not respond to browser sso prompt
```

four of the five credentials unlocked cleanly. the fifth — `ehmpathy.test.AWS_PROFILE` — needs an
interactive browser SSO the agent cannot complete, and its failure took the whole tier down.

## .the gap, precisely

the acceptance tier under test reads **no AWS credential at all**. it spawns a stub brain-cli on
`PATH` and drives the built binary; not one of its cases touches an aws sdk.

`AWS_PROFILE` reaches the `test` env by **inheritance**, never by a declaration this repo made:

```yaml
# .agent/keyrack.yml
env.test: []          # ← this repo asks for NONE in test
extends:
  - .agent/repo=ghlitch/role=observer/keyrack.yml   # ← AWS arrives from here
  - .agent/repo=ghlitch/role=operator/keyrack.yml
```

### 🔴 the precise mechanism is `env.all`, measured 2026-09-18

a first read of this dream suggests the extended role declares the key **under `env.test`**. it does
not. **all three of its env lists are empty**, and the key arrives on an axis that has no env at all:

```yaml
# .agent/repo=ghlitch/role=observer/keyrack.yml — and role=operator, identically
org: ehmpath
env.prod: []
env.prep: []
env.test: []
env.all:
  - key: AWS_PROFILE
    is-optional-if-has: AWS_ACCESS_KEY_ID
```

⇒ **`env.all` applies to EVERY env, test among them.** that is why no per-env edit in either
manifest would have prevented it, and why a reader who greps for `env.test` in the extends finds a
clean empty list and concludes the key cannot come from there.

🟡 **the `is-optional-if-has` clause is the second half.** the key is required only where
`AWS_ACCESS_KEY_ID` is absent from the process env — so the wall is **conditional on the host**, and
a box that exports static aws keys never sees it. that is one more reason it reads as intermittent.

so the chain is:

- a role this repo enrolls for *other* skills declares an aws credential, on the `env.all` axis
- `keyrack unlock --env test` unlocks the **union** of every extended manifest, `env.all` included
- the host rack holds no `AWS_PROFILE` and no `AWS_ACCESS_KEY_ID`, so the unlock reaches for an
  interactive browser SSO
- `git.repo.test` treats **any** unlock failure as fatal to the run
- ⇒ a browser SSO prompt gates a test tier that never reads a byte of aws

⚠️ **the evidence that the two are unrelated**: `--what integration` unlocked `ehmpath/test` and ran
green in the same session, minutes apart. only the acceptance path demanded the aws leg.

🔴 **the wall then widened.** measured 2026-09-18 on the same worktree, `--what integration` ALSO
exits 1 on it:

```
└─ ehmpathy.test.AWS_PROFILE
   ├─ status: errored 💥
   └─ aws sso login timed out: human did not respond to browser sso prompt
```

⇒ so the 2026-09-17 note above — that only acceptance demanded the aws leg — is a snapshot of one
session, not a property of the tiers. **both credential tiers are blocked locally.**

### 🟡 the discriminator, in one command

```
rhx keyrack status --owner ehmpath
```

- every env=test key shows minutes left, and **AWS_PROFILE is not listed at all** → this wall. the
  keys are fine; the requirement arrives by extends and has no host entry
- an env=test key shows expired → the ordinary case, self-fixable by an `unlock`

⇒ measured 2026-09-18: OPENAI / XAI / ANTHROPIC / FIREWORKS all at 536m, no AWS_PROFILE row.

### 🔴 the wall is PARTLY in this repo, and the repo's own config contradicts it

**measured 2026-09-20.** the acceptance bypass (`npm run test:acceptance:locally`, which skips the
`git.repo.test` wrapper) does **not** generalize to integration, because the demand there is not the
foreign skill's at all:

```ts
// jest.integration.env.ts:97 — this repo's own file
keyrack.source({ env: 'test', owner: 'ehmpath' });
```

`sourceAllKeysIntoEnv` defaults to `mode: 'strict'` and `process.exit(2)`s on any key that is not
granted and not waived. so **`npm run test:integration` fails on the aws leg with no wrapper in
sight** — a second, independent instance of the same defect, in a different bounded context.

🔴 **and the repo's own config says the credential is not needed.** the same env file computes
whether aws auth is required, from a declaration this repo makes:

```ts
// jest.integration.env.ts:45-52
const requiresAwsAuth = declapractUseContent.includes('awsAccountId');
if (requiresAwsAuth && !(process.env.AWS_PROFILE || process.env.AWS_ACCESS_KEY_ID))
  throw new Error('no aws credentials present. …');
```

```
rhx grepsafe --pattern 'awsAccountId|databaseUserName' --path declapract.use.yml  → 0 matches
```

⇒ `requiresAwsAuth` is **false**, so that guard is a **no-op** — the file's own considered answer is
*this repo needs no aws credential*. the `keyrack.source` call one paragraph below it then demands one
strictly anyway. **two gates in one file, on one question, and they disagree** — the stricter one wins
on the weaker evidence.

⇒ so a fourth fix candidate joins the three below, and it is the cheapest of all: **pass the fact the
file already computed.** the call should not strictly require the aws leg where `requiresAwsAuth` is
false. it needs an exclusion axis `sourceAllKeysIntoEnv` does not yet carry (its contract is
`env` · `owner` · `key?` · `reach?` · `mode?`), so the honest shape is a contract addition rather than
a blanket `mode: 'lenient'` — **lenient would hide a genuinely absent `ANTHROPIC_API_KEY`, which is
the failhide this repo forbids outright.**

### ⚠️ the org discrepancy, unresolved

both ghlitch manifests declare `org: ehmpath`, and the failure names `ehmpathy.test.AWS_PROFILE` — an
`ehmpathy` org, never `ehmpath`. so some layer rewrites the org between the manifest and the unlock.
**noticed, not diagnosed**; whoever takes this dream should settle it, since a fix aimed at
`ehmpath` may not reach the key that actually failed.

## .the shape of the fix

three candidates, cheapest first:

1. **degrade a failed unlock to a warn, and fail only when a test actually needs it.** the tier
   already fails loud on an absent credential at the point of use
   (`rule.require.failfast` — a `ConstraintError` that names the unlock command). so the pre-flight
   unlock is an optimization, and an optimization must not be a gate
   - ⚠️ must NOT become a silent skip (`rule.forbid.faked-or-quarantined-acceptance`) — print the
     credential that failed and the command that fixes it, then proceed
2. **scope the unlock to what the tier declares.** a `keyrack.yml` per test tier, or a
   `--credential` allowlist on the skill, so an acceptance run unlocks only what acceptance reads
3. **let the caller opt out**: `--keyrack skip` for a run the caller knows is credential-free
   - the weakest — it puts the judgment on every caller, every time

⇒ **(1) is the small, honest round**, and it generalizes: any credential from any extended role can
gate any tier today, and this will recur with a different credential.

## .why it is not done in this round

- the repair is to `git.repo.test`, a `role=mechanic` skill in **another repo** — a different
  bounded context from this wish (`v2026_09_11.fix-clone-say`, a clone-say read channel). a tree
  adopts only what is scoped to itself (`rule.always.scope-onetime-lessons-to-the-behavior`)
- it changes the failure semantics of the repo's most-used test command, which every driver leans
  on — that default is worth the wisher's eyes, not a ride-along
- its honest clamp needs its own dogfood: prove a tier runs green with one credential deliberately
  locked, AND that a test which needs it still fails loud

## .the workaround used in this round

none was needed for the tier itself — a later retry of the same command unlocked cleanly (the SSO
prompt was answered in the interim). so the cost paid here was one blocked run and a diagnosis,
never a bypass. the next driver may not be so lucky.

# domain.terms 🦉📜

this is the repo's **glossary** — one canonical word per concept, for the
**domain objects & operations declared in this repo**.

read it to learn what this repo calls things, and why.

## .what lives here

one folder-mate cluster per term (one word). each cluster has:

- `term=<x>._.choice._.md` — the chosen word, its kind (noun/verb/adj), its
  forbidden synonyms, and where it is used
- `term=<x>._.choice.reason.md` — why this word: etymology, any settled
  disputes, and the evidence behind the choice
- `term=<x>._.choice.example=<abc>.md` — a notable example of the term in use
  (optional, one file per example)

start with `._.choice._.md` for the quick answer; open `.reason.md` when you
want the full story.

## .the two rules

- `rule.require.domain-term-itemization` — every word that composes a declared
  domain object or operation gets a cluster here
- `rule.forbid.domain-term-synonyms` — contracts use the canonical term; if you
  believe a synonym is right, open a dispute rather than drift silently

### ⚠️ the synonym forbid binds VERBS, never result-state participles

a corpus grep for a forbidden synonym returns false positives, and one of them sits on a
**published `--json` contract**. before you file a blocker, check the part of speech:

> does the word sit where a **verb** goes (an operation name, a prefix), or where a **noun** goes
> (a result state, a status literal)? **the forbid binds the first only.**

the lived case: `asKeyrackDelReport` declares `effect: 'deleted' | 'not_found'`, which holds
`delete` — a forbidden synonym of the verb `del`. it **conforms**, because every result-state field
in this repo reports its outcome as a plain past participle, and not one is named for its
operation's prefix:

```
upsertFile.ts               → effect: 'UPDATED' | 'CREATED'      # never 'upserted'
findsertFile.ts             → effect: 'FOUND'   | 'CREATED'      # never 'findserted'
initKeyrackRepoManifest.ts  → effect: 'created' | 'found' | 'updated'
asKeyrackDelReport.ts       → effect: 'deleted' | 'not_found'
```

to "fix" that one would break the pattern, read as nonsense (`'delled'`), and break every `--json`
consumer — a real break, proposed to repair a violation that is not there.

## .what does NOT live here

**imported vocabulary.** a word this repo uses but does not coin belongs to whoever coined it:

- the four core verbs — `get` / `set` / `gen` / `del` — are defined by
  `rule.require.get-set-gen-verbs`, which ships from `rhachet-roles-ehmpathy`
- the same goes for `DomainEntity`, `IsoPriceWords`, `Role`, and any other dependency's term

⚠️ **the tell that you are about to over-reach:** you are about to itemize ONE member of an imported
set. if `del` gets a cluster while `get`/`set`/`gen` do not, a future traveler reads the asymmetry as
a gap and re-derives the answer — the exact drift this glossary exists to prevent.

what IS repo-born is the **repo-specific fact** you learned about that imported word. put it where
it belongs — an invariant in the term it addresses (`term=address`), a rule clarification (above),
or a brief — never a cluster for a word this repo did not coin.
